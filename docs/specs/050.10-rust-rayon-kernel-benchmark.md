## Goal

Determine whether a **small compiled Rust kernel** materially accelerates the numerical hotspot identified by 050.9, then determine how much additional gain comes specifically from bounded Rayon parallelism across independent Cells.

This child isolates two effects:

1. current Python/NumPy/pandas implementation -> equivalent **sequential Rust**;
2. sequential Rust -> the **same Rust kernel with 2/4-way Rayon**.

The result is benchmark evidence only. Do not wire the Rust candidate into normal production requests in this child.

## Entry condition from 050.9

Read 050.9 and its review first. It must identify at least one compact, stable, materially expensive array-oriented kernel worth testing.

If no such kernel exists, do not invent one. Record a no-go decision for native execution and hand that evidence to 050.11.

Candidate kernels may include only when measured as material:

- display-row selection/downsampling;
- contiguous run/segment classification;
- derivative rolling/smoothing;
- derivative gradient/postprocessing;
- finite-row/output-index generation;
- another compact numerical transform named by 050.9.

Ordinary consecutive Voltage-vs-Time may already have too little remaining transform work for Rust to matter. That is a valid outcome.

## Ownership boundary

Python remains owner of request/ORM/session lifecycle, source/protocol/provenance resolution, cache identity, normal Parquet orchestration, final result assembly and API serialization.

Rust owns only the measured numeric kernel:

```text
Python resolves compact numeric buffers
        -> one coarse Python/Rust call
             -> Cell A kernel
             -> Cell B kernel
             -> ...
        -> compact numeric/index outputs
        -> Python result/provenance assembly
```

Do not pass live SQLAlchemy state or a pandas object graph across the boundary. Prefer contiguous NumPy/Arrow-compatible numeric buffers and compact scalar descriptors.

## Locked decisions

1. **Sequential Rust before Rayon.** C1 vs C0 isolates native-code gain; C2/C3 vs C1 isolates Rayon gain.
2. **Same science.** Reproduce the current measured algorithm and operation semantics; no formula redesign.
3. **Measure the boundary.** Copies, dtype conversions, ownership transfer and output conversion count toward latency.
4. **Prefer borrowed/zero-copy numeric input when safe**, but report rather than assume it.
5. **No production integration.** A benchmark-only extension/build target is permitted.
6. **Bound Rayon to 1/2/4 workers** as applicable; never silently use all logical CPUs.
7. **Control nested native threading** and record PyArrow/NumPy/BLAS/Rayon settings.
8. **No whole-engine Rust port.** Reject a non-compact boundary rather than broadening scope.
9. **Keep ORM, SQLite, protocol planning and cache identity in Python.**
10. **Do not move Parquet reading into Rust by default.** 050.9 owns read-concurrency evidence; use identical resolved buffers unless that evidence explicitly identifies the read boundary itself as the experiment.
11. **No `CALC_VERSION`, migration or persistent-cache change** merely for equivalent native execution.
12. **No adaptive zoom, Plotly or cross-family work.**

## Build/binding choice

Re-inspect the current Windows/Tauri/Rust packaging setup before choosing PyO3, maturin or another binding route. The existing Tauri crate is not automatically the right home for a Python extension.

Use the smallest isolated arrangement that can build reproducibly, import from the backend, expose bounded worker controls and be removed cleanly if the candidate loses.

## Required ablation

### C0 — current Python reference

Measure the current implementation of the selected kernel on the same buffers used by Rust, both in isolation and in the representative backend context where practical.

### C1 — sequential Rust

Same kernel, forced to one native worker. Report separately:

- Python -> Rust preparation/conversion;
- borrowed vs copied input and copied bytes;
- Rust kernel time;
- Rust -> Python conversion;
- complete boundary wall time.

C1 vs C0 is the native-execution result.

### C2 — Rust/Rayon, 2 workers

Identical algorithm/boundary, two-way cross-Cell native execution.

### C3 — Rust/Rayon, 4 workers

Same with four workers.

C2/C3 vs C1 is the parallel-Rust result. Do not attribute C0 -> C3 entirely to Rayon.

## Cold and warm lifecycle

Measure separately:

- extension/module load if material;
- first Rust function call;
- first parallel call including lazy Rayon-pool initialization;
- steady-state warm calls;
- resident-memory change.

Do not hide one-time initialization in warm medians, but do not repeatedly charge it to every interaction either.

## Workloads

Use the 050.9 scenarios that actually exercise the chosen kernel rather than repeating the entire earlier matrix. Include at minimum:

- single-Cell control;
- representative 3/6-Cell case;
- 10-Cell case when relevant data permit;
- narrow/small-work case to expose crossing overhead;
- for a derivative kernel, the broad derivative cases identified by 050.9.

Use identical inputs/settings across C0-C3.

## Measurements

For every applicable C row record:

- full representative backend wall time where measurable;
- isolated kernel wall time;
- Python/native conversion/copy time;
- borrowed/copy status and copied bytes;
- Rust kernel time;
- Rayon queue/parallel-region time;
- worker count;
- CPU/effective cores;
- peak RSS/temporary allocation estimate where measurable;
- compiler profile/target and relevant build flags;
- native-thread settings;
- cold first-call and warm-call timings;
- scientific parity metrics;
- deterministic ordering.

Use at least five warm repetitions where practical and report median plus range/tail; keep cold timings separate.

## Scientific parity

For exact selection/index/downsampling operations, require exact canonical output and provenance equality.

For floating-point kernels:

- preserve current mathematical algorithm and operation semantics;
- use existing repository scientific/golden tolerances, not a new relaxed Rust tolerance;
- report maximum absolute and relative deviation;
- require identical finite/non-finite placement, segmentation, Cell ordering and provenance;
- preserve thresholds, sign rules and filter ordering.

Record bit-for-bit equality when achievable. If ordinary floating implementation details prevent bit identity while existing scientific tolerances are satisfied, state that explicitly.

A faster kernel with changed accepted science is rejected.

## Required decision

Record separately:

1. sequential native gain: C1 vs C0;
2. Rayon gain: C2/C3 vs C1;
3. Python/native boundary cost;
4. cold-start/build feasibility;
5. memory/oversubscription impact;
6. smallest useful Rayon worker count, if any.

Possible results: no Rust justified; sequential Rust only; Rust + 2-way Rayon; Rust + 4-way Rayon; or reject despite speed because boundary/build/memory/scientific cost is unacceptable.

050.11, not this child, selects the complete execution architecture.

## Acceptance criteria

- Kernel choice comes from 050.9 evidence.
- C0/C1/C2/C3 are separated whenever Rust proceeds.
- Boundary copy/conversion and cold/warm lifecycle are measured.
- Scientific parity passes existing repository criteria.
- No normal request is switched to Rust/Rayon.
- No migration, `CALC_VERSION`, persistent cache, saved/export or frontend behavior changes.
- 050.11 receives a clear statement of which native mechanism, if any, survived independently.

## Verification

Run focused Python/scientific tests affected by the benchmark adapter and isolated Rust kernel tests. If production scientific/service code is touched, run the golden corpus. Before handoff:

```text
git diff --check
python scripts\preflight.py
```

If a Rust candidate survives the local performance gate, run the smallest current Windows build/import smoke check needed to support a packaging-feasibility claim. Otherwise record it as NOT RUN.

## Out of scope

- production Python executors or multiprocessing;
- scientific algorithm changes;
- broad Rust rewrite;
- adaptive zoom / 050.P4;
- Plotly trace consolidation;
- progressive streaming / 050.P2;
