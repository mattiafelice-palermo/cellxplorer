## Locked user-acceptance decisions

### 1. Three-zone desktop layout

At normal desktop width, the navigation strip must have three visual zones:

```text
LEFT                         CENTER                                                     RIGHT
[Previous view] [Home]       Cycle navigation [window] [«|‹] [from] [—o—] [to] [›|»]  Jump to [cycle]
```

Requirements:

- `Previous cycle view` and `Show all cycles` belong on the **left**.
- `Jump to [cycle]` remains on the **right**.
- The main cycle-navigation cluster is **visually/geometrically centered in the available strip**, not merely placed between side groups by ordinary `space-between` flex behavior.
- The center should stay centered even if the left and right side groups have different widths. Use a three-zone/grid/absolute-centering pattern or equivalent robust Mantine/CSS layout rather than allowing side content to push the center off-axis.
- At normal desktop analysis width, the **entire center cluster must remain on one horizontal line**. The `› | »` group must never drop below the rest of the navigation controls.
- Do not use internal wrapping of the center cluster as the normal responsive strategy. If a genuinely narrower supported width requires a second row, move/wrap the center cluster as a whole; keep its own controls together on one line.
- Do not overlap or clip controls.

### 2. Arrow-button height

The backward and forward segmented arrow controls must have the **same visible height as the From/To numeric inputs**.

- Preserve the merged/split-button appearance and internal divider.
- Use the same compact control size/height contract as the adjacent numeric inputs rather than a visibly shorter icon-button geometry.
- Do not increase the whole toolbar height unnecessarily.

### 3. Back/Home position

The Previous View arrow and Home icon must sit together at the left of the main centered navigation cluster. They must no longer appear between the center cluster and `Jump to`.

All existing history/Home semantics, disabled states, Tooltips, and accessible names remain unchanged.

### 4. Hover slider callout anchored to the separator

The line-dot-line control between `From` and `To` remains the cycle-window positioning trigger.

The current detached/top-left behavior is a defect. The slider container must be spatially attached to that trigger.

Locked presentation:

- hovering the line-dot-line trigger opens the slider callout;
- the callout is centered on the trigger and appears **above it**, matching the user reference: a compact near-rectangular panel with only lightly rounded corners and a small centered **downward triangular pointer** that visually stems from the panel to the separator trigger;
- do **not** use highly rounded/pill-shaped callout borders;
- use Mantine/theme tokens and the app's light/dark chrome rather than fixed white/black styling;
- the callout body contains only the existing horizontal Slider concept; no mini timeline, histogram, labels, protocol markers, or other content;
- the separate `Move cycle window` Tooltip must not compete with or cover the hover slider callout. Keep an accessible name, but hovering this trigger should primarily reveal the slider callout.

Interaction requirements:

- the callout opens on pointer hover over the trigger;
- it must remain open while the pointer moves from the trigger into the callout so the slider can actually be dragged;
- use a small close delay or equivalent hover-region handling to avoid flicker when crossing the trigger-to-panel gap/arrow;
- leaving both trigger and callout closes it and discards uncommitted transient thumb state as in parent Spec 052;
- keyboard accessibility is retained: the trigger remains focusable, and focus/keyboard activation must provide access to the slider even though hover is the primary pointer interaction;
- Escape closes the callout;
- slider `onChange` remains transient and `onChangeEnd` performs exactly one canonical range commit/history step.

Anchoring requirement:

- the callout must never fall back to viewport `(0,0)` / top-left positioning;
- ensure the positioning target is a single stable ref-capable DOM/Mantine element (for example an `UnstyledButton`/button-like target) rather than a Fragment or wrapper that cannot provide the Popover/Floating UI reference;
- if a Portal is used, it must still anchor correctly to the separator target.

### 5. Jump stays right

Keep the current `Jump to` label and integer input on the right side. Do not move it into the centered cluster.
