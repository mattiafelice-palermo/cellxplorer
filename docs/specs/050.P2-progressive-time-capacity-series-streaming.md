# Proto-child 050.P2: progressive Time/Capacity series streaming

Status: **Proto-child — non-implementable until promoted**  
Parent: [`050-runtime-performance-optimization.md`](050-runtime-performance-optimization.md)  
Branch: `feature/runtime-performance-optimization`  
Repository baseline / merge base with `main`: `1dc3525ec42571504ed6d9bdb9a0668d35df309b`  
Origin: user-requested perceived-latency improvement for multi-series Time/Capacity plots  
Promotion timing: **after 050.7 is review-clean and post-050.7 multi-series behavior is measured**

## 1. Why this proto-child exists

Time/Capacity currently computes a multi-series result Cell-by-Cell, but the live frontend receives
only one complete `TimeCapacityResult` after every selected series has finished. On a slow
multi-series cache miss, the user therefore waits for the slowest/final series before any data from
the new request can be shown.

The proposed UX is progressive delivery:

```text
request starts
    ↓
series 1 complete ──────────→ render series 1
series 2 complete ──────────→ render series 1 + 2
series 3 complete ──────────→ render series 1 + 2 + 3
...
final metadata complete ────→ mark the plot complete
```

This does **not** aim to reduce scientific compute time. Its primary metric is **time to first useful
plot**. If total computation still takes 2 seconds but the first correct series becomes visible at
300 ms, the interaction should feel substantially faster without changing any calculation.

This is a plausible fit for the current implementation because `compute_time_capacity()` already
has a natural per-unit completion boundary: it loops over resolved analysis units, constructs one
complete trace, appends it to `traces`, and reports progress before moving to the next unit.

The proposal remains a proto-child because two things must be verified before implementation:

1. whether post-050.7 multi-series latency is still large enough for progressive display to be
   worthwhile; and
2. whether the packaged Windows/Tauri WebView2 path delivers `fetch()` response chunks promptly
   rather than buffering them until the response closes.

## 2. Verified current behavior

### 2.1 Frontend request boundary

`frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`

Current anchors:

```text
TimeCapacityPlotCardView(...)
dataSignature
compatibilitySignature
useQuery(["time-capacity", analysisId, compatibilitySignature, dataSignature])
post<TimeCapacityResult>(`/api/analyses/${analysisId}/time-capacity`, ...)
currentResult
exportTraces
traces
layout
plotExportReady
loadingWithoutResult
completeTimeCapacityProfile()
```

The React Query `queryFn` awaits one JSON response. Until that promise resolves, the component may
show a scientifically compatible previous result through `placeholderData`, but it cannot show
new-request series that have already finished on the backend because those traces have not crossed
the HTTP response boundary.

The plot is then built from the complete `result.cell_traces` collection through:

```text
timeCapacityTracesForResult(...)
timeCapacityLayout(...)
interactivePlotTraces(...)
<Plot ... />
```

### 2.2 Generic frontend API client

`frontend/src/api.ts`

Current anchors:

```text
apiUrl(...)
request<T>(...)
post<T>(...)
```

`request<T>()` calls `fetch()` and then `res.json()`. There is no incremental response-body reader.
A future promoted child would need a small fetch-stream helper that reads `Response.body` through a
`ReadableStream`, decodes UTF-8 incrementally, handles arbitrary chunk boundaries, and supports the
existing `AbortSignal` contract.

This transport helper belongs in the shared API layer only if it remains generic. Time/Capacity
progressive state and scientific result assembly remain owned by the Time/Capacity feature.

### 2.3 Backend route and cache boundary

`backend/app/routers/analyses.py`

Current anchors:

```text
compute_time_capacity_analysis(...)
_profiled_time_capacity_response(...)
_open_compute_job(...)
_progress_callback(...)
```

`compute_time_capacity_analysis()` currently:

```text
resolve Analysis/spec
-> validate canonical cycling capability
-> compute source_data_signature + result cache key
-> exact persisted result-body cache hit: return complete JSON bytes
-> otherwise call engine.compute_time_capacity(...)
-> store one complete Time/Capacity result
-> return one complete JSON response
```

The exact persisted cache-hit path is intentionally fast and must remain so. Progressive delivery
is a cache-miss UX optimization; it must not replace the normal exact-result fast path with a slower
per-series reconstruction.

### 2.4 Natural backend series boundary

`backend/app/services/analysis_engine.py`

Current anchor:

```text
compute_time_capacity(...)
```

The function resolves the selection and then iterates:

```text
for unit_index, unit in enumerate(units, start=1):
    ...
    # source planning / selective raw reads
    # exact transforms / prepared-derived reuse
    # protocol masking / downsampling / projection
    traces.append({ complete TimeCapacityTrace })
    progress(unit_index, total_units, ...)
```

Only after the loop does it finalize selection-wide fields such as:

- parser/current parser versions;
- calculation/current calculation versions;
- accumulated badges;
- data-driven selection-wide voltage-channel availability/roles/references;
- aggregate rendering metadata and total returned points.

This means the per-series trace itself can become available earlier than the final selection-wide
metadata, but the current synchronous function does not yield control to the HTTP response while the
loop is running.

## 3. Product goal

For a **multi-series interactive Time/Capacity cache miss**, show completed series progressively as
soon as they can be delivered safely, while the remaining series continue to compute.

The interaction should feel like:

```text
old compatible plot (optional, dimmed)
        ↓ first new series arrives
new-request partial plot: 1 of N series
        ↓
2 of N series
        ↓
...
        ↓
N of N series / final metadata / normal complete plot
```

Suggested compact status text:

```text
2 of 6 series loaded · calculating…
```

This is deliberately a quiet progress cue, not a modal or large overlay. It inherits the visual
style guide: compact `xs`/dimmed feedback, stable plot geometry, light/dark-safe chrome, and no
color-only state.

## 4. Locked scientific and UX principles if this is promoted

These principles are already clear enough to preserve even while the exact transport remains
provisional.

1. **No scientific change.** Streaming changes when complete trace objects reach the client, not how
   raw rows, cycles, phases, capacities, derivatives, protocol masks, downsampling, voltage channels,
   provenance, or exports are calculated.
2. **No parallel Cell compute in this feature.** Keep the existing deterministic unit order and
   backend compute semantics. Progressive delivery is not permission to introduce concurrent
   scientific computation.
3. **Never mix old-request and new-request data in one plot.** A compatible previous result may stay
   visible until the first new-request series arrives. Once progressive rendering begins, the plot
   contains only series belonging to the new request identity.
4. **Partial data is never a completed scientific result.** It must not enter the React Query cache,
   persisted analysis-result cache, saved-plot artifacts, thumbnails, portable reports, or exports.
5. **Exports remain complete-only.** Plot/image/vector export, export preview, data export, saved-plot
   creation/update, and any other artifact-producing action remain disabled while the live result is
   partial.
6. **Exact persisted result-cache hits stay one-shot and fast.** Do not stream/recompute one Cell at
   a time when the complete exact result already exists.
7. **The final assembled result must equal the ordinary complete endpoint result.** Progressive
   framing may differ, but the completed `TimeCapacityResult` supplied to the rest of the frontend
   must preserve the existing result contract and scientific values exactly.
8. **Selection-wide voltage capability does not flicker progressively.** The current voltage-channel
   availability/role/reference summary is finalized across the full selection. Do not publish
   provisional `false -> true` or single-role -> mixed-role transitions into the selector as Cells
   arrive. Keep the previous/unknown capability UI until the final metadata event.
9. **Canonical series order is stable.** Emit and render in the same resolved unit order used today
   so line colors, legend order, group identity and user expectations do not move as later series
   arrive.
10. **User zoom must survive later partial arrivals where the existing zoom-memory contract allows
    it.** A user who zooms after series 1 appears should not have that zoom reset by series 2.
11. **A failed stream is not a successful partial analysis.** On terminal error, discard the partial
    new result. If a compatible previous complete result exists, return to it and show the error;
    otherwise clear the partial plot and show the existing error state.
12. **Cancellation remains identity-safe.** Switching range/settings/selection aborts the fetch and
    immediately makes every later event from the obsolete request ineligible for display. This
    proto-child does not claim that aborting the browser fetch can interrupt synchronous work inside
    an already-running Cell calculation.
13. **One-Cell interactions should not pay repeated Plotly churn for no UX benefit.** A promoted
    implementation should either retain the ordinary endpoint for one resolved series or suppress
    partial rendering until the one-series result is final.
14. **No forced Time/Capacity frontend modularization.** The feature may add a small shared streaming
    transport helper, but file length alone is not justification for splitting the analysis-family
    component.

## 5. Preferred transport direction — provisional, to validate before promotion

### 5.1 Prefer one streamed POST, not N per-Cell HTTP requests

Do **not** implement progressive display by splitting a six-series analysis into six independent
Time/Capacity requests unless later investigation proves the single-stream model infeasible.

Per-Cell fan-out would complicate or duplicate:

- analysis-result cache identity;
- analysis selection/group semantics;
- selection-wide voltage-channel capability;
- source/provenance finalization;
- background-job ownership;
- cancellation and error aggregation;
- persisted exact-result cache behavior.

The preferred model is still one analysis request and one backend calculation, with incremental
result delivery over that single response.

### 5.2 Preferred framing: fetch + NDJSON

A dedicated streaming response or an explicit streaming mode should use ordinary `fetch()` response
streaming with newline-delimited JSON (NDJSON). WebSockets are unnecessary; browser `EventSource`
is awkward for the existing POST-with-body contract.

A provisional miss stream could look like:

```json
{"type":"start","stream_version":1,"request_id":"...","total_series":6,"data_signature":"...","source_data_signature":"...","cache_status":"miss"}
{"type":"series","index":1,"total_series":6,"trace":{"cell_id":17,"...":"..."}}
{"type":"series","index":2,"total_series":6,"trace":{"cell_id":23,"...":"..."}}
{"type":"series","index":3,"total_series":6,"trace":{"cell_id":42,"...":"..."}}
{"type":"complete","metadata":{"computed_at":"...","voltage_channels":{},"rendering":{},"badges":[]}}
```

The exact fields are **not locked while this is a proto-child**. A promoted child must define the
complete typed schema.

The important shape is:

- each `series` event carries one final `TimeCapacityTrace` exactly once;
- the final event carries only selection-wide metadata, not a second copy of all traces;
- the frontend assembles the final `TimeCapacityResult` from the ordered trace events + final
  metadata;
- therefore a cache-miss stream does not double the scientific payload merely to provide partial
  rendering.

For an exact persisted cache hit, the backend may emit one complete-result event containing the
existing spliced cached result body. The promoted design should preserve the current no-parse/
no-recompute fast path where practical rather than decoding the stored payload only to reframe it.

### 5.3 Stream protocol version is transport-only

If implemented, use a small independent stream-protocol version such as `stream_version: 1`.
Changing NDJSON framing is not a scientific calculation change and must not bump `CALC_VERSION`,
parser identity, canonical raw version, prepared-derived generation, analysis cache generation, or
Time/Capacity result-schema version unless the actual completed scientific result contract changes.

## 6. Backend execution-shape question that must be resolved before promotion

The current `compute_time_capacity()` function is synchronous. Adding an optional callback alone is
**not enough** to stream: the callback can observe that a Cell finished, but the HTTP generator still
cannot yield bytes until the synchronous function returns.

Do not solve that by passing the request-owned SQLAlchemy `Session` into an ad-hoc producer thread.
SQLAlchemy sessions are not a cross-thread work queue, and this repository deliberately avoids
sharing request sessions across workers.

The preferred implementation direction to investigate is a small internal iterator/event boundary:

```text
shared Time/Capacity setup
-> compute next resolved unit using today's exact code
-> yield complete trace + unit facts
-> compute next unit
-> ...
-> yield/finalize selection-wide metadata
```

Then:

- ordinary `compute_time_capacity()` consumes the iterator and assembles the same dict it returns
  today;
- the streaming route consumes the same iterator but sends each completed trace before continuing;
- there is one scientific implementation, not a streaming fork.

This does imply a coherent extraction from the existing large function. A promoted spec must inspect
the then-current 050.7+ implementation and define the smallest safe extraction rather than broadly
refactoring `analysis_engine.py` for style.

A producer-thread + bounded queue with a **separate** `SessionLocal` is a possible fallback only if
iterator-based response generation is infeasible in FastAPI/Starlette. It is not the default because
it adds database-session and worker-lifecycle complexity solely for perceived latency.

## 7. Frontend state model to evaluate

A future implementation should keep React Query as the owner of **complete** backend state and use
small ephemeral component state for the in-flight progressive result.

Conceptually:

```text
React Query
    previous complete result / final completed result

local progressive state, keyed by request identity
    stream_request_id
    total_series
    completed trace map/list
    status = starting | partial | complete | error
```

Suggested behavior:

1. start the query and keep a compatible previous complete result visible through the existing
   placeholder policy;
2. receive `start`, record total series, but keep the old complete plot until real new trace data
   exists;
3. receive the first `series` event, switch the visible plot entirely to the new-request partial
   result;
4. accumulate later series in canonical order;
5. receive final metadata, construct the complete `TimeCapacityResult`, let the query promise resolve,
   and clear ephemeral progressive state;
6. React Query stores only that final result.

Every event must be checked against the current `dataSignature` / request generation before it can
change visible state. A stale stream must be harmless even when its HTTP connection closes late.

## 8. Plotly update policy

Progressive rendering can reduce perceived latency only if repeated Plotly updates do not erase the
benefit.

The first implementation should remain simple:

- rebuild the Time/Capacity traces/layout from the currently completed `cell_traces` using the same
  existing builders;
- do not introduce a second incremental Plotly-trace builder unless measurement shows the normal
  React/Plotly update path is too expensive;
- coalesce very closely spaced series events (for example one render per animation frame or a short
  bounded interval) so a fast 25-series result does not force 25 redundant full Plotly updates;
- flush the first useful partial and final result promptly;
- preserve the existing stacked/flat remount rule and zoom-memory behavior.

Because the backend currently computes in canonical order, existing color assignment should remain
stable as the partial trace array grows. A future parallel backend would need explicit canonical
sorting before render; backend parallelization is outside this proto-child.

## 9. Partial-result UI behavior

When progressive mode is active and at least one new-request series is visible:

- show the partial plot at normal readability rather than dimming it as stale placeholder data;
- show a compact status such as `2 of 6 series loaded · calculating…`;
- retain existing Activity/background-job reporting independently;
- do not show the large center loading state once a partial plot is useful;
- keep controls and plot geometry stable;
- keep exports/artifact actions disabled until final completion;
- on final completion, remove the progress text without a layout jump.

Do not use animation, skeleton lines, guessed final axis ranges, or placeholder traces for series that
have not arrived.

If Plotly auto-ranging expands as later real series arrive, that is preferable to fabricating a
final range via a preliminary full-data pass. Explicit user zoom should remain governed by the
existing zoom-memory policy.

## 10. Selection-wide metadata and partial rendering

The final Time/Capacity result owns facts that are not complete after the first Cell:

- `badges`;
- `voltage_channels` availability/role/reference;
- parser/current parser display identity across the contributing sources;
- aggregate `rendering.total_points`;
- final `cache_status`, `data_signature`, and `source_data_signature`.

A partial render must not pretend these are final. The promoted stream schema should therefore send
only the per-series data needed to plot completed series, and publish these selection-wide fields in
the terminal completion event.

The currently selected voltage quantity is already part of the request. A completed trace may be
rendered for that requested quantity before the selector's selection-wide availability summary is
final, but the selector itself must keep its previous/unknown capability state until completion.

## 11. Cache and persistence consequences

If promoted as described:

- no SQLite migration;
- no `CALC_VERSION` bump;
- no parser or canonical cycling version change;
- no raw-layout or prepared-derived generation change;
- no new persistent partial-result cache;
- existing `analysis_cache.result_key(..., "time_capacity", ...)` remains the scientific/result
  identity;
- exact persisted hit behavior remains the preferred reopening path;
- on a miss, store the ordinary complete Time/Capacity result only after every unit and final
  selection-wide field have completed successfully;
- an interrupted/failed stream must never store a partial result under the complete result key.

The final cache entry produced by a streamed miss must be reusable by the existing ordinary complete
endpoint and saved-preview/export paths.

## 12. Errors and cancellation

### Error before response streaming starts

Keep normal HTTP error behavior where possible: capability/Analysis/request validation failures
should be reported before beginning the NDJSON body.

### Error after one or more series have been emitted

Once a `200` streaming response has started, HTTP status cannot be changed. The stream therefore
needs a terminal typed error event carrying the same safe user-facing detail that the ordinary route
would expose.

Frontend behavior:

```text
partial new-request series
-> terminal stream error
-> discard partial result
-> restore compatible previous complete result if one exists
   OR show the normal empty/error state
-> display the error
```

Never leave a partial plot looking complete after a terminal error.

### User changes request while streaming

The existing React Query `AbortSignal` remains the client cancellation trigger. The frontend must
invalidate the stream generation immediately so late chunks cannot render.

The promoted child must investigate what Starlette/Uvicorn and packaged WebView2 do on connection
abort and make the background compute job terminal correctly. Do not claim that browser abort can
interrupt the pandas/NumPy work already executing inside one Cell unless cooperative backend
cancellation is explicitly implemented and tested.

## 13. Profiling implications

The existing 050.4 profiler treats one HTTP response and one final Plotly callback as the interaction
boundary. Progressive delivery introduces a second user-relevant metric: first useful plot.

If this proto-child is promoted, adapt the profiler without changing ordinary scientific payloads so
a streamed interaction can distinguish at least:

- request start;
- first series bytes received;
- first partial frontend preparation;
- first partial Plotly completion;
- final series received;
- final metadata received;
- final Plotly completion;
- number of partial plot renders;
- total series;
- cache hit/miss.

The key product comparison is:

```text
old time-to-first-useful-plot ≈ old total interaction
new time-to-first-useful-plot = first partial Plotly completion
new final total interaction = final Plotly completion
```

Do not declare success merely because the backend emitted a chunk early; the first partial must
actually paint in the installed application.

## 16. Promotion criteria

Promote this proto-child only when all of the following are true:

1. **050.7 is implementation-complete and review-clean.** Re-profile the then-current code rather
   than assuming pre-050.7 derivative timing still applies.
2. A representative installed-app multi-series matrix shows a meaningful gap between first-series
   backend completion and final plot completion, or otherwise demonstrates that time-to-first-useful
   plot is worth optimizing after the direct compute optimizations.
3. A small packaged Windows/Tauri WebView2 feasibility probe demonstrates that response chunks from
   the local FastAPI sidecar become observable through `fetch().body` before the response closes.
4. Current cache-hit timing is rechecked so the streaming design does not degrade the already-fast
   exact-result reopen path.
5. The then-current `compute_time_capacity()` is re-inspected and the safe shared iterator/yield
   boundary is explicitly designed; no duplicate scientific implementation is accepted.
6. Replicate-group / resolved-unit semantics are confirmed so the UI progress noun and count are
   truthful (`series`, not blindly `selection entries`).
7. The promoted numeric child defines the exact stream event schema, frontend partial-state machine,
   error/cancellation behavior, profiler changes, and packaged-browser verification.
8. The promoted child sets evidence-based timing acceptance thresholds from the post-050.7 baseline,
   rather than inheriting a guessed number from this proto spec.

## 17. Future promoted-child verification shape

The eventual numeric child should include, at minimum:

### Backend automated verification

- stream cache hit returns one complete result without scientific recomputation;
- multi-series miss emits `start`, canonical ordered series events, and exactly one terminal
  completion;
- each emitted trace is byte/value-equivalent to the corresponding trace in the ordinary complete
  result;
- assembling all stream events produces the same completed scientific result as the ordinary route;
- incomplete/error stream never stores a result under the complete analysis-cache key;
- successful stream stores one ordinary complete result that the non-streaming route can reuse;
- selection-wide badges/voltage capability/rendering metadata match the ordinary route;
- one-series path does not incur unnecessary progressive behavior;
- result/cache/parser/scientific versions remain unchanged unless the completed result contract
  genuinely changes.

### Frontend automated verification

- NDJSON parser handles one line split across multiple chunks, multiple lines in one chunk, and UTF-8
  multi-byte characters split across chunk boundaries;
- `AbortSignal` terminates reading and stale-generation events cannot update state;
- partial traces are never written to React Query as final query data;
- old compatible placeholder and new partial data are never merged into one result;
- canonical order/color identity remains stable as traces accumulate;
- exports and artifact/save actions stay disabled while partial;
- terminal success promotes exactly one complete result;
- terminal error discards partial state and restores the correct previous/error presentation;
- closely spaced events are coalesced so render count remains bounded.

### Performance verification

Use the same machine/data for streamed and ordinary control runs, with repeated measurements. Record:

- total resolved series;
- cache status;
- time to first backend series completion;
- time to first series bytes;
- time to first partial Plotly completion;
- final backend completion;
- final Plotly completion;
- number of Plotly partial updates;
- total response bytes;
- ordinary/non-streaming control total.

The first useful plot must improve materially, while final completion must not regress materially due
to repeated frontend rendering. If the latter regresses, fix event/render batching before claiming
the feature successful; do not change science to hit the timing target.

### Manual packaged-app verification

This feature specifically depends on streaming behavior in the desktop browser runtime, so the
promoted child must include an installed Windows/Tauri check covering:

- multi-series cold/result-cache-miss progressive appearance;
- truthful `N of total series loaded` progress;
- range change while streaming, proving obsolete traces never appear;
- user zoom while more series arrive;
- final legend/color/order stability;
- cache-hit reopen showing the complete plot immediately;
- stream error presentation if a controlled test hook/fixture can exercise it safely;
- light and dark chrome for the progress cue;
- export/save actions unavailable until the result is complete.

Browser/manual results must be recorded as actually run or not run; they cannot be inferred from
unit tests.
