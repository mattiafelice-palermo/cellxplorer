## Goal

Make fresh Time/Capacity range changes behave more like navigation through prepared scientific data by eliminating two measured forms of repeated work:

1. **Do not calculate derived capacity vectors that the current compact view does not consume.** In particular, a compact Voltage/Current-vs-Time request currently reconstructs phase capacity, specific capacity and areal capacity even though those arrays are not returned or used by that view.
2. **Reuse exact source-derived phase/capacity values instead of reconstructing them from raw counters for every cache-miss range request.** The expensive `_phase_capacity()` result is invariant for a validated source row once the parser/scientific identity is fixed, so it may be stored as a regenerable performance sidecar and selectively read together with the already cycle-addressable raw cache.

This child is an **exact optimization**. It must not approximate scientific rows, change derivative mathematics, change Plotly trace architecture, introduce a multiresolution overview, or alter any user-visible scientific value.

The intended post-050.6 interaction is:

```text
compact Time-axis Voltage/Current miss
    -> selective raw read
    -> prepared phase when available
    -> continuous-time + protocol/display work actually required
    -> NO phase-capacity/specific/areal reconstruction
    -> bounded response

compact Capacity-axis / derivative miss
    -> selective raw read
    -> selectively read exact prepared phase + phase-capacity when available
    -> request-specific normalization / derivative / protocol / display work
    -> bounded response

prepared sidecar unavailable / invalid / busy
    -> current exact request-side phase/capacity calculation
    -> identical scientific result
```

| 1–20 | 1 | 10,611 | 18.8 ms | 3.5 ms | 49.0 ms | 155.7 ms |
| 1–150 | 1 | 56,044 | 31.8 ms | 12.0 ms | 260.9 ms | 471.4 ms |

050.5 also proved from current consumers that a compact `view="voltage_current"`, `x_axis="time"` request does not consume reconstructed phase capacity, specific capacity or areal capacity, although the current engine eagerly calculates all three.

The user's real installed-app 050.4 recording showed the same scaling: broad/multi-Cell HTTP interactions were dominated by backend work, while exact React Query memory revisits were already about 20–50 ms. Therefore another browser cache, speculative prefetch, JSON redesign or Plotly rewrite is not the first normal-view optimization.

050.5 separately found that dQ/dV has a different hotspot: post-gradient per-segment cleanup/statistics dominates backend derivative work and broad views create hundreds of Plotly traces. That derivative-specific optimization is deliberately **not** part of 050.6.

## Locked decisions

1. **Scientific outputs are byte/number equivalent after normalizing volatile metadata.** This child changes when/where exact values are derived, not their meaning.
2. **No approximation.** Complete selected cycles remain the scientific input. Do not downsample raw rows before phase, capacity, derivative or protocol logic.
3. **Canonical raw Parquet remains the one raw dataset.** The new prepared artifact may store only small regenerable derived vectors plus the minimum identity/alignment fields needed to validate them. Do not copy voltage/current/status/raw capacity counters into a second Time/Capacity raw dataset.
4. **Use one implementation of phase/capacity science.** Cache preparation and request fallback must call the same phase-classification and phase-capacity logic. Extract those helpers to a focused backend module if needed; do not duplicate formulas.
5. **Prepared phase/capacity is source-local where parity proves that source-locality is sufficient.** Dense global cycle relabeling is a bijection over source-local cycle labels and does not change the `(cycle, phase)` reconstruction groups. Continuation parity must prove this before the prepared path is accepted.
6. **Do not persist continuous time in 050.6.** 050.5 measured continuous-time reconstruction as small relative to phase capacity, while its range-relative reset/rebasing semantics are more sensitive to selected-range/source boundaries. Keep it request-side and simply skip it when the compact request does not consume time.
7. **Specific/areal capacity remains request-derived from exact absolute phase capacity.** Active-mass, electrode-area and user area override state must not become baked into the source-local sidecar.
8. **Prepared data is optional performance state, never scientific completeness.** Missing, stale, corrupt or currently-being-prepared derived data must fall back immediately to the current exact calculation. No badge/error should imply that the Cell's science is missing merely because the optimization sidecar is absent.
9. **No request-path preparation wait.** The live Time/Capacity request must not block on an in-progress derived-cache build. Use a non-waiting consistency boundary analogous to 050.3 raw-layout fallback.
10. **Preparation is cache-bytes-first.** Existing valid raw caches can prepare the derived sidecar without opening/reparsing the original source, including when the source is offline.
11. **A deliberately cleaned source cache is not recreated solely for this optimization.** The preparation predicate may act only when the relevant raw cache already exists or when a normal cache build is already occurring.
12. **Full-resolution export remains exact and complete.** It may reuse validated prepared phase/capacity values, but no response fields/rows may be omitted relative to the existing full non-compact path.
13. **Protocol masking, source provenance, continuation order, hidden/excluded sample semantics, voltage-channel availability and all existing badges remain unchanged.**
14. **No `CALC_VERSION` bump.** The phase/capacity formula is unchanged. The prepared representation gets its own cache-format generation and includes the current `CALC_VERSION` in its identity.
15. **No parser, canonical raw, raw-layout, result-schema or analysis-result generation bump solely for 050.6.** Ordinary result payload shape and cache keys remain unchanged.
16. **No SQLite migration.** Prepared-artifact state lives in the regenerable cache filesystem and is discoverable from cache metadata, not relational rows.
17. **Scientific-cache budget/cleanup remains authoritative.** New files stay under the existing checksum directory, count toward the scientific cache budget, participate in access/LRU touches, and disappear with the checksum directory.
18. **No whole-Cell RAM residency requirement, general LRU, neighbour prefetch, frontend change or new telemetry.**
19. **Do not optimize dQ/dV postprocessing or Plotly traces here.** Prepared phase/capacity may feed the unchanged derivative algorithm, but derivative-specific optimization is a later independent child only after 050.6 review.
20. **Do not implement proto-child 050.P1.**
21. Never modify, reset or discard unrelated branch work.

## Part A — dependency-aware transform plan

Before calculating derived arrays for one Cell, resolve the minimum exact transform set needed by the current request.

The implementation may use a small internal dataclass/typed structure such as `TimeCapacityTransformNeeds`, but the following behavior is required:

| Request contract | Continuous time | Phase | Absolute phase capacity | Specific capacity | Areal capacity |
| --- | --- | --- | --- | --- | --- |
| compact Voltage/Current + Time axis | required | required | **not required** | **not required** | **not required** |
| compact Voltage/Current + `capacity_mah` | not required | required | required | not required | not required |
| compact Voltage/Current + `capacity_mah_g` | not required | required | required | required | not required |
| compact Voltage/Current + `capacity_mah_cm2` | not required | required | required | not required | required |
| compact dQ/dV or dV/dQ, absolute capacity | not required | required | required | only when derivative-specific is enabled | not required |
| full/non-compact scientific response/export | required | required | required | required | required |

The existing response still emits `phase`, so phase classification remains required for compact normal views. Source provenance/boundaries and trace metadata remain separately required by the existing response contract.

### Part A acceptance details

- A compact Time-axis Voltage/Current request must not call `_phase_capacity()` at all, even when the prepared sidecar is absent.
- It must not allocate full-length specific/areal arrays merely to later emit `[]`.
- Compact capacity/derivative requests must not call `_continuous_time()` when no returned/displayed value consumes it.
- Full/non-compact behavior stays on the complete exact contract.
- No placeholder zeros/NaNs may leak into a field that previously contained an exact array. A value is either genuinely not part of the compact contract (`[]`) or exact.

Add focused tests that patch the expensive helper to raise if an explicitly unneeded request invokes it. Do not rely only on profiler timings to prove the dependency plan.

## Part B — prepared derived sidecar contract

### Logical row contract

Prepare only the invariant source-local values needed to eliminate repeated phase/capacity reconstruction. The logical artifact contains one row per canonical raw row, in canonical source order, with at least:

```text
record_index          integer identity/alignment field
cycle                 exact source-local canonical cycle label, for validation/filtering
phase_code            compact code for rest / charge / discharge
phase_capacity_mah    float64 exact output of the existing phase-capacity reconstruction
```

Use a stable documented code mapping, for example:

```text
0 = rest
1 = charge
2 = discharge
```

The implementation may choose a different compact numeric mapping only if it is defined once in the shared transform/preparation owner and round-trips exactly to the existing response strings.

The sidecar must **not** duplicate raw voltage, current, status, charge/discharge counters, timestamps, source paths, filenames, protocol metadata, active mass or electrode area.

### Derivation order

The prepared values must be produced with the exact same row ordering semantics as the current request path. In particular:

- derive phase from the canonical status/current fields using the existing phase rule;
- derive phase capacity using the existing reset/carry rule;
- use complete source rows and the same within-cycle record order that the request path uses;
- associate the result back to canonical `record_index`/cycle identity so selective reads can verify alignment;
- prove that slicing complete cycles from the prepared source produces the same values as calculating those cycles on the current fallback path.

If source-local preparation cannot reproduce the existing semantics for a verified continuation/boundary case, **do not silently invent a Cell-level full-row duplicate cache**. Keep the affected transform request-side and hand the evidence back to review for a scope decision.

### Filesystem identity

Introduce a dedicated prepared representation generation, e.g.:

```text
TIME_CAPACITY_DERIVED_CACHE_VERSION = 1
```

This is a cache-format generation, not a new scientific meaning. The artifact identity must include:

- source checksum directory;
- exact per-source parser identity;
- current `CALC_VERSION`;
- prepared derived-cache version;
- current `CANONICAL_RAW_VERSION` in validated metadata;
- the active raw-layout generation and/or the exact validated raw physical fingerprint used for row alignment.

A suggested naming convention is:

```text
time_capacity_derived__p<parser>__c<calc>__d<version>.parquet
time_capacity_derived_index__p<parser>__c<calc>__d<version>.json
```

The exact filename spelling may follow existing cache helpers, but the identity dimensions above are mandatory and must be inspectable/testable.

### Sidecar metadata/index

Publish a tiny metadata/index document sufficient to reject stale/misaligned prepared bytes without reading the full sidecar. At minimum validate:

```text
derived_cache_version
parser_version
calc_version
canonical_raw_version
raw_layout_version
raw_shape_fingerprint
row_count
row_group_count / row-group row counts when the representation is row-grouped
prepared column names/schema
```

Do not store source paths.

The prepared reader must fail closed to **performance fallback**, not scientific failure, when any metadata check fails.

### Physical access

The prepared representation must support bounded reads for selected cycles. Prefer deliberate row groups aligned with the existing 4,096-row raw layout so the same source-cycle -> row-group plan can be reused and row alignment can be checked cheaply.

For a selected source slice:

1. resolve the raw-layout index under the existing non-waiting consistency boundary;
2. select the same contributing source-local cycles/groups;
3. read only the prepared columns required by the transform plan (`phase_code` only, or `phase_code + phase_capacity_mah`);
4. filter row-group spillover to exact requested source cycles;
5. verify selected prepared identity/order against the selected raw rows before consuming the values;
6. decode phase codes and attach exact phase capacity without recomputing the formula.

The implementation may use an equivalent selective representation if profiling shows it is materially simpler/faster, but it must remain bounded, row-aligned, cache-local, exact and free of a whole-raw duplicate.

### All-or-nothing safety per resolved Cell/unit

For 050.6, use prepared derived values only when every contributing source needed by that resolved Cell/unit for the selected range has a valid aligned prepared artifact. If one contributing source is absent, invalid, busy or misaligned, fall back to the current exact request-side phase/capacity calculation for that entire Cell/unit.

This deliberately avoids partially mixing prepared and computed arrays in the first implementation. A later optimization may relax this only with its own parity evidence.

## Part C — preparation lifecycle

### New/current cache builds

When a complete validated canonical raw frame is already in memory during `cache.build()` / `build_write_behind()` or their current owner, prepare the derived artifact from those bytes without reparsing the source. Reuse the shared phase/capacity implementation.

Derived preparation is an optional performance publication. If it fails:

- canonical raw/index/cycles publication must remain valid;
- the source must not be marked scientifically invalid solely because the derived sidecar failed;
- log/report the preparation failure through the existing background/scientific-preparation mechanisms as appropriate;
- the live Time/Capacity request uses the exact fallback.

Do not turn an optional optimization artifact into an import failure.

### Existing cache upgrade

Extend the existing scientific preparation path instead of creating a new scheduler/thread family.

`scanner.start_capacity_summary_backfill()` already selects parsed sources needing current raw-layout preparation, and `_prepare_capacity_source_worker()` can prepare layout from existing raw bytes without source I/O. Add an analogous bounded predicate/job flag for a raw cache that exists but lacks a current Time/Capacity derived artifact.

Required behavior:

- if raw layout also needs conversion, prepare/validate raw layout first and then prepare derived data from the resulting canonical raw bytes;
- if raw layout is already current, prepare only the derived artifact;
- if the source file is offline but the canonical raw cache is valid, preparation may proceed from cache bytes and must not change `location_status`;
- if the raw cache itself is absent because the user cleaned it, normal startup must not reparse/recreate the source solely for 050.6;
- preserve the existing copied-library foreground/background resource rules; do not add an independent worker pool.

### Cleanup and race safety

- Keep all prepared files inside the source checksum cache directory.
- Reuse `protect_hash_from_cleanup()` / the existing live deletion boundary while preparing/publishing.
- A raw replacement/conversion must never leave a stale prepared artifact that can validate against new raw bytes. Remove/invalidate or fingerprint-reject it before use.
- Prepared readers must not wait on a conversion/preparation lock on the interactive request path; return fallback instead.
- Touch prepared payload/index files on successful reads so scientific LRU reflects real use.
- Existing checksum-directory deletion and scientific budget accounting should automatically include these files; add focused tests where current enumeration assumptions require them.

### Performance acceptance

Structural acceptance is primary:

- compact Time-axis Voltage/Current performs **zero** phase-capacity reconstruction work;
- prepared capacity-axis requests perform **zero** `_phase_capacity()` reconstruction when every contributing sidecar validates;
- prepared phase requests perform **zero** `_phase_from_raw()` classification when every contributing sidecar validates;
- prepared selected-cycle reads are bounded to contributing derived groups/rows rather than materializing every derived row;
- the scientific payload is unchanged.

Timing acceptance is same-machine/descriptive but this optimization must still demonstrate a real win. On the approved golden-source profiler, the median backend total for broad normal compact requests (`1–150` and `All`) should improve materially relative to the forced-fallback path. Treat **>=25% median reduction** on at least the one-Cell broad Time-axis cases and one representative multi-Cell broad case as the expected bar. If the implementation cannot meet that on the measured hotspot, do not broaden scope speculatively; record the evidence and hand back for review.

Do not use a universal absolute millisecond threshold across machines.
