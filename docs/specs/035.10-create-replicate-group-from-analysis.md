# 035.10 — Create a replicate group from an Analysis

**Status:** Plan  
**Parent:** [035 — User experience and workflow optimization](035-user-experience-and-workflow-optimization.md)  
**Depends on:** 035.9 clean review.  
**Scope:** Persistent `ReplicateGroup` creation from direct Cell entries in one Analysis, including
explicit folder-reference replacement.  
**Review document:** `reviews/035.10-create-replicate-group-from-analysis-review.md`

## Goal

Allow a scientist who notices replicate Cells inside an Analysis to create one persistent library
ReplicateGroup without leaving the Analysis. Replace the selected direct Cell entries in the
current Analysis, optionally place the group in folders, and remove only explicitly chosen folder
references.

## Existing architecture to preserve

- `frontend/src/pages/AnalysisPage.tsx::SamplePanel` owns the Analysis sample list.
- `AnalysisSpec.selection.entries` contains `cell` and `replicate_group` references.
- saved plots contain their own selection/visibility state.
- `POST /api/replicate-groups` creates a persistent group and supports:
  - `folder_ids`;
  - exact `remove_folder_cells: [{folder_id, cell_id}]`.
- `backend/app/routers/analyses.py::update_analysis` persists the Analysis spec.
- `backend/app/services/analysis_usage.py` already transforms selection blocks for lifecycle
  changes and provides relevant patterns.
- folder references do not own or delete Cells.

Do not implement an analysis-local pseudo-group.

## Locked user workflow

Add an action in `SamplePanel`:

```text
Create replicate group…
```

Availability:

- enabled only when the Analysis contains at least two direct Cell entries;
- replicate-group entries are not eligible members;
- archived/missing references follow existing Analysis missing-reference policy and cannot be
  selected if the backend cannot validate them;
- the action does not rely on plot-line selection or hidden/visible state.

The action opens one focused modal.

### Step 1 — Choose direct Cells

- checklist of direct Cell entries in the Analysis;
- select at least two;
- initially no selection unless the current UI already has an explicit compatible sample-row
  selection to reuse;
- show Cell name and enough context to avoid ambiguity;
- duplicate IDs cannot be selected twice;
- show a validation message before enabling Create.

### Step 2 — Group identity

- required unique name;
- optional description;
- trim whitespace;
- use current global ReplicateGroup uniqueness behavior.

### Step 3 — Current Analysis replacement

Show a locked checked statement:

```text
Replace the selected individual Cell samples with this replicate group in the current Analysis.
```

This is mandatory for this workflow. Keeping both direct entries and their new group in the same
Analysis would duplicate series and sample counts. Users who want a persistent group without
changing the current Analysis use the Cell Database workflow.

Supporting copy:

```text
The underlying Cells are not deleted.
```

### Step 4 — Folder placement

Allow zero or more destination folders.

```text
Place replicate group in:
[folder picker]
```

Add one toggle:

```text
In selected folders, replace the individual Cell references where all selected Cells are present.
```

Rules:

- default on only when at least one selected destination folder contains every selected Cell as a
  direct folder reference;
- list which selected destination folders are eligible;
- an ineligible destination folder may receive the group but no Cell references are removed;
- never remove a Cell from a folder not selected as a destination;
- never remove a Cell from another folder just because the Cell appears there;
- send exact eligible `(folder_id, cell_id)` pairs only;
- explain:
  `The Cells remain in the Cell Database and in all other folders.`

If no destination folder is selected, the group remains unfiled and no folder Cell references are
removed.

## New atomic endpoint

Add:

```http
POST /api/analyses/{analysis_id}/replicate-groups
```

Request:

```json
{
  "name": "Electrolyte A — 3 bar",
  "description": null,
  "cell_ids": [12, 13, 14],
  "folder_ids": [7],
  "remove_folder_cells": [
    {"folder_id": 7, "cell_id": 12},
    {"folder_id": 7, "cell_id": 13},
    {"folder_id": 7, "cell_id": 14}
  ]
}
```

Response:

```json
{
  "analysis": {"id": 22, "spec": {}},
  "replicate_group": {"id": 9, "name": "Electrolyte A — 3 bar"},
  "modified_saved_plot_ids": ["plot-a"],
  "removed_folder_cell_refs": 3
}
```

Use the repository’s full Analysis/ReplicateGroup response shapes rather than maintaining partial
frontend guesses.

## Backend validation

Validate every item before the first membership write:

- Analysis exists;
- unique `cell_ids`, at least two;
- every Cell exists and is active enough for grouping under current rules;
- every Cell is a direct entry in the current Analysis;
- no requested Cell is only present indirectly through another group;
- group name is non-empty and unique;
- every destination folder exists;
- every removal pair references:
  - one selected Cell;
  - one selected destination folder;
  - an actual current `FolderCell` reference;
- no duplicate removal pairs;
- all requested folder replacement pairs satisfy the server’s eligibility rule.

Do not trust the frontend’s eligibility calculation.

## Shared replicate-group service

Extract commit-free group creation from `routers/replicates.py` into a service, preferably:

```text
backend/app/services/replicate_groups.py
```

It should provide reusable primitives for:

- normalized name/ID validation;
- creating the group row;
- ordered memberships;
- destination folder links;
- exact folder Cell-reference removal;
- serializing/returning the group through an existing shared helper where appropriate.

Both the existing replicate endpoint and the new Analysis endpoint use the service. Do not call one
router function from another. The caller owns commit/rollback.

## Atomic transaction

In one database transaction:

1. validate live Analysis/direct entries/folders;
2. create `ReplicateGroup`;
3. add ordered memberships;
4. add destination folder references;
5. remove exact requested `FolderCell` pairs;
6. transform the Analysis spec;
7. transform every saved plot selection;
8. update Analysis modified time;
9. record a privacy-safe activity event in the same transaction when current activity helpers allow;
10. commit.

Any failure leaves:

- no group;
- no group membership;
- no folder change;
- no Analysis-spec change;
- no success activity entry.

Filesystem artifact invalidation happens only after commit and is idempotent/retryable.

## Selection transformation contract

Create a tested pure backend helper rather than inline dictionary mutation.

### Analysis main selection

For `analysis.spec.selection`:

- preserve all unrelated entry order;
- insert the new group entry at the position of the first selected direct Cell entry;
- remove every selected direct Cell entry;
- keep unrelated entries unchanged;
- do not copy a direct Cell `label_override` onto the group;
- preserve global Cell exclusions;
- remap selected direct-entry exclusions to:
  - `entry_kind: "replicate_group"`;
  - `entry_ref_id: new_group_id`;
  - same `cell_id`;
- de-duplicate equivalent exclusions;
- remove stale references to the deleted direct-entry context only after remapping.

### Saved plots

For every saved plot’s `selection`:

- perform the same entry replacement if the saved selection owns entries;
- if saved plots inherit the Analysis entry list through current schema semantics, transform only
  the actual persisted fields that exist; do not invent a second entries list;
- remap per-entry exclusions so every Cell keeps its prior visible/hidden status;
- preserve unrelated hidden replicate-group IDs;
- do not add duplicate entries/exclusions;
- preserve draft/saved-plot lifecycle invariants and do not persist session-only draft plots.

A saved plot where some selected Cells were hidden and others visible must retain that distinction
inside the new group.

## Cache and provenance consequences

After commit:

- invalidate/delete dependent Analysis result caches, rendered artifacts, previews, and thumbnails
  through existing analysis cache-maintenance paths;
- mark/refetch the Analysis normally;
- do not change source caches;
- do not bump `CALC_VERSION`; formulas and source scientific meaning are unchanged;
- provenance is refreshed on the next compute through existing mechanisms.

## Frontend structure

Avoid growing `AnalysisPage.tsx` substantially. Add:

```text
frontend/src/components/CreateAnalysisReplicateModal.tsx
frontend/src/analysisReplicatePolicy.ts
```

`analysisReplicatePolicy.ts` owns:

- eligible direct Cell entries;
- folder eligibility from the tree;
- exact replacement-pair construction;
- request validation;
- user-facing summary counts.

Place any new `AnalysisPage` hooks above early returns. Prefer passing callbacks/data into the child
component.

## Frontend success/error behavior

On success:

- set/refetch the returned Analysis;
- close the modal;
- invalidate:
  - Analysis detail/list;
  - Cells;
  - Replicate groups/previews;
  - tree/folders;
  - activity;
  - affected saved-artifact queries;
- remain on the current Analysis route and active tab;
- focus the new group row when practical.

On error:

- modal remains open;
- form and selected Cells/folders remain;
- no optimistic group or folder removal is shown.

- The workflow creates a persistent, reusable ReplicateGroup.
- No duplicate group/direct series remain in the current Analysis.
- Folder changes are explicit and local.
- The operation is atomic.
- Saved-plot visibility is preserved.
- Cells are never deleted by the workflow.
