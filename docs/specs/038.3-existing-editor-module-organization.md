## What the four family cards do

These explanations define ownership. They do not authorize scientific changes.

### Steps — `families/steps/StepsPlotCard.tsx`

One plotted point is one executed occurrence of a user-selected protocol-step block.

The existing file currently exports `StepsResult`, `useStepsResult`, `StepsSettings`,
`stepsVisibleSeries`, `stepsSeriesDescriptors`, `stepsTracesForResult`, `stepsLayoutForSpec`, and
`StepsPlotCard`.

The card owns:

- choosing explicit Cell–protocol-segment pairs and union/contiguous block mode;
- requesting `POST /api/analyses/{id}/steps`;
- choosing duration/voltage/capacity quantity and occurrence/cycle/time X axis;
- mapping backend block rows into series descriptors, Plotly traces, and layout;
- settings, visibility controls, live plot, style panel, and image/data export.

It does not decide how executions are grouped or how block quantities are calculated. Those remain
in `analysis_engine.compute_steps` and `backend/app/services/step_blocks.py`.

### DCIR — `families/dcir/DcirPlotCard.tsx`

One plotted point is one valid long-rest + short-current-pulse occurrence.

The existing file currently exports DCIR result types, `dcirViewFor`, X-axis/series/trace/layout
builders, `useDcirResult`, `DcirSettings`, and `DcirPlotCard`.

The card owns:

- requesting candidate rest/pulse definitions from
  `POST /api/analyses/{id}/dcir-protocols`;
- letting the user confirm/manage the protocol segment;
- requesting `POST /api/analyses/{id}/dcir`;
- showing absolute mΩ or relative % change against occurrence/cycle/time;
- mapping returned measurements to canonical Plotly output and exports.

It does not implement the direction-correct resistance formula or candidate thresholds. Those
remain in `backend/app/services/dcir.py` and `analysis_engine.compute_dcir`.

### Chargeability — `families/chargeability/ChargeabilityPlotCard.tsx`

The result is a set of matched voltage-controlled charge events; each event is displayed as a
curve with many points. It is not one scalar per cycle.

The existing file exports chargeability result types, computation/view normalization, query hook,
series/trace/layout builders, settings, and `ChargeabilityPlotCard`.

The card owns:

- entering supported initial/final SoC and current-ceiling filters;
- requesting `POST /api/analyses/{id}/chargeability`;
- displaying recognition progress and the matched protocol structure;
- choosing time/SoC/capacity X and current/C-rate/current-density Y views;
- rendering and exporting returned curves.

It does not parse Neware formula syntax, infer SoC semantics, resolve reference capacity, or extract
the executed curve. Those remain in `backend/app/services/chargeability.py`.

### Rate Capability — `families/rate-capability/RateCapabilityPlotCard.tsx`

One plotted point is one validated programmed charge or discharge rate condition from a recognized
sweep block.

The existing file exports result/block/point types, computation/view normalization, descriptor,
query, trace/layout builders, settings, and `RateCapabilityPlotCard`.

The card owns:

- semantic recognition configuration and selected charge/discharge family;
- requesting `POST /api/analyses/{id}/rate-capability`;
- displaying recognized protocol structure and progress;
- choosing capacity, retention, current, and comparison presentation;
- rendering/exporting the selected backend result.

It does not pair CC/CV steps, validate cutoffs, score sweeps, calculate CC-only capacity, or choose
the common reference rate. Those remain in `backend/app/services/rate_capability.py`.

## Diagnostic Cycles

Move `frontend/src/diagnosticCycles.ts` to
`features/analyses/editor/families/cycles/diagnosticCycles.ts` unchanged.

It detects likely diagnostic cycles using charge/discharge duration against rolling local
baselines. It is a Cycles display policy, not a backend scientific-result filter. Preserve:

- `DIAGNOSTIC_DEFAULTS` and `DIAGNOSTIC_SIGNALS`;
- detection, range formatting, and summary exports;
- default-off behavior;
- the rule that stored/exported scientific data are not silently removed;
- existing focused tests.

Do not replace duration with a capacity threshold. That would confuse actual degradation with a
diagnostic procedure and is explicitly prohibited by the change playbook.

## Protocol folder responsibilities

### `ProtocolSegmentsPanel.tsx`

Move the existing panel intact. It owns user-facing protocol-step search/filter/select, neighboring
step expansion, grouping mode, suggested segments, and creation/editing of named
`ProtocolSegment` targets keyed by protocol signature. It receives cells, existing segment state,
visibility sets, callbacks, and optional DCIR suggestions. It does not compute Steps/DCIR results.

### `ProtocolStructureViewer.tsx`

Move intact. It provides the read-only normalized protocol view used by Chargeability and Rate
Capability to show which steps were recognized. It does not change protocol definitions.

After the move, import `normalizeGroup` directly from sibling
`protocolGroupNormalization.ts`. Remove the old re-export from `ProtocolSegmentsPanel.tsx` once no
consumer needs it; ownership must remain visible rather than routing a pure helper through a UI
component.

### Pure protocol helpers

- `protocolGroupNormalization.ts`: deterministic normalization/stable IDs for legacy/current
  nested protocol groups;
- `protocolStepFilters.ts`: filter fields/operators, value parsing, matching, query search, and
  C-rate examples;
- `protocolStepNeighbours.ts`: innermost-group lookup, same-group expansion, and before/after/both
  adjacency selection.

Move verbatim and update their focused tests to the new paths.

Normalized scientific protocol reconstruction remains backend-owned by
`backend/app/services/protocol.py`; these frontend helpers only operate on the returned structure.

## Recognition folder responsibilities

- `RecognitionProgress.tsx` is the small visible determinate/indeterminate progress presentation.
- `recognitionProgress.ts` creates/shares recognition job tokens, polls background job state, and
  delays the visible progress indicator to prevent flashes.

Move both intact and update DCIR, Chargeability, and Rate Capability imports. Preserve shared-token
identity, polling interval/terminal behavior, delay, labels, and error handling.

Move intact. It owns pure transitions among normal workspace, new draft, edited saved plot,

functions and the invariant that draft plots never persist.

Update the already-moved `workspace/analysisWorkspace.ts` type import for
`NormalWorkspaceSnapshot` to the new policy path.

### `analysisPlotPolicy.ts`

Move intact. It owns saved-plot selection snapshots, restored-view specs, signatures, and

### `multiSourceAnalysisPolicy.ts`

Move intact. It mirrors the backend fail-closed rule for protocol-derived families when selected
Cells contain multiple ordered source files. It maps tabs to protected families and reports
supported, pending, unsupported, and affected Cells for UI disabling/explanation.

The backend guard before computation/cache lookup remains authoritative. Do not relax it here or
change the currently supported Cycles/Time-Capacity behavior.
