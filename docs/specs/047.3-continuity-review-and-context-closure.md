# B — Secondary `Continuity review` surface

Create a focused component, for example:

```text
frontend/src/components/ContinuationReviewModal.tsx
```

A drawer is acceptable only if it fits the existing application better; a small/medium Mantine Modal
is the default.

This is not a new wizard step and does not replace Step 3.

## B1 — Content

The review surface receives the current `ContinuationInspectResult` and current acknowledgement set.

Group findings by behavior, not decorative dashboards:

### Blocking

Show explicit red rows for `severity === "blocking"`.

- no checkbox;
- cannot be acknowledged away;
- explain the source(s);
- primary continued import remains disabled.

### Confirmation

Show orange/neutral confirmation rows for `severity === "confirmation"` with one checkbox per finding.

This includes:

- timestamp overlap/reversed order where backend marks confirmation;
- capacity/mass material mismatch confirmations;
- metadata-only source acknowledgement;
- path-refresh confirmation;
- any future backend confirmation code.

Do not hardcode a parallel list of confirmation codes if severity already defines the behavior.

### Warning / info

Show these only inside the review surface, preferably under a collapsed/secondary **Details** section.

They do not require acknowledgement and do not block import.

The main Step-3 workspace does not display them.

## B2 — Acknowledgement identity

Keep current `preserveAcknowledgements(...)`.

A checked confirmation is valid only while the exact semantic finding ID remains current.

Therefore:

```text
acknowledge finding
→ reorder/change source
→ inspection result/fingerprint changes
→ stale acknowledgement disappears unless same finding ID still exists
```

Keep `acknowledgedMetadataOnlySourceKeys(...)` binding to the currently acknowledged server finding.

Do not replace this with one generic "I understand" checkbox.

## B3 — Open/close behavior

When the user clicks **Inspect continuity**:

1. run/refetch the existing inspection;
2. while pending, keep compact loading state in the command/preview area;
3. when result is complete:
   - no blocking/confirmation findings → do not force an extra modal;
   - blocking or confirmation findings → automatically open `Continuity review`;
   - warning/info-only findings → do not interrupt; details remain available on demand.

After a completed inspection with any findings, the command may become a restrained secondary action:

```text
Review continuity
```

or:

```text
Inspected · Review
```

Do not add a large persistent alert stack.

If blocking/confirmation review is still required and the user closes the modal, the footer Import
button remains disabled and the nearby state must explain why, e.g.:

```text
Continuity review required before import.
```

This can be concise dimmed/semantic footer status text; a disabled button alone is insufficient.

## B4 — Clean inspection state

If inspection completes with no blocking or required confirmation:

- no modal interruption;
- combined preview proceeds;
- command state may show a compact success/check treatment;
- do not add a large success Alert.

# C — Submission safety remains server-backed

Keep:

```ts
continuedImportCanSubmit(...)
```

or a refactored equivalent with the same semantics.

The client can submit only when:

- at least two sources remain;
- Cell name/scientific draft is valid;
- continuation inspection exists and is complete;
- backend `can_submit` is true;
- every current confirmation finding is acknowledged.

The server remains authoritative and must reject stale/changed identity or missing acknowledgements
through the existing final validation path.

Do not make `Inspect continuity` a cosmetic button.
