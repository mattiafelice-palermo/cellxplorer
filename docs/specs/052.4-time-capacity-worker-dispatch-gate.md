# 052.4 — Time/Capacity worker dispatch gate

**Status:** Active child — implementable
**Parent:** Spec 052 — Time/Capacity cycle navigation
**Repository:** `mattiafelice-palermo/cellxplorer`
**Branch:** `feature/time-capacity-cycle-navigation`
**Reason for child:** explicit user decision after 052.3. Profiling showed the persistent worker pool is warm and resident but excluded from interactive requests by its own admission gate. This child opens the gate, sizes the pool to the work, and fixes the warmup fragility that opening it exposed.

## Goal

Let interactive Time/Capacity requests actually use the persistent pool that startup already warms, **without changing any scientific output**.

Spec 050.23 established a bounded persistent pool, warmed asynchronously from `main.py` at backend startup. It works. But `choose_execution` refused to dispatch to it for exactly the requests that need it most: a six-Cell ten-cycle slider preview is ~16.5k rows against a 24k workload floor, so it ran serially while warm workers idled.

## Verified current facts that constrain the implementation

Measured on this branch after 052.3, AC power, real application library ("Performance analysis", 6 Cells), 16 logical CPUs / 32 GB.

**The parallelizable fraction is much larger than the diagnostics suggest.** `cell_job_wall_ms` measures only `_cell_result`; the indexed Parquet read in `_materialize_read` is not counted in it and was therefore mis-attributed to owner setup. For a six-Cell ten-cycle time-axis preview the true split is ~11.7 ms planning against ~61 ms parallelizable work — **84% parallelizable**.

Dispatch-only measurements, warm pool, six Cells, ten-cycle window, time axis:

| workers | dispatch | vs serial |
|---|---|---|
| serial | 87.6 ms | 1.00× |
| 2 | 43.8 ms | 2.00× |
| 4 | 34.8 ms | 2.52× |
| 6 | 23.5 ms | 3.72× |

Process dispatch won at **every** size tested — down to ~8.2k rows (2.2×), a third of the old floor — and from two Cells upward (1.6× at 2, 2.2× at 3, 2.9× at 4, 2.4× at 6). No lower crossover was found. Only one Cell shows no benefit (~12 ms process vs ~10 ms serial), which is expected: one Cell is one job and cannot be split.

Constraints:

- jobs are per Cell, so a pool narrower than the selection runs in rounds — six Cells across four workers is two rounds whose second carries only two jobs;
- `_ready_pool` requires `_POOL_WORKERS == workers` exactly, and the startup warmup sizes the pool by calling `choose_execution` itself, so the tier table and the per-request decision must stay consistent;
- `_warm_pool` proved liveness with `_worker_ping`, which returns immediately. A fast process can answer several acknowledgements before its siblings spawn, so warmup could conclude that fewer workers were resident than requested and **fail closed to serial**. This was already fragile at 4 workers and reproducibly broken at 6.

## Stages

### Stage 1 — Remove the workload floor

- delete the `selected_rows < max(12_000, cell_count * 4_000)` gate entirely;
- lower the Cell floor from `cell_count < 3` to `cell_count < 2`, reason `single_cell`;
- **keep the host and memory gates unchanged** — they bound how many workers the machine can afford, which is a different question from whether a job is worth splitting.

### Stage 2 — Size the pool to the work

- add a `logical_cpus >= 12` tier selecting 6 workers, subject to the same memory arithmetic as the existing tiers (`6 * per_worker` plus reserve);
- hosts below that threshold keep their existing 4- and 2-worker tiers unchanged.

### Stage 3 — Make warmup robust

- hold each warmup acknowledgement briefly (`_WARMUP_PING_HOLD_SECONDS`) so concurrent pings cannot be served by one process, and warmup observes one distinct PID per requested worker;
- this is a startup-only cost on an already asynchronous thread;
- it is a prerequisite for Stage 2, and it also removes a pre-existing source of silent serial fallback at 4 workers.

## Non-goals

- No change to scientific transforms, cache formats, or the navigator's cadence.
- No per-request pool resizing. The pool is sized once at startup; `_ready_pool`'s exact-match invariant is preserved.
- No conversion of the route to async, and no change to request cancellation.

## Verification requirements

- **Scientific parity is mandatory and blocking**, proven with `scientific_digest` over the `scripts/profile_time_capacity_request_overhead.py` matrix, serial versus pooled.
- Performance evidence recorded per stage, same host, AC power.
- Focused gate tests must cover: the `single_cell` reason, absence of any workload floor across small multi-Cell requests, the 6-worker tier on a wide host, and the preserved 4-worker tier on an 8-CPU host.
- Warmup must be proven to acknowledge one distinct PID per requested worker at each supported tier.
- Canonical preflight.

## Results

Serial (pool unavailable) versus warm 6-worker pool, complete router boundary, disposable cache, 9 repetitions:

| Workload | Serial | Pooled | Change |
|---|---|---|---|
| single-cell explicit cycles | 30.4 ms | 31.1 ms | +2.2% |
| six-cell full range, time | 206.0 ms | 86.3 ms | **−58.1%** |
| **six-cell moving preview (time)** | **83.8 ms** | **41.4 ms** | **−50.6%** |
| six-cell moving preview (capacity) | 200.3 ms | 69.6 ms | −65.3% |
| six-cell full range, capacity | 1259.9 ms | 371.3 ms | −70.5% |
| six-cell derivative | 306.3 ms | 306.8 ms | +0.2% |

Scientific digests identical on every workload. The single-Cell and derivative rows are unchanged by design — one Cell stays serial, and the derivative view runs on the legacy engine path where this gate does not apply.

Time-axis moving preview across both children: **112.5 ms → 41.4 ms**, roughly 8.9 → 24.1 fps.
