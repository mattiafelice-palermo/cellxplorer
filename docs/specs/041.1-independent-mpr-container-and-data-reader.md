## Goal

Implement an **independently authored**, efficient low-level reader for the verified BioLogic EC-Lab `.mpr` modular binary container and VMP data records needed by GCPL-family files.

This child proves only the binary-decoding layer. It deliberately does **not** yet map the raw BioLogic fields into CellXplorer cycles/status/capacity semantics and does not make `.mpr` importable through the application.

At completion, given a supported `.mpr` path/bytes, production code must be able to:

- validate the BioLogic modular-file magic;
- walk module headers safely by declared lengths;
- identify module names/versions/dates;
- expose zero-copy/bounded views of module payloads;
- parse the VMP data header (`n_datapoints`, encoded column IDs, record data offset/version);
- build one NumPy structured dtype for the validated set of GCPL columns;
- decode the complete record block in bulk with `np.frombuffer`/equivalent;
- unpack bit flags vectorially;
- return a low-level typed result suitable for 041.2;
- fail clearly on unsupported/ambiguous versions/column layouts.

## Verified modular container contract

### File magic

The supplied file begins with the ASCII BioLogic modular-file signature:

```text
BIO-LOGIC MODULAR FILE
```

Validate the complete known prefix/padding pattern observed in independently inspected files, not only the first few characters if doing so could accept unrelated data.

### Module marker/header

The supplied file has a 52-byte initial file header followed by the ASCII marker:

```text
MODULE
```

For the supplied modern-format modules, the header immediately after `MODULE` is 59 bytes and contains:

```text
short_name   10 bytes
long_name    25 bytes
max_length    4 bytes little-endian
length        4 bytes little-endian
old_version   4 bytes little-endian
new_version   4 bytes little-endian
date          8 bytes ASCII
```

The independently verified sample uses `max_length = 0xffffffff`, `old_version = 0`, and module version from `new_version`.

The reader may support a verified older header variant if independent project evidence establishes it. Do not add guessed alternate layouts merely because they exist in third-party code.

### Sequential walk

Walk by:

```text
module_marker_offset
→ marker length
→ header length
→ declared payload length
→ next expected module marker
```

Requirements:

- validate every calculated boundary is within file size;
- verify the next module marker appears exactly where declared length predicts for known sequential modules;
- reject integer overflow/truncation/impossible lengths;
- do not call `contents.split(b"MODULE")` on the whole file;
- do not copy all payloads into separate Python `bytes` objects if `mmap`/memoryview slices suffice.

### Supplied sample acceptance

The reader must reproduce exactly:

```text
VMP Set  version 10  payload length 6,953
VMP data version 11  payload length 291,606
VMP LOG  version 10  payload length 8,309
```

and total end offset exactly equals `307,115` bytes.

## I/O strategy

Prefer `mmap.mmap` in read-only mode or an equivalent memory-mapped/zero-copy buffer for path input.

Requirements:

- mapping/file handles are closed deterministically;
- structured arrays/views must not outlive a closed mapping unless copied intentionally into an owning array;
- decide explicitly whether `read_mpr` returns owning NumPy arrays or keeps an object/context that owns the mapping;
- favor simple lifetime safety over microscopic memory savings.

A practical safe design is:

```text
memory-map while parsing
→ np.frombuffer views
→ copy only the compact structured record array / required columns before closing
```

if downstream lifetime would otherwise be unsafe.

Also support `bytes`/memoryview input in tests if it materially improves deterministic fixture testing, but path parsing is the production requirement.

## VMP data module header

For the independently inspected sample:

```text
payload[0:4]  = little-endian uint32 n_datapoints = 5483
payload[4]    = uint8 n_columns = 16
column IDs    = 16 encoded uint16 values beginning at payload offset 5
module version = 11
```

The sample's encoded ID sequence is:

```text
1, 2, 3, 21, 31, 65, 131, 4, 7, 13, 5, 6, 9, 39, 211, 468
```

For module version 11, independently verify the column-ID byte order and record-data offset in project tests/notes before locking code. The authoring investigation observed the modern data block pattern but the implementation must commit its own binary-format note showing the exact evidence used.

This document is the project's independent format notebook. Record only facts established from project-owned files/vendor docs/tests, with byte offsets/hex observations as needed. Do not copy third-party comments/tables.

## Column-definition strategy

MPR record layout depends on the encoded column ID list. Each supported ID needs an independently established:

```text
record dtype
raw semantic name
unit if known
flag bitmask if packed flag
```

### Initial allowlist

041.1 only needs to support the IDs required by the supplied/paired GCPL corpus. Build a small explicit `MPR_COLUMN_DEFINITIONS`/equivalent from independently verified facts.

Do not claim all EC-Lab column IDs are supported.

### Full encoded IDs versus low byte

Some encoded IDs may carry additional high-byte information/aliases. Do not simply truncate every ID with `% 256` unless independent evidence proves that is correct for the relevant definition.

For each accepted ID, tests should use the exact encoded value(s) observed in the corpus.

### Unknown ID

If an unknown ID affects record layout and its dtype/width is not known, fail:

```text
UnsupportedMprColumn(<id>)
```

Do not guess `float32` merely to keep reading subsequent bytes.

## Record data offset and row-size validation

For each supported VMP data module version:

1. determine the record-data start offset from independently verified samples;
2. build the structured dtype from the encoded column sequence;
3. compute:

```text
expected_data_bytes = n_datapoints * dtype.itemsize
```

4. verify the module payload contains exactly the expected record region plus any independently documented header/trailer bytes;
5. reject mismatches before decoding.

This catches a wrong dtype mapping that would otherwise produce plausible shifted floats.

Use one bulk operation:

```python
np.frombuffer(buffer, dtype=record_dtype, count=n_datapoints, offset=data_offset)
```

or equivalent.

Do not loop through 5,483/1,000,000 records with Python unpack calls.

## Packed flag decoding

The MPR data header can include several logical flag IDs stored in one physical byte/field.

041.1 must independently establish the flag bit masks needed by the GCPL corpus and unpack them vectorially:

```python
flag = (packed & mask) >> shift
```

on the NumPy array.

Do not duplicate the physical packed byte for every logical flag inside the structured dtype. Add it once and expose decoded flag arrays/views separately.

Required future-use flag concepts likely include sequence/control/counter changes; exact names/masks must come from independent project evidence and be documented in `docs/biologic-mpr-format.md`.

## Categorical mappings

041.1 may expose raw integer codes for fields such as control mode/current range. Do not convert every record to strings yet.

Where a human-readable mapping is needed for low-level debugging/tests:

- build a dictionary/array mapping;
- compute `np.unique(raw_codes)`;
- map each distinct value once;
- never scan a long mapping tuple for every row.

Scientific normalization belongs to 041.2.

## Settings and log modules in this child

041.1 must locate and expose `VMP Set` and `VMP LOG` module payloads/header metadata, but it does **not** need to decode the full GCPL settings/protocol yet.

It may decode only minimal independently verified fields needed to:

- identify/validate that the file is in the supported GCPL family if safely available;
- expose acquisition date/header version for tests;
- enable 041.2/041.3 to access payloads through typed helpers.

Do not add guessed settings offsets. Full settings/log semantics belong to 041.3.

## Optional/unknown modules

The module walker should be structurally capable of skipping an unknown module by its validated declared length.

Policy:

- unknown optional module name: preserve descriptor and skip payload, unless it is necessary to interpret the data safely;
- unknown VMP data module version: fail;
- multiple VMP data modules: fail in initial contract unless independently verified and parent amended;
- missing VMP data: fail;
- missing VMP Set: fail for GCPL support;
- missing VMP LOG: low-level reader may succeed structurally, but later timestamp capability may be false.

## Security/robustness

Treat `.mpr` as untrusted local binary input.

Validate before allocating:

- file size bounds;
- module count/length bounds;
- `n_datapoints` sanity relative to payload length;
- `n_columns` sanity;
- record dtype itemsize;
- multiplication overflow / impossible expected size;
- string decoding with bounded lengths/error handling.

Do not allocate arrays based solely on an unvalidated `n_datapoints` if module length proves the file cannot contain that many rows.
