## Purpose

Determine whether one or more **measured remaining numerical kernels** in the post-050 analysis path become materially faster when implemented in compiled Rust, and how much additional gain comes specifically from bounded Rayon parallelism across independent Cells.

This proto-child deliberately separates two effects:

1. **native-kernel acceleration** — current Python/NumPy/pandas implementation versus equivalent sequential Rust;
2. **parallel acceleration** — sequential Rust versus the same Rust kernel using 2 or 4 Rayon workers.

It does **not** authorize production Rust integration. A later implementation child is required after benchmark evidence and the composition decision in 050.P6.

## Why Rust is evaluated separately

A Rust extension can solve a different boundary from Python read concurrency:

```text
Python orchestration / relational resolution
        |
        +--> exact numeric buffers for selected Cells
        |
        v
one coarse Python -> Rust call
        |
        +--> Cell A numeric kernel --+
        +--> Cell B numeric kernel --+
        +--> Cell C numeric kernel --+--> deterministic compact outputs
        +--> Cell D numeric kernel --+
        |
        v
Python provenance/result assembly + serialization
```

This avoids the Windows process-pool costs that motivated concern about multiprocessing:

- no second Python interpreter;
- no per-request `spawn`;
- no DataFrame pickling or IPC;
- shared process address space;
- native parallel CPU execution outside the Python GIL.

Rayon still uses native OS threads internally, normally through a reusable pool. The benchmark must therefore distinguish cold initialization from warm steady-state latency and control oversubscription with PyArrow/NumPy/BLAS/native workers.

## Preconditions for promotion

Do not promote this proto-child merely because Rust is available.

The current post-050 profiler and/or 050.P3 must first identify at least one **compact, stable, materially expensive numerical kernel** whose inputs/outputs are suitable for array-oriented transfer.

Examples that may qualify if profiling supports them:

- derivative smoothing/rolling;
- derivative gradient/division/postprocessing;
- contiguous run/segment classification;
- finite-row filtering and output-index generation;
- display-row selection/downsampling;
- another array transform proven material by current profiling.

Ordinary consecutive Voltage vs Time after 050.6 may already contain too little transform work for Rust to matter. That is an acceptable result and should prevent unnecessary native-code complexity.

## Locked decisions for promotion

1. **Do not port the analysis engine wholesale.** Prototype only measured compact kernels.
2. **Preserve the existing scientific algorithm and semantics.** Rust is an execution change, not a formula redesign.
3. **Use a coarse Python/native boundary.** Prefer one call for all relevant Cell buffers over thousands of fine-grained calls.
4. **Prefer contiguous numeric buffers.** NumPy/Arrow-compatible arrays are the target interface; avoid Python object/string-heavy transfer in the hot boundary.
5. **Measure every boundary copy/conversion.** Zero-copy claims must be demonstrated, not assumed.
6. **Benchmark sequential Rust first.** This isolates native-kernel speed from Rayon speed.
7. **Then benchmark bounded Rayon at 2 and 4 workers.** Do not automatically use all logical CPUs.
8. **Preserve deterministic output order.** Parallel completion must be merged into canonical Cell/series order.
9. **Do not move ORM, SQLite, protocol planning or cache identity into Rust.** Python remains the orchestration/ownership layer.
10. **Do not read Parquet inside Rust in this benchmark unless later profiling independently proves that the Python/PyArrow boundary itself is the kernel under study.** The default comparison is against identical already-resolved numeric input buffers so compute gain can be isolated.
11. **No production Rust dependency is accepted solely on microbenchmark speed.** Packaging/startup/maintenance feasibility must be recorded.
12. **No adaptive zoom, Plotly redesign, migration, result-schema change or `CALC_VERSION` bump.**

## Required benchmark phases

### C0 — exact Python reference kernel

Extract the smallest current Python/NumPy/pandas code path that implements the measured operation. Benchmark it on the same input buffers used for the Rust candidate.

Record:

- input row count and dtypes;
- output size;
- Python/native stage wall time;
- CPU utilization;
- allocation/copy volume where measurable;
- exact/tolerance scientific reference output.

### C1 — sequential Rust kernel

Implement the same algorithm in Rust with parallelism forced off/one worker.

Measure separately:

- Python -> Rust argument/buffer preparation;
- bytes copied across the boundary;
- Rust kernel time;
- Rust -> Python result conversion;
- total candidate wall time.

C1 versus C0 is the authoritative measure of **native-kernel gain**.

### C2/C3 — Rayon across Cells

Using the same Rust kernel and same scientific inputs:

- **C2:** 2 Rayon workers;
- **C3:** 4 Rayon workers.

Parallelize independent Cell jobs first. Do not introduce within-formula parallel reduction/order changes merely to create more work for Rayon.

C2/C3 versus C1 isolates the **parallel Rust gain**.

## Required workload matrix

Use the kernel(s) that current profiling actually identifies. Do not force every Time/Capacity plot through Rust.

At minimum, where applicable:

### Normal Time/Capacity

- one representative single-Cell broad request;
- 3 Cells broad;
- 6 Cells broad;
- **10 Cells broad when representative local data permit**;
- one narrow request to detect boundary overhead dominating small jobs.

### Derivatives

Because post-050.7 derivatives remain a more plausible numerical hotspot, include where the selected kernel applies:

- 1 Cell, All, dQ/dV;
- 3 Cells, All, dQ/dV;
- 6 Cells, All, dQ/dV;
- one dV/dQ case;
- one small derivative range.

If the promoted kernel is unrelated to one of these cases, mark it `NOT APPLICABLE`; do not fabricate a Rust path solely to fill the table.

## First-call and lifecycle measurements

For each Rust candidate record separately:

- extension/module load state;
- first call latency;
- first parallel call including any lazy Rayon-pool initialization;
- warm steady-state median;
- worker count;
- resident-memory delta;
- relevant compiler profile/target settings.

Do not hide one-time startup cost inside warm medians, but do not repeatedly charge a one-time Rayon initialization to every interaction either.

## Scientific parity

The benchmark is performance-only.

For exact selection/index/downsampling operations, require exact output and provenance/index equality.

For floating-point kernels:

- preserve the same mathematical algorithm and operation semantics;
- compare against the existing repository scientific/golden tolerances;
- investigate any systematic drift before accepting a timing result;
- preserve NaN/finite filtering, sign rules, segment boundaries and assignment order where those are part of the existing contract.

A faster candidate with unresolved numerical differences is not an acceptable result.

## Required measurements

For every applicable C row record:

- end-to-end benchmark wall time;
- boundary preparation/conversion time;
- bytes copied or borrowed zero-copy;
- Rust kernel time;
- Rayon parallel-region/queue time where applicable;
- CPU utilization/effective core use;
- peak RSS and temporary allocation estimate;
- worker count;
- relevant PyArrow/NumPy/BLAS/Rayon thread settings;
- output digest/equality/tolerance result;
- deterministic canonical ordering.

Use at least five repetitions where practical, report median and range/min/max, and distinguish cold from warm measurements.

## Required questions and decision output

A promoted child must answer:

1. Which exact kernel was selected and why is it still material after 050.6/050.7/050.8?
2. How much of C0 wall time disappears in sequential Rust after all boundary costs are included?
3. Are buffers actually borrowed zero-copy? If not, how many bytes and milliseconds are copied?
4. How much additional gain comes from 2-way and 4-way Rayon over C1?
5. Is speedup limited by memory bandwidth, nested native threading or insufficient per-Cell work?
6. What is the first-call/Rayon initialization cost versus warm steady-state cost?
7. Is Windows packaged-sidecar integration feasible without unacceptable build/startup complexity?
8. Does the candidate preserve scientific parity and deterministic ordering?

The result must explicitly choose one of:

- **P5-A — no Rust justification:** sequential Rust does not materially beat the existing implementation after boundary cost;
- **P5-B — sequential Rust useful, Rayon not useful:** native kernel helps but cross-Cell native parallelism adds little;
- **P5-C — Rust + bounded Rayon useful:** native kernel and 2/4-way parallelism both provide material stable gains;
- **P5-D — kernel unsuitable for current architecture:** conversion/copy/lifecycle cost erases the computational benefit.

## Likely implementation ownership for the benchmark

Re-inspect at promotion time. A prototype should be isolated from production where practical, for example under a benchmark/test-only native module plus the existing performance profilers.

Do not wire the Rust path into production request handling merely to measure it.

## Verification requirements after promotion

At minimum:

- focused tests for the exact Python reference kernel and Rust equivalent;
- scientific/golden parity at repository-defined tolerances;
- deterministic ordering across 1/2/4 Rayon workers;
- cold/warm lifecycle measurements;
- Windows build/import smoke check for the native extension if the benchmark reaches packaging feasibility;
- `git diff --check`;
- canonical `python scripts\preflight.py`.

Do not claim installed-app or browser speedup from backend/native microbenchmarks alone.

## Explicit out of scope

Until separately promoted, do not:

- replace the full analysis engine with Rust;
- move SQLite/ORM/protocol planning into Rust;
- implement production Rust request routing;
- combine concurrent Python reads with Rust in the same benchmark result table as if one mechanism caused the whole speedup;
- add Python multiprocessing by default;
- change scientific formulas/result schemas;
- implement adaptive zoom or Plotly trace changes;
- add migrations or bump `CALC_VERSION` for benchmark-only work.

## Promotion criteria

Promote only when:

1. 050.8 is stable/review-clean;
2. current profiling or 050.P3 identifies a compact material numerical kernel;
3. the user/spec author explicitly chooses to test Rust/Rayon;
4. the numeric child remains a benchmark/decision gate;
5. 050.P6 composition remains separate so combined speedups can be attributed correctly.

The proto ID `050.P5` remains historically reserved after any future promotion and must not be reused.
