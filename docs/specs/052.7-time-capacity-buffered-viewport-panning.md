# 052.7 — Time/Capacity buffered viewport panning

**Status:** Active child — implemented, exploratory
**Parent:** Spec 052 — Time/Capacity cycle navigation
**Repository:** `mattiafelice-palermo/cellxplorer`
**Branch:** `feature/time-capacity-cycle-navigation`
**Reason for child:** explicit user request. After 052.3–052.6 made each drag step fast, dragging still read as a slideshow — "each cycle is shown one after the other" rather than the line moving through the plot. This child makes the slider a viewport onto a continuous timeline.

**The per-window model is retained and reachable as a fallback.** Nothing in this child deletes it.

## Why speed could not fix this

Every response is re-zeroed at its own first finite point, so consecutive windows are separate coordinate systems:

```
cycles   1-3 : x 0.00 → 5104.88 min
cycles  50-52: x 0.00 →  703.91 min
cycles 150-152: x 0.00 →  756.78 min
```

Each drag step therefore hands Plotly a fresh curve starting at zero, and the axis rescales to it. The frame never moves, so the curve is *replaced* rather than translated. No amount of latency work changes that — a faster slideshow is still a slideshow.

Panning needs two things the per-window model cannot provide:

1. **absolute coordinates**, so cycle 150 sits further right than cycle 50;
2. **more data loaded than is visible**, or there is nothing off-screen to drag into view.

## Design

### Backend — opt-in absolute positioning

`consecutive_time_request_facts` already resolves the prefix and origin needed to place a window at its true coordinate; it was gated to refinements, where lining a refined patch up with the overview is the whole point. Two gates are widened:

- `_build_jobs` resolves origin facts when `refinement` **or** an explicit `display_origin_cycle_start` was supplied;
- `_cell_result` applies the prefix whenever one was resolved, rather than only for refinements.

A new `ComputeRequest.absolute_time_origin_cycle` exposes this, and it is part of the **render cache identity** — two responses for the same cycles differ in their coordinates when anchored differently.

Verified:

```
origin = cycle 1
cycles   1-3 : x     0.00 →  5104.88
cycles  50-52: x 16134.38 → 16838.29
cycles 150-152: x 40319.87 → 41076.64
```

Opt-in: with no origin the behaviour is byte-identical, which the existing suites confirm.

### Frontend — buffered viewport

`timeCapacityViewportBuffer.ts` holds the pure policy. During a moving preview the request covers a **buffer** wider than the window, anchored at cycle 1, and the plot pins its x-range to the window's absolute span inside that buffer. Pointer movement then moves the range through data already held.

Two sizing rules mattered, both found by measurement rather than design:

- **A window multiple alone is useless for a narrow window.** Three cycles out of 324 gives ~15 cycles of context at factor 2, which a moving pointer leaves immediately — the first implementation refetched on nearly every step. The buffer therefore also spans at least `TIME_CAPACITY_BUFFER_MIN_EXTENT_FRACTION` (10%) of the range.
- **The point budget must scale with the buffer, and `viewport_width` with it.** `time_capacity_display_budget` caps a response at `(2 × viewport_width × 6) / visible_cells`, so asking for more points at the default width returns the same number spread wider — making the visible window *coarser*. Buffered requests raise `viewport_width` to 6000.

The buffer is resolved **during render, not in an effect**. An effect left the first render after each pointer move without a buffer, so the per-window request was issued and then aborted a render later — two requests per step, the first pure waste. This was visible in the first browser run as an `ERR`/`ok` pair on every step.

## Results

Browser-measured against the running application, real library, five Cells, 324 cycles, 3-second drag across 25% of the slider:

| | per-window (052.6) | buffered panning |
|---|---|---|
| requests during the drag | 41 | **3** |
| aborted requests | 1 | **0** |
| x-axis range movements | 0 (axis re-fitted each time) | **58** |
| what the user sees | discrete replacement | viewport sliding along one timeline |

Fifty-eight viewport movements from three data fetches: nearly every pointer move is a client-side range change over resident data, which is the panning behaviour requested.

Gates: focused policy tests (28 frontend navigation tests), canonical preflight **PASS** 4/4, browser acceptance **RUN**.

## Known issues

### K1 — The axis jumps back to zero on release

On release the committed range is fetched through the normal per-window path, which re-zeroes, so the x-axis snaps from absolute coordinates back to `0 → ~760`. Measured: the viewport ended a drag at `[5520, 6226]` and the committed view rendered `[0, 760]`.

Fixing this means deciding what the committed plot's x axis *means*. Keeping absolute coordinates on release is arguably more correct — a Time axis would show true elapsed time — but it changes what every ordinary Time/Capacity plot displays, and flows into exports and saved plots. **That is a product decision, not an implementation detail, so it is deliberately left open.**

### K2 — Very fast drags still outrun the buffer

A drag traversing all 324 cycles in 3 seconds moves ~108 cycles/second. With a 3-cycle window the content turns over ~36 times a second, faster than any buffering can present, and refills become frequent again. Panning behaves well at ordinary browsing speed; a full-range flick still degrades toward the per-window behaviour. Velocity-aware buffer sizing is the obvious next step if this matters.

### K3 — Buffer sizing is tuned against one dataset

`TIME_CAPACITY_BUFFER_MIN_EXTENT_FRACTION` and `TIME_CAPACITY_BUFFER_FACTOR` were chosen against one 324-cycle, five-Cell analysis. Libraries with very different cycle counts or Cell counts have not been checked.

## Fallback

`timeCapacityPanningEnabled()` returns the compiled default, overridable at runtime:

```js
localStorage.setItem("cellxplorer.timeCapacityPanning", "off")  // per-window model
localStorage.setItem("cellxplorer.timeCapacityPanning", "on")
localStorage.removeItem("cellxplorer.timeCapacityPanning")      // compiled default
```

With panning off, the request path, cache identity and rendering are exactly the 052.6 behaviour — the backend origin field is simply never sent.
