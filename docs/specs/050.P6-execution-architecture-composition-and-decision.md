## Purpose

Combine only the execution mechanisms that the isolated 050.P3 and 050.P5 benchmarks have already shown to be useful, then choose the smallest production architecture that gives most of the measured user-relevant gain.

This proto-child exists specifically to prevent attribution mistakes. It must answer:

> If concurrent cache reads, Python threads, sequential Rust and/or Rayon each help in isolation, do their gains actually compose in the real multi-Cell request path, or do I/O contention, memory bandwidth, serialization and nested native threading erase part of the benefit?

This is a **composition and final decision gate**, not a production implementation child.

## Preconditions for promotion

Do not promote P6 before there is actual isolated evidence to compose.

At minimum:

- 050.P3 must have a current sequential baseline and quantified Python/read-concurrency result;
- 050.P5 must either identify a useful Rust candidate or explicitly conclude that Rust is not justified.

If P3 shows no useful concurrency and P5 shows no useful native kernel, P6 may be unnecessary; record that conclusion instead of running combinations for completeness.

## Locked decisions for promotion

1. **Do not repeat the full isolated benchmark programme.** P6 consumes P3/P5 evidence and tests only justified combinations.
2. **Preserve one common scientific workload and baseline.** Combined rows must be directly comparable to the isolated rows.
3. **Calculate expected versus actual combined gain.** State whether mechanisms compose additively, sub-additively, neutrally or negatively.
4. **Control nested parallelism.** Do not let Python threads, PyArrow, BLAS/NumPy and Rayon all fan out unchecked.
5. **Preserve deterministic output order, formulas, provenance and result identity.**
6. **Do not share live SQLAlchemy sessions/ORM entities across workers.**
7. **Do not serialize whole source DataFrames to process workers merely to obtain CPU parallelism.**
8. **Python multiprocessing is an optional control only if P3/P5 leave a meaningful unanswered GIL-bound case.** It is not mandatory.
9. **No per-request process spawning.** Any process experiment must use a bounded persistent lifecycle so Windows `spawn` is not charged per Cell/plot.
10. **No adaptive zoom or Plotly architecture changes in this child.** Viewport/data-density behavior remains a separate frontend concern.
11. **Record frontend/Plotly contribution after the best backend candidate.** Backend execution work stops being the priority if frontend/transport becomes dominant.
12. **The output is an architecture recommendation and later implementation scope.** Do not quietly ship the winning combination from the benchmark child.

## Required composition rows

Run only rows justified by prior evidence.

### D1 — best read concurrency + sequential existing compute

If P3 showed useful read overlap but weak whole-Cell threading, reproduce the best bounded read-only configuration on the representative end-to-end backend path.

This provides the production-shaped control for "I/O overlap only".

### D2 — best read concurrency + sequential Rust kernel

Run only if:

- P3 showed useful read overlap; and
- P5 showed useful sequential Rust acceleration.

This isolates whether read overlap and native compute speed compose **without** parallel Rust.

### D3 — best read concurrency + best bounded Rayon configuration

Run only if P5 showed useful Rayon scaling.

This is the leading hybrid architecture candidate:

```text
bounded Python/native read concurrency
        |
        v
exact numeric buffers for selected Cells
        |
        v
one coarse Rust call
        |
        v
bounded Rayon cross-Cell compute
        |
        v
ordered Python provenance/result assembly
```

### D4 — whole-Cell Python threads + Rust/Rayon

Run only if P3 demonstrated useful whole-Cell threading **and** there is a concrete architecture where this does not duplicate or oversubscribe the same work that Rayon is already parallelizing.

Do not run D4 merely because both mechanisms were individually fast.

### E1/E2 — optional persistent process control

Only if the isolated results leave substantial Python/GIL-bound CPU work that Rust did not address and a process comparison remains scientifically/architecturally useful:

- **E1:** 2 persistent Python processes;
- **E2:** 4 persistent Python processes.

Process workers receive compact immutable job descriptors and open exact required caches themselves. Do not pass ORM sessions or large pandas DataFrames.

If threads/Rust already answer the measured bottleneck, record process testing as `NOT JUSTIFIED` rather than adding complexity.

## Representative workload matrix

Use the common benchmark matrix established by P3/P5, with emphasis on the user's real multi-Cell workload:

### Normal Time/Capacity

At minimum where local data permit:

- 1 Cell, All, Time axis;
- 3 Cells, All, Time axis;
- 6 Cells, All, Time axis;
- **10 Cells, All, Time axis**;
- 6/10 Cells, one representative narrow range;
- one capacity-axis broad case.

### Derivatives

Where the Rust kernel applies:

- 1 Cell, All, dQ/dV;
- 3 Cells, All, dQ/dV;
- 6 Cells, All, dQ/dV;
- one dV/dQ broad case.

### Controls

- exact persisted result-cache hit: must bypass all execution machinery;
- one single-Cell case: detects unnecessary dispatch overhead;
- one continuation-boundary case when representative data exist;
- one narrow viewport-like request so the winning backend path can later be compared with a separate adaptive-zoom study.

## Attribution table

The promoted child must maintain one table that includes, for every tested workload:

- sequential Python baseline;
- best isolated P3 read-concurrency result;
- best isolated P3 whole-Cell-thread result;
- best isolated P5 sequential-Rust result where applicable;
- best isolated P5 Rayon result where applicable;
- each justified D/E combination.

For every combination report:

1. expected wall time if the isolated gains composed perfectly;
2. actual measured wall time;
3. absolute and percentage delta from baseline;
4. delta from the best isolated strategy;
5. explanation for any lost/additional gain supported by profiler evidence.

Do not claim "hybrid is faster" without preserving the isolated rows that explain why.

## Measurements

Record at minimum:

- total backend wall time;
- metadata/planning time;
- raw/prepared read/decode time;
- Python->Rust boundary/copy time where applicable;
- Rust kernel and Rayon time where applicable;
- Python transform time that remains outside Rust;
- result assembly/serialization;
- worker dispatch/queue time;
- CPU utilization/effective core use;
- peak RSS and temporary allocation/copy estimate;
- physical row groups/rows/bytes read;
- worker counts for Python/Rayon/process candidates;
- PyArrow/NumPy/BLAS/Rayon native-thread settings;
- scientific digest/equality and deterministic output ordering.

Use at least five controlled repetitions where practical and distinguish cold initialization from warm steady-state when native/process lifecycle is involved.

## End-to-end boundary

After identifying the best backend execution candidate, measure or reuse an installed-app/browser profile when available to report:

- backend compute/serialize;
- HTTP/fetch/parse;
- frontend trace/layout preparation;
- Plotly completion;
- total interaction time;
- Plotly trace count/returned point count.

This does **not** authorize frontend changes. It determines whether another backend execution child is still the highest-value next step or whether the bottleneck has moved to viewport density, Plotly or transport.

## Required decision output

The promoted child must end with one explicit architecture decision:

### P6-A — remain sequential

Choose when isolated/combined execution strategies do not provide a material stable user-relevant gain after memory/I/O/lifecycle costs.

### P6-B — bounded Python/read concurrency only

Choose when the simplest thread/read strategy captures most of the gain and Rust adds insufficient net benefit.

### P6-C — Rust kernel without Rayon

Choose when sequential Rust materially reduces a proven CPU kernel but native parallelism/read concurrency adds little or creates contention.

### P6-D — bounded Python/read concurrency + Rust/Rayon hybrid

Choose when the hybrid materially outperforms the isolated mechanisms while keeping RAM, I/O, startup and scientific parity acceptable.

### P6-E — persistent Python processes

Choose only with explicit evidence that a remaining Python/GIL-bound boundary survives the thread/Rust experiments and the process result is materially better after spawn lifecycle, IPC, RAM and I/O costs.

### P6-F — backend no longer dominant

Choose when the best backend candidate is already small enough that frontend/Plotly, transport or another measured stage dominates. Author a separate child for that boundary rather than adding execution complexity.

For any implementation outcome, specify the **smallest worker count** that captures most of the gain; do not default to four merely because four was tested.

## Production implementation handoff

P6 itself does not implement the winner.

If the decision authorizes production work, author a new normal numeric child that contains only the chosen architecture, exact ownership/lifecycle, failure/fallback behavior, packaging consequences and acceptance tests.

Do not carry all rejected alternatives into that implementation spec.

## Verification requirements after promotion

At minimum:

- scientific/golden parity across every tested composition;
- deterministic ordering under out-of-order completion;
- exact-cache-hit bypass regression;
- lifecycle/teardown test for any reusable worker infrastructure used by the benchmark;
- RAM/I/O/oversubscription measurements;
- `git diff --check`;
- canonical `python scripts\preflight.py`.

Browser/manual evidence is required for claims about total user-visible or Plotly latency and must be recorded as `NOT RUN` when unavailable.

## Explicit out of scope

Until separately promoted, do not:

- ship production execution pools/native routing;
- change scientific formulas/result schemas;
- redesign persistent cache layout;
- add whole-Cell RAM caches/speculative prefetch;
- implement adaptive zoom or Plotly trace consolidation;
- reintroduce 050.P2 progressive streaming;
- add migrations or bump `CALC_VERSION` for benchmark-only work.

## Promotion criteria

Promote only when:

1. 050.8 is stable/review-clean;
2. P3/P5 isolated evidence exists and identifies at least one useful mechanism to compose;
3. the user/spec author explicitly chooses to perform the composition/architecture decision;
4. the numeric child remains benchmark/decision-only;
5. any production implementation is deferred to a later dedicated numeric child.

The proto ID `050.P6` remains historically reserved after any future promotion and must not be reused.
