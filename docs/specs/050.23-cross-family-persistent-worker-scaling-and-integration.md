## 1. Goal

After Rate Capability, DCIR, Chargeability, Steps and Cycles have each reached their best justified serial implementation in Specs 050.18-050.22, determine whether large multi-Cell workloads should use CellXplorer's already-resident Python multiprocessing infrastructure.

The key question is not whether one Cell is individually slow. It is whether the **aggregate independent per-Cell work** across a realistic multi-Cell request is large enough that four or eight already-warm worker processes beat the complete serial production route after queueing, serialization/deserialization, cache I/O, result transfer and deterministic merge are all counted.

The required scaling matrix is **4, 8, 12 and 16 Cells**. Compare the final serial implementation against **4 persistent workers** and **8 persistent workers**. A 1-Cell serial control may be retained as a sanity check, but it is not part of the promotion decision.

Time/Capacity is **not** part of the benchmark matrix and must not be re-optimized in this child. It is relevant only because Specs 050.14-050.15 already established the resident worker lifecycle that this child must reuse or safely generalize rather than duplicate.

This child is both a benchmark and, only where the evidence passes the gates below, a bounded production-integration child. A valid outcome is that some or all families remain serial.

## 2. Locked decisions

1. Benchmark exactly these five analysis families:
   - Rate Capability;
   - DCIR;
   - Chargeability;
   - Steps;
   - Cycles.
2. Do **not** benchmark or optimize Time/Capacity performance in this child.
3. Use the **review-clean final implementations from 050.18-050.22** as the serial baselines. Do not compare against the older 050.17 numbers except for historical context.
4. Required Cell counts are **4, 8, 12 and 16**.
5. Required execution candidates are:
   - `S1`: current serial route;
   - `P4`: four already-warm persistent Python worker processes;
   - `P8`: eight already-warm persistent Python worker processes.
6. Process startup/import/warmup is outside measured request latency because production workers are resident before an interactive request. Queueing, pickle/IPC, worker cache reads, worker computation, return transfer and owner merge are inside the measured boundary.
7. Do not create one pool per family. There must be at most **one application-level persistent analysis pool** if production integration is promoted.
8. Do not pickle complete Pandas DataFrames merely to obtain parallelism. ORM/session state must remain in the owner process.
9. Shared/request-wide work remains owner-owned where that is already an optimization. In particular, multiprocessing must not undo request-local protocol/context reuse established by 050.18-050.20.
10. Exact persisted result hits never dispatch workers and never build worker-only jobs.
11. Worker selection must be deterministic from request/host facts such as family, Cell count, available memory and logical CPUs. Never use timing history from previous requests as runtime policy.
12. Any production worker path must have the exact serial path as a fail-closed fallback.
13. Do not change scientific formulas, result meaning, source ownership, parser identity, cache identity or export semantics.

## 3. Why this child exists separately from 050.18-050.22

Each family child deliberately optimizes serial/vectorized/data-access behavior first. That ordering is retained.

A family can become individually fast while still accumulating enough work across many Cells to make parallel execution valuable. For example, 40 ms of independent CPU/data work per Cell is only a small single-Cell cost but becomes approximately 480 ms across 12 Cells. With a resident four-worker pool, the theoretical parallel portion can approach three waves rather than twelve serial units, provided IPC and memory/I/O contention stay small.

Therefore a fixed rule such as "do not test multiprocessing because one Cell is under 100 ms" is not sufficient. 050.23 evaluates the **aggregate** multi-Cell route after all family-specific serial cleanup is complete.

## 5. Architecture before benchmarking

### 5.1 Separate owner work from worker work

For each family, document the final request-wide and per-Cell boundaries before writing a process candidate.

The owner process must retain:

- SQLAlchemy `Session` and ORM objects;
- analysis/request-context resolution;
- source/parser/current-version ownership;
- result-cache key/hit/store ownership;
- request-wide protocol reconstruction or protocol facts that are deliberately reused across Cells;
- any cross-Cell aggregation that scientifically requires all Cells together;
- final deterministic response ordering/provenance assembly where worker completion order must not leak into output.

Workers may receive only immutable/pickle-safe data needed for genuinely independent work. Prefer compact scalars, tuples, dictionaries, arrays or existing immutable descriptors. If workers can safely read the canonical Parquet cache directly from hash/parser/version/index descriptors, prefer that over sending an already-materialized DataFrame through IPC.

### 5.2 Do not undo previous optimizations

The process candidate must preserve the ownership improvements already accepted in 050.18-050.22.

Examples:

- Chargeability must not reconstruct an identical protocol once per worker/Cell after 050.20 reduced six identical reconstructions to one request-local reconstruction.
- DCIR must not rebuild source-wide prepared frames once per series after 050.19 moved preparation to one source-local owner.
- Rate Capability must not restore repeated full-frame scans removed by 050.18.
- Steps/Cycles must consume their final post-050.21/050.22 representations rather than reintroducing legacy helper paths solely because they are easier to pickle.

A process candidate that wins only by bypassing the review-clean scientific/optimization path is invalid.

### 5.3 One pool, not family pools

The benchmark may initially use benchmark-only adapters to prove family job boundaries, but production promotion must converge on one resident pool lifecycle.

Preferred production shape if at least one family wins:

```text
backend startup
    -> one persistent analysis process pool

owner request
    -> exact result hit? return immediately
    -> resolve SQL/request/shared facts
    -> deterministic family execution policy
       -> serial final implementation
       -> or compact immutable per-Cell jobs to shared pool
    -> deterministic owner merge
    -> persist/serialize response
```

If no non-Time/Capacity family passes the promotion gate, do not generalize the production pool merely for architectural tidiness.

## 7. Candidate modes

### S1 — current serial route

This is the exact review-clean family implementation after 050.22. Do not create a simplified "serial benchmark" helper that skips route ownership, persistence or response assembly.

### P4 — four persistent workers

Use four fully warmed spawned workers. Warmup/import/PID acknowledgement must complete before measured requests.

P4 should reuse the already-resident production worker resource if the architecture has been safely generalized; during benchmark-only development it may use an isolated harness with the same initializer/lifecycle contract so long as worker startup is excluded and no second pool is shipped in production.

### P8 — eight persistent workers

Use eight fully warmed spawned workers. P8 is a benchmark candidate even though 050.15 rejected eight active Time/Capacity workers. The five family jobs may have substantially smaller IPC and memory footprints, so that older result is not sufficient to reject P8 here.

However, production P8 would increase the globally resident pool size. It therefore has the stronger memory/host/integration gate in Section 11.

Use **five warm repetitions** for every promotion-critical point. Keep the fixture and scientific input identical across S1/P4/P8.

- bracket a P4/P8 block with serial controls or otherwise demonstrate that serial drift did not materially change the conclusion;
- fully warm and PID-verify each pool before its timed samples;
- report ranges, not only the median;
- if a promotion point has >15% timing spread or reverses candidate order across samples, run one focused confirmation block before promoting it.

Do not rerun the whole matrix merely because one noisy point needs confirmation.

## 11. Promotion policy

### 11.1 P4 family promotion

For each family independently, choose the lowest tested Cell threshold `T` from `{4, 8, 12, 16}` where P4 qualifies.

P4 qualifies at `T` only if:

1. complete-route p50 is at least **15% faster** than S1 **and at least 10 ms faster** at `T`;
2. the same P4 mode remains non-regressing and still materially favorable at every larger tested Cell count where a larger point exists;
3. all scientific/order/provenance parity checks pass;
4. worker inputs contain no ORM/session state and no complete DataFrame transfer;
5. exact hits bypass the pool;
6. the route has a deterministic serial fallback when the pool is not ready/available;
7. no previous family-specific optimization is undone;
8. worker/owner memory remains within the existing four-worker host gate and no request exhibits unbounded growth.

Below `T`, production must choose S1 **before** doing process-only preparation. A family for which no threshold qualifies remains entirely serial.

The runtime gate may be based on Cell count plus existing host-resource facts. Do not create a timing-adaptive threshold.

### 11.2 P8 benchmark and global-pool promotion

P8 is compared both to S1 and P4. Because eight workers would change the resident application pool rather than merely reuse the already-resident four processes, P8 has a stronger gate.

Production may use an eight-worker global pool only if all of the following hold:

1. at least one family has a tested threshold where P8 beats P4 by **>=15% and >=15 ms** on the complete route;
2. P8 remains non-regressing at larger tested Cell counts for every family that would use P8;
3. the host exposes at least **12 logical CPUs** and sufficient measured available memory for eight workers plus a 512 MiB owner/system reserve;
4. combined parent + warm-worker RSS for P8 is no more than **1.5x** the equivalent P4 resident footprint at the promotion workload;
5. the shared pool can cap Time/Capacity execution to its existing four-worker behavior without changing Time/Capacity scientific or routing semantics;
6. families that qualify only for P4 can likewise cap their active submissions to four workers even if the global pool contains eight processes;
7. the additional idle/warm resident-worker memory is documented and accepted by the same deterministic host gate.

If P8 fails any condition, keep the production pool at four workers. The P8 benchmark evidence remains useful documentation; do not create a second eight-worker pool beside the existing four-worker pool.

### 11.3 No forced global concurrency

It is acceptable and expected that the final policy may differ by family, for example:

```text
Rate Capability: serial <8 Cells, P4 >=8 Cells
DCIR: serial at all tested counts
Chargeability: serial <12 Cells, P4 >=12 Cells
Steps: serial at all tested counts
Cycles: P4 >=8 Cells
```

This example is illustrative only. The implementation must use measured thresholds from the actual final family routes.

## 12. Production integration if any family wins

Only after the benchmark matrix identifies at least one P4/P8 winner:

1. extract/generalize the existing worker lifecycle only as much as necessary for one application-level pool;
2. keep Time/Capacity scientific job construction/execution in its current owner module;
3. preserve backend lifespan startup/shutdown and distinct-PID warmup semantics;
4. add narrow family-specific top-level worker entry points or immutable job types; do not create a giant generic scientific switch containing all family logic;

6. use deterministic per-request ordinals for merge;

9. keep exact hits above all worker routing;
10. re-run the promoted complete-route matrix after integration because lifecycle refactoring can change the measured win.

If no family qualifies, stop after benchmark/evidence/tests and leave production worker ownership unchanged.

## 21. Implementation record

The final implementation uses the existing resident pool in
`backend/app/services/time_capacity_workers.py`; no second pool or eight-worker
production pool was added. `backend/app/services/analysis_family_workers.py`
