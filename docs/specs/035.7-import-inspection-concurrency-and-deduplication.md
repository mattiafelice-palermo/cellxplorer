# 035.7 — Import inspection concurrency and repeated-work optimization

**Status:** Plan  
**Parent:** [035 — User experience and workflow optimization](035-user-experience-and-workflow-optimization.md)  
**Depends on:** 035.6 clean review.  
**Scope:** Bounded filesystem concurrency, one database identity snapshot, and safe reuse of
inspection work.  
**Review document:** `reviews/035.7-import-inspection-concurrency-and-deduplication-review.md`

## Goal

Reduce large-batch waiting time without weakening source identity, determinism, or SQLite safety.
Parallelize independent filesystem work conservatively, stop loading all registered source rows for
every candidate, and reuse header metadata only after content identity is re-proven.

## Current performance hazards to verify

- `backend/app/routers/files.py::list_import_sources` scans selected folders serially.
- `inspect_import_paths` calls `_inspect_import_path(Path(path), db)` in a serial comprehension.
- `_inspect_import_path` hashes, reads header metadata, and calls `import_match_info`.
- `import_match_info` performs `db.query(SourceFile).all()` for every candidate.
- A SQLAlchemy Session is passed into each inspection call.
- final Cell registration is serialized and transactional.
- scientific cache building already has a separate ProcessPool path.

Verify current code before editing. Do not overwrite unrelated import inspection or lifecycle work.

## Measure first

Before changing code, add lightweight instrumentation or a disposable benchmark that separates:

- folder listing/stat time;
- checksum time;
- header-read time;
- database identity-matching time.

Record the test environment and batch shape. Do not commit private source files. A synthetic
sleep/fake-I/O test can prove concurrency contracts, but it is not a performance claim.

## Locked folder-discovery concurrency

- Do not parallelize traversal inside one folder tree.
- When two or more top-level folders are selected, scan at most two roots concurrently.
- Loose-file stat/filter work may remain serial.
- Deduplicate and sort with exactly the same deterministic result as before.
- Progress updates from 035.6 continue to reflect completed roots.
- Do not try to detect HDD/NVMe/network type.
- If only one folder is selected, use the simple serial traversal path.

Reason: multiple roots can be independent devices/locations, but unbounded traversal inside one tree
can make rotational/network storage slower and harder to reason about.

## Locked file-inspection concurrency

Use a bounded `ThreadPoolExecutor`.

Worker count:

```python
min(4, max(1, len(paths)))
```

Expose a small helper so tests can pin this decision.

Each worker performs only filesystem/library work:

- path existence/type/extension validation;
- one initial stat capture;
- checksum calculation;
- Neware header metadata read;
- one final stat capture to detect a file that changed during inspection;
- metadata-preview shaping that does not need the database.

It must not receive:

- SQLAlchemy Session;
- ORM rows;
- mutable database-owned objects;
- frontend progress state.

If size or `mtime_ns` changes between the initial/final stat, return a structured unstable-file
result or the existing safe error; do not accept a checksum/header combination from a moving file.

Use indexed futures with `as_completed` for progress, then restore original input order in the
endpoint result.

## Database matching snapshot

Before starting workers, load existing source identity once.

Add a compact immutable structure in a focused service, preferably:

```text
backend/app/services/import_inspection.py
```

Example:

```python
@dataclass(frozen=True)
class ImportMatchCandidate:
    source_file_id: int
    hash: str
    filename: str
    barcode: str | None
    channel: str | None
    start_time: str | None
    remarks: str | None
    registered: bool
    archived: bool
    cell_id: int | None
    cell_name: str | None
    test_id: int | None
    test_name: str | None
    path: str
    location_status: str
    parse_status: str
```

Build:

- exact-hash dictionary;
- compact soft-match candidate list or indexes;
- enough registration/archival linkage to reproduce the current payload.

Requirements:

- use eager loading or bounded relational queries;
- do not trigger per-row lazy relationship access;
- do not include raw scientific data or Parquet reads;
- take the snapshot before threads start;
- perform matching through pure functions after worker results return.

Preserve current matching rules:

- exact hash wins;
- an exact source linked to an active Cell is a duplicate;
- archived blocking-source cleanup/reuse semantics remain;
- possible update requires the same strong combination of weak signals;
- generic same channel or filename alone is not enough;
- response payload remains backward compatible with the current import contract.

## Inspection result and fingerprint

Return and retain:

```json
{
  "hash": "...",
  "size": 123,
  "mtime_ns": 123456789,
  "metadata": {"...": "..."},
  "raw_metadata": {"...": "..."}
}
```

Do not expose a second inconsistent header representation if existing normalized/raw fields already
contain everything final registration needs. If backend-only reuse needs the parsed metadata,
include a narrowly scoped optional `inspection` payload in the draft request rather than trusting
arbitrary editable UI metadata.

## Safe final-registration reuse

Final registration still:

- resolves the source path;
- captures current stat;
- recomputes the checksum, or uses an equivalent full-content proof already performed inside the
  same request;
- performs final duplicate enforcement in the transaction;
- rejects a source that changed since inspection.

After the final checksum equals the inspected checksum:

- reuse inspected header metadata instead of reading the same header again;
- ignore/reject stale client metadata when checksum differs;
- preserve user-edited Cell metadata and scientific overrides as separate explicit fields;
- do not let an inspection hint overwrite Cell metadata silently.

This child may extend a source/draft with:

```json
"inspection": {
  "hash": "...",
  "size": 123,
  "mtime_ns": 123456789,
  "header_metadata": {"...": "..."}
}
```

The backend treats it as a cache hint, not authority.

## Repeated work to remove

Remove only work that is proven redundant:

- one database source-list query per file → one batch snapshot;
- second header read after an equal final checksum → reuse inspected result;
- repeated path normalization/stat calls inside one helper where one stable result suffices.

Do not remove:

- full checksum/content proof before durable registration;
- final transactional exact-duplicate check;
- file-stability detection;
- cache identity validation;
- any existing continuation-chain validation and provenance rules.

## Work that remains serialized

- all SQLite membership writes;
- final duplicate check;
- Cell/Test/SourceFile/TestFile/folder/replicate creation;
- commit/rollback;
- activity recording tied to the transaction.

Do not parallelize database inserts.

## Progress and failure behavior

- Update the 035.6 inspection job as futures complete.
- Completed count is monotonic even when output order is restored later.
- Current filename may reflect the latest started/active file; do not claim only one file is active
  when several workers are running. Preferred copy:
  `Inspecting 4 files · latest completed: cell_047.ndax`.
- One worker failure follows the endpoint’s current batch error policy.
- On fatal request failure, cancel pending futures where possible; already-running workers may finish
  but cannot mutate database/frontend state.
- Background job is marked failed.

## Required tests

- one registered-source snapshot build per inspection batch;
- no Session/ORM object passed into workers;
- worker bound is 1–4;
- multiple futures complete out of order but response order matches request;
- exact duplicate parity with prior rule;
- possible-update parity with prior rule;
- archived exact-match behavior;
- one folder remains serial;
- multiple roots use no more than two workers and retain deterministic ordering;
- moving-file stat mismatch fails safely;
- final equal checksum reuses header metadata;
- changed checksum ignores/rejects stale client metadata;
- final database duplicate check remains;
- progress updates are monotonic;
- scientific-cache ProcessPool behavior is unchanged.

Avoid wall-clock assertions in the main suite. Use fake executors, barriers, call counts, and ordered
results. Record before/after timing only when actually run on disposable representative data.

## Acceptance criteria

- Large inspection batches use bounded I/O concurrency.
- Database identity data are loaded once per batch.
- SQLAlchemy thread safety is preserved.
- Input order and identity semantics remain deterministic.
- Integrity checks are not removed to obtain speed.
- No new N+1 or per-file full-table database scan remains.
