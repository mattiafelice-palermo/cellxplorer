## 1. Goal

Reduce the current Rate Capability warm result-cache-miss latency as far as is reasonably justified by measurement, while preserving every existing scientific, protocol-recognition, validation, provenance, ordering, cache and export contract.

This child is deliberately broader than a one-function micro-optimization. The 050.17 profile identifies `extract_pair_executions()` as the dominant boundary, but the implementation must inventory and address **every measured Rate Capability cost that can produce a meaningful end-to-end gain**, re-profile after each promoted tranche, and stop only when the remaining costs are too small, too risky, or insufficiently attributed to justify further production complexity.

Time/Capacity is out of scope.

## 2. Locked baseline and why this child is first

The review-clean 050.17 five-family matrix measured the current production route using one committed golden Cell and six source-distinct/content-identical relational clones, three warm repetitions, forced result-cache misses and exact persisted hits.

Authoritative Rate Capability baseline:

| Workload | p50 |
| --- | ---: |
| 1 Cell forced miss | **219.61 ms** |
| 6 Cells forced miss | **1267.82 ms** |
| 6 Cells exact persisted hit | **14.99 ms** |
| dominant parent | `execution_extraction` |
| dominant parent p50/share | **1091.84 ms / 86.12%** |

The corrected deep profile attributes the largest execution children to approximately:

- `execution_phase_row_filtering`: **~658 ms** at six Cells;
- `measurement_filtering_grouping`: **~225 ms**;
- remaining direct `execution_extraction` residual: **~90 ms**;
- cutoff validation and capacity/current/rate extraction are measured separately and are materially smaller;
- protocol reconstruction is much smaller than the execution path and must not be mistaken for the principal cause of the ~1.27 s route.

The first optimization hypothesis is therefore to eliminate repeated full-DataFrame scanning/filtering in execution extraction. That hypothesis is **not** permission to ignore secondary costs after the dominant scans are removed.

The current execution loop repeatedly performs operations equivalent to:

1. select measurement rows for one protocol-pair measurement step;
2. group those rows into occurrences;
3. derive each occurrence cycle;
4. rescan the full raw frame for all phase steps in that cycle;
5. rescan again for the paired reference phase;
6. evaluate cutoff completion;
7. extract capacity/current/rate values;
8. repeat for both charge and discharge directions and every pair.

### Meaningful-work rule

A stage/candidate is worth production work when evidence shows a realistic route-level benefit, not merely because it can be made locally faster. As a default decision gate, investigate a stage when it is at least about **5% of the six-Cell miss or 10 ms p50**, or when several repeated operations from the same ownership boundary plausibly combine above that level.

Do not spend production complexity on 1–2 ms micro-optimizations.

## 6. Optimization tranche A — indexed execution ownership

The first implementation tranche should remove repeated whole-frame filtering while retaining current DataFrame/scientific semantics.

Preferred direction:

- normalize/inspect the raw frame once per source/Cell;
- build bounded request-local lookup structures for the columns already in memory, such as:
  - rows or positional ranges by `step_index`;
  - rows/ranges by `(cycle, step_index)` where useful;
  - execution-group boundaries for measurement steps;
- use those structures to obtain measurement, phase and reference rows without rescanning the entire raw frame for every occurrence/pair;
- preserve `_ordered()` semantics and exact row order;
- avoid copying the complete raw frame per lookup;
- keep the lookup request-local unless a later measured case justifies persistent cache state.

The implementer may choose a better current-code representation after inspection. The locked requirement is the outcome: repeated `raw[...]`/`.isin(...)` scans across the complete frame must not remain merely because they are convenient if a bounded indexed alternative produces a material complete-route win.

### Constraints

- Do not add a new SQLite schema or persistent scientific cache merely for this optimization without a separately demonstrated need.
- Do not reopen original source files.
- Do not create a global unbounded DataFrame cache.
- Do not pass ORM/session state to workers.
- Do not introduce concurrency before measuring the optimized serial/vectorized path.

## 7. Optimization tranche B — measurement grouping and numeric reuse

After tranche A, re-profile. If measurement grouping or numeric conversion remains material, address it.

Candidates include:

- compute measurement occurrence boundaries once for each relevant measurement-step subset instead of regrouping equivalent rows;
- avoid repeated `pd.to_numeric(...)` on the same cycle/current/voltage columns when a validated numeric view can be reused;
- reuse finite masks / extrema inputs where the same frame is tested repeatedly;
- keep capacity and current extraction vectorized;
- avoid building temporary Series/DataFrames solely to recover a scalar when an equivalent array/range operation is clearer and measurably faster.

Every change must retain NaN handling, ordering and cutoff semantics exactly.

## 8. Optimization tranche C — downstream Rate work

After execution extraction is improved, re-profile the whole route. Only then address newly material secondary costs.

Inspect and optimize where meaningful:

- `build_rate_pairs(...)`;
- `detect_sweep_blocks(...)`;
- candidate selection and `_selected_rate(...)`;
- `build_common_rate_comparison(...)`;
- invalid-neighbour/execution validation;
- result/provenance object construction;
- response serialization;
- owner/context/SQL work if it becomes material.

Prefer reducing repeated passes and allocations before concurrency.

## 9. Concurrency/native-code gate

Do **not** automatically copy the Time/Capacity process architecture or introduce Rust/Rayon.

Concurrency/native execution is eligible only if, after serial/indexed/vectorized cleanup:

- at least ~100 ms of independent CPU-bound work remains on the representative multi-Cell route;
- ownership boundaries can use immutable/non-ORM inputs;
- a controlled serial-vs-candidate benchmark shows a material **complete-route** win;
- one-Cell/small workloads do not regress unacceptably;
- deterministic order and scientific projection are exact;
- worker lifecycle/IPC/RSS cost is included.

If those conditions are not met, keep Rate Capability serial.

## 10. Cache and version consequences

Expected: **no migration, no `CALC_VERSION` bump, no result-schema bump**.

A version bump is required only if persisted scientific meaning or response shape changes, which this child should avoid.

Exact-hit behavior is a locked regression gate:

- exact persisted hit remains direct-body serving;
- no Rate `compute()` call;
- no raw read;
- no execution lookup/index construction;
- no worker/native dispatch.

## 11. Required implementation order

1. Capture the Rate-only baseline on the actual implementation head.
2. Preserve a scientific digest/order/provenance reference.
3. Implement tranche A only.
4. Run focused parity tests and re-profile 1/6 Cell complete route.
5. Keep tranche A only if it yields meaningful complete-route benefit without regressions.
6. Re-profile and implement tranche B only for remaining material costs.
7. Re-profile and inspect tranche C.
8. Apply the concurrency/native gate only if the cleaned serial route still justifies it.
9. Run final family benchmark, golden analysis and canonical preflight.
10. Record both rejected and retained candidates so future agents do not repeat failed experiments.

Do not batch all speculative changes and benchmark only at the end.

## 12. Performance acceptance

The child is complete when:

- every Rate stage that remains materially significant has either:
  - been optimized and retained with measured route benefit;
  - been experimentally rejected;
  - or has a documented scientific/complexity reason not to change;
- scientific digest/order/provenance are unchanged;
- exact-hit behavior remains clean.

Because the measured avoidable scan work is very large, the implementation should target a substantial improvement. As a minimum promotion bar, the final representative six-Cell forced-miss p50 should improve by **at least 25%** versus the 050.17 baseline of 1267.82 ms unless controlled experiments demonstrate that the measured scan time cannot safely be removed. That corresponds to a nominal ceiling of about **951 ms**. The goal is to beat this materially, not to stop at it if additional low-risk measured opportunities remain.

Also report:

- final 1-Cell miss p50;
- final 6-Cell miss p50/min/max;
- exact-hit p50;
- per-stage p50/share after optimization;
- response bytes;
- SQL counts/time;
- structural execution counts;
- profiler overhead;
- CPU/RSS/IPC if concurrency is tested.
