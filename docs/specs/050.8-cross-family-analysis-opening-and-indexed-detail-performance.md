## 1. Goal

Apply the performance lessons established and reviewed in 050.1-050.7 to the other Analysis families without changing their scientific meaning.

The families in scope are:

- **Cycles** — reference/control path for fast reopening and existing prepared per-cycle data;
- **Steps** — remove unnecessary full-raw stitching when only protocol-selected step executions are needed;
- **DCIR** — remove unnecessary full-raw stitching when only configured rest/pulse executions and their exact context are needed;
- **Chargeability** — avoid loading a complete raw source after protocol matching has already identified the measurement/reference steps required for chargeability curves;
- **Rate Capability / C-rate** — avoid loading a complete raw source after protocol pairing has already identified the charge/discharge phase steps required for sweep extraction and validation.

This child is deliberately a **data-access and measured-backend optimization**. It is not a second attempt at progressive Time/Capacity streaming. The rolled-back streaming idea remains the planning-only `050.P2` proto-child and is explicitly out of scope.

The desired interaction model is:

```text
reopen existing unchanged analysis
        ↓
exact analysis-result cache hit
        ↓
serve complete prepared result immediately
```

and, on a genuine result-cache miss:

```text
resolve analysis + protocol semantics
        ↓
identify the exact source steps / cycles / executions required
        ↓
read only the implicated Parquet row groups + columns
        ↓
run the existing scientific calculation unchanged
        ↓
store one normal complete analysis result
```

The child succeeds only if it preserves the first path and makes the second path more selective without introducing a new scientific source of truth.

## 2. Lessons from 050.1-050.7 that are now locked cross-family principles

### 2.1 Exact result-cache hits are the primary reopening path

050.1 established family-scoped result identity and the distinction between persistence changes and scientific invalidation. Existing unchanged analyses must continue to reopen from their exact persisted analysis-result cache when available.

Do not replace an exact result hit with source-cache reads merely because selective reads are now possible. A result hit must remain the cheapest path.

### 2.2 Profile the production path before claiming an improvement

050.4/050.5 showed that architectural intuition is not enough. Measure the path actually used by the family, including cache state, raw access, relevant postprocessing and serialization. Do not claim a user-visible speedup from one isolated microbenchmark.

This child must record before/after evidence per family. Structural counters — row groups, rows and columns read — are mandatory because they prove that the unnecessary full-materialization boundary was actually removed.

### 2.3 Use bounded indexed source reads for cache misses

050.2/050.3 established a validated physical raw layout with 4,096-row Parquet groups, a source index, exact observed source cycles, `cycle_to_row_groups`, and the selective `cache.load_raw_cycles()` reader.

The same architectural principle applies here: determine what raw detail is scientifically required **before** materializing raw data, then read only the relevant groups and columns.

Do not copy the Time/Capacity planner wholesale. Steps, DCIR, Chargeability and Rate Capability have different protocol/execution completeness requirements and need family-specific planning.

### 2.4 Add only the metadata that the measured planners actually require

The current 050.2 raw index is cycle-addressable but does not record which `step_index` values occur in each row group. The protocol-derived families in this child commonly know the relevant step indices before raw loading, so a small row-group step index is justified.

Do not add speculative statistics, precomputed scientific answers, per-analysis materializations, or large metadata blobs.

### 2.5 Prepared artifacts must be optional, regenerable and measured

050.6 proved both sides of this rule: an exact prepared sidecar can materially help when it replaces a measured expensive transform, but opening a sidecar can also be slower than computing a cheap value directly.

Therefore this child does **not** authorize new family-specific derived-value sidecars by default. The common step/row-group metadata described below is access metadata, not a prepared scientific result. If profiling exposes a separate expensive reusable transform, stop and return the evidence for a later child instead of growing 050.8 opportunistically.

### 2.6 Optimize repeated control/postprocessing only when measured

050.7 removed repeated derivative status/run classification while leaving the numerical derivative kernels untouched. The same rule applies here: a clearly dominant repeated in-memory classification may be optimized locally if it is part of the family path being changed and exact parity is proven, but broad scientific refactors are out of scope.

### 2.7 Exact fallback remains mandatory

A missing, stale, corrupt or busy performance index is not scientific incompleteness when the canonical raw cache is valid. In that case use the current full-raw implementation.

Do not block an interactive request waiting for background performance-index preparation. Do not reparse the original source on the request path merely to create performance metadata.

## 3. Verified current implementation

The following facts were re-inspected on `feature/runtime-performance-optimization` after 050.7 and before promotion of this child.

### 3.1 Cycles is already the reference path

`backend/app/services/analysis_engine.py` documents the Cycling result as rendering from versioned per-cycle caches rather than raw record-sized Parquet. 050.1 also provides family-scoped persisted analysis-result caching.

Cycles is therefore the control for the intended reopening architecture. Do not route Cycles through a new raw-detail layer. Measure it and protect it from regression.

### 3.2 The raw cache already has the physical foundation

Current anchors in `backend/app/services/cache.py`:

```text

RAW_CACHE_ROW_GROUP_SIZE = 4096
RawCycleReadDiagnostics
_build_raw_layout_index()
_validate_raw_layout_index()
load_raw_layout_index()

```

The current raw-layout index records:

```text

cycle_to_row_groups
voltage_data_availability
timestamp_start / timestamp_end
raw_shape_fingerprint
```

It does **not** currently expose step-index-to-row-group membership.

`cache.load_raw_cycles()` already demonstrates the required reader contract: validate the current raw/index pair, choose bounded row groups, read only requested columns, filter exact logical rows after group loading, expose diagnostics, and return `None` for safe fallback states.

Do not bump or redesign the current raw Parquet layout merely to add step-addressable metadata.

### 3.3 Steps still full-stitches raw data

Current anchor in `backend/app/services/analysis_engine.py`:

```text
compute_steps(...)
```

The function identifies configured protocol segments/targets but still reaches:

```python
raw, _raw_segments, _missing = stitch.stitch_raw(refs)
```

before reducing the frame to the relevant executions.

Target: determine the source-specific target `step_index` set from the configured protocol segment/signature first, then use bounded detail reads while preserving the current occurrence/order/time/quantity logic.

### 3.4 DCIR still full-stitches raw data

Current anchor in `backend/app/services/analysis_engine.py`:

```text
compute_dcir(...)
```

The current path likewise uses `stitch.stitch_raw(refs)` around protocol-target handling before extracting DCIR rest/pulse occurrences.

DCIR has a stricter completeness requirement than a generic step filter: the optimized planner must include every raw step/run required by the configured DCIR segment and the existing rest/pulse adjacency/completeness logic. Never trim a pulse or its required reference/rest context merely to reduce I/O.

### 3.5 Chargeability already knows its protocol targets before loading raw

Current anchors in `backend/app/services/chargeability.py`:

```text
detect_candidates()
_reference_capacity()
_occurrence_rows()
compute()
```

`compute()` reconstructs protocol semantics per source, but currently still performs:

```python
raw = cache.load_raw(source.hash, parser_version)
reconstructed = protocol.reconstruct_protocol(source.header_meta, nominal)
detected = detect_candidates(reconstructed)
```

and `_occurrence_rows()` subsequently uses the candidate measurement step plus protocol-recorded reference-capacity step rows.

The protocol metadata can therefore identify the raw step set before the full source is materialized. The optimized path must supply `_occurrence_rows()` with an exact reduced frame containing every row it currently relies on; the scientific function itself should not be rewritten unless required for a clean access boundary.

### 3.6 Rate Capability already knows its protocol pairs before extracting executions

Current anchors in `backend/app/services/rate_capability.py`:

```text
build_rate_pairs()
_phase_rows()
extract_pair_executions()
detect_sweep_blocks()
compute()
```

`compute()` currently performs:

```python
raw = cache.load_raw(source.hash, parser_version)
reconstructed = protocol.reconstruct_protocol(source.header_meta, nominal)
pairs = build_rate_pairs(reconstructed)
```

`extract_pair_executions()` then reads the measurement phase and its paired/reference phase, including cutoff/completion validation in the same cycle.

The optimized planner may therefore load the union of all step indices required by the candidate protocol pairs before calling the unchanged execution extractor. It must include CC+CV companion rows and both charge/discharge phase rows wherever the existing validation reads them.

### 3.7 Exact result-cache ownership remains separate

Current anchors in `backend/app/services/analysis_cache.py` and `backend/app/routers/analyses.py`:

```text

compute_dcir_analysis(...)
compute_chargeability_analysis(...)
compute_rate_capability_analysis(...)
```

050.8 must not weaken or bypass these complete-result cache boundaries.

## 4. Target access architecture

### 4.1 Add a small regenerable raw-detail index, separate from the 050.2 raw-layout generation

Add a dedicated access-metadata generation beside each canonical raw cache, conceptually:

```text
raw_detail_index__p<PARSER>__d<DETAIL_INDEX_VERSION>.json
```

Use a dedicated constant such as:

```python
RAW_DETAIL_INDEX_VERSION = 1
```

This is a **physical access metadata version**, not `CALC_VERSION`, parser identity, canonical-raw version, analysis result schema, or analysis cache identity.

Do not bump `RAW_CACHE_LAYOUT_VERSION` solely for this child. The existing 050.6 prepared Time/Capacity artifact validates against that raw-layout generation; changing it unnecessarily would invalidate useful prepared state that this child does not otherwise modify.

The detail index must be small and validate against the active raw cache. Minimum required fields:

```text
detail_index_version
parser_version
canonical_raw_version
raw_layout_version
raw_shape_fingerprint
raw_row_count
raw_row_group_count
step_index_to_row_groups
```

`step_index_to_row_groups` maps each exact canonical integer-like `step_index` observed in the raw source to the sorted unique Parquet row groups containing at least one such row.

Optional metadata is allowed only when the implementation proves it is required by one of the in-scope family planners. Do not add scientific summaries to this sidecar.

### 4.2 Build detail metadata without changing canonical raw bytes

For a newly built cache, publish the detail index from the complete validated in-memory raw frame while that frame is already available.

For an existing current raw cache, the detail index must be regenerable from **cache bytes alone**. It may read only the columns required to derive row-group step membership. It must never require the original source file merely to create this performance sidecar.

Preparation belongs in the existing scientific/cache preparation machinery (`scientific_preparation.py`, cache build/write-behind integration, or the smallest existing equivalent). It must be deduplicated, cleanup-safe and off the ordinary request critical path.

### 4.3 Add one bounded exact step-detail reader

Add the smallest coherent cache-layer reader needed by the family planners. A suitable contract is conceptually:

```python
load_raw_detail(
    file_hash,
    parser_version,
    *,
    step_indices,
    columns,
    source_cycles=None,
    diagnostics=None,
    wait_for_index=False,
) -> pd.DataFrame | None
```

Exact naming may follow existing cache conventions, but the behavior is locked:

1. validate the canonical raw-layout pair and detail index against the current raw fingerprint;
2. normalize exact integer-like step indices and optional cycles;
3. choose the union of row groups containing the requested steps;
4. if cycles are also known, intersect with `cycle_to_row_groups` from the existing raw-layout index where doing so is exact;
5. read only those row groups and only identity columns plus caller-required scientific columns;
6. filter the loaded rows exactly by requested `step_index` and optional cycle after loading;
7. preserve canonical physical/record order;
8. report deterministic diagnostics: status, row groups total/read, rows read/returned, columns read, requested steps/cycles;
9. return `None` rather than guessing when the detail index/raw layout is unavailable, invalid, stale, or busy.

The reader must never issue one Parquet access per returned row or per occurrence.

### 4.4 No request-path preparation wait

Like the review-clean 050.3 behavior, a request that encounters an in-progress detail-index preparation must fall back immediately to the current full-raw path. Do not wait for a converter merely to gain a performance optimization.

## 5. Family-specific planners and locked scientific boundaries

Do not build one generic "protocol analysis engine" that obscures the existing family semantics. Share only the physical index/reader and truly common source-planning mechanics.

### 5.1 Cycles

Required work:

- profile exact result-cache reopen and a cache miss from prepared cycle caches;
- add regression evidence that Cycles does not touch raw-detail Parquet on an exact result hit;
- make no raw-detail architecture change to Cycles unless profiling exposes a concrete regression introduced by 050.8 itself.

Cycles is the reference, not a target for forced unification.

### 5.2 Steps

Before raw loading, derive for each source/protocol signature the exact configured target step indices used by the current `compute_steps()` segment semantics.

The indexed path must:

- preserve source ordering and dense global cycle/continuation behavior;
- load all rows belonging to the targeted step executions, not sampled points;
- request only columns actually consumed by the current Steps calculation/payload;
- preserve occurrence numbering, cycle/time axes, direction/rest inclusion, quantities, labels, provenance and badges exactly;
- fall back to `stitch.stitch_raw()` if any source cannot be planned/read safely.

Do not change how a Steps series is defined.

### 5.3 DCIR

Before raw loading, derive the exact source-specific step set required by each configured DCIR segment/protocol target.

The indexed path must include every row needed by the existing scientific logic for:

- reference/rest voltage;
- pulse voltage/current;
- pulse/rest duration and execution boundaries;
- adjacent/paired run validation;
- cycle/occurrence ordering;
- any configured candidate filter currently applied after full stitching.

If exact adjacency cannot be proven from the reduced rows for a particular source/layout, use the legacy full-raw path for that request. Correct DCIR context is more important than selectivity.

Do not change the DCIR formula, pulse/reference definition, filters, sign conventions or output contract.

### 5.4 Chargeability

Perform protocol reconstruction and `detect_candidates()` before raw detail loading.

For candidates that can contribute under the current filters, derive the complete raw step set required by `_occurrence_rows()` and `_reference_capacity()` — including the candidate measurement step and every protocol-recorded reference/preparation step actually read by the current implementation.

Then:

- load those steps with the bounded detail reader;
- call the existing candidate/execution scientific logic on the exact reduced frame;
- preserve execution grouping, reference-capacity selection, SoC derivation, current/C-rate conversion, specific/areal normalization, fingerprints, badges and source metadata exactly.

If a candidate requires raw context not represented by the planned set, expand the exact planner or fall back. Do not infer missing context.

### 5.5 Rate Capability

Perform protocol reconstruction and `build_rate_pairs()` before raw detail loading.

For all candidate pairs that may contribute to the enabled families, derive the union of:

- measurement step indices;
- all charge-phase `step_indices` including CC+CV companions;
- all discharge/reference phase `step_indices` required by `_phase_rows()` and completion validation.

Load every execution of those steps, then call the existing `extract_pair_executions()`, `detect_sweep_blocks()` and common-rate comparison logic unchanged.

Preserve exactly:

- charge/discharge pairing;
- fixed/variable rate interpretation;
- cutoff tolerance checks;
- measurement/phase/reference completion requirements;
- scaffold/monotonic policies;
- block scoring/fingerprints;
- common-rate reference and retention/asymmetry outputs;
- source provenance and badges.

A faster path must never make an incomplete pair appear valid.

### Production-path selection rule

For Steps, DCIR, Chargeability and Rate Capability, enable the indexed-detail path in production only when:

- the planner can establish an exact required step/context set;
- the selective reader materially reduces irrelevant physical work on at least one representative sparse-protocol fixture;
- same-machine paired measurements do not show a repeatable material regression versus the legacy path.

If a family's protocol naturally touches nearly every row group and the indexed path provides no benefit, retain the legacy production path for that family and record the evidence. Do not force architectural symmetry at the expense of performance.

## 8. Cache lifecycle, conversion and invalidation

The raw-detail index is regenerable cache metadata and must follow the existing checksum-directory safety model.

Required behavior:

- fresh raw cache build can publish the detail index from the already validated frame;
- existing raw caches can prepare it from cache bytes without source reparsing;
- preparation is deduplicated and runs outside request/UI critical paths;
- raw replacement/removal makes an old detail index unusable through raw-fingerprint validation;
- corruption or schema mismatch fails to exact legacy behavior;
- offline sources remain safe because the canonical raw cache is never destroyed merely to regenerate metadata;
- cleanup/budget accounting includes the sidecar as ordinary cache bytes;
- request readers observe a consistent raw/index/detail boundary and never pair metadata with replacement raw bytes.

Do not edit released migrations.

## 12. Performance acceptance

The child is not accepted merely because a selective reader exists.

Required evidence:

- exact result-cache hits remain structurally free of raw/detail reads and show no repeatable material regression;
- each production-enabled indexed family demonstrably reads fewer irrelevant row groups/rows than its forced-legacy path on a representative sparse-protocol fixture;

Do not invent a universal millisecond target across different source sizes and analysis families.

## 17. Implementation record

Implemented on `feature/runtime-performance-optimization` as a backend/cache-only optimization.
The canonical raw Parquet and existing raw-layout sidecar remain unchanged. The new
`raw_detail_index__p<parser>__d<detail>.json` records exact step-to-row-group membership and is
validated against the active raw/layout identity and physical footer. Fresh raw publication creates
the sidecar from the validated frame; the scientific-preparation worker can create it from existing
raw Parquet `step_index` bytes without opening the source file. Publication removes stale detail
metadata before replacing raw bytes, uses the existing raw/index consistency boundary, and leaves
the full legacy reader available for missing, busy, stale or corrupt detail metadata. The detail
reader returns only exact requested step/cycle rows in physical order and reports bounded group,
row and column diagnostics.

`analysis_detail.py` owns only this mechanical access boundary. Steps and DCIR plan their exact
protocol steps before loading raw detail and stitch against full source-cycle metadata; retaining
`record_index` in reduced Step frames preserves the existing occurrence-block boundaries.
Chargeability plans matching candidates before reading and includes both measurement and
protocol-recorded reference steps. Rate Capability plans all phase steps, including CC+CV
companions, before using the existing pair/execution extractor. All four consumers fall back to
the complete legacy raw path immediately when indexed access is unavailable. Cycles remains the
prepared per-cycle cache control and was not routed through raw detail. No frontend, migration,
