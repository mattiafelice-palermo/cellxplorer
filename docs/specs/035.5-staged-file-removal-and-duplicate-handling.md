# 035.5 — Staged-file removal and duplicate handling

**Status:** Implemented

## Goal

A single repeated source must not make a large separate-cell import impossible. The offending file
must be visible and removable without restarting the entire workflow, while continuation-chain
identity remains fail-safe.

At the authoring baseline, any registered exact duplicate can make the full batch unsaveable, while
the duplicate state is easiest to see only when that file is active.

## Locked staged-row design

Every staged row displays:

- filename;
- concise state:
  - `Ready`
  - `Already imported`
  - `Possible update`
  - `Inspection failed` if the current UI exposes this state;
- icon plus text, not color only;
- remove action with accessible label `Remove <filename> from import`;
- full path/status explanation in tooltip or detail pane;
- current active-row highlight independent of duplicate status.

Add:

- `Remove all already imported` when at least one exact duplicate exists;
- summary copy such as `1 already imported — will be skipped`;
- an import count based on included valid drafts, not the raw staged-row count.

## Separate-cell mode

- Exact duplicates are automatically excluded from the outgoing request.
- They remain visible until removed so the user understands what happened.
- They cannot be manually re-enabled as new Cells.
- Valid files remain importable.
- The primary action says, for example, `Import 299 cells`.
- If every staged file is an exact duplicate, disable import and show:
  `All selected files are already in the Cell Database.`
- A possible update is not auto-excluded and keeps its current explicit warning/choice behavior.
- A duplicate that points to an archived Cell follows the backend’s current archived-source reuse
  semantics; do not invent a frontend rule that contradicts it.

## Continued-cell mode

Existing source-identity rules remain authoritative:

- a duplicate, already-linked source, or chain identity violation is a blocking finding;
- do not silently skip it;
- the user must remove the source or cancel;
- removing or reordering a source re-runs continuation inspection;
- acknowledgements are retained only for unchanged finding IDs;
- the submitted source order exactly matches the remaining visible chain.

## Remove-one state transition

Removing one staged source must:

1. remove its draft;
2. remove it from every staged separate-cell replicate group;
3. remove now-invalid staged replicate groups with fewer than two members, or return their remaining
   member to unassigned state according to the existing import policy;
4. choose the nearest remaining active row:
   - next row when available;
   - otherwise previous;
   - otherwise no active row;
5. preserve all edits made to every other draft;
6. update counts, size summary, warning, and ETA;
7. cancel or ignore a late preview response for the removed file;
8. clear raw-data/preview state owned only by the removed draft;
9. in continued mode, trigger fresh chain inspection;
10. restore focus to the next/previous row or to the empty state.

No registered source or Cell is deleted by this action.

## Remove-all-duplicates transition

- Remove only rows whose current inspected match is a registered `exact_duplicate`.
- Do not remove possible updates.
- Apply the same replicate cleanup and active-row policy once to the resulting batch.
- The action is immediately applied and reversible only by adding/selecting the files again; this is
  staged state, so no destructive confirmation modal is needed.

Pure functions should cover:

- remove-one transition;
- remove-all-duplicates transition;

- staged replicate cleanup;
- continued-mode blocking policy;
- request-entry construction that cannot accidentally include an exact duplicate.

Keep React effects limited to asynchronous reinspection/preview cancellation.

## Backend boundary

Do not weaken backend checks:

- `/api/imports/cells` still rejects a submitted exact duplicate;
- final checksum/identity validation remains;
- legacy callers cannot bypass duplicate safety;
- continuation-chain endpoints continue to reject invalid membership.

The frontend avoids sending excluded separate-cell drafts; it does not redefine identity.

## Loading, error, and accessibility

- Removing is disabled while the exact same draft is in a non-cancellable submission stage.
- An inspection error remains visible and removable.
- Long filenames truncate with tooltips.
- Remove actions work by keyboard and have visible focus.
- Empty-valid-batch and all-duplicate states are explicit, not generic disabled buttons.
