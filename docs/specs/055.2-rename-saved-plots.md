> Branch: `feature/plot-workflow-polish`.

## Parent

`055-plot-workflow-polish.md`

## Goal

Allow the user to rename an existing saved plot and use that customized name consistently wherever the saved plot is identified or used as the natural export name.

Example:

- autogenerated saved name: `Cycles — Discharge capacity`;
- user renames it to: `Gen2H 6 bar retention`;
- the saved-plot card, active saved-plot identity, report/export references, and plot export filename use `Gen2H 6 bar retention` where they currently derive from the saved plot name.

## Locked decisions

- Rename changes **metadata only**. It must not alter the saved plot ID, tab, scientific selection, computation, presentation, visibility, or style.
- Saved plot IDs remain the stable identity.
- Names do not need to be globally unique. Two saved plots may share the same display name because IDs disambiguate them internally.
- Trim leading/trailing whitespace.
- Reject an empty/whitespace-only name.
- Preserve a reasonable existing maximum-length convention if one exists. If no repository limit exists, use a modest UI-safe limit (recommend 120 characters) and enforce it consistently.
- Rename should be directly accessible from the saved-plot list; do not bury it in global analysis settings.
- Renaming must persist immediately as an intentional metadata mutation. It should not require opening the plot and pressing the plot `Update` button.
- Renaming an inactive saved plot must not disturb the current active plot or draft.
- Renaming the active saved plot must not make its scientific/presentation workspace appear dirty.
- Existing generated names remain the default for newly saved plots.
- No schema migration is expected because `SavedAnalysisPlot` is currently stored in the analysis spec JSON. Re-verify at implementation time.
- File-system-safe export names must continue to pass through the existing slug/sanitization helper rather than using the raw display name directly.

## Current implementation and anchors

### Saved plot list

`frontend/src/features/analyses/editor/artifacts/SavedPlotsPanel.tsx` currently:

- filters `plots` by active tab;
- renders `plot.name`;
- renders delete action;
- calls `onOpen(plot)`;
- has no rename action.

This is the primary UX anchor.

### Saved plot orchestration

`frontend/src/features/analyses/editor/AnalysisEditor.tsx` currently owns:

- `spec.saved_plots`;
- active saved plot resolution;
- saved plot update/delete/open logic;
- active dirty-state baseline.

Add rename orchestration here or in a narrowly extracted policy helper; do not push persistence responsibilities into the preview component.

### Saved plot data

Use the existing `SavedAnalysisPlot` shape from `frontend/src/api.ts` (or its current location at implementation time).

Do not introduce a second display-name field.

### Exports

Plot-family export paths already derive filenames through helpers such as:

- `slugFilename(...)`;
- family-specific `plotName` / base-name derivation.

Audit the active saved-plot path so that the custom saved name becomes the base name when exporting an opened saved plot.

Do not blindly replace scientifically useful default names for unsaved/draft plots.

## UX specification

### Rename affordance

Add a compact `Rename` action to each saved plot card.

Preferred interaction:

- existing saved plot card remains clickable to open;
- right-side actions contain `Rename` and `Delete`, or a compact overflow menu if spacing requires it;
- `Rename` opens a small Mantine modal/popover/dialog with the current name prefilled.

Do not turn the entire card title into permanently editable text.

### Rename dialog

Fields/actions:

- title: `Rename saved plot`;
- text input prefilled with current `plot.name`;
- primary action: `Rename`;
- secondary action: `Cancel`.

Behavior:

- focus the input on open;
- place the cursor/select text in a convenient editing state;
- Enter submits when valid;
- Escape/cancel closes without mutation;
- empty trimmed name disables/rejects submission;
- unchanged trimmed name closes with no persistence mutation.

### Persistence

On valid rename:

- update only the matching saved plot object's `name`;
- update `modified_at` if current saved-plot metadata semantics treat metadata edits as modifications;
- persist through the existing analysis spec persistence mechanism;
- invalidate/refresh the same analysis query state used for other saved-plot mutations;
- keep `activeSavedPlotId` unchanged.

### Dirty-state semantics

If the active saved plot is scientifically unchanged before rename:

- rename it;
- its display name updates;
- `Update` remains disabled;
- leaving the plot must not trigger a scientific-edit prompt solely because of rename.

If the active saved plot is already scientifically dirty:

- rename it;
- dirty state remains dirty;
- pressing `Update` later updates the view/configuration but must not revert the custom name.

Implementation must ensure baseline/signature logic excludes or separately handles metadata exactly as current saved-plot policy intends.

## Export naming

When exporting an **opened saved plot**:

- use the current saved plot `name` as the user-facing filename base;
- continue sanitizing through `slugFilename` or the current common equivalent;
- append/retain existing format/quantity suffixes only if they are currently useful and not duplicative.

Examples are illustrative:

- display name: `Gen2H 6 bar retention`
- sanitized base: `gen2h-6-bar-retention`
- output: `gen2h-6-bar-retention.png`

Do not require exact lowercase/hyphen behavior if `slugFilename` currently produces another deterministic convention.

For a new/unsaved plot:

- keep the existing generated export naming behavior.

For portable reports or other places that visibly label a saved plot:

- use the stored custom `plot.name`;
- do not recompute a default name from quantity/tab when a saved name exists.

## Tests

Add focused tests for a pure rename helper or editor mutation path:

- renames only the matching ID;
- preserves ID/tab/selection/computation/presentation/style;
- trims whitespace;
- rejects empty name;
- allows duplicate names;
- leaves non-target saved plots untouched;
- keeps active ID unchanged;
- does not alter scientific dirty signature;
- an already-dirty plot remains dirty after rename;
- export filename uses custom saved name and existing slug sanitizer;
- unsaved plot export still uses generated naming.

Add component-level coverage for the rename interaction if existing frontend test patterns make this inexpensive.

## Manual checks

1. Save two plots.
2. Rename the first from the saved-plots panel.
3. Confirm the new name appears immediately.
4. Confirm the second plot is unchanged.
5. Reload the analysis; confirm rename persisted.
6. Open renamed plot; confirm ID/open behavior is intact.
7. Confirm `Update` is not enabled solely by rename.
8. Export PNG; confirm filename uses the custom saved name.
9. Rename to a name already used by another saved plot; confirm allowed.
10. Try blank/whitespace name; confirm rejected.
11. Rename an inactive plot while another plot has unsaved edits; confirm active edit state is undisturbed.

## Acceptance criteria

- Existing saved plots have a direct rename action.
- Rename persists and survives reload.
- Saved plot ID is unchanged.
- Duplicate display names are allowed.
- Blank names are rejected.
- Rename does not alter plot calculation/presentation state.
- Rename alone does not create a false `Update` state.
- Existing real dirty state is preserved.
- Opened saved plot exports use the custom saved name through the existing filename sanitizer.
- Saved-plot labels elsewhere use the stored name rather than regenerating it.
- Focused tests and canonical preflight pass.

## Out of scope

- bulk rename;
- uniqueness enforcement;
- folders/tags;
- saved-plot ordering;
- changing autogenerated default naming rules except where necessary to respect a custom stored name.
