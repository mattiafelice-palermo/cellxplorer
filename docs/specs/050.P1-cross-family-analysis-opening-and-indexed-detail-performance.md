## Why this proto-child exists

Investigation for 050.2/050.3 exposed a broader performance pattern across the Analysis module.
Time/Capacity is the clearest current case because a narrow cycle-range request can still materialize
complete raw source files. However other scientific families also contain full-raw paths even though
they ultimately consume only a much smaller structured subset of the experiment.

At the same time, CellXplorer has an intentional user-experience goal that must not be lost while
optimizing cache misses:

> Reopening an existing analysis should show its default/current plot from already prepared result
> data essentially immediately whenever the selected sources and scientific inputs have not changed.

This proto-child records both ideas for later investigation. It is not detailed enough to implement
safely yet and therefore must remain outside the active workflow until promoted.

## Current observations to preserve for later investigation

### Cycles is already the reference opening-speed path

The Cycles analysis renders from versioned per-cycle caches rather than raw record-sized Parquet.
Its endpoint also has an exact-result fast path that can serve stored result bytes directly on a
cache hit. This is close to the desired reopening model and should be treated as a reference rather
than rewritten to use raw-detail indexing unnecessarily.

Likely future question:

- Is the current cold application -> open analysis -> first Cycles paint already sufficiently fast
  on representative large analyses, or is proactive preparation of the canonical live Cycles result
  needed?

### Steps still contains full raw stitching

Steps identifies protocol/step targets but currently contains a `stitch_raw()` path before reducing
the data to the relevant step executions.

Likely future question:

- Can protocol targets be translated into bounded cycle/step detail reads using the source index or
  a small extension of that index, while preserving exact execution/order/provenance semantics?

### DCIR uses only specific rest/pulse occurrences

DCIR calculations ultimately need selected adjacent rest/pulse runs, but the surrounding analysis
path can still materialize full raw data first.

Likely future question:

- Can protocol recognition and occurrence planning identify the small set of row groups required for
  the selected DCIR series before raw detail is loaded?

### Chargeability uses selected protocol executions

Chargeability currently loads complete raw source data and then extracts the protocol-defined
preparation/reference/measurement steps and occurrences needed for the scientific curve.

Likely future question:

- Can those target executions be resolved to bounded cycle/step detail reads before full raw
  materialization?

### Rate Capability / C-rate also selects protocol-defined executions

Rate Capability currently loads complete raw source data before extracting the relevant charge/
discharge protocol pairs and measurement executions.

Likely future question:

- Can the existing semantic protocol pairing drive selective indexed raw reads without altering the
  validated charge/discharge completion logic?

## Architectural principle to evaluate later

The likely reusable model is:

```text
prepared source cache / compact metadata
        ↓
analysis-specific planner
        ↓
identify required cycles / steps / occurrences
        ↓
read only required raw row groups + columns
        ↓
existing scientific calculation
        ↓
analysis result cache
```

This is only a hypothesis for the later promoted child. Do not generalize 050.2's Time/Capacity
reader blindly across every analysis family; each family has different completeness and adjacency
requirements.

## Opening-speed invariant

Future work promoted from this proto-child should distinguish two different latency paths:

```text
exact analysis-result cache hit
        ↓
serve prepared numerical result
        ↓
render plot
```

versus:

```text
analysis-result cache miss
        ↓
compute efficiently from prepared/indexed source caches
        ↓
store result
        ↓
render plot
```

The first path should remain the normal fast reopening path. Selective indexed reads improve the
second path; they must not replace or weaken persistent exact-result caching.

The later investigation should explicitly measure at least:

- cold application -> open existing analysis -> first Cycles plot paint;
- first open of Steps, DCIR, Chargeability and Rate Capability when an exact result cache exists;
- the same family opens on a result-cache miss with source caches already prepared;
- result-cache identity/invalidation behavior after ordinary analysis persistence changes;
- backend result retrieval versus frontend Plotly rendering time where either is material.

## Possible future scope — deliberately not locked

A promoted child or set of children may eventually include some combination of:

- analysis-family-specific selective raw readers built on the 050.2 source index;
- additional index metadata only where measured analysis planners require it, such as step presence
  per row group;
- preserving/strengthening exact result-cache fast paths across all analysis families;
- selectively preparing the canonical live/default plot configuration of an analysis if profiling
  shows that this materially improves reopening latency without wasteful background computation;
- payload/frontend rendering improvements if backend cache-hit service is already fast.

Do **not** assume all of these belong in one implementation child. Split by ownership/risk when this
proto-child is promoted if combining them would increase partial-implementation or scientific
regression risk.
