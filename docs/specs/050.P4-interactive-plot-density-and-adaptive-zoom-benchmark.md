## Purpose

Determine the best interactive point-density strategy for ordinary **consecutive Voltage vs Time** plots, with particular emphasis on the user's real workload of up to roughly **10 large Cells displayed at once**.

The current 4,000-point-per-Cell overview is already considered visually sufficient when the user is viewing the complete experiment without zooming. The open problem is therefore not to maximize point count globally. It is to preserve that fast overview while making zoomed views reveal more local detail without turning Plotly rendering, frontend preparation, response transfer, or backend recomputation into the new bottleneck.

This proto-child is a measurement/design gate. It does **not** authorize an adaptive-zoom implementation until the competing strategies below have been benchmarked on the current post-050 branch.

## User-locked decisions

1. **4,000 displayed points per Cell is sufficient for the unzoomed full-view Voltage vs Time overview.** Do not increase the default merely for visual quality at full range.
2. **The important stress case is up to approximately 10 simultaneously displayed large Cells.** Benchmark single-Cell behavior too, but do not optimize only for one or two Cells.
3. **Adaptive zoom is preferred if it can provide materially higher local resolution without interaction problems.**
4. **Plotly rendering/update should be around 200 ms or faster for the target interactive workload.** Treat `plotly_update_ms <= 200 ms` as the primary median target for the user-facing candidate and record tail behavior separately rather than hiding it in the median.
5. The 200 ms target is specifically the **frontend Plotly render/update boundary**, not a license to omit backend, HTTP, serialization or frontend-preparation timing. End-to-end latency must still be reported separately.
6. **Scientific calculations, selected cycles, source provenance, export fidelity and saved-plot semantics must not change.** Display downsampling/refinement remains a presentation concern.
7. **Adaptive refinement must not blank, reset or visibly jump the plot.** The already rendered overview remains usable while any higher-resolution refinement is prepared.
8. **Pan/zoom itself must remain immediate.** Refinement must follow a completed/coalesced interaction and must not trigger a request storm while the pointer is moving.
9. **Stale refinement work must be abortable/ignorable.** A second zoom/pan must not allow an older response to overwrite the newer viewport.
10. **Do not revive progressive series streaming.** The failed progressive Time/Capacity streaming experiment remains out of scope. This work concerns bounded viewport refinement after an ordinary plot is already visible.

## Verified current implementation

### Point budget and request identity

`frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx` currently defines:

- `DEFAULT_TIME_CAPACITY.max_points_per_cell = 4000`;
- an editable `Max points per cell` setting;
- a fixed `viewportWidth = 1200` for cache/request identity;
- `max_points_per_cell` in the Time/Capacity `dataSignature` and therefore in the React Query identity.

The compact/standard interactive request sends the whole selected cycle/range contract to:

```text
POST /api/analyses/{analysisId}/time-capacity
```

and the backend returns a bounded display result.

### Current zoom behavior

The same card uses `useZoomMemory(...)` and handles Plotly `onRelayout`, but the relayout currently records/reapplies axis ranges only. Zooming **does not request a higher-resolution representation of the visible x-range**.

Therefore a 4,000-point-per-Cell full experiment remains a 4,000-point-per-Cell source after zoom: Plotly magnifies the already returned sample.

### Current interactive renderer

`frontend/src/features/analyses/editor/plotting/plotRuntime.ts` converts ordinary interactive `scatter` traces to `scattergl` when WebGL is available. For ordinary **consecutive** Voltage vs Time, Time/Capacity segmentation uses one consecutive segment rather than a cycle-by-cycle trace explosion. The representative 10-Cell use case is therefore a high-point-count / low-trace-count workload, unlike broad dQ/dV and dV/dQ plots.

### Existing profiler is already close to what this study needs

`frontend/src/features/analyses/editor/performance/timeCapacityPerformanceProfile.ts` already records:

- backend total/compute/serialize time;
- HTTP round trip;
- response bytes;
- returned points;
- frontend result-to-plot-props time;
- Plotly update time;
- total interaction time;
- resolved Cell count;
- Plotly trace count.

A promoted benchmark should extend/reuse this profiler rather than create a competing timing framework.

## Primary question

Given a full-view baseline of **4,000 displayed points per Cell**, what is the cheapest way to gain higher local detail after zoom while keeping Plotly around the 200 ms rendering target for approximately 10 large Cells?

The benchmark must compare fixed-density and adaptive approaches before choosing production architecture.

## Candidate A — fixed higher Plotly density

Keep the current architecture and simply increase the points rendered per Cell.

Benchmark at least:

```text
4k / Cell   x 10 Cells =  40k displayed voltage points
8k / Cell   x 10 Cells =  80k displayed voltage points
16k / Cell  x 10 Cells = 160k displayed voltage points
32k / Cell  x 10 Cells = 320k displayed voltage points
```

This is the simplest candidate and establishes how far `scattergl` can be pushed before Plotly, JavaScript allocation, response size or trace preparation becomes unacceptable.

Do not assume 16k or 32k is too much. Measure it.

However, because 4k already looks good at full range, a fixed higher budget should only be selected if its cost is negligible enough to make adaptive complexity unjustified.

## Candidate B — higher-resolution client reservoir, 4k displayed

Request/store a larger bounded interactive reservoir per Cell — for example 8k, 16k or 32k — but feed only approximately **4k points per Cell** to Plotly for the current viewport.

On zoom:

```text
higher-resolution in-memory reservoir
        -> select visible x-range
        -> re-decimate that visible range to ~4k / Cell
        -> Plotly update
```

Advantages to measure:

- no HTTP request after ordinary zoom/pan;
- Plotly workload stays near the already acceptable 4k/Cell level;
- higher effective local resolution than the full-view sample.

Costs to measure:

- larger initial HTTP response;
- more frontend memory and array allocation;
- more frontend filtering/decimation work;
- finite refinement depth: once zoom exceeds the reservoir's retained resolution, no exact additional detail is available.

The reservoir is **not** a second scientific cache. It is disposable interactive presentation data.

## Candidate C — on-demand viewport refinement, 4k displayed

Keep the initial request and initial Plotly render at approximately **4k points per Cell**.

After a completed zoom/pan, request a higher-resolution representation of only the visible x-range, then downsample that visible range back to approximately **4k displayed points per Cell**:

```text
full experiment
    -> initial 4k / Cell overview

user zooms to visible window
    -> keep overview immediately visible
    -> resolve exact visible detail
    -> return <= ~4k representative points / Cell for that window
    -> replace only the plotted data while preserving axis range
```

This is the strongest adaptive hypothesis because zooming increases **effective resolution** without increasing the normal Plotly point budget.

A production version must not make arbitrary zoom ranges create an unbounded persistent analysis-result cache. A promoted benchmark/design child must explicitly determine the ephemeral/cache policy for viewport refinement — for example request-local computation, bounded client memory, quantized reusable windows, or another measured approach. Do not silently put every arbitrary x-range into durable result caching.

The first investigation is limited to **consecutive Voltage vs Time**. Do not generalize the viewport contract to capacity axes, overlap/mirror modes or derivatives until this simpler x-coordinate mapping is proven correct and useful.

## Candidate D — hybrid only if evidence requires it

A hybrid may keep a modest higher-resolution local reservoir and use server refinement only when the viewport demands more detail than that reservoir contains.

Do **not** implement this merely because it sounds comprehensive. Evaluate it only if Candidates A-C each expose a measured tradeoff that the hybrid can plausibly remove.

## Required benchmark matrix

Use the current compact/standard interactive Time/Capacity path and the existing profiler. Prefer representative real prepared data. Synthetic duplication may be used only as a performance stress harness when clearly labelled; it is not scientific parity evidence.

### 1. Fixed-density baseline: ordinary consecutive Voltage vs Time

For **1, 5 and 10 Cells**, measure:

- 4k points per Cell;
- 8k points per Cell;
- 16k points per Cell;
- 32k points per Cell.

For the 10-Cell case this corresponds to nominal maxima of approximately 40k, 80k, 160k and 320k displayed voltage points.

Record actual returned/displayed point counts rather than assuming every Cell reaches the maximum.

### 2. Stacked-current stress case

For **10 Cells**, repeat at least:

- 4k points per Cell;
- 8k points per Cell;
- 16k points per Cell;

with the normal voltage plot plus one stacked current quantity. This intentionally increases both trace count and rendered point count and is a realistic upper-bound Time/Capacity interaction.

If 32k is already clearly outside the 200 ms Plotly target in the simpler voltage-only case, it need not be repeated for stacked current; record the reason.

### 3. Adaptive zoom quality/performance cases

Start from the 10-Cell / 4k-per-Cell full overview and test viewport spans corresponding approximately to:

- full range;
- 25% of the original x-span;
- 10%;
- 2%;
- 0.5%, when the representative experiment contains enough raw detail.

For each zoom level compare, where implementable in an isolated benchmark prototype:

- current behavior: zoom the original 4k sample only;
- Candidate B reservoir refinement;
- Candidate C on-demand viewport refinement.

Measure the number of **distinct original/raw points represented in the visible window** or another explicit resolution metric so that a faster candidate is not accepted if it merely redraws the same coarse sample.

### 4. Rapid-interaction correctness cases

Exercise at least:

- zoom A, immediately zoom B before A refinement completes;
- repeated pan across neighboring windows;
- double-click/autorange reset;
- resize/style-panel open-close after refinement;
- changing the configured cycle range while a viewport refinement is in flight;
- switching away from and back to the plot.

Acceptance requires no stale overwrite, range reset, blank plot, duplicate traces, request storm or React update loop.

## Required measurements

For every relevant scenario record at least:

- requested point budget per Cell;
- actual returned points;
- actual Plotly-displayed points;
- resolved Cell count;
- Plotly trace count;
- response bytes;
- backend total time;
- backend serialization time;
- HTTP round-trip time;
- frontend result-to-plot-props time;
- adaptive visible-window filtering/decimation time when applicable;
- `plotly_update_ms`;
- total interaction/refinement time;
- peak or delta frontend memory where the environment allows reliable measurement;
- WebGL availability;
- visible-resolution metric for zoom refinement.

Use at least five measured repetitions after warmup for each comparable local scenario and report median plus a tail statistic (prefer p95 when enough repetitions are collected; otherwise report max and say why p95 would be misleading).

## Performance decision rules

### Full-view rendering

The preferred user-facing configuration should keep **10-Cell ordinary consecutive Voltage vs Time Plotly rendering around or below 200 ms median**.

If 4k/Cell itself materially exceeds that target on the representative installed application, first investigate the frontend rendering path before increasing density.

A fixed 8k/16k/32k default is not justified merely because it technically renders. Because the user has already judged 4k sufficient at full range, additional full-view density must have negligible enough cost to beat the simpler 4k + adaptive alternative.

### Adaptive refinement

An adaptive candidate is acceptable only if:

- it materially increases local visible resolution;
- Plotly remains near the same bounded 4k/Cell workload or otherwise remains around the 200 ms target;
- the existing coarse view stays interactive during refinement;
- no stale response can overwrite a newer viewport;
- repeated zoom/pan does not create unbounded requests, cache entries or retained arrays;
- the refinement does not change scientific/export/saved-plot semantics.

### Architecture selection

Prefer the least complex candidate that satisfies the performance and resolution targets:

1. fixed density if higher density is essentially free;
2. client reservoir if its initial transfer/memory cost is low and local refinement is sufficient;
3. on-demand viewport refinement if it gives substantially better resolution with acceptable request latency;
4. hybrid only with explicit evidence.

Do not select based on FPS, GPU utilization or theoretical scalability alone. The decision is user-visible wall time + usable zoom detail + bounded resource cost.

## Scientific and persistence invariants

- Display downsampling remains display-only; CSV/data export must continue to use the existing exact/full-resolution export path.
- Saved plots and portable reports must not silently persist an ephemeral zoom-refinement sample as if it were the scientific source data.
- Zoom viewport is presentation state, not a scientific calculation input.
- No `CALC_VERSION` bump merely for a display-density/refinement strategy.
- No database migration merely for ephemeral zoom state.
- No change to parser/cache scientific identity merely because a different number of display points is requested.
- Source provenance and hover metadata must remain correct after refinement.
- Multi-source Cell continuation order and global/local cycle identity must remain unchanged.

## Out of scope

- dQ/dV and dV/dQ trace consolidation; that is a separate Plotly trace-count problem.
- overlap-reset and overlap-mirrored trace consolidation.
- progressive series streaming.
- full-resolution scientific export redesign.
- replacing Plotly.
- Rust/WebAssembly rendering.
- broad `AnalysisPage.tsx` refactoring.
- backend cross-Cell thread/process implementation; that belongs to the separate 050.P3 decision path.

P3 and P4 may use one combined installed-app profiling session because both need the same 10-Cell Time/Capacity controls, but their decisions must remain separable: **P3 asks how to compute independent Cells faster; P4 asks how much interactive detail to deliver/render and how zoom should refine it.**
