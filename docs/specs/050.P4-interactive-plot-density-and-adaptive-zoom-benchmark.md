## Purpose

Determine the best interactive point-density strategy for ordinary **consecutive Voltage vs Time**, especially the real workload of roughly **10 large Cells displayed together**.

The user has already established that approximately **4,000 displayed points per Cell is visually sufficient for the unzoomed overview**. The open question is how to reveal materially more local detail after zoom without making Plotly, frontend preparation, transport or backend refinement slow.

The bounded on-demand viewport-refinement portion of this proto was promoted into numeric child
050.15 and is implemented/review-clean for eligible ordinary non-stacked consecutive Time. This
document remains a benchmark/design gate for the unimplemented fixed-density, client-reservoir,
Plotly-timing, stacked/other-mode and hybrid experiments below; it does not authorize those
variants implicitly.

## User-locked targets

1. Keep the normal full-view baseline around **4k displayed points/Cell** unless measurement proves a higher fixed density is essentially free.
2. Benchmark up to approximately **10 simultaneous large Cells**.
3. Prefer adaptive zoom if it increases local resolution cleanly.
4. Target approximately **200 ms or less median Plotly render/update time** for the representative 10-Cell interactive workload; record tail behavior separately.
5. The ~200 ms target is specifically the Plotly render/update boundary. Backend, HTTP, frontend preparation and complete interaction time remain separate measurements.
6. Zoom/pan must react immediately using the already rendered plot; any refinement follows without blanking/resetting the plot.
7. Coalesce refinement requests and ignore/abort stale work so rapid pan/zoom cannot overwrite a newer viewport.
8. Preserve scientific calculations, provenance, exact data export, saved plots and portable reports.
9. Do not revive the rejected progressive-series streaming design in `050.P2`.

## Candidates to benchmark if promoted

### A — fixed higher density

Keep the current architecture and render more points per Cell. At least test the representative 10-Cell maxima:

```text
4k/Cell  -> ~40k voltage points
8k/Cell  -> ~80k
16k/Cell -> ~160k
32k/Cell -> ~320k
```

Do not assume 16k/32k is too much; measure it. However, 4k is already visually sufficient at full range, so a higher default wins only if its end-to-end cost is negligible enough to make adaptive complexity unnecessary.

### B — larger client reservoir, ~4k displayed

Receive/store a bounded higher-resolution reservoir, such as 8k/16k/32k per Cell, but feed Plotly only about 4k points/Cell for the current viewport. On zoom, filter/re-decimate the in-memory reservoir.

Measure the tradeoff between no extra HTTP request and larger initial transfer/memory plus finite refinement depth.

The reservoir is disposable presentation data, not a scientific cache.

### C — on-demand viewport refinement, ~4k displayed (promoted subset implemented in 050.15)

Keep the initial overview at ~4k/Cell. The eligible ordinary non-stacked consecutive-Time subset
is implemented by 050.15. Any future extension must preserve the same bounded/ephemeral contract.
After a completed zoom/pan:

```text
show existing zoom immediately
-> request exact detail for visible time window only
-> downsample that window back to <= ~4k/Cell
-> replace plotted data while preserving viewport
```

This is the leading adaptive hypothesis because the Plotly workload can remain roughly bounded while effective local resolution increases dramatically.

Do not persist an unbounded analysis-result cache entry for every arbitrary viewport. A promoted child must define a bounded/ephemeral refinement policy.

Initial scope should remain **consecutive Voltage vs Time**; do not generalize immediately to capacity axes, overlap/mirror or derivatives.

### D — hybrid only if evidence requires it

A modest local reservoir plus server refinement is allowed only if A-C expose complementary measured weaknesses. Do not choose a hybrid by default.

## Minimum benchmark matrix

For ordinary consecutive Voltage vs Time:

- 1, 5 and 10 Cells at 4k/8k/16k/32k per Cell;
- 10 Cells with voltage plus stacked current at least at 4k/8k/16k, unless a lower-density case already proves a higher case unnecessary;
- from a 10-Cell 4k overview, zoom to approximately full, 25%, 10%, 2% and 0.5% of the original time span when the experiment contains enough raw detail;
- compare current coarse zoom, client-reservoir refinement and on-demand refinement where an isolated prototype is practical;
- exercise rapid zoom A -> B, neighboring pans, autorange reset, resize, cycle-range change during refinement, and switching away/back.

For every adaptive candidate include an explicit **visible-resolution metric** so a fast redraw of the same coarse sample is not mistaken for refinement.

## Measurements

Record at least:

- requested and actual returned points;
- actual Plotly-displayed points;
- resolved Cell count and trace count;
- response bytes;
- backend total and serialization time;
- HTTP round trip;
- frontend filtering/decimation and result-to-plot preparation;
- `plotly_update_ms`;
- total refinement/interaction time;
- WebGL availability;
- frontend memory delta where reliable;
- visible-resolution metric.

Use at least five warm repetitions for comparable scenarios where practical; report median plus p95 when meaningful, otherwise max/range with explanation.

## Decision rules

Prefer the least-complex candidate that satisfies both responsiveness and useful local detail:

1. fixed density if extra points are essentially free;
2. client reservoir if transfer/memory remain small and local refinement is sufficient;
3. on-demand viewport refinement if it provides better resolution with acceptable refinement latency;
4. hybrid only with explicit evidence.

The preferred design should keep the representative 10-Cell Plotly update around/below 200 ms median. Pan/zoom itself should remain visibly immediate even if a higher-resolution refinement arrives later.

A backend refinement taking a few hundred milliseconds may still produce good UX if the existing plot zooms immediately and the refined data replace it without disruption; record both perceived interaction and refinement completion instead of collapsing them into one number.

## Scientific/persistence invariants

- display downsampling remains presentation-only;
- exact CSV/data export continues through the full-resolution scientific export path;
- saved plots/portable reports must not treat an ephemeral viewport sample as scientific source data;
- zoom viewport is presentation state, not scientific calculation identity;
- no `CALC_VERSION` or database migration merely for display density/refinement;
- provenance/hover source identity remains correct after refinement;
- continuation/global/local cycle identity remains unchanged.

## Separation from 050.9-050.11

The backend execution study and adaptive zoom are complementary but independent:

- 050.9-050.11 ask **how to prepare independent Cell results faster**;
- P4 asks **how much data Plotly should receive and how visible detail should increase on zoom**.

A narrow viewport workload in 050.9-050.11 may estimate composition, but those children must not implement adaptive zoom. Likewise, P4 must not silently choose a thread/Rust architecture without the backend decision evidence.

## Out of scope

- dQ/dV/dV/dQ trace consolidation;
- overlap-reset/mirrored trace consolidation;
- progressive series streaming;
- replacing Plotly;
- broad Analysis editor refactor;
- production cross-Cell concurrency/native execution;
- cross-family indexed detail / 050.P5.

## Promotion criteria

Promote only when:

1. the user explicitly chooses to run the density/adaptive-zoom study;
2. the current backend execution work is stable enough that its moving baseline will not invalidate the frontend experiment, or the benchmark explicitly controls for that baseline;
3. the promoted numeric child is a self-contained benchmark/design gate before any production adaptive implementation;
4. the representative 10-Cell workload is available, or a labelled stress harness plus later installed-app acceptance is explicitly defined.

The proto ID `050.P4` remains reserved after any future promotion and must not be reused.
