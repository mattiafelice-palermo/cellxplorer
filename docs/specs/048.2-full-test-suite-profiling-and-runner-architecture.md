## Goal

Profile **every discovered automated test case** and then determine whether the backend suite can run faster by
reducing repeated Python interpreter/import startup while preserving the complete test population and all
scientific, parser, database, migration, packaging-policy and failure-path assertions.

The work has two distinct phases:

1. **exhaustive measurement** — establish where the time is actually spent across the complete suite;
2. **runner architecture experiment** — compare three execution models on the same clean Windows CI runner and
   retain a new model only if it is faster and its isolation guarantees are proven equivalent for the tests it runs.

No test may be removed, skipped, sampled, marked optional, weakened, or given looser tolerances to improve timing.

## Locked decisions

1. **Profile the complete test population.** Do not profile only the slowest modules or a representative sample.
2. Record the exact discovered test count by framework at implementation time rather than assuming the historical
   count. The user expects the suite to contain 1000+ individual tests, but discovery output is authoritative.
3. Backend case-level profiling must include every discovered `unittest` test case. Frontend policy/test timing must
   likewise cover every discovered Node test case/file that canonical preflight executes.
4. Profiling instrumentation may add overhead; use it to attribute cost, not as the canonical wall-time benchmark.
5. Compare runner architectures using uninstrumented equivalent workloads on the **same GitHub Actions Windows job**
   whenever practical.
6. Preserve all assertions, fixtures, tolerances, failure cases, dialects, migrations, golden corpus inputs and
   scientific expected values.
7. Preserve private mutable filesystem/database/report/cache state wherever the existing test requires it.
8. A one-interpreter benchmark is allowed as a **diagnostic architecture**, even if it temporarily lacks the current
   per-module interpreter isolation. It may not become canonical unless equivalent isolation and order-independence
   are demonstrated.
9. Persistent worker/shard execution may become canonical only after explicit tests prove that module-global state,
   environment-derived configuration, SQLAlchemy engines/sessions, caches, monkeypatches, multiprocessing settings
   and temporary data roots do not leak across module boundaries.
10. Do not trade deterministic failures for speed. Failure attribution must still identify the exact failing test
    case/module and preserve useful stdout/stderr.
11. Do not add test-result caching or changed-test selection in this child. The purpose is to make the **complete
    fresh suite** faster.
12. Use GitHub Actions as the authoritative performance reference because the user's local workstation has shown
    substantial unrelated timing variability.
13. Temporary benchmark/profiling workflows may be committed for CI evidence, but remove them before final handoff
    unless they have durable diagnostic value and are explicitly documented as such.

## 1. Exhaustively profile every test

### Backend

Instrument the full backend unittest discovery so the implementation record can answer, for **every individual test
case**:

- fully-qualified test ID;
- owning module/class;
- elapsed test-case time;
- module elapsed time;
- whether module/class/test setup or teardown is a material part of the cost when measurable;
- pass/fail outcome.

Do not run each individual test in a fresh Python process merely to obtain its timing. That would distort the cost
being measured. Prefer a custom `unittest.TestResult`/runner or equivalent instrumentation in a diagnostic command.

Produce aggregate statistics at minimum:

- total discovered backend cases;
- total backend wall/CPU time for the profiling run;
- p50, p90, p95, p99 and maximum individual test-case duration;
- top 50 individual tests by duration;
- every module's cumulative test-body duration;
- percentage of cumulative test-body time accounted for by the top 10, 25 and 50 tests;
- modules where setup/teardown materially exceeds test-body work.

### Frontend

Profile the complete frontend policy/test population executed by preflight. Record at minimum:

- total discovered files and individual Node test cases/subtests where the native runner exposes them;
- per-file elapsed time;
- per-test/subtest elapsed time where available without changing semantics;
- p50/p90/p95/p99/max and top 50 slow cases/files;
- cumulative concentration of runtime.

### Cost classification

For the slowest/highest-cumulative backend tests, classify the dominant work based on code inspection and focused
profiling. Use concrete categories such as:

- Python interpreter/import startup;
- scientific-stack imports;
- SQLite creation/migration/backup;
- ORM/API application startup;
- XLSX/ZIP generation or parsing;
- Neware source parsing;
- Parquet read/write;
- portable HTML/Plotly/SVG/report serialization;
- checksum/hash work;
- multiprocessing/process startup;
- sleeps/polling/timeouts;
- filesystem copy/delete work;
- actual scientific calculation.

Do not optimize a category merely because it looks expensive. Record evidence first.

## 2. Measure Python startup/import tax directly

The current canonical backend runner launches each backend module through a fresh command equivalent to:

```text
python -m unittest tests.test_<module>
```

Measure how much cost this execution model adds independently of test bodies.

At minimum collect:

1. plain Python interpreter startup on the same Windows runner;
2. import of the common CellXplorer backend/scientific stack used by tests;
3. import/discovery-only cost for representative light and heavy test modules;
4. aggregate difference between summed individual test-body timing and end-to-end backend runner wall time.

Use Python import profiling (`-X importtime` or equivalent) only diagnostically; do not leave noisy import tracing in
canonical tests.

The implementation record must explicitly estimate how much of the complete backend wall time is attributable to:

```text
interpreter/process startup + repeated imports
versus
fixture/setup/teardown
versus
actual test bodies
```

A bounded estimate is acceptable when exact decomposition is impossible, but explain the method.

## 3. Benchmark three backend execution architectures on one clean Windows runner

Create a temporary diagnostic GitHub Actions workflow or equivalent same-job benchmark. Install dependencies once,
then run the following architectures against the exact same commit and complete backend test population.

### Architecture A — current per-module process model

Baseline:

```text
one fresh Python process per backend test module
bounded concurrent module pool
private CELLXPLORER_DATA root per module
```

This is the correctness reference.

### Architecture B — one Python interpreter

Run the complete backend suite in one Python interpreter using normal unittest discovery/explicit suite assembly.

Purpose: measure the upper bound of interpreter/import-startup savings.

Requirements for the diagnostic run:

- execute every backend test case exactly once;
- record exact discovered IDs/count;
- use a fresh overall data root;
- report failures by exact test ID;
- do not make this canonical solely because it is fastest.

Before retaining Architecture B, prove test-order independence and module-level state isolation. If that cannot be
proven, treat B only as diagnostic evidence.

### Architecture C — persistent worker shards

Start a small fixed number of long-lived Python interpreters and assign multiple backend modules sequentially to each
worker. On standard `windows-latest`, use the actual runner CPU count as the primary shard count; also measure one
reasonable adjacent configuration when useful.

Each worker should:

- import the common runtime once;
- execute several complete test modules sequentially;
- create/use a fresh private mutable data root for each module;
- preserve exact module/test failure attribution;
- reset environment variables and known test-owned global state between modules;
- never run two modules concurrently inside the same interpreter unless separately justified.

Architecture C is the likely production candidate if it captures most of B's startup savings while preserving
stronger isolation.

### Counterbalanced comparison

Runner warm-up and filesystem caches can bias sequential measurements. Use a counterbalanced order in the same job,
for example:

```text
A -> B -> C -> C -> B -> A
```

or another design that gives each architecture both early and late positions.

Every measured pass must execute the same complete backend test population. Record:

- host logical CPU count;
- requested/effective worker count;
- exact test case/module count;
- wall time for each pass;
- failures, if any;
- median/mean per architecture;
- speedup relative to A.

Do not use profiling-instrumented runs for these canonical wall-time comparisons.

## 4. Prove semantic and isolation equivalence before changing the canonical runner

If B or C is materially faster, inspect the complete backend suite for dependencies on fresh-interpreter semantics.
At minimum test/prove:

- `CELLXPLORER_DATA` changes take effect correctly between modules;
- database engines/sessions are disposed or recreated as required;
- settings/configuration read from environment are not incorrectly cached across modules;
- temporary directories/files do not leak between modules;
- monkeypatch/mock state does not leak;
- module-level registries/caches/singletons are reset or demonstrably immutable;
- migration/global application startup state does not contaminate subsequent modules;
- multiprocessing/NDAX worker settings are restored;
- random state and locale/timezone changes, if any, are restored;
- a deliberately failing module is attributed correctly without suppressing later cleanup/failures;
- changing module order does not change pass/fail results.

Add focused runner regression tests for every reset/isolation mechanism introduced.

If some modules genuinely require fresh-process isolation, a **hybrid model is allowed**:

```text
persistent workers for proven-safe modules
+
fresh-process execution for an explicit, small isolation-sensitive set
```

The isolation-sensitive set must be justified by code/tests, not guessed, and must not become a dumping ground for
slow modules.

## 5. Optimize individual slow tests after architecture attribution

After complete profiling, investigate every test/module that remains a material contributor to the critical path or
aggregate runtime.

For each optimization candidate:

1. identify the expensive operation;
2. decide whether it is behavior under test or redundant setup;
3. preserve the smallest fixture that still exercises the same semantics;
4. preserve at least the required real-source/golden parity tests where production-format fidelity matters;
5. retain private mutable state;
6. measure before/after on a clean or paired reference;
7. add/retain regression coverage proving the optimization did not weaken the test.

High-value patterns to consider include:

- immutable migrated SQLite templates copied per test instead of rebuilding the same schema repeatedly;
- compact semantically complete XLSX/Neware fixtures instead of unnecessarily large generated sources;
- class/module-level immutable fixture preparation with per-test private copies;
- avoiding repeated app/router/service startup where the test does not exercise startup itself;
- compact Parquet/report fixtures;
- separating serializer correctness from large-output stress tests;
- keeping a small number of explicit real-file/full-scale parity tests while unit behavior uses compact fixtures.

Do not rewrite production scientific code merely to make a test faster unless the production change is independently
correct, useful and reviewed as such.

## 6. Selection rule

Choose the final canonical backend execution architecture by this order:

1. **correctness and isolation equivalence**;
2. complete coverage and deterministic failure attribution;
3. clean Windows CI wall time;
4. implementation complexity/maintenance cost.

Retain a new architecture only if it gives a material, repeatable improvement. As a default threshold, aim for at
least **20% backend-suite wall-time reduction** relative to Architecture A on the same clean runner; smaller gains may
be accepted only when the implementation is very simple and low-risk.

If B is dramatically faster but cannot preserve required isolation, do not use it canonically; use its result to
quantify the maximum startup/import tax and prefer C or a hybrid.

If none of B/C/hybrid beats A materially after preserving isolation, keep A and use the exhaustive profile to focus
only on individual test-body/fixture costs.
