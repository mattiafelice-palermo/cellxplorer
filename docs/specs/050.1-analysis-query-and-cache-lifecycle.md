Status: **Plan — implementable first child**

Branch: `feature/runtime-performance-optimization`  
Repository baseline: `main` at `1dc3525ec42571504ed6d9bdb9a0668d35df309b`

## Goal

Remove four verified sources of unnecessary Analysis-editor work before redesigning the deeper
Time/Capacity raw-data path:

1. persisting an already-live analysis draft must not invalidate/refetch scientific queries;
2. Time/Capacity should keep the previous plot visible while a **scientifically compatible** new
   request is loading;
3. React Query cancellation must be propagated into Time/Capacity HTTP fetches;
4. backend result-cache identity must include only the scientific inputs consumed by the requested
   analysis family, not unrelated family configuration.

This child is deliberately about **query lifecycle and cache dependency scope**. It does not change
Time/Capacity raw Parquet access, source stitching, downsampling algorithms, formulas, protocol
recognition, or plot/export meaning.

## Verified current behavior

### 1. Autosave causes scientific invalidation

`frontend/src/features/analyses/editor/AnalysisEditor.tsx` treats plot-setting edits as draft/spec
changes and marks the analysis dirty. Its autosave effect waits 1.8 seconds, persists the stable
payload with:

```text
PUT /api/analyses/{analysis_id}
```

and on success currently performs all of:

```ts
qc.invalidateQueries({ queryKey: ["analysis", aid] });
qc.invalidateQueries({ queryKey: ["analyses"] });
void invalidateAnalysisQueries(qc, aid);
```

`invalidateAnalysisQueries()` in
`frontend/src/features/analyses/workspace/analysisQueryCache.ts` owns a broad set of analysis-query
roots, including live scientific results, saved previews, plot artifacts/thumbnails, and recognition
families. For a scoped analysis it cancels, invalidates, and then refetches active stale queries.

This broad invalidation is correct after a source/cell/scientific-data mutation, but not after
persisting the same spec that the mounted editor already used to create its live query key. The PUT
changes persistence state; it does not change source bytes, parser identity, scalar metadata, or the
scientific input represented by the current in-memory spec.

### 2. Time/Capacity range changes create a new query and drop the old visible result

`frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx` constructs a
`dataSignature` containing selection/protocol identity plus the Time/Capacity fields that alter the
returned result, including:

```text
explicit cycles
cycle_start / cycle_end
max_points_per_cell
x_axis
time_unit
display_mode
electrode_area_cm2
voltage_channel
derivative settings when applicable
```

The live query key is currently:

```ts
["time-capacity", analysisId, dataSignature]
```

Changing `cycle_end` therefore correctly requests new data. However the current query no longer
retains a compatible previous result as placeholder data, despite the earlier Time/Capacity
contract requiring the existing plot to remain visible during a background refresh.

A generic unconditional `keepPreviousData` is **not acceptable** because compact Time/Capacity
responses bake coordinate/display choices into the returned arrays. For example, retaining a result
from one X quantity while immediately relabelling it as another would show scientifically wrong
intermediate content.

### 3. The Time/Capacity React Query ignores its abort signal

The shared frontend API helper already supports:

```ts
post(url, body, { signal })
```

and ultimately passes the signal to `fetch()`.

The live Time/Capacity `useQuery()` currently defines a query function without consuming React
Query's `{ signal }`. `SavedTimeCapacityPreview` likewise issues a React Query-owned
Time/Capacity POST without passing the query signal. Therefore a superseded query can be cancelled
inside React Query while its browser HTTP request remains alive.

This child must wire browser cancellation correctly. It must **not** claim that aborting `fetch()`
necessarily terminates synchronous FastAPI/pandas work that has already entered the backend. Server
cooperative cancellation/in-flight deduplication is separate work.

### 4. Backend result keys include unrelated computation families

`backend/app/services/analysis_cache.py::_scientific_spec()` currently returns a structure including:

```python
"selection": ...
"computation": spec.get("computation") or {}
"aggregation": spec.get("aggregation") or {}
"protocol_segments": ...
"dcir_segments": ...
"hidden_protocol_segment_ids": ...
```

`result_key()` hashes this structure for every result kind. Consequently, changing e.g. a DCIR,
Steps, Chargeability, or C-rate configuration changes the Time/Capacity backend key even though
`compute_time_capacity()` does not consume those family blocks. The inverse problem exists for
other families.

The current code already establishes several family ownership boundaries:

- Cycles owns generic per-cycle computation/filter/aggregation settings;
- Time/Capacity owns `computation.time_capacity` plus its generic cycle-range fallback and shared
  protocol filtering;
- Steps owns `computation.steps` and shared `protocol_segments` targets;
- DCIR owns `computation.dcir.series` plus private top-level `dcir_segments` and explicitly does not
  derive scientific state from shared `protocol_segments`;
- Chargeability owns `computation.chargeability` and automatic source-protocol/raw-data recognition;
- Rate capability owns `computation.rate_capability` and automatic source-protocol/raw-data
  recognition.

The result key must reflect those actual dependencies.

## Locked behavior 1 — ordinary autosave does not invalidate scientific queries

### Target

When the Analysis editor autosaves the current stable spec successfully:

1. the server's returned `AnalysisFull` becomes the authoritative cached detail for
   `['analysis', aid]` without forcing a second detail fetch where avoidable;
2. the compact Analysis Database/index query `['analyses']` is refreshed or invalidated so title,
   modified time, saved-plot index, and other relational summary fields remain current;
3. **no live scientific/result/artifact query is invalidated merely because the same in-memory spec
   was persisted**;
4. the dirty/saving/saved state machine remains unchanged from the user's perspective;
5. a late save for an older autosave signature must not clear `dirty` for a newer edit, preserving
   the existing `autosaveSignatureRef` guard.

Prefer a small shared helper in `analysisQueryCache.ts` (or an equivalently focused existing policy
module) so this distinction is testable:

```text
persisted-analysis-record refresh
!=
scientific/source invalidation
```

Do not weaken `invalidateAnalysisQueries()` for callers that genuinely changed source/scientific
inputs. Source replacement, continuation changes, cell metadata/scientific identity mutations, and
other current callers that require broad invalidation must keep that behavior.

### Saved-plot/artifact safety

Autosave decoupling must not suppress explicit saved-plot invalidation. The paths that create,
update, delete, or regenerate a saved plot/artifact remain responsible for their own thumbnail,
artifact, prepared-marker, and preview lifecycle. Do not rely on ordinary autosave's former broad
invalidation as an accidental substitute for those explicit paths.

### Acceptance

Automated coverage must prove at least:

- an ordinary persisted-analysis save updates/refetches the analysis detail/index as intended;
- mounted `time-capacity`, `compute`, `steps`, `dcir`, `chargeability`, `rate-capability`, saved
  preview, thumbnail, and artifact queries are **not** marked invalid solely by that autosave helper;
- the existing broad `invalidateAnalysisQueries()` tests still prove real scientific invalidation
  cancels/refetches affected active queries;
- unrelated analysis IDs remain untouched by a scoped save.

## Locked behavior 2 — compatible Time/Capacity placeholder retention

### Principle

A previous result may remain visible only when the **meaning of every returned coordinate/series is
compatible** and the new request merely changes which cycles/point density are requested.

### Add a separate compatibility identity

Keep the full `dataSignature` as the fetch/cache identity. Add a second, pure, tested
Time/Capacity placeholder-compatibility signature/policy.

The compatibility identity must include all fields whose change can make a previous compact result
misleading:

```text
analysis selection
protocol_segments
computation.protocol_filter
presentation.hidden_protocol_segment_ids
x_axis
time_unit
display_mode
electrode_area_cm2
voltage_channel
view (voltage/current vs dQ/dV vs dV/dQ)
derivative_phase
derivative_specific
derivative_absolute_discharge
smoothing_window
fixed viewport/render contract if it becomes variable
```

It must deliberately exclude only request-window/density fields that are safe to show temporarily
under the same scientific coordinate meaning:

```text
cycle_start
cycle_end
explicit cycles
max_points_per_cell
```

Changing one of those excluded fields may leave the old range/density on screen while the new
request is in flight. The UI must continue to report fetching/not-ready state correctly; the old
plot is temporary content, not the new result.

### Incompatible changes

Do **not** retain the old result when any compatibility field changes. In particular, never show:

- old cells under a new selection;
- old protocol-masked data under a new protocol selection/filter;
- old Time values relabelled as capacity or another unit;
- old consecutive placement under overlap/mirror mode;
- old mass/area-normalized values under a new normalization basis;
- primary cell voltage under a working/counter-potential label;
- voltage/current data under derivative labels or vice versa;
- derivative data computed with different phase/sign/smoothing semantics.

### Query-key implementation

The exact React Query key shape may change to carry the compatibility identity, for example:

```ts
["time-capacity", analysisId, compatibilitySignature, dataSignature]
```

or an equivalent query-policy mechanism that gives `placeholderData` access to the previous
compatibility identity. Preserve the stable root and analysis ID so existing scoped query-cache
predicates continue to work.

Do not remove any existing `dataSignature` field to achieve placeholder reuse.

### Acceptance

Add pure frontend coverage for the compatibility policy:

- `cycle_end: 3 -> 20` => compatible;
- range -> explicit cycle list => compatible if every other field is unchanged;
- `max_points_per_cell` change => compatible;
- selection change => incompatible;
- protocol filter/hidden segment change => incompatible;
- X quantity/time unit/display mode/electrode area change => incompatible;
- voltage-channel change => incompatible;
- derivative view/phase/sign/specific/smoothing change => incompatible.

The live query must retain the old result only in the compatible cases.

## Locked behavior 3 — propagate React Query abort signals

### Live Time/Capacity

Change the live query function from an argument-less callback to the React Query context form and
pass the signal into the existing API helper:

```ts
queryFn: ({ signal }) => post<TimeCapacityResult>(..., body, { signal })
```

Keep job-token creation/clearing and progress behavior correct when the request aborts. An aborted
superseded request must not publish a stale result or leave the component permanently in a
fetching/ready mismatch.

### Saved Time/Capacity preview

`SavedTimeCapacityPreview` is also React Query-owned and must pass its query signal into the
Time/Capacity POST used to generate a missing preview. Preserve its warmup/background flag,
artifact lookup ordering, and saved-plot signature checks.

Do not change portable-report sequential requests or non-React-Query request flows solely for
symmetry.

### Explicit limit of this child

Browser-side abort is the acceptance boundary here. FastAPI's synchronous compute may continue on a
worker thread after client disconnect. Do not add server cancellation flags, polling inside pandas,
or in-flight result deduplication in 050.1.

### Acceptance

- focused frontend tests continue to prove a cancelled active query is superseded safely;
- add a focused test/helper or structural assertion that the live and saved-preview Time/Capacity
  React Query functions forward the supplied signal to `post()`;
- abort must not be reported as a user-facing scientific error for an intentionally superseded
  request;
- real non-abort errors keep existing error behavior.

## Locked behavior 4 — family-specific backend scientific cache identity

### Replace whole-computation hashing with explicit dependency projection

Change `_scientific_spec()` or introduce an equivalent helper so `result_key(kind, ...)` hashes an
explicit scientific projection for that `kind`.

The target dependency map is:

### `cycles`

Include:

```text
selection
computation.cycle_range
computation.exclude_check_cycles_every_n
computation.retention_reference
computation.formation_cycles
computation.polarization
computation.protocol_filter
aggregation
protocol_segments (scientific fields; continue stripping protocol_group_id editor provenance)
presentation.hidden_protocol_segment_ids
```

Exclude:

```text
computation.time_capacity
computation.steps
computation.dcir
computation.chargeability
computation.rate_capability
dcir_segments
all other presentation-only fields
```

### `time_capacity`

Include:

```text
selection
computation.time_capacity
computation.cycle_range          # legacy/fallback cycle-range semantics
computation.protocol_filter
protocol_segments (scientific fields; strip protocol_group_id)
presentation.hidden_protocol_segment_ids
```

Exclude:

```text
aggregation
computation.exclude_check_cycles_every_n
computation.retention_reference
computation.formation_cycles
computation.polarization
computation.steps
computation.dcir
computation.chargeability
computation.rate_capability
dcir_segments
other presentation-only fields
```

Keep request options (`viewport_width`, `precision`, `compact`) in the existing separate
`request_options` key exactly as today.

### `steps`

Include:

```text
selection
computation.steps
protocol_segments (scientific fields; strip protocol_group_id)
```

Exclude generic Cycles/TimeCapacity/recognition-family computation, `aggregation`,
`dcir_segments`, hidden/presentation-only fields.

### `dcir`

Include:

```text
selection
computation.dcir
private top-level dcir_segments (scientific fields; strip protocol_group_id editor provenance)
```

Do **not** include shared `protocol_segments`; DCIR's documented scientific segment ownership is
private and isolated from Cycles/Steps protocol segments.

Exclude `aggregation`, unrelated computation-family blocks, and `presentation.dcir_view` including
candidate-recognition display thresholds.

### `chargeability`

Include:

```text
selection
computation.chargeability
```

The source fingerprints, parser identities, scalar metadata, and provenance/version inputs already
added by `result_key()` remain part of the complete key outside this spec projection.

Exclude `aggregation`, shared/private manual segment collections, unrelated computation blocks, and
presentation axis/view choices.

### `rate_capability`

Include:

```text
selection
computation.rate_capability
```

Again retain the existing source/unit/version fingerprints outside `_scientific_spec()`.

Exclude `aggregation`, shared/private manual segment collections, unrelated computation blocks, and
presentation renderer/axis choices.

### Unknown/new kinds

Fail closed rather than silently hashing too little. If `result_key()` is called with a result kind
that has no explicit dependency projection, raise a clear internal error or require an explicit
mapping before that new family can use the persistent result cache. Do not fall back to a broad
whole-spec hash that would reintroduce hidden dependencies.

### Defaults and legacy stored specs

Do not normalize missing keys into values that change scientific behavior. The cache projection must
match what the actual compute function will read from the same legacy/current spec. If a compute
path uses a generic fallback (notably Time/Capacity cycle range), retain the fallback source field in
its identity as specified above.

Do not mutate the persisted analysis spec while computing a key.

### Cache-generation consequence

This changes result-key computation. Follow the convention documented in
`backend/app/services/analysis_cache.py`:

- bump `ANALYSIS_CACHE_VERSION` from its current generation;
- add a concise comment identifying Spec 050.1 and the dependency-scope change;
- do **not** bump `CALC_VERSION` because scientific meaning is unchanged;
- do **not** change `RESULT_SCHEMA_VERSIONS` because response payload shapes are unchanged.

Because `saved_plot_data_signature()` is built from `result_key()`, saved plot artifacts/thumbnails
will receive a new scientific data signature once. Existing files remain disposable cache artifacts
and must never be served under the new identity. Normal warmup/artifact regeneration may recreate
them afterward.

No migration is required.

### Cache-key acceptance matrix

Extend `tests/test_analysis_cache.py` with direct, deterministic dependency tests. At minimum prove:

1. for every family, changing its own computation block changes its key;
2. for every family, changing another family's computation block does **not** change its key;
3. changing selection changes every family key;
4. Cycles changes for its generic calculation/filter/aggregation inputs;
5. Time/Capacity changes for its own config, generic fallback cycle range, protocol filter,
   scientific protocol segments, and hidden protocol-segment IDs;
6. Steps changes for its series/mode and scientific protocol segments, but not DCIR private
   segments;
7. DCIR changes for `computation.dcir` and private `dcir_segments`, but not shared
   `protocol_segments`;
8. Chargeability changes only for its own configuration among spec-owned analysis settings;
9. Rate capability changes only for its own configuration among spec-owned analysis settings;
10. changing presentation-only axes/styles does not change a scientific result key;
11. `protocol_group_id` editor provenance remains excluded from protocol/DCIR scientific segment
    identity;
12. existing source hash/parser/calc/unit-metadata/request-option key tests continue to pass.

Do not satisfy these tests by mocking `_scientific_spec()` itself; exercise the real projection and
`result_key()` where practical.

## Acceptance criteria

Child 050.1 is complete when all of the following are true:

- ordinary editor autosave no longer invalidates/refetches scientific analysis queries;
- genuine source/scientific invalidation remains broad and safe;
- compatible Time/Capacity range/density changes retain the previous result during fetch;
- incompatible Time/Capacity semantic changes never display an old result under new labels/meaning;
- live and saved-preview Time/Capacity React Query requests forward abort signals;
- cache keys are explicitly family-scoped according to the dependency map above;
- irrelevant family settings no longer alter another family's result key;
- relevant scientific inputs, source fingerprints, parser/calc identities, and request options still
  alter the appropriate key;
- `ANALYSIS_CACHE_VERSION` is advanced and old result/artifact identities cannot be served as new;
- `CALC_VERSION`, result payload shapes, scientific formulas, source provenance, exports, and
  database schema are unchanged;
- focused tests and `python scripts\preflight.py` pass;
- implementation/review records state the actual performance/request-count and manual/browser
  evidence obtained;
- the implementer stops after handoff and does not begin the reserved 050.2 investigation or code.

## Out of scope

- partial Parquet reads, predicate pushdown, row-group design, raw-column minimization, or source-cycle
  indexing;
- changes to `stitch_raw()` or global/source-local cycle mapping;
- changes to `_continuous_time`, capacity reconstruction, derivative calculation, protocol masking,
  voltage-channel semantics, or downsampling;
- server-side cooperative request cancellation;
- in-flight backend compute deduplication;
- generalized query-cancellation refactors for every analysis family;
- new database schema/migrations;
- `CALC_VERSION` changes;
- Time/Capacity scientific response schema changes;
- implementing or finalizing Child 050.2.
