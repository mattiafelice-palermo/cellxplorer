# 111.1 — Identity, storage and resolution

**Status:** Planned implementation step 1 of 7. [Parent contract](111-virtual-cells.md). First child on the shared feature branch.

Give a Virtual cell a distinct, stable identity. Implement the model behind an internal service before exposing a library action.

- Add a forward-only database revision for virtual definitions, ordered member references and their join settings. Reference existing physical Cell IDs. Apply uniqueness, ordered-position and referential integrity constraints. Preserve every pre-existing Cell, internal Test, file link, watch, analysis, folder and replicate membership.
- Use a typed analysis subject, for example `{kind: "virtual_cell", ref_id}`. Numeric IDs from different kinds may coincide. Keep physical-cell APIs and existing serialized selections compatible. Audit dictionaries, visibility keys, worker payloads and cache keys currently keyed by a bare Cell ID.
- Resolve a definition to ordered runs, each run’s ordered sources, parser capabilities, scientific references and join boundaries. Use the physical resolver within each run. Batch reads across subjects. Library listing and eligibility checks read registered facts without opening MPRs or scientific caches.
- Enforce the parent eligibility rules on the server. Preserve the distinction between a registered BioLogic source with limited measurements and an unsupported file. Never infer a protocol or measurement capability from the suffix. Return reasons tied to the affected run.
- Represent active and retired definitions and a revision used for stale-preview detection. Distinguish the live member chain from the retained source-membership record needed when ungrouping. Keep physical ownership unique.

**Acceptance.** Upgrade a database containing A, B, an existing A analysis and a B folder watch. Compare IDs, ordered file links, analysis JSON and watch configuration before and after migration. Exercise ID collisions, duplicate members, nested selections, empty chains, mixed suppliers and a physical run that already has multiple MPRs. Verify ordinary requests still use the existing physical fast path.
