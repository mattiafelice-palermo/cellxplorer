## Goal

Reduce the elapsed time from starting the GitHub Windows release job to a verified, usable release
**without removing, weakening, sampling, or bypassing any correctness, packaging, signing, updater,
or publication safety check**.

Optimize duplicated work and scheduling, not verification content. The key principles are:

- a successful canonical preflight for the **exact release SHA** may be reused instead of rerun;
- unavailable caches or reusable CI results must degrade to the existing full work, never to less work;
- independent work should run concurrently when GitHub Actions supports it and the steps do not have
  a data/output dependency or unsafe shared writes;
- the exact frontend/sidecar artifacts passed to Tauri must still be verified before packaging;
- release publication remains fail-closed and sequential after artifacts exist.

No application, scientific, parser, database, or UI behavior changes are part of this child.

Use the live workflow history again before implementation, but the authoring baseline is the successful

The Windows job ran approximately from 15:08:39 to 15:23:32 UTC on 2026-08-16. The channel pointer was
published at about 15:22:48, so the meaningful **release-ready wall time** was about **14 min 09 s**;
post-job cache cleanup extended total job completion by roughly another 44 s.

Representative step timings from that run:

| Step | Approx. wall time |
| --- | ---: |
| cancel redundant main preflight | 15 s |
| install backend dependencies | 41 s |
| install frontend/Tauri dependencies | 38 s |
| canonical release-local preflight | 1 min 58 s |
| rebuild requested frontend channel | 32 s |
| build Python sidecar | 56 s |
| Tauri signed-release stage | 8 min 17 s |
| of which Cargo release compilation | 7 min 33 s |
| NSIS packaging itself | roughly 30–35 s |
| post-run Rust-cache save/cleanup | roughly 36 s |

The same SHA also ran the normal `main` Windows preflight concurrently. That job succeeded, while the
release job independently performed another full preflight for the exact same commit. The current
best-effort cancellation therefore did not prevent duplicated verification.

The release Rust cache also reported **no cache found**. Its cache is currently created from the tag
release workflow itself. GitHub Actions cache scope isolates different tags, so a cache saved under one
release tag cannot warm the next tag. GitHub permits branch/tag workflows to restore a matching cache
from the default branch, which is the path this spec should use.

## Locked decisions

1. **Do not remove any existing correctness or publication safety gate.** Release tag/version checks,
   main reachability, channel rules, immutable-release checks, release-note extraction, updater signing,
   packaged-backend smoke testing, updater-manifest/signature verification, draft-before-publish,
   optimistic channel-pointer update, public/raw verification, and non-target pointer invariance remain.
2. **Do not replace a full preflight with a partial test selection.** A release may skip its own full
   preflight only when a trusted canonical Windows preflight already succeeded for the exact same SHA.
3. **A failed exact-SHA canonical preflight is a release failure.** Do not rerun until green and then
   publish over a known failing CI result. Missing/skipped/cancelled results may use the release-local
   full-preflight fallback.
4. **Caches are acceleration only.** A cache miss/corrupt/unavailable cache must cause normal rebuild,
   not failure to verify and not skipped compilation.
5. **Seed reusable Rust cache only from a trusted default-branch workflow.** Do not rely on release-tag
   caches as the cross-release source of truth; GitHub isolates caches between different tag names.
6. **Release-tag Rust cache use should be restore-only.** Once `main` owns the reusable seed, do not spend
   tens of seconds cleaning/saving a tag-scoped cache that future tags cannot reuse.
7. **Use native GitHub Actions parallel steps.** GitHub Actions supports `parallel`, `background`,
   `wait`, and `wait-all`. Prefer a `parallel` block for bounded independent work instead of shell
   background jobs, PowerShell jobs, or interleaved logging hacks.
8. Parallelize only when steps have no ordering dependency and do not unsafely mutate the same files.
   Failure of any member of a required parallel group must fail the group/job normally.
9. **Do not parallelize publication state mutations.** Draft creation/upload, staged-asset discovery,
   manifest/signature verification, undraft/publication, and channel-pointer mutation/verification stay
   ordered exactly by their data dependencies.
10. Preserve deterministic logs and useful step names. Runtime optimization must not turn failures into
    opaque combined shell output.
11. Do not add paid third-party runners, external build services, unpinned third-party actions, or a
    new CI platform for this work.
12. Do not change release SemVer/channel policy or application version numbers solely to test this spec.
13. If concurrent CPU-heavy work is measurably slower or flaky on `windows-latest`, keep that particular
    pair serial and record the measurement. The requirement is lower reliable wall time, not concurrency
    for its own sake.

## 1. Make the `main` Windows preflight a reusable exact-SHA gate

### Current problem

The preflight workflow currently contains a release-tag gate intended to avoid duplicate work, while
the release workflow independently tries to cancel an in-progress main preflight and then unconditionally
runs its own no-cache preflight. In the observed release both full preflights ran anyway.

### Target

The `push` to `main` Windows preflight becomes the preferred canonical result for release tags pointing
at that same commit.

- A normal push to `main` should run the canonical Windows preflight even if a release tag is created
  around the same time. Remove/simplify the gate that makes the main result disappear precisely when a
  release wants to reuse it.
- `workflow_dispatch` remains available for manual clean verification.
- Preserve the existing complete Windows preflight contents.
- Give the Windows preflight job a stable, grep-able name; release logic must verify that this specific
  job succeeded, not merely that some workflow run with the same SHA exists.

The release workflow must stop trying to cancel the `main` preflight. Reduce `actions: write` to
`actions: read` if no remaining release operation requires Actions write permission.

### Exact-SHA trust rules

Release-side discovery must use the GitHub API/CLI and accept a reusable result only when all required
facts are true:

```text
workflow file/name = canonical preflight workflow
head SHA = GITHUB_SHA exactly
origin = trusted main push (not an arbitrary sibling/PR result)
Windows canonical preflight job = completed + success
```

Do not trust only workflow display name, branch text, or a commit-status string.

If the exact-SHA run is still active when the release reaches the verification barrier, wait for it in
a bounded/observable way. Because dependency setup and other safe preparation can happen first, the
release should normally reach this barrier after much of the main preflight has already elapsed.

Resolution policy:

- canonical Windows preflight **success** -> mark `reuse_preflight=true`; do not rerun it;
- canonical Windows preflight **failure** -> fail release;
- canonical Windows preflight **missing, skipped, or cancelled** -> run the existing full release-local
  no-cache preflight;
- canonical Windows preflight still active after a generous bounded wait -> fail with a clear message or
  run the full local fallback only if implementation can prove this does not mask an already-failed run.
  Prefer fail-closed over publishing while the canonical run later turns red.

Manual build-only dispatch on a feature branch will usually have no exact-SHA main result and therefore
must continue to exercise the full local fallback.

## 2. Seed a production Rust dependency cache from `main`

### Current problem

`Swatinem/rust-cache` is currently invoked only in the release job. The observed release restored
nothing and spent about 7 min 33 s inside Cargo. A tag-created cache is scoped to that tag and does not
warm a differently named future tag.

### Target cache ownership

Add a small independent Windows job to `.github/workflows/preflight.yml` whose sole purpose is to keep a
**default-branch production-profile Rust dependency cache** warm.

Recommended structure:

1. checkout;
2. install the exact same Rust toolchain action/version as release;
3. use the exact same pinned `Swatinem/rust-cache` action/version as release;
4. configure a stable shared key for the Windows release dependency cache and disable automatic job-ID
   differentiation so the preflight cache-warmer and release job resolve the same cache family;
5. keep `workspaces: src-tauri -> target` and the automatic Cargo manifest/lock/toolchain environment hash;
6. if the exact cache is absent, run a production-profile Cargo build sufficient to compile the release
   dependency graph, e.g. `cargo build --release --locked --manifest-path src-tauri/Cargo.toml` after
   confirming that command succeeds on a clean runner without generated frontend/sidecar inputs;
7. if the exact cache is already present, avoid recompiling merely to save the same dependency cache again.

Do **not** invent dummy packaged resources to make the warm build pass. If plain Cargo cannot safely warm
this Tauri crate on a clean checkout, use the least invasive production-profile Cargo/Tauri preparation
that builds dependencies without publishing/signing, and document why.

The cache-warmer should be an independent job so GitHub can run it concurrently with the normal Windows
preflight on a separate runner. It is an acceleration helper, not the canonical correctness gate:

- a cache-warm failure must never cause release verification to be skipped;
- release must remain capable of a cold Cargo build;
- decide whether a cache-warm infrastructure failure should fail the overall preflight workflow or report
  a warning only; prefer not making cache availability a correctness requirement.

### Release restore behavior

Configure the release `rust-cache` step with the matching shared key and as **restore-only** (for
`Swatinem/rust-cache`, use its supported `save-if`/equivalent configuration rather than a custom cache
upload). Keep the automatic Rust-environment/Cargo manifest hash so dependency changes invalidate safely.

Acceptance evidence must show, after a cache has been seeded on the same branch/default-branch scope,
that a later release rehearsal reports a Rust cache restore and materially reduces the Cargo stage.

## 3. Parallelize independent dependency installation

After checkout and the language/toolchain setup actions complete, the following commands operate on
independent dependency domains and should run with a native GitHub Actions `parallel` group:

### Backend member

```powershell
python -m pip install --upgrade pip
python -m pip install -r backend/requirements.txt
python -m pip install pyinstaller
python -m pip check
```

### Frontend/Tauri member

```powershell
npm ci
npm --prefix frontend ci
```

Both must retain separate step names/logs and normal failure propagation. Do not parallelize setup actions
that concurrently modify shared `PATH`/environment files unless GitHub's documented semantics and a real
run prove it safe and useful; their few seconds are not the meaningful bottleneck.

Apply the same principle elsewhere in CI when there is a material independent pair. Do not create a large
parallel block around one-second policy gates just to maximize the count of concurrent steps.

## 4. Build release inputs concurrently where their write sets are independent

The channel frontend and Python sidecar are independent package inputs:

```text
frontend build -> frontend/dist + channel stamp
sidecar build with -SkipFrontend -> src-tauri/binaries/backend/... (+ PyInstaller build/dist paths)
```

On the path where an exact-SHA main preflight is reused, build these two inputs in one native `parallel`
group, then verify both after the group finishes:

- `python scripts/build_frontend_channel.py <channel>`;
- `.\scripts\build-app.ps1 -Channel <channel> -SkipInstall -SkipFrontend -SkipInstaller -ForceBackend`.

Follow with the existing channel-stamp verification, packaged-input existence checks, and real packaged
backend smoke test before Tauri packaging.

### Release-local preflight fallback path

Do not build the frontend twice when the release has to run its own preflight.

The local no-cache preflight already includes a production frontend bundle. Make that build the selected
release channel by providing `VITE_CELLXPLORER_CHANNEL=<resolved channel>` to the preflight environment.
After the preflight succeeds:

```powershell
python scripts/frontend_channel.py write --channel <channel>
python scripts/frontend_channel.py verify --channel <channel>
```

This stamps and verifies the **same `frontend/dist` bundle that passed the local preflight** rather than
rerunning Vite immediately afterwards.

The sidecar may run concurrently with the release-local preflight only if a real rehearsal shows the
shared Windows runner has enough CPU/I/O headroom to reduce wall time without flakiness. Child 048's
preflight/test pool may intentionally use most CPU cores, so this pair requires measurement. If parallel
execution is slower or unstable, keep the sidecar serial on the fallback path and record why.

There must be no execution path that reaches Tauri packaging with:

- no full exact-SHA preflight proof;
- an unstamped frontend;
- a frontend stamp for the wrong channel;
- missing sidecar files; or
- an un-smoke-tested packaged backend.

## 5. Preserve the release publication barrier

Do not move these operations ahead of completed verification merely to overlap network time:

```text
Stage signed draft release / Build release artifacts only
Locate generated updater manifest
Export draft release assets metadata
Download staged draft manifest and signature
Verify updater manifest
Publish verified draft release
Publish channel manifest pointer
```

The draft-release model is intentional: the installer/signature/manifest are staged, read back, verified,
and only then published. The selected channel pointer is changed only after the immutable GitHub Release
is valid. Keep this dependency chain sequential.

The final `frontend_channel.py verify` immediately before Tauri remains valuable and should stay even if an
earlier verification has already passed; it is cheap and protects against accidental later mutation.

## 6. Workflow tests

Extend `tests/test_release_workflow.py` and add a focused preflight-workflow test if that is clearer.
Tests should fail if future edits silently restore the slow/unsafe architecture.

At minimum assert:

1. release no longer contains the best-effort main-preflight cancellation loop;
2. release permissions no longer request `actions: write` unless another demonstrated operation needs it;
3. exact-SHA reusable preflight logic requires the canonical Windows job to be successful;
4. exact-SHA failure cannot silently fall through to publication;
5. missing/skipped/cancelled reusable result still leads to a full local no-cache preflight;
6. preflight workflow no longer suppresses the canonical main verification merely because a release tag
   points at that commit;
7. the reusable Rust cache uses matching stable/shared key configuration in main preflight and release;
8. release cache use is restore-only while main owns cache seeding;
9. backend pip install and frontend npm install are inside a native GitHub `parallel` group with both
   command sets preserved;
10. exact-SHA reuse path builds frontend + sidecar concurrently, then verifies both before Tauri;
11. local fallback uses a channel-aware production bundle and writes/verifies its channel stamp without a
    second redundant frontend production build;
12. Tauri packaging still depends on preflight proof + verified frontend + verified/smoke-tested sidecar;
13. updater/signature/draft/pointer verification steps still exist and preserve their ordering.

Prefer structural YAML assertions where practical rather than fragile whole-file substring ordering. If
introducing a YAML parser dependency would be disproportionate, bounded text/regex tests are acceptable;
do not add a large dependency solely for workflow tests.

1. run all focused static/unit workflow tests locally;
2. run canonical local preflight;
3. if repository permissions/secrets permit, manually dispatch the updated preflight workflow on the

5. record per-step GitHub timings and whether cache restore hit;
6. if manual GitHub dispatch is unavailable to the implementer environment, state that explicitly and do

Use **release-ready** time as the metric for production tags: Windows job start through successful
`Publish channel manifest pointer`, excluding post-job cache cleanup. For manual build-only rehearsal,
use job start through completion of `Build release artifacts only`, again excluding post-job cleanup.

### Performance target

On a warm Rust-cache path, target at least a **40% reduction** versus the comparable current release
pipeline, with an expected production release-ready time in roughly the **5–7 minute** range. Treat this
as a performance target, not a reason to delete a safety check if GitHub runner variance causes one run
to exceed it.

The most important step-level acceptance is that a seeded cache removes the multi-minute cold dependency
compile: the warm Cargo/Tauri compile should be materially below the observed 7m33s baseline. Record the
actual value rather than assuming a particular number.

## Acceptance criteria

1. A trusted successful canonical Windows preflight for the exact release SHA can be reused by a tag
   release, eliminating the duplicate full preflight seen in the baseline.
2. A failed exact-SHA canonical Windows preflight blocks release. Missing/skipped/cancelled reuse evidence
   falls back to a full release-local no-cache preflight.
3. The `main` preflight workflow no longer races the release by skipping/canceling its canonical result.
4. A default-branch production Rust dependency cache is seeded with the same dependency/toolchain key
   semantics used by the release job.
5. Release tags restore that cache when available and remain correct on a cache miss; tag builds do not
   spend post-job time saving a cache that a differently named future tag cannot use.
6. Backend pip and frontend/Tauri npm dependency installs run concurrently using native GitHub Actions
   parallel-step syntax and retain independent failure logs.
7. On the reused-preflight path, channel frontend and sidecar builds run concurrently, and both are fully
   verified before Tauri starts.
8. On the local-preflight fallback path, the selected-channel production frontend bundle is built once,
   stamped after successful preflight, and verified before packaging; there is no redundant immediate
   second Vite build.
9. The packaged backend smoke test still executes the built sidecar before Tauri packaging.
10. Release channel/version/reachability, immutable-release, signing, draft staging, updater manifest /
    signature verification, publication, channel-pointer optimistic update, public byte verification, and
    non-target pointer checks remain present and fail-closed.
11. Focused workflow tests and full local no-cache + normal preflight pass.
12. GitHub rehearsal evidence is recorded when tooling permits. A warm run shows a material reduction in
    Cargo/release wall time attributable to cache reuse/parallel scheduling rather than removed checks.
13. Durable Windows/release documentation describes the new exact-SHA preflight reuse and default-branch
    Rust-cache ownership accurately.
14. Final review can state that every removed release-time operation was either duplicate work, serial
    scheduling of independent work, or unusable tag-scoped cache maintenance — not removed verification.
