## Goal

Measure the **current post-050.7 Time/Capacity execution path** and determine how much independent per-Cell work benefits from ordinary Python threading before any production concurrency architecture is chosen.

This child intentionally separates two hypotheses:

1. concurrent threads help primarily because independent PyArrow/Parquet reads/decode overlap;
2. the complete existing per-Cell Python job also scales because enough of its NumPy/PyArrow/vectorized work executes outside the GIL.

Do not conflate them. The output of this child is a reproducible ablation table and a decision, not production executor wiring.

## Why this child exists

Accepted Spec 050 evidence shows that the bottleneck has moved repeatedly:

- before 050.6, six-Cell All/Time was about 4.42 s and phase/capacity reconstruction dominated;
- after dependency-aware work elimination in 050.6, the representative six-Cell All/Time backend median was about 0.54 s;
- broad capacity-axis work remained more expensive, about 0.72 s for six Cells on the accepted fixture;
- after 050.7, a broad one-Cell derivative stage was still about 156-158 ms.

Those historical numbers justify re-measuring cross-Cell scaling, but they do **not** establish today's I/O/CPU percentages. Start from the actual current branch.

The representative real user stress case is roughly **10 large Cells displayed together**. Do not optimize only for one Cell.

## Locked decisions

1. **Current production path first.** Re-profile before building concurrency experiments.
2. **No production executor in this child.** Threaded candidates belong to a benchmark/test adapter or isolated harness.
3. **Cross-Cell only.** Do not parallelize within one derivative segment or formula.
4. **Deterministic merge.** Completion order must never alter Cell/series/result ordering.
5. **Exact result-cache hits remain direct.** Do not dispatch benchmark workers on a persisted exact hit.
6. **Use bounded worker counts:** sequential, 2 threads and 4 threads. Do not auto-scale to CPU count.
7. **Control native oversubscription.** Record relevant PyArrow/NumPy/BLAS/native worker settings.
8. **No ORM/session sharing.** Resolve relational state in the owning Python context; worker jobs receive only the minimum safe immutable inputs needed by the experiment.
9. **No scientific change.** Formulas, thresholds, phase rules, derivative behavior, provenance, continuation semantics and response shape remain unchanged.
10. **No new persistent cache or whole-Cell RAM cache.** Measure against the current architecture.
11. **No Rust in 050.9.** Rust/Rayon is isolated in 050.10 so its gain can be attributed separately.
12. **No adaptive zoom or Plotly redesign.** A narrow range may be used as a workload control only.

## Required baseline decomposition — A0

First measure the existing sequential production path. For representative broad normal and derivative requests report, where measurable:

- total backend wall time;
- relational/request setup;
- raw/prepared Parquet read/decode;
- required scientific transforms;
- derivative stage when applicable;
- downsampling/display-row selection;
- result assembly;
- serialization;
- aggregate CPU time / effective core use;
- peak RSS;
- row groups, rows and columns materialized.

If existing profilers already expose a stage accurately, reuse it. Do not add intrusive timing that materially changes the workload.

Also record whether the nominally sequential request already uses multiple cores through native libraries.

## Required Python-thread ablation

Run every applicable candidate against identical prepared data/settings.

### B1 — read/decode concurrency only, 2 threads

Parallelize only independent per-Cell raw/prepared Parquet materialization/decode. After reads finish, execute the existing scientific transform path sequentially.

Purpose: isolate the value of overlapping I/O/native decode.

### B2 — read/decode concurrency only, 4 threads

Same boundary with four workers.

Record whether wall time falls, remains flat, or grows because the SSD/cache/native decoder is saturated.

### B3 — whole existing per-Cell job, 2 threads

Each worker performs the existing per-Cell read plus existing transforms; final merge remains deterministic in original selection order.

Purpose: test whether the current job spends enough time in PyArrow/NumPy/native vectorized operations for ordinary Python threads to scale despite the GIL.

### B4 — whole existing per-Cell job, 4 threads

Same boundary with four workers.

The benchmark must separately report B1/B2 and B3/B4. Do not report only the fastest thread configuration.

## Implementation record and evidence

The benchmark and its profiler-only instrumentation are implemented on the branch. The
production path remains sequential and keeps its existing scientific response contract when
diagnostics are not requested.

### Implementation boundary

- `analysis_engine.compute_time_capacity()` now records per-Cell job wall time only inside the
  existing opt-in profiling diagnostics. `time_capacity_profiling` aggregates that measurement
  without exposing Cell identity or raw data.
- `time_capacity_path` has an opt-in `wait_for_layout` read-boundary override used only by the
  benchmark to avoid measuring a transient cache-layout lock race. Its default remains the
  existing non-blocking behavior.
- `scripts/profile_time_capacity_concurrency.py` measures A0, B1/B2 read/decode prefetch, and
  B3/B4 complete existing per-Cell jobs. B3/B4 use independent SQLite sessions and merge by
  original selection index; no production executor, process pool, Rust extension, adaptive zoom,
  or Plotly behavior was added.
- The benchmark records stage timings, CPU/effective cores, queue/dispatch time, row groups,
  rows, columns, native thread settings, and process-lifetime peak RSS on Windows. It compares
  scientific payload digests, finite/non-finite placement, and canonical output ordering for
  every candidate.

The application suite used the real local database read-only. Its saved `Performance analysis`
(database analysis id 36) selects five Cells; the benchmark derives the available contiguous
  BQV performance batch and measures eleven Cells. The database is copied to a disposable SQLite
  file for benchmark-owned analysis rows, while the real cache sidecars are only read. The
  controlled suite uses the committed golden source plus ten disposable source-identical Cell
  clones. No Cell names, paths, hashes, or raw values are written to the report.

### Full matrix result

Command:

```text
python scripts/profile_time_capacity_concurrency.py --repetitions 5 --output tmp/050.9-concurrency-profile.json
```

The run covered 27 workload rows (13 golden-fixture and 14 real-application rows, including the
11-Cell workload), five repetitions, and 675 candidate runs. Every candidate passed scientific
parity and canonical ordering. Both exact persisted-cache controls passed: first request miss,
second request hit, with no raw access or worker dispatch on the hit. The continuation-boundary
control is `NOT RUN` because both harnesses contain one source per Cell; a continuation is not
available in the representative data used here. The narrow viewport-like control was run as
`control-6-cycles-1-20-time`.

Representative median backend wall times in milliseconds are:

| Suite / workload | A0 | B1 | B2 | B3 | B4 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Golden, 6 Cells, All capacity | 679.3 | 679.9 | 667.7 | 904.2 | 962.8 |
| Golden, 6 Cells, dQ/dV | 1491.0 | 1498.7 | 1492.0 | 1870.0 | 2168.5 |
| Real app, 11 Cells, All time | 1002.8 | 1004.8 | 1031.5 | 1094.3 | 1086.2 |
| Real app, 6 Cells, All capacity | 747.3 | 754.5 | 743.8 | 977.3 | 1118.4 |
| Real app, 6 Cells, dQ/dV | 1997.8 | 1972.5 | 1978.4 | 2246.1 | 2777.3 |

Using the specified 5% median paired-change threshold, the decisions are:

1. Read/decode concurrency: **useful** at both B1 (2 workers) and B2 (4 workers), with the
   benefit workload-dependent rather than a universal wall-time reduction.
2. Whole-Cell Python threads: **harmful** at both B3 (2 workers) and B4 (4 workers).
3. Small-job regression: **not acceptable**; the single-Cell and small derivative controls do
   not justify a general threaded whole-Cell executor.
4. Dominant residual stage: **Python/native transform** overall. Derivative requests have a
   separate dominant derivative stage: the six-Cell dQ/dV derivative median was 838.7 ms in the
   golden suite and 1238.9 ms in the real application suite, versus transform medians of 369.0
   ms and 410.7 ms respectively.
5. 050.10 handoff: isolate the measured derivative rolling, gradient, ratio/filter, and
   postprocess kernels. The derivative stage spans approximately 136–1263 ms across the measured
   one- to six-Cell suites, so 050.10 should measure those kernels separately before selecting a
   Rust/Rayon boundary.

The full report also records the execution environment: Python sees 16 CPUs, NumPy is 2.5.0,
PyArrow is 24.0.0 with a 16-CPU pool and 8 I/O threads, and the common native-thread environment
variables were unset. Peak RSS is explicitly labelled as process-lifetime Windows
`PeakWorkingSetSize`. A final one-repetition derivative smoke after report-format enrichment
passed the same parity and cache-control checks and verified derivative substages and RSS scope.

## Acceptance criteria

- A0 current-path decomposition is recorded from the current branch, not inferred from old 050.5 measurements.
- B1/B2 and B3/B4 are all measured independently on the required representative workloads where the environment permits.
- The 10-Cell Time-axis workload is measured when a valid representative dataset/stress harness is available; otherwise it is explicitly deferred rather than extrapolated as proof.
- I/O contention, native oversubscription, CPU use and peak memory are reported.
- Scientific parity and deterministic ordering are proven for every executed candidate.
- Exact persisted cache hits do not enter worker execution.
- No production thread pool, process pool, Rust extension, adaptive zoom or Plotly change lands from this child.
- The child records an explicit handoff to 050.10 naming the measured kernel(s), if any.
