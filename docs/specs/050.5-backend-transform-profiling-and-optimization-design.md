# Spec 050.5: backend transform profiling and optimization design

Status: **Implementation-ready profiling child**  
Parent: [`050-runtime-performance-optimization.md`](050-runtime-performance-optimization.md)  
Branch: `feature/runtime-performance-optimization`  
Origin: user-supplied installed-app 050.4 profile on 2026-08-21 and explicit user decision to let the implementer perform the next profiling activities locally.

## Goal

Turn the 050.4 end-to-end evidence into a precise backend optimization design by profiling the remaining expensive Time/Capacity scientific stages in enough detail to determine what work is actually avoidable.

This child is still a **measurement/design child**, not the optimization itself. It may add bounded profiler-only timing counters, benchmark scripts and focused tests, but it must not introduce a production derived-data cache, precompute layer, multiresolution representation, new scientific algorithm, Plotly rewrite or derivative optimization before the evidence identifies the correct boundary.

The child must answer these questions:

1. Why does the normal Voltage/Current Time/Capacity path spend most remaining time in the combined `continuous_time_phase_capacity` stage?
2. Which sub-operations inside that stage are required for each interactive view/x-axis, and which are currently performed even when the selected view does not consume them?
3. Which expensive derived quantities are invariant for a prepared Cell/source chain and therefore plausible candidates for safe reuse rather than recomputation on every range request?
4. For broad/multi-Cell interactive views, is the best next step reusable derived-row preparation, a scientifically safe overview representation, or another measured design?
5. Why does dQ/dV scale separately to multi-second backend work and hundreds of Plotly traces, and should that become a separate optimization child?
6. Are the occasional large HTTP-minus-backend gaps seen in the user's profile reproducible, or transient/non-systematic?
7. What does a true persisted analysis-result-cache HTTP hit cost when React Query memory is deliberately bypassed?

The child must end with an evidence-backed recommendation for the next implementation child or children. It must not guess the implementation first and then benchmark it.

## Evidence that triggered this child

The user's installed-app 050.4 recording contained **35 completed interactions**: 19 HTTP interactions and 16 React Query memory hits. The profiler used the real interactive contract (`precision="standard"`, `compact=true`, normal 4,000-point-per-Cell budget).

Representative normal Voltage/Current measurements were:

| 1-20 | 1 | 294 ms | 197 ms | 25 ms | 9,423 | 3,700 |
| 1-150 | 1 | 454 ms | 370 ms | 20 ms | 42,563 | 3,964 |

The indexed 050.3 access path is working: narrow requests read only the relevant row groups. For the one-Cell normal path, indexed raw access was about 31 ms for 1-20, 40 ms for 1-150 and 45 ms for All, while the combined `continuous_time_phase_capacity` stage was about 53 ms, 198 ms and 418 ms respectively. For five Cells / All, indexed raw access was about 177 ms while `continuous_time_phase_capacity` was about 1,983 ms. For six Cells / All, indexed raw access was about 662 ms while `continuous_time_phase_capacity` was about 2,620 ms.

The interactive output remains bounded near 4,000 points per Cell even when hundreds of thousands of selected rows enter transforms. This is **not** permission to downsample raw rows before scientific transforms; it is the measured reason to determine whether some transformations can be safely reused or avoided.

React Query exact-memory reuse is already excellent: the 16 memory-hit interactions had a median total interaction of about **34 ms**. Therefore this child must not start by adding another general-purpose browser cache or speculative neighbor prefetch.

The same recording showed a separate dQ/dV signature:

| dQ/dV scenario | Backend total | Derivative stage | Plotly | Trace count |
| --- | ---: | ---: | ---: | ---: |
| 1-3, 1 Cell | 238 ms | 26 ms | 25 ms | 7 |
| 1-20, 1 Cell | 320 ms | 155 ms | 28 ms | 35 |
| All, 1 Cell | 3,013 ms | 2,296 ms | 388 ms | 610 |

That is sufficiently different from the normal Voltage/Current path that 050.5 must diagnose it separately and must not silently combine both optimization implementations into one later child.

The installed-app recording did **not** contain a true persisted analysis-result-cache HTTP hit; exact warm revisits were satisfied from React Query memory. It also contained two five-Cell narrow HTTP requests where the HTTP round trip was about 1.17 s while backend total was only about 0.30-0.39 s. A later comparable five-Cell single-cycle miss was about 296 ms HTTP / 270 ms backend. Treat the earlier gaps as an investigation question, not as established transport cost.

## Locked decisions

1. **Profiling/design only.** Do not implement the eventual optimization in this child.
2. **No scientific change.** Time, cycle mapping, phase meaning, capacity reconstruction, derivative mathematics, protocol masking, provenance, units, hidden-data semantics and exports remain unchanged.
3. Scientific calculations remain backend-owned.
4. Complete selected-cycle rows still feed any calculation whose result depends on those rows; do not pre-downsample scientific inputs merely because display output is bounded.
5. Split the combined hotspot before choosing a solution; do not assume `continuous_time_phase_capacity` is one cost.
6. Audit actual downstream dependencies; do not assume every transform is required for every view.
7. Any proposed reusable/prepared quantity must have explicit dependency, invalidation and version ownership before a later implementation can use it.
8. Do not add a persistent derived cache, multiresolution representation, derivative cache, Plotly redesign or general RAM/browser cache in 050.5.
9. Keep dQ/dV diagnosis separate from normal Voltage/Current diagnosis.
10. `CALC_VERSION`, parser identity, canonical/raw-layout/result-schema versions and SQLite schema remain unchanged for profiler-only work.
11. Profiler overhead is bounded and opt-in/test-only; ordinary requests must not permanently pay for fine-grained diagnostics.
12. No external telemetry.
13. Preserve the existing 050.4 installed-app profiling controls.
14. Do not implement proto-child 050.P1 or cross-family work.
15. Do not modify, reset or discard unrelated branch work.

## Profiling activity A — split the normal transform hotspot

For normal `voltage_current` requests, add profiler-only timing boundaries around the work currently grouped under `continuous_time_phase_capacity`. At minimum distinguish, where current code confirms these boundaries:

1. `_continuous_time(raw)`;
2. source-column/source-boundary preparation used by continuation handling;
3. `_phase_from_raw(...)` or equivalent phase classification;
4. `_phase_capacity(...)` / capacity reconstruction;
5. DataFrame assignment/copy/materialization directly associated with those derived columns;
6. any other substantial operation currently hidden inside the combined stage.

The exact boundaries must follow actual code rather than this list mechanically.

For each measured sub-stage report wall time, input rows, output rows where meaningful, Cells processed, cycle range/All state, and whether the current view/x-axis actually consumes the derived quantity downstream.

### Required matrix

Use representative prepared data and the real compact/standard request contract. At minimum profile:

- 1 Cell: 1 cycle, 1-20, 1-150, All;
- multi-Cell: 1-20, 1-150, All, using 3-6 Cells when representative data are available;
- both `x_axis="time"` and `x_axis="capacity_mah"` for at least one broad range;
- one cached exact HTTP hit and one result-cache miss for the same request.

If the exact user's six-Cell dataset is unavailable, use the nearest representative fixture/analysis and preserve structural counts. Do not fabricate equality with the user's timings.

## Profiling activity C — reuse/preparation feasibility

For each expensive sub-transform, determine whether the value is invariant for a prepared Cell/source chain or depends on request-specific settings.

For every candidate reusable quantity, document:

- exact inputs/dependencies;
- whether it changes with cycle range;
- whether it changes with source continuation order;
- whether it changes with parser/canonical/raw-layout identity;
- whether it changes with protocol filter, selected voltage channel, x-axis, display mode, derivative settings or presentation-only state;
- whether it can be derived once while complete canonical source rows are already being prepared;
- whether storing/reusing it would duplicate canonical scientific data or merely store a regenerable derived representation;
- what cache key/version/invalidation boundary a future implementation would require;
- expected memory/disk footprint order of magnitude on the representative source.

Do not implement the candidate here.

## Profiling activity D — broad interactive overview decision

Using measured stage costs, determine whether broad/All latency is primarily:

- repeated exact derivation that could be safely prepared/reused while still returning exact interactive values;
- unavoidable exact transform work that should instead be represented by a separate interactive overview;
- another specific measured cause.

If a multiresolution/overview child is recommended, define what would remain exact and what could be approximate. Full-resolution export remains exact. Do not implement the overview in 050.5.

## Profiling activity E — dQ/dV decomposition

Profile `_derivative_curve()` deeply enough to explain the 050.4 scaling from ~26 ms at 1-3 cycles to ~2.30 s at All cycles for one Cell.

At minimum record:

- cycles/phase segments processed;
- rows entering derivative calculation;
- number of derivative output series/segments;
- time spent in the main numerical derivative/smoothing/interpolation sub-operations identified in current code;
- returned points;
- backend-produced series/segment count if available;
- relationship to frontend Plotly trace count (050.4 observed 7, 35 and 610 traces for 1-3, 1-20 and All respectively).

Inspect frontend trace construction to explain why All cycles produces hundreds of traces. Do not change the trace architecture here.

The final recommendation must state whether derivative optimization belongs in the same later implementation child as normal Time/Capacity transforms or should be split. Prefer a separate child when ownership/scientific risk differs.

## Profiling activity G — investigate unexplained HTTP/backend gaps

050.4 observed two five-Cell narrow misses with ~1.17 s browser HTTP round trip but only ~0.30-0.39 s backend total, while a later similar request was ~296 ms HTTP / ~270 ms backend.

Use the local route/test harness to determine whether a systematic gap exists outside the backend timer. Investigate only measured boundaries such as request parsing/route prelude before backend timing, response handoff after backend timing, local server scheduling/queueing, and the already-defined fetch/JSON-parse boundary.

Do not add production instrumentation everywhere merely to chase two outliers. If the gap does not reproduce under controlled repetitions, record it as non-reproducible/transient and stop.
