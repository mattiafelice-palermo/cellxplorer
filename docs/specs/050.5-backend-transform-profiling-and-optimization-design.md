# Spec 050.5: backend transform profiling and optimization design

Status: **Implementation-ready profiling child**  
Parent: [`050-runtime-performance-optimization.md`](050-runtime-performance-optimization.md)  
Branch: `feature/runtime-performance-optimization`  
Origin: user-supplied installed-app 050.4 profile on 2026-08-21 and explicit user decision to let the implementer perform the next profiling activities locally.

## Goal

Turn the 050.4 end-to-end evidence into a precise backend optimization design by profiling the remaining expensive Time/Capacity scientific stages in enough detail to determine what work is actually avoidable.

This child is still a **measurement/design child**, not the optimization itself. It may add bounded profiler-only timing counters, benchmark scripts and focused tests, but it must not introduce a production derived-data cache, precompute layer, multiresolution representation, new scientific algorithm, Plotly rewrite or derivative optimization before the evidence identifies the correct boundary.

The child must answer these questions:

1. Why does the normal Voltage/Current Time/Capacity path spend most remaining time in the combined `continuous_time_phase_capacity` stage?
2. Which sub-operations inside that stage are required for each interactive view/x-axis, and which are currently performed even when the selected view does not consume them?
3. Which expensive derived quantities are invariant for a prepared Cell/source chain and therefore plausible candidates for safe reuse rather than recomputation on every range request?
4. For broad/multi-Cell interactive views, is the best next step reusable derived-row preparation, a scientifically safe overview representation, or another measured design?
5. Why does dQ/dV scale separately to multi-second backend work and hundreds of Plotly traces, and should that become a separate optimization child?
6. Are the occasional large HTTP-minus-backend gaps seen in the user's profile reproducible, or transient/non-systematic?
7. What does a true persisted analysis-result-cache HTTP hit cost when React Query memory is deliberately bypassed?

The child must end with an evidence-backed recommendation for the next implementation child or children. It must not guess the implementation first and then benchmark it.

## Locked decisions

1. **Profiling/design only.** Do not implement the eventual optimization in this child.
2. **No scientific change.** Time, cycle mapping, phase meaning, capacity reconstruction, derivative mathematics, protocol masking, provenance, units, hidden-data semantics and exports remain unchanged.
3. Scientific calculations remain backend-owned.
4. Complete selected-cycle rows still feed any calculation whose result depends on those rows; do not pre-downsample scientific inputs merely because display output is bounded.
5. Split the combined hotspot before choosing a solution; do not assume `continuous_time_phase_capacity` is one cost.
6. Audit actual downstream dependencies; do not assume every transform is required for every view.
7. Any proposed reusable/prepared quantity must have explicit dependency, invalidation and version ownership before a later implementation can use it.
8. Do not add a persistent derived cache, multiresolution representation, derivative cache, Plotly redesign or general RAM/browser cache in 050.5.
9. Keep dQ/dV diagnosis separate from normal Voltage/Current diagnosis.
10. `CALC_VERSION`, parser identity, canonical/raw-layout/result-schema versions and SQLite schema remain unchanged for profiler-only work.
11. Profiler overhead is bounded and opt-in/test-only; ordinary requests must not permanently pay for fine-grained diagnostics.
12. No external telemetry.
13. Preserve the existing 050.4 installed-app profiling controls.
14. Do not implement proto-child 050.P1 or cross-family work.
15. Do not modify, reset or discard unrelated branch work.

### Dependency audit

The audit follows current consumers rather than inferred view semantics:

| Derived quantity | Actual consumers in the current pipeline | Avoidable in compact Voltage/Current time view? |
| --- | --- | --- |

| Source provenance from `source_columns()` | `source_cycle`, `source_position`, `source_filename`, and `source_hash` response fields; source descriptors are also built from the ordered source chain. | No for the current response contract; it is small relative to capacity reconstruction. |

This confirms that normal compact Voltage/Current time requests currently compute phase capacity,
specific capacity, and areal capacity even when their values are not emitted or used as the display
x-axis. The future optimization may avoid that work only after preserving full-resolution raw and
scientific semantics and separately handling full export, derivative, protocol, and axis changes.
The profiler's `consumed_by` labels describe requested display/response consumers; eager internal
construction of an unrequested specific or areal vector is intentionally not counted as a view
consumer, which is why the normal time-row phase-capacity entry can have an empty consumer list.

The dependency key for a future prepared representation must include the ordered source-chain
hashes and positions, per-source parser identities, canonical/raw-layout identity, calculation
version, and the relevant Cell metadata revision. The expected 050.5 design footprint for the
normal reusable arrays is on the order of 5–15 MB per 71k-row Cell once typed arrays, provenance,
and cache/container overhead are included; this is an engineering estimate, not a measured
allocation. The representation should store regenerable derived arrays, not another canonical
raw-data copy, and must retain exact full-resolution rows for exports.
