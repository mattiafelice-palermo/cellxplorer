**Status:** Active implementation plan

## Goal

Make supported BioLogic GCPL-family `.mpr` cycling files analysis-capable when the file does not expose an independently decoded full-cycle field, by reconstructing **source-local logical cycle numbers** from the already decoded protocol and execution structure.

The motivating failure is the repeating/mixed-direction EGG file from the Spec 051 review. Its MPR binary records now decode correctly, but header inspection still marks it metadata-only because the current adapter permits only an explicit full-cycle field or the narrow non-repeating single-direction `cycle = 1` fallback.

After this child, a normal repeated charge/discharge GCPL test must not remain metadata-only merely because a dedicated full-cycle column is absent, provided CellXplorer can reconstruct cycle boundaries deterministically from the supported GCPL settings and observed execution sequence.

This is a **BioLogic adapter change**, not a generic scientific-calculation change. Existing `calc.py`, `step_blocks.py`, stitching, caches, and analysis families must continue consuming the canonical `cycle` column without BioLogic-specific branches.

## User decision — locked for this child

The previous Parent 041 rule said that, without an explicit verified full-cycle field or independently validated half-cycle formula, general mixed/repeating BioLogic runs must fail closed.

The user has now explicitly changed that product decision:

> If a supported BioLogic cycling file has no full-cycle field, CellXplorer should reconstruct the cycles from the cycling protocol/execution structure instead of leaving the file metadata-only, whenever that reconstruction is deterministic.

This child therefore **supersedes only the old “no full-cycle field => metadata-only” decision**. It does not authorize guessing ambiguous binary fields, weakening capacity validation, or inventing cycle boundaries for arbitrary pulse/branching protocols.

## Current implementation anchors

### Header candidate gate

`backend/app/services/biologic_gcpl.py::_gcpl_metadata_from_document(...)` currently calls `_single_direction_protocol_direction(...)` and sets `canonical_cycling_pending` only for that narrow candidate. Repeating/mixed sources are marked metadata-only before full execution validation.

### Full parse cycle gate

`map_gcpl_to_canonical(...)` currently validates `raw_half_cycle_index` with `_validate_supported_half_cycle(...)`, rejects any non-zero half-cycle progression, accepts an explicit `raw_cycle_index` when present, and otherwise allows `_cycle_column(...)` to emit cycle 1 only after `_single_direction_cycle_is_safe(...)` succeeds.

### Existing evidence already available

The adapter already decodes/derives the information needed to reconstruct normal cycling safely: declared settings sequences, normalized `Ns`, valid `goto Ns` / repeat-loop structure, packed control mode, signed current direction, executed-step boundaries, canonical block direction/status, elapsed time, and capacity counters.

Cycle reconstruction belongs in `biologic_gcpl.py`; do not add a second parser or a downstream reconstruction layer.

## Cycle-identity priority

Use the following order. A stronger source identity always wins.

### 1. Explicit full-cycle field

If independently decoded `raw_cycle_index` is present, retain current validation and mapping unchanged. Provenance must identify the explicit source cycle field.

### 2. Protocol-backed repeated-cycle reconstruction — new primary fallback

When no explicit cycle field exists, reconstruct cycles from a **validated declared GCPL loop plus observed execution** when all conditions below are satisfied.

A cycle boundary is not “every direction change.” It is the start of the next independently validated iteration of the declared cycling loop.

### 2a. Execution-evidenced loop fallback for sources without usable loop fields

Some supported GCPL sources, including the motivating EGG family, execute a stable
charge/discharge loop while their decoded settings contain no usable `goto Ns` / repeat
declaration. For this bounded source-local case, the adapter may use the observed execution as
the loop declaration only when every condition below holds:

- the full GCPL settings are decoded and contain a contiguous observed body of declared sequence
  IDs from `loop_start_step` through `control_step`, with no usable declared loop declaration;
- acquisition has at most one unique backward `Ns` edge, and that edge is exactly
  `control_step -> loop_start_step` with `0 < loop_start_step < control_step`;
- the first observed row in the loop body is at `loop_start_step` (apart from a preceding neutral
  Rest or verified zero-current Control preamble), every forward transition is to the same or
  next body step, and the execution never leaves the body or takes a second backward/restart edge;
- the settings body has independently resolved charge and discharge sequences, neutral controls
  are genuinely zero-current, and every decoded row agrees with its declared direction;
- every completed iteration contains actual positive-current charge and negative-current
  discharge execution; a final valid forward prefix may be retained as an interrupted cycle;
- no active preconditioning or other active block occurs outside the observed body, and the
  existing capacity-boundary/error/voltage checks still pass.

This fallback is an execution-evidenced loop rule, not a generic restart heuristic. A single
direction repeat, multiple backward edges, a skipped/branching step, an unresolved control, or a
non-cycling restart remains metadata-only with a precise reason.

### 3. Non-repeating one-cycle reconstruction

If there is no declared repeat loop, a source may still be represented as source-local cycle 1 when the complete execution is one non-repeating cycling episode:

- charge-only plus neutral rests/setup;
- discharge-only plus neutral rests/setup;
- one charge-side phase and one discharge-side phase, in either order, with neutral rests/control between them;
- multiple executed blocks in the same active direction are allowed and remain within the same source-local cycle.

If the active direction returns to the initial direction after an opposite-direction phase, the execution is repeating and must use the repeated-cycle reconstruction path rather than silently remaining cycle 1.

### 4. Ambiguous structure

If none of the above establish deterministic logical cycles, remain metadata-only with a precise reason. Do not fall back to “pair every two active blocks,” `floor(half_cycle/2)`, record-count heuristics, timestamps, or capacity resets.

## Protocol-backed reconstruction contract

### Supported loop shape

Initial implementation must support one unambiguous top-level GCPL cycling loop.

Requirements:

- exactly one effective loop declaration is used for cycle reconstruction;
- `loop_start_step` and the loop control step are valid declared sequence IDs;
- the loop start precedes the control step;
- the loop body contains at least one independently resolved charge sequence and at least one independently resolved discharge sequence;
- neutral Rest / verified zero-current Control sequences may occur anywhere in the loop body;
- there is no nested, overlapping, forward, or otherwise unresolved second loop affecting the same execution;
- unresolved C-rate direction/control semantics remain fail-closed.

A single-direction repeated loop is **not** automatically a sequence of full battery cycles. Leave it metadata-only unless an explicit cycle field exists or a later reviewed rule defines its semantics.

### Observed execution must match the declared loop

After executed blocks are identified, validate normalized `step_index` / `Ns` progression. For a
declared loop, the backward edge must match its declared control/start pair. For the bounded
execution-evidenced fallback, the single observed edge establishes that pair under the conditions
above:

- ordinary forward progression within an iteration must stay inside the declared loop structure;
- a backward `Ns`/`step_index` transition is accepted as a cycle wrap only when it matches the
  declared loop edge, or the one execution-evidenced control/start edge defined above;
- any other backward transition/restart is ambiguous and fails reconstruction;
- a valid loop wrap increments source-local cycle by exactly one;
- the first observed loop iteration is cycle 1;
- cycle numbers are dense positive integers `1..N` in acquisition order.

Do not derive observed cycle count solely from the declared repeat count. The record sequence is authoritative for how many iterations were actually acquired; settings are structural evidence and a consistency constraint only where semantics are already established.

### Direction proof per completed iteration

Every completed reconstructed loop iteration must contain actual decoded execution consistent with the declared cycling meaning:

- at least one positive-current charge block;
- at least one negative-current discharge block;
- no executed block whose decoded direction contradicts its declared sequence semantics;
- no active block with unresolved direction.

Multiple charge steps, multiple discharge steps, existing supported CCCV structure, and rests are all allowed inside one cycle and must not create extra cycles merely because there are several executed steps.

### Neutral preamble

A neutral preamble before the first cycling-loop active block may be attached to cycle 1 only when it is genuinely non-transferring: Rest or verified zero-current Control, current within existing neutral tolerance, and no capacity transfer under existing safety rules.

An active charge/discharge preconditioning block outside the reconstructed loop is not silently absorbed into cycle 1. That formation/preconditioning case remains metadata-only unless an explicit cycle field establishes its identity.

### Interrupted final cycle

Accept a partial final cycle when all completed prior iterations satisfy the loop contract, the tail is a valid prefix of the next declared iteration, and no invalid `Ns` regression or contradictory direction occurs. Assign the partial tail the current cycle number; do not fabricate the missing opposite phase.

## Refactor mapping order — important

The current mapper attempts to obtain `cycle` before fully constructing executed-block ranges/directions/statuses. Repeated-cycle reconstruction needs the opposite ownership order.

Refactor `map_gcpl_to_canonical(...)` conceptually to:

```text
validate/decode record columns
-> validate settings/observed Ns identity
-> derive executed-step boundaries without needing reconstructed cycle
-> classify block direction/status
-> reconstruct/validate cycle identity
-> populate row-level cycle values
-> build capacity columns and canonical DataFrame
-> canonical_cycling.validate_raw_timeseries(...)
```

An explicit source cycle field may still participate in boundary validation when present, but the no-explicit-cycle path must not require a cycle array before reconstruction can run. Do not create circular logic where cycle boundaries define steps while steps simultaneously define inferred cycles.

## Half-cycle field policy — changed

`raw_half_cycle_index` remains decoded source evidence, but this child must **not** use an unverified arithmetic formula on it to create full cycles.

For the new reconstruction path:

- require finite integer non-negative values;
- do not reject a source solely because the half-cycle counter progresses above zero;
- do not use `floor(x/2)`, parity, starting value, or reset behavior to assign canonical cycles;
- do not use half-cycle changes as the sole executed-step or cycle boundary signal;
- retain source values in diagnostics/provenance where currently available.

If implementation independently establishes a useful relationship on the private source, it may be documented as diagnostic evidence only unless a reviewed rule explicitly promotes it to cycle semantics.

## Header metadata and capability behavior

Replace the header-only “single-direction candidate or metadata-only” decision with a bounded **cycle reconstruction candidate** decision.

Header inspection remains record-decode-free. It may mark canonical cycling as pending when settings alone prove:

- the existing non-repeating one-cycle/single-direction shape; or
- a simple mixed-direction top-level loop satisfying the declared-protocol conditions above.

For a candidate, `metadata_only` must be false so normal full parse can verify records, `canonical_cycling_pending` must be true, and metadata must state cycle identity is pending execution verification.

After successful full parse, provenance/capability metadata must distinguish the cycle source, conceptually equivalent to `explicit_full_cycle`, `protocol_loop_reconstruction`, or `non_repeating_cycle_1`, using existing naming conventions.

If full validation fails, preserve metadata-only behavior with a useful reconstruction-specific reason rather than the stale generic “full-cycle field missing” message.

## Parser identity and reinspection

This child changes which sources become canonical and can change the emitted `cycle` column. Therefore:

- bump `BIOLOGIC_GCPL_ADAPTER_REVISION` from `gcpl9` to the next revision (`gcpl10` unless branch state changed first);
- keep `MPR_READER_REVISION = 2` unless binary decoding itself changes independently;
- use existing parser-version upgrade/reinspection machinery so prior `gcpl9` metadata-only sources are reconsidered;
- do **not** bump global `CALC_VERSION`; downstream scientific formulas are unchanged.

Existing canonical single-direction output must remain numerically/structurally identical after reparse except parser/provenance identity fields.

## Existing scientific semantics are unchanged

Do not weaken or redesign reviewed Spec 051/041 rules merely to obtain cycles. Keep the ID-211 / ID-7 capacity-direction and boundary checks, narrow EGG counter-origin reset, positive-charge current sign, primary-voltage/Ewe/Ece semantics, unsupported potentiostatic cases, canonical status strings, and time semantics unchanged.

Do not add BioLogic-specific branches to `calc.py`, `step_blocks.py`, analysis workers, or frontend scientific logic.

- normal repeated charge/discharge GCPL MPR files no longer require an explicit full-cycle field to become canonical;

- explicit cycle fields still take precedence;
