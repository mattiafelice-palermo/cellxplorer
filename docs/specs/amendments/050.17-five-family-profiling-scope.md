# Amendment — Spec 050.17: profile the non-Time/Capacity analysis families only

Date: 2026-08-23  
Status: **Normative user-directed amendment**  
Applies to: [`../050.17-analysis-family-performance-profiling-and-prioritization.md`](../050.17-analysis-family-performance-profiling-and-prioritization.md)

## User clarification

The user clarified during independent review that Spec 050.17 is **not intended to re-benchmark or re-prioritize Time/Capacity**. Time/Capacity has already been the subject of the dedicated 050.4–050.15 profiling and optimization sequence and should now serve only as historical/reference context.

The purpose of 050.17 is to obtain detailed, comparable profiling for the **other five user-facing Analysis families** before selecting further optimization work:

1. Cycles;
2. Steps;
3. DCIR;
4. Chargeability;
5. Rate Capability.

## Normative changes to 050.17

This amendment overrides any 050.17 wording that requires a fresh six-family matrix, fresh Time/Capacity one-/multi-Cell benchmark, or inclusion of Time/Capacity in the optimization-priority ranking.

### Required profiling set

Mandatory current-route profiling, exact-hit controls, attribution, scaling evidence and prioritization apply to:

- Cycles;
- Steps;
- DCIR;
- Chargeability;
- Rate Capability.

Time/Capacity is **excluded from the mandatory 050.17 benchmark matrix and ranking**.

### Time/Capacity handling

- Do **not** rerun Time/Capacity merely to satisfy 050.17.
- Do **not** change Time/Capacity production code, worker behavior, compact/standard request behavior, adaptive refinement, downsampling, cache identity, or frontend profiling controls in this child.
- Existing accepted 050.4–050.15 measurements may be cited as historical/reference context when useful.
- If the cross-family profiler continues to support Time/Capacity as an optional developer control, it must be disabled by default for the 050.17 final matrix and clearly labelled **reference only — not part of prioritization**.
- A Time/Capacity row must not affect priority bands, recommendation ordering, or the choice of the next optimization child.

### Acceptance criteria adjustment

Where the original child says “all six families”, read it as **all five non-Time/Capacity families listed above**.

The mandatory Rate Capability deep decomposition remains unchanged. The common timing/reconciliation rules, exact-hit controls, scientific/order/provenance parity, profiler-overhead requirement, structured JSON output, no-optimization rule, no migration/`CALC_VERSION` change, and canonical preflight requirement also remain unchanged.

## Effect on the implementation already handed off

The implementer’s fresh Time/Capacity measurements in commit `22b8012ea8b15e6769086a5a988fd70654eeb5a4` are extra evidence, not an acceptance requirement. They must not be used to rank future work. No Time/Capacity rerun is required during the review-fix tranche.

The implementer should update the final 050.17 report/profiler defaults so the authoritative result and priority output cover only the five in-scope families, while preserving optional Time/Capacity support only if it remains clearly non-authoritative and does not complicate the profiler.
