# Amendment — Spec 050.8 progressive rendering stability

Status: Normative user-directed amendment

Applies to: `docs/specs/050.8-progressive-time-capacity-series-streaming.md`

Decision date: 2026-08-22

## Reason

Hands-on use of the initial 050.8 implementation showed that one-by-one delivery can still feel choppy when every newly arrived scientific series causes the plot axes/frame to rescale. The same hands-on review also found that the older whole-plot translucent placeholder transition is no longer useful now that replacement data arrives progressively and quickly.

This amendment changes presentation behavior only. It does not change scientific calculations, cache identity, stream framing, canonical order, complete-result ownership, saved/portable behavior, or the prohibition on intentionally delayed/batched delivery.

## Locked decisions

### 1. Stable progressive frame

For the same Time/Capacity quantity/display semantics, later progressive scientific-series arrivals must not repeatedly reframe the figure.

- Manual user zoom/ranges take precedence and must survive later arrivals.
- When a scientifically compatible previous complete plot exists, reuse the applicable existing frame while the new request starts and through partial rendering where that does not conflict with changed X semantics.
- Where a changed request requires a new data-driven frame, establish that frame at the first current partial result and then keep it fixed for later partial arrivals.
- Y-axis ranges and stacked current-axis ranges must not expand/contract per arriving series.
- X-axis/frame geometry must likewise not jump per arriving series. A changed X semantic or request extent may establish a new frame once, but later partial traces must not keep changing it.
- The terminal complete result may perform one authoritative reconciliation/autoscale if the full result requires a broader extent.
- Do not predict unseen future extents and do not run a preliminary full scientific pass merely to compute axes.

The objective is that progressive delivery changes the plotted **data**, not the surrounding plot frame, until terminal reconciliation.

### 2. Remove the whole-plot translucent previous-result transition

The previous compatible complete plot must remain at normal opacity while the new request is starting.

- Do not dim the entire retained plot merely because the replacement query is fetching.
- `start` does not change plot opacity.
- The first current `series` event still replaces previous-generation data rather than merging old and new generations.
- Complete-only actions remain governed by current request identity exactly as in the base 050.8 spec; keeping the old plot fully readable does not make it exportable as the pending result.

This supersedes any 050.1/050.8 presentation behavior that intentionally fades the entire retained plot during a compatible Time/Capacity transition.

### 3. Trace-local smoothing is permitted, but delivery may not be delayed

The base spec's prohibition on animation is narrowed as follows:

- general Plotly animation, whole-figure fading, skeleton animation, and animated axis/layout transitions remain out of scope;
- a very short opacity fade applied only to the newly arriving logical scientific series is permitted if it is technically safe with the selected Plotly ownership model;
- such a fade must start immediately when the series becomes renderable, be no longer than 200 ms, and introduce no intentional wait before rendering;
- it must not coalesce/batch multiple completed series, trigger a component remount/newPlot, change final series opacity/style, or materially increase per-arrival/final Plotly cost;
- if trace-local fading cannot be implemented without those regressions, immediate trace appearance is preferred. Stable frame behavior remains mandatory.

Accordingly, the original `Do not add animation` and `add an animation delay` language continues to prohibit delayed/general animation, but does not prohibit this bounded trace-local opacity refinement.

## Acceptance additions

- A later series with a wider Y extent does not change the partial plot's Y range/frame established for the current progressive request.
- Stacked `y2`/`y3` ranges and margins likewise remain stable across later partial arrivals.
- Manual zoom survives all later arrivals and terminal reconciliation unless the user explicitly resets it.
- The previous compatible plot is never globally dimmed while waiting for the first current series.
- If trace-local fade is used, it is ≤200 ms, delay-free, does not batch arrivals, and does not alter final figure equality.
- Final complete scientific/visual state remains identical to the ordinary complete-result path.
