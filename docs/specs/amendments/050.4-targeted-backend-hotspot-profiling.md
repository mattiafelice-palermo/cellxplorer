## Purpose

The installed-app 050.4 recording supplied 35 completed Time/Capacity interactions and is sufficient to rule out several speculative directions, but it also exposes the next profiling question more precisely. Before a 050.5 optimization is authored, the implementer must use the repository and runnable backend/test environment to decompose the dominant backend stages and return measured evidence to the reviewer.

This amendment is **profiling/investigation only**. Do not implement the optimization discovered by the profiling. Do not begin 050.5 or 050.P1.

The indexed reader is working as intended. For one Cell, the profile read 3/20 groups for 1-20, 11/20 for 1-150, and 20/20 for All. On the one-Cell normal path, selected rows entering transforms increased from 9,423 (1-20) to 42,563 (1-150) to 79,259 (All), while the interactive response stayed close to 4,000 points.

The currently aggregated `continuous_time_phase_capacity` stage increased from about 53 ms to 198 ms to 418 ms across those three one-Cell ranges. For five Cells / All it was about 1.98 s; for six Cells / All it was about 2.62 s. This makes the transform stage, not Parquet I/O, the leading normal-view candidate.

Warm React Query reuse is already fast: 16 memory-hit records had a median total interaction of about 34 ms. Do not add a general RAM cache/prefetch optimization merely to improve exact-repeat interactions.

Derivative work is distinct. One-Cell dQ/dV All took about 3.62 s total, with about 3.01 s backend, about 2.30 s inside the derivative stage, about 388 ms Plotly, and 610 Plotly traces. Treat derivative cost as a separate hotspot from the normal Voltage/Current path.

Two five-Cell narrow misses showed a large HTTP-minus-backend gap (~0.8 s), but a later five-Cell single-cycle miss did not reproduce it. Treat this as an anomaly to probe, not as evidence of a transport redesign.

The local recording did **not** capture a true persisted analysis-result HTTP cache hit; its warm examples were React Query memory hits.

## Required profiling activities

### A. Split `continuous_time_phase_capacity` into measured sub-stages

Inspect the current `compute_time_capacity()` implementation and instrument the existing profiling-only diagnostics so the aggregate stage can be decomposed without changing ordinary responses.

At minimum measure separately, using grep-able current anchors rather than guessed names:

- `_continuous_time(raw)`;
- `source_columns(raw, files)` and source-boundary index construction;
- `_phase_from_raw(raw)`;
- `_phase_capacity(raw, phases)`;
- assignments/copies needed to attach the resulting derived columns if they are materially measurable.

If inspection shows another operation inside the current aggregate stage is significant, add a narrowly named sub-stage for it. Do not create dozens of micro-timers whose overhead obscures the result.

Run the stage breakdown on representative row counts/ranges comparable to the local evidence: narrow (~1-20), broad (~1-150), and All. Use the approved real/golden long-source fixture where possible. Run enough repetitions to report a median and range; use at least one warm-up and at least five measured repetitions unless the existing profiler convention establishes a stronger pattern.

### B. Audit which derived transforms each view actually consumes

Code-read and instrument as necessary to answer, for each current interactive shape:

1. `voltage_current` with `x_axis=time`;
2. `voltage_current` with `x_axis=capacity_mah` (or the exact current capacity-axis token);
3. `dqdv`;
4. `dvdq` if supported by the same backend path.

For each case, report which of continuous time, phase classification, phase capacity, derivative, display-coordinate construction and downsampling are scientifically required by the returned payload versus merely executed because the pipeline is shared.

This is a dependency audit, not permission to skip calculations yet. Do not change output or scientific semantics in this amendment.

### C. Drill into derivative cost separately

For dQ/dV (and dV/dQ if the same implementation owns it), profile the current `_derivative_curve` path on approximately 1-3, 1-20 and All cycles.

Report at least:

- rows entering the derivative stage;
- number of cycle/phase groups processed by the derivative implementation;
- median derivative time;
- returned points;
- resulting trace count where the backend can determine it or where existing deterministic frontend logic makes it derivable without a browser;
- the dominant internal operation/loop after code inspection and profiling.

If one internal operation clearly dominates, add one or two profiling-only timers around it. Do not optimize it yet.

### D. Exercise the persisted analysis-result cache path automatically

Use the existing route/service test or a small profiling harness to issue the same compact/standard Time/Capacity scientific request twice such that the first request is a miss and the second is a **persisted analysis-result cache hit**, not React Query memory reuse.

Record/cache-assert:

- `result_cache` miss then hit;
- backend total/serialization timing where truthfully available;
- returned byte size;
- scientific payload equality ignoring profiling diagnostics;
- that the hit does not rerun scientific transforms.

No browser is required for this activity.

### E. Probe the unexplained narrow multi-Cell HTTP gap

Use a repeatable local route/client harness around a representative five- or six-Cell narrow request if the available fixture/data permits it. Run multiple repetitions and compare client-observed request duration with backend-reported total.

Goal: determine whether the ~0.8 s gaps in two user records are reproducible backend/ASGI serialization/response-copy overhead, client JSON parsing/transfer overhead, or simply transient noise.

Do not invent a transport optimization if the gap is not reproducible. Report `not reproduced` if appropriate.

### F. Return a decision-quality report, not optimization code

The implementer handoff must include a compact table with at least:

| Scenario | Rows | Relevant sub-stage timings | Cache state | Median/range | Conclusion |
| --- | ---: | --- | --- | --- | --- |

and answer these questions explicitly:

1. What operation inside `continuous_time_phase_capacity` dominates normal broad/multi-Cell requests?
2. Which of those operations are invariant/reusable across range changes, based on current scientific semantics?
3. Is the normal Time-axis Voltage/Current view computing any expensive derived quantity it does not consume?
4. Is a prepared exact derived-data layer technically plausible without changing scientific meaning/provenance, or would the correct next design instead be a broad-view multiresolution representation?
5. What specifically dominates dQ/dV, and should that remain a separate later child?
6. Is the persisted result-cache hit path fast and scientifically identical?
7. Was the narrow multi-Cell HTTP/backend gap reproduced?

The reviewer will use this evidence to author the next numeric child or close the optimization workstream. The implementer must not choose and implement that child itself.
