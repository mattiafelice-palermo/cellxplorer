# Spec 050.4 amendment — installed-app profiling controls

Status: **Implementation-ready amendment**  
Governing child: [`../050.4-end-to-end-time-capacity-profiling-and-decision-gate.md`](../050.4-end-to-end-time-capacity-profiling-and-decision-gate.md)  
Branch: `feature/runtime-performance-optimization`  
Decision date: 2026-08-21

## User decision

After 050.4 became review-clean, Parent 050 was blocked because the required local end-to-end profile could only be collected through browser/DevTools commands. The user explicitly rejected that evidence-collection UX and requested **two in-app controls inside the existing Debug/Diagnostics surface: start recording and stop recording**.

This file is a normative amendment to 050.4. It changes only how the already-implemented local profiler is controlled and exported. All existing scientific, cache, timing, privacy, bounded-retention, and no-speculative-optimization requirements remain locked.

## Goal

Allow the user to collect the 050.4 Time/Capacity profile from the normal installed CellXplorer application without browser DevTools, console commands, or manual JSON copying.

## Current anchors

The implementer must inspect the current branch before editing. At amendment time:

- `frontend/src/components/QuickSettingsMenu.tsx` exposes the existing **Debug** item through `onOpenDebug`.
- `frontend/src/components/DiagnosticsModal.tsx` is the existing Debug/Diagnostics surface and already owns local diagnostic export behavior through `saveDownload`.
- `frontend/src/features/analyses/editor/performance/timeCapacityPerformanceProfile.ts` owns the existing singleton profiler and its `enable()`, `disable()`, `isEnabled()`, `reset()`, `records()`, and `exportJson()` behavior.
- The existing profiler remains disabled by default, local-only, bounded, and non-persistent.

Do not create a new top-level settings page or expose profiling in the normal analysis controls.

## Locked target behavior

1. Add a **Performance** area inside the existing Debug/Diagnostics modal. A dedicated `Performance` tab is preferred because the current modal already uses Health / Resources / Logs tabs.
2. Inside that area, provide a compact **Time/Capacity profiling** control with exactly the two primary actions the user requested:
   - **Start recording**
   - **Stop recording**
3. **Start recording** must:
   - clear the previous capture with the existing profiler reset behavior;
   - enable profiling;
   - update the Debug UI to show that recording is active;
   - not navigate away from the current analysis or change scientific/editor state.
4. Closing the Debug/Diagnostics modal **must not stop recording**. The user must be able to start recording, close the modal, exercise normal Time/Capacity interactions, reopen Debug, and stop recording.
5. **Stop recording** must:
   - disable profiling so no further interactions are captured;
   - preserve all completed records already collected;
   - export the captured records immediately as a JSON file using the repository's existing download abstraction (`saveDownload`), so the installed Tauri app works without DevTools;
   - use a clear filename such as `cellxplorer-time-capacity-profile-YYYYMMDD-HHMMSS.json`;
   - show a concise success/error notification including the completed-record count where practical.
6. The Debug UI must expose the current recording state and completed-record count. A small status row such as `Recording · 7 completed interactions` / `Stopped · 7 completed interactions` is sufficient. Do not add a heavyweight dashboard.
7. Starting a new recording intentionally resets the previous in-memory capture. Because Stop exports immediately, no persistent profiling database or history UI is required.
8. If Stop is pressed with zero completed records, handle it explicitly and harmlessly. Either export an empty JSON array with a clear notification or warn that no completed interactions were captured; do not throw or leave profiling enabled accidentally.
9. The existing `window.cellxplorerPerformance.timeCapacity.*` helper may remain for developer use, but the user-facing acceptance path for Parent 050 is now the installed-app Debug controls.
10. Profiling remains opt-in, local, bounded, disabled by default, and absent from external telemetry. No SQLite persistence, analytics, network upload, or background recording is added.
11. No scientific behavior, result identity, request invalidation, parser/canonical/raw-layout/result-schema version, `CALC_VERSION`, or export semantics may change.
12. Do not implement any measured optimization, 050.5, or proto-child 050.P1 as part of this amendment.

## Suggested ownership

Prefer a small UI integration rather than another profiling subsystem:

- `frontend/src/components/DiagnosticsModal.tsx` — Performance tab/card, Start/Stop controls, status/count, JSON export through `saveDownload`.
- `frontend/src/features/analyses/editor/performance/timeCapacityPerformanceProfile.ts` — reuse the existing singleton; add only the smallest UI-facing helper if current ownership makes that cleaner/testable.
- focused frontend tests — verify control semantics without requiring a real Plotly/browser timing run.

Do not move the profiler into `App.tsx` or broadly refactor the Diagnostics modal merely for this control.

## Required tests

Add focused automated coverage for the control semantics. At minimum prove:

1. Start resets an older capture and enables profiling.
2. Recording remains enabled independently of the Debug modal being open or closed.
3. Stop disables profiling but preserves completed records long enough to export them.
4. The exported JSON is exactly the profiler's bounded completed-record payload and does not mutate those records.
5. A second Start begins a fresh capture rather than appending silently to the previous one.
6. Zero-record Stop/export behavior is deterministic and non-throwing.
7. Existing profiler state-machine tests, frontend type/build checks, and canonical preflight remain green.

If component-level browser testing is not part of the repository's current lightweight test stack, extract only the minimal control/helper policy needed for deterministic unit testing rather than introducing Playwright/Selenium.

## Manual acceptance path after implementation

The installed-app workflow should become:

1. Open **Debug**.
2. Open **Performance**.
3. Click **Start recording**.
4. Close Debug and exercise the required Time/Capacity scenario matrix.
5. Reopen **Debug → Performance**.
6. Click **Stop recording**.
7. Send the downloaded JSON file to the reviewer.

No DevTools or console command is part of the required user workflow after this amendment.

## Acceptance criteria

- [ ] Installed CellXplorer exposes Time/Capacity profiling under the existing Debug/Diagnostics surface.
- [ ] Start recording resets and enables the existing profiler.
- [ ] Closing Debug does not stop or reset the capture.
- [ ] Stop recording disables capture and preserves completed records.
- [ ] Stop produces an immediately usable local JSON export through the existing download abstraction.
- [ ] Recording state and completed-record count are visible in the Debug UI.
- [ ] Zero-record and repeated-recording flows are harmless and deterministic.
- [ ] Profiling remains local, bounded, opt-in and disabled by default.
- [ ] No scientific/cache/version/migration semantics change.
- [ ] Focused frontend tests and canonical `python scripts\preflight.py` pass before handoff.
- [ ] Browser/manual timing matrix may remain `NOT RUN` in the implementer environment; the purpose of this amendment is to make that evidence straightforward for the user to collect in the installed app.
- [ ] No 050.5 optimization or 050.P1 implementation is started.
