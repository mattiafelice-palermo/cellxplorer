## Goal

Finish the remaining high-value optimization work for ordinary **Voltage/Current vs Time, consecutive mode** without reopening the scientific architecture.

050.14 already moved the real production backend to approximately **127 ms p50 for 6 Cells Time All, 161 ms for 10 Cells, and 176 ms for 11 Cells**, with four bounded Python workers on eligible broad requests. The remaining work is therefore deliberately narrow:

1. reduce the ~2 MB compact response/IPC representation by removing repeated provenance strings;
2. tune the already-productionized adaptive overview density only where lower density is visually safe;
3. add automatic adaptive zoom refinement so a low-density overview can reveal materially higher local resolution after zoom;
4. perform one bounded 4/6/8-worker tuning pass for 10-11 Cell Time requests and keep a larger pool only if it clearly wins.

The product objective is a fast overview **and** high local detail when zooming. This child does not optimize Capacity and does not redesign Plotly.

## Locked scope and non-goals

1. Scope is only ordinary `view=voltage_current`, `x_axis=time`, `display_mode=consecutive`, `precision=standard`, `compact=true` unless a shared type/helper must be touched for compatibility.
2. **Capacity performance is out of scope.** Do not benchmark or optimize its remaining ~231 ms path here. Preserve it by regression tests only.
3. Do not add Rust/PyO3/Rayon, read threads, cache write-behind, a new JSON serializer, a RAM result cache, progressive streaming, or a new plotting library.
4. Do not change scientific formulas, cycle identity, continuation semantics, voltage-channel semantics, provenance meaning, protocol masking, full-resolution export, or saved-plot scientific identity.
5. Adaptive refinement is presentation-only. It must not create arbitrary persistent analysis-cache entries, mutate the Analysis spec, or become a source for scientific/full-resolution data export.
6. Exact persisted overview cache hits keep the 050.14 direct body-splice fast path. A zoom refinement is never written to the persistent analysis-result cache.
7. Reuse the 050.14 worker service and indexed Time/Capacity path. Do not create a second scientific implementation for refinement.
8. No broad `AnalysisPage.tsx` refactor. Keep ownership in the existing Time/Capacity feature and backend services.

# A. Compact provenance/transport

## A1. Wire shape

For the narrow compact ordinary Time response only, replace the three repeated per-point arrays:

```text
source_position[]
source_filename[]
source_hash[]
```

with exactly:

```ts
sources: Array<{
  position: number;
  filename: string;
  hash: string;
}>

source_index: Array<number | null>
```

Rules:

- `source_index.length === cycle.length` for a non-excluded trace;
- each non-null `source_index[i]` is a zero-based index into `sources`;
- `sources` is ordered by Cell source-chain position and contains each contributing source once;
- `source_cycle[]` remains per-point because it is not constant within one source;
- excluded traces may keep empty arrays/table following the current excluded-trace convention;
- full/non-compact output and non-consecutive/derivative response contracts remain unchanged in this child.

Build this compact form **inside the per-Cell worker/serial shared result function before worker -> owner IPC**, so the smaller representation benefits both IPC and HTTP serialization. Do not first materialize the old filename/hash/position arrays and then compact them.

## A2. Frontend consumption

Add one small helper that resolves `{position, filename, hash}` from `(sources, source_index, pointIndex)`. Use it in ordinary Time segment/hover/export preparation.

Do not eagerly reconstruct three complete duplicated string arrays merely to restore the old in-memory shape. The normal plot path may create the bounded `customdata` it actually needs, but repeated filename/hash arrays must not be recreated unless an existing export helper specifically requires them.

The rendered hover must still show local cycle, short filename and source position exactly as today. Plot/vector/image export must remain unchanged. Full-resolution **data export** continues through its separate exact non-compact request and must not depend on this compact representation.

## A3. Cache compatibility

This is a compact response-schema change, not a scientific change:

- do **not** bump `CALC_VERSION`;
- use the repository's existing Time/Capacity/result response-schema/cache-generation mechanism so a pre-050.15 compact cached body cannot be interpreted as the new shape;
- do not invalidate raw/derived scientific Parquet caches.

## A4. Keep/reject gate

Measure the real S25 6-Cell and 10-Cell Time responses before/after A. Keep the compact provenance production change only if it satisfies both:

- response bytes fall by **>=15%** on at least one broad case without increasing the other; and
- complete backend route does not regress by more than **5 ms or 5%**, whichever is larger.

If the threshold is not met, revert A's production wire change and record the result. Do not invent a second encoding in this child.

# B. Overview density tuning

050.14 currently uses a total budget equivalent to approximately **12 viewport-widths of points across visible Cells**, bounded by floor `800` and the configured `max_points_per_cell`.

Test only these three total-budget multipliers with the same extrema/source-boundary preservation logic:

```text
12  # current production baseline
10
8
```

Keep floor `800` and the configured ceiling unchanged. Do not test additional formulas/floors in this child.

Use 1, 6, 10 and 11 visible Cells at 1200 px for structural measurements; 600 and 2400 px are only required for the selected candidate's final check.

Promotion rule:

- choose the **lowest** multiplier whose output preserves mandatory extrema/source boundaries and passes the manual visual check;
- if browser/manual visual validation cannot be performed, **keep multiplier 12**. Do not promote a lower density from timing evidence alone;
- full/non-compact export ignores this display budget exactly as in 050.14.

# C. Adaptive zoom refinement

## C1. Interaction behavior

For the narrow ordinary Time path:

1. the user zooms/pans and Plotly immediately displays the already-loaded overview data;
2. after **150 ms without another relayout**, start one refinement request for the current viewport;
3. abort/supersede the previous refinement when another zoom/pan, cycle-range/spec identity change, tab change, or unmount occurs;
4. only the response matching the latest overview scientific/data identity **and** latest viewport generation may replace the displayed points;
5. replacement must preserve the current x/y viewport exactly — no autorange/reset/flicker;
6. reset/autorange discards the refinement and returns to the canonical overview result.

Do not show a blocking loader and do not blank the existing plot while refinement is pending. A refinement failure leaves the overview visible; it may use the existing non-blocking error/diagnostic pattern but must not make the plot unusable.

## C2. When refinement is worthwhile

Do not request refinement for every minor relayout.

Trigger only when:

- the visible x span is **<=50%** of the canonical overview x span; and
- the current overview contains at least one visible point for the trace/Cell.

No refinement request is made for style-only relayouts or when the viewport is effectively the full overview.

## C3. Request boundary

Add one dedicated ephemeral endpoint under the existing analysis router, conceptually:

```text
POST /api/analyses/{analysis_id}/time-capacity/refine
```

Use a narrow request model containing:

```ts
spec                       // current unsaved Analysis spec
viewport_x_min
viewport_x_max             // current displayed Time coordinate, same unit as display_x
viewport_width
cycle_start
cycle_end                  // bounded candidate cycle range derived client-side
request_generation         // opaque client identity echoed back
```

The frontend derives `cycle_start/cycle_end` from overview points intersecting the visible x range and expands by **one adjacent global cycle on each available side**. This limits indexed raw reads without requiring a new time-indexed cache.

Backend requirements:

- reuse the existing canonical guard, voltage-channel semantics, owner resolution, stitch plan, indexed reads and 050.14 serial/process Cell implementation;
- preserve the **same display_x coordinate origin as the canonical overview**. A zoom response must not re-zero time at the first requested cycle;
- after ordinary Time coordinates are produced, retain only points inside `[viewport_x_min, viewport_x_max]`, while keeping required boundary/extrema points needed by the existing downsampling contract;
- downsample the visible window to the existing configured `max_points_per_cell` (default 4000) per Cell. Do not add another user setting;
- return the same compact ordinary trace contract selected after Part A plus `request_generation` and the canonical overview/data identity needed to reject stale responses;
- do not read/write `analysis_cache.store_result()` or create persistent keys for arbitrary viewport ranges.

The refinement may use the already-warm persistent process pool for eligible multi-Cell work. It must fall back to the exact serial implementation if the pool is unavailable, as 050.14 does.

## C4. Visible-resolution acceptance

Use one representative broad S25 Time case and zoom to approximately 25%, 10% and 2% of the full x span.

Where raw data density permits it, the 10% viewport must show **at least 3x as many visible samples as simply zooming the overview sample**, capped by raw rows and `max_points_per_cell`. Record actual overview-visible versus refined-visible points so a fast redraw of the same coarse sample cannot pass.

Verify one continuation/source-boundary viewport when available. If not available, synthetic regression coverage must exercise a boundary.

# D. One bounded process-pool tuning pass

Do not redesign multiprocessing. Benchmark only existing architecture with:

```text
4 workers  # production baseline
6 workers
8 workers
```

Only the real/S25 **10-Cell and 11-Cell Time All** workloads are required, three warm repetitions each. Do not benchmark Capacity.

A 6- or 8-worker mode may enter production only if it:

- improves complete backend-route p50 by **>=10% or >=15 ms** versus four workers on **both** 10- and 11-Cell cases;
- preserves exact digest/order/provenance parity;
- does not increase combined parent+worker RSS by more than **50%** relative to the four-worker pool; and
- passes an explicit host gate requiring at least as many logical CPUs as workers plus sufficient measured available memory.

If neither candidate passes every condition, keep four workers unchanged. Never select all logical CPUs automatically. If a larger pool wins, use it only for `>=8` resolved Cells; 3-7 Cell gating remains the 050.14 policy unless measured evidence requires a smaller correction.

## Acceptance criteria

050.15 is complete when:

1. ordinary Time transport uses the locked compact provenance representation **only if A4's measured gate passes**;
2. overview density is either safely lowered to 10/8 after visual acceptance or explicitly remains at 12;
3. zoom refinement is production code, ephemeral, abortable, stale-safe, coordinate-stable and materially increases visible local resolution;
4. arbitrary zoom ranges never populate the persistent analysis-result cache and never affect scientific/full-resolution export;
5. the worker pool remains four workers unless 6/8 satisfies every D promotion condition;
6. ordinary Time scientific/provenance/order parity and saved/export behavior remain intact;
7. Capacity behavior is unchanged and no Capacity optimization was added;
8. focused checks, required frontend build/type checks and exactly one final preflight pass; and
9. the implementation record states what was measured, what was promoted/rejected, commands/durations, and any browser checks not run.
