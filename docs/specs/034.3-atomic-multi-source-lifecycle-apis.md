# 034.3 — Atomic multi-source lifecycle APIs

**Status:** Plan — architecture corrected 2026-07-31  
**Parent:** [034 — Multi-source cell continuations](034-multi-source-cell-continuations.md)  
**Depends on:** 034.1, 034.2  
**Scope:** Backend mutation contracts for initial import, attach, reorder, and detach.  
**Review document:** [034.3 review](reviews/034.3-atomic-multi-source-lifecycle-review.md)

## Architecture correction

The implementation record below describes the first implementation and uses Test-level routes. The
current locked product model is now **one Cell with one ordered source chain**.

`Test` and `TestFile` remain in the database only to avoid a schema redesign:

```text
Cell -> one internal Test row -> ordered TestFile links
```

No user or frontend workflow may select, name, create, or manage multiple Tests. New and ordinary
existing Cells must use exactly one internal Test row. If a legacy Cell unexpectedly has multiple
Tests, preserve all data and fail lifecycle mutation clearly; do not silently normalize or delete
records in this spec.

This section supersedes Test-level wording in the original implementation record.

## Current hazards

- Import and lifecycle code still exposes `test_name`, `test_id`, Test-local ordering, and
  `/api/tests/{test_id}` routes to frontend contracts.
- Test-local operations can represent only part of a Cell chain and make preview/mutation disagree.
- Test-local detach rules protect each container rather than the Cell’s one source chain.
- Source-order mutations must consistently validate, invalidate, and log their complete Cell impact.

## Locked API behavior

### Initial import

`POST /api/imports/cells` accepts one Cell draft with one ordered `sources[]` array:

```json
{
  "cells": [{
    "cell_name": "Cell A",
    "description": null,
    "sources": [{
      "staged_name": "...",
      "source_path": "C:\\...",
      "filename": "a.ndax"
    }, {
      "staged_name": "...",
      "source_path": "C:\\...",
      "filename": "a-continue.ndax"
    }],
    "acknowledged_finding_ids": []
  }]
}
```

- `test_name` is not a user-editable or required request field.
- Keep Cell metadata/override/preset fields at Cell-draft level.
- Preserve compatible one-source requests by normalizing them to one `sources[]` entry.
- Create one Cell, one internal Test row, and one SourceFile/TestFile per ordered source with dense
  positions `0…n-1`, in one transaction.
- Folder and replicate placement apply to the Cell.

### Cell-level lifecycle surface

The canonical mutation surface is Cell-level. Exact route naming may follow current router style,
but the contract must be equivalent to:

```http
POST /api/cells/{cell_id}/sources/impact
POST /api/cells/{cell_id}/sources/continuations
POST /api/cells/{cell_id}/sources/reorder
POST /api/cells/{cell_id}/sources/{file_id}/detach
```

The backend resolves the Cell’s one internal Test row. The frontend does not send or select a Test
ID.

Existing `/api/tests/{test_id}` routes may remain only as compatibility wrappers while callers are
migrated. They must resolve the owning Cell, enforce the one-chain invariant, and must not permit a
second Test to be created or independently managed.

### Attach continuations

- Request contains ordered staged sources plus `acknowledged_finding_ids`.
- Re-run 034.2 inspection server-side immediately before mutation.
- Append to the Cell source chain in submitted order.
- Cell metadata, name, overrides, folder membership, and replicate membership do not change.
- A protocol change between the current tail and new source is a finding, not a new Test.

### Reorder

- Require an exact permutation of every source ID in the Cell chain.
- Reject missing, extra, duplicate, or foreign IDs.
- Re-run findings for the complete proposed Cell order and require current acknowledgements.
- Write dense positions in one transaction.
- There is no per-Test reorder or cross-Test drag distinction.

### Detach

Require:

- source belongs to the stated Cell chain;
- at least one source remains in the Cell;
- an explicit confirmation token/flag from impact preview;
- no deletion of the underlying original file.

Detaching removes only the source’s ordered membership link. An unlinked SourceFile may remain
indexed according to existing lifecycle rules.

### Authoritative proposal and impact

One read-only operation-specific proposal response must drive both review and mutation. It returns:

- Cell identity;
- complete current and proposed source order;
- old and proposed tracked tail;
- compatibility findings and required acknowledgements;
- affected analyses and saved plots;
- whether global cycle numbering changes;
- opaque confirmation data where required.

The mutation must validate exactly the proposal the user reviewed. Do not show a partial
Test-local inspection followed by a different Cell-wide validation.

## Validation and transaction rules

- Resolve and validate every source, hash, path, finding, Cell, internal Test row, folder, and
  replicate plan before the first membership write.
- A source can belong to one Cell chain only.
- Exact duplicate hash in a chain is rejected.
- Recompute source hashes/file stability before attaching/importing.
- Database membership/order changes use one transaction.
- Filesystem cache/artifact deletion happens only after relational commit and remains idempotent.
- Queue parsing for every newly attached source through the existing cache-job mechanism.
- Return the complete updated Cell/source order, tracked source ID, invalidated analysis IDs, and
  queued jobs.

## Invalidation and activity

Use `invalidate_cell_dependents` causes:

- `continuation_attached`
- `source_order_changed`
- `continuation_detached`

Invalidate dependent results/artifacts/thumbnails after commit. Create privacy-safe activity entries
with Cell/source IDs, filenames, hash prefixes or positions, and affected analysis IDs. Do not log
raw data or filesystem paths.

No schema migration should be added.

## Acceptance

- One request creates one Cell with one or more ordered sources and one internal Test row.
- Frontend/API lifecycle contracts require `cell_id`, not user-selected `test_id`.
- No `test_name` is requested from the user.
- A continuation attaches to the Cell chain without changing Cell metadata.
- Reorder is an exact permutation of the whole Cell chain.
- Detach cannot empty the Cell and never deletes the original file.
- Every mutation is all-or-nothing at the relational layer.
- Compatibility is revalidated server-side and conflicts return structured data.
- Dependent analysis state/artifacts are invalidated and mutation is logged.
- Protocol changes never create a second Test.
- Legacy one-file import still works.
