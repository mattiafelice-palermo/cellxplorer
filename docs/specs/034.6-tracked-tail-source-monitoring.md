# 034.6 — Tracked-tail source monitoring

**Status:** Plan — architecture corrected 2026-07-31  
**Parent:** [034 — Multi-source cell continuations](034-multi-source-cell-continuations.md)  
**Depends on:** 034.3  
**Scope:** Scheduled automatic checks inspect only each active Cell’s final ordered source.

## Locked product model

Each Cell has one ordered source chain and one tracked tail: the final source in that chain.
`Test` is an internal compatibility row and does not create another monitoring scope.

## Current behavior

- Manual source checks can inspect all registered sources for selected Cells.
- Scheduled monitoring should inspect only one final source per active Cell.
- The first implementation derives Cell order through Test rows and records Test IDs in job items.
  That storage detail may remain internally, but selection, copy, validation, and tests must describe
  one Cell chain rather than multiple Tests or per-Test tails.

## Locked selection rules

Use explicit scopes:

- `all_ordered_sources`
- `tracked_tails`

| Trigger/operation | Scope |
|---|---|
| scheduled monitor | tracked tails |
| scheduled auto-update | tracked tails |
| retry of scheduled work | same captured tracked tails |
| manual Check sources | all ordered sources |
| manual Check and update | all ordered sources |
| tray action explicitly initiated by user | all ordered sources |
| portable export preflight | all ordered sources |

For each non-empty Cell, tracked tail means the final source in the Cell-level order. A Cell with no
sources contributes no job. Complete Cells remain skipped by the existing default.

## Job compatibility and concurrency

- Capture source IDs, registered hashes, paths, Cell IDs, positions, and physical file signature at
  job start.
- A retry uses the same captured items.
- A later scheduled run uses the then-current Cell order.
- Coalesce only requests with the same immutable contract: source scope, normalized Cell selection,
  include-complete behavior, scan mode, check/update semantics, and relevant stability/retry rules.
- A manual all-source operation must never be represented by or upgrade a scheduled tail-only job.
- Incompatible work must queue/start separately or return a clear already-running response with the
  actual scope.

## Final adoption guard

Immediately before automatic adoption from a `tracked_tails` job, require that:

1. the source remains attached to the captured Cell;
2. it remains the final source in that Cell’s current chain;
3. its current registered hash equals the captured registered hash;
4. the final stable physical signature matches the checked source state.

If any condition fails, skip adoption and report a precise reason: detached, became historical,
registered identity changed, or source changed again. Internal Test ID may be retained for
compatibility diagnostics but is not the scientific role check.

## Performance

Select tails without N+1 queries. A bounded eager-load or SQL subquery is acceptable. The result is
one source per Cell, never one per Test.

## User-visible activity

Use clear Cell-level descriptions:

- “Checking current source for N cells” for scheduled tail scans;
- “Checking all N source files” for explicit integrity scans.

Historical sources retain their last known status; skipping them does not falsely mark them online.
Do not mention Test in user-facing activity.

## Acceptance

- A three-source active Cell contributes one scheduled item: its final source.
- Two active Cells contribute at most two tail items regardless of historical source count.
- No per-Test tail or Test count affects selection.
- Manual check/update includes all Cell sources.
- Complete filtering and explicit `include_complete` remain unchanged.
- Reorder affects subsequent jobs; in-flight jobs stay deterministic.
- Scheduled adoption cannot update a detached, historical, or stale-snapshot source.
- Incompatible manual/scheduled requests do not silently coalesce.
- Activity text and job metadata state the actual scope without Test terminology.
