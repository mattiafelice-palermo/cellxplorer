## 1. Goal

Extend the verified Stable/Beta updater and release machinery to Alpha, then close Parent 053 with a
three-product regression and disposable Windows matrix.

After this child:

- installed Alpha checks, downloads, verifies, and installs only Alpha updates;
- exact Alpha tags can drive a signed draft-verify-publish workflow;
- Alpha GitHub releases are prereleases;
- the manifest-only release-channels branch can safely bootstrap alpha/latest.json once and require
  it thereafter;
- publishing any channel protects every non-target pointer;
- build-only and installed tests prove Stable/Beta behavior did not regress.

This child prepares publication. It must not push a production tag, publish a release, or mutate
the release-channels branch without separate explicit user authorization for that exact operation.

## 2. Current behavior to preserve and generalize

At the authoring baseline:

- src-tauri/src/app_channel.rs accepts Stable exact versions and Beta dotted/legacy compact versions;
- src-tauri/src/app_updates.rs owns standard self-update state and a separate Stable-only
  PendingBetaInstall state;
- scripts/release_tag.py accepts only Stable and Beta tags;
- scripts/release_channel_policy.py requires Beta cores to exceed the latest exact Stable release;
- scripts/release_channels.py expects README.md, stable/latest.json, and beta/latest.json and has a
  first-Beta bootstrap exception;
- scripts/verify_updater_manifest.py validates Stable/Beta versions and installer product names;
- .github/workflows/release.yml resolves only Stable/Beta, protects one “other” pointer, stages a
  signed draft, verifies it, undrafts it, and updates one channel pointer;
- Stable's first-Beta installer commands remain separate from standard self-update state.

Extend these mechanisms. Do not duplicate the updater state machine or create a second release
workflow.

## 3. Locked Alpha updater behavior

Alpha's standard updater uses the endpoint embedded by 053.1:

    https://raw.githubusercontent.com/mattiafelice-palermo/cellxplorer/release-channels/alpha/latest.json

The configured Tauri identifier remains authoritative for the installed channel.

Alpha accepts only exact versions:

    MAJOR.MINOR.PATCH-alpha.N

Rules:

- N is a SemVer numeric identifier with no leading zero unless it is exactly 0;
- no compact alphaNNN legacy spelling;
- no Beta, Stable, rc, arbitrary prerelease, build metadata, or leading v;
- rejected versions must not populate pending-update state;
- check/download/install continues through the shared PendingAppUpdate path;
- Alpha never uses PendingBetaInstall or Stable's Beta discovery/install commands;
- Stable and Beta validators remain byte-for-byte equivalent in accepted behavior.

Add Rust tests for accepted/rejected Alpha versions and crossed-channel manifests.

## 6. Manifest-only release-channels transition

### 6.1 Tree contract

Generalize scripts/release_channels.py to model these states:

**Pre-Alpha bootstrap, only when no published Alpha GitHub release exists**

    README.md
    stable/latest.json
    beta/latest.json

**Post-first-Alpha**

    README.md
    stable/latest.json
    beta/latest.json
    alpha/latest.json

Rules:

- README, Stable, and Beta pointers are always required;
- Alpha is optional only when authoritative published-release metadata proves that no Alpha release
  has ever been published;
- once an Alpha release is published, missing Alpha is an error for every target channel;
- unexpected blobs or directories always fail;
- truncated/malformed tree payloads fail;
- a first Alpha target may create the absent pointer race-safely;
- never infer bootstrap eligibility solely from target_channel=alpha;
- never initialize or recreate the branch from main.

Pass explicit published-Alpha evidence into the validator from the release workflow. Unit tests must
cover forged/missing evidence and the post-publication deletion case.

### 6.2 README preparation

Before an authorized first Alpha release, update the release-channels branch README in a focused
manifest-only commit so it documents Stable, Beta, and Alpha. Do not add source, scripts, or copied
main history.

This operational branch change is not authorized merely by implementing this child. Record it as a
pending release-preparation step unless the user explicitly requests it.

## 7. Three-channel release workflow

Extend .github/workflows/release.yml.

### 7.1 Channel resolution

Manual build-only input choices are exactly:

    stable
    beta
    alpha

Tag resolution must be explicit and fail closed:

| Channel | Product | Overlay | Manifest | Prerelease |
|---|---|---|---|---|
| Stable | CellXplorer | none | stable/latest.json | false |
| Beta | CellXplorer Beta | tauri.beta.conf.json | beta/latest.json | true |
| Alpha | CellXplorer Alpha | tauri.alpha.conf.json | alpha/latest.json | true |

Do not use a final “else Stable” branch for unknown manual input or tag shape.

### 7.2 Pre-publication gates

For Alpha tags:

- require exact publishable tag;
- require tag commit reachable from origin/main;
- require public repository;
- query published releases and require future-Stable core;
- prove the release-channels branch tree is in an allowed bootstrap/post-bootstrap state;
- refuse replacement of a published non-draft release;
- require synchronized version declarations and exact changelog notes;
- require signing secrets;
- reuse trusted exact-SHA main preflight or run the complete no-cache fallback;
- build and verify the Alpha frontend stamp and shared onedir sidecar.

Preserve every existing Stable/Beta gate.

### 7.3 Draft verification and publication

Use the existing pinned Tauri action and one workflow:

- product-specific release name;
- Alpha overlay arguments;
- Alpha prerelease=true;
- signed Alpha NSIS setup executable, matching .sig, and latest.json;
- exact manifest verification using the shared public key;
- no undraft before all verification succeeds;
- no plain binary upload;
- no production publication from manual build-only dispatch.

Alpha must not become GitHub's normal latest release.

### 7.4 Protect all non-target pointers

Replace the single other_path/other_sha model with a bounded map/list of every existing non-target
pointer.

Before draft staging:

- capture the branch ref SHA;
- capture the target pointer SHA when it exists;
- capture each present non-target path and blob SHA;
- require all pointers expected for the proven lifecycle state.

After updating the selected pointer:

- verify branch update used optimistic SHA protection;
- download and byte-compare the selected manifest;
- verify the public raw selected endpoint;
- re-read the complete branch tree;
- prove every captured non-target path still has exactly its prior blob SHA;
- prove no extra file appeared;
- prove the branch README did not change during publication.

For first Alpha publication, Stable and Beta are both protected non-targets. After Alpha exists,
Stable or Beta publication must protect both other channel manifests.

### 7.5 Failure recovery

- Before undraft: fix main and move only the unpublished tag as existing policy allows.
- After undraft but before pointer update: do not replace release assets; repair only the
  manifest-only branch with optimistic protection.
- Never rebuild a published version.
- Never delete or overwrite another channel pointer to recover Alpha.

## 11. Disposable three-product installed/update matrix

Use disposable profile roots/account and signed test artifacts. Record each item RUN or NOT RUN.

### Installation and identity

- [ ] Stable, Beta, and Alpha install side by side.
- [ ] Product names, install folders, uninstall entries, shortcuts, icons, deep links, and autostart
      values are distinct.
- [ ] All three run simultaneously; second launch focuses only its matching product.
- [ ] Alpha uses only .cellxplorer-alpha by default.
- [ ] Alpha contains no Beta bootstrap or cross-product installation flow.

### Same-channel updates

- [ ] Stable N to Stable N+1 updates Stable only.
- [ ] Beta N to Beta N+1 updates Beta only.
- [ ] Alpha N to Alpha N+1 updates Alpha only.
- [ ] Each update preserves its own profile root.
- [ ] Each updater notification/modal uses its own product identity.

### Crossed manifests and installers

- [ ] Stable rejects Beta and Alpha versions.
- [ ] Beta rejects Stable and Alpha versions.
- [ ] Alpha rejects Stable and Beta versions.
- [ ] No updater overwrites another installation directory or registration.
- [ ] Stable's existing explicit first-Beta install remains functional and does not involve Alpha.

### Uninstall isolation

- [ ] Uninstalling each product leaves the other two installed and launchable.
- [ ] Default uninstall preserves that product's data.
- [ ] Explicit destructive Alpha removal deletes only .cellxplorer-alpha.
- [ ] Alpha uninstall never changes .cellxplorer or .cellxplorer-beta.

### Release behavior

- [ ] Stable build/release remains normal-latest eligible.
- [ ] Beta build/release remains a prerelease.
- [ ] Alpha build/release is a prerelease.
- [ ] Build-only dispatch creates no GitHub Release and changes no channel pointer.
- [ ] Simulated/authorized pointer update changes only the selected manifest and protects all others.

Never run destructive uninstall tests against real user data.
