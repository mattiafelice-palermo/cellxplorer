## Goal

Combine only the execution mechanisms that proved useful independently in 050.9/050.10, determine whether their gains actually compose, and choose the **production architecture** for a later implementation child.

This remains a benchmark/decision child. The winner must not quietly become production behavior here; a later 050.12+ child is required.

## Required inputs

Read the accepted 050.9/050.10 implementation and review records first.

050.9 supplies current sequential decomposition plus isolated read-concurrency and whole-Cell Python-thread results, including small-job regressions, I/O contention, CPU and memory.

050.10 supplies isolated sequential-Rust and Rayon results, Python/native boundary cost, cold/warm lifecycle and build feasibility.

Do not repeat losing mechanisms by default. This child is about interaction between survivors.

## Locked decisions

1. **Combine only individually useful mechanisms.** A losing read-thread or Rust experiment does not enter a hybrid merely for completeness.
2. **Preserve attribution.** Compare each measured hybrid with the improvement expected from its isolated parts.
3. **Control nested threading.** Explicitly bound Python/PyArrow/BLAS/Rayon worker counts.
4. **Preserve deterministic order and scientific output.** Completion order never becomes result order.
5. **Exact result-cache hits stay direct** and bypass all worker/native machinery.
6. **No live ORM/session sharing across execution boundaries.**
7. **No scientific algorithm change.**
8. **No whole-Cell RAM cache, speculative prefetch or new persistent cache layout.**
9. **Python processes are optional control only**, never mandatory.
10. **Frontend/Plotly/adaptive zoom remain separate.** Measure their remaining share if evidence exists; do not modify them.

## Composition matrix

Use the representative scenarios shared by 050.9/050.10, especially broad multi-Cell Time/Capacity and the 10-Cell workload when data permit.

### D0 — best isolated control

Carry forward the fastest accepted isolated strategy: sequential Python, bounded Python threads, sequential Rust or Rust/Rayon depending on prior evidence.

### D1 — concurrent reads + sequential Rust

Run only when read concurrency was independently useful in 050.9 and sequential Rust was independently useful in 050.10. Use the smallest useful bounded read count and the one-worker Rust kernel.

### D2 — concurrent reads + bounded Rust/Rayon

Run only when both read concurrency and Rayon were independently useful. Use the smallest worker counts that captured most of each isolated gain; do not automatically combine 4 Python threads with 4 Rayon threads.

### D3 — whole-Cell Python threads + internally parallel Rust

Run only when this is architecturally distinct from D2 and oversubscription can be controlled. Otherwise record `NOT RUN` with the reason instead of manufacturing a redundant row.

## Optional process control

Benchmark persistent Python processes only if all are true:

- 050.9 shows weak thread scaling;
- material Python/GIL-bound CPU work remains;
- 050.10 shows Rust is infeasible, inferior or does not cover that stage;
- potential gain is large enough to justify Windows process/memory complexity.

If justified:

- E1 — persistent 2-process pool;
- E2 — persistent 4-process pool.

Never spawn per plot/Cell. Workers receive compact immutable descriptors and open exact cache data themselves; do not pickle whole DataFrames or pass SQLAlchemy state.

## Workloads

Carry forward only scenarios that discriminate surviving strategies. Include at minimum:

- single-Cell control;
- 3/6-Cell broad Time-axis request;
- **10-Cell All/Time** when representative data permit;
- broad capacity-axis case if still material;
- derivative-heavy case if the Rust kernel targets derivatives;
- narrow/small case to expose dispatch/boundary overhead;
- exact persisted result-cache hit;
- one viewport-like narrow range for later comparison with 050.P4.

Do not make a measured 10-Cell claim by extrapolating six Cells.

## Attribution

For every D/E candidate report:

- baseline wall time;
- relevant isolated component wall times from 050.9/050.10;
- simple expected combined saving if the isolated gains were independent;
- actual combined wall time/saving;
- interaction classification: **additive, sub-additive, neutral or negative**;
- explanation supported by I/O, CPU, memory bandwidth, dispatch and native-thread evidence.

The expected arithmetic is descriptive only; gains need not add linearly.

## Measurements

Record for every executed candidate:

- total backend wall time;
- per-Cell wall time where meaningful;
- thread/process/native worker counts;
- dispatch/queue time;
- Parquet read/decode and structural read counters;
- transform/kernel/derivative time;
- Python/native boundary cost when applicable;
- assembly/serialization time;
- CPU/effective cores;
- peak RSS/temporary allocation estimate where measurable;
- relevant PyArrow/NumPy/BLAS/Rayon settings;
- cold vs warm lifecycle for reusable pools/native extension;
- scientific parity and canonical ordering.

Use at least five comparable warm repetitions where practical; report median plus range/tail and alternate candidate order where cache warming could bias results.

## End-to-end boundary

If an installed-app/browser run is available for the best backend candidate, report separately:

- backend total;
- HTTP/fetch/parse;
- frontend trace/layout preparation;
- Plotly completion;
- total interaction time;
- Plotly trace/point count.

This identifies whether backend execution remains the dominant opportunity. It does not authorize frontend changes.

## Scientific parity

Every candidate preserves the same Cells/sources/cycles/protocols, algorithms/thresholds, existing exact/tolerance rules, finite/non-finite placement where applicable, provenance/continuation mapping, deterministic Cell/series ordering and saved/export/result-cache semantics.

Any speedup that changes accepted science is rejected.

## Required final architecture outcome

Finish with exactly one primary outcome:

- **A — remain sequential Python**: concurrency/native options do not produce material stable net gain.
- **B — bounded Python threads**: read-only or whole-Cell threading captures most useful gain with lowest complexity.
- **C — sequential Rust kernel**: native execution is useful but cross-Cell native parallelism adds little.
- **D — bounded Rust/Rayon**: Rust helps and Rayon adds material stable gain without Python read concurrency.
- **E — hybrid concurrent reads + Rust/Rayon**: both isolated mechanisms help and their composition remains best.
- **F — persistent Python processes**: only under the explicit process gate and only if they beat simpler/native alternatives after startup/IPC/memory.
- **G — backend execution no longer dominant**: transport/frontend/Plotly/adaptive resolution is now the larger user-visible boundary.

For the chosen outcome record recommended bounded worker count(s), measured representative behavior, memory/build/lifecycle consequences, exact later production scope and explicit exclusions.

## Production follow-up rule

050.11 does not implement the winner. Author one focused **050.12+** implementation child after review-clean evidence selects the architecture. That child owns real lifecycle/fallback/packaging/tests rather than carrying all alternatives forward.

## Acceptance criteria

- Only useful isolated mechanisms are combined.
- Every hybrid has attribution back to 050.9/050.10.
- Nested threading/storage contention are measured/controlled.
- Optional processes run only if justified.
- Multi-Cell and small-job behavior are both considered.
- Scientific output/order/provenance remain unchanged.
- One explicit architecture outcome A-G is recorded.
- No production executor/native path, adaptive zoom or Plotly redesign is implemented here.

## Verification

Run focused benchmark/scientific parity tests for involved adapters, golden analysis if production scientific/service code is touched, then:

```text
python scripts\preflight.py
```

Record browser/manual evidence only if actually run.
