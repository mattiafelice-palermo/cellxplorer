**Status:** Active child — implementable  
**Parent:** Spec 052 — Time/Capacity cycle navigation

**Branch:** `feature/time-capacity-cycle-navigation`  
**Reason for child:** explicit post-implementation user acceptance decisions collected after child 052.1. This child is the governing instruction for the next UX refinement round. It supersedes parent/052.1 behavior only where stated below.

## Goal

Make the Time/Capacity cycle navigator feel like direct plot navigation rather than a form wrapped around a plot, while keeping one canonical scientific range and preserving the query/cache/runtime guarantees established by Specs 050, 051.2, 052 and 052.1.

This child adds four related refinements:

1. richer range navigation and history access;
2. live slider-drag feedback without history/autosave/query flooding;
3. better defaults for a brand-new Time/Capacity view;
4. a Time/Capacity Plotly modebar control for the existing canonical grid setting.

No backend scientific calculation, parser, migration, endpoint, or cache-version change is intended.

## Verified current facts that constrain the implementation

At the 052.1 handoff:

- `DEFAULT_TIME_CAPACITY` still stores `cycle_start: 1` and `cycle_end: 3`;
- the default plot style already uses `marker_mode: "none"`, which resolves Time/Capacity primary series to line rendering;
- the default plot style already owns `show_grid: true`;
- `timeCapacityLayout(...)` reads `style.show_grid` for its axes;
- the Time/Capacity Plotly config currently only customizes logo display and legend-position editing;
- the Time/Capacity query identity includes `cycle_start` and `cycle_end` and sends the current `spec` to `/time-capacity`;
- the current cycle-position slider keeps only its thumb value transient during `onChange` and commits the canonical range once in `onChangeEnd`;
- the visible From/To inputs currently read the canonical stored range, so they do not move during a slider drag.

These facts mean live drag preview must be deliberately separated from persisted/history state. Do not obtain dynamic feedback by calling the normal editor `update(...)` path on every pointer movement.

## Locked user decisions

### 1. The slider represents the full current cycle window

Replace the conceptual single-center-thumb presentation with a range-shaped navigator that visually represents the complete current inclusive window over the full available cycle extent.

Example for cycles `189–208` of `720`:

```text
1 ─────────────[════ current 189–208 ════]──────────────────────── 720
```

Requirements:

- the highlighted segment position is proportional to `start..end` within `1..maxAvailableCycle`;
- the segment width represents the current inclusive cycle-window width;
- dragging the segment moves the **whole window** horizontally and preserves its width;
- dragging clamps at the lower and upper bounds without changing width;
- the existing Cycle window size selector remains the owner of resizing the window;
- do not turn the slider into a second arbitrary From/To editor with independently draggable endpoints unless the final implementation keeps window width locked and cannot accidentally resize it;
- the callout geometry/hover anchoring from 052.1 remains unchanged unless a small size adjustment is required to make the range segment usable.

Do not add an `of 720` text status or other extra chrome. The user explicitly rejected that addition.

### 2. Live drag feedback: range boxes and plot follow the drag

While the user is actively dragging the range segment:

- the displayed `From` and `To` values must update immediately to the transient preview range;
- the plot should follow the transient range dynamically rather than waiting until mouse/pointer release;
- the visual movement should feel continuous enough to understand where the window is moving;
- the transient drag must **not** create one history entry, autosave mutation, persisted spec mutation, or canonical editor update for every pointer event.

Use one explicit transient preview range, owned locally by the Time/Capacity frontend path. It may be passed from the navigator to the plot card through an ephemeral callback/prop or equivalent narrow mechanism.

The canonical scientific range remains:

```text
spec.computation.time_capacity.cycle_start
spec.computation.time_capacity.cycle_end
```

and is committed exactly once when the drag ends successfully.

#### Query/runtime constraint for live plot preview

Because the current Time/Capacity query identity includes the range, do **not** issue an uncapped request for every raw pointer event.

The implementation must use a bounded, cancellation-aware preview policy. Acceptable patterns include request coalescing with animation-frame/short throttling plus cancellation of superseded preview work, or an equivalent existing repository pattern. The important contract is:

- immediate local range-box feedback;
- no request-per-pixel/query flood;
- no unbounded concurrent preview requests;
- reuse existing cached range results immediately when present;
- keep the last compatible plot visible while a newer preview result is pending rather than blanking/flashing the plot;
- release commits one canonical range/history step;
- after release, the canonical query identity settles on the same final range instead of triggering a second semantically different state.

Do not move scientific calculations into the browser merely to make dragging look live.

If the callout is closed/Escape is pressed before a completed drag commit, discard the transient preview and restore both displayed From/To values and plot view to the canonical pre-drag range without adding history.

### 3. Slider keyboard navigation uses the directional keys

When the range slider/segment itself has keyboard focus:

- `ArrowLeft` moves the whole current window one cycle earlier;
- `ArrowRight` moves the whole current window one cycle later;
- preserve width and clamp at bounds;
- use the same transient/commit semantics appropriate to the slider control rather than creating a separate range model;
- retain standard focus visibility and Escape behavior.

Do not add extra PageUp/PageDown, Shift+Arrow, Home/End or other keyboard shortcuts in this child unless they are required by the chosen accessible slider primitive. The user only approved the normal directional-key behavior.

### 4. Previous View gets a recent-history dropdown

Keep the existing main Previous View action: normal activation restores the immediately preceding cycle view.

Add a compact dropdown affordance beside it so the user can directly choose a recent historic range.

Requirements:

- preserve the existing session-only bounded history; do not persist history;
- show approximately the last 5–10 distinct historic ranges, newest first;
- range labels should be compact, e.g. `189–208`;
- selecting an older history entry should behave like going back to that point in the history stack: restore that range without pushing the current range as a new history item, and discard the more-recent back-stack entries above the selected point;
- do not create duplicate adjacent history items;
- the main Previous View action and its disabled/null-bound behavior from Spec 052 remain unchanged;
- use compact Mantine split-action/menu geometry consistent with the existing toolbar.

### 5. Ctrl+click gives first/last-window navigation on both arrow buttons

Normal click semantics stay exactly as today:

- `‹` → previous cycle;
- `«` → previous whole window;
- `›` → next cycle;
- `»` → next whole window.

Add Windows `Ctrl+click` semantics:

- Ctrl+click either left button (`‹` or `«`) → move directly to the **first valid window**, preserving current width: `[1, width]` after clamping;
- Ctrl+click either right button (`›` or `»`) → move directly to the **last valid window**, preserving current width: `[max-width+1, max]` after clamping.

Do not change the normal click behavior.

Tooltips must advertise the modifier, for example:

- `‹`: `Previous cycle · Ctrl+click: first window`;
- `«`: `Previous window · Ctrl+click: first window`;
- `›`: `Next cycle · Ctrl+click: last window`;
- `»`: `Next window · Ctrl+click: last window`.

The existing Specific-cycles/null-bound disabling rules continue to apply. Do not invent extreme navigation when no reliable upper bound exists.

### 6. New Time/Capacity views default to the last 20 available cycles

For a genuinely **new/virgin Time/Capacity view**, once a reliable selected maximum is available, initialize the continuous range once as:

```text
end   = maxAvailableCycle
start = max(1, maxAvailableCycle - 19)
```

Examples:

```text
max 200 -> 181–200
max 20  -> 1–20
max 12  -> 1–12
```

Use the existing selected-Cell maximum resolver from Spec 052. Visibility/exclusion state must not change this maximum.

Important safeguards:

- do not overwrite a saved plot's restored range;
- do not overwrite an edited draft/workspace range;
- do not reinitialize every time `maxAvailableCycle` changes or the component rerenders;
- do not overwrite a range the user changed before the maximum finished loading;
- do not initialize while Specific cycles is active;
- initialization is a one-time new-view default, not a continuous "follow latest cycles" mode.

The implementation should establish an explicit/testable virgin-state guard rather than infer "untouched" forever from the numeric value `1–3` alone.

This user decision supersedes the parent Spec 052 instruction that retained `1–3` as the new Time/Capacity default.

### 7. New Time/Capacity views default to line-only rendering

A new/virgin Time/Capacity plot should resolve to **lines without point markers**.

The repository-wide base plot style currently already uses `marker_mode: "none"`; reuse that canonical style behavior rather than hardcoding Plotly `mode` per trace.

Requirements:

- ensure a fresh Time/Capacity view resolves its primary series to line-only rendering;
- do not overwrite a saved/restored Time/Capacity scoped style;
- do not reset a user's explicit per-series override or applied style preset;
- do not change other analysis-family defaults as part of this child.

If current code already guarantees this behavior, add/strengthen regression coverage rather than making a redundant state mutation.

### 8. Add a Time/Capacity Plotly modebar button for Grid on/off

Add one custom Plotly modebar action to the Time/Capacity plot that toggles the same canonical style property already used by the Plot Style panel:

```text
style.show_grid
```

Requirements:

- the button appears with the other Plotly hover/modebar actions;
- activating it toggles the Time/Capacity scoped `show_grid` value through the existing plot-style update path;
- do not manipulate Plotly DOM/layout directly as an isolated visual hack;
- the Plot Style panel stays synchronized immediately;
- saved plots/drafts/export rendering therefore see the same canonical grid state;
- the button's title/accessible name should reflect the action, e.g. `Hide grid` while the grid is visible and `Show grid` while hidden;
- avoid duplicate custom buttons across rerenders;
- keep `displaylogo: false` and existing legend-edit behavior intact.

This child adds the modebar control to Time/Capacity only. Do not broaden the task to every analysis family.

## Out of scope

- persisted navigation history;
- protocol markers/timeline mini-map inside the callout;
- slider endpoint resizing as a second width-control paradigm;
- an `of N cycles` toolbar label;
- new backend endpoints or scientific computations;
- query-per-pointer-event behavior;
- new keyboard shortcut families beyond the directional slider keys and Ctrl+click requested above;
- grid modebar buttons for Cycles, Steps, DCIR, Chargeability, C-rate, etc.;
- broad `AnalysisEditor.tsx` refactoring;
- changes to Plotly export dimensions or scientific trace definitions.

3. Add transient preview-range plumbing so From/To and plot can follow the drag without canonical mutation or request flooding.
4. Add Previous View history dropdown and Ctrl+click tooltips/actions.
5. Implement the one-time new-view last-20 guard and verify line-only default behavior.
6. Add the Time/Capacity modebar Grid action through the canonical scoped style update path.
