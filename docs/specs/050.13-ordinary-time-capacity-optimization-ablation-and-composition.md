## Goal

Find the fastest scientifically equivalent architecture for the everyday **ordinary Time/Capacity Voltage/Current interaction**, with the user's primary product target remaining approximately **200 ms user-visible p50 latency** for a representative warm multi-Cell interaction.

This child is an **ablation-and-composition benchmark**, not permission to merge every plausible optimization into the production path. Test candidate mechanisms independently first, measure their isolated contribution, then combine only the winners and measure the composed stack again. A later child should own final productionization of the selected architecture if 050.13 needs temporary benchmark-only mechanisms or dependencies.

Derivatives are regression coverage only. Do not optimize the architecture around derivative performance.

## Why this child exists

050.12 reduced ordinary Time/Capacity latency materially without new concurrency or native code, then reconciled the complete production request into exclusive timings.

Representative real saved `Performance analysis` p50 values after 050.12 are:

| workload | complete ordinary route p50 |
|---|---:|
| 1 Cell — Time — cycles 1-3 | ~43.5 ms |
| 6 Cells — Time — All | ~382.1 ms |
| 10 Cells — Time — All | ~637.9 ms |
| 11 Cells — Time — All | ~679.8 ms |
| 6 Cells — capacity — All | ~542.9 ms |

For real 6-Cell Time All, the complete route is dominated by the engine (~316 ms). Synchronous result-cache persistence contributes ~45 ms; guard/signature work and final response serialization are much smaller but measurable.

The reconciled 6-Cell Time All **sequential Cell-job aggregate** is approximately 312 ms. Important exclusive costs are:

|---|---:|

| Parquet footer/schema | 2.35 ms |
| row-group decode / Arrow -> pandas | 18.51 ms |
| raw exact-cycle filter | 12.41 ms |
| raw record-index sort | 3.95 ms |
| raw cycle mapping | 16.83 ms |
| raw frame concat | 0.54 ms |
| indexed raw-access residual | 3.62 ms |
| exact-cycle filter + engine sort | 20.32 ms |
| continuous-time transform | 5.30 ms |
| source-boundary construction | 0.79 ms |
| phase classification | 34.92 ms |
| phase/capacity parent residual | 0.29 ms |
| scalar capacity metadata | 7.26 ms |

For 6-Cell capacity All, an additional major cost exists: the prepared phase/capacity parent residual is approximately **129 ms**.

At the complete request level, 6-Cell Time All result-cache persistence is approximately 45 ms, split roughly into 27.6 ms JSON encode, 14.0 ms gzip, <1 ms atomic file replacement, and ~1 ms sidecar/prune work. Raw storage hardware is therefore not the main persistence cost.

These numbers are starting evidence only. Candidate promotion must use like-for-like measurements on the current implementation.

## Locked decisions

1. **Ordinary Time/Capacity is primary.** Optimize `view=voltage_current`, especially Time/Consecutive broad multi-Cell interaction. Capacity remains required secondary coverage.
2. **Ablate before composing.** Every candidate gets an isolated A0-vs-candidate measurement before being allowed into a winner stack.
3. **Do less work before parallelizing it.** Elimination/reuse/payload slimming candidates run before process/native composition decisions.
4. **Real data decides production value.** Synthetic data is an iteration accelerator, never the final promotion gate.
5. **Exact persisted result-cache hits remain direct.** They must not dispatch engine, raw-read, process-pool or native work.
6. Preserve scientific calculations, provenance, deterministic ordering, continuation semantics, voltage-channel semantics, protocol masking, source-boundary semantics and full-resolution export fidelity.
7. Full-resolution/non-compact scientific export is not allowed to inherit display-only omissions or adaptive point limits.
8. No unbounded RAM cache or speculative prefetch.
9. SQLite/SQLAlchemy state stays in the owner process. Workers receive immutable descriptors; never share a live `Session`.
10. Do not pickle complete pandas DataFrames into worker processes merely to obtain parallelism.
11. Bound concurrency. Benchmark 2 and 4 persistent Python workers before considering any larger count. Record nested PyArrow/NumPy/BLAS/native threading and prevent oversubscription.
12. Rust/native work must be coarse enough to attack a measured material boundary. Do not port the analysis engine wholesale.
13. No `CALC_VERSION` bump for a performance-only equivalent implementation. Any response-schema/cache-shape change must use the repository's existing schema/cache-version policy.
14. Do not broadly refactor `AnalysisPage.tsx` or unrelated frontend architecture.
15. Never modify, reset or discard unrelated branch work.

# Part A — calibrate a fast synthetic benchmark tier

## A1. Purpose

The full real matrix is too expensive to run for every small experiment. Add a deterministic synthetic benchmark workload that exercises the **same ordinary indexed Time/Capacity branches** while being shorter.

The synthetic workload is for performance iteration only. It must not replace golden scientific fixtures or real-data acceptance.

## A2. Synthetic variants

Create or generate deterministic variants representing approximately:

- **S100** — current representative synthetic length;
- **S50** — ~50% of S100 raw rows/cycles;
- **S25** — ~25% of S100 raw rows/cycles.

Prefer a generated indexed cache/fixture owned by the benchmark rather than adding a large opaque binary source file when the same execution shape can be generated deterministically. If an actual synthetic source file is necessary to exercise the correct cache-building path, document why.

Each candidate dataset must preserve enough structure to exercise:

- 6 independent Cells for the main fast workload;
- representative cycle/status patterns including charge/rest/discharge;
- indexed Parquet row groups and source-index planning;
- source provenance/boundaries;
- broad cycle selection;
- the compact ordinary Time/Consecutive path;
- display downsampling — the raw selection must remain comfortably above the point budget;
- the same trace projection and response serialization path;
- a 1-Cell cycles 1-3 small control.

If continuation/multi-source topology materially affects the real Performance dataset, include a representative continuation case as a separate control rather than distorting every synthetic Cell.

## A3. Calibration gate

Run A0 on S100/S50/S25 and the real 6-Cell Time All case. Choose the **smallest** synthetic variant that remains representative.

A shorter variant is acceptable only if:

- it follows the same indexed/compact/downsample execution branches;
- downsampling remains active with approximately the same returned display-point regime;
- the same major bottleneck classes remain visible (filter/map, phase where applicable, downsampling, post-downsample materialization, compact projection, persistence/serialization);
- it does not invert the broad ordering of the important stage costs in a way that would change which optimization mechanism is being tested;
- scientific/trace-order parity against its own A0 is exact for every candidate.

If S25 satisfies these conditions, use S25 for most development iterations. Otherwise use S50. Do not force S25 merely because it is faster.

Use at least 3 warm repetitions for rapid synthetic candidate screening and at least 5 warm repetitions for final synthetic winner/composition confirmation.

# Part B — atomic isolated experiments

Every candidate below must be measured **independently against the same A0 baseline** before composition. Candidates that are unsafe, impossible under current invariants or obviously duplicate another candidate may be rejected after code inspection, but the record must say why rather than silently skipping them.

For each candidate report:

- exact code boundary changed/tested;
- synthetic p50 and min/max;
- relevant exclusive stage changes;
- total engine and complete-route delta where the candidate affects those boundaries;
- output bytes/returned points where relevant;
- CPU/effective-core and memory evidence for concurrency/native candidates;
- scientific digest, deterministic Cell/trace order and source/provenance parity;
- small-control regression;
- classification: **promote / retain only as supporting technique / reject**.

## Wave 1 — eliminate duplicated or unnecessary work

### T1 — skip phase classification when the ordinary compact request provably does not consume phase

Test the narrow case at minimum:

```text
view=voltage_current
x_axis=time
display_mode=consecutive
compact=true
standard interactive precision
```

Verify all backend/frontend/export consumers first. If phase is not needed for this path, avoid `_phase_from_raw()` and do not manufacture/send a redundant phase array. Overlap/reset, overlap/mirror, derivative and any scientific/full-export path that consumes phase must retain it.

### T2 — skip unnecessary scalar metadata

For ordinary Time/current-mA requests, determine which of active mass, nominal capacity and electrode area are actually needed by the returned trace and selected current axes. Avoid retrieving/materializing metadata fields not consumed by the request. Preserve trace metadata where the UI contract genuinely requires it.

### T3 — reuse owner-resolved Cell/source state

Measure and prototype resolving selection, ordered source chains, source versions/capabilities and bulk scalar metadata once in the owner request context, then passing immutable snapshots/descriptors into the per-Cell executor. Eliminate repeated ORM walking/lazy loads without changing identity semantics.

### T4 — build Time/Capacity cache identities from one shared owner fingerprint pass

`time_capacity_data_signature()` and render-specific `result_key()` currently perform closely related identity work. Benchmark producing one authoritative base scientific/source fingerprint and deriving the render-specific key from it without rebuilding the same relational/source fingerprint twice.

### T5 — request-local validated raw-layout/index descriptor reuse

The stitch plan and actual raw read both validate closely related index/layout state. Preserve the non-waiting publication/race safety contract, but test whether one request-local validated descriptor plus a cheap freshness/generation check can replace repeated JSON/footer/index work.

### T6 — remove a provably redundant sort

The indexed reader sorts by `record_index`; the engine later sorts by cycle/segment/record index. Establish the precise ordering invariant. Test eliminating one sort only if exact deterministic order remains guaranteed for single- and multi-source chains.

### T7 — remove duplicate exact-cycle filtering

Indexed planning/read already selects requested cycles and the engine filters again. Test carrying an exact-selection invariant into the engine so a redundant filter can be skipped when safe. Stale/out-of-range/fallback paths must remain correct.

### T8 — replace cycle mapping with a denser vectorized/index-based mapping

Benchmark a NumPy/dense-array/offset mapping appropriate to the already-dense global/local cycle index rather than generic pandas/dict work, while preserving continuation mapping exactly.

### T12 — remove redundant compact response arrays

Audit what the ordinary compact frontend actually consumes. In particular test whether returning `display_x` makes the underlying time/capacity x-array redundant for the interactive response. Also remove derivative/full-export-only arrays from ordinary compact payloads where they are already logically unused. Do not remove information required by hover, export, saved-plot parity or alternate display mode.

### T13 — compact provenance representation

The response currently repeats per-point source filenames/hashes/positions while also carrying source descriptors. Benchmark a compact representation such as per-point source index/id plus `source_cycle`, with filename/hash reconstructed from the descriptor table where safe. Preserve exact provenance semantics and full export fidelity.

## Wave 2 — reduce copying, projection, payload and persistence cost

### T9 — optimize downsample-index selection

Benchmark a faster vectorized implementation of `_downsample_indices()` while keeping all mandatory extrema/boundary/visibility behavior and deterministic output.

### T10 — eliminate `raw.iloc[take]` as the central post-downsample gather

Test keeping raw input immutable and gathering only the final response arrays directly with NumPy/Arrow `take`-style operations. Avoid creating a second pandas frame merely to return the selected display rows.

### T11 — fuse downsample selection and final-array gathering

After T9/T10 are measured independently, test a fused path that produces final selected arrays once and avoids repeated index/array materialization. Record incremental benefit over the best independent implementation, not only versus A0.

### T14 — optimize ndarray -> Python-list conversion

Benchmark improving `_jsonsafe_plot()`/`_jsonsafe_int()` conversion, rounding, non-finite/null handling and text/int projection. Avoid repeated Python scalar loops where vectorized/native representation can preserve the exact JSON contract.

### T15 — NumPy-aware JSON serialization

Benchmark an established high-performance serializer that can consume NumPy-like arrays or otherwise reduce Python-object projection, if it can preserve exact permitted JSON semantics, deterministic key/payload behavior where required, packaging constraints and Windows support. Treat a new dependency as provisional until the final composition proves material value.

### T16 — serialize the scientific response body once

The cache miss currently JSON-encodes the result for persistent cache storage and serializes it again for the HTTP response. Prototype one authoritative scientific JSON-byte construction that can feed both destinations without parsing/re-encoding the large body. Preserve the cache body/header split and direct-hit byte-splice path.

### T17 — bounded write-behind for disposable result-cache persistence

Because the analysis result cache is disposable rather than canonical, benchmark moving gzip/file persistence off the response critical path **only after the exact immutable cache bytes/key are fixed**. Requirements:

- response correctness cannot depend on successful cache persistence;
- bounded queue/backpressure; no unbounded background accumulation;
- same-key ordering/race semantics explicit;
- shutdown/cleanup behavior defined;
- failed cache writes remain safe misses later;
- no source/scientific recalculation in the background writer.

Measure synchronous baseline versus one-encode synchronous store and versus bounded write-behind.

### T18 — adaptive interactive point budget

Benchmark reducing compact display-point count according to viewport width, visible Cell/trace count and a documented samples-per-pixel rule while retaining source boundaries and required extrema. This is display-only; full precision/export remains unchanged.

Test at least current representative 1200 px plus one narrower and one wider viewport. Report returned points, response bytes, backend timing and, if available through the existing 050.4 installed profiler, frontend/Plotly impact. Do not assume fewer points are acceptable solely because backend is faster; visual equivalence/manual inspection is required before production promotion.

## Wave 3 — cross-Cell and native execution

Run these against both A0 and the best serial `do less work` stack from Waves 1-2, because a worker/native mechanism that looks useful on wasteful work may become irrelevant after the waste is removed.

### T19 — persistent 2-process whole-Cell Python pool

Start two Python worker processes once per application/runtime lifecycle, outside warm interaction timing. Owner resolves relational/scientific identity and sends only compact immutable work descriptors. Each worker independently performs the measured per-Cell cache read + transforms + downsampling + compact final trace preparation. Return only compact final results for deterministic owner merge.

Do not send complete DataFrames through IPC. Record startup separately, steady-state dispatch/IPC bytes, worker RSS, parent RSS, CPU/effective cores and nested native thread limits.

### T20 — persistent 4-process whole-Cell Python pool

Same contract as T19 with four workers. Compare directly with T19; do not assume four is better.

### T21 — workload-gated persistent process pool

If T19/T20 materially improve broad multi-Cell requests but regress 1-Cell/small requests, benchmark the smallest deterministic gating rule based on already-known request facts such as resolved Cell count/expected row count. No timing-history/ML heuristic.

### T22 — in-process Rust/PyO3 fused display-preparation kernel

Benchmark a coarse in-process native boundary, borrowing NumPy buffers where practical, that attacks a **material measured region** such as filter/map/optional phase/downsample/final gather/round-null projection. Do not merely rewrite the already-cheap ordinary arithmetic kernels from 050.10.

Measure:

- sequential native kernel time;
- Python/native transfer/copy bytes;
- complete engine/request delta;
- Windows build/package implications;
- exact numerical/provenance/order parity.

### T23 — Rust/Rayon fused display kernel

Only if T22 is independently worthwhile, test bounded Rayon 2 and 4 workers inside the same coarse native operation. Prevent oversubscription with PyArrow/NumPy/process candidates. Report isolated and complete-request gains separately.

### T24 — persistent Rust-process control

As a comparison/control, test the same coarse native work behind a resident Rust subprocess only if implementation effort is modest. Record IPC/copy cost explicitly. Reject if the process boundary erases the in-process/native benefit.

## Capacity-specific experiment

### C1 — decompose and reduce the ~129 ms prepared phase/capacity parent residual

Before choosing an implementation, split the 6-Cell capacity parent residual into at least:

- prepared derived read/decode;
- alignment/join/index matching;
- phase-code materialization;
- prepared capacity materialization/copies;
- fallback or validation work;
- residual.

Then benchmark the simplest equivalent reduction, preferably positional/index-aligned consumption by construction if the prepared/raw identity permits it. Do not use Rust merely to hide an avoidable pandas alignment.

Capacity improvements are secondary to ordinary Time, but the winning stack must not regress Capacity materially.

# Part C — composition

Do not test the full Cartesian product. Build compositions in evidence order.

### W1 — winning serial/elimination stack

Combine only independently promoted Wave 1 candidates. Measure incremental gains as each candidate is added in a fixed documented order.

### W2 — winning serial + output/persistence stack

Layer the promoted Wave 2 candidates onto W1. Because T12-T18 can overlap strongly, report each candidate's **incremental** contribution after earlier winners are present.

### W3 — W2 + best Python process strategy

Combine W2 with the best of T19/T20/T21. If multiprocessing no longer provides a stable material complete-request gain after serial optimization, reject it.

# Promotion thresholds

Use judgment, but do not keep complexity for tiny wins.

A candidate is normally worth composing when it provides either:

- >=10% stable complete-route improvement on the representative 6-Cell Time All case; or
- >=10 ms stable p50 saving in a measured stage **and** that saving survives into complete-route timing; or
- a smaller direct gain that is prerequisite to a larger composed simplification such as removing duplicated serialization/payload.

A process/native/new-dependency candidate should meet a higher bar: prefer >=15% stable complete-route improvement on broad multi-Cell Time after the simpler serial stack, with no material small-control regression unless a simple workload gate removes it.

Do not promote based on one favorable run.
