## 1. Goal

Improve perceived latency of multi-series Time/Capacity interactions by delivering each completed
scientific series to the live plot as soon as it is ready, instead of withholding every series until
the slowest/final series finishes.

The target interaction is:

```text
request starts
    ↓
series 1 complete ──────────→ render series 1
series 2 complete ──────────→ render series 1 + 2
series 3 complete ──────────→ render series 1 + 2 + 3
...
final metadata complete ────→ promote one ordinary complete TimeCapacityResult
```

This child changes **delivery and presentation timing only**. It must not alter how raw rows, global
cycles, phase, capacity, derivative values, protocol masking, downsampling, voltage quantities,
provenance, cache identity, saved artifacts, exports, or portable analyses are calculated.

The user explicitly wants genuinely progressive appearance. **Intentional batching is not an
acceptable substitute.** A completed scientific series becomes eligible for display immediately.
If several series naturally complete faster than the browser can paint distinct frames, do not add
artificial delays merely to manufacture an animation.

## 2. Why this child is now authorized

050.3 removed unnecessary whole-source materialization for narrow Time/Capacity requests. 050.6
removed/reused measured normal-view transform work. 050.7 then reduced the remaining exact backend
derivative postprocessing cost by roughly 61–64% in the implementer's same-machine paired matrix and
is review-clean.

The live architecture still has a separate perceived-latency limitation: `compute_time_capacity()`
already finishes one resolved analysis unit at a time, but the current HTTP and React Query boundary
returns only one complete `TimeCapacityResult` after every unit has finished. A user looking at a
five- or six-series plot therefore receives no new-request series until the final unit completes.

The former proto-child required several questions to be answered before promotion. The user's
2026-08-21 promotion decision intentionally moves those questions into this implementable child.
They are now **implementation/verification gates**, not reasons to leave the work as a proto-child.
If a packaged-runtime limitation prevents safe progressive delivery, stop and hand the measured
constraint to review rather than silently changing the product to batched rendering.

Current anchor:

## 4. Locked product and scientific decisions

1. **No scientific change.** Streaming changes when a complete trace reaches the client, not how any
   scientific value is calculated.
2. **No parallel Cell compute.** Keep the existing deterministic resolved-unit order. Progressive
   delivery is not authorization to parallelize scientific computation.
3. **One completed scientific series at a time.** Every completed resolved unit becomes eligible for
   one logical visible addition immediately. Do not intentionally wait for another unit to make a
   batch.
4. **No artificial delay.** If completions are faster than the browser can paint separately, finish
   promptly rather than slowing computation for visual effect.
5. **Never mix request generations.** A compatible previous complete plot may remain until the first
   new-request series arrives. Once new progressive data is visible, the plot contains only the
   current request generation.
6. **Partial is never final.** Partial traces must not enter React Query as completed query data,
   persisted analysis-result cache, saved-plot artifacts, thumbnails, prepared markers, portable
   reports, or any export path.
7. **Exports are complete-only.** Plot/image/vector export, export preview, full data export,
   New/Update saved-plot actions, warmup/artifact generation and portable export cannot consume
   ephemeral partial state.
8. **Persisted cache hits stay one-shot and fast.** Do not decompose an already available exact full
   result into per-series scientific recomputation.
9. **Final equality is mandatory.** The final assembled `TimeCapacityResult` from a streamed miss
   must preserve the ordinary endpoint's complete scientific contract exactly.
10. **Selection-wide metadata is final-only.** Do not make voltage-channel capability, roles,
    references, badges or aggregate rendering metadata flicker as units arrive.
11. **Canonical order is stable.** Stream and render in the existing resolved-unit order so colors,
    legend order and identities do not move.
12. **Zoom survives later arrivals where the existing zoom-memory contract allows it.** New series
    must not reset an explicit user zoom merely because another series arrived.
13. **Terminal stream error discards partial data.** Restore a compatible previous complete result
    when available; otherwise show the existing error/empty presentation. A partial plot must never
    remain looking complete after an error.
14. **Cancellation is identity-safe.** Changing range/settings/selection immediately makes every
    later event from the obsolete request ineligible to render.
15. **One resolved series gets no visual churn benefit.** A one-series miss may use the stream
    transport internally, but the frontend should wait for terminal completion rather than perform a
    partial-then-final Plotly update for the same single series.
16. **No broad Time/Capacity refactor for style.** Extract only the coherent engine/transport/state
    boundaries needed to share the existing science and deliver it progressively.
17. **Portable analyses remain complete-result artifacts.** No streaming event/state is serialized
    into portable HTML or understood by portable import.
18. **No migration/scientific version bump.** Delivery framing is not scientific meaning. Do not
    change SQLite schema, `CALC_VERSION`, parser identity, canonical raw version, 050.2 raw-layout
    generation, 050.6 prepared-derived generation, analysis-result schema version, or analysis-cache
    scientific key unless the implementer discovers an actual completed-result contract change and
    stops for review first.
19. **050.P1 remains planning-only.** Do not implement or schedule it in this child.

## 5. Transport contract

### 5.1 Dedicated live progressive endpoint

Add a dedicated live Time/Capacity route, preferably:

```text
POST /api/analyses/{analysis_id}/time-capacity/stream
```

It accepts the same scientific/request options as the existing Time/Capacity compute request plus a
bounded client-generated stream request ID used only for event correlation. It must use the same
scientific result key and source-data signature as `/time-capacity`.

The ordinary `/time-capacity` endpoint remains the complete-result endpoint for:

- saved Time/Capacity previews;
- saved artifacts and warmup;
- plot/image/vector/data export where a complete result is required;
- portable snapshot generation;
- tests/control parity;
- any code path that does not need progressive live delivery.

### 5.2 Dual response mode preserves the exact cache-hit fast path

The streaming endpoint has two legal successful response content types:

**Exact persisted complete-result hit**

```text
Content-Type: application/json
body: the ordinary complete TimeCapacityResult
```

Use the existing stored-body splice behavior where practical. A persisted hit must not parse the
large cached body merely to convert it into a sequence of per-series events.

**Cache miss**

```text
Content-Type: application/x-ndjson
body: stream_version=1 events
```

The frontend helper detects the content type. JSON resolves as one normal complete result; NDJSON is
read incrementally.

This is a transport distinction only. The result cache key is unchanged.

### 5.3 NDJSON event schema — stream version 1

Use newline-delimited UTF-8 JSON. Every event is one JSON object terminated by `\n`.

#### `start`

Emit only after request identity has been validated and the total resolved-unit count is known:

```json
{
  "type": "start",
  "stream_version": 1,
  "request_id": "client-generated-id",
  "total_series": 6,
  "data_signature": "backend-result-key",
  "source_data_signature": "backend-source-data-key",
  "cache_status": "miss"
}
```

`total_series` is the resolved analysis-unit count, not `selection.entries.length`. Replicate groups
therefore report the real number of scientific series that will arrive.

#### `series`

One event per resolved unit, in canonical order:

```json
{
  "type": "series",
  "stream_version": 1,
  "request_id": "client-generated-id",
  "index": 1,
  "total_series": 6,
  "trace": { "...": "one complete ordinary TimeCapacityTrace" }
}
```

`index` is one-based so it directly supports `N of total series loaded` presentation. A scientific
series may later expand into more than one Plotly trace; all Plotly traces belonging to that one
scientific series form one logical visual arrival.

#### `complete`

After all units and selection-wide metadata are final:

```json
{
  "type": "complete",
  "stream_version": 1,
  "request_id": "client-generated-id",
  "metadata": { "...": "ordinary TimeCapacityResult fields except cell_traces" }
}
```

The frontend assembles exactly one final result:

```text
{ ...metadata, cell_traces: orderedCompletedTraces }
```

The `metadata` object must include the ordinary final cache/data/source signatures, settings,
voltage-channel summary, badges, parser/calculation/version fields, rendering metadata and any other
current top-level fields except `cell_traces`. Do not send all completed traces a second time in the
terminal event.

If opt-in 050.4 profiling is active, its final backend profiling facts may be included in the final
metadata exactly as ordinary profiled responses do; per-series client timing remains profiler-only
and must not enter ordinary scientific responses.

#### `error`

After HTTP 200 streaming has begun, errors use a terminal event:

```json
{
  "type": "error",
  "stream_version": 1,
  "request_id": "client-generated-id",
  "message": "safe user-facing error text"
}
```

Do not expose traceback/internal data. Validation failures detected before streaming begins should
retain ordinary HTTP status/error behavior.

### 5.4 Streaming parser

Add a small generic API helper that:

- uses the existing `apiUrl()` sidecar resolution and debug request/response/error conventions;
- accepts `AbortSignal`;
- handles ordinary JSON complete responses and NDJSON responses;
- reads `Response.body` incrementally;
- uses `TextDecoder(..., {stream: true})` correctly;
- handles one JSON line split across arbitrary chunks;
- handles several lines in one chunk;
- handles a UTF-8 multibyte character split across chunks;
- rejects malformed/unknown stream events;
- never exposes a partially parsed event;
- stops reading promptly on abort.

Do not introduce WebSockets or `EventSource`.

## 6. Backend execution shape

### 6.1 One scientific implementation

Refactor `compute_time_capacity()` only enough to expose its existing resolved-unit completion
boundary to two consumers:

```text
shared setup
-> exact unit 1 calculation -> complete trace 1
-> exact unit 2 calculation -> complete trace 2
-> ...
-> shared finalization -> complete TimeCapacityResult metadata
```

The ordinary function consumes all steps and returns the same complete dict it returns today. The
streaming route consumes the same shared unit calculation and emits each completed trace before
continuing.

There must not be one scientific implementation for `/time-capacity` and another copy for
`/time-capacity/stream`.

A small internal context/state object is acceptable if it is the minimum coherent way to preserve
selection-wide accumulators such as badges, parser identities, voltage capability candidates and
returned-point totals.

### 6.2 Do not share the request-owned SQLAlchemy Session across a streaming worker boundary

A `StreamingResponse` may iterate its body outside the original synchronous endpoint call. Do not
pass the request dependency's SQLAlchemy `Session` into an ad-hoc producer thread or otherwise rely
on request-thread affinity.

Preferred implementation:

1. perform cheap request existence/capability/cache-hit validation before starting a miss stream;
2. the miss stream's synchronous iterator/generator opens its own `SessionLocal` within the context
   in which the generator is consumed;
3. re-resolve the Analysis/spec/provenance and verify that the expected result/source identity still
   matches before emitting `start`;
4. consume the shared Time/Capacity unit iterator using that owned session;
5. close the session in `finally`.

If the current FastAPI/Starlette execution model makes this shape unsafe or buffers the body, a
bounded producer/queue with its **own** `SessionLocal` is an allowed fallback. Do not share the
request session with it. Record the chosen execution shape and why.

### 6.3 Cache publication

On a streaming miss:

- never store a partial result;
- after every unit succeeds and final metadata is complete, assemble the ordinary full result;
- store that ordinary result under the existing exact Time/Capacity result key;
- only then emit the terminal `complete` event;
- that stored result must be immediately reusable by the ordinary endpoint, saved previews, exports,
  warmup and portable snapshots.

A client disconnect before full completion may terminate computation. In that case do not publish a
partial cache entry. If full computation and cache publication have already completed before the
connection is noticed, retaining the complete cache entry is valid.

### 6.4 Background-job lifecycle

Keep the existing analysis-compute activity entry truthful. Unit completion events may reuse the
same canonical progress boundary, but do not create a second job per series. On success, terminal
error or cancellation, the job must reach an existing legitimate terminal state; it must not remain
permanently `running` because the HTTP consumer disappeared.

Do not claim that aborting the browser can interrupt pandas/NumPy work already executing inside a
single unit unless cooperative cancellation is actually implemented and tested.

## 7. Frontend progressive state

React Query remains the owner of **complete** server state. Ephemeral in-flight state lives in the
Time/Capacity feature and is keyed by the current frontend request generation.

Minimum state:

```text
request generation / dataSignature
server stream request_id
status = starting | partial | complete | error
total_series
ordered completed scientific traces
```

Behavior:

1. a new query may keep a scientifically compatible previous complete result through the existing
   placeholder policy;
2. `start` records the truthful resolved total but does not replace the old complete plot;
3. the first `series` event switches the plot entirely to current-request partial data;
4. every later `series` event becomes eligible for its own visible update immediately;
5. no intentional timer waits for another series to create a batch;
6. `complete` assembles the ordinary final `TimeCapacityResult`, resolves the React Query promise,
   and clears ephemeral partial state;
7. React Query stores only that final result;
8. an obsolete/stale request generation may finish or emit chunks, but none may update current UI;
9. abort/error discards partial data and restores the compatible previous result or existing error
   presentation.

### 7.1 Partial render metadata

`timeCapacityTracesForResult()` currently reads `result.voltage_channels` for labels and the layout
builder consumes result-level context. Selection-wide voltage metadata is not final after one Cell.
Do not perform a preliminary full scientific pass merely to obtain it.

For partial rendering, use a small explicit render-only context:

- if the existing compatible previous complete result is valid for the same semantic voltage/display
  context, its non-scientific presentation metadata may be used while partial data arrives;
- otherwise use a stable generic label for the already-requested voltage quantity and an
  unknown/non-published capability state;
- do not update the external voltage selector's selection-wide availability until `complete`;
- final completion reconciles to the authoritative metadata once.

Keep this helper clearly render-only. It is not a `TimeCapacityResult` accepted as final data.

### 7.2 Loading/progress presentation

Once one current-request partial series is visible:

- show the partial plot at normal opacity/readability, not the dimmed placeholder opacity;
- suppress the large center loading state;
- show compact theme-safe helper text such as:

```text
2 of 6 series loaded · calculating…
```

Use the existing visual style guide (`Text size="xs"`, dimmed/semantic chrome, stable geometry,
light/dark safe). Do not add animation, skeleton traces, guessed future axes or placeholder lines.

The Activity/background-job UI remains independent.

### 7.3 Complete-only actions

While progressive state is partial, the following must remain unavailable to that state:

- plot/image/vector export and export preview;
- full data export;
- New plot / Update saved plot actions if they would capture the live figure;
- artifact/thumbnail writes;
- portable export.

A separate complete previous result may remain visible before the first new trace, but the existing
050.1 identity rules still prevent exporting it as if it were the pending current request.

## 8. Required Plotly strategy benchmark

The user explicitly rejected intentionally batched visual updates. Before locking the production
partial-render implementation, benchmark **both** one-series-at-a-time strategies against the same
representative installed-app request.

### Strategy A — declarative React / `Plotly.react()`

For each `series` event:

1. append the complete scientific trace to the current partial state;
2. rebuild plot traces/layout using the canonical Time/Capacity builders/render-only partial context;
3. pass the new `data`/`layout` props to the existing `<Plot>`;
4. let `react-plotly.js` reconcile the existing graph without changing its component key.

Prefer this if its repeated reconciliation cost is small because React remains the sole owner of the
figure.

### Strategy B — targeted `Plotly.addTraces()`

For each `series` event, use the existing `graphDiv` and add only the Plotly traces belonging to the
newly completed scientific series. A derivative Cell may produce many Plotly traces; those all arrive
together because they are one completed scientific series.

Keep a canonical shadow list of completed scientific traces for:

- final result assembly;
- canonical colors/order;
- cancellation/error discard;
- terminal declarative reconciliation.

This strategy is acceptable only if measurement and tests prove that React rerenders, resize,
status-text updates and zoom callbacks cannot erase, duplicate or reorder imperatively inserted
traces. Terminal completion must reconcile once to the same canonical full declarative figure.

### 8.1 Benchmark measurements

For both strategies, using the same machine, dataset and request, record:

- request start;
- each scientific `series` event receipt;
- each logical series visible-Plotly completion;
- time to first useful partial paint;
- per-arrival Plotly update duration: individual values, median and maximum;
- final series received;
- final metadata received;
- final Plotly completion;
- total interaction time;
- scientific series event count;
- visible partial-update count;
- true Plotly remount/`newPlot` count;
- zoom preservation across later arrivals;
- final trace/legend/color/order equality.

Use repeated runs where practical. Do not compare absolute times from different machines as a
regression metric.

### 8.2 Selection rule

- If declarative per-series reconciliation is already inexpensive and final completion does not show
  a repeatable material regression versus the ordinary control, select Strategy A.
- If Strategy A is materially expensive and `addTraces()` removes that cost while preserving React
  ownership/correctness, select Strategy B.
- If neither can support one-series-at-a-time presentation without a material correctness or final-
  latency problem, **do not switch to batching**. Hand the evidence back to review/user.

Do not invent a universal absolute millisecond threshold before measuring the installed runtime.
The implementation record must explain the measured selection.

The stacked ↔ flat key transition remains the existing intentional remount exception. Incoming
series must not trigger a new component key or `newPlot` per arrival.

## 10. Portable analysis and saved-artifact boundary

050.8 does **not** change the portable-analysis format.

### 10.1 Complete-result consumers remain complete

Keep these paths on the ordinary complete-result contract:

```text
SavedTimeCapacityPreview
buildPortablePlotSnapshots(...)
saved artifact generation
thumbnail / hover-preview generation
background warmup
plot/image/vector/data export
```

They may reuse the exact complete result cached by a successful streamed live miss, but they do not
subscribe to the live stream.

### 10.2 Portable HTML remains version 2

Do not add any of the following to the portable package:

- NDJSON events;
- stream version;
- request IDs;
- partial-series state;
- progress state.

Therefore 050.8 requires:

```text
no portable format-version bump
no manifest change
no new payload kind
no portable report runtime change
no importer stream knowledge
```

Portable import continues to validate the package without executing its JavaScript, restore/reuse
Cells/sources/analysis state, and then use normal local application behavior. An imported analysis
may use progressive live Time/Capacity later; that is runtime behavior after import, not portable
state.

A frozen portable HTML must remain viewable while its original sources are offline, exactly as
before.

## 17. Implementation record

Implemented on `feature/runtime-performance-optimization`.

### Delivered shape

- `compute_time_capacity()` now exposes its existing canonical per-unit completion boundary through
  an optional callback. The ordinary result path is unchanged; the stream route consumes the same
  scientific implementation and preserves canonical one-based unit order.
- `POST /api/analyses/{analysis_id}/time-capacity/stream` performs the same capability, source
  signature, request-option and result-key checks as the ordinary route. Persisted complete bodies
  return one-shot `application/json`; misses use typed v1 NDJSON `start`, `series`, `complete` or
  terminal `error` events. The miss worker owns a `SessionLocal`, verifies identity before `start`,
  applies bounded backpressure, stores one ordinary complete result before `complete`, and settles
  the existing background job on success, failure or disconnect.
- `postJsonOrNdjson()` handles JSON/NDJSON dual responses, abort signals, arbitrary UTF-8/chunk
  boundaries and fail-closed event parsing. Time/Capacity keeps partial traces outside React Query,
  persistent caches, artifacts and exports; stale generations are ignored and complete-only actions
  remain gated. The compact cue is `N of M series loaded · calculating…`.

  stacked/flat key exception only. Strategy B remains an opt-in diagnostic benchmark, not a second
  production rendering owner.

  byte/timestamp boundaries, partial/final Plotly boundaries, strategy and remount facts.
