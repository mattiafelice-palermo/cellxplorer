## Goal

Given two or more selected source files, optionally plus an existing Cell/Test, report a suggested
chronological order and explain whether the sources look like a plausible continuation. The
service is advisory except for identity/integrity violations. It must not decide that differing
numeric step IDs mean different cells.

## Backend design

Create `backend/app/services/continuations.py`. Keep compatibility comparison out of the router and
make the core comparison pure/testable.

Add:

```http
POST /api/imports/continuations/inspect
```

Request:

```json
{
  "sources": [
    {"staged_name": "...", "source_path": "C:\\...\\a.ndax"}
  ],
  "existing_test_id": null,
  "proposed_order": ["staged-a", "staged-b"]
}
```

`existing_test_id` is optional and causes the current ordered Test sources to be prepended as
read-only existing entries. `proposed_order` applies only to newly selected staged sources and must
be an exact permutation when supplied.

Response:

```json
{
  "sources": [{
    "key": "staged-a",
    "kind": "existing|staged",
    "source_file_id": null,
    "filename": "a.ndax",
    "hash": "...",
    "start_time": "...",
    "end_time": "...",
    "local_cycle_start": 1,
    "local_cycle_end": 73,
    "local_cycle_count": 73,
    "protocol_signature": "...",
    "device_info": "...",
    "channel": "...",
    "nominal_capacity_mah": 3.18,
    "active_mass_mg": null,
    "inspection_status": "ready|pending|error"
  }],
  "suggested_order": ["staged-a", "staged-b"],
  "findings": [{
    "id": "stable deterministic id",
    "code": "timestamp_gap",
    "severity": "info|warning|confirmation|blocking",
    "source_keys": ["staged-a", "staged-b"],
    "title": "Six-day gap between files",
    "message": "Plain-language explanation",
    "details": {}
  }],
  "can_submit": true
}
```

The exact Pydantic class names may follow local conventions, but the semantic fields are required.

## Inspection performance

- Reuse existing header/hash/import-preview work. Do not parse the same file twice during one
  inspection.
- Raw end timestamp and observed local cycle range may require the existing parse/cache path.
  Report `inspection_status="pending"` while that work is unavailable; never fabricate values.
- Keep expensive parsing off the request/UI critical path using the existing background import
  preview/job pattern. A follow-up inspection after the cache is ready returns final findings.
- Hash/stability checks must use the existing source stability rules.

## Finding policy

### Blocking

- same hash appears twice in the proposed chain;
- staged hash is already linked to another Test (including another Cell);
- source path is missing, unreadable, changing, or not `.nda`/`.ndax`;
- proposed order contains missing, duplicate, or foreign keys;
- inspection failed such that identity cannot be established.

### Explicit confirmation required

- recorded timestamp ranges overlap;
- proposed user order reverses the reliable chronological suggestion;
- nominal capacity or active mass differs materially from the Cell/first source;
- an existing indexed but unlinked `SourceFile` would have its stored path/header refreshed.

Use documented tolerances: relative difference greater than 5% for positive nominal capacity or
active mass. Missing values are informational, not mismatches. Confirmation is represented by
stable finding IDs so the write API in 034.3 can require acknowledgement after revalidation.

### Warning or information

- gap between end and next start, including a human-readable duration;
- device/channel/remarks/barcode differ;
- protocol signatures differ;
- local cycles restart, continue, overlap numerically, or contain gaps;
- timestamp confidence is incomplete.

Protocol mismatch and channel difference must not block. The user’s supplied example legitimately
contains both.

## Suggested order

Sort staged sources by:

1. reliable first-record timestamp;
2. header `start_time`;
3. selected-input order as stable fallback.

Existing sources retain their current relative order. Never silently apply the suggestion to a
mutation; return it for the UI to offer.

## Frontend policy

Add typed contracts/functions to `frontend/src/api.ts` and a small pure module
`frontend/src/continuationPolicy.ts` for:

- whether submit is blocked;
- which finding IDs require acknowledgement;
- stable suggested-order application;
- labels for `Historical source` and `Tracked tail`;
- concise user-facing finding summaries.

No modal or page is created in this child.

## Acceptance

- Findings are deterministic for identical inputs.
- The server, not the client, owns compatibility classification and tolerances.
- Suggested order is chronological when timestamps are reliable and stable otherwise.
- Duplicate/linked/missing/unstable inputs block.
- Protocol, channel, local step, and local cycle differences are visible but do not reject a valid
  continuation.
- No private file is committed.

### Intentionally asynchronous inspection

When header/hash inspection succeeds but parse caches are absent, sources return
`inspection_status="pending"` and a background thread calls `cache.build`. Clients should re-call
the inspect endpoint after cache preparation to receive final gap/overlap/cycle findings. Header
findings and blocking identity checks are still returned on the first response.

### R* review fixes

- **R1:** When `proposed_order` is omitted, `order_reversed` now compares `staged_keys` input order
  against the suggested chronological order instead of collapsing to the suggestion.
- **R2:** `timestamp_range_from_raw` uses min/max of successfully parsed timestamps rather than
  first/last row order.
- **R3:** Removed unused `import re` and unused locals in `_pair_findings`.
