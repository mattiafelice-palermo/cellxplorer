## 1. Goal

Create one comparable, current-code performance map for **every user-facing scientific Analysis family** before selecting further optimization work.

The six families in scope are:

1. Cycles;
2. Time/Capacity;
3. Steps;
4. DCIR;
5. Chargeability;
6. Rate Capability.

This child exists because Spec 050 has accumulated strong family-specific evidence, but the evidence was produced at different times and at different levels of decomposition. The next optimization must not be chosen simply because one slow function happened to be under inspection. The output of 050.17 must make it possible to answer, across the Analysis module:

- which family is currently slowest for representative interaction;
- whether the delay is cache/key/ORM work, data access, protocol reconstruction, scientific extraction, result assembly, serialization, transfer/parse, trace construction, or Plotly rendering;
- how the cost scales from one Cell to a representative multi-Cell workload;
- which specific current-code stage dominates each slow route;
- what realistic optimization ceiling exists before changing code;
- which optimization child or children should be attempted next, in ranked order.

**050.17 is a profiling and decision child, not an optimization child.** It may add bounded, opt-in profiling instrumentation and benchmark scripts required to measure the current path truthfully. It must not productionize a new scientific algorithm, cache, worker architecture, native implementation, downsampling rule, or request contract.

## 2. User decision locked by this child

The user explicitly decided on 2026-08-23 that further Analysis performance work must be driven by **detailed profiling for every analysis type**, rather than continuing opportunistically from whichever family is currently being edited.

Rate Capability receives specific scrutiny because the 050.16 representative six-Cell route was about **1.3 s** while raw materialization was only about **26 ms**. That evidence rules out raw I/O as the primary explanation but does not yet identify the real bottleneck. 050.17 must resolve that uncertainty before recommending a Rate Capability optimization.

The governing rule after this child is:

> Do not promote a new performance optimization until the complete route has been decomposed far enough to name the dominant current-code cost, quantify its absolute time and share of the route, and show why the proposed optimization attacks that cost.

## 5. Common benchmark matrix

### 5.1 Mandatory workloads

For every family, profile:

- **1 Cell**;
- **6 Cells** or the closest scientifically truthful representative multi-Cell workload already supported by the committed fixture/corpus;
- **10/11 Cells only when useful and available without inventing protocol semantics**, or when the six-Cell p50 remains above 500 ms and the larger case helps establish scaling.

Use committed golden-analysis sources/cases wherever possible. Scaling by content-identical, source-distinct Cell clones is acceptable when it preserves the real relational/source/cache route and does not pretend unrelated protocols are one Cell; follow the established 050.16 fixture pattern. Real saved application data may be measured read-only when available, but the required report must not depend on one developer's private database to be reproducible.

### 5.2 Required route states

For each workload record separately:

1. **forced result-cache miss**, with underlying raw/cycle/prepared caches already in the state expected during normal app use;
2. **exact persisted result-cache hit**;
3. where a family has a promoted selective/full fallback path, one controlled full-path comparison only if needed to explain current cost — do not rerun already accepted broad matrices without a profiling question.

Do not mix a cold Python import/startup measurement into ordinary interaction p50. If startup/import cost is relevant, record it separately and label it explicitly.

### 5.3 Repetitions and environment

Default to **three warm repetitions** per reported workload. Five repetitions are permitted only when variance prevents a stable interpretation. Do not rerun a passing matrix for confidence.

Record at minimum:

- branch commit SHA;
- OS/platform;
- Python version;
- relevant pandas/NumPy/PyArrow versions;
- logical CPU count;
- selected worker/process mode if any;
- whether the app was on mains/battery if the environment exposes a meaningful distinction;
- whether the measurement is fixture, cloned fixture, or read-only real application data.

## 6. Common timing model

Every family must expose the same top-level decomposition so results are comparable:

1. request/route setup;
2. selection + ORM/source/scalar context resolution;
3. cache-key construction;
4. exact-cache lookup/read or miss decision;
5. protocol reconstruction/recognition where applicable;
6. data access/materialization;
7. family scientific extraction/calculation;
8. cross-Cell aggregation/comparison;
9. result/provenance assembly;
10. cache persistence;
11. JSON serialization;
12. complete backend route.

Nested timers must not be summed as if they were independent. The report must provide either exclusive timings or an explicit parent/child hierarchy and a **residual/unattributed** value. If the unexplained residual is the dominant bucket, profiling is not complete enough to recommend an optimization.

For each stage report:

- p50 ms;
- min/max or equivalent small-sample range;
- percentage of complete-route p50 where attribution is valid;
- call count;
- key structural count relevant to that stage where available.

Instrumentation overhead must be measured. Pair or otherwise compare profiled and unprofiled complete-route calls using the same scientific input. Do not label a stage dominant if profiler overhead materially changes the route ranking. Prefer the reconciliation methods already established in 050.12.

## 7. Data-volume and scaling evidence

Timing alone is insufficient. Each workload should record where applicable:

- SQL statement/query count;
- selected Cells and SourceFiles;
- physical raw/cycle rows read;
- row groups read;
- rows returned after exact filtering;
- final scientific point count;
- trace count if frontend figure construction is measured;
- response body bytes;
- worker/process count and IPC bytes when already part of the production route;
- peak or delta RSS only when it is easy to measure truthfully and relevant to a candidate bottleneck.

For 1 Cell versus multi-Cell cases, state whether the observed route is approximately:

- constant;
- linear in Cell count;
- sublinear due to shared work/parallelism;
- superlinear, requiring explanation.

Do not infer algorithmic complexity from two points alone; this classification is an operational observation, not a Big-O proof.

## 8. Frontend interaction boundary

Backend speed is not sufficient to rank user-visible performance if payload preparation or Plotly rendering dominates.

For every family, record at least what is available without adding invasive production code:

- response bytes;
- JSON parse/preparation time where measurable;
- trace construction time where measurable;
- trace count and point count.

Reuse the existing 050.4/Time-Capacity opt-in profiling approach where practical rather than introducing a second general telemetry framework.

Actual browser Plotly completion timing is desirable for representative slow families, especially any family whose backend is already below ~150 ms but still feels slow. However, **manual/browser timing is not a merge blocker for this backend-led profiling child when the agent environment cannot run the installed app**. In that case record `NOT RUN`, do not claim end-to-end user latency, and classify the frontend boundary as unresolved rather than guessing.

Do not add remote telemetry, analytics, or persistent cross-user performance logging.

## 10. Scientific parity and observational safety

Profiling must be observational.

For every family/workload:

- compare profiled versus unprofiled payloads after excluding profiling-only timestamps/diagnostics;
- preserve deterministic Cell/series/occurrence order;
- preserve current scientific result digests;
- preserve source/provenance identity;
- exact cache-hit controls must not enter scientific compute or raw reads merely because profiling is enabled unless the profiler is explicitly measuring a separate forced-miss call;
- profiling must not reopen original source files merely to collect a metric that can be derived from cache/metadata already on the route.

No scientific formula, protocol-recognition rule, cutoff rule, normalization, sign convention, fingerprint, axis value, export value or candidate-selection rule may change in this child.

## 12. Rate Capability acceptance requirement

Because Rate Capability motivated this child, its final report must answer these questions explicitly:

1. Where does the roughly six-Cell ~1.3 s observed around 050.16 actually go on the current branch?
2. What fraction is owner/cache work, raw materialization, protocol reconstruction, pair building, execution extraction, sweep detection, common-rate comparison, result assembly/persistence/serialization, and residual?
3. Which substage scales most strongly from 1 Cell to 6 Cells?
4. Are repeated DataFrame scans/filtering or repeated protocol-derived operations materially responsible, or not?
5. What is the first optimization worth implementing, and what complete-route improvement could it plausibly unlock if successful?

A statement such as "raw access is not the bottleneck" is **not** sufficient closure.

## 13. Out of scope

Do **not** in 050.17:

- change scientific formulas or protocol semantics;
- implement a Rate Capability optimization after profiling it;
- change Steps/DCIR selective-read algorithms except a test/profiling hook needed to observe them;
- add new persistent cache layers;
- add a whole-Cell RAM cache or speculative prefetch;
- add/replace process pools, thread pools, Rayon kernels, Rust production dependencies, GPU code or Web Workers;
- change Time/Capacity overview density or adaptive-refinement behavior;
- change response payload schemas for ordinary non-profiled requests;
- change persistent SQLite schema;
- change `CALC_VERSION`;
- broadly refactor `AnalysisEditor.tsx` or family plot cards;
- create remote telemetry or upload benchmark data.

If a profiler reveals an obvious one-line performance defect, record it as the highest-priority next action; do not silently fix it inside this profiling child unless the user explicitly amends the scope.

### Rate Capability closure

The six-Cell Rate Capability route measured 1,295.30 ms p50. Of the attributable deep stages,
execution extraction was 1,113.41 ms p50, protocol reconstruction 131.10 ms, raw materialization
25.86 ms, rate-pair building 3.40 ms, sweep detection 1.88 ms combined, common-rate comparison
0.88 ms, invalid-neighbour validation 0.20 ms, result assembly 0.04 ms, and cache persistence /
JSON serialization 7.85 / 0.38 ms. The execution parent contains phase-row filtering and cutoff
checks; the opt-in substage timers separately recorded capacity extraction 19.03 ms, current
extraction 33.51 ms, and rate normalization 0.24 ms. The residual after the common root-stage
reconciliation was 1.26 ms p50.

The six-Cell structural counts were 6 Cells, 6 unique SourceFiles, 122,946 raw rows loaded,
1,290 reconstructed protocol steps, 198 rate pairs, 444 execution rows/groups, 12 chosen blocks,
6 invalid execution pairs, 48 common-comparison points, and 102 final response points. The
1-Cell-to-6-Cell route ratio was approximately 5.7x, an operationally linear observation. The
first evidence-backed follow-up is therefore a separate Rate Capability child around
`extract_pair_executions()` and its repeated phase-row/cutoff work; no optimization is included
in 050.17. The plausible ceiling from removing the measured parent stage is approximately
180.85 ms for this workload, before accounting for implementation risk or scientific-parity
validation.
