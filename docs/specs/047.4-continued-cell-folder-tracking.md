## Goal

Let a continued Cell keep filling itself in. When the user imports from a folder a cycler is still
writing to, they enable **Track this folder for new files** at save time; afterwards, new stable
files matching the configured rules are appended to that Cell's source chain automatically and
become its tracked tail.

The feature is an extension of continuation *import*, not a new scientific concept: an attached file
goes through exactly the same validation, ordering and provenance rules as a manual attach. Nothing
about existing sources changes — they remain historical, in position, untouched.

---

# Locked decisions

These were decided by the user and may not be reversed by implementation.

## 1. Tracking lives in the One continued cell tab

The toggle appears only in continued mode. It is **default-enabled** and labelled exactly:

```text
Track this folder for new files
```

A **Settings** button sits beside it and opens the tracking settings modal.

The toggle is offered only when the staged selection is trackable:

- exactly one staged source; or
- several staged sources that share **one parent folder** and **one supported extension/format**.

A mixed-folder or mixed-format selection is not trackable. Hide the toggle and say why in one dimmed
line rather than showing a disabled control with no explanation.

## 2. A single-source continued Cell is allowed only with tracking enabled

Today the mode selector renders only at `drafts.length >= 2`
(`frontend/src/pages/InboxPage.tsx`) and `canSubmit` requires `order.length >= 2`
(`frontend/src/continuedImportWorkspacePolicy.ts`).

Change both, narrowly:

- the user may **enter** One continued cell with a single staged source;
- submission with exactly one source is permitted **only while tracking is enabled**.

```text
sources >= 2                      → submit allowed (unchanged)
sources == 1 and tracking on      → submit allowed (new)
sources == 1 and tracking off     → submit blocked, with copy explaining why
```

Do not relax any other submission gate. `continuedImportCanSubmit(...)` keeps owning inspection
completeness, blocking findings and acknowledgement.

Define what continuity inspection means for a lone source: it still inspects that source for
readiness, and `inspection_complete` still requires it `ready`. There is simply no pair to compare,
so pairwise findings are absent — that is not the same as "inspection passed vacuously" and must not
be presented as a clean multi-source chain.

## 3. Discovery follows the global source monitor

New-file discovery is conceptually the same act as change-detection on a tracked tail. Therefore
per-Cell tracking runs **only when the global source monitor is enabled**, and additionally respects:

- `automation.is_paused(db)` — a global pause stops discovery;
- the existing idle deferral (`library.source_check_running()` / `_running_background_work()`).

Consequence that must be handled in the UI, not hidden: disabling the global monitor silently stops
discovery for **every** tracked Cell. Wherever tracking status is shown, a Cell whose watch is
enabled but whose global monitor is off must read as paused — for example
`Tracking paused — source monitoring is disabled` — never as active. Offer a direct route to the
source-monitor settings from that state.

# A — Save-modal surface

## A1 — Footer precedence

The toggle replaces the neutral `Review N selected file(s) before saving.` footer copy in continued
mode. It must **not** replace the states 047.3 introduced. Precedence, highest first:

```text
1. registration done / continue-in-background      (existing)
2. Continuity inspection failed …                  (047.3)
3. Continuity review required before import.       (047.3)
4. Continuity inspection is still preparing.       (047.3)
5. Inspect continuity before importing.            (047.3)
6. [ Track this folder for new files ]  [Settings] (this child)
```

The toggle is a control, not a status line: it stays interactive whenever it is shown, and its own
folder/pattern summary sits next to it in dimmed `size="xs"` text.

## A2 — What the toggle captures

Enabling the toggle records the intended watch for the pending import: folder path, extension/format,
pattern, ordering rule, recursion flag and cadence override. Nothing is persisted until the Cell is
created — a cancelled import leaves no watch behind.

# B — Tracking settings modal

A focused Mantine modal, in the register of `ContinuationReviewModal`. It must state plainly, at the
top, whether tracking is enabled and exactly what is being watched:

```text
Tracking: enabled
Folder:   C:\Data\BioLogic\CellA
Matching: *.mpr  ·  files directly in this folder
Ordering: source start time, then filename
```

Advanced options:

- **Filename matching** — glob (default) or regular expression, with a live preview of which
  currently-present files match. A regex that fails to compile is rejected in the dialog, never
  stored.
- **Extension / parser format** — constrained to the formats the import policy already admits
  (`import_filename_allowed`). A watch may not name a format the importer would refuse.
- **Ordering rule** — see section D.
- **Include subfolders** — default **off**, with a depth limit when enabled.
- **Cadence** — inherit the global monitor interval by default; per-Cell override allowed.

The modal never edits Cell metadata, source order, or anything scientific.

# C — Persistence and migration

Add one migration `backend/app/migrations/versions/v0004_cell_folder_watch.py`, registered in
`backend/app/migrations/registry.py`, following the existing `v0003` pattern exactly.

Two tables:

**`cell_folder_watches`** — one row per Cell (`UNIQUE(cell_id)`, `ON DELETE CASCADE`):
folder path, enabled flag, pattern kind + pattern, extension/format, ordering rule, recursion flag +
depth, cadence override, and observed state (`last_scan_at`, `last_status`, `last_error`,
`folder_last_seen_at`, consecutive-failure count).

**`cell_folder_watch_candidates`** — files the watcher has seen but not attached, so unresolved
problems survive a restart and stay actionable: path, hash when known, first-seen/last-seen,
stability state, a structured `status` (`pending_stability`, `duplicate`, `unsupported`,
`malformed`, `ambiguous_order`, `blocked_by_finding`, `needs_confirmation`, `attach_failed`),
message, and attempt count.

Successfully attached candidates are removed from the candidate table — the Cell's source chain is
the record of what was attached.

No `CALC_VERSION` change. No change to cache identity, checksum ownership, or the portable-report
format. Attaching a source is an ordinary continuation append.

---

# D — Ordering

Filename order and mtime are both unreliable — cyclers rename, and copying resets mtime. The default
ordering rule is:

```text
1. parsed source-local start timestamp
2. natural filename sort            (tie-break)
3. content hash                     (final deterministic tie-break)
```

The settings modal may offer filename-only ordering for users whose files are reliably named, but the
default is timestamp-first.

Ordering is decided over the **whole batch of new candidates**, then validated as one proposed
extension of the existing chain.

## D1 — Partial batches attach as a prefix

If a batch of candidates contains a problem in the middle, attach the **longest valid prefix and
stop**. Never skip a candidate to reach a later one: skipping manufactures a silent cycle gap, which
is exactly the failure the continuation model exists to prevent. The skipped remainder stays in the
candidate table as actionable.

## D2 — Ambiguity is a refusal, not a guess

If the ordering rule cannot separate two candidates — identical start timestamps and the tie-breaks
do not apply meaningfully — attach neither and record `ambiguous_order` naming both files.

---

# E — Scan, stability and attachment

Run discovery as an additional pass inside the **existing** `source_monitor` scheduler thread. Do not
create a thread per Cell and do not add a second scheduler.

Each pass, for every enabled watch whose gate conditions hold:

1. list candidate files (respecting recursion setting and pattern);
2. drop anything already attached to this Cell;
3. require **stability** before hashing: size and `mtime_ns` unchanged across two samples separated by
   the configured stability window, reusing `source_monitor.stability_seconds(...)` semantics;
4. inspect each stable candidate through the existing import inspection path;
5. order the batch (section D) and run the existing cell continuation inspection over
   `existing chain + ordered candidates`;
6. attach the valid prefix through the existing `attach_cell_continuations` path — not a new
   attach implementation — so provenance, positions and tracked-tail semantics stay identical to a
   manual attach;
7. record what happened.

The final attached source becomes the tracked tail; every prior source keeps its position and
historical role.

# F — Safety rules

| Case | Required behavior |
|---|---|
| Already in this chain | Skip silently. Not an error. |
| Same content registered to a **different** Cell | Never attach. Actionable error naming the other Cell. |
| Still being written | Hold in `pending_stability`. Never hash an unstable file. A Windows lock/open failure retries next pass and only becomes an error after the configured retry count. |
| Extension not configured | Not a candidate. Ignored silently. |
| Matches pattern but fails to parse | Actionable `malformed` error, retried per retry count, then parked until the user acts. |
| Ambiguous ordering | Attach nothing from the ambiguous point on; record both filenames. |
| Candidate changes between detection and attach | Re-enter stabilization. Do not attach this pass. |
| Already-attached source changed on disk | **Not this watcher's job.** The global monitor owns change detection on existing tails. |
| Folder missing / unreachable | Do **not** auto-disable. Record `folder_missing` with `folder_last_seen_at`, back off, keep retrying — network drives return. Only the user disables a watch. |
| Blocking continuity finding | Never attach. Actionable error. |
| Confirmation continuity finding | **Never auto-acknowledge.** Park as `needs_confirmation` for the user to acknowledge through the existing review surface. |

The confirmation rule is the hard line of this child. Parent 047 spent three review rounds making
acknowledgement identity-bound and server-backed; automation that ticks those boxes on the user's
behalf would silently undo that guarantee. An automated attach may only proceed on a chain that needs
no human confirmation at all.

Nothing invalid or ambiguous is ever silently dropped: every refusal leaves a visible, actionable
candidate row.

---

# G — Status and error feedback

Surface tracking state wherever the Cell's sources are already managed
(`ContinuationManagementPanel` is the natural home), showing:

- enabled/paused/disabled, with the global-monitor cause when paused;
- folder and pattern;
- last scan time and outcome;
- a count of unresolved candidates, expandable into filename + reason + suggested action.

Errors must be dismissible or resolvable — retry, ignore this file, open the folder, or edit the
watch. A permanently stuck candidate that cannot be cleared is a defect.

Keep this quiet in the common case: a healthy watch is one compact line, consistent with 047.3's
decision that the workspace must not become a diagnostics dashboard.

# I — Tests

Backend, at minimum:

1. a stable new file is attached and becomes the tracked tail; prior sources keep position and role;
2. an unstable (still-growing) file is not hashed or attached until stable;
3. duplicate content already in the chain is skipped silently;
4. duplicate content registered to another Cell is refused with an actionable error;
5. batch ordering follows timestamp → filename → hash;
6. a mid-batch failure attaches the valid prefix only and never skips;
7. ambiguous ordering attaches nothing and records both files;
8. a blocking finding refuses attachment;
9. a confirmation finding parks as `needs_confirmation` and is **not** auto-acknowledged;
10. a missing folder does not disable the watch and keeps retrying;
11. discovery does not run while the global monitor is disabled, while paused, or while other work is
    running;
12. attachment goes through the existing attach path (assert positions/provenance match a manual
    attach);
13. migration `v0004` applies cleanly forward from a `v0003` database;
14. no `CALC_VERSION` change.

Frontend, pure policy tests:

1. trackability: single file, same-folder/same-format multi-file, mixed folder, mixed format;
2. single-source submission allowed only while tracking is enabled;
3. footer precedence — tracking never outranks a 047.3 continuity state;
4. glob and regex matching, including an invalid regex being rejected;
5. ordering-rule preview matches backend ordering semantics for the same inputs;
6. paused-because-global-monitor-off renders as paused, not active.

# Acceptance criteria

047.4 is reviewable when a trackable selection offers a default-enabled folder-tracking toggle with a
settings modal in the continued-cell tab; a single-source continued Cell can be created only while
tracking is enabled; the watch persists through a registered `v0004` migration linked to the Cell and
its format; the existing source-monitor scheduler performs discovery under the global monitor's
enable/pause/idle gates; new stable matching files are ordered deterministically and appended through
the existing attach path so prior sources stay historical and the last becomes the tracked tail;
duplicates, unstable, unsupported, malformed, ambiguous, blocked and confirmation-requiring
candidates are each handled by the rules in section F with **no silent attachment and no automatic
acknowledgement**; unresolved candidates remain visible and actionable; and status accurately
distinguishes enabled, paused and disabled tracking.
