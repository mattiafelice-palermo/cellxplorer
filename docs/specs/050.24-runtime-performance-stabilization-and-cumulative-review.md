## 6. I1 — Time/Capacity LoD continuity during repeated zoom

### 6.1 Observed behavior

The user can start from a Time/Capacity view that has already received an adaptive refinement, then zoom further. The current UI briefly shows a much coarser polyline with visibly fewer points before the next detailed refinement arrives.

The visible sequence is:

```text
refined LoD A
    -> user zooms further
    -> coarse overview suddenly reappears
    -> debounce + network + backend refinement
    -> refined LoD B appears
```

This looks like the plot lost detail and then recovered, even though the old refinement was still a perfectly useful visual source while the next request was pending.

### 6.2 Verified cause

`cancelRefinement()` currently performs three jobs at once:

1. invalidates the pending request generation;
2. cancels timer/HTTP work;
3. discards the displayed refined result.

In addition, `activeRefinedResult` validates the already displayed result against the **current pending generation**. Therefore merely incrementing `refinementGenerationRef` makes the old displayed refinement ineligible even if `setRefinedResult(null)` were removed.

### 6.3 Target behavior

For a compatible zoom-in refinement transition:

```text
refined LoD A
    -> user zooms further
    -> existing LoD A remains visible under the new Plotly axis range
    -> next refinement is requested in background
    -> LoD B replaces A when ready
```

At no point should a compatible already-refined view fall back to the coarse overview solely because a newer refinement is pending.

### 6.4 Required state separation

Split the current cancellation/display concepts. Exact naming is implementation-owned, but the behavior should be equivalent to:

- `cancelPendingRefinement()`:
  - increments/changes request generation;
  - clears debounce timer;
  - aborts pending HTTP request;
  - clears pending-request viewport state as appropriate;
  - **does not discard a still-compatible displayed refinement**.

- `clearDisplayedRefinement()`:
  - removes the currently displayed transient refinement only when it is no longer semantically/display compatible.

The helper currently named `timeCapacityRefinementRequestIsCurrent(...)` should remain strict for **accepting a newly arriving response**. Do not relax stale-response generation gating. Instead, add or use a separate compatibility test for whether the already displayed refinement can remain visible.

### 6.5 When displayed refinement must be cleared

Clear the displayed refinement when the underlying overview or rendering semantics genuinely invalidate it, including as applicable:

- overview `data_signature` changes;
- selection/data-source identity changes;
- cycle range/configuration changes that alter returned data;
- voltage channel or Time/Capacity view changes;
- x-axis/time-unit/display-mode semantics change;
- refinement eligibility becomes false;
- the tab is deactivated if the existing lifecycle intentionally discards ephemeral refinement on inactive tabs;
- Plotly autorange/full overview is explicitly restored.

Do not retain an old refinement merely because it exists.

### 6.6 Viewport compatibility

The main required case is **zooming further into the already refined region**. If the user pans or jumps to a viewport that is not covered by the displayed refinement, it is acceptable to fall back to the stable overview while a new refinement is prepared.

If current response metadata is insufficient to determine whether a previous refinement covers the new viewport, add only the smallest ephemeral client/request metadata needed for that decision. Do not change scientific cache identity or persist viewport refinements.

### 6.7 Stale-response safety

Rapid A -> B -> C zooms must retain generation safety:

- B may remain displayed while C is pending if B covers C;
- a late A or B network response must never overwrite C after C becomes the active request generation;
- aborts/network errors leave the best currently valid displayed data visible;
- no stale refinement can become an export/full-resolution scientific source.

### 6.8 Acceptance criteria

Starting from an already-refined Time/Capacity view, zooming further into that refined region must **not** temporarily replace the detailed trace with the coarse overview while the next refinement request is pending. The previous compatible LoD remains visible until the replacement is ready, then the new refinement replaces it. Obsolete responses remain generation-gated and cannot overwrite the newer viewport.

Add focused tests covering at minimum:

- refined A -> zoom B -> A remains displayed while B is pending;
- rapid A -> B -> C where a late B response cannot replace C;
- autorange/full overview clears refinement;
- semantic/data-signature change clears refinement;
- incompatible pan/jump falls back safely if the prior refinement cannot cover the new viewport;
- refinement failure/abort leaves the best valid current display rather than flashing coarse unnecessarily.

## 7. I1 optional polish — short refinement transition

The user prefers a short visual effect in which the immediately zoomed existing LoD is shown first and the finer detail then appears smoothly when the new response arrives, **provided there is no meaningful performance penalty**.

This is optional polish, not a correctness requirement.

### 7.1 Preferred effect

When a compatible new refined trace arrives, use a very short transition of approximately **100–180 ms**; ~120–150 ms is a sensible starting point.

The semantic effect should be "resolution appears" rather than "scientific values move".

A practical implementation keeps the old traces at full visual weight while revealing the new
traces over the same 140 ms window:

```text
t0        old 100% / new 0%
~75 ms    old 100% / new 50%
~140 ms   old 100% / new 100%, then old is removed
```

This avoids alpha-compositing two fading copies of the same styled line, which can briefly change
apparent lightness or thickness. If custom trace opacity makes the reveal ambiguous, use an atomic
replacement instead.

Do not implement expensive coordinate-by-coordinate interpolation between old and new arrays. The two LoDs may contain different point counts and do not have a stable one-to-one mapping.

### 7.2 Performance constraints

The transition must:

- not delay refinement request dispatch;
- not block zoom/pan interaction;
- not perform scientific transforms in animation frames;
- not rebuild thousands of coordinates per frame in React;
- be immediately superseded/cancelled by a new user interaction;
- respect `prefers-reduced-motion` with an atomic swap;
- remain bounded for `scattergl` traces;
- be dropped if targeted profiling shows meaningful main-thread/rendering regression or visible frame loss.

If the animation is not cheap and robust, retain the LoD continuity fix and use an atomic replacement. Do not hold 050.24 open merely to preserve the animation idea.

### Issue ledger

#### I1 — Time/Capacity refinement continuity during repeated zoom

- **Observed / reproduction:** After an adaptive Time/Capacity refinement was already visible, a
  second zoom incremented the request generation and immediately cleared the displayed refinement.
  The plot therefore fell back to the coarse overview during debounce, HTTP, and backend work.
- **Scope:** `TimeCapacityPlotCard.tsx` and
  `timeCapacityRefinementPolicy.ts`; the existing adaptive refinement endpoint and scientific
  result/cache contracts are unchanged.
- **Cause:** `cancelRefinement()` combined pending-request cancellation with displayed-result
  disposal, while `activeRefinedResult` also required the displayed result to match the newest
  request generation. A newer request therefore invalidated both the old response and the useful
  display, even when the new viewport was inside the old refined viewport.
- **Target:** Keep a compatible refined LoD visible while the next refinement is pending; clear it
  only when identity, semantics, autorange, tab lifecycle, or viewport coverage invalidates it.
  Preserve strict generation and overview-identity checks for accepting responses.
- **Risk:** This was a visible interaction regression. The old behavior did not change scientific
  values or cache identity, but the fallback made zoom appear to lose resolution and could obscure
  whether the requested refinement was still active.
- **Implementation:** Split pending cancellation from displayed clearing. Store the displayed
  refinement's requested viewport and compatibility signature in ephemeral refs. A deeper viewport
  contained by that range keeps the old result; an autorange, semantic/data-signature change,
  inactive keep-mounted tab, or uncovered viewport clears it. The response path still requires the
  current generation and exact overview/result signatures before replacing the display. A bounded
  140 ms new-trace opacity reveal runs over the old traces kept at their exact full visual weight;
  it does not alpha-composite two fading copies of the same line, interpolate coordinates, or
  rebuild coordinate arrays per frame. The old traces are non-interactive and the new traces retain
  the legend/hover state. If a custom trace opacity would make a reveal visually ambiguous, the
  replacement is atomic. The transition is cancelled by a new viewport interaction, autorange,
  semantic invalidation, tab deactivation, or unmount, and reduced motion uses an atomic swap. The
  old whole-plot `opacity: 0.42` fetch placeholder was removed so a background request no longer
  dims a stable plot.
- **Verification:** `node --test frontend\tests\timeCapacityRefinementPolicy.test.ts` passed 10/10;
  tests cover old-LoD retention while a newer generation is pending, late B rejection after C,
  autorange/null viewport, semantic identity changes, uncovered pans, bounded transition timing,
  and reduced-motion atomic behavior. Relevant frontend tests passed 35/35; `npm.cmd run build`
  passed TypeScript plus Vite production build. Component event wiring and export separation were
  inspected directly. Browser/manual validation: **NOT RUN** at the user's explicit request.
- **Disposition:** Fixed.
