**Status:** Implemented

**Review document:** `reviews/035.6-import-progress-ui-review.md`

## Goal

Replace the three unexplained import spinners with distinct, truthful progress states:

1. discovering supported files from the selected locations;
2. inspecting file identity and Neware metadata;
3. registering Cells and queuing scientific preparation.

## Current pipeline to preserve

Verify the current owners before editing; the logical stages remain.

### Stage A — discover selected sources

- frontend calls `POST /api/imports/list-sources`;
- backend recursively lists supported `.nda`/`.ndax` files and stats their sizes;
- it does not hash, read Neware metadata, or parse cycling data.

### Stage B — inspect files

- frontend calls `POST /api/imports/inspect-paths`;
- backend hashes each file;
- reads Neware header metadata;
- checks exact duplicate / possible update identity;
- returns drafts for the final editor.

### Stage C — register Cells

- frontend calls `POST /api/imports/cells`;
- backend revalidates files and duplicate identity;
- creates relational Cell/Test/SourceFile/TestFile/folder/replicate state;
- commits;
- queues scientific cache jobs.

This child explains and instruments those operations without changing their serial execution.
035.7 owns concurrency and repeated-work optimization. 035.8 owns lazy previews and the final cache
handoff presentation.

## Job-token contract

Reuse:

- `backend/app/services/background_jobs.py`;
- `GET /api/background-jobs/by-token/{token}`;
- existing frontend `BackgroundJob` typing and polling patterns.

Add optional `job_token` to:

- import-source-list request;
- inspect-paths request;
- import-cells request.

Tokens are client-generated unique strings. Each endpoint creates its job immediately before work.
A missing token keeps backward-compatible endpoint behavior without a visible job.

### Optional common job fields

Jobs may expose:

```json
{
  "stage": "scan|inspect|register",
  "current_item_id": "path-or-staged-name",
  "current_item_label": "cell_047.ndax",
  "total_bytes": 123456789,
  "completed_bytes": 45678900,
  "discovered_files": 214
}
```

`background_jobs.update_job` already accepts arbitrary values. Preserve generic service
compatibility.

On success:

- `completed == total`;
- status is `completed`;
- current item is cleared;
- endpoint result remains the source of truth for navigation/state.

On failure:

- status is `failed`;
- `error` contains a user-safe message;
- the endpoint still returns its normal HTTP error;
- relational atomicity remains unchanged.

## Stage A job — scanning locations

Kind: `import_scan`

- `total` is selected roots/items, not unknown discovered files.
- Progress label: `Scanning 2 of 3 selected locations`.
- `discovered_files` increments as each selected root completes.
- File percentage is indeterminate because final file count is not known in advance.
- Show the root currently being scanned.
- Loose files count as one grouped `Loose files` item.
- The progress bar is striped/indeterminate; root count is textual determinate progress.
- If only loose files are selected and stat/filter work is effectively immediate, do not force a
  perceptible progress modal, but preserve accurate state for slow/unavailable paths.

## Stage B job — inspecting files

Kind: `import_inspect`

- total is candidate file count;
- one job item per file;
- update current filename before hash/header work;
- after each file, increment completed and completed bytes;
- label: `Inspecting 47 of 214 files`;
- detail: `Checking identity and reading Neware metadata`;
- determinate progress uses completed file count;
- byte progress is used only for ETA, not the visible percentage.

## Stage C job — registering Cells

Kind: `import_register`

- total is submitted Cell-draft count, not raw source count;
- continued-cell mode may contain several sources in one Cell draft;
- label: `Registering 126 of 214 cells`;
- current label is Cell name or primary filename;
- increment as each draft is validated/staged inside the transaction;
- do not display a draft as durably registered until the transaction commits;
- if a later failure rolls back, the job becomes failed and the UI says:
  `Import failed. No partial Cell registration was kept.`
- after commit, mark the registration job completed before the scientific-cache handoff.

For a multi-source Cell, optional secondary text may show source count, but the primary progress
unit remains Cell drafts.

## Frontend component

Create:

```text
frontend/src/components/ImportProgressPanel.tsx
frontend/src/importProgress.ts
```

Do not rename the generic recognition component unless reuse is trivial and behaviorally safe.

Panel requirements:

- stage title;
- one-sentence explanation;
- current file/root;
- determinate `Progress` for known totals;
- striped/indeterminate presentation for unknown file total in Stage A;
- `N of M` text;
- discovered-file count in Stage A;
- ETA only when supported;
- compact geometry suitable for the existing modal;
- error state with endpoint error;
- no misleading 100% while the request is still finalizing.

While a stage is active:

- disable repeated submission;
- do not allow closing the modal in a way that implies the operation was cancelled;
- preserve existing content under an overlay/panel where practical;
- polling stops on success, error, or unmount;
- an unavailable job token falls back to accurate stage copy and a non-determinate loader rather
  than blocking forever.

## ETA and history

Use `frontend/src/importTiming.ts` from 035.4.

Live ETA:

- require at least 3 completed items and at least 2 seconds elapsed;
- use completed bytes when available;
- otherwise use completed item count;
- display a range with friendly rounding;
- update no more frequently than progress polling;
- never show negative, infinite, or zero remaining time before completion;
- label it `Estimated remaining`.

After a successful complete blocking import workflow, record one history sample:

- included file count;
- total bytes;
- elapsed Stage B plus Stage C seconds;
- do not include Stage A browse/discovery time;
- do not include user metadata-editing time;
- do not include background cache time;
- do not record failed or cancelled runs.

Persist the start timestamp in the open import-session state, not globally.
