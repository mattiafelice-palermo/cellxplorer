## Goal

Measure the **actual user-visible Time/Capacity interaction path** after 050.1-050.3, identify where the remaining latency lives, and make an evidence-backed decision about whether another optimization child is needed.

This child is deliberately a **profiling and decision-gate child**, not a preselected optimization. It must not add a multiresolution overview, RAM LRU, neighbor prefetch, response compression scheme, Plotly rewrite, worker architecture, or other acceleration merely because one might help.

The governing question is:

> After 050.3 removed whole-source materialization for narrow Time/Capacity requests, what now dominates the latency between a user changing the Time/Capacity view and the replacement plot becoming visibly ready?

The answer must separate backend access/calculation, response serialization/transport, frontend preparation, and Plotly render/update cost rather than reporting only one aggregate stopwatch.

## Why this child exists

050.3 proved an important structural fact: narrow requests no longer need to materialize every raw row in the selected source chain before filtering. On the approved 71,190-row golden source, the indexed path reads 1/18 groups for one cycle, 3/18 for the first 20 cycles, 14/18 for the first 150 cycles, and 18/18 for all cycles, while preserving exact selected rows and scientific output parity.

That evidence answers the storage/scientific-consumer question, but it does **not** close the user-visible performance question for three reasons.

1. `scripts/profile_time_capacity_path.py` profiles the backend scientific path with a full-detail configuration (`precision="full"`, `compact=False`, and a very high point budget). It is not the same configuration used by the interactive plot.
2. The real Time/Capacity card sends `precision: "standard"`, `compact: true`, uses the normal display point budget, then builds Plotly traces/layout in the browser.
3. The existing profiler explicitly records `frontend_profile: "not run"`. No accepted evidence currently separates response transfer, frontend trace/layout preparation, and Plotly paint/update time.

Therefore the previous provisional conclusion "050.4 not needed" is withdrawn. The correct current state is:

> 050.4 is required as a measurement/decision gate. Optimization scope remains undecided until this child produces representative end-to-end evidence.

## Locked decisions

1. **Profiling first; optimization later.** This child may add profiling instrumentation and repeatable profiling harnesses, but it must not implement the eventual optimization except for trivial instrumentation overhead fixes required to make the measurements truthful.
2. **No scientific change.** Formulas, cycle mapping, continuation semantics, protocol masking, voltage capability semantics, provenance, hidden-data behavior, units, exports, and result meaning are unchanged.
3. **No performance claim from backend-only evidence.** Structural backend counters remain valuable, but they are not sufficient to claim the original `1-3 -> 1-20` interaction is solved.
4. **Measure the production interaction shape.** At least one profiling path must use the same request configuration as the live Time/Capacity card: standard precision, compact response, current display point budget, selected voltage channel, current view/display mode, and the current React Query lifecycle.
5. **Separate stages.** The evidence must distinguish backend compute/cache service, response serialization/transport, frontend result-to-trace/layout preparation, and Plotly completion.
6. **Cache state is explicit.** Every measurement row must say whether it is an exact analysis-result cache hit, an indexed result-cache miss with prepared source layout, or a forced/observed legacy fallback. Do not mix those cases into one median.
7. **Do not defeat normal caching merely to make a benchmark dramatic.** Cold/miss runs may be prepared deliberately, but the normal warm reopen/cache-hit path must also be measured because that is the expected common case.
8. **Instrumentation is bounded and opt-in.** Production behavior must not continuously accumulate profiling records, console spam, Performance API entries, or large diagnostic payloads when profiling is disabled.
9. **No new heavyweight dependency by default.** Reuse browser `performance.now()` / User Timing APIs, existing Plotly lifecycle callbacks, existing request helpers, backend monotonic timers, and existing test infrastructure. Do not add Playwright, Selenium, a telemetry SDK, or an analytics service only for this child.
10. **No network telemetry.** Profiling data remains local. Do not send measurements to OpenAI, GitHub, an analytics provider, or any external service.
11. **No SQLite migration.** Profiling records are ephemeral or explicitly exported by the user; they do not become persistent application data.
12. **No `CALC_VERSION`, parser, canonical, result-schema, or raw-layout version bump.** Instrumentation must not alter scientific/cache meaning. If the implementation unexpectedly requires a payload-shape change on a normal scientific response, stop and re-evaluate rather than silently version it here.
13. **No automatic speculative follow-up.** This child ends with a documented decision. If another optimization is justified, author a new numeric child (normally 050.5) with scope determined by the measured dominant cost.
14. **Manual/browser evidence is valuable but must be reported truthfully.** If the implementer/reviewer environment cannot run the desktop/browser interaction, implement the instrumentation, run all automatable evidence, mark the browser matrix `NOT RUN`, and leave the final parent decision blocked until the user supplies the required local profile. Do not fabricate timings.
15. **Do not pre-implement proto-child 050.P1.** Cross-family work remains planning-only and is outside this child.

## Required profiling model

The implementation must produce one profiling record per completed request/render with at least the following conceptual fields. Exact naming may follow repository conventions, but the information must be present and unambiguous.

```ts
interface TimeCapacityInteractionProfile {
  profile_version: 1;
  analysis_id: number;
  request_id: string;
  scenario?: string;

  // request identity/context
  started_at_ms: number;
  selection_count: number;
  cycle_start: number | null;
  cycle_end: number | null;
  explicit_cycle_count: number;
  view: string;
  x_axis: string;
  display_mode: string;
  max_points_per_cell: number;
  compact: true;
  precision: "standard";

  // lifecycle/cache facts
  placeholder_was_visible: boolean;
  result_cache: "hit" | "miss" | "unknown";
  raw_access: "indexed" | "legacy" | "mixed" | "not_applicable" | "unknown";

  // backend/transport
  backend_total_ms?: number;
  backend_compute_ms?: number;
  backend_serialize_ms?: number;
  http_round_trip_ms: number;
  response_bytes?: number;

  // frontend
  frontend_result_to_plot_props_ms: number;
  plotly_update_ms: number;
  total_interaction_ms: number;

  // structural context when available
  row_groups_read?: number | "full";
  row_groups_total?: number | "full";
  raw_rows_materialized?: number;
  selected_rows_before_transforms?: number;
  returned_points?: number;
  trace_count?: number;
}
```

This is a conceptual contract, not necessarily the exact wire shape. Backend-only fields may be absent on an exact analysis-result cache hit if deriving them would require recomputation. In that case the record must explicitly say `result_cache: "hit"` rather than invent zero-cost scientific stages.

### Timing definitions

The implementation must document and test the event boundaries.

At minimum:

- **interaction start**: the current Time/Capacity data identity changes because of an applicable user/config action, not because React rerendered equivalent state;
- **HTTP round trip**: immediately before the live `post()` call until its parsed result resolves or rejects;
- **frontend result-to-plot-props**: from receipt of the resolved current result until the trace/layout inputs for the new result are ready;
- **Plotly update**: from committing the new plot data/layout to the point the Plotly wrapper reports the new figure completed, or the documented bounded equivalent if no direct callback exists;
- **total interaction**: interaction start until the new non-placeholder plot is complete and corresponds to the current request identity.

Do not mark the following as completion:

- retained placeholder becoming visible;
- React Query changing from `loading` to `fetching` while old data is still shown;
- HTTP response resolution before traces/layout and Plotly update complete;
- an unrelated rerender or style-panel resize.

### Request identity and races

Profiling must be bound to the same current request identity used for correctness. If the user changes the range again while an earlier request/render is still running:

- the superseded record may be marked `cancelled`/`superseded` and excluded from completed-scenario medians;
- it must never be attributed to the newer request;
- abort behavior from 050.1 must remain intact;
- late Plotly callbacks from an obsolete request must not close the newer profile.

The profiling code should be implemented as a small pure state machine/helper where possible so these cases can be unit tested without requiring Plotly in every test.

## Backend timing requirements

Use monotonic clocks.

The backend evidence must be able to distinguish:

1. exact persisted analysis-result cache hit;
2. result-cache miss using indexed 050.3 raw access;
3. legacy fallback when the source layout/index is unavailable or the non-waiting conversion boundary requires fallback.

For cache misses, preserve/reuse the current 050.3 stage diagnostics. At minimum retain:

- relational/source resolution;
- indexed planning or legacy full read;
- exact cycle filter/sort;
- continuous time / phase / capacity;
- derivative;
- protocol masking;
- display-coordinate/downsampling where applicable;
- selected/raw row diagnostics;
- returned point count.

Do not expose source paths, full specs, raw rows, or private data in profiling records.

### How backend diagnostics reach the profiler

Choose the smallest safe mechanism after inspecting the current route/request models. Acceptable patterns include:

- a profiling-only request flag that returns a clearly namespaced diagnostic block only when explicitly requested;
- a dedicated local profiling endpoint that calls the exact same production service/cache path;
- another existing repository pattern that preserves the production request path.

Do **not** add diagnostics unconditionally to every normal Time/Capacity response merely for convenience.

If a profiling flag adds an optional response field, keep it strictly absent for ordinary requests and document why no scientific result-schema bump is required. If current schema/type ownership makes that unsafe, prefer a dedicated profiling endpoint/side channel instead.

## Representative scenario matrix

The profiling decision must use representative interactions, not one convenient request.

### Required single-cell scenarios

Using a prepared long analysis/source comparable to the approved 71,190-row golden source:

1. **small range expansion:** `1-3 -> 1-20`;
2. **neighbor navigation:** one later cycle -> next cycle -> previous cycle;
3. **broad range:** `1-20 -> 1-150` or nearest meaningful broad range for the source;
4. **all cycles:** broad -> All cycles;
5. **return narrow:** All cycles -> one/small range;
6. **x-axis/display change:** one Time/Capacity x-axis or display-mode change using the same selected scientific rows;
7. **derivative:** one representative dQ/dV or dV/dQ configuration.

### Required cache-state scenarios

At least distinguish:

- exact result-cache hit/reopen;
- first result-cache miss with prepared indexed source layout;
- repeated nearby indexed miss if the exact result key differs;
- one legacy/fallback case if it can be produced safely without corrupting normal caches.

Do not delete the user's only offline cache or otherwise create unsafe state just to force fallback.

### Multi-cell scaling

Measure at least:

- one selected Cell;
- several selected Cells/replicates, preferably 3-5 when representative data are available.

Record actual selected cell count. Do not extrapolate multi-cell latency from a single-cell run.

### Continuation boundary

If a representative continued Cell is available, include one range that crosses a source boundary. If not available in the runnable environment, record `NOT RUN` rather than fabricating a synthetic user timing. Existing automated parity tests continue to protect continuation semantics.

## Decision rule

050.4 must end with exactly one of these outcomes, recorded in the child implementation record, child review, and Parent 050 final review.

### Outcome A — no further optimization child

Choose this when representative end-to-end interactions are already satisfactory and no distinct avoidable stage dominates. Record the evidence and close 050.4 without authoring speculative acceleration.

### Outcome B — backend selective detail remains dominant

If repeated nearby/narrow result-cache misses are still primarily limited by indexed Parquet/detail access, author a later child scoped specifically to the measured cause. Candidate techniques may include a small bounded recent-cycle working-set cache or measured neighbor prefetch, but the new spec must define memory limits/invalidation and must not make whole-cell RAM residency mandatory.

### Outcome C — broad/all-cycle detail dominates

If broad interactive views are dominated by reading/transforming exact all-cycle detail while narrow navigation is already fast, author a later child for a scientifically safe interactive overview/multiresolution representation. Full-resolution exports remain exact and must bypass the approximation.

### Outcome D — payload/serialization/transport dominates

If backend scientific work is already fast but response serialization, payload size, JSON parsing or transfer dominates, author a later child specifically for payload/transport. Do not change numerical precision or omit scientific/export data silently.

### Outcome E — frontend trace/layout/Plotly dominates

If browser preparation or Plotly update dominates, author a frontend-focused child. Reuse current components and preserve WebGL/export/artifact behavior. Do not introduce backend caches to solve a browser bottleneck.

### Mixed outcome

If two stages are independently significant, do not automatically combine them. Prefer separate later children when ownership/risk differs.
