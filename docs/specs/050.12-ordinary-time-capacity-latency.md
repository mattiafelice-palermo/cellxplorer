## Goal

Make the everyday **ordinary Time/Capacity Voltage/Current view** feel effectively immediate during warm interactive use.

The user's product target is approximately **200 ms user-visible latency** for a representative warm Time/Capacity interaction. This is a product target rather than permission to trade away correctness, provenance, deterministic ordering, bounded memory or local-first behavior.

Derivatives are **not** the optimization priority for this child. The Rust derivative results from 050.10/050.11 remain valid evidence but must not drive 050.12 architecture unless a normal Time/Capacity measurement independently justifies native work.

## Implementation record

The ordinary indexed production path now applies a request-aware raw-column
projection for standard compact responses. Time/Voltage/Current requests read
only the cycle, status, time, selected voltage, current and row-identity fields;
capacity-axis and derivative requests add the exact capacity columns they
consume. Full-detail, non-compact and legacy fallback requests retain the
historical projection and execution boundary.

Compact source provenance is now built after display downsampling. Source
boundaries are still calculated before downsampling and are always retained in
the display selection, so the returned source-cycle/position/filename/hash
arrays remain row-aligned and scientifically unchanged while discarded raw
rows no longer pay for client-bound list construction.

The implementation adds focused projection, indexed-reader, compact-parity and
bounded-provenance tests. The diagnostic runner
`scripts/profile_time_capacity_ordinary_latency.py` measures the sequential
production router/backend path over the fixture and the read-only real
Performance analysis batch with five warm repetitions, detailed backend
stages, range controls and an exact result-cache control. No new RAM cache, worker pool,
native path, migration or calculation-version change was introduced.

## Results

The mains-power command was:

```text
python scripts/profile_time_capacity_ordinary_latency.py --repetitions 5 --output tmp/050.12-ordinary-full-mains.json
```

It covered 13 ordinary workloads in each suite (fixture plus the real saved
Performance analysis batch), including 1/3/6/10/11-Cell Time and capacity
requests when available, cycles 1-3, both range-expansion controls, and exact
cache miss-then-hit controls. All 130 measured A0 samples passed scientific
digest and deterministic ordering checks; both cache controls reported equal
scientific payloads and a direct hit.

The initial O1 direct-engine diagnostic medians (retained for the before/after
optimization comparison, not the complete router boundary) were:

| workload | backend median | indexed columns | raw access | transform | provenance |
|---|---:|---:|---:|---:|---:|
| Time — 6 Cells — All | 323 ms | 6 | 68 ms | 48 ms | 10 ms |
| Time — 10 Cells — All | 554 ms | 6 | 112 ms | 81 ms | 18 ms |
| Time — 11 Cells — All | 591 ms | 6 | 125 ms | 88 ms | 20 ms |
| capacity — 6 Cells — All | 514 ms | 8 | 83 ms | 146 ms | 11 ms |

Against the accepted 050.11 real A0 baselines, these are reductions of about
45%, 47%, 46% and 31%, respectively. The compact provenance change reduced
the real 6-Cell Time provenance stage from approximately 198 ms in the
pre-change smoke measurement to approximately 10 ms; the residual dominant
stage is indexed raw read/decode. The product target of approximately 200 ms
user-visible latency was not measured in this backend-only run; browser,
HTTP/fetch/parse, frontend preparation and Plotly completion remain an
external/manual gate.

The safe O1 work therefore clears the broad-request materiality target. O2
prepared-state reuse, O3 cross-Cell execution and O4 alternate serialization
were not added because the ordinary backend already improved materially
without introducing cache identity or concurrency complexity. The next narrow
performance child, if needed, should be based on the residual indexed
Parquet/read-decode stage rather than derivatives or speculative caching.

opt-in measurement path. The ordinary profiler now calls the production
`/analyses/{id}/time-capacity` router directly. Each reported sample is a pair:
one normal unprofiled miss for the latency headline and one `profile=True` twin
for decomposition. The profiled twin records its own measurement overhead; it
is not presented as the ordinary latency.

Capacity requests use prepared phase/capacity rows, so the absent phase and
continuous-time child timers are represented by the explicit phase/capacity

decode is material but is not the dominant exclusive residual in this
reconciled table. Any next optimization should be chosen from these measured

## Accepted starting evidence

Use the corrected 050.11 A0 production-path medians as the current ordinary-path baseline:

| real application workload | current Python A0 backend median |
|---|---:|
| Time — 6 Cells — All | ~586 ms |
| Time — 10 Cells — All | ~1,052 ms |
| Time — 11 Cells — All | ~1,097 ms |
| capacity — 6 Cells — All | ~746 ms |

The corrected 050.11 native candidates do **not** materially improve ordinary Time/Capacity. Sequential Rust is neutral-to-slower overall and four-way Rayon/read-thread composition remains below the promotion threshold. Therefore the normal production path stays Python/NumPy unless this child produces new like-for-like evidence to the contrary.

050.9 also established that bounded whole-Cell Python threading can help some normal multi-Cell workloads modestly, while read-only concurrency improves the isolated read stage but generally does not materially improve the whole request. Treat those as prior evidence, not as automatic production choices.

## User-visible target and measurement boundaries

The primary target is the complete warm interaction:

```text
user changes ordinary Time/Capacity setting
    -> backend request
    -> response received/parsed
    -> frontend traces/layout prepared
    -> Plotly update complete
```

Aim for approximately **200 ms p50** on a representative warm multi-Cell interaction. Report backend and frontend shares separately; do not hide a slow backend behind retained stale content or a slow frontend behind backend-only timing.

Because installed browser timing may not be available to the implementer, the child may complete its implementation/review cycle with backend evidence plus the existing 050.4 installed profiler. Parent completion must state explicitly whether the ~200 ms user-visible target was actually measured or remains an external/manual validation target.

## Locked decisions

1. **Ordinary Time/Capacity is primary.** Optimize `view=voltage_current` Time and capacity interactions before derivative work.
2. **Profile the real production path first.** Do not optimize from the 050.11 benchmark mirror alone.
3. **Exact result-cache hits remain direct.** An exact persisted/cache hit must bypass new worker/reuse/native machinery.
4. **Do less work before doing the same work faster.** Remove unnecessary transforms, copies, conversions and response fields before adding concurrency or native code.
5. **Scientific calculations and identity stay authoritative in the existing backend services.** Preserve parser/calc versions, source ordering, continuation semantics, protocol masking, voltage-channel semantics, provenance and existing tolerance/golden contracts.
6. **No unbounded RAM cache.** Any new reusable in-memory preparation layer requires measured justification, a byte-bounded eviction policy, explicit data/version identity, deterministic invalidation and tests. Do not cache whole user datasets indefinitely.
7. **No speculative prefetch.** Reuse may only follow an actual request or existing offline preparation lifecycle.
8. **No N+1 relational/source access.** Owner relational state is resolved once; workers never share a live SQLAlchemy `Session`.
9. **Bound concurrency.** Reuse the smallest measured useful worker count and keep NumPy/BLAS/PyArrow/Rayon oversubscription controlled.
10. **No Rust-by-default for ordinary Time/Capacity.** Native normal execution is rejected unless a new complete-boundary benchmark demonstrates a material stable win after copy/IPC/assembly cost.
11. **Do not broadly refactor `AnalysisPage.tsx`.** Frontend changes, if later justified by measurement, must extract one coherent responsibility at a time and preserve saved-plot/autosave/draft behavior.
12. **Derivatives remain regression coverage only** unless required to ensure a shared-path optimization did not break them.

## Phase 1 — production ordinary-path decomposition

Instrument or extend the existing opt-in 050 profiling so an ordinary request can be decomposed without materially perturbing it. At minimum separate:

- owner relational/request setup;
- indexed raw access / Parquet read-decode;
- exact cycle filter + stable sort;
- continuous-Time transform;
- source provenance column construction;
- source-boundary construction;
- phase classification / prepared alignment where needed;
- phase-capacity and normalization work where needed;
- voltage/current and plot-array materialization/copies;
- display-coordinate calculation;
- display downsampling;
- JSON-safe numeric/text projection into trace payloads;
- multi-Cell result merge / rendering metadata;
- final backend serialization;
- HTTP/fetch/parse, frontend trace/layout preparation and Plotly completion when installed evidence is available.

Report p50 plus a small range/tail from at least five comparable warm repetitions. Do not combine stages whose optimization mechanism is materially different.

## Phase 2 — optimize in measured order

Apply only changes justified by Phase 1, in this priority order.

### O1 — remove ordinary-path work that is not consumed

First eliminate avoidable work on compact ordinary requests. Examples to investigate, not assumptions:

- derivative-only arrays or helpers executed for `voltage_current`;
- capacity/specific/areal transforms not consumed by the selected x-axis;
- repeated `DataFrame.copy()` / NumPy `.copy()` operations where immutable/owned arrays already satisfy downstream requirements;
- repeated source-boundary/provenance materialization where a cheaper equivalent production representation already exists;
- JSON-safe conversion of fields omitted from the compact ordinary response;
- building both raw and display representations when only the bounded display representation is returned.

Every removal must preserve exact response semantics for fields that remain part of the contract.

### O2 — reuse already prepared state across nearby warm interactions, only if measured necessary

The motivating interaction is a user changing ordinary range/settings while the underlying Cells and source identities remain unchanged, for example cycles 1-3 -> 1-20.

Before adding a new reuse layer, prove from Phase 1 that repeated raw-read/prepare work is a material share of the interaction and prototype the expected complete-request saving.

If a reusable prepared-state cache is justified, it must:

- be process-local and explicitly byte-bounded;
- use a complete immutable identity including Cell/source order and hashes, effective parser identity, calculation version, relevant voltage-channel/source interpretation, and any preparation setting that changes the stored representation;
- never treat a broader/narrower cycle selection as scientific identity if the stored representation is intentionally range-independent;
- invalidate on source replacement, parser/calc identity change and application/database lifecycle reset;
- avoid storing SQLAlchemy objects or live file handles;
- expose hit/miss/eviction diagnostics in opt-in profiling;
- preserve exact result-cache precedence: exact final-result hits still bypass this layer entirely;
- have focused byte-budget, identity, invalidation and scientific-parity tests.

Do not introduce this cache if removing ordinary-path work and existing disk-prepared data are already sufficient.

### O3 — bounded cross-Cell execution, only after O1/O2

If independent per-Cell work remains dominant after O1/O2, re-evaluate the accepted 050.9 whole-Cell threading boundary with the optimized ordinary path.

- Compare sequential vs 2 workers first; use 4 only if 2 does not capture most of the gain.
- Resolve relational/request state once in the owner.
- Worker inputs are immutable descriptors/cache plans; no shared ORM/session.
- Preserve selection order on merge.
- Reject the candidate if representative complete-request gain is <5% or if 1-Cell/small-range median regresses >10%.
- Do not combine read threads and whole-Cell threads unless the optimized-path evidence shows a distinct additional gain and oversubscription is controlled.

### O4 — response projection / serialization

If response projection or serialization becomes a major residual after O1-O3:

- measure Python-object/list conversion separately from actual JSON encoding;
- reduce intermediate Python-object churn before adding a dependency;
- preserve the existing compact response schema unless a separate explicit API/schema change is justified;
- do not silently downsample scientific export/full-resolution paths;
- any alternate encoder must preserve finite/non-finite handling and exact client contract.

## Decision thresholds

A production optimization is promoted when it provides a stable **>=5% complete-backend** improvement on the workload class it targets, with no unacceptable small-request regression and exact scientific parity.

Prefer changes that save **tens to hundreds of milliseconds** over changes that make an already-sub-millisecond numeric kernel faster.

For the overall child, aim for at least a **30% reduction** from the accepted real ordinary-path baselines on representative broad 6- and 10/11-Cell requests. If the safe measured changes do not reach that milestone, do not force risky architecture; record the residual stage decomposition and author the next narrow child against the largest remaining bottleneck.

The ~200 ms user-visible target remains the product goal even if this child is only the first implementation step toward it.

## Explicit out of scope

- productionizing the 050.10/050.11 derivative Rust kernel merely because it wins derivative workloads;
- changing derivative mathematics, smoothing, thresholds or scientific meaning;
- unbounded/all-CPU concurrency;
- per-request process spawning;
- speculative prefetch;
- a whole-dataset permanent RAM cache;
- new persistent SQLite/Parquet scientific cache schema unless separately specified after evidence;
- migration or `CALC_VERSION` changes unless scientific output meaning actually changes;
- adaptive zoom/progressive streaming from planning proto children;
- cross-family Cycles/Steps/DCIR/Chargeability/Rate Capability work;
- broad AnalysisPage refactoring;
- unrelated UI redesign.

## Acceptance criteria

- Ordinary Time/Capacity is demonstrably the optimized path; derivative work is secondary regression coverage.
- The real production ordinary path has a stage-level before/after decomposition.
- At least one material ordinary-path bottleneck is reduced without scientific/provenance/cache-identity regression, or the child records why no safe material implementation was possible and identifies the next largest measured bottleneck.
- Representative broad ordinary requests improve by the measured thresholds above, or a narrower follow-up child is authored from the residual evidence rather than forcing a losing optimization.
- Exact result-cache reopening remains direct and unchanged.
- No unbounded worker/cache behavior is introduced.
