# Spec 054.1 — Channel-isolated updater shutdown

> Repository snapshot used while drafting: `main` at `e396a32f86a4bfd8f4ed9c547096a08bc397d911` (2026-08-26).
> Re-verify anchors against the implementation branch before coding, especially if Spec 053 has merged.

## Parent

`054-updater-lifecycle-hardening.md`

## Goal

Guarantee that an updater or installer for one CellXplorer release channel can stop **only** the frontend/backend processes owned by that same installed application.

The concrete failure to prevent is:

> Starting an Alpha update closes a running Beta or Stable installation, or vice versa.

This child is primarily a lifecycle/packaging correctness task. It must establish a mechanically testable ownership rule before Spec 054.2 changes the updater install mode.

## Locked decisions

- Process ownership is installation-specific, not executable-name-specific.
- The preferred Windows installer ownership signal is the process executable path being under the target install directory (`$INSTDIR`).
- Never use blanket `taskkill /IM cellxplorer*.exe`, shared product-name matching, port matching, or broad command-line substring matching as the primary shutdown mechanism.
- The running Tauri app may stop the backend child it spawned because that child is held in its own `BackendChild` state. Killing that PID tree is local to the current app instance.
- Stable, Beta, and Alpha must have distinct application/install identities after Spec 053. This child consumes those identities; it must not create a parallel channel model.
- Stale/orphaned backend processes from the **target installation** should still be reaped so locked executable files do not block installation.
- Installer/uninstaller helper processes and their protected ancestor chain must never be killed by their own cleanup helper.
- Failure to establish a clean target-installation process state should abort the update with an actionable error rather than broadening the kill scope.
- No user data directory is part of process ownership. A data-root path must never be used as the criterion for terminating a process.

## Current behavior and anchors

### Installer-side cleanup

`src-tauri/nsis-hooks.nsh` currently calls:

- `KillInstallationProcesses`
- `NSIS_HOOK_PREINSTALL`
- `NSIS_HOOK_PREUNINSTALL`

The macro invokes:

`src-tauri/kill_installation_processes.ps1`

with `$INSTDIR`.

The PowerShell helper currently:

- normalizes `$InstallDir`;
- protects its ancestor process chain;
- finds processes whose `ExecutablePath` starts with the target installation directory;
- optionally restricts uninstall cleanup to backend processes;
- repeatedly kills matching process trees until a quiet period is observed or a timeout is reached.

That is the correct base behavior and should be generalized/verified, not replaced with a name-based solution.

### Running-app cleanup

`src-tauri/src/main.rs` currently contains:

- `struct BackendChild(Mutex<Option<CommandChild>>)`
- `stop_backend(app)`
- `prepare_exit_for_update(app)`

On Windows, `stop_backend` uses `taskkill /F /T /PID <tracked child pid>` and then calls the Tauri shell child's `kill()`.

This is expected to affect only the backend started by the current Tauri instance.

### Channel identity

At the drafting snapshot `main` has Stable and Beta in `src-tauri/src/app_channel.rs`. Spec 053 adds/owns Alpha. Rebase or merge as needed so this child verifies the final Stable/Beta/Alpha identity model.

## Target behavior

### A. Concurrent installed channels

Given Stable, Beta, and Alpha are installed in their own configured install locations:

- all three may be launched concurrently;
- each may have its own Tauri frontend and Python backend alive;
- invoking update installation for channel X may terminate channel X's own frontend/backend as needed;
- channels Y and Z remain alive and usable.

This applies equally to:

- Stable update while Beta/Alpha run;
- Beta update while Stable/Alpha run;
- Alpha update while Stable/Beta run.

### B. Target-installation stale processes

If an old backend from the target installation remains alive after its frontend has gone away:

- installer cleanup should identify it by executable path under the target `$INSTDIR`;
- it may be terminated;
- processes under another channel's install directory must not match.

### C. Same executable names

Assume the channels may continue to share binary names such as:

- `cellxplorer.exe`;
- `cellxplorer-backend.exe`.

Correctness must not depend on renaming those binaries.

### D. Failure

If a target-owned process cannot be stopped within the existing bounded wait:

- abort the install/update;
- preserve the existing clear failure behavior;
- do not retry using broader process matching;
- do not kill unrelated channels.

## Implementation requirements

### 1. Audit every shutdown path

Inspect all Windows release/update/uninstall code for process termination, including at minimum:

- `src-tauri/src/main.rs`;
- `src-tauri/src/app_updates.rs`;
- `src-tauri/nsis-hooks.nsh`;
- `src-tauri/kill_installation_processes.ps1`;
- custom NSIS template/hooks;
- Spec 053 Alpha packaging/configuration;
- release scripts that may launch installers.

Remove or constrain any path that kills CellXplorer by shared image/product name.

### 2. Keep installer ownership explicit

The PowerShell cleanup helper should continue to receive the exact target install directory from NSIS.

If helper code is refactored, make the ownership predicate testable as a pure or separable function where practical:

`process executable path belongs to install root`

with case-insensitive Windows path semantics and a directory-boundary-safe comparison.

Avoid a naive prefix comparison that would make:

- `C:\Apps\CellXplorer`
match
- `C:\Apps\CellXplorer Beta`

unless the normalized root includes the separator boundary.

The current helper already appends a trailing separator; preserve equivalent protection.

### 3. Preserve protected process ancestry

The cleanup helper must continue excluding:

- itself;
- its installer/uninstaller ancestor chain.

Do not create a self-termination race.

### 4. Preserve backend PID-tree shutdown

Do not replace the current tracked-PID `stop_backend()` with a shared-name kill.

If Spec 053 changes backend launch handling, keep the invariant that the Tauri instance owns and terminates only the process tree it launched.

### 5. Do not use ports as ownership

The backend uses dynamically allocated loopback ports. Ports are not sufficiently durable or safe as installer ownership markers and must not become the kill criterion.

## Tests

Add focused automated coverage where repository tooling permits.

### Rust/unit coverage

Test any extracted channel/install-identity helpers introduced here.

At minimum prove:

- Stable/Beta/Alpha resolve to distinct identifiers/product/install identities supplied by the channel configuration;

### PowerShell/helper coverage

Prefer a testable helper/predicate or script-level test that demonstrates:

- a process path under the exact target install root matches;
- a sibling channel install path does not;
- path matching is case-insensitive on Windows;
- prefix collisions do not match;
- protected PIDs are excluded;
- `-BackendOnly` restricts matches appropriately.

If the repository has no PowerShell test harness, keep logic simple and cover it through packaged manual verification below; do not add a large testing framework only for this spec.

## Packaged manual verification

This child cannot be considered fully verified from dev mode alone.

On Windows:

1. install at least two channels, preferably Stable + Beta + Alpha when Spec 053 is available;
2. launch both/all channels;
3. confirm each frontend has its own backend alive;
4. trigger/install an update for one target channel;
5. verify the target installation can stop its own processes and update;
6. verify every non-target frontend remains open;
7. verify every non-target backend remains alive and responsive;
8. repeat with a different target channel;
9. test an orphan target backend if practical;
10. confirm no unrelated process is terminated.

Record exactly which matrix rows were performed.

## Acceptance criteria

- No updater/installer path kills CellXplorer processes by shared executable image name.
- Installer cleanup is constrained to the exact target installation directory.
- Current-app backend shutdown remains PID-tree-scoped to that app instance.
- Stable/Beta/Alpha concurrent-run behavior is preserved.
- Updating one channel does not close another channel's frontend.
- Updating one channel does not kill another channel's backend.
- Stale processes belonging to the target installation can still be reaped.
- Cleanup failure aborts safely without broadening scope.
- Automated focused tests pass.
- Canonical preflight passes.
- Packaged Windows verification is recorded.

## Out of scope

- changing updater UI;
- changing updater install mode;
- automatic relaunch redesign;
- release publication;
- data migration/reset policy;
- renaming binaries solely to make process ownership easier.
