# 052.6 — Time/Capacity drag stall and preview activity noise

**Status:** Active child — implementable
**Parent:** Spec 052 — Time/Capacity cycle navigation
**Repository:** `mattiafelice-palermo/cellxplorer`
**Branch:** `feature/time-capacity-cycle-navigation`
**Reason for child:** two user-reported defects observed while dragging the cycle slider in the running application — the plot standing still for hundreds of cycles, and the activity feed continuously reloading. Both were reproduced in the browser and fixed here.

This child closes the acceptance criterion child 052.2 recorded as **NOT RUN**: "actual browser proof that sustained pointer movement visibly advances the plot before release".

## Reported symptoms

1. Dragging the slider across hundreds of cycles leaves the plot visibly still.
2. The activity button/status shows continuous reloading during a drag.

## Root causes

### C1 — Workers deferred their scientific imports to the first real job

`_warm_pool` proved liveness with `_worker_ping`, which returned the worker PID after importing `time_capacity_workers`. That module's top level imports only numpy — `pandas`, `pyarrow`, `analysis_engine` and `time_capacity_path` are all imported lazily inside the functions that use them.

The warmup therefore proved each worker process *existed* while leaving it unable to do work without first paying the scientific-stack import. That cost landed on the first **real** job in each worker, which is the first dispatch of the first drag.

Measured in the browser against the running application, cold backend, six-Cell selection, 324 cycles:

| | first request | slowest | max gap between requests |
|---|---|---|---|
| before | **1597 ms** | 1597 ms | ~1660 ms |
| after | **69 ms** | 70 ms | 144 ms |

Because child 052.2 admits one moving request at a time and holds the newest range in `pendingRange`, the entire drag waits on that first request. During the measured 1.6 s stall the pointer travelled from cycle 6 to cycle 173 with no plot movement — exactly the reported symptom. The next admitted range was 173, so the plot then jumped rather than tracked.

This also explains an unexplained outlier recorded during 052.4: a one-Cell dispatch measured ~1122 ms in one sweep and ~12 ms in focused diagnostics. The slow sweep was the first real job in a freshly warmed pool.

### C2 — Every transient preview opened and closed an activity entry

Child 052.3 made moving previews non-persistent, so they always miss the result cache. The route opens an activity entry on any cache miss carrying a `job_token`, and the frontend sends a token on every request.

A sustained drag therefore created and finished roughly thirty activity entries per second — an INSERT plus an UPDATE each — and flooded the activity feed with work the user never asked to see. 052.3 did not introduce the job-opening path, but by making previews permanently uncacheable it made the churn constant rather than occasional.

## Stages

### Stage 1 — Warm the workers with the imports a real job needs

- `_worker_ping` imports `analysis_engine` and `time_capacity_path` before acknowledging;
- the import is guarded so a failure degrades to the previous behaviour rather than failing warmup;
- the existing acknowledgement hold from 052.4 is preserved, so distinct-PID proof is unaffected;
- the cost moves into the asynchronous startup warmup thread, where nothing waits on it.

### Stage 2 — Keep transient previews out of the activity log

- the route opens a compute job only when `req.persist` is true;
- committed ranges and idle-promoted full-resolution previews still report themselves exactly as before;
- `_open_compute_job` now also receives the 052.5 request context instead of re-resolving the selection.

## Non-goals

- No change to the navigator's cadence, resolution, or backpressure policy.
- No change to scientific transforms or cache identity.

## Verification

Reproduced and verified in the running application (backend on port 8642, real library, "Performance analysis", five Cells, 324 cycles) by dispatching a synthetic 3-second pointer drag across the full slider width and recording every `/time-capacity` request plus the Plotly trace contents.

| | before | after |
|---|---|---|
| first request latency (cold backend) | 1597 ms | **69 ms** |
| slowest request in the drag | 1597 ms | **70 ms** |
| longest gap with no plot update | ~1660 ms | **144 ms** |
| requests completed in a 3 s drag | 9 | **42** |
| plot updates during the drag | stalled, then jumped 6 → 173 | tracked continuously |
| activity entries created by the drag | one per request | **0** |

Warm-state behaviour was also captured before the fix (41 requests, 20–59 ms each, 32 plot updates), confirming the defect was specific to the first dispatch rather than steady state.

- canonical preflight: **PASS**, 4/4 stages;
- browser/manual acceptance: **RUN** — this is the first child in the 052 series able to record that truthfully for the drag path.
