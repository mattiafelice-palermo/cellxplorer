## Goal

Stop parsing every staged source merely to prepare previews the user may never inspect. Preview only
the active source, reuse the inspected checksum safely, and finish the blocking import flow after
relational registration rather than after scientific cache completion.

## Current behavior to verify

At the authoring baseline:

- inspection success builds drafts;
- `added.forEach(loadPreview)` starts a preview for every added file;
- `/api/imports/preview` / `build_capacity_preview` computes a hash and uses
  `cache.build_write_behind`;
- cache jobs later wait for pending writes and reuse valid caches;
- final import already queues cache preparation after relational creation.

Verify how the current code represents multi-source Cells and use the same active-source concept.

## Locked preview state

Every staged source has explicit preview state:

```ts
type ImportPreviewState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "ready"; preview: ImportPreviewResult }
  | { status: "error"; message: string };
```

Rules:

- Newly inspected sources start `idle`.
- Only the active staged source starts a preview request.
- Switching to another source starts its preview if still idle.
- Returning to a ready source reuses the loaded result.
- Returning to an error source shows the error and offers explicit Retry.
- Do not preload adjacent sources in this child.
- Exact duplicates excluded in separate-cell mode do not auto-preview.
- A removed source cannot receive a late result back into state.
- Continued-cell mode requests a preview only for its active source.
- Raw-data preview follows the same active-source/lazy policy if it currently starts eagerly.

Remove every batch-wide `forEach(loadPreview)` or equivalent effect.

## Preview identity request

Extend preview request:

```json
{
  "staged_name": "...",
  "source_path": "C:\\...",
  "expected_hash": "...",
  "expected_size": 123,
  "expected_mtime_ns": 123456789
}
```

Backend rule:

1. resolve and stat the path;
2. if size and `mtime_ns` equal the inspected fingerprint, use `expected_hash` as the verified
   cache key for this request;
3. if the fingerprint differs, compute a fresh hash;
4. if fresh hash differs from `expected_hash`, return structured 409/source-changed detail and
   require reinspection;
5. if fresh hash matches, continue with the fresh verified identity;
6. never write a cache under an unverified stale identity.

Refactor:

```python
def build_capacity_preview(path: Path, file_hash: str | None = None) -> tuple[dict | None, str | None]:
    ...
```

so it does not recompute a checksum when a verified hash is supplied.

A matching size/mtime fingerprint is a fast unchanged-file guard within one open import session. The
full checksum from 035.7 remains the inspected content identity; final registration still performs
its own integrity proof.

## Frontend query/cache key

Use a query or request cache keyed by inspected content identity, not only path:

```text
["import-capacity-preview", expectedHash]
```

Include path/fingerprint where needed to avoid treating two currently different local files as one
mutable request. Requirements:

- a changed file does not reuse an old preview;
- identical already-loaded content is not parsed twice within the open modal;
- cancellation/late results are scoped safely;
- close/reset of the import session removes only disposable modal state, not the backend scientific
  cache.

## Capacity-cache behavior

Keep the existing versioned scientific cache path:

- `cache.build_write_behind` may parse and return cycles;
- pending cache writes remain synchronized before process workers consume them;
- existing valid cache is reused;
- no second preview-specific numerical cache or database table is added;
- display preview derives from the same per-cycle cache used later.

Do not change scientific calculation meaning. Do not bump `CALC_VERSION`.

## Registration and background handoff

After `/api/imports/cells` commits:

- return created Cells and background cache job identifier/count when available;
- mark the Stage C registration job complete;
- close the blocking import modal;
- invalidate Cells/tree/replicate/activity queries;
- show:

```text
214 cells imported. Cycling data are being prepared in the background.
```

- if every imported source already has a valid cache and no job is queued, use:
  `214 cells imported and ready.`
- do not keep the modal open until all Parquet caches finish;
- existing Cell status shows Parsing/Calculating/Ready/Error;
- Activity/background jobs remains the detailed progress surface;
- provide one normal navigation action only if the existing notification pattern supports it,
  such as `View activity`; do not open a second modal automatically.

A cache failure after commit:

- does not claim the Cell import rolled back;
- marks the corresponding `SourceFile`/cache status;
- appears in Activity/background jobs;
- remains retryable through existing cache/source workflows.

## Continued-cell behavior

For one continued Cell with multiple sources:

- registration success refers to one Cell, not source count;
- every new source is queued for cache preparation according to the current cache-preparation contract;
- existing Analysis availability guards remain effective until all required
  sources are usable;
- do not present a partially cached chain as fully ready.

- cache write-behind uses the verified hash;

- response returns before mocked cache workers complete;
- cache failure after commit leaves registered Cell intact with error status;
- no `CALC_VERSION` change.
