## Goal

Apply the performance lessons proven by 050.1-050.15 to the other analysis families **without changing their scientific meaning**.

Families in scope:

- **Cycles** — reference/control only; change it only if a genuinely shared cache helper requires a compatible edit.
- **Steps**
- **DCIR**
- **Chargeability**
- **Rate Capability / C-rate**

The withdrawn 050.8 implementation and `050.P7` are historical evidence only. **Do not cherry-pick or restore `f76ace...`.** Re-measure the current branch and implement only the mechanisms justified now.

Current production differences from optimized Time/Capacity are important:

1. Steps/DCIR/Chargeability/Rate Capability still load parsed result objects on exact cache hits and then serialize them again; they do not yet use the direct stored-body splice fast path used by Cycles/Time-Capacity.
2. `analysis_cache.result_key()` resolves selection, sources, parser identities and scalar metadata, then the family compute functions resolve much of the same request state again on a miss.
3. Steps/DCIR still materialize complete stitched raw sources before selecting protocol detail; Chargeability and Rate Capability call `cache.load_raw()` source-by-source before extracting a comparatively small set of protocol events.
4. Protocol-derived families remain **fail-closed for multi-source Cells** through `protocol_analysis_guard`. This child must not change that safety rule.

## Locked implementation order

### A. Measure the current production boundary once

Create one focused cross-family profiler. Use the real production router/service paths, not reconstructed microbenchmarks.

For each family record:

- exact persisted cache-hit complete-route p50;
- forced cache-miss complete-route p50;
- 1-Cell and representative multi-Cell workload (prefer 6 Cells when the existing fixture/corpus can represent it truthfully);
- result bytes;
- raw rows physically/materially read on a miss;
- owner/cache-key setup, raw read/materialization, scientific extraction, cache persistence and response serialization where measurable;
- exact scientific/order parity against the existing path.

Use **3 warm repetitions**. Do not rerun a passing matrix for confidence. Keep each focused benchmark invocation below ~60 s where practical. Existing scientific fixtures/corpora may be cloned for scale; do not invent unsupported protocol semantics just to make a benchmark.

### B. Productionize the two shared low-risk wins

These are required unless measurement proves they are already effectively present.

#### B1. Direct exact-cache-hit response

For Steps, DCIR, Chargeability and Rate Capability, exact persisted result-cache hits must follow the same principle already proven for Cycles/Time-Capacity:

```text
exact key
  -> load stored body bytes
  -> splice only current availability/cache-status/data-signature fields
  -> return
```

An exact hit must not:

- enter the family scientific compute function;
- read raw/cycle Parquet;
- dispatch worker processes;
- parse and fully re-encode the large cached scientific body merely to serve it.

Keep the existing legacy-object upgrade fallback for old cache entries where required.

#### B2. One request-local owner context

Resolve the following once per cache miss and reuse it for cache identity **and** family computation:

- selection units / missing refs;
- unique Cells and labels/group context;
- ordered SourceFiles;
- resolved per-source parser identities;
- scalar metadata needed by the family.

The exact implementation shape may be a small immutable request context/helper, but the constraints are locked:

- **request-local only** — no new cross-request RAM cache;
- no live SQLAlchemy Session/ORM object crosses a process boundary;
- do not change scientific cache identity;
- existing direct service callers/tests may retain a safe fallback that resolves context internally;
- do not broadly refactor `analysis_engine.py` merely to create architectural symmetry.

Re-measure after B before adding family-specific machinery.

### C. Add selective raw-detail access only where the post-B profile justifies it

For a family, continue to C only when its representative cache miss still has either:

- full raw materialization >= **30 ms**, or
- full raw materialization >= **25%** of complete-route p50.

Otherwise leave that family's raw path unchanged.

If at least one family qualifies, extend the existing physical raw-layout sidecar with an optional, regenerable **`step_index -> row_groups`** mapping and one exact step reader. This is physical access metadata, not scientific data.

Required behavior:

- build from canonical cache bytes / an already available canonical frame; **never reopen original source files on the interactive request path** merely to make the index;
- interactive requests do not wait for index preparation;
- missing/stale/corrupt/busy detail metadata immediately falls back to the current full-raw path;
- read only requested columns from implicated row groups, then filter the exact requested `step_index` values;
- raw replacement invalidates/rebuilds the access metadata by the existing physical-layout lifecycle;
- no SQLite migration and no `CALC_VERSION` bump.

Family planners remain family-owned:

- **Steps:** exact protocol target step indices already selected for the configured series.
- **DCIR:** exact confirmed rest + pulse step indices; retain every row needed by current adjacency/completeness/resistance logic.
- **Chargeability:** candidate measurement step plus the exact reference-capacity step(s) consumed by the existing extractor. Do not change candidate detection or SoC/reference semantics.
- **Rate Capability:** exact charge/discharge measurement/reference steps and any CC/CV/CCCV companion rows required by current cutoff/completion validation. Do not simplify the scientific pairing grammar.

Selective access is promoted per family only if it improves the **complete route by >=15% or >=20 ms** on the representative miss workload and preserves exact payload semantics. A large row-count reduction without wall-time benefit is not a win.

### D. Decide, but do not force, cross-Cell multiprocessing

After B/C, measure the remaining per-Cell scientific/extraction boundary for any family whose representative multi-Cell miss is still > **150 ms**.

A 2/4-process control is allowed using immutable per-Cell descriptors/results, following the 050.14 safety rules:

- owner process keeps SQLite/ORM ownership;
- do not pickle complete DataFrames into workers;
- deterministic selection/order merge;
- include real result IPC in timing;
- exact scientific/provenance parity;
- small 1-Cell control included.

**Do not create a second permanently resident process pool and do not refactor/replace the proven Time/Capacity pool in 050.16.** If a process candidate gives >=15% complete-route improvement after B/C but safe production reuse would require a significant pool-lifecycle refactor, record the measured result and recommend a separate 050.17 child instead of forcing it into this child.

## Scientific and product invariants

- No formula, protocol-recognition rule, cutoff rule, normalization, sign convention, fingerprint, axis value or export value changes.
- Preserve deterministic Cell/series/occurrence order and provenance.
- Preserve all current saved-plot, thumbnail and portable-report behavior.
- Preserve current `protocol_analysis_guard` multi-source fail-closed behavior for Steps/DCIR/Chargeability/Rate Capability.
- Cycles remains the prepared/cache-native control; do not route it through raw-detail access for symmetry.
- Do not change Time/Capacity behavior except for a truly shared helper with regression proof.
- No Rust/PyO3/Rayon, Plotly work, progressive streaming, adjacent-cycle prefetch, cache write-behind redesign, new JSON dependency, or broad Analysis editor refactor.
- Bump a per-family `RESULT_SCHEMA_VERSIONS` entry only if that family's persisted response shape actually changes. Do not bump `CALC_VERSION` for equivalent performance work.

Required focused scientific coverage includes the existing Steps/DCIR/Chargeability/Rate Capability tests, relevant analysis-cache tests, protocol/corpus tests, and golden analysis where the touched path participates.

For every productionized optimization:

- compare optimized miss with forced legacy/serial behavior after removing only volatile fields (`computed_at`, cache status/signatures as appropriate);
- exact cache miss -> hit returns the same scientific payload;
- exact hit proves no raw/scientific compute path is entered;
- multi-source protocol-derived selections still fail closed exactly as before;
- cache deletion/corrupt optional access metadata falls back safely;
- no original source-file read is introduced on the interactive path.

## Acceptance outcome

050.16 is complete when:

1. exact cache-hit serving for the four protocol-derived families is direct and bypasses scientific/raw work;
2. cache misses do not repeat avoidable owner-side relational/source/scalar resolution;
3. every family that still qualified for selective raw access has either a productionized measured win or an explicit measured rejection;
4. Cycles and all four protocol-derived families retain exact scientific/cache/provenance behavior;
5. any remaining case >150 ms has a measured explanation and, only if justified, a narrowly scoped recommendation for the next child rather than speculative architecture.

## Implementation record

The measurements below use three warm repetitions of the production routes with one-Cell and representative six-Cell fixture workloads. The six-Cell fixture uses content-identical, source-distinct copies so relational ownership and ordering remain real without pretending that unrelated scientific files form one Cell. Times are complete-route p50 milliseconds; `1/6` means one Cell / six Cells.

| Family | baseline hit | baseline miss | post-B miss | post-C miss if used | raw rows/groups change | final decision |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| Steps | 20.6 / 25.7 | 64.1 / 329.9 | 54.5 / 292.9 | 35.9 / 192.0 | 71,190 / 427,140 full rows to 4,096 / 24,576 physical rows; 1 / 6 groups | Promote selective step access |
| DCIR | 17.3 / 26.2 | 249.6 / 1,527.5 | 243.9 / 1,494.1 | 72.8 / 403.1 | 157,354 / 944,124 full rows to 57,344 / 344,064 physical rows; 14 / 84 groups | Promote selective rest/pulse access |
| Chargeability | 18.9 / 24.2 | 43.9 / 197.2 | 38.9 / 201.8 | — | 20,491 / 122,946 unchanged; raw stage 5.0 / 27.7 ms, below the selective-access thresholds | Retain full raw path; C rejected |
| Rate Capability | 17.8 / 26.4 | 226.5 / 1,296.3 | 228.9 / 1,311.0 | — | 20,491 / 122,946 unchanged; raw stage 4.7 / 26.3 ms, below the selective-access thresholds | Retain full raw path; C rejected |

Modern cache hits for all four families performed the request-local selection/context and key work, then spliced the stored body and current availability badges without entering family computation, reading raw Parquet, or serializing the scientific response. The legacy full-raw control remained parity-equivalent: Steps improved from 56.4 to 35.9 ms (one Cell) and 285.5 to 192.0 ms (six Cells); DCIR improved from 249.6 to 72.8 ms and 1,439.6 to 403.1 ms. Scientific/order digests were equal in every comparison.

The optional raw-detail index was promoted only for Steps and DCIR. It preserved exact miss-to-hit payload parity, source cycle labels, timestamps, record-index gaps, and protocol occurrence/completeness behavior. Chargeability and Rate Capability did not meet the representative raw-materialization threshold, so their existing full-raw path remains the measured choice.

The D process controls used immutable per-Cell descriptors/results and included real result IPC. All scientific parity arrays were true, but the disposable process controls were slower than serial execution:

| Family | serial six-Cell wall | 2 processes | 4 processes | decision |
| --- | ---: | ---: | ---: | --- |
| Chargeability | 230.6 ms | 2,004.5 ms | 2,284.2 ms | Reject |
| DCIR | 534.2 ms | 2,018.7 ms | 2,327.5 ms | Reject |
| Rate Capability | 1,352.4 ms | 2,532.2 ms | 2,763.9 ms | Reject |
| Steps | 324.8 ms | 1,930.9 ms | 2,153.3 ms | Reject |

No separate 050.17 child is justified by these controls. Focused backend tests and the profiler passed; the canonical preflight is run once at final handoff. Browser/manual verification is `NOT RUN` because this child is backend-only.

The R1/R2 review-fix tranche hardens the promoted detail path without changing its measured work: each generated raw-layout sidecar now carries bounded per-row-group step facts and a detail fingerprint, so a semantically inconsistent map falls back before selective science; the non-waiting raw-layout lock remains held through index validation, row-group selection, Parquet access and filtering. Focused parity/safety tests and the final preflight passed. The three-warm-repetition benchmark was not rerun because these fixes only close corruption and TOCTOU fallback boundaries; they do not alter the selected rows or normal valid-read algorithm.
