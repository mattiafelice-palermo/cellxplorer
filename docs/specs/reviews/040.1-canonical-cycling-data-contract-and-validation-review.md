### Current-sign convention

The spec forbids assuming this from memory. The reviewer parsed
`tests/fixtures/golden_analysis/sources/cycles_time_steps.ndax` (71,190 rows) through the production
`parsing.parse_timeseries` path and grouped `current_ma` by `status`:

| status | mean | min | max | rows |
|---|---|---|---|---|
| `CC_Chg` | +3.681311 | +2.496 | +75.903 | 1,294 |
| `CCCV_Chg` | +19.248884 | +2.486 | +146.210007 | 27,775 |
| `CC_DChg` | −15.918737 | −75.903 | −2.498 | 32,479 |
| `Rest` | 0.000000 | 0.0 | 0.0 | 9,642 |

**Positive `current_ma` = charge, negative = discharge.** These figures match the implementer's
report exactly. Neither parser normalizes the sign; both pass the instrument's own convention
through (`parsing.RAW_COLUMNS`, `neware_excel` column map), so the convention is inherited rather
than imposed. Downstream consumers (`chargeability.py:353`, `rate_capability.py:368`,
`protocol.py:110/121/128`) take `abs()`, and `neware_excel._segment_capacity` branches on the status
string, so no existing production code depended on the polarity being documented.

### Status vocabulary

`CV_Chg`, `CCCV_Chg`, `CCCV_DChg`. `CV_DChg` — which appears in Parent 040's illustrative table —
occurs nowhere in `backend/` or `tests/`. The implementer correctly declined to copy the parent's

### Validation boundary

Repo-wide grep confirms `cache.py:300` (`build_write_behind`) and `cache.py:337` (`build`) are the
only runtime callers of `parsing.parse_timeseries`. The remaining caller,
`scripts/build_golden_analysis_corpus.py:259`, is a corpus-build script and not an application

`scanner.py` metadata paths reach only `read_header_metadata`. Validation therefore does not fire on

violations. This both confirms the programmed/executed distinction is real in production data and
demonstrates the rule does not false-positive on it.

## Findings

### R1 — Resolved. Documentation contradicted the implementation.

`docs/agent-knowledge/canonical-cycling-data.md` stated that `validate_raw_timeseries` is called
"inside `parsing.parse_timeseries`". It is not; it is called in `cache.build` and
`cache.build_write_behind`. The claim appeared three times, including in section 8 ("How a future
source format should map into the contract") — the section written specifically for the Parent 041
BioLogic adapter author. Following it would have produced an adapter that reaches production
unvalidated.

The text was stale from the implementer's first attempt, which did place validation in
`parse_timeseries` and was moved after it broke
`test_parser_dispatch_preserves_binary_and_excel_boundaries`. The contradiction was internal: the
implementer's own docstring at `parsing.py:99-106` already recorded the opposite.

Resolved in `bbffa2b`. All three passages now describe the real call sites, and a "Practical
consequence for a future adapter" paragraph was added stating that dispatch through
`parsing.parse_timeseries` confers no validation by itself — today's adapters are validated only
because their sole production route to a cache is `cache.build`/`cache.build_write_behind`.

### R2 — Resolved. Redundant column coercion.

`_check_numeric_column` and `_check_integer_like` each independently called
`_numeric_with_malformed_check`, so `record_index`, `cycle`, `step_index`, `step` and `total_time_s`
were coerced twice per validation — five redundant full-column passes on every cache build. Spec
035.8's review records a real source at 427,772 rows, so this was worth removing.

Resolved in `bbffa2b` by threading an optional pre-coerced series through both helpers. Reviewed as
behavior-preserving: `_check_step_index` and `_check_step` now guard column presence themselves,
which previously came from the callee's guard.

## Parent amendment (user-ratified)

`REQUIRED_CYCLING_COLUMNS` omits `timestamp`, which Parent 040's "Required core columns" table
listed as required. The reviewer verified the justification rather than accepting it: `parsing.py:120`
normalizes the column only `if "timestamp" in df.columns`, and `calc.py:293` guards its cycle
start/duration derivation identically. Nothing in current code guarantees the column exists, so
requiring it at the canonical boundary could reject a source CellXplorer supports today — which this
child's acceptance criteria forbid.

The user ratified moving `timestamp` to the canonical optional-but-standard set. Parent 040 was
amended accordingly, with the original requirement noted inline. The field's *meaning* is unchanged.

Note for 040.4: once capability metadata exists, a source that cannot produce absolute timestamps
should declare `absolute_timestamps: false` rather than communicate it by column absence.
