## Open findings

### R1 — Medium: The progressive frame is stable, but it is the wrong frame for changed request extents

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRenderingPolicy.ts`
- backend/cache/index code needed for a bounded viewport preflight
- focused frontend/backend viewport tests and profiling

**Current**

The R1 fix freezes one frame per request generation. However, that frame is captured from either:

1. the compatible retained previous complete result; or
2. the first current progressive series.

This removes repeated per-series autoscaling, but it does not solve the user's actual changed-range case. If the request changes from one cycle to another, or from cycles 1-3 to 1-20, the old frame can be stale. If the frame is taken from the first new Cell, a later Cell may have a much longer X duration or wider Y span. The code therefore either starts from a stale/too-narrow frame or relies on terminal reconciliation.

**Target**

For automatic axes, establish a conservative viewport for the **new request** before the first new logical scientific series becomes visible, then keep that viewport fixed while series arrive. Manual zoom/ranges remain authoritative and bypass automatic viewport preflight.

The viewport preflight must be metadata-first and bounded. Prefer existing cache/index metadata and Parquet footer/row-group statistics for only the row groups implicated by the requested cycles. Do not perform a preliminary full scientific pass, materialize all selected rows solely for extrema, construct every complete trace twice, or duplicate derivative calculations.

The viewport does not need mathematically exact extrema; a conservative envelope plus deterministic frontend padding is acceptable. If trustworthy bounds cannot be obtained cheaply for a mode, preserve the streaming performance instead of adding an expensive second pass, and use the best bounded fallback with at most one final authoritative correction.

**Acceptance criteria**

- A cycle/time-range change moves the automatic X viewport once to the new request's frame before first current-series paint.
- A later Cell with longer duration does not extend/shrink X after progressive rendering starts.
- A later Cell with wider voltage/current range does not change Y/Y2/Y3 after progressive rendering starts.
- Manual zoom/ranges survive unchanged.
- Normal Voltage/Current viewport preflight uses bounded metadata/footer statistics or equivalent metadata-only access; it does not read/process the full selected scientific data twice.
- Viewport-preflight cost is instrumented/measured and shown not to materially erase the first-useful/final latency benefit of streaming.
- Derivative modes do not run dQ/dV or dV/dQ twice just to determine Y extrema.
- If a mode cannot obtain cheap trustworthy bounds, the fallback is documented and does not introduce deliberate batching or a duplicate scientific pass.
- Final complete figure remains scientifically/visually identical to the ordinary complete-result path.

### R2 — Medium: Whole-plot dimming is removed, but the user-requested trace-local fade is still absent

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- Plotly rendering helper/policy code as needed
- focused progressive-rendering tests

**Current**

The old whole-plot opacity transition is correctly removed. Newly arriving scientific series still appear immediately at their final style with no local fade.

**Target**

Implement a brief fade-in for every newly arriving logical scientific series, approximately 100-150 ms and never more than 200 ms. The fade must be presentation-only and must start immediately when the series becomes renderable.

It must not delay rendering, batch/coalesce completed scientific series for animation purposes, animate axes/layout, dim the whole figure, trigger per-arrival remount/`newPlot`, alter canonical final opacity/style, or leak into exports/save/cache/portable state. If the selected declarative ownership model cannot do this safely, return concrete evidence to review rather than silently omitting the requested fade.

**Acceptance criteria**

- Each newly arriving logical scientific series visibly transitions from local low/zero opacity to its canonical opacity in about 100-150 ms, hard maximum 200 ms.
- The series is inserted immediately; no animation timer delays event handling or waits for another series.
- Several fast arrivals remain scientifically/order-correct and are not intentionally batched.
- Axes/layout and retained/other traces do not animate or fade.
- Final trace styles/opacity equal the ordinary complete figure exactly.
- No per-arrival remount/`newPlot` is introduced and measured Plotly cost remains acceptable.

Retain Strategy A only if the measured representative evidence supports the selection rule.

**Acceptance criteria**

- Evidence records per-arrival visible timings, first useful, median/max update cost, final completion/ordinary control, update/remount/newPlot counts, zoom preservation, and final trace/legend/color/order equality.
