## Findings

### R1 — Medium: Progressive arrivals re-autoscale the plot frame on every series

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- focused frontend tests for Time/Capacity progressive rendering/layout

**Current**

Each partial arrival replaces `renderResult`, rebuilds `exportTraces`, and calls `timeCapacityLayout(renderResult, spec, exportTraces)`. `timeCapacityLayout()` derives `xRange`, `yRange`, and `y2Range` from the currently arrived Plotly traces. A later scientific series with a broader voltage/current extent therefore changes axis ranges and visibly reframes the plot. The user reproduced this when changing cycle range: the first series appears with a narrow Y range, then a later series forces the Y axis wider, producing a choppy progressive transition.

**Target**

Progressive delivery must keep the visual frame stable across later series arrivals for the same quantity/display semantics. Manual user zoom has precedence. Otherwise establish the progressive frame once and do not recompute it from every later partial series. When a compatible previous complete plot exists, reuse the applicable previous frame where this does not conflict with changed X semantics; when no compatible frame exists, establish it from the first current partial result. The terminal complete result may reconcile/autoscale once if the authoritative full extent requires it. Do not predict future scientific extents or run a preliminary full pass merely to determine axes.

**Acceptance criteria**

- A regression test feeds a second series whose Y extent is materially broader than the first and proves the partial layout's axis ranges/geometry do not change between the first and later partial arrivals.
- The same test covers stacked current axes where applicable (`y2`/`y3`) and confirms no per-arrival margin/legend/frame jump caused by partial data extent.
- Manual zoom remains unchanged across later arrivals.
- Final completion may perform at most one authoritative reconciliation; final layout/trace equality with the ordinary complete result remains exact.
- No guessed future extent, preliminary full scientific pass, batching, or per-arrival remount is introduced.

### R2 — Medium: The obsolete whole-plot translucent transition is still active

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `docs/specs/amendments/050.8-progressive-rendering-stability.md`
- focused frontend rendering-policy tests

**Current**

The plot container still sets `opacity: 0.42` whenever the query is fetching and progressive state has not yet become current, with `transition: "opacity 160ms ease"`. The user explicitly reported that this old "transparent previous version" transition is now distracting because 050.8 makes the replacement fast. It creates an unnecessary visual sequence: dim old plot → current partial plot → later series.

**Target**

Keep a compatible previous complete plot at normal opacity/readability while the new request starts. `start` must not dim it. The first current scientific series replaces the previous-generation data directly, and later series appear within the stable frame from R1. A very short trace-local opacity fade for newly arriving logical series is permitted as a presentation refinement only if it starts immediately, introduces no timer delay/batching, does not animate or dim the whole figure, does not remount Plotly, and has no material rendering regression. If that cannot be implemented safely with the selected Plotly ownership model, immediate trace appearance is preferable; the whole-plot dim must still be removed.

**Acceptance criteria**

- No fetching/progressive path applies reduced opacity to the entire retained previous plot.
- Before first current series, the compatible prior complete plot remains at normal opacity and complete-only actions remain correctly disabled for the pending identity.
- First current series still replaces previous-generation data rather than merging with it.
- If a trace-local fade is implemented, it is bounded to at most 200 ms, starts without delaying delivery, does not batch arrivals, and does not change final trace opacity/style or trigger a remount.
- Focused tests cover the full-opacity placeholder → first-current-series transition.

### R3 — Medium: The required Plotly A/B decision benchmark was replaced by a synthetic microbenchmark

Affected files:
- `frontend/src/features/analyses/editor/performance/timeCapacityPlotStrategyBenchmark.ts`
- `frontend/src/features/analyses/editor/performance/timeCapacityPerformanceProfile.ts`
- `docs/specs/050.8-progressive-time-capacity-series-streaming.md`

**Current**

050.8 requires both one-series-at-a-time strategies to be compared on the same representative installed-app Time/Capacity request, recording per-series event/visible completion timing, first useful paint, final completion, remounts, zoom preservation, and final order/color/legend equality. The committed benchmark instead creates off-screen synthetic sine-wave traces, sets `staticPlot: true`, directly calls `Plotly.react()` or `Plotly.addTraces()`, measures only one aggregate duration per pass, and compares only serialized final `graphDiv.data`. It does not exercise the real Time/Capacity trace/layout builders, React rerender ownership, multi-Plotly-trace scientific series, zoom callbacks, legend/color/order, or event-to-visible completion boundaries. The implementation record's 78.7 ms vs 73.7 ms medians therefore do not satisfy the locked strategy-selection gate.

**Target**

Benchmark both strategies using the same representative Time/Capacity request and the production rendering path (or a diagnostic harness that faithfully invokes the production builders/React lifecycle). Measure the full 050.8 §8.1 matrix and retain Strategy A only if the representative evidence supports the locked selection rule.

**Acceptance criteria**

- Strategy A and B use the same representative request/data and same installed runtime.
- The benchmark exercises canonical Time/Capacity trace/layout builders and logical scientific series that may expand to multiple Plotly traces.
- Evidence records individual event→visible completion durations, first useful paint, median/max update cost, final metadata/Plotly completion, total interaction, visible update count, true remount/newPlot count, zoom preservation, and final trace/legend/color/order equality.
- The implementation record is corrected to distinguish this representative decision evidence from any synthetic diagnostic microbenchmark.
- Production remains one-series-at-a-time; no batching is introduced to make either strategy look faster.

### R4 — Medium: Streaming profiler calls first-byte receipt "first useful" and cannot measure per-series visible latency

Affected files:
- `frontend/src/features/analyses/editor/performance/timeCapacityPerformanceProfile.ts`
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/tests/timeCapacityPerformanceProfile.test.ts`

**Current**

`streamSeries()` sets `stream_first_useful_ms` when the first scientific series event is **received**. That is not the first useful plot boundary required by 050.8. `partialPlotlyComplete()` only increments counters; it stores no completion timestamp and is not paired with the corresponding series receipt. Consequently the profiler cannot report first useful Plotly completion or per-arrival event→visible completion latency, even though those are the measurements needed to judge the progressive UX and the A/B strategy.

**Target**

Separate transport receipt from visual completion. Keep each series receipt timestamp/bytes, then record the corresponding logical partial Plotly completion timestamp and event→paint duration. `stream_first_useful_ms` must be derived from the first actual partial Plotly completion, not from receipt of bytes.

**Acceptance criteria**

- With a fake clock where series 1 arrives at t=2 and Plotly completes at t=7, `stream_first_useful_ms` records 7 (relative to request start), not 2.
- Each retained series boundary can report its visible Plotly completion timestamp and event→visible duration in canonical order without storing scientific data.
- Fast consecutive arrivals remain truthful: if multiple events are reconciled by the browser before separate paints, profiling distinguishes receipts from actual visible completions rather than inventing paints.
- Final metadata receipt and final Plotly completion remain separately measurable.
- Bounded/privacy behavior remains unchanged.

### R5 — Medium: Required cancellation/disconnect regression coverage is absent

Affected files:
- `frontend/tests/apiStreaming.test.ts`
- `tests/test_analysis_engine.py`
- streaming route/parser implementation as needed by the tests

**Current**

The implementation includes an `AbortSignal` on `fetch()` and a backend `disconnected` event, but the focused tests do not exercise either required cancellation boundary. `apiStreaming.test.ts` covers split UTF-8/chunk parsing and JSON hits only; it does not abort a live NDJSON reader. The 050.8 backend additions cover success, terminal error, and exact-hit behavior, but there is no disconnect-before-completion test proving that no partial cache is stored and the background job terminalizes. Both cases are explicitly required by §13.

**Target**

Add deterministic regression coverage for frontend abort and backend disconnect/cancellation before full completion, exercising the real boundaries rather than only source-text assertions.

**Acceptance criteria**

- Frontend test starts an NDJSON response whose reader is still pending, aborts through `AbortController`, and proves `postJsonOrNdjson()` stops/rejects without delivering later events.
- Backend test disconnects after streaming has started but before terminal completion and proves no partial `analysis_cache.store_result()` occurs.
- The same backend test proves the existing background job reaches a legitimate terminal state and the worker/session is cleaned up.
- Successful complete-stream and exact-hit behavior remain unchanged.
