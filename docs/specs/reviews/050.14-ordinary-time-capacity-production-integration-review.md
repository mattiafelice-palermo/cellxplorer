## Finding

### R1 — High: pool publication/warmup can still put Windows process spawn/import on the first interaction critical path

Affected files:

- `backend/app/services/time_capacity_workers.py`
- `backend/app/main.py` only if lifecycle wiring needs adjustment
- `tests/test_time_capacity_workers.py`
- focused production benchmark/test record in `docs/specs/050.14-ordinary-time-capacity-production-integration.md`

**Current**

`start_time_capacity_worker_pool()` launches a background thread, calls `_ensure_pool(workers)`, and then submits a single `_worker_ping()` before considering warmup complete. `_ensure_pool()` assigns the newly-created `ProcessPoolExecutor` to the global `_POOL` immediately. There is no separate READY state.

This leaves two related production problems:

1. A real eligible Time/Capacity request can arrive while the background warmup is still in progress, call `_ensure_pool()`, receive the globally published but cold executor, and wait for worker spawn/import on the request path.
2. `ProcessPoolExecutor` creates workers lazily. A single ping does not establish that all 2 or 4 selected workers have been spawned and imported. A four-worker pool can therefore have only one worker warm before the first broad request, which then starts the remaining workers on its critical path.

The warm benchmark p50s do not detect this first-interaction lifecycle problem because startup/warm samples occur before the reported steady-state medians.

This violates the 050.14 production requirement that startup/import/warmup occur off the interaction critical path.

**Target**

Make readiness explicit and fail closed to serial until the selected persistent pool is genuinely warm.

Required behavior:

- Do not make a newly-created executor eligible for interactive dispatch until its warmup has completed successfully.
- Warm **all workers in the selected bound**, not just one task. The readiness proof must establish that the required number of distinct worker processes have started and completed a top-level lightweight ping/import task.
- If an eligible request arrives while warmup is incomplete, use the production serial path for that request; do not block the interaction waiting for process creation.
- If warmup fails, leave the process path unavailable and use serial fallback. Avoid repeatedly forcing cold initialization on every request after a known startup failure unless there is an explicit bounded retry/recovery mechanism outside the request path.
- Preserve deterministic 2/4 worker gating, clean shutdown, process-crash serial fallback, and exact cache-hit bypass.
- Do not change the accepted process architecture or rerun S100/S50/full exploratory matrices.

**Acceptance criteria**

- Focused lifecycle test proves a request arriving before READY does not create/wait for pool workers and selects serial execution.
- Focused warmup test proves 2-worker and 4-worker readiness only after 2/4 distinct spawned worker PIDs have acknowledged warmup.
- Once READY, the same production worker path is reused for eligible requests without new process creation.
- Warmup failure leaves requests on serial fallback without returning partial results.
- Shutdown remains deterministic and does not leak a warmup thread/pool.
- Existing process-result parity/crash-fallback and exact cache-hit tests remain passing.
- Verification follows the fast rule: run each passing focused suite once, rerun only after an actual failure/fix, use S25 if a production timing smoke is needed, and run canonical preflight once at final handoff. Do **not** rerun the broad 1/6/10/11 matrix for this lifecycle-only fix.
