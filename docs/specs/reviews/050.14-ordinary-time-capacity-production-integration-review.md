## R1 — High: pool publication/warmup can still put Windows process spawn/import on the first interaction critical path

Status: **Resolved in `ceb940434b344a56e2c5e5300a239f0150cc627f`**

The worker service now has explicit `stopped`, `warming`, `ready`, and `failed` states. A newly-created executor is not eligible for interactive dispatch until background warmup receives distinct PID acknowledgements from the full selected 2- or 4-worker bound. `_run_process()` obtains only a READY pool; requests that arrive while warmup is incomplete, after warmup failure, or for a nonmatching unavailable bound immediately execute the serial path rather than creating or waiting for workers.

Warmup failure marks the process path failed and preserves serial fallback. Process failure during a request also marks the pool failed and retries the complete request through the serial path rather than returning partial results. Shutdown clears state, joins the warmup thread, and synchronously closes the pool.

Focused lifecycle coverage verifies:

- a production request before READY uses serial execution and cannot create a cold pool;
- a READY pool is reused without new process creation;
- warmup failure leaves the process path unavailable until shutdown/restart;
- existing serial/process parity, crash fallback, and cache-hit controls remain passing.
