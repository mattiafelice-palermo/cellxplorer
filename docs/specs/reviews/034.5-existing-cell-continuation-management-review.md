## Assessment

The Files-tab lifecycle surface, reusable picker, atomic attach/reorder/detach calls, impact preview
and query invalidation are present. The reviewed implementation is not safe for users yet because
its review responses are not the authoritative complete Cell proposal, multiple sources are labelled
as the tracked tail, pending inspection does not converge automatically, and the UI can display
fabricated cycle ranges.

The findings below use local review IDs and name the matching parent review finding from the
cumulative 034.4-034.6 review.

## Confirmed correct by code reading

- Existing-Cell attach, reorder and detach use explicit atomic backend endpoints.
- Reorder is limited to one Test; cross-Test dragging is not introduced.
- Detach requires a separate impact preview and confirmation token.
- Detach copy states that the original source file remains on disk.
- The Files tab invalidates Cell detail, Cell list, tree, file, analysis, activity and background-job
  queries after successful lifecycle changes.
- Per-source manual Update behavior remains available.
- The reusable filesystem picker is used rather than duplicating browse/Tauri behavior.
- No persistent schema or migration change is introduced by this child.

## Follow-up tasks

### R1 — High: add and reorder review do not inspect the authoritative complete Cell proposal

**Parent review mapping:** R3

**Affected files**

- `backend/app/routers/files.py`
- `backend/app/services/continuations.py`
- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/api.ts`
- `tests/test_continuations.py`
- `frontend/tests/continuationManagement.test.ts`

**Current**

The generic inspection endpoint loads existing sources only from `existing_test_id`. It does not
construct the complete Cell chain containing preceding and following Tests.

Therefore:

- adding to an earlier Test does not display findings against the following Test;
- reordering an earlier Test does not display cross-Test adjacency findings;
- the UI can show a clean review while the mutation endpoint later runs the full authoritative
  lifecycle validation and rejects the same proposal or requests acknowledgements that were never
  shown.

The reorder flow also enables impact review based on local dirty state rather than authoritative
inspection completeness. It has no reorder-specific confirmation checkboxes, and it reuses an
acknowledgement set primarily maintained by the attach flow.

**Target**

Provide one operation-specific proposal response for attach and reorder. The server must:

1. load the complete Cell chain in canonical Test/file order;
2. apply the requested Test-local change in memory;
3. run the same authoritative inspection used by mutation;
4. calculate complete-Cell before/after tracked tail and impact;
5. return findings, required acknowledgements and impact for that exact proposal.

The frontend must use that response as the single review state. Do not show a less-authoritative
inspection followed by a different mutation-time inspection.

**Acceptance criteria**

- Adding to an earlier Test displays findings against the following Test before confirmation.
- Reordering an earlier Test displays internal and cross-Test changed boundaries.
- Review/save remains disabled while inspection is pending, failed or blocking.
- Reorder confirmation findings have explicit checkboxes.
- Reviewed and submitted proposals use identical Test ID, order, source identities and finding IDs.
- Multi-Test backend and frontend tests cover earlier and final Tests.

### R2 — High: the Files panel assigns multiple incorrect tracked-tail roles

**Parent review mapping:** R4

**Affected files**

- `frontend/src/continuationPolicy.ts`
- `frontend/src/components/ContinuationSourceList.tsx`
- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/components/CellDetailTabs.tsx`
- `frontend/tests/continuationManagement.test.ts`

**Current**

`sourceRoleLabel` marks the last item of every array as `Tracked tail`. The management panel renders
one source array per Test, so the final source of every Test is labelled tracked. The copy reinforces
this incorrect model by saying an earlier Test has its own tracked tail.

The same Files tab then renders a second legacy table which calculates the Cell-wide final source
correctly. A source can consequently appear as `Tracked tail` in the management list and
`Historical source` immediately below it.

Reorder confirmation text also compares the old/new final file of the selected Test as though it
were the Cell-wide tracked tail even when a later non-empty Test remains.

**Target**

Determine the role from the complete Cell chain and expose one canonical `trackedTailSourceId` or
explicit role per source.

- Exactly one source in a non-empty Cell may be labelled tracked.
- All sources in earlier Tests are historical when a later non-empty Test exists.
- A trailing empty Test must not change the role.
- Use one canonical source inventory in the Files tab; integrate manual Update actions rather than
  rendering a contradictory duplicate table.
- Reorder impact text must use server-reported Cell-wide before/after tail IDs.

**Acceptance criteria**

- Exactly one tracked-tail badge is rendered for each non-empty Cell.
- Earlier Test reorder reports no tail change when a later Test still owns the tail.
- Detaching the final Cell-wide source moves the role to the correct preceding source.
- No source appears twice with contradictory roles.
- Tests include two Tests plus an empty trailing Test.

### R3 — High: pending attach/reorder inspection and submission conflicts do not recover

**Parent review mapping:** R2

**Affected files**

- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/api.ts`
- `frontend/tests/continuationManagement.test.ts`

**Current**

Attach and reorder inspection queries execute once. A successful response can contain pending
sources while backend cache preparation continues, but no polling/refetch observes completion. The
controls may therefore remain blocked indefinitely.

Mutation errors are displayed only as a toast. A changed source hash or newly discovered finding
does not preserve the open review state and refresh the authoritative proposal.

**Target**

- Poll/refetch while the current proposal is incomplete or contains pending preparation.
- Stop on ready, failed/blocking, modal close or proposal identity change.
- Keep preparation state visible after the first network response.
- On 409/422 proposal conflicts, retain modal state, refresh the proposal/findings and require new
  acknowledgements where applicable.
- Keep polling restrained and rely on backend cache-build deduplication.

**Acceptance criteria**

- Pending attach and reorder become ready without closing the modal.
- Failure becomes a stable error state.
- Polling stops on modal close or proposal change.
- Hash-change conflict refreshes findings without clearing selected files/order.
- Tests use successive mocked pending/ready and conflict/refreshed responses.

### R4 — Medium: acknowledgement IDs can survive materially changed findings

**Parent review mapping:** R7

**Affected files**

- `backend/app/services/continuations.py`
- `frontend/src/continuationPolicy.ts`
- backend and frontend continuation tests

**Current**

Finding IDs contain only code and source keys. A changed timestamp gap, protocol mismatch, source
hash or order can keep the same ID and therefore preserve a previous acknowledgement.

**Target**

Generate confirmation IDs from a canonical semantic fingerprint: code, ordered source identity and
normalized relevant details. Preserve acknowledgement only when that fingerprint is unchanged.

**Acceptance criteria**

- Identical findings preserve acknowledgement.
- Materially changed findings receive a new ID and clear acknowledgement.
- Presentation-only wording changes do not unnecessarily clear it.
- Tests cover attach and reorder findings.

### R5 — Medium: existing-source cycle ranges and protocol detail are fabricated or omitted

**Parent review mapping:** R8

**Affected files**

- `frontend/src/components/ContinuationManagementPanel.tsx`
- Cell-detail or dedicated continuation-detail API payload
- backend detail service/router
- relevant frontend/backend tests

**Current**

The management panel constructs local source information as:

- start cycle `1` when `cycle_count` is truthy;
- end cycle equal to `cycle_count`;
- protocol signature `null`;
- end time `null`.

This fabricates a contiguous one-based range. Sparse or non-one-based local labels are valid and
must use observed labels. Existing authoritative cache evidence is not exposed to the source list.

**Target**

Expose authoritative per-source continuation detail from the backend detail surface.

- Report observed local minimum, maximum and count from current cache evidence.
- Report detected end time and protocol signature when available.
- Show pending/unknown when evidence is unavailable; never infer `1..cycle_count`.
- Keep expensive Parquet access off list endpoints; this is a bounded Cell-detail operation.

**Acceptance criteria**

- A source with labels `12..211` or sparse labels shows observed min/max/count correctly.
- Missing evidence displays pending or unknown.
- Protocol and end-time values appear when available.
- No frontend helper constructs start/end from count.
- Tests use non-one-based and sparse local cycles.

### R6 — Medium: attach source order cannot be edited and disabled drag/drop remains active

**Parent review mapping:** R9

**Affected files**

- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/components/ContinuationSourceList.tsx`
- `frontend/src/continuationPolicy.ts`
- `frontend/tests/continuationManagement.test.ts`

**Current**

Multiple sources selected for attachment are shown in a disabled list. The user cannot remove one,
reorder them or apply suggested order before review, so filesystem-selection order becomes the
submitted order.

`ContinuationSourceList` remains draggable whenever callbacks exist, independently of `disabled`.
During inspection or mutation, arrow controls can be disabled while drag/drop still changes order.

**Target**

- Allow staged attachment sources to be removed and reordered before proposal review.
- Provide Use suggested order when the server suggestion differs.
- Submit exactly the displayed staged order.
- Disable drag start, drag over, drop and keyboard movement while disabled/submitting.
- Freeze order once impact review or mutation begins unless the review is cancelled.

**Acceptance criteria**

- Multiple attach sources can be manually or automatically ordered.
- Removing a staged source reruns the complete proposal and clears obsolete acknowledgements.
- Disabled source lists cannot change through drag/drop.
- The order shown in confirmation equals the mutation request order.
- Tests cover remove, reorder, suggested order and disabled state.

### R7 — Medium: management UI violates the visual and accessibility contract

**Parent review mapping:** R10

**Affected files**

- `frontend/src/components/ContinuationSourceList.tsx`
- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/components/ImportFilesystemPickerModal.tsx`

**Current**

Concrete deviations include:

- findings use color-only text rather than severity icon plus text;
- truncated paths/filenames lack consistent tooltip/title access;
- fixed numbered light shades and pale-gray borders are used for ordinary chrome;
- attach and reorder share a filled red `Confirm change` button even though only detach is
  destructive;
- high-zoom layout/focus behavior has no recorded manual verification.

**Target**

Follow the visual style guide:

- semantic icon plus explicit label for findings;
- theme-safe light/dark surfaces and borders;
- full-value tooltip/title for truncation;
- channel-primary confirmation for attach/reorder and red only for detach;
- responsive wrapping/scrolling with predictable keyboard focus.

**Acceptance criteria**

Code-level corrections plus a user-run manual checklist cover:

- Light, Dark and Auto appearance;
- 70%, 100%, 130% and 160% UI zoom;
- long paths and filenames;
- keyboard-only add, reorder, acknowledgement and detach;
- pending, blocking, confirmation, failure and empty states;
- focus after move, removal and modal close.
