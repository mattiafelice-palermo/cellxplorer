## Locked correction before implementation

The Cell detail Files tab manages one ordered source chain. Multiple user-facing Tests were never a
product requirement or an existing database workflow.

Luna must remove:

- one card per Test;
- Test names and “Final/Earlier Test” copy;
- Target Test selector;
- per-Test reorder and detach semantics;
- per-Test tails;
- frontend dependence on a user-selected `test_id`.

The existing `Test` table remains only as exactly one internal compatibility row per Cell. Every
source-chain action must be Cell-level, and code must reject any attempt to create a second Test for
the same Cell.

## Confirmed useful work to preserve

- Reusable filesystem selection and source-list components.
- Explicit attach/reorder/detach operations with backend validation.
- Impact preview and confirmation before detach.
- Disk-preservation explanation.
- Query invalidation after lifecycle mutation.
- Per-source manual Update action.

## Required changes

### R1 — High: replace the multiple-Test workflow with one Cell-level source chain

**Affected files**

- `frontend/src/components/CellDetailTabs.tsx`
- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/components/ContinuationSourceList.tsx`
- `frontend/src/api.ts`
- `backend/app/routers/files.py`
- `backend/app/services/analysis_usage.py`
- backend/frontend continuation tests

**Current**

The Files tab renders one management card per `cell.tests`, offers a Target Test selector, limits
reordering to one Test, prevents emptying each Test, and describes each Test as owning a tail. The
backend lifecycle URLs and request contracts are Test-level.

**Target**

- Render one flattened, canonical Cell source inventory.
- Exactly one final source is `Tracked tail`; every earlier source is `Historical source`.
- Add always targets the Cell chain; there is no selector.
- Reorder accepts an exact permutation of all Cell source IDs.
- Detach is blocked only when the Cell would have no source.
- Canonical frontend/API operations use `cell_id`.
- Backend automatically resolves the Cell’s single internal Test row.
- Every Cell has exactly one internal Test row.
- New imports/lifecycle code never create a second Test.
- Multiple Tests per Cell are not a legacy state to support. They were never part of the app’s
  approved or used data model.
- Existing Test-level routes may remain only as internal wrappers, not as the frontend contract.

**Acceptance criteria**

- One Cell with four sources displays one list and one tracked tail.
- No Test word or selector appears in Files/continuation UI.
- Any source can be moved to any position in the Cell chain.
- Add/reorder/detach requests identify the Cell, not a user-selected Test.
- Every Cell creation path leaves exactly one internal Test row.
- Tests assert that a second Test cannot be created through import, attach, reorder, detach, or
  compatibility-wrapper paths.

---

### R2 — High: review and mutation must inspect the same complete Cell proposal

**Affected files**

- `backend/app/routers/files.py`
- `backend/app/services/continuations.py`
- `backend/app/services/analysis_usage.py`
- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/api.ts`
- continuation tests

**Current**

The first implementation can inspect only the selected Test while later mutation logic considers a
larger Cell order. Review can therefore show a proposal different from the one the server accepts.

**Target**

Provide one operation-specific Cell proposal response that:

1. loads the complete ordered Cell chain;
2. applies attach/reorder/detach in memory;
3. runs the same inspection used by mutation;
4. returns findings, required acknowledgements, old/new tracked tail, and impact;
5. supplies the exact confirmation/proposal identity used by mutation.

There are no Test-to-Test boundaries. The only boundaries are adjacent source files in the one Cell
chain.

**Acceptance criteria**

- Review and mutation use identical source IDs/order/hashes/finding IDs.
- Every changed adjacent boundary is shown before confirmation.
- Save remains disabled while proposal inspection is pending, failed, or blocking.
- Attach/reorder acknowledgements have explicit checkboxes.
- Tests assert complete-chain proposals, including first/middle/final insertion and arbitrary
  reorder.

---

### R3 — High: pending inspection and submission conflicts do not recover

**Affected files**

- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/api.ts`
- `frontend/tests/continuationManagement.test.ts`

**Current**

Attach/reorder queries run once even when preparation remains pending. Mutation conflicts are shown
as toasts without refreshing the proposal.

**Target**

- Poll/refetch while proposal inspection is incomplete.
- Stop on ready, stable failure, modal close, or proposal change.
- Preserve staged sources/order on conflict and refresh findings.
- Require new acknowledgements whenever semantic finding identity changes.

**Acceptance criteria**

- Pending proposals become ready without reopening.
- Stable failures stop polling and remain visible.
- Hash/new-finding conflict refreshes without clearing user choices.
- Tests use successive pending/ready and conflict/refreshed responses.

---

### R4 — Medium: acknowledgement IDs survive materially changed findings

**Affected files**

- `backend/app/services/continuations.py`
- `frontend/src/continuationPolicy.ts`
- backend/frontend continuation tests

**Current**

Finding IDs omit hashes, timestamps, gap magnitude, protocol values, and order. An old confirmation
may remain checked after the warning changes.

**Target and acceptance**

Use a canonical semantic fingerprint. Identical findings preserve acknowledgement; changed gap,
overlap, protocol, hash, or order receives a new ID. Presentation-only copy changes do not.

---

### R5 — Medium: existing-source cycle ranges and details are fabricated or omitted

**Affected files**

- `frontend/src/components/ContinuationManagementPanel.tsx`
- Cell detail or dedicated continuation-detail API
- backend detail service/router
- tests

**Current**

The frontend derives cycle start `1` and end `cycle_count`, and omits end time/protocol signature.
This is false for sparse or non-one-based local labels.

**Target**

Expose observed local minimum, maximum, and count plus end time/protocol signature when available.
Show Pending/Unknown when unavailable. Keep Parquet access bounded to Cell detail, never list rows.

**Acceptance criteria**

- Non-one-based and sparse fixtures show real observed values.
- No frontend helper constructs `1..cycle_count`.
- Missing evidence is explicitly unknown.

### R6 — Medium: staged attach sources cannot be edited and disabled drag/drop remains active

**Affected files**

- `frontend/src/components/ContinuationManagementPanel.tsx`
- `frontend/src/components/ContinuationSourceList.tsx`
- `frontend/src/continuationPolicy.ts`
- frontend tests

**Current**

Multiple staged sources are displayed in a disabled list and filesystem selection order becomes the
submitted order. Drag/drop can remain active when the list is disabled.

**Target**

- Remove and reorder staged sources.
- Offer Use suggested order.
- Submit exactly the displayed order.
- Disable every movement path while disabled/submitting.
- Freeze order while impact review/mutation is active.

**Acceptance criteria**

- Remove/reorder/suggested order refresh the proposal and acknowledgements.
- Disabled list cannot move.
- Confirmation order equals mutation request order.

---

### R7 — Medium: Files tab contains contradictory duplicate inventories and roles

**Affected files**

- `frontend/src/components/CellDetailTabs.tsx`
- `frontend/src/components/ContinuationManagementPanel.tsx`

**Current**

The management cards and a second legacy table both display sources, sometimes with contradictory
role labels.

**Target**

Use one canonical source inventory. Integrate manual Update and all status/detail columns into that
surface.

**Acceptance criteria**

- Each source appears once.
- Exactly one tracked-tail badge exists.
- Updating, reordering, and detaching remain available from the canonical inventory.

---

### R8 — Medium: management UI misses visual/accessibility requirements

**Affected files**

- shared continuation components and picker

**Target and acceptance**

- Severity icon plus text.
- Theme-safe surfaces and borders.
- Tooltip/title for truncated values.
- Primary confirmation for attach/reorder; red only for detach.
- Predictable keyboard focus and high-zoom wrapping/scrolling.
- User-run Light/Dark/Auto and 70/100/130/160% checklist recorded as not run unless performed.
