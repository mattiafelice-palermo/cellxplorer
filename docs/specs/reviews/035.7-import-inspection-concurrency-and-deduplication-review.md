## Performance investigation — second-to-third modal transition

### Boundary and corpus

The measured boundary is the confirmation action in the second import modal through completion of
`POST /api/imports/inspect-paths`, immediately before the third modal is opened. Capacity preview
requests and rendering after the third modal starts are excluded.

The representative corpus was the disposable local folder
`C:\Users\matti\Desktop\MOLS - Copy - variants-1000`:

| Property | Value |
|---|---:|
| Files | 1,000 |
| `.nda` / `.ndax` | 0 / 1,000 |
| Total bytes | 1,589,178,113 |
| Median file size | 1,535,840 bytes |
| Minimum / maximum | 885,019 / 2,571,224 bytes |
| Storage | Local Windows `C:` volume; media type was not observable from the restricted shell |
| OS / Python | Windows 11, Python 3.14.4 |
| Logical CPUs | 16 |
| Database | `%USERPROFILE%\.cellxplorer\cellxplorer.db`, 17,362,944 bytes |
| Registered sources / cells | 44 / 0 |

The current application was restarted before the clean live measurement. An earlier 88.4-second
live result was from a backend process that had loaded the pre-035.7 serial implementation; it is
not a current-branch baseline.

### Instrumentation and commands

Temporary benchmark scripts used `time.perf_counter()` around the service phases and were removed

### Experiment A — baseline phase profile

The clean direct service profile was 17,199.7 ms. The live endpoint was 17.4 seconds. The direct
profile separated the database snapshot, concurrent inspection, and matching; the small difference
to the live request covers endpoint response construction, JSON serialization/transfer, and client
request handling.

| Phase | Measured wall time | Share of blocking interval | Notes |
|---|---:|---:|---|
| Request/path preparation | not materialized separately | — | Path list arrives already prepared from modal two |
| Preliminary serial stat pass | 19.0 ms | ~0.1% | 1,000 `Path.stat()` calls; total 1,589,178,113 bytes |
| Job creation/setup | not isolated | <0.1% | In-memory job registry |
| Identity snapshot | 92.4 ms | 0.5% | 44 `SourceFile` rows with eager relationships |
| Concurrent hash/header inspection | 17,056.1 ms | 99.2% | Direct service wall time; hash/header worker phases overlap |
| Post-inspection matching | 51.1 ms | 0.3% | In-memory snapshot matcher |
| Response construction/serialization/transfer | approximately 0.2 s | ~1% | Inferred from 17.2 s direct vs 17.4 s live; compact response is 5,770,313 bytes |
| Frontend JSON/state transformation | not independently isolated | — | No browser performance marks were added; not measurable from the backend harness |
| **Total** | **17.2–17.4 s** | **100%** | Preview work excluded |

Per-file accumulated worker timing from an instrumented warm run was approximately 35.9 seconds of
hash work and 55.7 seconds of metadata work, but these are accumulated CPU/I/O times across
overlapping workers and must not be added to the 24-second instrumented wall time. The first
single-worker run was cold and took 362.7 seconds; it is reported separately rather than mixed
with warm runs.

### Experiment B — worker-count benchmark

The worker-count prototype used the same 1,000 files and added lightweight timing wrappers around
the parser calls. Results after the cold single-worker run were:

| Workers | Wall time | Hash accumulated | Metadata accumulated | Interpretation |
|---:|---:|---:|---:|---|
| 1 | 362.7 s cold | 344.1 s | 18.2 s | Serial path is unacceptable |
| 2 | 24.0 s warm | 21.8 s | 25.2 s | Large improvement over one worker |
| 4 | 24.0 s warm | 35.9 s | 55.7 s | No material gain over two in wrapped run |
| 8 | 23.4 s warm | 59.8 s | 116.2 s | More overlap, substantially more accumulated work |
| 12 | 23.0 s warm | 86.6 s | 173.4 s | No material wall-time gain |

The clean production endpoint with the fixed four-worker implementation measured 17.4 seconds;
the wrapper benchmark is intentionally treated as directional because the wrappers add overhead.
Counts above 4 do not provide a material benefit on this corpus and increase contention and
accumulated parser work. The four-worker cap is appropriate for the current hardware and remains
safer for HDD/network folders.

### Experiment C — database-size sensitivity

The real database has only 44 registered sources. Its identity snapshot took 92.4 ms and matching
took 51.1 ms, so neither is a material part of the 17-second delay.

A pure in-memory synthetic comparison prototype showed the scaling risk of the old soft matcher:

| Candidate rows | 1,000 selected-file match time |
|---:|---:|
| 44 | 56.2 ms |
| 1,000 | 1,102.7 ms |
| 10,000 | 15,323.8 ms |

An indexed prototype reduced those synthetic values to approximately 3.3 ms, 8.4 ms, and 27.5 ms
including index construction. The prototype was not installed because the current database is tiny
and the production matcher already runs in 51 ms. It is a future safeguard if libraries grow into
the thousands of registered sources.

### Experiment D — progress bookkeeping

The in-memory background-job registry was measured independently with 1,000 items:

| Operation | Time |
|---|---:|
| 1,000 `update_job` calls | 1.2 ms |
| 1,000 `record_result` calls, including linear item lookup | 21.8 ms |

The bookkeeping is not material against a 17-second parser interval. The frontend polls every 500
ms, but those reads are also outside the dominant interval.

### Experiment E — narrow identity projection

The current eager snapshot contains 44 rows and completes in 92.4 ms. A production-safe narrow
projection was not installed or benchmarked against a copied database because the measured snapshot
is already below the one-second materiality threshold. The implementation does not share ORM
objects with workers and does not produce an N+1 query.

### Experiment F — indexed soft matching

The synthetic prototype above normalized/indexed filename and metadata values once, gathered only
potentially relevant candidates, and then applied the same strong-combination rule. It shows a
large asymptotic improvement for a future large library, but no current-user benefit above the
materiality threshold. Full corpus result-equivalence testing was not performed because the current
corpus contains no registered-cell match cases; the prototype is therefore a recommendation, not a
production change.

### Experiment G — redundant preliminary stat pass

The 1,000-file preliminary stat pass took 19.0 ms. Removing it cannot materially improve a 17-second
transition and would weaken the known-byte progress setup. It should remain serial and explicit.

### Experiment H — response and frontend transformation

Commit `439c98e` removed the full parsed `header_metadata` object from each response item. A single
`.ndax` header was approximately 57,735 JSON bytes with 977 raw fields; sending that structure for
1,000 files would be roughly 57 MB. The compact current response was 5,770,313 bytes. The clean
live endpoint measured 17.4 seconds versus 17.2 seconds for the direct service, showing that the
compact response path is not a material remaining bottleneck.

The frontend transformation was not separately marked because the requested boundary ends before
third-modal post-open rendering, and browser performance instrumentation was not available in the
investigation harness. The current 17.4-second live result includes request transfer and server
response handling but not a browser-side `performance.measure()` breakdown.

## Findings

### R1 — Full hash and Neware header reads dominate inspection

- **Priority:** High
- **Affected files:** `backend/app/services/import_inspection.py`, `backend/app/services/parsing.py`
- **Current:** Four bounded workers perform a full SHA-256 and Neware header read per file.
- **Measured evidence:** 17.06 seconds of a 17.2-second direct interval is concurrent inspection; one
  worker took 362.7 seconds cold, while 2–12 workers were approximately 23–24 seconds in the
  wrapped warm prototype. The clean production endpoint is 17.4 seconds.
- **Target:** Keep identity and mutation checks intact while avoiding duplicate reads or shifting
  nonessential work out of the blocking boundary.
- **Acceptance criteria:** Full checksum, before/after stability check, deterministic order, and
  final duplicate enforcement remain unchanged; a representative 1,000-file run improves by at
  least 1 second.
- **Estimated benefit:** Worker-count changes above four are not expected to help materially on this
  corpus. Reusing already-proven header work or changing the parser/library is the realistic path.
- **Risk:** High if checksum or header reuse is trusted without a matching fingerprint.

### R2 — Soft matching will scale poorly for very large libraries

- **Priority:** Medium
- **Affected files:** `backend/app/services/import_inspection.py`
- **Current:** Soft matching scans every snapshot candidate for every selected file.
- **Measured evidence:** 56.2 ms at 44 candidates, 1.10 s at 1,000, and 15.3 s at 10,000 in a
  synthetic no-match prototype.
- **Target:** Normalize candidate fields once and index potential matches.
- **Acceptance criteria:** Exact, possible-update, archived, tie-breaking, and deterministic payload
  semantics are byte-for-byte equivalent on a corpus containing positives and negatives.
- **Estimated benefit:** No current-user benefit; material only when the registered library is in the
  thousands of sources.
- **Risk:** Medium; an incomplete index could suppress a valid possible-update warning.

## Ranked recommendations

1. **Keep the current four-worker implementation.** It is the best measured safe setting for this
   local corpus; 8 and 12 workers add contention without material wall-time improvement.
2. **Do not remove the preliminary stat pass.** Its measured cost is 19 ms.
3. **Retain the compact response/server-side header cache.** It removed roughly 57 MB of response
   payload and reduced the live endpoint from 50.9 seconds with the full header payload to 17.4
   seconds.
4. **Consider indexed soft matching as a separate future safeguard** if registered-source counts
   grow substantially.
5. **If 17 seconds remains unacceptable, investigate parser-level optimizations or staged identity
   inspection.** Any staged approach must keep duplicate status pending, disable final import until
   identity checks complete, and revalidate the source before registration.

## Limitations

- Three clean live HTTP repetitions were not obtained: an initial PowerShell loop queued failed
  client requests and contaminated later timings. The 17.4-second live result is one clean run,
  corroborated by the 17.2-second direct service profile and a separate 17-second live run.
- CPU model and physical-disk media type were restricted by the execution environment; logical CPU
  count and Windows/Python versions were recorded.
- Frontend click-to-request and JSON-parse marks were not captured independently. The backend
  direct-versus-live comparison bounds their combined cost to roughly the small gap between 17.2
  and 17.4 seconds, but does not split it.
- Synthetic matching results are directional and not a substitute for a full positive/negative
  equivalence corpus.

## Conclusion

The current 17-second transition is fundamentally limited by full-file SHA-256 hashing and Neware
header parsing. The database snapshot, matching, preliminary stat pass, progress bookkeeping, and
compact response are all below the materiality threshold for the current 44-source library. The
four-worker cap is appropriate for the observed hardware/corpus; higher counts do not produce a
material improvement and are less safe for slower storage. Further material improvement requires
parser-level work or an explicitly staged inspection UX, not another small endpoint or progress
bookkeeping optimization.

No additional permanent production optimization was made during this investigation.
