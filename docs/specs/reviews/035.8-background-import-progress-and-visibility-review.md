# Spec 035.8 follow-up — Background import progress and early Cell visibility

Repository: `mattiafelice-palermo/cellxplorer`
Branch: `feature/spec-035-user-experience-optimization`

## Goal

After the user clicks **Import**:

1. the third modal may remain open and show progress;
2. **Continue in background** must detach only the UI;
3. the global Activity indicator must continue showing the real count;
4. all Cell rows must appear together in the Cell Database as soon as relational registration commits;
5. Parquet/cache generation must continue afterward;
6. existing Cell Database statuses must show `Parsing` / `Calculating` until each source is ready.

## Current defects

- The import modal shows `phase_current / phase_total`, but global Activity uses only `completed / total`, so after detaching it appears stuck at `0/1000`.
- `_create_imported_cells_impl_raw()` performs source work and creates all rows inside one long transaction, then commits only at the end.
- The Cell Database therefore remains empty until the complete registration worker finishes.
- After the modal closes, no global watcher refreshes the Cell Database when the import job commits.
- New sources begin as `unparsed`, so the existing `Parsing` status is not shown immediately.

## Required changes

### 1. Make global Activity phase-aware

Files:

- `frontend/src/App.tsx`
- `frontend/src/importProgress.ts`

Extract/reuse one helper for all import progress surfaces.

For a running job:

- use `progress_percent` when present;
- during `validation` or `registration`, display `phase_current / phase_total`;
- otherwise use `completed / total`.

The header and Background activity modal must show the same count as the third modal.

Examples:

```text
Validating Cells — 620 / 1000
Registering Cells — 850 / 1000
Preparing cycling data — 145 / 1000
```

Do not display `0/1000` while `phase_current` is advancing.

### 2. Split registration from scientific preparation

File:

- `backend/app/routers/files.py`

Refactor the accepted import into three stages.

#### Stage A — prepare and validate outside the write transaction

Build plain prepared records for every submitted Cell/source:

- validate names and duplicates;
- validate folder and replicate references;
- resolve source paths;
- reuse the inspection hash/header metadata;
- compare size + mtime with the inspected fingerprint;
- recompute the hash only when the fingerprint changed;
- check existing SourceFile ownership;
- perform continuation-specific checks only for continued cells.

Do not parse timeseries or generate caches here.

#### Stage B — one short relational transaction

Insert all Cells, Tests, SourceFiles, metadata, folder links and replicate links in one atomic commit.

For every source requiring cache preparation, persist:

```python
parse_status = "parsing"
capacity_summary_status = "pending"
```

For an already valid cache, preserve/set the corresponding ready state.

Commit all submitted Cells together. After this commit, they must be immediately queryable even though Parquet generation is still running.

Do not perform hashing, header parsing, timeseries parsing or cache generation inside this write transaction.

#### Stage C — post-commit cache preparation

Start the existing bounded cache workers only after Stage B commits.

As each cache result arrives:

- update that SourceFile;
- commit its `parsed` or `error` state;
- update cycle/capacity summaries;
- update the cache background-job progress.

A cache failure must never remove an already registered Cell.

### 3. Refresh the database globally after detaching

File:

- `frontend/src/App.tsx`

Track background-job transitions globally.

When an `import_register` job changes to `completed`, invalidate:

```ts
["cells"]
["files"]
["tree"]
["replicate-groups"]
["activity"]
["background-jobs"]
```

When an `import_cache` job advances, invalidate `["cells"]` and `["files"]` on a throttled cadence, for example at most once per second.

On terminal `import_cache` completion or failure, perform one final invalidation.

This must work even when the third modal is unmounted.

### 4. Reuse the existing Cell Database status UI

Do not add a new status.

The Cell Database already supports:

- `Parsing`
- `Calculating`
- `Summary failed`
- `Ready`

Immediately after Stage B:

- imported Cells are visible;
- status shows `Parsing` and/or `Calculating`;
- capacity fields show `Calculating...`.

As cache results arrive, rows transition to `Ready` or `Summary failed`.

## Tests

### Backend

Add focused tests proving:

- relational rows commit before cache workers finish;
- all submitted Cells appear in one atomic commit;
- sources are committed with `parsing` / `pending`;
- no timeseries parser runs before relational commit;
- cache failure preserves Cell rows;
- individual cache results update SourceFiles incrementally.

Use a blocked/fake cache worker so the test can inspect SQLite after registration commit but before cache completion.

### Frontend

Add tests for:

- global Activity uses `phase_current / phase_total`;
- detaching does not reset progress to `0/N`;
- completed `import_register` invalidates Cell queries;
- advancing `import_cache` refreshes Cell statuses;
- refresh works with the import modal unmounted.

## Acceptance criteria

- The third modal and global Activity show consistent progress.
- Clicking **Continue in background** does not reset the counter.
- The Cell Database populates automatically without browser refresh.
- All imported Cells appear together before Parquet generation finishes.
- Their status initially shows `Parsing` / `Calculating`.
- Rows update progressively to `Ready` or `Summary failed`.
- Cache failures preserve relational Cell records.
- The application remains responsive while scientific caches are generated.

## Implementation record

Implemented in the Spec 035 feature branch:

- Shared frontend progress helpers now use validation/registration phase counts when available, and the global Activity watcher refreshes Cell, file, folder, replicate, activity, and background-job queries after registration and during cache progress. This continues to work after the import modal is detached.
- Registration now prepares and validates source identity and metadata before the relational write transaction, commits all Cell/SourceFile/TestFile rows atomically, and hands only the remaining cache work to bounded workers after commit.
- New or incomplete sources are committed as `parsing` / `pending`; cache results commit individually and transition them to `parsed` / `ready` or preserve the Cell with an error state when cache work fails.
- Added focused frontend progress/refresh-policy tests and a backend blocked-cache test covering atomic visibility, initial statuses, post-commit cache work, incremental updates, and failure preservation.
- The background-detach action and modal close control now remain locked until registration is `completed`; once the relational commit is visible, the user can detach while cache preparation continues. A retry test confirms the committed source is rejected as already registered.
- Registration now carries the inspected header payload into the submit request, batches existing-source lookup, and builds the Cell/Test/SourceFile graph before one flush. This keeps hashing/header reads and cache generation out of the short relational commit path.
- The registration job now exposes an explicit relational-commit marker, so the modal can offer “Continue in background” as soon as the database transaction is durable even if cache progress is still running.
