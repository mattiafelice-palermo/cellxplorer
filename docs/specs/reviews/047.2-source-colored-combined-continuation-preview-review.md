## Findings

### R1 — Medium: metadata-only chains are classified by substring-matching prose, and a real parser downgrade is misclassified as a source-change conflict

Affected files:
- `backend/app/routers/files.py`
- `frontend/src/components/ContinuedImportEditor.tsx`

**Current**

`preview_continuation_sources` collects each unsupported source into `unavailable` with a
human-readable `reason`, then decides the response status by searching that prose for two literal
phrases:

```python
metadata_only = any(
    "canonical cycling" in item["reason"].casefold()
    or "cycle identity" in item["reason"].casefold()
    for item in unavailable
)
...
status_code=422 if metadata_only else 409,
```

The metadata-only `reason` comes from `parsing.source_metadata_only_message(meta)`, which returns the
first `protocol_warnings` entry containing `"cycle"` **or** `"canonical"` — a strictly wider filter
than the two phrases the endpoint then looks for. Any warning that satisfies the former but not the
latter is silently reclassified as a source-change conflict.

That is not hypothetical. `backend/app/services/parsing.py` builds exactly such a warning in the
fail-closed single-direction downgrade path (`_mark_biologic_source_metadata_only`, the
`"BioLogic MPR decoded rows did not verify the declared single-direction cycle-1 contract; this
source is metadata-only."` case). Executed against the real production code:

```
$ python -c "... parsing.source_metadata_only_message(meta) ..."
metadata_only detected: True
reason returned: 'BioLogic MPR decoded rows did not verify the declared single-direction
                  cycle-1 contract; this source is metadata-only.'
endpoint metadata_only sniff: False
=> status_code: 409
```

`source_metadata_only(meta)` is `True`, so the endpoint correctly takes the metadata-only branch and
correctly refuses the preview — the science is not wrong. But the response is `409` with
`"The combined preview is not ready; inspect continuity again before previewing."`, and the frontend
keys all three of its presentation choices off that status:

```tsx
color={... error.status === 422 ? "gray" : "orange"}
title={... error.status === 409 ? "Re-inspect continuity" : "Combined preview could not be generated"}
{!(... error.status === 409 || error.status === 422) && (<Button ...>Retry</Button>)}
```

so a permanently metadata-only source is presented as an orange **“Re-inspect continuity”** with the
Retry affordance suppressed. Re-inspection cannot change a metadata-only verdict, so the user is left
in a loop with no recovery path and no explanation.

This contradicts spec section K, which separates the two states deliberately: source-change conflict
"must tell the user to re-inspect rather than retry forever", while a metadata-only chain must
"State clearly that a **combined cycling preview is unavailable**".

The accompanying backend test does not catch this because its fixture warning is chosen to satisfy
the sniff:

```python
"protocol_warnings": ["Canonical cycling rows are unavailable."],
```

That string contains `"canonical cycling"`, so `test_continuation_preview_rejects_metadata_only_sources_without_science`
asserts `422` and passes while the production constants that actually reach this path are untested.

**Target**

Metadata-only classification is carried as structured data from the point where the decision is
already made, not re-derived from a message downstream. `parsing.source_metadata_only(meta)` is
already the authority and is already consulted three lines above the message is built; the
`unavailable` entry should record that verdict (for example a `kind: "metadata_only"` /
`"cache_not_ready"` / `"unsupported"` field), and the status/message selection should read that field.

No frontend contract change is required — 422 must simply be produced for every genuinely
metadata-only source, whatever its warning text says.

**Acceptance criteria**

- A source whose `parsing.source_metadata_only(...)` is `True` produces `422` regardless of the
  wording of its `protocol_warnings`.
- No control-flow decision in this endpoint depends on substring-matching a human-readable message.
- A backend regression test drives the metadata-only path with the real production constant whose
  text lacks both `"canonical cycling"` and `"cycle identity"` (the single-direction `cycle-1
  contract` downgrade warning is the concrete case) and asserts `422`.
- The existing `Canonical cycling rows are unavailable.` fixture case keeps asserting `422`.

### R2 — Low: the per-source failure detail the backend fails closed with is never shown to the user

Affected files:
- `frontend/src/components/ContinuedImportEditor.tsx`

**Current**

The backend deliberately fails closed with structured per-source detail, as spec section B3 requires
("fail closed with structured detail identifying the affected source(s)"):

```python
{"code": ..., "message": ..., "sources": [{"source_key", "filename", "reason"}, ...]}
```

The frontend renders only the top level:

```tsx
{combinedPreviewQuery.error instanceof Error ? combinedPreviewQuery.error.message : ...}
```

and `api.ts`'s `errorMessage(...)` reduces an object detail to `String(detail.message)`, so the
`sources` array is parsed, carried into `ApiError.detail`, and then discarded at render time.

For a four-source chain the user sees only "A combined cycling preview is unavailable for this source
chain." with no indication of which source is responsible — even though the response names the
filename and the specific reason for each one. Section K asks the metadata-only/incomplete case to
"State clearly" what is unavailable, and the information needed to do so is already on the client.

**Target**

The inline error surfaces the affected source(s) — filename and reason — from
`ApiError.detail.sources` when present, while remaining a concise inline error rather than an alert
stack. Falling back to the top-level message when `sources` is absent or malformed is correct.

**Acceptance criteria**

- When the preview fails with per-source detail, each affected source's filename and reason is
  visible in the Preview pane.
- A response without a usable `sources` array still renders the top-level message and does not throw.
- The pane geometry requirement in section K ("Loading and error states do not move the pane
  geometry") is preserved.

### R3 — Low: the trace test asserts only the first trace, leaving the spec's per-trace invariants uncovered

Affected files:
- `frontend/tests/continuedImportPreviewPolicy.test.ts`

**Current**

`buildContinuationPreviewTraces` is correct — it maps over every segment and sets `showlegend: false`
and the source color on each. The test, however, narrows to a single element before asserting:

```ts
const first = traces[0] as { ... };
assert.equal(first.line?.color, "#228be6");
assert.equal(first.marker?.color, "#228be6");
assert.equal(first.showlegend, false);
```

The second trace's color and `showlegend` are never checked, and the fixture is built so the first
segment is the *reordered* one, which makes the uncovered element the more interesting of the two.

Spec section H states `showlegend: false` on **every** trace, and calls source-color parity
("left row number color === plot trace color") an **acceptance invariant** that "needs a pure test
where possible". The spec's frontend test list names both explicitly (items 8 and 9). A future change
that set `showlegend` per-trace conditionally, or that colored by index rather than by `source_key`,
would keep this test green while silently reintroducing a legend or breaking color parity — the exact
regression this file exists to prevent.

**Target**

Assert the invariants across all returned traces rather than a sampled one, and assert color parity
by `source_key` rather than by position.

**Acceptance criteria**

- The test asserts `showlegend === false` for every trace in the returned array.
- The test asserts each trace's `line.color` and `marker.color` equal
  `colorsBySourceKey[segment.source_key]` for that trace's own segment, with at least one case where
  segment order differs from the color-map insertion order.
- A trace whose `source_key` is absent from the color map still falls back deterministically.

### R4 — Low: the full stitched capacity arrays are materialized only to read the quantity and label

Affected files:
- `backend/app/routers/files.py`

**Current**

`_build_continuation_preview` resolves the chain-level quantity/label with an unbounded call, then
discards the arrays it just built:

```python
capacity = capacity_preview_from_cycles(cycles)   # no max_points
...
segment_preview = capacity_preview_from_cycles(segment_frame, max_points=segment_limit,
                                               quantity=capacity["quantity"])
...
return {"quantity": capacity["quantity"], "label": capacity["label"], "segments": response_segments}
```

Only `capacity["quantity"]` and `capacity["label"]` are used, but the call runs
`cycles[["cycle", quantity]].dropna()` over the whole stitched chain and builds two full Python lists
(`[int(v) for v in rows["cycle"]]` and the matching float list) for every cycle in every source. The
response stays correctly bounded, so this is not a contract violation — but the parent spec states the
plot "must remain cheap enough for import UX", and section E's intent is that nothing full-size is
built merely to draw a small import chart.

Choosing the quantity from the stitched frame is the right behavior and must be kept: it is what
guarantees every segment is sampled on the same quantity. Only the wasted materialization is at issue.

**Target**

Resolve the chain-level quantity and label without building the full point arrays — for example a
small `resolve_capacity_quantity(cycles) -> (quantity, label)` helper that
`capacity_preview_from_cycles` also uses internally, so the two cannot disagree.

**Acceptance criteria**

- Building the combined preview does not construct unbounded x/y lists for the whole chain.
- The selected quantity/label is still derived from the stitched chain and still applied uniformly to
  every segment, with the existing ordered-segment test still asserting
  `quantity == "discharge_capacity_mah"`.
- `capacity_preview_from_cycles`'s behavior for the ordinary `/api/imports/preview` path is unchanged.

## Checked and accepted (no finding)

- **Authoritative global-cycle mapping.** The endpoint calls `stitch.stitch_cycles(refs, CALC_VERSION)`
  and derives nothing itself: no re-implementation of `observed_local_cycles`, dense cycle-map
  construction, or missing-source handling. `_stitch_ordered` assigns `segment` by
  `enumerate(ordered_sources)`, so the `metadata_by_segment[segment_index]` / `enumerate` pairing in
  `_build_continuation_preview` is correctly aligned with the proposed order, and
  `cycles[cycles["segment"] == segment_index]` selects the right rows. Section C satisfied.
- **Per-source parser identity.** `parsing.parser_identity(source_path)` is resolved per source and
  carried into each `stitch.CachedSourceRef`; no global parser version is introduced. The ordered-segment
  test asserts both the per-source call order and that `cache.load_cycles` received `parser-b` then
  `parser-a`. Section B2 satisfied.
- **Global cycle regression behavior.** The ordered-segment test exercises a non-1 start with gaps
  (local `2,4` → global `1,2`; local `1,3,7` → global `3,4,5`), confirming observed labels are mapped
  densely without inventing the missing ones. Matches section C's examples.
- **Fail-closed behavior.** A cold cache is rejected before stitching (the test patches
  `stitch_cycles` to raise if reached), and `_build_continuation_preview` independently re-guards on
  `missing or not stitch_metadata(cycles)["complete"]`, which also covers `skipped_segments` after a
  mid-chain failure. No partial chain is returned. Section B3 satisfied.
- **Source identity.** `_preview_source_fingerprint` reproduces the ordinary `/imports/preview` rules
  exactly — same stat-first fingerprint match, same full re-hash fallback, same structured `409
  source_changed` payload — and the change test confirms the request stops before header metadata is
  read. It duplicates ~30 lines rather than sharing a helper, which is worth watching if either path
  changes, but it is not a *weaker* identity path, which is what section B1 forbids. Section B1
  satisfied.
- **Bounded sampling.** `_sample_preview_rows` always retains index `0` and index `last`, so every
  non-empty segment keeps its boundaries; per-segment budgets (`max(2, 600 // n)`) give short sources
  a floor so a long chain cannot sample them away. Total is bounded by source count, never by raw
  record count. The bounded test asserts 600 total points and both segment boundaries. Section E
  satisfied.
- **Ordinary preview semantics unchanged.** `capacity_preview_from_cycles` called with its new
  defaults (`max_points=None`, `quantity=None`) is behaviorally identical to the pre-047.2 function on
  every branch, including the empty-frame quantity/label. Section D satisfied.
- **Request timing.** The combined query's `enabled` requires
  `opened && previewMode === "combined" && inspectionRequested && result?.inspection_complete &&
  orderedDrafts.length >= 2`, so opening Step 3, switching modes, and adding drafts start nothing;
  the request is one query, never one per source. The pre-inspection branch renders exactly the copy
  section F1 specifies, as plain dimmed text rather than an Alert. Sections F1/F2 satisfied.
- **Query identity and stale results.** `continuationPreviewQueryKey` includes the visible order, each
  source's `staged_name`/hash/size/`mtime_ns`/path, and `inspectionQuery.dataUpdatedAt`, so reorders
  and content changes produce distinct cache entries and a late result lands on its own key rather
  than the current plot. `previewContinuationSources` forwards React Query's `AbortSignal`, so
  obsolete requests are cancelled. `staleTime: Infinity` gives section F3's "switching away/back may
  reuse the in-session query cache". Section F3 satisfied.
- **Plot construction.** One trace per segment; `x`/`y` passed through from the backend untransformed;
  color read from the 047.1 `colors` map by `source_key`; `showlegend: false` on each trace *and*
  `showlegend: false` on the layout; transparent paper/plot backgrounds; title `Capacity vs. cycle`;
  x axis `Cycle number (global)`; y axis from the backend `label`; hover carries source number and
  filename. No filename legend was reintroduced. Section H satisfied (the optional vertical join
  separators were not added, which section H permits).
- **Selector and Raw data.** The selector offers `All sources (combined)` plus `Source N — filename`,
  defaults to combined, and does not mutate source order or the Cell draft. Raw data remains a single
  header button bound to the selected source row and still gated by
  `continuationSourceCanOpenRawData`; no combined raw-data endpoint was added. Sections G/J satisfied.
- **047.1 behavior preserved.** The metadata-only "Capacity preview unavailable" branch added for
  047.1 R3 is intact in the individual-source path, the `selectedSourceKey` preview effect and the
  `disabled = importing` interaction lock are untouched, and `ContinuationSourceList` was not modified
  by this commit.
- **No scientific/schema change.** `CALC_VERSION` is only read, never redefined; no models, migrations
  or config version files are in the commit. Section D and parent decision 14 satisfied.

## Round 2 — all findings resolved (`1dddf0a`)

**R1 — RESOLVED.** Classification is now structural. Every `unavailable` entry carries an explicit
`kind` (`missing` / `unsupported` / `metadata_only` / `parser_error` / `cache_not_ready`, plus
`cache_incomplete` on the two `_build_continuation_preview` fail-closed paths), and the status choice
reads it:

```python
metadata_only = any(item.get("kind") == "metadata_only" for item in unavailable)
```

The prose sniff is gone, and a grep of the endpoint confirms no control-flow decision matches a
human-readable message any more (the remaining `casefold()` calls are path suffixes, hash comparisons
and sort keys).

The new regression test is built from production code rather than a fixture string — it calls
`parsing.mark_biologic_mpr_cycle_verification_failed(...)` and asserts `422`,
`sources[0]["kind"] == "metadata_only"`, and that the reason contains `single-direction cycle-1
contract`. I confirmed it is a genuine regression test rather than a tautology: re-running the old
prose sniff against that same generated reason still yields `False → 409`, so this test would have
failed before the fix. Both it and the original `Canonical cycling rows are unavailable.` case pass.

**R2 — RESOLVED.** `continuationPreviewFailureSources(detail)` parses `detail.sources` defensively —
non-array, non-object entries and entries missing a filename or reason are dropped — and the Preview
pane renders each surviving `filename: reason` beneath the top-level message. Geometry is bounded by
`maxHeight: 96` with internal scrolling, so the error state cannot push the pane around. A response
with no usable `sources` yields `[]` and falls back to the top-level message alone. Covered by a new
test spanning the valid, malformed-entry, message-only and `null` cases.

**R3 — RESOLVED.** The trace test now asserts across every returned trace instead of `traces[0]`:
length equals segment count, and each trace's `x`, `y`, `line.color`, `marker.color` and
`showlegend === false` are checked against its own segment. Colour is asserted by `source_key`, the
fixture's segment order differs from the colour-map insertion order, and a third segment whose key is
absent from the map covers the deterministic fallback.

**R4 — RESOLVED.** `_capacity_quantity_and_label(cycles, quantity=None)` resolves the quantity and
label without touching the point arrays, and `_build_continuation_preview` uses it instead of the
throwaway full-frame call. `capacity_preview_from_cycles` now delegates to the same helper, so the
two cannot disagree. I traced every branch to confirm the ordinary `/api/imports/preview` path is
behaviourally identical: empty frame, missing `cycle` column, discharge present, discharge absent with
charge present, and both absent (which still returns `quantity="charge_capacity_mah"` with label
`"Capacity (mAh)"`, matching the pre-047.2 function). Chain-level quantity is still derived from the
stitched frame and still applied to every segment.

No new defects were introduced by the fixes. 047.2 is clean.
