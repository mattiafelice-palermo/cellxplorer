#### R11 — Low: success feedback still equates canonical capability with an actually queued cache job

Affected files:
- `frontend/src/importProgress.ts`
- `frontend/src/pages/InboxPage.tsx`
- `frontend/tests/importProgress.test.ts`

**Current**

`importRegistrationSuccessMessage()` now gives the correct pure metadata-only message:

```text
no cycling data preparation is queued
```

and tests metadata-only, canonical-only and mixed capability combinations. However, for every source with `canonical_cycling=true` and `metadata_only=false`, it states that cycling-data preparation **continues** in the background.

The backend does not equate canonical capability with queued work. `_complete_prepared_import_source_file()` can mark a canonical source `cache_ready=true` when an existing unregistered `SourceFile` already has the current parsed/cache state. During final registration, such a source is deliberately omitted from `cache_jobs`:

```text
if not prepared_source["cache_ready"] and not prepared_source["metadata_only"]:
    cache_jobs.append(...)
```

Therefore a canonical-only or mixed submission can legitimately have no new cache job for one or all canonical sources. The current helper receives only source capability, not actual `cache_jobs`, so its definite wording can still claim background work that registration does not queue. This is exactly the edge covered by the existing R11 acceptance criterion that mixed feedback must not assume every accepted source has a cycling job.

The notification is emitted immediately on acceptance, before the background registration worker has resolved `cache_ready`, so the frontend cannot truthfully know actual job creation at that moment from the current response shape.

**Target**

Keep the pure metadata-only message. For canonical/mixed acceptance-time feedback, either:

1. use deliberately conditional wording based only on capability, for example that cycling data **will be prepared in the background if needed**; or
2. defer definitive preparation wording until actual post-registration job state is available.

Do not add format-specific logic and do not force a backend/API expansion merely for copy if conditional generic wording is sufficient.

**Acceptance criteria**

- Pure metadata-only acceptance still does not claim scientific/cycling work is queued.
- Canonical-capable acceptance does not state that background preparation is definitely running before actual cache-job state is known.
- Mixed submission copy does not imply every canonical source necessarily has a new cycling job.
- Existing actual-running cache progress/“Continue in background” UI remains unchanged and may continue to use definitive wording once job state is known.
- Focused policy tests cover metadata-only, canonical and mixed acceptance-time wording, including the conditional/no-assumption semantics.
