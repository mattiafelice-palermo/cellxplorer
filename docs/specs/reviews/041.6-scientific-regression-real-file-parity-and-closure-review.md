## New findings

### R4 — High: existing gcpl3 sources can retain scientifically invalid canonical capability and pinned caches after the gcpl4 downgrade to metadata-only

Affected files:
- `backend/app/services/scanner.py`
- `backend/app/services/parsing.py`
- `backend/app/services/analysis_engine.py`
- focused upgrade/regression tests for BioLogic parser-identity transition
- any startup/upgrade service chosen to own the one-time capability correction

**Current**

The gcpl4 fix correctly makes newly inspected/registered verified MPR sources metadata-only. However, an existing SourceFile created by the earlier gcpl3 implementation can already persist all of the following:

- `parse_status="parsed"`;
- `parser_version="bm:gcpl3:r1"`;
- `header_meta.capabilities.canonical_cycling=true` from the old adapter;
- valid-looking gcpl3 raw/cycle Parquet caches;
- saved-analysis provenance pinned to `bm:gcpl3:r1`.

Startup parser-identity bring-forward detects the gcpl3→gcpl4 mismatch and attempts a current cache rebuild. That rebuild now fails closed, which is scientifically correct. But `_apply_capacity_source_result()` handles the failure by recording `parse_error` and, when the old capacity summary was already ready, deliberately leaves the existing summary and parser registration intact. It does **not** convert the SourceFile to `metadata_only`, replace the stale header capability, clear/disable the old parsed state, or otherwise mark gcpl3 scientific output as unusable.

`analysis_engine.canonical_cycling_capability()` blocks analysis only when `parsing.source_record_metadata_only(source)` is true. That helper trusts the persisted `parse_status`/`header_meta`; an upgraded gcpl3 row still says parsed/canonical. In addition, saved-analysis provenance intentionally resolves pinned historical parser identities when `use_current_versions=False`, so a saved analysis can continue resolving `bm:gcpl3:r1` and consume the old cache generation even though R2 established that gcpl3's cycle grouping was scientifically unverified.

This is not the normal “preserve historical parser output for reproducibility” case: gcpl3 canonical cycling has now been explicitly rejected as scientifically unsupported. Preserving it as renderable scientific truth defeats the purpose of the gcpl4 fail-closed correction.

**Target**

Add an explicit, deterministic upgrade path for BioLogic sources produced by the unsafe gcpl3 canonical implementation. On first run/current-state reconciliation, such sources must be reclassified to the truthful gcpl4 metadata-only capability without requiring a successful canonical cache build. Existing gcpl3 cache files may be retained for forensic/cleanup purposes if desired, but no live Cell preview, saved analysis, recompute, portable scientific export, or other scientific consumer may continue treating them as valid canonical cycling data.

The correction should be relational/bounded and should not create per-row file reads on list paths. Reuse existing parser-identity/startup reconciliation patterns rather than adding a generic BioLogic branch inside scientific calculations.

**Acceptance criteria**

- A regression fixture starts from a persisted BioLogic SourceFile representing the old gcpl3 state (`parsed`, `bm:gcpl3:r1`, old canonical capability, old gcpl3 cache/provenance) and exercises the normal upgrade/startup reconciliation path.
- After reconciliation, the SourceFile is truthfully metadata-only for the current verified layout (`parse_status`/capability state cannot advertise canonical cycling), with current gcpl4 identity recorded according to the chosen ownership model.
- A saved analysis pinned to `bm:gcpl3:r1` is blocked with the normal `canonical_cycling_unavailable` capability response rather than rendering the old gcpl3 cache.
- Current Cell/cycle preview, analysis recompute, warmup/background preparation, and portable scientific export cannot consume old gcpl3 canonical caches once the source has been reclassified.
- The fix does not delete or rewrite unrelated Neware/Excel caches and does not require a `CALC_VERSION` bump for unrelated formats.
- If old gcpl3 cache files are retained, their existence cannot make the source appear scientifically usable; if removed, cleanup remains conservative with respect to unrelated/pinned cache generations.
- Focused tests cover both an online old source and an offline/unavailable old source so the scientific downgrade does not depend on rereading the original file successfully.
