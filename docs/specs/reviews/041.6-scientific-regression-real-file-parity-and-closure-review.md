#### R6 — High: metadata-only acknowledgement is still keyed to staged name, not immutable source identity, and the required end-to-end regression is absent

Affected files:
- `frontend/src/components/ContinuedImportEditor.tsx`
- `frontend/src/continuationPolicy.ts`
- `frontend/src/pages/InboxPage.tsx`
- `backend/app/services/continuations.py` and/or the chosen owner of confirmation-finding identity
- `tests/test_import_flow.py`
- `frontend/tests/multiSourceImport.test.ts`

**Current**

`ContinuedImportEditor` correctly includes each draft's hash in the continuation-inspection React Query key:

```text
staged_name : hash : source_path
```

so a source whose bytes are re-inspected under the same staged key is intentionally a different query/source identity. The editor then preserves checked confirmations across returned results with `preserveAcknowledgements()`, which retains any acknowledgement whose finding ID still exists.

For `metadata_only_source`, however, the backend finding ID is generated from the finding code plus `source_keys=[staged_name]`; the source content hash is not part of the finding identity. Therefore a new result for different bytes under the same `staged_name` produces the same metadata-only finding ID. The old checkbox acknowledgement survives, and `acknowledgedMetadataOnlySourceKeys()` can authorize `allow_metadata_only=true` for the new bytes without a fresh user acknowledgement.

That directly violates R6's existing acceptance criterion that re-inspecting/replacing a source must not transfer acknowledgement to a different source. CellXplorer's source identity is the content hash, so request-local staged name alone is insufficient for an acknowledgement that authorizes a scientific capability limitation.

The added frontend regression tests only exercise the helper functions with static source keys. No backend test was added in this round, and the existing import-flow tests cover single-source metadata-only registration and attachment to an existing Cell, not the **initial multi-source “one continued cell” `/api/imports/cells` path** required by R6. A regression in final payload construction or registration could therefore still pass the new helper tests.

**Target**

Bind the metadata-only confirmation to the immutable inspected source identity, or explicitly clear/reissue the acknowledgement whenever that identity changes. Preserve acknowledgement across harmless reorder of the same source, but never across a content-hash change. Add an end-to-end continued-import regression through the real final import request/registration path.

**Acceptance criteria**

- Changing a draft's inspected hash while retaining the same `staged_name` invalidates the previous metadata-only acknowledgement; submission remains blocked until the new server-issued confirmation is acknowledged.
- Reordering the same hash/source may preserve its acknowledgement; removing a source removes its authorization.
- The final `/api/imports/cells` payload sets `allow_metadata_only=true` only for the exact currently acknowledged source identity.
- A focused backend import-flow test creates one new continued Cell from multiple staged sources including metadata-only MPR, acknowledges the required findings, runs the normal initial import registration path, and proves registration succeeds with no MPR cycling-cache job.
- A matching unacknowledged case is rejected by the real final-registration/continuation validation path.
- Frontend coverage includes the hash-change/re-inspection case, not only two static staged-name examples.

## New finding

### R9 — High: R8 changed the supported MPR binary-decoding contract without advancing the BioLogic parser identity

Affected files:
- `backend/app/services/biologic_gcpl.py`
- `backend/app/services/parsing.py`
- `backend/app/services/scanner.py` or the chosen bounded upgrade/reconciliation owner
- `tests/test_biologic_closure.py`
- parser-identity/reader tests and durable BioLogic/canonical-cycling documentation

**Current**

R8 materially changed production binary decoding: before `82e5119`, the reader accepted both the observed 16-ID/53-byte sequence and an inferred 15-ID/49-byte Ece-omitted sequence; after `82e5119`, `_decode_vmp_data()` accepts only the observed 16-ID/53-byte sequence and explicitly rejects the 15-ID variant.

Parent 041 locks this rule:

```text
The MPR adapter revision must change when binary decoding or GCPL canonical mapping semantics change.
```

Despite that binary-contract change, `BIOLOGIC_GCPL_ADAPTER_REVISION` remains `gcpl4`, so the effective persisted identity remains `bm:gcpl4:r1`.

This is not only bookkeeping. A 15-ID MPR registered during the earlier gcpl4 checkpoint can already exist as `parse_status="metadata_only"`, `parser_version="bm:gcpl4:r1"`, with persisted header/capability metadata produced by the now-withdrawn layout. Because metadata-only sources are intentionally excluded from normal cache bring-forward and the explicit retirement list currently covers only `bm:gcpl3:r1`, that persisted row can continue to look like a current supported gcpl4 registration even though a fresh read of the same binary layout now fails as unsupported.

Thus fresh-reader fail-closed behavior and persisted source provenance can disagree.

**Target**

Advance the BioLogic adapter/parser identity for the R8 binary-contract change and define a bounded upgrade path for already persisted gcpl4 MPR registrations. The upgrade must not require unbounded source-file reads on list/request paths and must distinguish the observed 16-ID layout from the withdrawn synthetic-only 15-ID layout using persisted evidence where safely available or a deliberate reinspection state where it is not.

**Acceptance criteria**

- The current BioLogic parser identity advances beyond `bm:gcpl4:r1` for the post-R8 binary contract; all parser-identity tests/docs are updated consistently.
- A persisted pre-R8 gcpl4 source representing the withdrawn 15-ID layout is not silently presented as current/supported after upgrade. Its lifecycle/capability state truthfully indicates that the layout is unsupported or requires reinspection; it cannot gain canonical scientific availability.
- A persisted gcpl4 source whose stored header proves the observed 16-ID/53-byte layout is brought to the new current metadata-only identity by a bounded, deterministic path, including when the original file is offline if the persisted evidence is sufficient.
- Upgrade handling does not reread every source on list endpoints, does not touch unrelated Neware/Excel identities, and does not require a `CALC_VERSION` bump.
- Focused regression tests start from both relevant pre-R8 gcpl4 persisted states and prove the post-upgrade capability/parser identity behavior.
