## New findings

### R6 — High: metadata-only acknowledgement in the continued-cell import UI is not propagated to final source registration

Affected files:
- `frontend/src/components/ContinuedImportEditor.tsx`
- `frontend/src/pages/InboxPage.tsx`
- focused frontend/import-flow tests for continued metadata-only sources

**Current**

The continued-cell flow correctly asks the server to inspect each staged source with `allow_metadata_only: draft.metadata_only`, receives `metadata_only_source` confirmation findings, and requires the user to tick those confirmation checkboxes before `continuedImportCanSubmit()` enables **Import one continued cell**.

However, the final import payload does not derive each source's `allow_metadata_only` from those accepted continuation findings. In `InboxPage.tsx`, continued-mode sources are serialized with:

```text
allow_metadata_only: item.metadata_only && item.metadata_only_acknowledged
```

The continuation editor never sets `metadata_only_acknowledged`; its acknowledgement state is a separate `Set<string>` of finding IDs and is passed only as the cell-level `acknowledged_finding_ids` array.

The backend final-registration boundary independently requires each metadata-only `ImportSourceDraft.allow_metadata_only` to be true; otherwise `_prepare_import_source_file()` returns `422 metadata_only_source_requires_acknowledgement`. Therefore a user can satisfy the visible continuation acknowledgement, reach an enabled Import button, and still be rejected at final registration.

This affects the only currently supported real MPR lifecycle state, because the verified MPR layout is intentionally metadata-only.

**Target**

Make the continued-cell acknowledgement path authoritative end to end. Once the user acknowledges the server-issued metadata-only confirmation for a staged source, the final continued import request must set `allow_metadata_only=true` for that exact source (or use one other server-verifiable representation with equivalent semantics). Do not bypass the server's final per-source acknowledgement check.

**Acceptance criteria**

- A continued import containing one or more metadata-only MPR sources can be submitted after the visible confirmation findings are acknowledged.
- The final `/api/imports/cells` payload carries per-source metadata-only acknowledgement that matches the server-issued findings/source keys; it does not depend on the separate-cell `metadata_only_acknowledged` draft flag unless that flag is explicitly synchronized by the continuation editor.
- Removing/reordering/re-inspecting sources cannot accidentally transfer an acknowledgement to a different source.
- Without acknowledgement, the continued import remains blocked in the UI and/or rejected by the backend.
- Focused tests cover a successful continued metadata-only submission and the unacknowledged rejection path.

### R7 — Medium: continued-cell source list exposes a Raw data action for a source that is intentionally incapable of canonical raw data

Affected files:
- `frontend/src/components/ContinuationSourceList.tsx`
- `frontend/src/components/ContinuedImportEditor.tsx`
- focused frontend policy/component tests

**Current**

`ContinuedImportEditor` passes `onRawData` to `ContinuationSourceList` for the whole chain. `ContinuationSourceList` renders **Raw data** whenever that callback exists, without checking `source.metadata_only` / `source.canonical_cycling`.

For the verified MPR layout, metadata-only is a deliberate scientific capability state: canonical raw rows are unavailable, and the backend raw/preview path returns the stable `canonical_cycling_unavailable` response. The separate-cell import path already suppresses raw-data behavior for metadata-only sources, but the continued-cell source list still exposes a guaranteed-failing action.

**Target**

Hide or disable Raw data for sources whose returned capability says metadata-only / canonical cycling unavailable, using the same capability-driven policy as the rest of the UI. Do not infer capability from file extension.

**Acceptance criteria**

- Metadata-only continuation sources do not expose an enabled Raw data action.
- Canonical-capable continuation sources retain the existing action.
- The policy is driven by `metadata_only` / `canonical_cycling`, not `.mpr` string checks.
- Focused frontend coverage prevents this action from reappearing for metadata-only sources.

### R8 — High: production accepts an Ece-omitted 49-byte two-electrode MPR binary layout that is not independently evidenced by a project-owned real file

Affected files:
- `backend/app/services/biologic_mpr.py`
- `tests/test_biologic_mpr.py`
- `tests/biologic_mpr_fixture.py`
- `docs/biologic-mpr-format.md`
- `docs/specs/041.1-independent-mpr-container-and-data-reader.md`
- `docs/specs/041.3-gcpl-settings-protocol-and-three-electrode-semantics.md`

**Current**

The independent byte evidence recorded by 041.1 establishes one real production data layout: the supplied GCPL6 file has 16 encoded IDs

```text
1,2,3,21,31,65,131,4,7,13,5,6,9,39,211,468
```

and a 53-byte record. The format notebook's direct-byte offsets/hex observations and the private-sample implementation record all describe that 16-column three-electrode layout.

Production nevertheless also accepts `SUPPORTED_TWO_ELECTRODE_COLUMN_IDS`, defined as the same ID sequence with ID 9 (`Ece`) simply removed, and constructs a compact 49-byte packed dtype by shifting the subsequent fields left by four bytes. The associated test generates those 49 bytes itself and labels them a verified Ewe-primary record, but no project-owned real two-electrode MPR observation is recorded for the 15-ID sequence, its 49-byte record size, or the shifted offsets.

Under Parent 041 / 041.1, unknown or alternate record layouts must be supported only after independent evidence establishes their ID sequence, widths and offsets. A synthetic fixture can regression-test a known contract; it cannot establish that EC-Lab actually serializes the alternate contract that way. The current path therefore promotes an inferred binary layout to production support despite the project's explicit fail-closed provenance rule.

**Target**

Until a privacy-approved/project-owned two-electrode MPR independently demonstrates the Ece-omitted sequence and packed offsets, production must reject that 15-column variant as unsupported. Keep the two-electrode semantic design in the adapter/spec, but do not claim or decode a binary layout that has not been observed.

If real evidence later confirms the exact 49-byte contract, record the observations in the format notebook and then re-enable the layout with evidence-backed tests.

**Acceptance criteria**

- Production no longer accepts the Ece-omitted 15-column/49-byte layout solely because it is an order-preserving subset of the verified 16-column layout, unless independent project evidence is added.
- `docs/biologic-mpr-format.md` clearly distinguishes observed real layouts from synthetic future/regression layouts.
- Tests do not label project-authored bytes as verification of an EC-Lab binary layout.
- A synthetic Ece-omitted file is rejected as unsupported while the layout is unverified, or a real evidence record is added that independently proves the exact ID sequence, record width and offsets.
- The three-electrode verified 53-byte reader path remains unchanged.
