## Findings

### R1 — High: Scanner ingestion leaves a replaced invalid Excel source falsely `online`

Affected files:
- `backend/app/services/scanner.py`
- `tests/test_source_and_replicates.py`

**Current**

`scanner.ingest_path()` computes the new hash and, for new content, now calls `parsing.read_header_metadata(path)` plus `ensure_supported_source_metadata(...)` **before** it queries `SourceFile.path == str(path)` and marks an existing source at that path as `location_status="changed"`.

For a previously registered valid `.xlsx` whose bytes are replaced in place by a corrupt or unrelated workbook, the Excel structure check raises before the existing `SourceFile` is marked changed. The scanner job records an error, but the registered source can remain `location_status="online"` / `parse_status="parsed"` even though the bytes currently present at its stored path no longer match the registered hash.

This regresses the pre-existing scanner ordering, where same-path new content was marked changed before attempting to create/adopt the new source, and it violates 039.3's conservative source-lifecycle contract. The old identity/cache should remain recoverable, but the status must not imply that the registered bytes are still present and current.

The added `test_invalid_xlsx_scan_does_not_create_or_dirty_a_source` covers only an invalid workbook at a path with **no existing SourceFile**. `test_invalid_xlsx_replacement_preserves_existing_source_identity` exercises `update_source_from_path()`, not the recursive scanner `ingest_path()` path where this ordering defect exists.

**Target**

Preserve the existing registered source identity and last usable cache when same-path replacement bytes are invalid, but ensure scanner ingestion truthfully marks the registered source as changed (or the exact existing source-lifecycle failure state established by current scanner policy) before returning the parser error. Do not create/adopt a second invalid SourceFile and do not delete the old cache.

**Acceptance criteria**

- Start with a registered valid `.xlsx` SourceFile at path P, then replace P with an unrelated/corrupt `.xlsx` whose hash differs.
- Calling the scanner ingestion path rejects the replacement with the structured Neware error.
- The original SourceFile hash, parser version, row/cycle counts and usable old cache remain unchanged.
- No second SourceFile is created for the invalid replacement.
- The original SourceFile no longer remains falsely `online`; its status reflects that the path contents changed under the existing source-lifecycle vocabulary.
- The scan job records the failure without losing recoverability.
- Existing valid new-source and same-hash relink behavior remains unchanged.

### R2 — Medium: The required mixed-format continuation proof is not implemented

Affected files:
- `tests/test_import_flow.py` and/or `tests/test_continuations.py`
- implementation files only if the missing test exposes a real defect

**Current**

039.3 explicitly requires proof that a `.xlsx` source can participate in an ordered Cell source chain **only when the existing continuation compatibility rules allow it**, without format-based relaxation. The required test matrix also calls for an `.xlsx` continuation position and preservation of the one-internal-Test invariant.

The new `test_structured_xlsx_continuation_uses_the_normal_source_chain_path` inspects one standalone Excel source through `_continuation_staged_source()` and asserts only that its extension is accepted and its inspection is pending. It does not construct a mixed binary/Excel chain, run the pairwise compatibility/acknowledgement rules, persist the ordered sources, assert `TestFile.position`, or prove that one and only one internal `Test` remains attached to the Cell.

Therefore the child does not yet provide the required regression evidence that mixed-format continuation semantics remain format-neutral and conservative.

**Target**

Add focused mixed-format continuation tests using the existing continuation inspection/registration seams. The tests must exercise real existing rules rather than introducing a special Excel compatibility path.

**Acceptance criteria**

- A generated/controlled `.xlsx` plus a binary-shaped/fixture source can form one ordered source chain when the existing compatibility result is submittable (including required acknowledgements, if any).
- Persisted `TestFile.position` values preserve the requested order and the Cell still has exactly one internal `Test`.
- A mixed-format pair that violates an existing blocking rule remains blocked; format difference itself neither grants nor removes compatibility.
- Existing continuation findings/acknowledgement IDs are used unchanged; no `.xlsx`-specific compatibility rule is added merely to satisfy the test.

### R3 — Medium: Required Excel source-lifecycle verification stops short of stable update/source-monitor coverage

Affected files:
- `tests/test_source_and_replicates.py`
- `tests/test_source_monitor.py`
- implementation files only if these tests expose defects

**Current**

Child 039.3 defines an explicit required scanner/source-lifecycle matrix, including unchanged online behavior, offline behavior, valid changed-workbook adoption, changing/growing deferral, old-cache recoverability and confirmation that the source monitor does not exclude `.xlsx` through a stale binary-only assumption.

The implementation adds good Excel-specific coverage for scanner discovery, new-source persistence, invalid new workbook rejection and invalid replacement via `update_source_from_path()`. However, `tests/test_source_monitor.py` is unchanged, and there is no Excel-specific regression that drives a **valid changed `.xlsx`** through the stable replacement path or drives a registered `.xlsx` through the monitor's unchanged/offline/changing states. The focused suite passing existing `.nda/.ndax` lifecycle tests demonstrates generic behavior, but it does not prove the new source format is actually included at each required lifecycle seam.

This matters because 039.3 is specifically the source-lifecycle integration child and R1 already shows that a format-specific validation insertion can alter lifecycle state ordering even when generic tests remain green.

**Target**

Complete the required Excel lifecycle regression matrix with generated structured workbooks, reusing the current source-monitor and stable-update code paths. Do not add Excel-specific lifecycle logic unless a test demonstrates it is necessary.

**Acceptance criteria**

- A registered unchanged `.xlsx` remains online without unnecessary adoption/reparse under the current monitor policy.
- A missing registered `.xlsx` becomes offline under the existing policy.
- A valid, stable changed `.xlsx` is adopted through `update_source_from_path_if_stable`, with new hash/parser counts/capacity state visible only after successful validation/build; old cache cleanup follows the existing success rule.
- A growing/changing `.xlsx` is deferred without mutating the registered identity.
- At least one source-monitor test uses `SourceFile.ext="xlsx"` / an `.xlsx` path and proves no stale extension filter excludes it.
- The invalid-replacement case from R1 preserves the old usable state while reporting the changed path truthfully.
