## Findings

### R1 — High: Scanner ingestion leaves a replaced invalid Excel source falsely `online`

Affected files:
- `backend/app/services/scanner.py`
- `tests/test_source_and_replicates.py`

**Current**

`scanner.ingest_path()` computes the new hash and, for new content, now calls `parsing.read_header_metadata(path)` plus `ensure_supported_source_metadata(...)` **before** it queries `SourceFile.path == str(path)` and marks an existing source at that path as `location_status="changed"`.

For a previously registered valid `.xlsx` whose bytes are replaced in place by a corrupt or unrelated workbook, the Excel structure check raises before the existing `SourceFile` is durably marked changed. The scanner job records an error, but the registered source can remain `location_status="online"` / `parse_status="parsed"` even though the bytes currently present at its stored path no longer match the registered hash.

This regresses the previous scanner ordering and violates the conservative source-lifecycle contract. The old source identity/cache must remain recoverable, but status must not imply that the registered bytes are still present and current.

The added invalid-Excel scanner test covers only an invalid workbook at a path with **no existing SourceFile**. The invalid replacement test exercises `update_source_from_path()`, not recursive scanner `ingest_path()`.

**Target**

Preserve the existing registered source identity and last usable cache when same-path replacement bytes are invalid, but ensure scanner ingestion truthfully and durably marks the registered source as changed (or the exact established source-lifecycle failure state) before returning the structured parser error. Do not create/adopt a second invalid SourceFile and do not delete the old cache.

**Acceptance criteria**

- Start with a registered valid `.xlsx` SourceFile at path P, then replace P with unrelated/corrupt `.xlsx` bytes whose hash differs.
- Calling scanner ingestion rejects the replacement with the structured Neware error.
- The original SourceFile hash, parser version, row/cycle counts and usable old cache remain unchanged.
- No second SourceFile is created for the invalid replacement.
- The original SourceFile no longer remains falsely `online`; its persisted status reflects that path contents changed under the existing lifecycle vocabulary.
- The scan job records the failure without losing recoverability.
- Existing valid new-source and valid same-format relink behavior remains intact.

### R2 — Medium: The required mixed-format continuation proof is not implemented

Affected files:
- `tests/test_import_flow.py` and/or `tests/test_continuations.py`
- implementation files only if the missing tests expose a real defect

**Current**

039.3 explicitly requires proof that a `.xlsx` source can participate in an ordered Cell source chain **only when existing continuation compatibility rules allow it**, without format-based relaxation. The required matrix also calls for an `.xlsx` continuation position and preservation of the one-internal-Test invariant.

The new `test_structured_xlsx_continuation_uses_the_normal_source_chain_path` inspects one standalone Excel source through `_continuation_staged_source()` and asserts only that its extension is accepted and inspection is pending. It does not construct a mixed binary/Excel chain, run pairwise compatibility/acknowledgement rules, persist ordered sources, assert `TestFile.position`, or prove exactly one internal `Test` remains attached to the Cell.

**Target**

Add focused mixed-format continuation tests using existing continuation inspection/registration seams. Exercise the actual existing rules rather than introducing a special Excel compatibility path.

**Acceptance criteria**

- Persisted `TestFile.position` values preserve the requested order and the Cell still has exactly one internal `Test`.
- A mixed-format pair that violates an existing blocking rule remains blocked; format difference itself neither grants nor removes compatibility.
- Existing continuation finding/acknowledgement IDs are used unchanged; no `.xlsx`-specific compatibility rule is added merely to satisfy the test.

However, `tests/test_source_monitor.py` is unchanged, and there is no Excel-specific regression that drives a **valid changed `.xlsx`** through the stable replacement path or a registered `.xlsx` through monitor unchanged/offline/changing states.

Generic `.nda/.ndax` lifecycle tests demonstrate the shared mechanics, but they do not prove the newly inserted Excel structure-validation seam participates correctly. **Target**

### R4 — High: Exact-hash scanner relinking bypasses the Excel format contract and leaves persisted extension stale

Affected files:
- `backend/app/services/scanner.py`
- `tests/test_source_and_replicates.py`

**Current**

`scanner.ingest_path()` queries `SourceFile.hash == file_hash` immediately after hashing. If that hash is already known, it relinks `path`/`filename`, marks the source online, records the new stat signature, commits and returns **before** `read_header_metadata()` / `ensure_supported_source_metadata()` is called. It also does not update `existing.ext` on the relink.

This fast path was safe when scanner discovery was limited to the two Neware binary extensions handled by the same parser family. With `.xlsx`, the suffix selects a different parser and the path itself makes a format claim that must be structurally verified.

Concrete failure: take the bytes of a registered valid `.nda/.ndax` source and expose/copy them at a new filename ending in `.xlsx`. The SHA-256 is identical, so scanner ingestion relinks the existing source to that `.xlsx` path without checking workbook structure. The source is marked `online`, `ext` remains the old binary value, and later parsing dispatches by the **new path suffix** to the Excel parser, which cannot parse those bytes. The database therefore contains an internally inconsistent path/extension/parser state while an arbitrary non-workbook `.xlsx` has bypassed the locked structure rejection.

The inverse parser-family rename (a known Excel source relinked to a binary suffix) likewise leaves `SourceFile.ext` inconsistent with the relinked path and can route future parsing through the wrong parser family.

No added test exercises the existing-hash relink branch with an Excel/binary parser-family boundary.

**Target**

Keep content-hash relinking, but do not let an exact hash bypass the source-format contract when the relinked path changes parser family. A relinked source must end with coherent path suffix, persisted `ext`, and parser contract. Same-format/same-parser-family relinking should remain cheap and preserve existing behavior.

Do not add a full point-level parse merely to relink a known valid `.xlsx` to another `.xlsx` path. The fix should be the smallest conservative guard needed around parser-family/Excel structure transitions.

**Acceptance criteria**

- Start with a registered binary Neware source of hash H; present the exact same bytes at `renamed.xlsx`; scanner ingestion must not relink that source as a valid Excel workbook. The original source path/extension/status remains coherent and no invalid second source is created.
- A valid structured `.xlsx` of known hash moved/copied to another `.xlsx` path still relinks successfully without creating a duplicate SourceFile.
- After every accepted relink, `SourceFile.ext` agrees with the path suffix/parser family.
- A relink across the Excel/binary parser-family boundary is either rejected conservatively or independently proven valid under the target parser contract before adoption; it must never leave a path/ext/parser mismatch.
- Existing `.nda`/`.ndax` same-family relink behavior is not unnecessarily broadened or redesigned.
- Existing cache identity/content remains untouched by a rejected invalid relink.
