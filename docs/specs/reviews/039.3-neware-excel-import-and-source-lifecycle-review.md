## Findings status

### R1 — High: Scanner same-path invalid Excel replacement status — **RESOLVED**

`scanner.ingest_path()` now queries the registered same path and durably sets `location_status="changed"` before validating the new metadata. If the replacement `.xlsx` is unrelated/corrupt, validation raises while the old hash, parser version, row/cycle counts, parse state and cache identity remain untouched. The focused regression confirms no second SourceFile is created and old-cache deletion is not invoked.

The surrounding scanner job already records ingestion exceptions through its existing error path; no Excel-specific job mechanism was added.

### R2 — Medium: Mixed-format continuation proof — **RESOLVED**

The follow-up constructs an ordered binary/Excel draft chain and runs the existing continuation inspection/submittable path before registration. It then verifies:

- exactly one internal `Test` for the Cell;
- `TestFile.position == [0, 1]`;
- persisted source extensions/order `ndax`, `xlsx`;
- source filenames remain in requested order.

It also mutates the analyzed pair into an existing generic `duplicate_hash` blocking condition and confirms the same blocker prevents submission. No Excel-specific compatibility rule or acknowledgement identifier was added.

The binary side is controlled/mocked at the parser/cache boundary because this test owns continuation semantics rather than binary parsing; the Excel source is a generated structured workbook. That is sufficient for the locked format-neutral continuation contract.

### R3 — Medium: Excel stable-update/source-monitor lifecycle proof — **RESOLVED**

The follow-up adds generated `.xlsx` coverage for the required lifecycle seams:

- unchanged registered workbook remains online without hashing/adoption;
- missing workbook becomes offline;
- stable changed workbook is detected and adopted through the source-monitor update path, with new hash, extension, parse state, row/cycle counts and successful old-cache cleanup verified;
- growing/changing workbook is deferred and retains the registered hash while becoming `changing`;
- the tests use real `SourceFile.ext="xlsx"` paths, proving the source monitor does not exclude Excel through a stale extension gate.

The stable adoption test mocks the expensive metadata/cache result but uses a real generated workbook for path/hash/stat behavior. The production `update_source_from_path_if_stable()` path independently shows metadata validation and cache build occur before SourceFile identity mutation, then applies parser/count/capacity summaries and removes the replaced cache only after successful adoption. Existing generic tests continue to own the detailed capacity-summary field semantics.

### R4 — High: Exact-hash scanner relink parser-family consistency — **RESOLVED**

A new `source_parser_family()` distinguishes Excel from the shared NDA/NDAX binary family. For an existing content hash, `scanner.ingest_path()` now rejects unsupported/cross-family relinks before mutating the SourceFile. Accepted same-family relinks update `path`, `filename` and persisted `ext` coherently.

Focused regressions verify:

- binary bytes exposed at an `.xlsx` path are rejected without changing the original binary SourceFile;
- a known valid structured `.xlsx` relinks to another `.xlsx` path without duplication;
- `.nda`→`.ndax` same-family relinking remains supported and updates `ext`.

Because an `.xlsx`→`.xlsx` relink has identical bytes to an already registered/validated Excel source, it does not reopen or point-parse the workbook; the hash identity itself is sufficient inside the same parser family. This preserves the cheap relink path while preventing format-contract bypass.
