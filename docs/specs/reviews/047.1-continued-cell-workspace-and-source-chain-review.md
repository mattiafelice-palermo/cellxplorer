## Findings

### R1 — High: the source chain is inert until continuity inspection returns

Affected files:
- `frontend/src/components/ContinuedImportEditor.tsx`

**Current**

The workspace derives its interaction lock from the inspection query's pending status:

```ts
const disabled = inspectionQuery.isPending || importing;
```

`inspectionQuery` is `enabled: opened && inspectionRequested && orderedDrafts.length >= 2`. In
TanStack Query v5 a query that is disabled and has never resolved reports `status: "pending"`, so
`isPending` is `true`. Confirmed directly against the installed v5.101.2:
`status = pending | isPending = true | fetchStatus = idle`.

Therefore `disabled` is `true` on entry to continued mode, before the user has requested inspection.
That value is propagated into the compact source list as:

```tsx
onDragStart={disabled ? undefined : setDragIndex}
onDrop={disabled ? undefined : (index) => { ... }}
onRemove={disabled ? undefined : (sourceKey) => { ... }}
disabled={disabled}
```

and inside the list `draggable={Boolean(onDragStart) && !disabled}`, with the up/down
`ActionIcon`s taking `disabled={disabled || ...}` and the remove control rendered only
`{onRemove && ...}`. `move(...)` also early-returns on `disabled`.

The result in the default state of the pane this child exists to deliver:

- rows are not draggable;
- up/down reorder buttons are disabled;
- the remove control is not rendered at all;
- so a source can be neither reordered nor removed until the user clicks **Inspect continuity**
  and it completes.

There is a second occurrence of the same root cause. `order` is part of the query key:

```ts
queryKey: ["continued-import-inspection", order, drafts.map(...).join("|")]
```

so every reorder produces a new key with no data, `isPending` returns to `true`, and the list locks
again for the duration of the next inspection round-trip (which polls at 1 s until
`inspection_complete`). Sequential reordering — move a source up twice, or drag then correct with the
arrows — is blocked between steps.

This contradicts 047.1's acceptance criteria ("source rows are compact, draggable and
keyboard-reorderable"), spec section C3 ("Drag-and-drop remains first-class", "Keep up/down
controls"), section C4 ("using drag/up/down does not lose selection"), section H ("Remove"), and
Parent 047's Source-chain acceptance criteria ("Rows remain draggable", "Up/down controls remain
usable without drag-and-drop", "Remove uses stable source identity"). Manual checks 5, 6, 7 and 10
in the spec would fail as written.

The expression is carried over verbatim from the pre-047.1 editor, so this is inherited rather than
newly written. It is reported here because 047.1 is the child that owns this pane and asserts these
behaviors as acceptance criteria, and because the compact variant makes the lock more damaging:
removal is now the only way to drop a source in continued mode, and pre-inspection it is invisible.

**Target**

Ordering and removal are available whenever the workspace is otherwise editable. The interaction
lock must reflect work actually in flight, not the absence of a never-requested query — for example
`inspectionQuery.isFetching` (true only during a real fetch) combined with `importing`, or an
explicit "inspection in flight" flag. Reordering before any inspection, and reordering repeatedly
without waiting for each re-inspection to settle, must both work.

Whatever lock is chosen must still keep submission safety intact: `canSubmit` already requires a
complete, submittable `ContinuationInspectResult`, so an order changed after inspection continues to
gate import through `continuedImportCanSubmit(...)` until the new inspection resolves. Do not relax
that.

**Acceptance criteria**

- With 2+ staged sources in continued mode and no inspection requested, rows are draggable, both
  up/down buttons are enabled (except at the list ends), and the remove control is rendered and
  enabled.
- After an inspection completes, reordering twice in succession does not require waiting for an
  intermediate inspection to finish.
- `canSubmit` remains false while the current order has no complete/submittable inspection result;
  blocking findings and confirmation acknowledgement remain enforced exactly as today.
- Spec manual checks 5, 6, 7 and 10 recorded as PASS from an actual browser run.

**Round 2 — RESOLVED** (`5de11c3`)

`disabled` is now `importing` alone; the inspection query is not consulted for the interaction lock at
all. Rows are draggable and up/down/remove are rendered and enabled from entry into continued mode,
and a reorder no longer re-locks the list while the next inspection round-trip runs, so successive
reorders never wait on an intermediate inspection. Submission safety is intact and was re-verified at
the mechanism level rather than accepted on assertion: the inspection query declares no
`placeholderData`, the app `QueryClient` in `main.tsx` sets only `retry` / `retryDelay` /
`refetchOnWindowFocus` as query defaults, and `startupQueryPersistence` calls `setQueryDefaults` only
to set `gcTime` on startup keys. `inspectionQuery.data` therefore really is `undefined` for a
reordered key with no cache entry, and `buildContinuedImportSubmissionState` passes that `undefined`
into `continuedImportCanSubmit(...)`, which returns `false` on a falsy result — so `canSubmit` still
drops to false the moment the order outruns its last complete inspection. The acknowledgement
checkboxes are the only other consumer of `disabled`, and they render only inside a
`confirmationIds.length > 0` branch that requires a present `result`, so widening the lock cannot
expose them without a matching inspection.

### R2 — Medium: the row's Enter/Space handler suppresses keyboard activation of its own row actions

Affected files:
- `frontend/src/components/ContinuationSourceList.tsx`

**Current**

In the `compact-import` variant, the row `Paper` is a `role="button"` with an unguarded keydown
handler:

```tsx
onKeyDown={(event) => {
  if (!onSelect) return;
  if (event.key === "Enter" || event.key === " ") {
    event.preventDefault();
    onSelect(source.key);
  }
}}
```

The handler does not check the event target, so it also runs for keydown events that originate on
the nested `ActionIcon`s (Move up, Move down, Remove) and bubble up to the row.

For a native `<button>`, the `click` that activates it is the default action of the key event
(fired on `keydown` for Enter, and on `keyup` after an uncancelled `keydown` for Space). Calling
`preventDefault()` from an ancestor listener during bubbling cancels that activation. A keyboard
user who tabs to "Move source up" and presses Enter or Space therefore does not reorder the source —
the row is selected instead. The `stop(event)` guard on each `ActionIcon`'s `onClick` does not help,
because it only stops the click, and with the keydown cancelled no click is produced.

This defeats 047.1 section C3 ("up/down buttons as the non-drag / keyboard-accessible ordering
path"), the acceptance criterion "keyboard-reorderable", Parent 047's "Keyboard access remains
available for source ordering", and spec manual check 19.

Note this is currently masked by R1 (the buttons are disabled before inspection anyway); it becomes
user-visible once R1 is fixed. Severity is Medium rather than High only because it could not be
browser-confirmed in this session; the mechanism is standard HTML activation behavior, and the fix is
correct regardless — even under the most conservative reading, the handler wrongly fires row
selection for every Enter/Space aimed at a nested control.

**Target**

The row-level Enter/Space handler acts only on keys pressed on the row itself, not on descendants.
The standard guard is an early return when `event.target !== event.currentTarget`.

**Acceptance criteria**

- Tabbing to a row's Move up / Move down / Remove control and pressing Enter or Space performs that
  control's action.
- Pressing Enter or Space with the row itself focused still selects the row and still suppresses
  page scroll for Space.
- Spec manual check 19 recorded as PASS from an actual browser run.

**Round 2 — RESOLVED** (`5de11c3`)

The row handler now early-returns on `event.target !== event.currentTarget`, which is the standard
guard named in the Target. Enter/Space pressed on a nested `ActionIcon` has that button as its
target, so the row handler returns before `preventDefault()` and the button's native activation
proceeds; the existing `stop(event)` on each icon's `onClick` still keeps the resulting click from
selecting the row. Enter/Space pressed with the row itself focused has `target === currentTarget`, so
selection and the Space scroll suppression are both unchanged.

### R3 — Low: an automatically selected source shows "Preview is available when this source is selected"

Affected files:
- `frontend/src/components/ContinuedImportEditor.tsx`

**Current**

A lazy preview request is issued only from the user-driven `selectSource(...)` path. Selection also
changes automatically in two places that do not request anything: the initial selection
(`useState(() => drafts[0]?.staged_name ?? "")`) and the neighbour chosen by `nextSelectedSourceKey`
after a removal. `InboxPage.activateDraft` explicitly skips preview loading in continued mode
(`!continuedMode && ...`), so nothing else fills the gap.

The pane then renders, for a source that is selected and highlighted in the left list:

```tsx
{selectedDraft.preview_state.status === "idle"
  ? "Preview is available when this source is selected."
  : ...}
```

which contradicts what the user sees. On first entry to continued mode the preview pane is always in
this state, and the only way out is to click the already-selected row.

Spec section E requires the preview to stay lazy and permits selection to trigger that source's
request; it does not require the initial selection to stay unloaded, and the message is wrong either
way.

**Target**

Either request the selected source's preview when selection changes automatically (still exactly one
source, still no batch load — the 035.8 / parent decision 10 lazy contract must hold), or change the
idle copy so it describes the actual state and the action that loads it.

**Acceptance criteria**

- No state exists in which the preview pane tells the user a preview is available "when this source
  is selected" while that source is selected.
- Entering continued mode issues at most one preview request, and never one per staged source.
- Existing `importPreviewPolicy` lazy-preview tests stay green.

**Round 2 — STILL OPEN** (`5de11c3`), narrowed to metadata-only sources

The fix is correct as far as it goes. The new effect keyed on `selectedSourceKey` does fire on mount
(`selectedSourceKey` is seeded from `drafts[0]`, and the `byKey` memo read inside the effect is built
from that same `drafts` array, so the initial selection resolves), it fires again for the
`nextSelectedSourceKey` fallback after a removal, and `onPreviewRequested` is wired straight to
`previewLoader.load` in `InboxPage` — not through `activateDraft`, whose `!continuedMode` guard was
the round-1 gap. The lazy contract holds: `shouldRequestImportPreview` requires
`preview_state.status === "idle"`, so re-selecting a source that is already loading, ready or errored
requests nothing, and there is still no batch.

What remains is acceptance criterion 1, for the one selection the fix cannot cover.
`shouldRequestImportPreview` also requires `!draft.metadata_only`, and `previewLoader.load`
independently hard-returns `if (draft.metadata_only) return;`. A metadata-only source is staged with
`preview_state: { status: "idle" }` and can never leave that state. Selecting one in the compact
source chain therefore still renders:

```tsx
{selectedDraft.preview_state.status === "idle"
  ? "Preview is available when this source is selected."
  : "No capacity preview points were found in this file."}
```

while that source is selected and highlighted, and clicking the row again does nothing — the same
contradiction R1's sibling finding described, on a first-class continued-mode case (metadata-only
sources have their own confirmation findings, `acknowledgedMetadataOnlySourceKeys` handling, and a
dedicated "Raw data is unavailable for a metadata-only source" tooltip in this very pane).

The second half of R3's original Target — corrected copy — is the remaining work, and separate mode
already shows the house pattern: `InboxPage` renders a `draft.metadata_only` branch *before* the
`loading / error / ready / idle` chain, with an Alert titled "Capacity preview unavailable" that
explains the limitation and that retrying will not change it. The continued-mode pane needs the
equivalent branch ahead of its status chain. No change to the effect added in round 2 is needed.

**Round 2 acceptance criteria (unchanged criteria, remaining work only)**

- Selecting a metadata-only source in continued mode shows copy that describes the actual limitation
  rather than telling the user the preview loads on selection.
- The non-metadata-only path added in round 2 stays as implemented: one request per selection change,
  no batch, no re-request for a source already loading/ready/errored.

**Round 3 — RESOLVED** (`9b86b9d`)

Both round-2 criteria are met, and the fix is scoped to exactly the render branch that was asked for.

*Criterion 1 — copy describes the actual limitation.* `ContinuedImportEditor.tsx` now opens the
Preview pane's conditional with `selectedDraft.metadata_only ? <Alert color="gray" title="Capacity
preview unavailable"> … </Alert> : selectedDraft.preview_state.status === "loading" ? …`. The branch
sits ahead of the whole `loading / error / ready / idle` chain, so a metadata-only source — which is
permanently `preview_state: idle` because `previewLoader.load` hard-returns on it — can no longer
reach the idle string that told the user the preview loads on selection. The copy is not newly
written prose: it is character-for-character the Alert `InboxPage.tsx` already renders for
`draft.metadata_only` in separate mode (`InboxPage.tsx`, under the "Quick preview" divider), so the
two modes now say the same thing about the same condition. It describes the limitation rather than
an action, and its closing sentence explicitly forecloses the retry reading. Note that the sibling
`error` branch's Retry button is inside a branch metadata-only sources can no longer reach, so there
is no control in this pane offering an action the copy says will not help.

*Criterion 2 — round-2 effect untouched.* `git diff 3266765..HEAD` is three files: this component,
plus the two workflow files. The component's diff is a single 8-line hunk containing only the new
branch. The `useEffect` keyed on `[selectedSourceKey]` that calls `onPreviewRequested` via
`shouldRequestImportPreview` is byte-identical, as are `shouldRequestImportPreview` and
`previewLoader.load` (untouched files). One request per selection change, no batch, and no
re-request for a source already loading/ready/errored all still hold on the round-2 mechanism.

*Non-metadata-only sources.* Unchanged. The previous chain is intact and merely chained after the new
ternary arm, so for `metadata_only === false` the rendered output is identical to `5de11c3`
branch-for-branch.

*Considered and not blocking.* The idle string still exists as the final fallback and is technically
reachable for a non-metadata-only source in the single frame between render and the selection effect
firing. That is a sub-frame transient of the round-2 design that round 2 already accepted, not the
persistent contradictory state acceptance criterion 1 was written against, and removing it would mean
reopening the effect that round 2 explicitly directed the implementer not to change.

Implementer tooling for this round (focused tests 30/30, `tsc --noEmit`, `vite build`, canonical
preflight 4/4 with 137 modules) was taken as given; reading raised no doubt that warranted a
spot-check, since the change is one JSX branch reusing an existing string and an existing field.

### R4 — Low: the source number circle is hidden from assistive technology

Affected files:
- `frontend/src/components/ContinuationSourceList.tsx`

**Current**

```tsx
function SourceColorCircle({ number, color }: { number: number; color?: string }) {
  return (
    <Text aria-hidden="true" ... >
      {number}
    </Text>
  );
}
```

The ordinal is the row's only non-color position indicator, and Parent 047 decision 4 makes it the
identifier that keeps color from being the sole cue; decision 5 makes the numbered circles the
visual key that 047.2's combined preview will refer to. `aria-hidden="true"` removes it from the
accessibility tree, so a screen-reader user gets the filename, the status badge and the
Historical/Tracked tail badge, but no source position — while the visual user gets "1", "2", "3".

The row's `aria-pressed` selection state and the `aria-label`s on the move/remove controls are
correct; this is the one piece of row information with no non-visual equivalent.

**Target**

Expose the source position to assistive technology while keeping the decorative circle from being
announced twice — for example drop `aria-hidden` and give the circle an accessible label such as
`Source 2`, or keep the visual element hidden and add a visually-hidden text node carrying the
position.

**Acceptance criteria**

- Each compact-import row exposes its 1-based source position to assistive technology.
- The visible numbered circle and its session color are unchanged.
- Parent 047's "Selected state is still recognizable independently from source color" remains true.

**Round 2 — RESOLVED** (`5de11c3`)

`<VisuallyHidden>Source {index + 1}.</VisuallyHidden>` sits inside the row `Paper`, which carries
`role="button"` and no `aria-label` / `aria-labelledby`, so the row's accessible name is computed
from its contents and now includes the position. Clip-based hiding does not remove a node from the
accessible name computation, unlike the `aria-hidden` circle beside it, so the ordinal is announced
exactly once. The visible circle is untouched: `SourceColorCircle` is unchanged, and Mantine's
`VisuallyHidden` root class (`m_515a97f8`) is `position: absolute` with `clip: rect(0 0 0 0)`, so as
an out-of-flow child it adds no `Group` gap and no layout shift.

## Checked and accepted (no finding)

The four scope decisions the implementer flagged were each evaluated against the spec text rather
than accepted on assertion. All four are within what the specs permit:

1. **Direct `PALETTE` import from `plotting/plotStyle.ts`.** Parent decision 4 conditions extraction
   on the direct import creating "an undesirable dependency". It does not: `components/` already
   imports from `features/analyses/` in four pre-existing places
   (`AppUpdateCoordinator`, `BetaInstallCoordinator`, `QuickSettingsMenu`, and
   `ContinuationManagementPanel`, the latter being the sibling continuation surface). `PALETTE` is
   the same array as `PLOT_PALETTES.app`, so this is the canonical app plot palette the visual style
   guide names, and no second near-identical color set was introduced. Extracting a module here
   would have been churn.
2. **Dropping "Use suggested order" from continued mode.** Spec section B states the command row
   "contains only step-specific commands" and gives a three-command target that excludes it; section
   C1's row content list also excludes it. `applySuggestedOrder` is untouched, still tested, and
   still has a live consumer in `ContinuationManagementPanel`'s attach mode, so no policy was
   orphaned.
3. **Removing the informational/warning findings Alert now.** Parent decision 7 explicitly bans
   persistent info/warning finding Alerts from the main workspace. Section B only forbids removing
   *acknowledgement requirements* in this child, and blocking findings plus the confirmation
   checklist are both still rendered. This is closer to required than to premature.
4. **Preview pane `flex: 1, minWidth: 0` instead of a 480–520 px floor.** `IMPORT_MODAL_WIDTH` is
   `78rem`; against the two fixed panes (310 + 380) and two `md` gaps the preview computes to roughly
   490 px at default geometry, i.e. inside the spec's suggested range without a hard floor. A hard
   floor would overflow `.work` (`overflow-x: auto`) on viewports narrower than the modal's
   preferred width, which is the failure class Spec 036 T6 fixed. Parent decision 2 permits adjusting
   within the range and forbids introducing a horizontal scrollbar; this choice honours both.

Also verified by reading:

- **`ContinuationSourceList` default variant is untouched.** The diff is additive only, entirely
  above the original `return`; the default branch's markup, findings rows, path/hash/protocol
  details and raw-data button are byte-identical. `ContinuationManagementPanel` passes no `variant`
  and no new props, so existing-cell continuation management renders exactly as before.
- **Backend submission safety is preserved, not weakened.**
  `buildContinuedImportSubmissionState` composes the same three checks the old inline `canImport`
  did — `scientificDraftIsValid`, `continuedImportCanSubmit(result, cellName, acknowledged)`, and a
  ≥2-source requirement — and `acknowledgedMetadataOnlySourceKeys(result, acknowledgedFindingIds,
  order)` keeps metadata-only acknowledgement bound to both the finding ID and the current source
  keys. `preserveAcknowledgements` still drops stale acknowledgements on every new result, and
  removing a source still clears the acknowledgement set.
- **One footer-owned Import action.** The internal primary button is gone;
  `ImportModal` renders `Import one continued cell` only in the idle branch of
  `ImportModalPrimaryActions`, so the existing progress / Continue in background / Done sequence is
  untouched (section F3). Submission goes through `save.mutate({ mode: "continued", ... })` with the
  projected order — no DOM query, no hidden button. The separate-mode branch and its payload are
  unchanged.
- **Cell draft independence.** `continuedCellDraft` is re-initialized only from the
  `[opened, targetFolderId]` effect, so adding, removing, reordering, selecting or recoloring a
  source cannot reset it.
- **No eager preview.** There is no `drafts.forEach(loadPreview)`; the inspection query stays behind
  the explicit `inspectionRequested` flag, and no combined/all-source preview was invented, so
  parent decisions 8 and 10 and 047.2's scope boundary hold.
- **Raw data is a button.** It is bound to the selected source and gated by
  `continuationSourceCanOpenRawData(...)`, with a tooltip explaining the metadata-only case; no table
  is embedded, and the compact rows carry no raw-data control (decision 6, section C1).
- **Colors follow source identity.** `assignContinuationSourceColors` keys off the source key, never
  the index, reuses only unused palette slots, drops removed keys, and repeats the palette on
  overflow rather than inventing colors. The mapping is component state only — not persisted, not in
  any payload.
- **No backend files touched.** Commit `1779685` changes five frontend files plus the two workflow
  files.
