## Findings

### R1 — High: The promotion matrix does not measure the integrated production P4 route

Affected files:
- `scripts/profile_analysis_family_concurrency.py`
- `backend/app/services/analysis_family_workers.py`
- `backend/app/routers/analyses.py`
- `tests/test_analysis_family_workers.py`

**Current**

`_run_serial_miss()` calls the real analysis router, but `_run_parallel_miss()` does not. It manually recreates the candidate route: it builds an owner context, uses profiler-local `_worker_jobs()`, submits `run_family_job()`, uses profiler-local `_merge_results()`, computes the result key, persists the result, and serializes it. Those profiler-local job/merge implementations duplicate, rather than invoke, the production `_worker_jobs()`, `_merge_results()` and `try_compute_family()` path in `analysis_family_workers.py`.

Consequently the recorded "post-integration" P4 timings do not include production-only policy/owner work such as the Cycles route precheck, `_owner_cache_ready()`, the actual production merge/finalization call chain, or real serial-fallback policy. The asymmetry is already observable in Cycles: S1 includes the new route-level `resolve_selection()` call while the P4 benchmark candidate bypasses that route-level work.

The exact-hit benchmark record has the same evidence problem: `_run_exact_hit()` assigns `worker_dispatch_count = 0` and `worker_job_count = 0` as constants instead of observing job construction/submission. The route is structurally above worker dispatch today, but the benchmark field itself does not prove that acceptance criterion.

**Target**

Promotion-critical P4 evidence must measure the integrated production route, with only the executor/pool lifecycle controlled by the benchmark. Benchmark-only P8 plumbing may remain isolated because P8 is not a production mode, but it must share the same production job/compute/merge core rather than maintain a second scientific/merge implementation.

Exact-hit proof must observe that no production worker job is constructed/submitted, not populate a hard-coded zero.

**Acceptance criteria**

- Rework the P4 benchmark so the 4/8/12/16 promoted-family samples traverse the actual router + production `try_compute_family()` integration with a fully warm four-worker pool.
- Remove or collapse profiler-local duplicated job/merge logic where practical; if a benchmark adapter remains, prove it calls the same production core and cannot drift semantically.
- Re-run the P4 promotion evidence for Cycles, DCIR, Rate Capability and Steps at 4/8/12/16 Cells and show the production route still clears the locked >=15% and >=10 ms gates at the selected threshold and remains favorable at larger counts.
- Preserve exact scientific, result-shape, provenance and deterministic-order parity against S1.
- Add an observed exact-hit control/test that spies on production job construction and/or pool submission and proves zero worker work.
- Canonical preflight PASS after the correction.

### R2 — Medium: P4 Rate Capability rewrites replicate-group selection contexts as direct-Cell contexts

Affected files:
- `backend/app/services/analysis_family_workers.py`
- `scripts/profile_analysis_family_concurrency.py`
- `tests/test_analysis_family_workers.py`
- relevant Rate Capability route/visibility regression tests

**Current**

Serial `rate_capability.compute()` returns `selection_contexts` from each resolved unit's real `entry_kind` and `entry_ref_id`. The P4 merge instead reconstructs every context as:

```python
{
    "cell_id": cell_id,
    "entry_kind": "cell",
    "entry_ref_id": cell_id,
}
```

This changes result semantics whenever four or more unique Cells are selected through a replicate group. The frontend uses these context fields in `isCellHiddenInAnalysis()` to decide scoped exclusions and `hidden_replicate_group_ids`; therefore a P4 result can show/hide a Rate Capability series differently from the serial result even when the scientific points themselves are identical.

The scaling fixture uses explicit Cell selections, so the current digest/parity matrix does not exercise this path.

**Target**

The P4 merge must preserve the exact owner/serial `selection_contexts` contract, including replicate-group entry identity and scoped selection semantics. The worker split may change execution ownership, not user-facing selection meaning.

**Acceptance criteria**

- Preserve/merge the original `entry_kind` and `entry_ref_id` for Rate Capability rather than synthesizing direct-Cell contexts.
- Add a 4+ Cell replicate-group P4-vs-S1 regression asserting exact `selection_contexts` parity and deterministic order.
- Cover `hidden_replicate_group_ids` and/or a scoped exclusion so the test proves the downstream visibility policy receives equivalent context.
- Retain direct-Cell behavior and exact scientific/order parity.
- Canonical preflight PASS.

### R3 — Medium: The advertised cache-only Cycles worker can derive and write a missing cycle cache

Affected files:
- `backend/app/services/analysis_family_workers.py`
- `backend/app/services/cache.py` / existing cache-read contract as applicable
- `tests/test_analysis_family_workers.py`

**Current**

Both `_owner_cache_ready()` and `_assert_cache_only()` check only for the raw Parquet file. For a Cycles job, `_compute()` reaches `analysis_engine.compute()` → `stitch_cycles()` → `cache.load_cycles()`. `load_cycles()` explicitly derives `calc.per_cycle(pd.read_parquet(raw))` and writes the cycle Parquet when the requested cycle cache is absent and the calculation version is current.

Therefore `run_family_job()` is not necessarily the read-only canonical-cache boundary described by this child: a production P4 Cycles request can perform cache rebuilding and publication inside a spawned worker. The worker process also cannot see the owner process's `_pending` write-behind registry, so a raw-present/cycles-not-yet-published state is not safely represented by the current raw-only readiness check.

**Target**

A promoted Cycles worker should execute only when the exact parser+calculation-version cycle artifact required by that job is already ready for read-only use and no owner-side in-flight publication makes that readiness ambiguous. Otherwise the request must stay/fall back to the established owner/serial path; do not move scientific cache construction into the interactive worker pool.

**Acceptance criteria**

- Make Cycles worker eligibility require the exact cycle cache identity needed by the request, not only raw-cache existence.
- Account for owner-side in-flight cache publication before cross-process dispatch so a spawned worker does not infer readiness from stale process-local state.
- Add a focused raw-present/cycles-missing test proving the P4 worker path is not dispatched and does not call cycle-cache write/derivation code.
- Add/retain a ready-cycle-cache case proving normal P4 dispatch still works.
- Preserve pinned parser/calc-version reproducibility and serial fallback behavior.
- Canonical preflight PASS.

### R4 — Medium: Cycles adds redundant selection/context work to every result-cache miss, including ineligible small requests

Affected files:
- `backend/app/routers/analyses.py`
- `backend/app/services/analysis_family_workers.py`
- focused Cycles route/performance tests

**Current**

After a Cycles result-cache miss, the route now calls `engine.resolve_selection(db, spec)` only to decide whether P4 might be eligible. For four eligible Cells it then calls `try_compute_family()` without a `request_context`, causing that helper to build the request context/resolution again. If the helper falls back, `engine.compute()` is also called without that context. For 1–3 Cell requests, which can never use P4, the new `resolve_selection()` is still paid before the unchanged serial compute builds its own context.

This is a regression against the 050.22 review-clean serial route and violates 050.23's requirement to retain the prior serial optimizations and avoid penalizing small requests.

**Target**

Keep the exact persisted-hit fast path untouched. Once a genuine Cycles result-cache miss is established, resolve/build the owner request context at most once and reuse it for threshold selection and whichever compute path is chosen, or provide an equivalent single-owner-resolution design.

**Acceptance criteria**

- A 1-Cell and a 3-Cell Cycles miss perform no worker job construction/submission and no new duplicate selection/context resolution relative to the final serial path.
- A 4+ Cell Cycles miss reuses one owner context across promotion decision and P4/serial fallback rather than resolving selection independently in the route and helper.
- Exact persisted hits remain above this work and retain the current fast path.
- Re-run a bounded 1-Cell/3-Cell serial no-regression control and include the corrected Cycles production route in the R1 matrix.
- Canonical preflight PASS.

### R5 — Medium: The P8 resident-RSS gate is computed from repeated worker samples and omits parent RSS

Affected files:
- `scripts/profile_analysis_family_concurrency.py`
- `docs/specs/050.23-cross-family-persistent-worker-scaling-and-integration.md`

**Current**

`ResidentFamilyPool.start()` submits `workers * 2` ping tasks and appends every `(pid, rss)` acknowledgement. It then computes `warm_idle_rss_bytes = sum(rss_values)`, so the same resident process can be counted multiple times. `_promotion_decision()` compares that worker-only aggregate as `rss8 <= rss4 * 1.5`.

The locked gate requires **combined parent + warm-worker RSS** for P8 to be no more than 1.5x the equivalent P4 resident footprint. The current value is neither one stable RSS sample per distinct worker nor the required combined footprint. The implementation record's P8 memory rejection is therefore not auditable from the reported metric.

The recorded P8 latency results already fail the independent >=15% and >=15 ms speed gate for a valid global P8 promotion, so correcting this RSS metric is not expected to force P8 into production; it is still required to make the evidence truthful.

**Target**

Measure resident memory once per distinct warm worker PID at a defined idle point, add the contemporaneous parent RSS, and compare like-for-like combined P4/P8 footprints. Report the timing gate and memory gate independently so a timing rejection is not justified by an invalid memory statistic.

**Acceptance criteria**

- Deduplicate worker RSS by PID and use a defined stable warm-idle sampling point.
- Include parent RSS in both P4 and P8 resident-footprint totals before applying the 1.5x gate.
- Record corrected P4/P8 memory values and ratio in the durable implementation record.
- Re-evaluate/document the P8 decision using the corrected evidence; if the existing speed gate independently rejects P8, state that explicitly.
- Add a focused test for RSS aggregation/gate math so repeated ping acknowledgements cannot inflate the footprint.
- Canonical preflight PASS.
