### Product behavior now accepted

The renderer now satisfies the narrowed functional requirements.

#### Aggregate path

`cycleTracesForResult(...)` computes `aggregateEmission = cycleTraceEmissionPlan(...)`. The primary block contains:

- confidence-band traces;
- aggregate primary trace;
- low-n marker trace.

The CE trace is emitted in a separate `aggregateEmission.ce` branch after the primary block. Therefore hiding `cycles:gN` while leaving `cycles:y2:coulombic_efficiency:gN` visible no longer short-circuits CE, and the primary band/low-n helpers are not emitted in CE-only mode.

#### Cell path

The cell loop likewise computes `cellEmission` without requiring primary visibility to continue through the source. The primary block contains:

- the primary cell trace;
- source-boundary helper markers.

CE is emitted independently from `cellEmission.ce`. Therefore hiding `cycles:cN` while leaving the CE key visible produces the CE trace without the primary/source-boundary helper traces.

#### Normal behavior

When both visibility gates are true, the primary branch and CE branch both execute, preserving the ordinary primary+CE plot. When CE is hidden but primary is visible, primary and its helpers remain available without CE. These conditions follow directly from the independent `cycleTraceEmissionPlan(...)` gates.

No product-code defect remains identified in this re-review.

### Verification gap

- the renderer source contains `cycleTraceEmissionPlan(...)` calls for aggregate and cell paths;

It still does **not** invoke `cycleTracesForResult(...)` with representative aggregate/cell data and inspect the actual emitted traces. The exact original bug was renderer control flow outside the pure visibility helper, so helper-only behavior plus source regex is not a sufficient regression for the acceptance criterion previously recorded in this review.
