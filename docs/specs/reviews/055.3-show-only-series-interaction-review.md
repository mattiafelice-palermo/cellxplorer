## Accepted architecture and behavior

### Persistent user-level visibility and dirty/save/reopen semantics

`presentation.hidden_series_ids` remains presentation state and is part of `plotViewSignature(spec)` because the signature serializes `presentation`. A visibility change therefore produces a real saved-plot dirty transition rather than transient Plotly state.

The existing saved-plot update/open path is compatible with this implementation:

- `applyUpdateActivePlot(...)` saves the current presentation through the existing `savedPlotFromSpec(...)` path and resets the saved-view baseline;
- `openSavedPlotDirect(...)` restores the saved plot presentation through `specForSavedPlot(...)`/`specForSavedPlotView(...)`;
- `hidden_series_ids` therefore survives saved-plot Update and reopen without a new persistence mechanism or schema migration.

The added `analysisPlotPolicy` regression explicitly confirms that changing `hidden_series_ids` changes `plotViewSignature`.

### Applicable-set restoration policy

The shared pure policy is correctly separated from higher-level applicability:

- `hiddenSeriesIdsAfterShowOnly(...)` changes only keys in the supplied applicable candidate set, unhiding the target and hiding the other applicable targets;
- `hiddenSeriesIdsAfterShowAll(...)` removes only candidate keys from the hidden set and preserves unrelated/stale keys;
- `plotSeriesVisibilityItems(...)` deduplicates by stable key rather than label.

The policy regressions explicitly cover same-label/different-key identity and preservation of non-applicable hidden keys.

Steps and DCIR implement the required layering particularly clearly: their `*ApplicableSeries(...)` helpers filter data availability, cell/sample visibility and segment visibility first; `*VisibleSeries(...)` applies `hidden_series_ids` only afterward. Chargeability similarly builds visibility candidates from finite data plus analysis-sample visibility before user-level hiding. Rate Capability derives candidates from the same view/data/cell filters used by its descriptor/trace path.

No finding is raised against the shared Show-all policy or those family-specific applicability splits.

### Stable series identity

The implementation does not use rendered labels as persistence identity. Family-owned keys are stored in `hidden_series_ids`; existing Steps/DCIR identifiers remain supported, while newer families use scoped keys such as `cycles:*`, `time_capacity:*`, `chargeability-*` and `rate-capability-*`.

The `SeriesDescriptor.visibilityKey` addition is a useful separation between styling identity and visibility identity. The remaining R1 concerns **which descriptors are intentionally collapsed onto the same visibility key**, not use of unstable text labels.

### True helper traces

The trace builders correctly keep several non-first-class Plotly traces out of the action list and make them follow their owning data series. Examples include Cycles confidence bands, low-n markers and source-boundary markers, and Time/capacity stacked-current/source-boundary helper traces. They are emitted inside the owner-series visibility boundary and do not become independent menu targets.

### Passive Plotly legend behavior

The shared `Plot` wrapper now disables both native legend click and double-click mutation in two ways:

- layout policy sets `legend.itemclick = false` and `legend.itemdoubleclick = false`;
- both `onLegendClick` and `onLegendDoubleClick` return `false` after forwarding any caller callback.

The focused `plotRuntime` regression verifies both layout flags and the `false` event policy. This resolves the spec requirement that native single-click/double-click must not create a Plotly-only visibility state.

R2 below is about preserving the **reference stability** of the derived passive layout, not about whether the native legend mutation is blocked.

### Keyboard accessibility

The new series action is exposed through Mantine `Menu` and real `Button`/`Menu.Item` controls in `PlotHeader`, rather than custom pointer-only elements. The menu target has an explicit accessible label and standard Mantine keyboard behavior. No child-level keyboard defect was found in this checkpoint.

Formal end-to-end manual acceptance remains deferred to the parent FINAL_REVIEW by explicit user decision.

## Findings

### R1 — P1 — First-class CE and multi-voltage series are collapsed into one visibility target

**Affected files**

- `frontend/src/features/analyses/editor/families/cycles/CyclePlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/plotting/seriesStyling.ts`
- `frontend/tests/seriesStyling.test.ts`
- focused family visibility tests as appropriate

**Current**

Spec 055.3 defines a series as a user-visible plotted trace/series that corresponds to a CellXplorer series descriptor and can meaningfully be hidden/shown. Only helper traces such as confidence bands, source-boundary markers and annotation-only traces should be collapsed into an owning target unless they already represent a first-class series.

The implementation currently collapses additional first-class descriptors:

1. **Cycles CE overlay**
   - capacity and CE have distinct `SeriesDescriptor.key` values, distinct measures/axes and distinct legend entries;
   - the CE descriptor nevertheless receives the same `visibilityKey` as its capacity primary (`cycles:g...` / `cycles:c...`).

2. **Time/capacity multi-voltage view**
   - `timeCapacityVoltageSeriesDescriptor(...)` explicitly creates independently stylable descriptors such as `c1|voltage`, `c1|working_potential` and `c1|counter_potential`;
   - those descriptors have separate legend entries and quantity labels;
   - all are intentionally assigned the same `visibilityKey`, e.g. `time_capacity:c1`;
   - `timeCapacitySeriesVisibilityCandidates(...)` likewise creates only one candidate per cell/group, not one per selected first-class voltage descriptor.

The focused test currently codifies that all three voltage descriptors resolve to the same visibility key.

This creates a direct user-visible failure of the feature. For example, a Time/capacity plot with one cell and three selected voltage channels contains three first-class user-visible series, but the visibility menu receives only one candidate. `PlotSeriesVisibilityMenu` hides itself when there is one visible candidate and nothing to restore, so the plot exposes **no `Show only this series` action at all**. With multiple cells, choosing a cell-level target keeps every voltage channel for that cell rather than isolating the selected user-visible series.

The same semantic problem applies to Cycles capacity versus its CE overlay: they are separate descriptor/legend series but cannot be isolated independently.

This is different from true Plotly helper traces. Bands, low-n markers, boundary markers and stacked-current helpers may remain linked to an owning first-class target and must not become extra menu rows.

**Target**

Every first-class user-visible series descriptor must have a stable independently targetable visibility identity, while genuine helper traces remain linked to their owner and stay out of the menu.

In particular:

- independently selected Time/capacity voltage-channel descriptors must be individually targetable;
- Cycles CE must be independently targetable from the primary capacity series when it is rendered as its own first-class descriptor/legend entry;
- stable keys, not labels or trace indices, must remain the persistence contract;
- current higher-level applicability filtering must still be applied before user visibility;
- true auxiliary Plotly traces must continue to follow the appropriate owner without becoming standalone targets.

Do not solve this by reverting to native Plotly legend visibility.

**Acceptance criteria**

1. A one-cell Time/capacity plot with `voltage`, `working_potential` and `counter_potential` selected exposes three first-class visibility targets with distinct stable keys.
2. `Show only` on one voltage channel leaves that channel visible and hides the other first-class voltage channels.
3. Time/capacity current/source-boundary helper traces remain non-targets and follow the intended owner semantics rather than appearing as extra menu rows.
4. A Cycles plot with a primary capacity trace and CE overlay exposes both first-class series independently; isolating either does not force the other to remain visible merely because they share a sample/group.
5. Cycles confidence bands, low-n markers, source-boundary markers and similar helper traces remain non-targets and follow the appropriate first-class owner.
6. Applicable-set `Show all` restores only first-class targets currently applicable under selection/filter/data constraints.
7. Stable persisted visibility keys survive saved-plot Update/reopen through the existing presentation snapshot path.
8. Add focused regressions against the **actual Cycles and Time/capacity candidate/trace builders**, not only the generic set helper. Include the one-cell/multi-voltage case and CE/helper ownership case.
9. Re-run the relevant focused frontend tests and `python scripts\preflight.py --no-cache`.

### R2 — P2 — Shared passive-legend wrapper destroys stable Plotly layout identity on every render

**Affected files**

- `frontend/src/components/Plot.tsx`
- `frontend/src/features/analyses/editor/policies/analysisVisibility.ts`
- focused Plot wrapper/layout policy coverage as appropriate

**Current**

`disablePlotlyLegendVisibility(layout)` always constructs a new top-level layout object and a new nested legend object using object spreads. `Plot.tsx` calls that helper inline during every React render:

```tsx
layout={disablePlotlyLegendVisibility(props.layout)}
```

Therefore even when a plot family has correctly memoized and reuses the exact same `props.layout` reference, the shared wrapper hands `react-plotly.js` a different `layout` reference on every wrapper render.

This defeats a deliberate repository performance invariant. The existing plotting code and state/performance guidance explicitly keep Plotly layout/config identities stable because reference changes cause Plotly to update/relayout. The same guidance also documents that Plotly `onUpdate` can feed React state and that equivalent size updates must be guarded to avoid loops.

The new wrapper is used by every interactive family, so this change turns otherwise unrelated React renders into Plotly update work across the application. The existing `plotRuntime` regression verifies flag values but cannot detect this reference churn.

No incorrect native visibility mutation is observed—the legend blocking itself is correct—but the implementation should not discard the stable object identities the family cards already establish.

**Target**

Keep the passive legend policy while deriving the passive layout with stable identity. When the incoming `props.layout` reference is unchanged, unrelated wrapper renders must reuse the same derived passive-layout reference. A new incoming layout may produce a new passive layout.

A straightforward solution is to memoize the derived layout in `Plot.tsx` by `props.layout` identity; an equivalent solution is acceptable if it preserves the same invariant without mutating caller-owned layout objects.

**Acceptance criteria**

1. Native `itemclick` and `itemdoubleclick` remain disabled and both legend event callbacks still return `false`.
2. Re-rendering `Plot` with the identical incoming `layout` object reuses the same passive-layout object rather than allocating a fresh one.
3. Supplying a new incoming layout produces a correctly updated passive layout.
4. Caller-owned layout/legend objects are not mutated.
5. The fix does not remove the existing guarded `rememberPlotDiv`/size-update behavior in family cards.
6. Add focused regression coverage where practical for the stable derived-layout contract, or otherwise document the React-level memoization and retain the existing pure legend-policy tests.
7. Re-run the focused plotting tests and `python scripts\preflight.py --no-cache`.
