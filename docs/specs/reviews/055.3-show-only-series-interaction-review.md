## Re-review of R1 — P1 — First-class series visibility

### What is resolved

The original identity/candidate defect is substantially fixed.

#### Time/Capacity

Multi-voltage descriptors now receive independent stable visibility identities, for example:

- `time_capacity:c1|voltage`;
- `time_capacity:c1|working_potential`;
- `time_capacity:c1|counter_potential`.

`timeCapacitySeriesVisibilityCandidatesForConfig(...)` creates one candidate per selected voltage channel that has finite data after sample applicability filtering. `timeCapacityVisibleVoltageChannels(...)` then applies those same persisted keys to the render path.

The actual `timeCapacityTracesForResult(...)` implementation aligns with that policy:

- multi-voltage rendering does not apply the legacy sample-level hidden key;
- each channel is filtered by its independent channel visibility key;
- only visible channel styles emit first-class voltage traces;
- stacked current traces remain non-target helper traces and are emitted only while at least one owning voltage channel is visible for the segment;
- the source-boundary marker remains a helper and derives its Y coordinate from an actually visible voltage channel rather than becoming an independent target.

This satisfies the Time/Capacity portion of R1. A one-cell three-voltage plot now has three candidate identities and can isolate an individual voltage channel without exposing current/boundary helpers as menu targets.

#### Cycles stable identities and candidates

Cycles now also defines separate keys:

- primary: `cycles:g7` / `cycles:c1`;
- CE: `cycles:y2:coulombic_efficiency:g7` / `cycles:y2:coulombic_efficiency:c1`.

`cycleSeriesVisibilityCandidatesForResult(...)` creates CE candidates only when the overlay is applicable and contains finite CE data. Bands, low-n markers and source-boundary markers do not appear in this candidate builder.

`seriesStyling.ts` likewise assigns the CE descriptor its own visibility identity instead of reusing the primary key.

These changes resolve the original key-collision/candidate-list portion of R1.

### What remains broken

The **actual Cycles renderer still structurally depends on primary visibility**, so independent CE isolation does not work.

For aggregate series, `cycleTracesForResult(...)` currently does the equivalent of:

```ts
const aggregateVisibility = cycleTraceVisibility(spec, aggKey);
if (!aggregateVisibility.primaryVisible) continue;
...
if (showCeOverlay && ...) {
  if (... && aggregateVisibility.ceVisible) {
    // emit CE
  }
}
```

The `continue` occurs before the CE block. Therefore a valid state such as:

- `cycles:g7` hidden;
- `cycles:y2:coulombic_efficiency:g7` visible;

never reaches the CE emission branch.

The ungrouped-cell loop has the same defect: `!cellVisibility.primaryVisible` is part of the early `continue`, and the independent CE branch is below it.

This is exactly the state produced by `Show only` on CE: the shared policy hides the other applicable first-class keys (including the primary) and leaves CE visible. The candidate/menu state therefore says CE is isolated, while the trace builder emits no CE trace.

The new focused test does not catch this. It verifies:

- CE and primary candidate keys are distinct;
- `cycleTraceVisibility(...)` reports separate booleans;
- source text contains the expected helper calls.

It does **not** call `cycleTracesForResult(...)` with primary hidden / CE visible and assert that a CE trace is actually returned. Thus the implementer statement that the actual Cycles candidate and trace builders are covered is only partially supported: candidate generation is behavior-tested, but the failing renderer control flow is not.

### R1 target

Make primary and CE emission independently conditional while keeping genuine primary helpers owned by the primary.

For each applicable aggregate/ungrouped-cell source:

- primary trace, confidence band, low-n markers and source-boundary markers should require primary visibility;
- CE should require CE visibility and CE applicability/data, **not** primary visibility;
- hiding both should emit neither;
- showing only CE should emit CE without primary helpers;
- showing only primary should emit primary plus its genuine primary helpers, without CE.

Do not merge the keys again and do not turn helper traces into first-class menu targets.

### R1 acceptance criteria

1. `cycleSeriesVisibilityCandidatesForResult(...)` continues to expose independent primary and CE stable keys.
2. `cycleTracesForResult(...)` with an aggregate primary hidden and CE visible returns the CE trace and does not return the aggregate primary/band/low-n helper traces.
3. `cycleTracesForResult(...)` with an ungrouped-cell primary hidden and CE visible returns the CE trace and does not return the primary/source-boundary helper traces.
4. Primary visible / CE hidden returns the primary and appropriate primary helpers but no CE trace.
5. Both hidden returns neither first-class trace and no owner helpers.
6. The existing diagnostic-cycle, sample/replicate applicability and `show_individual_cells` rules remain unchanged.
7. Add focused behavior regressions that execute the **actual `cycleTracesForResult(...)` path** for CE-only isolation (aggregate and ungrouped-cell paths, or a shared refactor that demonstrably covers both). Source-text regex checks are not sufficient for this acceptance point.
8. Keep the now-correct Time/Capacity channel-key and helper-ownership behavior unchanged.
9. Re-run the relevant focused frontend tests, TypeScript build and `python scripts\preflight.py --no-cache`.

**R1 status: OPEN.**

## Re-review of R2 — P2 — Stable passive Plotly layout identity

`Plot.tsx` now derives the passive legend layout with:

```tsx
const passiveLayout = useMemo(
  () => disablePlotlyLegendVisibility(props.layout),
  [props.layout],
);
```

and passes `layout={passiveLayout}` to `PlotlyComponent`.

This resolves the original cross-cutting reference-churn defect:

- the incoming family `layout` reference remains the memoization dependency;
- unrelated wrapper rerenders with the identical incoming layout reuse the identical derived passive-layout object;
- a new incoming layout produces a new passive layout;
- `disablePlotlyLegendVisibility(...)` still copies the caller's top-level layout/legend instead of mutating them;
- `legend.itemclick` and `legend.itemdoubleclick` remain `false`;
- both legend callbacks still return `false` after forwarding any caller callback.

The focused regression checks that the wrapper uses `useMemo`, depends on `[props.layout]`, and passes the memoized result. The existing policy tests continue to verify the passive legend values/event cancellation. This is sufficient for the requested invariant; no mounted React test is required for this simple direct `useMemo` dependency.

**R2 status: RESOLVED.**
