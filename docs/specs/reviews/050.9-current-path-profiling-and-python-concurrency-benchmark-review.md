## Findings

### R1 — High — B3/B4 do not benchmark the locked worker boundary

**Affected files**

- `scripts/profile_time_capacity_concurrency.py`
- `docs/specs/050.9-current-path-profiling-and-python-concurrency-benchmark.md`

**Current**

The locked 050.9 decision says relational state must be resolved in the owning Python context and worker jobs must receive only the minimum safe immutable inputs. B1/B2 follow that model by building read jobs before dispatch.

B3/B4 do not. `_whole_cell_task()` opens a new SQLAlchemy session inside every worker and calls the complete one-Cell `analysis_engine.compute_time_capacity()` request path. Each worker therefore repeats relational selection/source resolution, ORM loading and other per-request setup in addition to the raw read and scientific transforms whose thread scalability the experiment is intended to test.

This makes the reported B3/B4 wall times a measurement of **threading + duplicated ORM/request work + independent SQLite-session contention**, not a clean measurement of whether the existing independent per-Cell read/transform work scales under Python threads. The current conclusion that whole-Cell Python threads are harmful is therefore not supported by the required ablation boundary.

The B3/B4 parity merge also starts from the already-computed sequential reference result and replaces only `cell_traces` plus `rendering.total_points`. Non-trace scientific/provenance fields are inherited from the reference rather than independently produced by the threaded candidate, so the reported whole-result digest cannot validate those fields for B3/B4.

**Target**

Benchmark B3/B4 at the actual independent per-Cell boundary after relational/request state has been resolved once in the owning context. Worker inputs must be immutable/non-ORM descriptors or already-resolved numeric/cache inputs; no SQLAlchemy `Session` may be created or used inside the worker task. The candidate must measure the same necessary per-Cell read + transform work as A0 without multiplying parent/request setup merely to obtain thread safety.

Parity must compare independently produced candidate scientific/provenance outputs at the boundary being benchmarked. Do not make non-trace parity pass by copying those fields from the sequential reference before hashing.

**Acceptance criteria**

- B3/B4 workers receive no live ORM objects or SQLAlchemy sessions and do not perform relational selection/source-resolution work.
- Parent/request setup is measured once outside the worker pool and is not multiplied by Cell count in B3/B4.
- The benchmark still preserves deterministic original Cell order.
- Candidate parity covers independently produced per-Cell scientific values, finite/non-finite placement, source/provenance identity required by the benchmark boundary, and does not obtain those values by copying them from A0.
- Rerun the B3/B4 matrix on the controlled fixture and the available real application workload, including the 11-Cell All/Time case, and update the decision from the corrected measurements.
- Focused benchmark/profiling tests and canonical `python scripts\preflight.py` pass before handoff.

### R2 — Medium — the committed evidence does not show the measurements supporting the B1/B2 “useful” decision

**Affected files**

- `docs/specs/050.9-current-path-profiling-and-python-concurrency-benchmark.md`
- `scripts/profile_time_capacity_concurrency.py`

**Current**

The implementation record labels both B1 and B2 read/decode concurrency as **useful** using the 5% paired-change threshold, but the durable table records only total backend wall time. In the representative rows currently shown, total backend latency is effectively unchanged or slightly worse: for example the real 11-Cell All/Time case is 1002.8 ms A0, 1004.8 ms B1 and 1031.5 ms B2.

The harness computes the read-concurrency decision from `read_wall_ms` versus A0 `raw_read_decode_ms`, but those isolated measurements/ratios are not present in the committed evidence. The disposable `tmp/050.9-concurrency-profile.json` is not part of the branch. A reviewer or later 050.10/050.11 agent therefore cannot audit how large the read-only gain actually was, on which scenarios it occurred, or distinguish “the read stage is faster” from “the request is faster.”

**Target**

Persist a compact, privacy-safe summary of the isolated B1/B2 read-stage evidence in the 050.9 implementation record. Keep the important distinction explicit: read/decode concurrency may accelerate that stage while producing little or no total backend improvement when transforms dominate.

**Acceptance criteria**

- Record, for B1 and B2, the paired median read-stage ratio or percentage change versus A0 and enough representative scenario values to make the 5% classification auditable.
- Include the real 11-Cell workload and at least one controlled broad workload in that summary.
- State separately the total backend effect for those same scenarios; do not describe B1/B2 as an end-to-end backend speedup when the total measurement is neutral.
- If the corrected R1 rerun changes the benchmark report, regenerate this summary from the final accepted run.

## Reviewer assessment of the current results

The real-data run is useful and materially stronger than a synthetic-only result. It establishes that the current real 11-Cell All/Time backend path is about **1.0 s** on the measured machine and that the representative total request is not I/O-bound: neither B1 nor B2 moves that total materially in the recorded medians. The current evidence therefore points toward post-read transforms as the more important remaining backend cost.

The derivative numbers also justify a 050.10 native-kernel experiment: the recorded six-Cell dQ/dV derivative stage is roughly 0.84 s on the controlled fixture and 1.24 s on the real application dataset, substantially larger than the corresponding transform stage. That is a credible compact area for sequential Rust versus Rayon isolation.

The only conclusion that should **not** yet be carried forward is “whole-Cell Python threads are harmful.” B3/B4 currently include duplicated ORM/request work that the locked design explicitly excludes, so that conclusion must be re-measured at the correct boundary before 050.10/050.11 use it as evidence.
