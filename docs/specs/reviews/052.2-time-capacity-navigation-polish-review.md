## Findings

### R3 — Medium: Slider drag maps pointer distance to the full track instead of the segment's actual travel

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityCycleNavigation.tsx`
- `frontend/tests/timeCapacityCycleNavigation.test.ts`

**Current**

`CycleWindowSlider.rangeAtPointer(...)` converts pointer movement with:

```ts
Math.round(((clientX - startX) / rect.width) * (maxAvailableCycle - width))
```

The highlighted segment itself already occupies `width / maxAvailableCycle` of the track. Therefore its legal left-edge travel is only `rect.width * (maxAvailableCycle - width) / maxAvailableCycle`, not the complete `rect.width` used by the conversion above. The error becomes material for wide windows: with `max=100` and a 50-cycle window, dragging the segment from the first window to the right edge of its legal track travel moves only about 25 starts instead of reaching the last valid window `[51,100]`; reaching the upper boundary would require pointer travel well beyond the segment's available track distance.

The implementer manual record did not actually verify pointer dragging to both slider bounds: it states that lower/upper boundary behavior was exercised through the separate first/last-window actions.

**Target**

Map pointer movement to the range segment's actual draggable travel while preserving the grab point, inclusive window width, and whole-window clamping. A pointer drag that moves the segment to either legal edge of the track must reach the first or last valid window without requiring the pointer to leave the track.

**Acceptance criteria**

- Add focused coverage for a materially wide segment, e.g. `max=100`, width `50`, proving a drag from the first legal position to the last legal segment position resolves to `[51,100]`, and the reverse resolves to `[1,50]`.
- The same coverage proves width stays fixed throughout the mapping and clamps at both edges.
- Browser verification explicitly drags the segment itself to both lower and upper boundaries; do not substitute Ctrl+click/first-last actions for this check.

### R4 — Medium: Trailing debounce can starve live plot preview during continuous dragging

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- relevant focused frontend tests

**Current**

`cyclePreviewRange` is converted into `previewQueryRange` by a pure trailing 120 ms timeout. Every preview-range change clears and restarts that timer. During a normal continuous drag, pointer events can arrive much more frequently than 120 ms, so the preview query can remain pinned to the old range for the entire movement. If the pointer is released before a 120 ms idle gap, the navigator clears the transient preview and the pending timeout is cancelled, so no preview request for the dragged intermediate ranges is guaranteed to start at all.

This satisfies request suppression, but it does not satisfy the locked requirement that the **plot follows the transient range dynamically before release** and that cached range results can be reused promptly while dragging.

**Target**

Use bounded, cancellation-aware coalescing/throttling that advances the preview query promptly and periodically during an ongoing drag rather than only after movement becomes idle. Retain immediate local From/To feedback, React Query cancellation of superseded work, compatible placeholder retention, and one canonical/history commit on release.

**Acceptance criteria**

- Add deterministic focused coverage showing that a stream of preview updates arriving faster than the coalescing interval still advances the query preview range at least once **before** the event stream ends/release occurs.
- Cached preview ranges remain eligible for immediate reuse rather than waiting for a trailing-idle timeout.
- Superseded network work remains bounded/cancelled; no request-per-pointer-event behavior is introduced.
- Browser verification performs a continuous drag without pausing and confirms the plotted range changes before pointer release, with no blank/flicker or request storm.

### R5 — Medium: Reopening an existing unsaved Time/Capacity draft incorrectly marks it virgin

**Affected files:**

- `frontend/src/features/analyses/editor/AnalysisEditor.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityCycleNavigation.tsx`
- relevant focused frontend tests

**Current**

The `SavedPlotsPanel` `onOpenDraft` handler unconditionally does this for Time/Capacity:

```ts
setTimeCapacityNavigationSession((value) => value + 1);
setTimeCapacityVirginNavigation(true);
```

That handler is also used to reopen the already-existing live unsaved draft card. Incrementing the navigation reset key resets the navigator's virgin-default refs, and `isVirgin=true` permits the last-20 effect to commit a new range as soon as a maximum is known. An edited unsaved draft can therefore have its manually chosen range replaced by the last-20 default merely by reopening its draft card.

This violates the explicit 052.2 safeguard that virgin initialization must not overwrite an edited draft/workspace range.

**Target**

Treat only genuine new/default Time/Capacity plot creation as virgin. Reopening an existing live unsaved draft/workspace must preserve its current continuous range and style state exactly. The guard must also prevent a user edit made before the maximum finishes loading from being overwritten when the maximum later becomes available.

**Acceptance criteria**

- Add focused regression coverage for: create/open a Time/Capacity draft, set a non-default/non-last-20 range, reopen the draft card with a known maximum, and verify the range is unchanged.
- Add coverage for a virgin view where the user edits the range before `maxAvailableCycle` resolves; resolving the maximum later must not apply the last-20 initializer over that edit.
- Saved/restored Time/Capacity plots continue to bypass virgin initialization.
- A genuinely new Time/Capacity plot still initializes once to the last 20 available cycles.

### R6 — Low: Ctrl+click on the null-bound single-left arrow silently performs the normal one-cycle action

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityCycleNavigation.tsx`
- `frontend/tests/timeCapacityCycleNavigation.test.ts`

**Current**

The single-left `‹` remains correctly enabled without a reliable maximum because ordinary backward movement is safe. It also passes `boundary="first"` on Ctrl+click. In `move(...)`, however, the boundary path is only selected when `hasBound`; with a null maximum the call falls through to the ordinary single-cycle backward shift. Consequently `Ctrl+click` — which is advertised as the **first-window** gesture — silently behaves like a normal click when the required upper-bound context is unavailable.

052.2 explicitly says not to invent extreme navigation when no reliable maximum exists. The normal safe backward click must remain available, but the modified extreme gesture must not masquerade as it.

**Target**

When no reliable maximum is available, Ctrl+click extreme navigation is a no-op while ordinary `‹` continues to shift backward safely and lower-clamp at cycle 1.

**Acceptance criteria**

- Focused coverage proves: with `max=null`, normal `‹` shifts back one cycle, while Ctrl+`‹` leaves the range unchanged.
- With a reliable maximum, Ctrl+`‹` still reaches the first valid window.
- Specific-cycles disabling and the resolved R1 null-bound behavior remain unchanged.
