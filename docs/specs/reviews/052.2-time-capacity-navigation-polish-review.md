## Findings

### R4 — Medium — Resolved in code — Moving previews could be cancelled continuously before any result completed

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityCycleNavigationPolicy.ts`
- `frontend/tests/timeCapacityCycleNavigation.test.ts`

**Previous Current**

The previous R4 implementation admitted a new low-resolution React Query key every ~40 ms even when the prior moving request had not completed. Because the query function consumes React Query's `AbortSignal`, sustained dragging could cancel each low-resolution request before any result reached Plotly.

**Resolution**

Commit `5558d33289e1b3816cc1c8a009c2f4a0ccb351a3` adds explicit moving-request backpressure:

- `TimeCapacityPreviewSchedulerState` now tracks `inFlight` and the currently `publishedRequest`;
- while a moving request is in flight, `timeCapacityPreviewOnMove(...)` does **not** publish a replacement request and instead overwrites only `pendingRange` with the newest desired range;
- `previewRequest` therefore remains unchanged in `TimeCapacityPlotCard.tsx`, so the active React Query key remains observed rather than being replaced on every 40 ms interval;
- once the moving query settles (`timeResult.isFetching === false`), the component calls `timeCapacityPreviewOnMovingRequestComplete(...)` and admits only the newest pending range;
- intermediate pointer positions are discarded rather than queued;
- the request-only moving point cap remains `min(configured max_points_per_cell, 1000)`;
- the 50 ms idle promotion still switches the latest transient range to full configured resolution;
- movement after full-resolution promotion still invalidates/obsoletes that full request immediately and returns to low-resolution moving mode;
- release/cancel still invalidates transient preview state so the canonical range uses the normal full-resolution configuration.

This removes the concrete starvation mechanism identified in the previous review. No new implementation defect was found in this patch by static inspection.

**Acceptance criteria status**

- Simulated moving latency greater than the 40 ms cadence: **covered** by the focused scheduler test using 100 ms delayed completions.
- At most one moving request in flight: **satisfied** by `inFlight` gating and the unchanged `previewRequest` while a request is active.
- Newest-only pending retention/no FIFO backlog: **satisfied** by overwriting `pendingRange` on later pointer moves.
- Admission after completion: **satisfied** by the `timeResult.isFetching` completion effect and `timeCapacityPreviewOnMovingRequestComplete(...)`.
- Multiple low-resolution completions before release under the simulated delayed stream: **covered at policy level** (`first -> fourth -> sixth`).
- Request-only 1000-point cap without canonical mutation: **preserved**.
- ~50 ms full-resolution idle promotion: **preserved**.
- Renewed movement cancels/obsoletes full-resolution idle work: **preserved**.
- Release/cancel invalidation and final canonical full resolution: **preserved**.
- Actual browser proof that sustained pointer movement visibly advances the plot before release: **NOT RUN for this implementation**. The earlier browser evidence predates this backpressure patch and cannot prove the latest code path.

**Status:** Resolved in implementation. The remaining browser acceptance is an external final-review gate rather than an implementer code finding.
