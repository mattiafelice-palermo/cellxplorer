## Findings

### R4 — Medium — Open — Fixed-cadence query replacement can still starve every moving preview

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityCycleNavigationPolicy.ts`
- `frontend/tests/timeCapacityCycleNavigation.test.ts`

**Current**

Commit `ae5bfe26...` correctly introduces the requested two-resolution request identities:

- moving preview: `min(configured max_points_per_cell, 1000)`;
- moving publication target: 40 ms;
- idle promotion: 50 ms;
- full configured resolution after idle/release;
- resumed movement immediately leaves the full-resolution phase.

However, the moving path still admits a **new React Query request every ~40 ms regardless of whether the previous moving request has completed**. `previewRequest` changes range on each publication; `dataSignature` therefore changes; `useQuery` changes query key; and the query function passes React Query's abort `signal` into `post(...)`, which passes it through to browser `fetch`.

That means a continuous drag can repeatedly cancel the previous low-resolution request before it produces any plot data. If a representative low-resolution Time/Capacity request takes longer than the 40 ms scheduler cadence, the sequence is effectively:

```text
low A starts
40 ms -> low B becomes authoritative -> A cancelled
40 ms -> low C becomes authoritative -> B cancelled
40 ms -> low D becomes authoritative -> C cancelled
...
```

When the pointer finally stops, the 50 ms idle promotion can then replace the final low-resolution request with a full-resolution request before that low-resolution request has completed. The visible result can therefore remain the old compatible placeholder throughout the drag and then wait on the expensive full-resolution result after movement stops. That is exactly the failure mode the live-scrubbing requirement is intended to prevent.

The new focused tests do not cover this integration failure. They prove scheduler decisions at synthetic timestamps, but they do not simulate an asynchronous request whose latency exceeds the 40 ms publication cadence and verify that moving results actually complete/render during a continuous drag.

The generation helper also does not change this outcome: request generations are tracked in the pure policy, while the actual render path is still driven by the active React Query key/result.

**Target**

Make the moving low-resolution pipeline **completion-aware and backpressured**, while preserving the existing latest-wins/no-FIFO semantics.

A robust model is:

```text
MOVING
  -> at most one low-resolution request in flight
  -> while it is running, retain only the newest desired range
  -> do not cancel that low-resolution request merely because 40 ms elapsed
  -> when it completes, advance the plot and immediately admit the newest pending range
  -> skip all intermediate pending positions

IDLE >= ~50 ms
  -> promote the current transient range to full configured resolution

MOVEMENT RESUMES FROM FULL
  -> abort/obsolete the full-resolution request immediately
  -> immediately restart low-resolution moving mode for the newest range

RELEASE
  -> one canonical range/history commit
  -> full configured resolution guaranteed
```

The 40 ms value should be treated as a **minimum scheduling/admission target when no moving request is already in flight**, not as an unconditional cancellation deadline for low-resolution work. This still satisfies the locked requirement that there is no FIFO backlog: there is one active low-resolution request and at most one latest pending desired range.

Do not weaken the explicit user decision for the full-resolution idle request: when movement resumes after idle promotion, that full-resolution request should still be cancelled/obsoleted immediately and low-resolution preview should resume.

**Acceptance criteria**

- Add deterministic async/integration coverage with simulated moving-request latency greater than 40 ms (for example 80–120 ms) and pointer updates arriving faster than 40 ms.
- During a continuous drag lasting several request durations, at least multiple low-resolution preview results complete and become eligible to render **before release**; the test must fail for an implementation that cancels every moving request before completion.
- While one moving request is in flight, only the newest desired range is retained; intermediate ranges do not form a FIFO queue.
- When the active moving request completes, the newest pending moving range is admitted immediately, subject only to the intended minimum cadence/backpressure policy.
- Moving requests still use `min(configuredMaxPoints, 1000)` without mutating canonical spec/config.
- The 50 ms idle promotion still requests the same transient range at full configured resolution.
- Renewed movement still cancels/obsoletes an in-flight **full-resolution** idle request immediately and restarts low-resolution moving mode.
- Release still performs one canonical/history/autosave commit and settles the final range at full configured resolution.
- Escape/cancel still restores the canonical pre-drag range with no history entry.
- Browser acceptance must verify the actual user-visible requirement: while the pointer remains held and moves continuously, the plot visibly advances rather than remaining static until pause/release. Given the user's previous observed regression, this item is required before R4 can be closed.

**Status:** Open.
