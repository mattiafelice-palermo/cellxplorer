## Findings

### R3 — Medium — Resolved — Slider drag maps pointer distance to the full track instead of the segment's actual travel

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityCycleNavigation.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityCycleNavigationPolicy.ts`
- `frontend/tests/timeCapacityCycleNavigation.test.ts`

**Previous Current**

Pointer movement was scaled against full track width even though the highlighted window itself occupies part of that track, so materially wide windows could not reach the opposite legal edge without pointer travel beyond the available segment path.

**Resolution**

Commit `08d44dae28b13a4d9b024011fd8011eb8a64deae` moves the mapping into `timeCapacityCycleRangeAtPointerDelta(...)`. The helper computes legal segment travel as:

```text
trackWidth * (maxAvailableCycle - width) / maxAvailableCycle
```

and maps pointer delta against that travel before whole-window clamping. Focused coverage verifies `max=100`, width 50, first -> last, last -> first, midpoint behavior, fixed width and overshoot clamping. The implementer also reports a real browser segment drag reaching `1–20` and `278–297` on a 297-cycle view.

**Status:** Resolved.

### R4 — Medium — Open — Live scrubbing still uses one full-resolution 120 ms preview mode instead of the user-approved moving/idle resolution state machine

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityCycleNavigationPolicy.ts`
- relevant focused frontend tests

**Current**

The original starvation defect is improved: commit `08d44dae...` replaces the trailing-only debounce with leading + periodic latest-range publication, so a continuous drag can advance `previewQueryRange` before release.

However, the resulting implementation still has one preview mode:

- `TIME_CAPACITY_PREVIEW_INTERVAL_MS = 120`;
- `requestSpec` is built with `timeCapacitySpecWithCycleRange(spec, previewQueryRange)`, which changes only the range and therefore keeps the user's normal `max_points_per_cell` unchanged (4000 by default);
- there is no distinct low-resolution moving request;
- there is no approximately 50 ms pointer-idle promotion to full configured resolution while the pointer remains held;
- there is no state transition that immediately cancels/obsoletes an in-flight full-resolution idle request and returns to low-resolution mode when movement resumes.

This is now a direct user-acceptance requirement. The governing 052.2 spec has been amended in this reviewer round to make it explicit.

**Target**

Implement an explicit transient scrubbing state machine without mutating canonical analysis state:

```text
MOVING
  -> immediate/latest-wins low-resolution preview
     max_points_per_cell = min(user configured value, 1000)

IDLE >= ~50 ms while still holding
  -> full configured resolution for the same transient range

MOVEMENT RESUMES
  -> abort/obsolete pending full-resolution work
  -> immediately resume low-resolution newest-range preview

RELEASE
  -> one canonical range/history/autosave commit
  -> full configured resolution guaranteed
```

The low-resolution cap is request-only. It must never overwrite the user's `max_points_per_cell`, saved plot, draft, preset, export setting, or canonical spec. Use the normal query identity so low- and full-resolution requests are distinct cache identities. Preserve compatible-placeholder behavior and abort signals; a stale response must never replace a newer range/resolution state.

Use a short latest-wins moving cadence around 40 ms as the initial scheduler target rather than deliberately limiting moving publication to 120 ms. The 40 ms value is a scheduling target, not a pass/fail requirement that backend + transport + Plotly always finish within 40 ms.

**Acceptance criteria**

- Focused tests prove moving preview requests use `min(configuredMaxPoints, 1000)` and never mutate the canonical spec/config.
- The first movement publishes low resolution immediately; continuous movement retains only the newest desired range and remains bounded.
- Approximately 50 ms after the latest pointer movement, while the drag is still active, the same transient range is promoted to the user's full configured point budget.
- If movement resumes after that promotion starts, the full-resolution request becomes cancelled/obsolete and the newest low-resolution range becomes authoritative immediately rather than waiting for the old throttle interval.
- Query/request identity prevents late low- or full-resolution responses from replacing a newer range/resolution state.
- Pointer release performs one canonical/history commit and guarantees full configured resolution for the final range; an already-cached exact full-resolution result may be reused.
- Escape/cancel restores canonical pre-drag range and does not add history.
- Browser/manual verification, when permitted, demonstrates: responsive moving updates, low-resolution scrubbing, sharpening after roughly 50 ms stationary while still held, immediate low-resolution resumption after renewed movement, and full resolution after release. If browser use is restricted, record NOT RUN truthfully and rely on deterministic state-machine/query-identity coverage until user acceptance.

**Status:** Open.

### R5 — Medium — Resolved — Reopening an existing unsaved Time/Capacity draft incorrectly marks it virgin

**Affected files:**

- `frontend/src/features/analyses/editor/AnalysisEditor.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityCycleNavigation.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityCycleNavigationPolicy.ts`
- `frontend/tests/timeCapacityCycleNavigation.test.ts`

**Previous Current**

`onOpenDraft` reset the Time/Capacity navigation session and set virgin navigation true, allowing an edited unsaved range to be replaced by the last-20 initializer.

**Resolution**

Commit `08d44dae...` removes the Time/Capacity virgin reset from `onOpenDraft`. The navigator still clears its pending virgin-default flag on an ordinary user range commit, and `timeCapacityVirginDefaultCanApply(...)` makes the one-time preconditions explicit/testable. Focused coverage verifies edit-before-max gating and the source-level draft reopen path; the implementer reports browser verification that an edited `100–119` draft retained that range after reopening.

**Status:** Resolved.

### R6 — Low — Resolved — Null-bound Ctrl+first silently performs a normal previous-cycle action

**Affected files:**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityCycleNavigation.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityCycleNavigationPolicy.ts`
- `frontend/tests/timeCapacityCycleNavigation.test.ts`

**Previous Current**

With no reliable max, Ctrl+click on the enabled single-left arrow fell through to ordinary one-cycle backward movement even though the modifier advertised first-window navigation.

**Resolution**

`navigateTimeCapacityCycleRange(...)` now returns `null` for boundary/extreme navigation without a reliable max while preserving the safe ordinary backward single-cycle path. Focused coverage checks null-bound normal backward movement, null-bound Ctrl+first no-op, and bounded Ctrl+first behavior.

**Status:** Resolved.
