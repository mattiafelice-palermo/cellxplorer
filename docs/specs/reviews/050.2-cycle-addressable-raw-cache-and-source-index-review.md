## Findings

### R1 — Medium: scientific cleanup can still delete a checksum directory after layout conversion has acquired cleanup protection

Affected files:
- `backend/app/services/cache_maintenance.py`
- `backend/app/services/cache.py` as the cleanup-safe primitive owner if needed
- focused cache-maintenance/raw-layout tests

**Current**

050.2 correctly adds `protect_hash_from_cleanup()` around raw-layout conversion, and the adaptive `ProcessPoolExecutor` path also acquires that protection in the parent process before dispatching a worker. However the scientific deletion paths do not enforce that protection at the actual deletion boundary.

`cleanup_eligible_scientific()` and `enforce_scientific_limit()` take a one-time snapshot from `cache.pending_hashes()`, build deletion candidates, and later call `shutil.rmtree()` / `_remove_directory()` directly. A conversion can therefore acquire protection after the snapshot but before the directory deletion. `cleanup_offender(kind="scientific", ...)` does not consult pending/protected hashes at all and also removes the directory directly.

The cache layer already has `remove_hash_cache()`, which waits on `_wait_for_cleanup_safe()` before deleting a checksum directory, but these maintenance paths bypass it. The focused conversion-protection test only asserts that the hash appears in `pending_hashes()`; it does not run a cleanup path while the conversion is held. Consequently the child does not yet satisfy its locked requirement that active conversion be protected from concurrent cleanup or required test 22 that cleanup cannot delete a hash while conversion owns protection.

This is a lifecycle-safety race rather than a calculation defect: indexed reads themselves fail safe, but a concurrent maintenance action can remove the raw/index/candidate directory underneath preparation and cause avoidable conversion/cache loss or failure.

**Target**

Every scientific checksum-directory deletion path must honor the live pending/protected boundary immediately before deletion, not only through an earlier snapshot. Reuse one cache-owned cleanup-safe deletion primitive where practical so automatic eligible cleanup, budget enforcement and explicit scientific-offender cleanup cannot drift apart.

Preserve the existing offline-source policy and explicit forced-cleanup semantics; the change is specifically about serializing deletion against an active writer/converter, not making caches undeletable.

**Acceptance criteria**

- If a raw-layout conversion owns cleanup protection, `cleanup_eligible_scientific()` cannot delete that checksum directory until protection is released.
- `enforce_scientific_limit()` revalidates/waits at the deletion boundary so a hash that becomes protected after candidate discovery is not removed mid-conversion.
- `cleanup_offender(kind="scientific", ...)` uses the same live protection boundary, including the explicit-force case.
- Add a focused concurrency regression test that holds conversion protection, starts at least the automatic/budget cleanup paths, and proves the checksum directory remains intact until the conversion finishes; include explicit-offender coverage or an equivalent shared-primitive assertion.
- Existing offline-source preservation, sidecar accounting and cleanup behavior after protection is released remain unchanged.
- Run the focused raw-layout/cache-maintenance/preparation tests and canonical `python scripts\preflight.py` before handoff.
