The indexed reader is behaving as intended: for one Cell the profile read 3/20 groups for 1-20, 11/20 for 1-150, and 20/20 for All. The existing aggregate `continuous_time_phase_capacity` timing grew from about 53 ms to 198 ms to 418 ms across those one-Cell ranges; it reached about 1.98 s for five-Cell All and 2.62 s for six-Cell All. This makes post-read transforms the primary normal-view candidate rather than Parquet I/O.

Sixteen React Query memory-hit records had a median total interaction of about 34 ms, so exact-repeat client reuse is already fast and does not justify a speculative general RAM cache/prefetch optimization.

Derivative behavior is distinct: one-Cell dQ/dV All took about 3.62 s total, about 3.01 s backend, about 2.30 s in the derivative stage, about 388 ms Plotly, and produced 610 traces. This should be profiled separately from the normal Voltage/Current transform path.

The user capture did not contain a true persisted analysis-result HTTP cache hit. Two five-Cell narrow misses also showed an unexplained ~0.8 s HTTP-minus-backend gap that was not consistently reproduced in the same capture.

### R6 — Medium: decompose the measured backend hotspots before authoring an optimization

Affected files are intentionally not prescribed beyond the current profiling/scientific anchors. Likely ownership includes `backend/app/services/analysis_engine.py`, the existing profiling diagnostics/services, profiling scripts/tests, and documentation. Production computation must remain unchanged.

**Current**

The installed-app evidence is sufficient to show that normal broad/multi-Cell Time/Capacity misses are backend-dominated and that the aggregated `continuous_time_phase_capacity` stage scales strongly with exact rows entering transforms. It is not yet sufficient to tell which operation inside that aggregate is dominant, which derived calculations are actually required by each view, or whether the correct next design is reusable exact prepared derivations versus a broad-view representation.

The derivative path is clearly a separate hotspot, but the existing `derivative` timer is also too coarse to identify its internal cause. The local capture also lacks a persisted-result HTTP cache hit and contains two non-reproducible-looking narrow multi-Cell HTTP/backend gaps.

**Target**

Perform the profiling activities in `docs/specs/amendments/050.4-targeted-backend-hotspot-profiling.md` and return the resulting decision-quality evidence to the reviewer. In particular:

1. split `continuous_time_phase_capacity` into bounded sub-stage measurements for `_continuous_time`, source-column/boundary work, `_phase_from_raw`, `_phase_capacity`, and any materially significant attachment/copy step;
2. profile narrow, broad and All ranges with repetitions sufficient for median/range reporting;
3. audit which transforms are actually consumed by Voltage/Current-Time, Voltage/Current-Capacity and derivative views;
4. drill into `_derivative_curve` separately for roughly 1-3, 1-20 and All;
5. automate a compact/standard persisted-result-cache miss -> hit sequence and prove scientific payload equality while confirming the hit does not rerun transforms;
6. probe the anomalous narrow multi-Cell HTTP/backend gap with repeated local route/client measurements and report whether it reproduces;
7. answer whether the evidence points toward reusable exact prepared derivations, a broad-view multiresolution representation, or another specifically measured design.

Do **not** implement the resulting optimization, 050.5 or 050.P1 in this round.
