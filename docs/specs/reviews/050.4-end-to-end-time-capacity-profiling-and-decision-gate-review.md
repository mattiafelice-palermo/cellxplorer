## Findings

### R1 — High: incompatible frontend/backend identity comparison

Status: **Resolved in `36aa9ee`**

**Current in round 1**

The profiler compared the frontend React Query JSON `dataSignature` with the backend analysis-cache digest in `result.data_signature`, so valid profiled HTTP results could not reach frontend/Plotly completion.

**Target**

Use one coherent frontend query/profile identity and retain placeholder/supersession safety without comparing unrelated identity namespaces.

**Acceptance criteria / resolution**

- PASS by inspection: the current query signature is compared only with the profile's captured query signature; backend `data_signature` is not used as that identity.
- PASS by focused regression: a backend digest distinct from the frontend JSON identity is accepted for the current profiled request.
- PASS by existing state-machine coverage: placeholder and superseded callbacks cannot complete the wrong record.

### R2 — Medium: React Query memory hits inherited stale backend facts

Status: **Resolved in `36aa9ee`**

**Current in round 1**

A client-memory hit cloned the profiling block from the earlier server response, potentially reporting an old backend miss/compute/access path for an interaction that made no HTTP request.

**Target**

Represent the client-memory hit as its own interaction and do not recycle historical server diagnostics.

**Acceptance criteria / resolution**

- PASS by inspection: `memoryCacheHit()` sets `response_source: "react_query_memory"`, zero HTTP time, `result_cache: "unknown"`, and `raw_access: "not_applicable"`.
- PASS by inspection/test: backend timings, bytes, row groups/rows and prior resolved-cell facts are cleared rather than inherited.
- PASS by focused regression: server miss followed by warm memory hit preserves no stale server evidence.

### R3 — Medium: actual resolved Cell count was ambiguous

Status: **Resolved in `36aa9ee`**

**Current in round 1**

`selection_count` counted selection entries while `trace_count` could mean either backend Cell traces or Plotly traces, leaving no stable actual-Cell dimension for multi-cell scaling.

**Target**

Keep selection-entry count, resolved Cell/unit count and Plotly trace count distinct.

**Acceptance criteria / resolution**

- PASS by inspection: backend/frontend profiling expose unique `resolved_cell_count` separately from `selection_count` and `trace_count`.
- PASS by focused regressions: one selection entry can resolve to two Cells while six Plotly traces remain a separate count.

### R4 — Medium: profiling repeatedly serializes the full response after its backend timer stops, perturbing and misclassifying the measured interaction

Affected files:
- `backend/app/routers/analyses.py`
- focused backend profiling/route tests

**Current**

`_profiled_time_capacity_response()` performs a full `render()` once to measure `backend_serialize_ms`, stores `backend_total_ms` immediately after that first render, then performs another full render and up to three additional renders while converging `response_bytes`:

```python
content = render()
profile["backend_serialize_ms"] = ...
profile["backend_total_ms"] = ...
content = render()
for _ in range(3):
    profile["response_bytes"] = len(content)
    next_content = render()
    content = next_content
    ...
```

On a result-cache miss, `render()` calls `fast_json(payload).body`, so a profiled compact Time/Capacity response may be full-JSON-encoded multiple times. That is extra backend work which the ordinary production interaction does not perform. Worse, `backend_total_ms` is captured before the repeated renders, while the browser's `http_round_trip_ms` includes them. The missing serialization work is therefore liable to appear as transport/parse/frontend overhead in the very stage decomposition 050.4 is intended to use for the optimization decision.

This is a measurement defect, not a scientific-output defect. The 050.4 spec explicitly allows instrumentation-overhead fixes needed to make the measurements truthful and requires separation of backend service/serialization/transport.

**Target**

Prepare the profiled response with bounded observational overhead and make the timing boundary truthful. Do not repeatedly full-serialize the scientific payload merely to embed self-referential timing/byte-count fields. `backend_total_ms` must cover backend work through final response-body readiness sufficiently for `http_round_trip_ms - backend_total_ms` not to contain hidden profiler-induced full-response encodes. Optional fields such as `response_bytes` may be omitted or obtained by a non-perturbing mechanism if exact in-body self-measurement would require repeated serialization.

**Acceptance criteria**

- A profiled result-cache miss does not repeatedly full-JSON-serialize the Time/Capacity scientific payload beyond the normal response construction path.
- `backend_total_ms` is recorded at a boundary that includes final profiled-body preparation, rather than before additional full-response encodes.
- If `response_bytes` is retained, it reflects the returned response without requiring repeated full scientific-payload serialization; otherwise omit the optional field and document that choice.
- Add a focused regression that structurally detects repeated full-response serialization/body rendering on the profiled miss path and covers the persisted-cache-hit path as relevant.
- Ordinary non-profiled responses, scientific result/cache identity, golden outputs, parser/canonical/raw-layout/result-schema versions and `CALC_VERSION` remain unchanged.
- Run the focused profiling tests, relevant type/diff checks and canonical preflight before handoff; browser/end-to-end matrix may remain `NOT RUN` until the child is review-clean and the user supplies local evidence.
