## Findings

### R1 — High: the live identity guard compares incompatible signatures, so profiled HTTP requests cannot complete a record

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/tests/timeCapacityPerformanceProfile.test.ts` and/or a focused integration/policy test

**Current**

050.4 defines the frontend `dataSignature` as the JSON serialization used in the React Query key. The backend sets `result.data_signature` to `analysis_cache.result_key(...)`, i.e. the persisted analysis-cache key digest. The new profiling guards require:

```ts
currentResult.data_signature === dataSignature
```

inside `profileResultIsCurrent`, and use the same comparison in the React Query memory-hit path. These two values are not the same identity. A normal profiled server response therefore makes `profileResultIsCurrent` false, so `frontendPrepared()` is never accepted and the guarded Plotly completion callback cannot close the record. The pure state-machine tests do not exercise this real frontend/backend identity pairing.

**Target**

Bind profiling completion to one coherent identity already owned by the live query/profile request. Do not compare the backend analysis-cache digest with the frontend JSON query identity. The current non-placeholder React Query result plus the 050.4 request identity must be sufficient to reject obsolete callbacks without conflating two unrelated signature formats.

**Acceptance criteria**

- A real profiled HTTP result carrying the normal backend `data_signature` can progress through response -> frontend prepared -> Plotly complete and yields exactly one completed record for the current request.
- A superseded/late result or Plotly callback still cannot close the newer request.
- Placeholder data still cannot close a request.
- Add a focused regression that uses the real identity shapes (frontend JSON signature and distinct backend digest-like `data_signature`) rather than only the isolated profiler state machine.

### R2 — Medium: React Query memory hits inherit stale backend profiling facts from the previous request

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/performance/timeCapacityPerformanceProfile.ts`
- focused frontend profiling tests

**Current**

When React Query satisfies a current key directly from its in-memory cache, no HTTP request runs. The 050.4 layout effect handles that by cloning `data.profiling`, replacing only its `request_id`, and passing the old block to the new record with `http_round_trip_ms = 0`.

That block describes the earlier server interaction that originally populated the React Query entry. It can therefore carry an earlier `result_cache: "miss"`, `raw_access: "indexed"`, backend timings, row counts and response size even though the current interaction performed no backend request at all. A warm client-memory reopen can consequently be reported as a fresh backend miss/compute, contaminating the cache-state and stage breakdown that 050.4 is intended to use for the optimization decision.

**Target**

Represent the React Query memory-cache case as its own current interaction fact. Do not copy prior backend timing/access diagnostics into a no-HTTP interaction. It is acceptable to extend the profiling model with an explicit frontend-query-cache state/fact; if the persisted backend result-cache state is unknowable because no request occurred, report that truthfully rather than recycling historical server evidence.

**Acceptance criteria**

- A React Query in-memory hit records `http_round_trip_ms = 0` (or an equivalent explicit no-request state) and does not reuse previous backend compute/serialization/access timings or row counters as if they occurred now.
- The exported record unambiguously distinguishes the client-memory hit from a persisted backend result-cache hit reached through HTTP.
- A focused regression covers: profiled server miss -> navigate away -> return to the same still-fresh query key -> current memory-hit record, proving stale backend diagnostics are not inherited.

### R3 — Medium: the exported profile does not record the actual selected-cell count required for multi-cell scaling

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/performance/timeCapacityPerformanceProfile.ts`
- `backend/app/services/time_capacity_profiling.py` as needed
- focused profiling tests

**Current**

`selection_count` is populated from `spec.selection.entries.length`. One selection entry may be a replicate/group that resolves to multiple Cells, so this is not the actual selected-cell count required by the 050.4 scenario matrix. The backend profiling block initially sets `trace_count = len(result["cell_traces"])`, but the frontend later overwrites the same `trace_count` with `traces.length`, which is the number of Plotly traces and can exceed the number of Cells because one Cell can emit multiple visual traces.

As a result, the exported JSON has no stable field that answers the required question "how many Cells were actually measured?". Multi-cell scaling evidence could therefore be mislabeled, especially when replicate selections are used.

**Target**

Record actual resolved Cell/unit count separately from selection-entry count and separately from Plotly trace count. Preserve distinct names/meanings for these quantities through backend and frontend profiling.

**Acceptance criteria**

- Exported records include the actual resolved selected-cell/unit count for the completed result.
- Replicate/group selection that expands to multiple Cells reports the expanded count, not only one selection entry.
- Plotly trace count remains a separate field and cannot overwrite the cell-count field.
- Focused tests cover a selection-entry count that differs from resolved Cell count and a plot with multiple traces per Cell.
