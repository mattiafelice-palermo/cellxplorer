## The overriding constraint: scientific output must not change

The user's explicit instruction for this child was that the calculations must not change. It is also
the parent's locked decision 1. This was verified independently of the repository's own tests,
because the repository's golden fixtures were refreshed during this child and a refreshed fixture
cannot prove its own correctness.

**Method.** Before the implementer started, the reviewer captured the full `calc.per_cycle`
projection for all four golden `.ndax` sources at 12 significant figures (`float_format="%.12g"`),
computed through `parsing.parse_timeseries` → `calc.per_cycle` with no cache and no database
involvement. After the child landed, a git worktree was created at the pre-040.3 commit `c0a8e8e`,
the baseline was re-derived there from the *old* code, and compared against the current tree.

```text

cycles_time_steps.ndax           IDENTICAL  sha256=2e8b9d54bb8a183c…
```

Every derived per-cycle quantity — capacities, energies, efficiencies, durations, voltages — is
byte-identical across the change.

(An initial comparison reported spurious differences caused by a Windows newline-translation defect
in the reviewer's own capture script, which wrote `\r\r\n` to disk. The re-derivation above used a
clean baseline computed inside the pre-040.3 worktree and is the authoritative result.)

## Parser identity

Grammar `<prefix>:<adapter_revision>:r<canonical_raw_version>`, built on 040.2's
`source_parser_descriptor()` rather than duplicating its logic:

```text
nb:v2026.06.11:r1   (17 chars)
nx:6:r1             (7 chars)
```

Both inside the `String(30)` `SourceFile.parser_version` bound, which is asserted at construction
via `parsing._MAX_PARSER_IDENTITY_LENGTH` rather than checked by eye. Tests lock determinism,
content-independence and `CALC_VERSION`-independence — the spec's locked identity properties.

Two entry points, correctly separated: `parser_identity(path)` (content-aware) and
`current_parser_identity_for_extension(ext)` (zero I/O).

## The silent-recompute defect — the primary review target

This was the specific bug hunted: a saved analysis pinned to identity P1, whose P1 cache exists,
being recomputed under current identity P2 and relabelled. It would not surface as a test failure
unless someone wrote the test, and a user would experience it as their numbers quietly changing.

`test_legacy_pinned_analysis_renders_from_pinned_cache_without_reparsing` covers it properly. It
writes real cache files at a genuinely different old identity (`nb:vOLD.00.00:r1`), supplies
legacy-shaped provenance (scalar `parser_version`, no `files` array), and patches
`scanner.parse_file` with `side_effect=AssertionError` so any reparse fails loudly rather than
passing silently. It then asserts real data renders, that provenance reports the *old* identity, that
old ≠ current (so the assertion is meaningful), and that a `newer_parser` badge appears.

**Reviewer check for a bypass.** A `parse_file` patch only proves anything if that is the sole
reparse route. Confirmed: `analysis_engine` reaches parsing only through `scanner.parse_file`
(two call sites, lines 1670 and 2420), and `stitch` exclusively calls `cache.load_cycles` /
`cache.load_raw`, which are read-only and never build. There is no path by which the analysis flow
could reparse while evading the patch.

`test_missing_legacy_cache_is_not_relabeled_as_current` covers the companion case: a pinned identity
with no cache yields an empty series and a `cache_missing` badge naming the missing identity, rather
than a silent reparse under current identity.

## Cache invalidation is surgical

Proven with `patch.dict` on the format registry rather than by mutating released constants:
bumping the Excel adapter revision leaves binary identities byte-identical
(`test_bumping_excel_revision_does_not_disturb_binary_current_check`), the converse holds, and
bumping `CANONICAL_RAW_VERSION` changes both.

## Performance invariants

`scanner._has_current_scientific_cache` resolves the expected identity from the stored
`SourceFile.ext` alone through `current_parser_identity_for_extension`, with no file I/O and no
parser import, so list and backfill paths remain safe for many sources at once.
`test_current_identity_check_does_not_touch_the_filesystem` and
`test_has_current_scientific_cache_uses_extension_only` enforce this directly rather than leaving it
to inspection.

## Items recorded for the 040.5 closure review

### `ANALYSIS_CACHE_VERSION` 4 → 5

The implementer flagged this itself as not strictly required. Accepted: the analysis-result digest
structure changed to carry the per-source `files` array, and serving a result cached under the old
digest structure against new-shaped provenance is the kind of ambiguity a version bump exists to
prevent. Conservative and correct.

**User-visible consequence:** cached analysis *results* are invalidated, so users pay a one-time
recompute after upgrading. This is not a scientific change — recomputation reproduces the same
numbers, as the baseline above demonstrates — but it is a performance event worth naming in release
notes. 040.5 should confirm it is mentioned.

### `display_parser_version` "mixed" sentinel

New decision not specified by the spec. When contributing sources legitimately carry different
identities, the human-facing summary returns `"mixed"` rather than arbitrarily picking one, with
per-source truth remaining in `sources[].files[]`. Accepted as truthful; the `frontend/src/api.ts`
type documents it. 040.4/040.5 should confirm the UI renders it sensibly rather than showing a bare
"mixed" with no affordance to see the per-source detail.

### Pre-existing defect fixed in passing

Portable import was not remapping `provenance.sources[].files[].hash` alongside `file_hashes`. Found
and fixed by the implementer. Out of this child's strict scope but correct to fix here, since the
`files` array is what this child introduced.
