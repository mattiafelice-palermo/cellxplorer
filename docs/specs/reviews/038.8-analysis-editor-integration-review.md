## Findings

### R1 — Medium: `AnalysisEditor` still constructs application routes

**Affected files**

- `frontend/src/features/analyses/editor/AnalysisEditor.tsx`
- `frontend/src/pages/AnalysisPage.tsx`
- `frontend/src/features/analyses/workspace/AnalysisWorkspaceContent.tsx`

**Current**

The child locks `AnalysisEditor` as a feature-owned editor and explicitly states that it must not know route URL construction. The extraction removed `useParams`, but the new editor still imports `useNavigate` from `react-router-dom` and directly constructs application destinations:

- duplicate success: `navigate(`/analyses/${a.id}`)`;
- delete success: `navigate("/analyses")`;
- not-found recovery: `navigate("/analyses")`.

The editor also still owns `useSearchParams` for the existing `?tab=` / `?plot=` deep-link consumption. That query-parameter behavior is not itself treated as a defect in this finding; the concrete violation is that the feature editor constructs route URLs directly. The implementation record currently states that the editor does not construct URLs, which is therefore not true at this checkpoint.

**Target**

Keep the editor product behavior unchanged while removing direct route construction from `AnalysisEditor`.

Use the smallest route-adapter boundary that fits the existing architecture. For example, the route/workspace adapters may supply narrow semantic navigation callbacks/intents for:

- open the duplicated analysis;
- return to the Analysis Database after delete;
- return to the Analysis Database from the not-found state.

An equivalent semantic navigation mechanism is acceptable if it keeps URL construction outside `AnalysisEditor`. Do not introduce a global state store or a general routing abstraction for this fix.

Preserve the existing deep-link behavior, workspace keep-mounted/unmount behavior, duplicate/delete invalidations, not-found UX, history semantics, and the minimal typed editor boundary. If the chosen fix needs a small extension to `AnalysisEditorProps`, keep it narrowly semantic rather than passing router objects or the editor state object.

**Acceptance criteria**

1. `AnalysisEditor.tsx` contains no direct construction of `/analyses` or `/analyses/<id>` navigation destinations and no `navigate(...)` calls that encode those routes.
2. Duplicate success still opens the duplicated analysis through both direct-route and workspace usage.
3. Delete success and the not-found Back action still return to the Analysis Database through both direct-route and workspace usage.
4. Existing `?tab=` / `?plot=` deep-link restore-and-consume behavior remains unchanged; do not drop or double-consume it while changing the navigation boundary.
5. `AnalysisPage.tsx` remains a thin adapter and `AnalysisWorkspaceContent.tsx` remains page-independent; no module under `features/analyses/` imports a route page.
6. Update the 038.8 implementation record so its statement about route/URL ownership matches the actual implementation.
7. Rerun the focused frontend/app-channel checks, TypeScript, Vite, structural searches, `git diff --check`, and `python scripts\\preflight.py --no-cache`; record exact results and continue to record the manual matrix accurately as run or NOT RUN.
