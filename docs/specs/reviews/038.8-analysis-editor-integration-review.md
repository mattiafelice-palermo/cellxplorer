## Findings

### R1 — Medium: `AnalysisEditor` still constructed application routes

**Status: RESOLVED in `6b512b1e17b14ec1dcaa8eb1c55922171545e893`.**

**Original current state**

The initial extraction removed `useParams`, but `AnalysisEditor` still used `useNavigate` and directly constructed `/analyses/${id}` and `/analyses` destinations for duplicate success, delete success, and the not-found Back action. That contradicted the child’s locked feature/route ownership boundary.

**Resolution verified**

The final editor no longer imports `useNavigate`, contains no `navigate(...)` call, and does not construct `/analyses` navigation destinations. It receives two narrow semantic callbacks:

- `onOpenAnalysis(analysisId)`;
- `onOpenAnalysisDatabase()`.

`AnalysisPage.tsx` and `AnalysisWorkspaceContent.tsx` own the corresponding route construction. Duplicate, delete, and not-found transitions call those semantic callbacks. Existing `useSearchParams` handling remains in the editor for the pre-existing `?tab=` / `?plot=` deep-link restore-and-consume behavior.

The new focused `analysisEditorNavigation.test.ts` pins this boundary by asserting the editor has no `useNavigate`, `navigate(...)`, or `/analyses` destination literal while both adapters own the required destinations and callback wiring.

**Acceptance:** satisfied.
