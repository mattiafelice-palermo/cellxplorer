## Findings

### F1 — Stage 1's first freshness token could never match (fixed during implementation)

The index memo was first keyed on `st_mtime_ns` + size. Measurement showed no improvement, and a profile of the real router boundary showed `_validate_raw_layout_index` still running 6× per request — every lookup missed.

Cause: `cache._touch()` rewrites the mtime of both the Parquet and index files on every read to drive cache-reclamation LRU (`cache.py:1760-1761`, `1941-1942`), so an mtime-based token is invalidated by the very act of reading.

Resolution: the token is now built from file identity and size (`st_ino`, `st_dev`, `st_size` for both files), which survives a touch and changes on the atomic replace used to publish a new index. Verified directly: after `os.utime`, `st_ino`/`st_dev`/`st_size` are unchanged while `st_mtime_ns` differs. Covered by `test_touching_the_pair_for_lru_does_not_invalidate_the_memo`.

**This is worth remembering:** mtime is not a valid freshness signal anywhere in this cache, because reads deliberately rewrite it.

### F2 — Stage 2 was inverted in the original analysis (corrected before implementation)

The first proposal was to skip the isolation `deepcopy` on the process path and keep it on the serial path. That is backwards — `_run_process` pickles jobs to workers, which already deep-copies, whereas `_run_serial` executes in-process on shared objects.

The corrected proposal was to relocate the copy into `_run_serial`. Measurement showed that would have been pointless for the workload that matters: moving previews take the serial path (`small_selected_row_count`, 16,492 rows against a 24,000 gate), so relocating the copy would have preserved its full cost exactly where it hurt.

Resolution: a direct experiment digested `plan`, `plan_diagnostics`, `descriptor` and `request` before and after `_run_serial` across three workloads and found **no mutation**, so the copy was deleted outright. Pinned by `test_owner_job_state_is_not_mutated_by_a_serial_run`.

### F3 — Stage 5 closed by measurement, not implemented

See the spec's Stage 5 section. A realistic drag supersedes at most one request, at the idle promotion. Recorded, not implemented, with a failing-tripwire test if the cadence ever changes.

### F4 — Stage 2's invariant is now load-bearing across requests (accepted, mitigated)

Before Stage 1, each request re-read its own index, so the non-mutation property was merely wasteful to violate. Now that one validated index object is shared between requests, a consumer that mutated it would corrupt other requests.

Mitigation: `test_owner_job_state_is_not_mutated_by_a_serial_run` runs the real read path and fails on any mutation. Both the test and the code carry comments explaining that a future change needing to mutate plan state must reintroduce a copy at that point.

## Outstanding

- **Browser/manual acceptance NOT RUN.** The Stage 3 frontend change (`persist: false` for moving previews) is covered by type check, bundle, and a backend route test, but no drag has been exercised in the running app.
- The `six-cell-full-range-capacity` workload remains at ~1.28 s and was essentially untouched by this child. It is dominated by capacity-axis scientific work, not fixed overhead, and is out of scope here — worth its own child if interactive capacity-axis navigation matters.
- `pool_not_ready_serial` appears throughout this harness because it invokes the router directly and never runs app startup, which is the only caller of `start_time_capacity_worker_pool()`. Absolute numbers here are therefore serial-path numbers. This is correct for the moving preview (which is gated to serial regardless) but understates full-range workloads in the real app.
