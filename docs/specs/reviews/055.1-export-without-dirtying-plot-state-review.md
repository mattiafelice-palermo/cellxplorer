## Confirmed by code inspection

The following parts are correct and should not be reworked unless resolving R1 proves the diagnosis itself was wrong:

- `exportFigure(...)` no longer hands Plotly the caller-owned trace array or nested layout objects. It deep-clones the export layout and traces before any image renderer sees them.
- The change does **not** reset `activePlotBaselineSignature`, `dirty`, or any other saved-plot dirty flag after export. It therefore does not hide pre-existing real edits by resetting state after the fact.
- Export-only width/height/autosize/margin/title changes remain on the derived export figure.
- The shared `styledPlotExportPreview(...)` and `downloadStyledPlotExport(...)` paths both route through `exportFigure(...)`, so PNG/SVG/PDF and shared preview generation inherit the clone boundary.
- Cycles and Time/Capacity use the same `exportFigure(...)` helper in their family-level export paths; Steps uses the shared styled export helpers. The fix is therefore placed at an appropriate common boundary rather than copied into one family.
- `PlotHeader`'s ordinary one-click export action uses the already-selected persistent format and does not itself rewrite `export_format`; explicit changes made inside export settings remain intentional persistent style edits, which is consistent with the child spec.
- The implementation does not broaden into saved-plot naming or series-isolation work.

## Dirty-state architecture checked

The actual dirty contract remains:

- `AnalysisEditor.tsx::snapshotSignature(spec)` delegates to `plotViewSignature(spec)`;
- `activePlotDirty` is true only when that persisted-view signature differs from `activePlotBaselineSignature`;
- `plotViewSignature(...)` serializes saved-view state from `selection`, `dcir_segments`, `computation`, `aggregation`, and `presentation`.

The current regression test does **not** exercise that contract. It proves only that mutations made to the figure returned by `exportFigure(...)` do not flow back into the particular `traces`, `layout`, and `style` variables constructed by the test.

This matters because the reported reproduction names inferred `xaxis.type` / `yaxis.type` mutations on a derived Plotly layout, while the Cycles layout path constructs fresh axis/layout objects from normalized style values and `currentPlotStyle(...)` itself returns a normalized copy. A mutation to a derived layout object is therefore not, by itself, evidence that `plotViewSignature(spec)` changed.

The patch may still be the correct fix, but the repository currently lacks the causal proof required by the spec.

## Findings

### R1 — P1 — The regression does not prove the export mutation changes the persisted dirty signature

**Affected files**

- `frontend/tests/plotExport.test.ts`
- `frontend/src/features/analyses/editor/plotting/plotExport.ts` if the current diagnosis proves incomplete or incorrect
- relevant actual mutation owner if the reproduced false-dirty state originates elsewhere

**Current**

`plotExport.test.ts` constructs standalone traces/layout/style values, calls `exportFigure(...)`, manually mutates the returned export figure, and checks that those standalone inputs remain unchanged. It never constructs an `AnalysisSpec`, never evaluates `plotViewSignature(...)` / `snapshotSignature(...)`, and never demonstrates the user-visible transition that defines the bug: baseline signature equal before export and unequal after export on the pre-fix implementation.

The implementation handoff reports that Plotly added inferred nested axis fields to the shallow export graph, but Spec 055.1 explicitly required the baseline signature, pre-export current signature, post-export current signature, and exact persistent field(s) that changed. That evidence is absent.

Code inspection also shows why this distinction is material: `activePlotDirty` depends only on the serialized analysis spec, while the inspected Cycles layout/axis/style builders create derived objects rather than storing Plotly's inferred `xaxis.type` / `yaxis.type` fields in the spec.

**Target**

Tie the regression to the actual saved-plot dirty-state mechanism. Reproduce the false-dirty transition against the pre-fix parent or an equivalent deterministic harness using the real saved-view signature boundary, identify the exact persisted field/reference that changes, and prove the current fix prevents that same change.

If the former shallow `exportFigure(...)` path cannot be shown to change `plotViewSignature(spec)`, treat that as evidence that the present diagnosis is incomplete and locate/fix the actual state mutation instead of retaining an unrelated prophylactic clone as the claimed root-cause repair.

**Acceptance criteria**

- Record the saved-plot baseline signature immediately before export.
- Record the current saved-view signature immediately before export and show it matches the baseline.
- Reproduce the pre-fix export action and record the post-export signature plus the exact persistent field/reference that changed.
- Demonstrate that the repaired path leaves the same signature unchanged after export.
- Add a focused regression that fails when the actual root-cause repair is removed/reverted and passes with the repair.
- Cover an unchanged saved plot remaining clean after export.
- Cover an already-dirty saved plot remaining dirty after export; export must neither create nor clear unrelated dirty state.
- Establish that preview and PNG/SVG/PDF use the same side-effect-free boundary, without creating separate family-specific fixes.
- Do not add a post-export dirty/baseline reset workaround.
- Re-run the focused test and canonical preflight after the final repair/evidence change.
