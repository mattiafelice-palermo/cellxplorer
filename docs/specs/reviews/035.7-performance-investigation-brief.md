## Current implementation points to verify

The following were observed previously and must be re-verified against the current branch:

1. `inspection_worker_count()` is capped at four workers.
2. Each file inspection performs:
   - initial `stat()`;
   - full SHA-256 hashing;
   - `parsing.read_header_metadata(...)`;
   - final `stat()`;
   - insertion into the in-memory header cache.
3. `/api/imports/inspect-paths` performs a serial preliminary `stat()` pass to calculate total bytes.
4. `build_identity_snapshot()` loads complete `SourceFile` ORM objects with joined relationships rather than a narrow scalar projection.
5. Exact hash matching uses a dictionary.
6. Soft matching loops over all snapshot candidates for each file and normalizes values repeatedly.
7. Background-job progress is maintained per file.
8. The inspection response no longer includes complete `header_metadata`, following commit `439c98ea16ec5986f350ff31a2e4d9c422911a45`; verify whether other large fields remain.
9. The frontend waits for the inspection response and transforms it before opening the third modal.

Do not treat any item above as proven until confirmed on the current branch.

## Hypotheses to test

Test these hypotheses with measurements rather than assuming them:

### H1 â€” Hashing and Neware metadata parsing dominate

If true, database and payload optimizations may save little. The largest safe improvements would probably come from:

- better worker-count selection;
- avoiding duplicate file reads where technically possible;
- or deferring full identity work while preserving mandatory verification before final registration.

### H2 â€” Four workers underutilize a local SSD

If true, 8 or 12 workers may reduce wall time. Confirm that this does not worsen HDD or network-path behaviour.

### H3 â€” The identity snapshot is heavier than intended

Loading full ORM rows and relationships may retrieve and instantiate unnecessary data.

### H4 â€” Soft matching has undesirable scaling

The current algorithm may perform approximately:

`selected files Ã— registered source files`

candidate scans.

### H5 â€” Progress bookkeeping adds significant overhead

Per-file job records, callbacks, polling, list scans, copying, and serialization may consume meaningful time for 1,000 files.

### H6 â€” The preliminary serial stat pass is measurable

One extra serial filesystem call per selected file may be avoidable.

### H7 â€” Response creation and frontend transformation are material

Even after removing `header_metadata`, the response may still contain unnecessary data or require expensive transformation before the third modal opens.

## Correctness constraints

Any recommendation must preserve:

- full identity and duplicate/update correctness;
- file-change detection during inspection;
- deterministic output order;
- stable duplicate/update classification;
- archived-cell behaviour;
- provenance;
- safe final registration;
- local-first SQLite and filesystem architecture;
- no database session sharing across worker threads;
- bounded filesystem concurrency;
- no N+1 database access;
- no per-row source-file or Parquet reads in list endpoints.

Do not recommend weakening SHA-256 identity without explicitly documenting the correctness impact.

If proposing deferred hashing, the recommendation must ensure that:

- the third modal may open before hashing completes;
- duplicate/update status is visibly pending;
- the final Import action remains disabled until required identity checks complete;
- the source is revalidated before registration;
- errors are surfaced per file;
- no incorrect or partially verified registration can occur.

## Decision standard

Do not recommend a permanent optimization merely because it is theoretically cleaner.

A recommendation should be considered material when it is expected to reduce the approximately 17-second blocking interval by at least one of:

- **1 second**, or
- **10%**,

unless it is a prerequisite for a larger optimization.

Prefer the smallest reversible changes with measured benefit.
