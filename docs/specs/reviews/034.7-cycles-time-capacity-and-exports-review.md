## Follow-up tasks

### R1 — High: analysis and Library contracts still expose and accept multiple Tests

**Affected files**

- `backend/app/services/analysis_engine.py`
- `backend/app/routers/library.py`
- `frontend/src/api.ts`
- analysis, Library, staleness, and source-chain tests

**Current**

The corrected architecture says a Cell has one ordered source chain and exactly one internal Test
row. The implementation still:

- makes `cell_ordered_hashes` iterate and flatten every `cell.tests` row;
- makes `current_cell_hashes` order by `Test.id` and therefore silently accepts several rows;
- emits `test_ids` in each analysis result/provenance source entry;
- requires `test_ids` in the frontend `Provenance` type;
- calculates and returns `n_tests` in Library summaries and detail payloads.

This preserves the rejected multiple-Test hierarchy in scientific/API contracts. It also means an
invalid second Test row would be silently incorporated into cycles, cache keys, provenance, and
Library totals instead of failing the one-row invariant.

**Target**

Introduce or reuse one canonical backend Cell-source-chain resolver that:

1. requires exactly one internal Test row for every non-empty normal Cell;
2. returns sources in `TestFile.position` order;
3. fails closed with a structured internal-invariant error when the row count is not one;
4. is used by analysis, provenance/staleness, Library summaries, portable work, and monitoring.

New scientific/API output must describe only `cell_id`, ordered source hashes, descriptors, and
positions. Do not emit Test IDs or Test counts. Existing persisted provenance containing `test_ids`
may remain readable during upgrade, but new provenance must not write the field and no frontend
behavior may depend on it.

**Acceptance criteria**

- Cycles and time/capacity results contain no `test_ids`.
- Frontend `Provenance` and Library contracts contain no Test-shaped fields.
- One internal Test row produces the same ordered hashes and scientific results as today.
- Zero or two internal rows fail clearly before compute/cache/provenance work.
- A focused test proves a second Test row cannot be silently flattened into a Cell analysis.
- Single-source and valid multi-source golden projections remain unchanged.

### R2 — Medium: a boundary marker is lost when the transition row is not plottable

**Affected files**

- `frontend/src/sourceChainPlot.ts`
- `frontend/src/pages/AnalysisPage.tsx`
- `frontend/tests/sourceChainPlot.test.ts`

**Current**

`sourceBoundaryPointIndices` checks only the exact row where `source_position` changes. If that row
has a null/non-finite x or y value for the selected quantity, it skips the row and never searches
forward within the new source. The function therefore does not always return the first **plotted**
point of the later source, despite the specification and test name.

Example:

```text
source position: [1, 1, 2, 2]
y:               [10, 11, null, 12]
```

The required marker is at the fourth row; the current helper returns none.

**Target**

For each transition to a later source, scan within that source segment until the first row with
finite plotted x and y. Emit at most one marker per later source. If the source has no plotted point
under the current filters/quantity, emit no marker.

**Acceptance criteria**

- The null-transition example above returns the later finite row.
- Multiple invalid rows before the first valid point are handled.
- A wholly unplottable source produces no marker.
- One marker maximum is produced per later source.
- Live, saved, thumbnail, and image-export figures continue to share the same marker trace.
