## Findings

### R1 — Medium: compact Time-axis requests take the slower prepared phase-only path — **Resolved**

Affected files:
- `backend/app/services/analysis_engine.py`
- `backend/app/services/time_capacity_derived.py`
- `scripts/profile_time_capacity_transforms.py`
- `tests/test_analysis_engine.py`
- `docs/specs/050.6-prepared-time-capacity-derived-rows.md`
- `docs/agent-knowledge/state-and-performance.md`

**Current after fix**

Compact Voltage/Current + Time no longer opens the prepared sidecar merely to obtain `phase_code`. It computes phase from the already-selected raw rows, while phase-capacity/specific/areal reconstruction remains skipped. Prepared access is now gated by `transform_needs.phase_capacity`, which preserves exact prepared reuse for capacity axes, derivative views and full/non-compact responses.

The rerun correctly measures the actual production path rather than labeling the phase-only sidecar as an optimization. Representative medians are:

| Scenario | Forced-fallback control | Actual production | Result |
| --- | ---: | ---: | --- |
| 1 cycle / Time / 1 Cell | 23.8 ms | 23.2 ms | no material regression |
| 1–150 / Time / 1 Cell | 80.6 ms | 80.7 ms | effectively identical |
| All / Time / 1 Cell | 92.0 ms | 90.2 ms | effectively identical |
| All / Time / 6 Cells | 533.0 ms | 543.1 ms | descriptive run variance; no extra sidecar I/O |
| 1–150 / capacity / 1 Cell | 168.8 ms | 106.7 ms | 36.8% prepared win |
| All / capacity / 1 Cell | 202.5 ms | 117.7 ms | 41.9% prepared win |
| All / capacity / 6 Cells | 1,218.8 ms | 718.6 ms | 41.0% prepared win |

The large Time-axis improvement relative to the accepted 050.5 pre-optimization baseline now comes from the scientifically safe dependency pruning — chiefly not reconstructing unused phase capacity — rather than from an unnecessary phase-only sidecar read.

### R2 — Medium: `build_write_behind()` cannot publish the prepared sidecar because it joins its own pending thread — **Resolved**

Affected files:
- `backend/app/services/cache.py`
- `tests/test_calc_and_cache.py`
- 050.6 lifecycle documentation

**Current after fix**

`_wait_for_pending()` now declines only the impossible/self-deadlocking operation of joining `threading.current_thread()`. The write-behind owner remains registered in `_pending` throughout raw/index, cycles and derived publication, so external readers/builders still join that thread and cannot cross the pending boundary before the complete writer returns. Inside the owner, `prepare_time_capacity_derived(..., raw_frame=raw)` can now proceed from the already validated in-memory frame and publish the derived payload/index.

A focused regression asserts the complete write-behind output set and no swallowed logger exception while preserving the single parse.
