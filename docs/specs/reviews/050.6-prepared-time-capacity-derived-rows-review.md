## Review scope

Reviewed the complete 050.6 delta from `8c6fb358` to `bb3e5673` on `feature/runtime-performance-optimization`, including dependency-aware Time/Capacity transforms, the new exact source-local prepared phase/capacity sidecar, cache identity/publication/invalidation, selective reads, scanner/scientific-preparation integration, profiler changes, tests, and durable documentation.

The implementation preserves the intended scientific architecture: canonical raw Parquet remains the raw dataset, phase/capacity science is shared between preparation and request fallback, the prepared artifact is regenerable and versioned independently from `CALC_VERSION`, missing/invalid/busy prepared data falls back to exact request-side calculation, and prepared capacity-axis requests show substantial broad-range wins in the implementer evidence. The reported parity/golden coverage is also strong.

Two concrete implementation issues remain. One is a measured production-path performance regression: compact Time-axis requests still read the prepared sidecar even after 050.6 makes phase capacity unnecessary, although the implementer's own profiler proves that sidecar I/O is slower than computing phase from the already-loaded raw rows. The second is a cache-lifecycle bug in `build_write_behind()`: the background writer calls the public prepared-cache builder while that same writer is registered as the pending thread, causing the builder to attempt to join the current thread and fail.

No derivative-specific optimization, multiresolution overview, frontend feature, SQLite migration, parser/canonical-format change, or proto-child 050.P1 implementation was identified in the 050.6 delta.

## Findings

### R1 — Medium: compact Time-axis requests take the slower prepared phase-only path

Affected files:
- `backend/app/services/analysis_engine.py`
- `backend/app/services/time_capacity_derived.py`
- `scripts/profile_time_capacity_transforms.py`
- `tests/test_analysis_engine.py`
- `docs/specs/050.6-prepared-time-capacity-derived-rows.md`
- `docs/agent-knowledge/state-and-performance.md`

**Current**

`TimeCapacityTransformNeeds` correctly establishes that a compact Voltage/Current-vs-Time request needs continuous time and phase, but does **not** need absolute phase capacity, specific capacity, or areal capacity. `compute_time_capacity()` then attempts the prepared sidecar whenever `transform_needs.phase` is true, reading `phase_code` even when phase capacity is not needed.

The implementation's own profiler shows that this production choice is counterproductive after Part A removes the expensive unused capacity work. On the approved fixture, the phase-only prepared path is slower than the forced request-side fallback:

| Scenario | Faster computed-phase path | Current prepared-phase path | Regression |
| --- | ---: | ---: | ---: |
| 1 cycle / 1 Cell | 25.3 ms | 38.3 ms | +51.5% |
| 1–150 / 1 Cell | 96.3 ms | 124.3 ms | +29.1% |
| All / 1 Cell | 116.5 ms | 157.3 ms | +35.0% |
| All / 6 Cells | 549.8 ms | 677.3 ms | +23.2% |

The broad Time-axis acceptance bar was therefore missed for a specific, avoidable reason: the implementation pays a second Parquet/index access to replace a cheap phase classification even though the expensive `_phase_capacity()` work is already skipped.

**Target**

For compact phase-only Time-axis requests, do not open/read the prepared derived sidecar. Compute phase from the already-selected raw rows and keep phase capacity/specific/areal work skipped. Continue using the prepared sidecar where exact phase capacity is actually required (capacity axes, derivatives, and full/non-compact contracts) and preserve the measured capacity-axis wins.

The reviewer accepts the profiling result that prepared phase-only I/O is not useful; do not add speculative caching or another representation merely to force the original prepared-vs-fallback timing assumption to pass.

**Acceptance criteria**

- [ ] With a valid sidecar present, compact Voltage/Current + Time does not call/read `load_indexed_time_capacity_derived()` and reports prepared access as `not_needed` (or an equivalently truthful diagnostic state).
- [ ] Compact Time-axis still calls no phase-capacity/specific/areal reconstruction and emits the same scientific payload as the exact fallback.
- [ ] Capacity-axis, derivative, and full/non-compact requests still use validated prepared phase/capacity when available and preserve prepared-vs-fallback parity.
- [ ] Re-run the 050.6 profiler and record the **actual production Time-axis path**, showing no material one-cycle regression and the broad improvement relative to the accepted pre-050.6 baseline; do not claim a prepared-phase win that the evidence disproves.
- [ ] Preserve the reported broad capacity-axis gains or explain any measured variance without broadening scope.
- [ ] Update the 050.6 implementation record and durable performance documentation so they describe the measured phase-only decision accurately.

### R2 — Medium: `build_write_behind()` cannot publish the prepared sidecar because it joins its own pending thread

Affected files:
- `backend/app/services/cache.py`
- `tests/test_calc_and_cache.py` or equivalent focused write-behind coverage
- any 050.6 lifecycle documentation that claims write-behind publication

**Current**

`build_write_behind()` creates `_write`, stores its `thread` in `_pending[file_hash]`, and starts it. Inside `_write`, after publishing raw and cycles, 050.6 calls `prepare_time_capacity_derived(file_hash, parser_identity, raw_frame=raw)`.

`prepare_time_capacity_derived()` begins by calling `_wait_for_pending(file_hash)`. On this path `_pending[file_hash]` is the currently executing `_write` thread itself, so `_wait_for_pending()` executes `thread.join(timeout)` on the current thread. Python raises `RuntimeError: cannot join current thread`. The nested optional-sidecar `except Exception` catches/logs the error, so the raw/cycle write still completes but the prepared artifact is silently absent until a later repair/preparation path happens to create it.

This contradicts the 050.6 new/current-cache lifecycle contract and the implementation record's statement that `build_write_behind()` prepares the derived artifact from the in-memory frame.

**Target**

Allow the write-behind owner to publish the optional derived artifact from the already validated in-memory raw frame without waiting on itself, while preserving `_pending` semantics for **external** readers/builders. Do not remove the external wait guarantee or expose partially published raw/cycle caches simply to avoid the self-join.

**Acceptance criteria**

- [ ] A focused write-behind regression creates a fresh cache with `build_write_behind()`, waits for completion, and asserts raw, cycles, raw index, derived payload, and derived index are all current.
- [ ] The write-behind parse still occurs once and uses the in-memory raw frame for derived preparation; it does not reopen/reparse the source solely for 050.6.
- [ ] No self-join exception is logged/swallowed and the worker terminates normally.
- [ ] External `wait_for_pending()` callers still wait for the complete write-behind publication boundary; no partial raw/cycle publication becomes observable through this fix.
- [ ] Existing write-behind, cache safety, cleanup protection, prepared-cache, golden, and canonical preflight checks remain passing.
