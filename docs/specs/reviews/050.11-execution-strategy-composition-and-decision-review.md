## Findings

### R1 — High — A0 and the Rust candidates do not use the same backend timing boundary

**Affected files**

- `scripts/profile_time_capacity_composition.py`;
- `docs/specs/050.11-execution-strategy-composition-and-decision.md`.

**Current**

The reported `A0` backend wall comes from `concurrency.run_production_sample()`. That timer stops immediately after `compute_time_capacity()` and records JSON serialization separately.

`_run_composed_candidate()` instead starts its candidate phase before read/native work, calls `_run_patched_backend()`, then calls `concurrency._serialize_result(result)`, and only **after serialization** stops `phase_wall_ms`. The published `backend_wall_ms = owner_setup + phase_wall_ms` therefore includes serialization for R1/D0/D1/D2 but not for A0.

The resulting headline comparisons such as “R1 is 34.9% faster than A0” and “normal Rust is 45.8% slower than A0” are not like-for-like complete-backend measurements.

**Target**

Use one identical backend wall boundary for A0/R1/D0/D1/D2. Either exclude serialization from every candidate and keep it as a separate metric, matching current A0 semantics, or include the same serialization boundary in A0 as well. Preserve serialization as an independently reported stage.

**Acceptance criteria**

- A0 and every composed candidate start/end at the same backend boundary.
- Serialization is either excluded from all candidate backend walls or included in all of them; it remains separately reported.
- Rerun the full representative composition matrix after correction.
- Update all A0-vs-native percentages, interaction classifications, and the final A-G architecture decision from corrected medians.
- Scientific parity/order and existing cache-hit controls remain unchanged.

### R2 — High — composed native candidates double-execute substantial pre-native transform work

**Affected files**

- `scripts/profile_time_capacity_composition.py`;
- `docs/specs/050.11-execution-strategy-composition-and-decision.md`.

**Current**

Before the Rust call, `_build_derivative_dataset()` / `_build_normal_dataset()` independently:

- filter/sort the selected raw rows;
- resolve continuous-time/phase/capacity needs;
- align or compute phase/capacity data;
- materialize the native numeric buffers.

After Rust returns, `_run_patched_backend()` calls the normal `analysis_engine.compute_time_capacity()` path over the same prefetched payloads. That production path repeats the selected-row filter/sort and the same continuous-time/phase/capacity transforms before reaching the patched derivative/display function.

The reported `buffer_prepare_ms` therefore is not merely unavoidable Python→native conversion cost: it contains a second execution of production transforms that a real single-pass integration would already have available at the native call site. On the reported real 6-Cell dQ/dV row this prepass is about 300 ms, large enough to materially distort the complete-boundary denominator and therefore the C-vs-D decision.

**Target**

Measure the composed architecture with one scientific pre-native transform pass per request. Python should resolve/read each Cell once, perform the existing owner/per-Cell transforms once, capture the already-produced compact native inputs at the real derivative/display boundary, make one coarse native call for all selected Cells, then continue the existing downstream masking/downsampling/provenance/response assembly without rerunning those upstream transforms.

This remains benchmark-only; do not productionize the Rust path here. A narrowly factored benchmark helper is acceptable if needed, but it must preserve the production mathematics and downstream assembly rather than creating a second scientific pipeline.

**Acceptance criteria**

- Each selected row is filtered/sorted and each required continuous-time/phase/capacity transform is executed once per candidate request, not once for buffer construction and again inside the patched backend.
- Report native-specific buffer materialization/copy separately from ordinary production transforms.
- Preserve one coarse Rust call for all selected Cells and deterministic ordering.
- Rerun A0/R1/D0/D1/D2 with the corrected single-pass boundary and exact scientific parity.
- Re-evaluate whether sequential Rust or bounded Rayon is the best production architecture from the corrected complete request, rather than carrying forward the current C outcome automatically.

### R3 — Medium — the intended 10-Cell derivative composition case is silently absent

**Affected files**

- `scripts/profile_time_capacity_composition.py`;
- `scripts/profile_time_capacity_concurrency.py` only if the shared workload generator is intentionally extended, otherwise keep the change local to 050.11;
- `docs/specs/050.11-execution-strategy-composition-and-decision.md`.

**Current**

`_selected_workloads()` explicitly asks for `derivative-10-all-dqdv`, but it filters `concurrency.workload_matrix()`, whose derivative matrix only generates 1-, 3- and 6-Cell dQ/dV workloads. The requested 10-Cell derivative row therefore never exists and is silently omitted.

That matters specifically for the C-vs-D decision: 050.10 showed increasing useful cross-Cell Rayon scaling on broad 6/10-Cell derivative work, while 050.11 currently decides the native architecture without a composed 10-Cell derivative case even though 10/11 real Cells are available.

**Target**

Add the intended 10-Cell broad derivative composition workload locally to 050.11 (or deliberately extend the shared generator without changing 050.9 evidence semantics) whenever at least ten representative Cells are available.

**Acceptance criteria**

- Golden fixture runs a real 10-Cell broad dQ/dV composition row.
- Real application data run the 10-Cell broad dQ/dV row when at least ten Cells are available; otherwise record `NOT RUN` with the actual reason.
- A0/R1/D0/D1/D2 are measured with the same corrected boundaries from R1/R2.
- Include the 10-Cell derivative result in the final sequential-Rust-vs-Rayon architecture decision rather than extrapolating from six Cells.

## Reviewer assessment of the current evidence

The qualitative direction is credible but the final architecture choice is premature.

Current evidence still strongly supports **native Rust for broad derivative work**: even under the candidate-unfavorable harness, the reported real 6-Cell dQ/dV request falls from about 2009 ms on A0 to about 1213 ms with resident sequential Rust. Read concurrency contributes little at the complete request boundary, and ordinary Time/Capacity should remain on the existing Python/NumPy path.

However, 050.11's purpose is specifically to decide whether the accepted production architecture should stop at sequential Rust or retain bounded cross-Cell Rayon. The current harness inflates all native candidates with duplicated upstream work, uses a serialization boundary that differs from A0, and omits the intended 10-Cell derivative composition row. Those issues can suppress or misattribute the marginal value of Rayon. The current outcome **C — sequential Rust kernel** therefore must not be promoted to 050.12 until R1-R3 are corrected.
