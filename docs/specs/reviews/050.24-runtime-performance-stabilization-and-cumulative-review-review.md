## Findings

### R1 — Medium: Refinement survives the `stacked` transition even though stacked mode is refinement-ineligible

**Affected files**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRefinementPolicy.ts`
- `frontend/tests/timeCapacityRefinementPolicy.test.ts` (or equivalent focused component/state coverage)

**Current**

`timeCapacityRefinementEligible(spec)` correctly returns `false` when `cfg.stacked === true`, but the displayed-refinement lifecycle does not use that eligibility transition as an invalidation boundary.

`invalidateRefinement()` is called by an effect keyed to `currentResult?.data_signature` and `dataSignature`. The ordinary Time/Capacity `dataSignature` intentionally excludes `stacked`, because stacked rendering is client-only. The compatibility signature also excludes `stacked` for the same reason. Therefore toggling from the eligible flat voltage/current view to stacked mode changes neither identity watched by the invalidation effect.

At the same time, `activeRefinedResult` checks only the stored compatibility signature and overview data identity; it does not require the current spec to remain refinement-eligible. The previously accepted transient refinement therefore remains `plotResult`. `useZoomMemory(..., cfg.view !== "voltage_current" || !cfg.stacked)` disables zoom-memory application in stacked mode, so the stacked layout can autorange using the transient refinement subset rather than `currentResult`. If the 140 ms reveal is active during the toggle, its old flat trace list can also persist briefly across the `tc-flat` -> `tc-stacked` remount.

The current pure-policy tests establish that stacked mode is ineligible, but they do not prove that an already-displayed refinement and transition are cleared when eligibility becomes false.

**Target**

A transition from refinement-eligible to refinement-ineligible Time/Capacity state must invalidate transient refinement state immediately. In particular, switching `stacked` on after a refined zoom must cancel any pending request/reveal and clear the displayed refinement so the ineligible stacked render is based on the stable canonical `currentResult`. Switching back to an eligible view must not resurrect the stale pre-stacked refinement.

Do not weaken the existing request-generation guard, and do not change scientific/cache/export identity merely to implement this lifecycle boundary.

**Acceptance criteria**

1. Start from an accepted refined flat Time/Capacity view, then set `stacked=true`: pending refinement work and any reveal transition are cancelled/invalidated and the displayed result becomes the canonical overview, not the transient refinement subset.
2. The stacked render cannot autorange from the stale refined subset.
3. Switching back to `stacked=false` cannot resurrect the pre-stacked refinement; a new refinement is obtained only through the normal eligible zoom/request path.
4. A late response from the pre-toggle generation remains rejected.
5. Add focused regression coverage for the eligibility transition, not only the pure fact that stacked mode is ineligible.
