## Findings and resolution

### R1 — Medium: Refinement survives the `stacked` transition even though stacked mode is refinement-ineligible

**Resolution: RESOLVED.**

The current implementation now evaluates `timeCapacityRefinementEligible(spec)` during render and uses that value as a synchronous display boundary. `timeCapacityRefinementDisplayIsCurrent(...)` refuses to select a transient refinement when the current Time/Capacity state is ineligible, so stacked mode immediately falls back to the canonical `currentResult`. The transient reveal list is independently gated by the same eligibility value.

A layout effect invalidates refinement state when eligibility becomes false. This cancels pending debounce/HTTP work, cancels any active reveal, and clears the displayed refinement before paint. The separate `refinementEligibilityRef` is updated synchronously with render and is checked both before scheduling and before accepting a response, so a late response created under the pre-toggle flat state cannot be installed after the stacked transition.

The fix deliberately leaves `stacked` out of scientific/query/cache identity. This is the correct ownership boundary: stacked is a client rendering mode, while the invalidated state is ephemeral display/refinement state.

Focused coverage now proves that a previously accepted flat refinement is not display-current in stacked mode, while the source-contract coverage checks the component lifecycle gates for eligibility invalidation, transition suppression, and late-response rejection.

**Acceptance criteria:** satisfied.
