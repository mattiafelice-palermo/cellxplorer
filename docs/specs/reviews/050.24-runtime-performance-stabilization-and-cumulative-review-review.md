## Findings

### R1 — Medium: Refinement survives the `stacked` transition even though stacked mode is refinement-ineligible

**Resolution: RESOLVED, but its implementation must be preserved without causing R2.**

The stacked-mode problem remains a valid defect: switching from an accepted refined flat view into stacked mode must invalidate the transient refinement and reject late pre-toggle responses without changing scientific/query/cache identity.

The required stacked behavior remains locked, but the implementation strategy used in `abaabbc` is no longer accepted as a whole because it coincides with the loss of normal adaptive zoom reported by the user.

### R2 — High: R1 lifecycle correction regresses normal adaptive Time/Capacity zoom

**Affected files**

- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRefinementPolicy.ts`
- focused Time/Capacity frontend tests covering real refinement lifecycle

**Current**

The user reports that normal adaptive Time/Capacity zoom worked before the R1 correction and no longer works after it. This is a direct regression of the primary 050.24 behavior.

The known-good implementation boundary is `a42e910`. In that version, the ordinary eligible path used `timeCapacityRefinementCanSchedule(active, spec)` for relayout scheduling and accepted a response using the existing generation plus overview-identity guards. The R1 correction in `abaabbc` added:

- a render-time `refinementEligibilityRef`;
- a layout-effect invalidation tied to eligibility;
- `timeCapacityRefinementDisplayIsCurrent(...)` as an additional display gate;
- an eligibility gate on transition traces;
- an additional eligibility gate before scheduling refinement;
- an additional eligibility gate before accepting a refinement response.

The pure eligibility rule itself remains essentially unchanged. The regression therefore lies in the new lifecycle integration or in an interaction between those gates and the live component state.

The current tests are insufficient evidence for this path: they prove policy facts and source text contracts, but they do not prove that an actual eligible relayout schedules `/time-capacity/refine`, accepts the matching response, and installs the refined result as the displayed plot.

**Target**

Restore the normal non-stacked adaptive-zoom behavior that existed at `a42e910`, while retaining the valid stacked-mode protection from R1.

The correction must be narrow. Treat the `a42e910` ordinary flat refinement path as the behavioral baseline. The stacked transition should be isolated as a specific transient-state invalidation boundary rather than changing the ordinary scheduler/response pipeline more broadly than necessary.

A suitable implementation direction is:

- keep normal eligible flat relayout scheduling and response acceptance equivalent to `a42e910` unless a deviation is explicitly necessary and proven by tests;
- on `stacked: false → true`, synchronously suppress/clear displayed transient refinement and cancel pending/reveal work;
- rely on that invalidation's generation increment to reject late pre-toggle responses;
- gate stacked rendering from using a transient refinement, but avoid redundant eligibility refs/checks throughout the normal flat scheduling and response path unless they are shown to be necessary;
- when returning to flat mode, do not resurrect the pre-stacked refinement, but allow the next ordinary zoom to schedule and accept a fresh refinement normally;
- do not alter backend scientific results, query/cache identity, `CALC_VERSION`, result schemas, or export authority;
- do not broadly refactor the Time/Capacity card or `AnalysisPage.tsx`.

**Acceptance criteria**

1. In an ordinary eligible flat Time/Capacity view (`voltage_current`, Time axis, consecutive display, non-stacked, no explicit sparse cycle list), a Plotly zoom must schedule a refinement request and the matching response must become the displayed refined result.
2. Starting from an already refined view, zooming deeper must keep the existing compatible refined LoD visible while the replacement is pending, then replace it with the newer refinement without falling back to the coarse overview.
3. Rapid A → B zooms must continue to reject obsolete responses by generation; an older response cannot overwrite the newer viewport.
4. Switching `stacked=true` after an accepted refinement must immediately display the canonical overview, cancel pending/reveal work, and reject any late pre-toggle response.
5. Switching back to `stacked=false` must not resurrect the pre-stacked refinement, and a subsequent fresh zoom must again schedule and accept adaptive refinement normally.
6. Add focused **interaction/lifecycle regression coverage** that drives the relevant sequence from relayout through scheduling/request acceptance to displayed-result selection. Pure helper tests or regex/source-contract assertions alone are not sufficient for R2.
7. Explicitly compare the ordinary flat lifecycle against `a42e910`; any intentional behavioral difference must be documented and justified.
8. Run the focused frontend checks required by the change, TypeScript/Vite build, and canonical `python scripts\preflight.py` before handoff.
9. Because this regression escaped the existing automated suite and is directly user-visible, perform a real browser/manual adaptive-zoom check if the implementer environment supports it. If browser validation cannot be run, report **NOT RUN** and do not claim visual/interaction acceptance; final closure must wait for reviewer/user confirmation.
