## Reviewer inspection

### Passive updater configuration and channel resolution

`src-tauri/tauri.conf.json` now sets:

```json
"plugins": {
  "updater": {
    "windows": {
      "installMode": "passive"
    }
  }
}
```

The standalone NSIS bundle remains `installMode: "perMachine"`, so the fresh/manual installer scope was not conflated with updater UI mode.

Beta and Alpha overlays replace only their channel-specific updater endpoints and identifiers. Tauri CLI configuration extensions use JSON Merge Patch object semantics, so `plugins.updater.windows.installMode = passive` is inherited by both overlays while their endpoint arrays replace Stable's endpoint. The added `deep_merge` tests mirror those object/array semantics for the relevant configuration shape and assert all three resolved channels use `passive`, not `basicUi` or `quiet`, with their own endpoint.

The repository pins `tauri-plugin-updater = "2.10"`. Current Tauri v2 documentation defines Windows `passive` as unattended installation with a small progress-bar window, whereas `basicUi` requires interaction and `quiet` supplies no progress feedback. The configuration choice therefore matches the amended user decision.

### Visible `Applying update…` handoff

`runVerifiedInstall()` dispatches the `launching` state before the asynchronous `/api/session/finish` call and before `install_app_update` is invoked. The modal renders the exact `Applying update…` label, explanatory passive-window copy, and an animated/striped progress bar; launching is protected against modal dismissal and duplicate menu actions.

This satisfies the in-app handoff requirement by code inspection. The asynchronous session-finish boundary also gives React an opportunity to paint the launching state before installer takeover.

### Retry install without re-downloading

`retryInstall()` is available only for an install-phase error with a release. It calls `runVerifiedInstall(current.release)` directly rather than `runDownload()` / `downloadAppUpdateTauri()`.

On the Rust side, `install_app_update()` takes the verified update + bytes and, when `update.install(&bytes)` returns an error while the old process is still alive, restores the same `Update` and byte vector through `restore_failed_install()`. The subsequent frontend retry therefore re-enters installation against the restored verified bytes without another network download. Version/channel validation still runs on each install attempt.

### Signature/version/channel policy

No 054.2 Rust policy code was weakened. `check_app_update`, `download_app_update`, and `install_app_update` still resolve the exact application identifier to `AppChannel` and validate the advertised/requested version for that channel. Updater artifacts remain enabled and all three channels inherit the same committed public key while retaining their distinct endpoints/identifiers.

## Findings

### R1 — P1 — Passive progress page skips the initialization required by CellXplorer's custom NSIS styling

**Affected files**

- `src-tauri/cellxplorer-installer.nsi`
- `tests/test_updater_configuration.py` or another focused packaging-policy test

**Current**

054.2 changes the updater to Tauri `passive`, which launches the NSIS updater with `/P`. The custom template parses `/P` into `$PassiveMode`.

Every custom page that normally initializes the CellXplorer installer window deliberately skips itself in passive mode:

- `CellXplorerWelcomePage` aborts before calling `CxPrepareWindow`;
- `CellXplorerInstallPage` aborts before calling `CxPrepareWindow`;
- `PageReinstall` detects passive mode and calls `PageLeaveReinstall` without calling `CxPrepareWindow`.

However the install-files page still unconditionally executes `CxBeforeInstFiles` + `CxStyleInstFiles`. `CxStyleInstFilesBody` assumes the setup performed by `CxPrepareWindow`: it uses `$CxHeadingFont`, `$CxBrandFont`, and `$CxBodyFont`, and lays out a 680×430 inner progress surface intended for the 760×500 outer window created by `CxPrepareWindow`. `CxBeforeInstFiles` also unconditionally re-shows native wizard controls. There is no passive-specific call that initializes those fonts/outer-window dimensions before the progress-page show handler executes.

This was harmless while the in-app updater used `basicUi`, because the interactive page path initialized the custom window first. Switching to `/P` newly exercises a path where the styled progress page can run against the stock outer wizard geometry and uninitialized custom font handles. The exact visual packaged row that would reveal clipping, malformed layout, or ordinary wizard chrome is the row the handoff explicitly did not run.

The issue is not that `passive` itself is unsupported; Tauri documents it as the correct mode. The issue is that CellXplorer replaces Tauri's stock NSIS template and its custom progress-page styling currently depends on initialization that passive mode skips.

**Target**

Make the install-files/passive path self-sufficient. Before custom progress-page geometry/fonts are used, initialize the required CellXplorer window state on both interactive and passive updater paths, or deliberately use an unmodified stock-style passive progress page that does not depend on `CxPrepareWindow`.

Do not restore interactive welcome/location/reinstall pages for `/P`, and do not replace `passive` with `quiet` or `basicUi`.

**Acceptance criteria**

1. A `/P /UPDATE` run reaches the install-files page with all geometry/font prerequisites initialized, without relying on a custom page that passive mode skips.
2. The passive update does not expose the ordinary welcome/location/reinstall/finish workflow or require a user decision.
3. The progress surface is compatible with the actual outer window dimensions and does not depend on uninitialized `$Cx*Font` handles.
4. Add focused regression coverage that encodes the passive-page initialization contract rather than only asserting `installMode: passive` in JSON.
5. The normal standalone interactive installer still follows its branded pages and `perMachine` scope.
6. Focused updater/config tests and canonical `python scripts\preflight.py --no-cache` pass after the repair.
7. The corrected path is then exercised by the packaged visual matrix in R2.

### R2 — P1 — Required signed packaged passive-update acceptance matrix is NOT RUN

**Affected area**

- Windows signed updater acceptance for Stable/Beta/Alpha
- `docs/specs/054-agent-coordination.md` / this review record

**Current**

The handoff explicitly reports:

> signed updater artifact and packaged passive-window/manual update matrix: NOT RUN (`TAURI_SIGNING_PRIVATE_KEY` unavailable; no safe desktop visual control surface; no claim of installer-window observation)

The amended 054.2 specification makes this a required acceptance gate and explicitly says not to infer installer-phase progress from configuration alone. Static confirmation that Tauri maps `passive` to a progress window is necessary but not sufficient because CellXplorer uses a custom NSIS template and because the user specifically locked continuous visible feedback through installer takeover.

Unsigned disposable installer builds prove that the bundle compiles, but they do not exercise the real in-app signed updater verification/takeover path.

**Target**

After R1 is repaired, perform the signed packaged in-app update matrix for every available channel configuration and record exactly what was observed. No application-code change is required for R2 unless the matrix exposes another defect.

**Acceptance criteria**

For Stable, Beta, and Alpha, using a real signed updater artifact and disposable/test data:

1. Start from an older installed build and initiate the update from CellXplorer.
2. Observe CellXplorer download progress (determinate when length is known; otherwise visibly indeterminate).
3. Observe the `Applying update…` handoff before the old app exits.
4. Confirm the ordinary interactive NSIS wizard does **not** appear.
5. After the main CellXplorer window/process closes, observe the compact passive updater/progress window while installation is actually running.
6. Confirm there is no material blank/no-feedback interval between the app handoff and installer progress.
7. Confirm installer-phase progress requires no user interaction and terminates with an understandable completion/failure outcome.
8. Confirm automatic relaunch when supported by the packaged path, or record the exact clear completion/manual-launch fallback if not.
9. Confirm the requested new version is installed/running.
10. Confirm representative analyses, saved plots, and settings remain present.
11. With another channel concurrently running, confirm its frontend remains responsive and its backend remains alive/responsive (cross-check the accepted 054.1 ownership model).
12. Exercise a controlled download/install failure if practical; if a row is genuinely impractical, record it explicitly as NOT RUN with the exact reason rather than claiming PASS.
13. Record exact build/version/channel and actual observations. The private signing key itself must never be committed or copied into review records.

The current `TAURI_SIGNING_PRIVATE_KEY` / desktop-control limitation is an exact and acceptable explanation for why the gate has not yet run, but it does **not** satisfy the child acceptance criterion.
