## Findings

### R1 — High: reconcile the complete production request into named and residual timings before choosing the next architecture

Affected files:

- `scripts/profile_time_capacity_ordinary_latency.py`
- `scripts/profile_time_capacity_concurrency.py`
- `backend/app/routers/analyses.py`
- `backend/app/services/analysis_engine.py`
- `backend/app/services/analysis_cache.py`
- `backend/app/services/time_capacity_path.py`
- `backend/app/services/cache.py`
- `backend/app/services/time_capacity_profiling.py`
- `docs/specs/050.12-ordinary-time-capacity-latency.md`

**Current**

The 050.12 headline `backend_median_ms` is not the complete production HTTP backend boundary. `profile_time_capacity_ordinary_latency.py` delegates to `run_production_sample()`, whose wall timer surrounds `analysis_engine.compute_time_capacity()` directly and records serialization separately. The real `/analyses/{analysis_id}/time-capacity` miss path performs additional synchronous work before and after that engine call: analysis lookup, canonical capability guard, `time_capacity_data_signature()`, a second render-specific `result_key()`, persisted-result lookup, optional activity setup, synchronous result-cache persistence, and final response serialization. Those costs are therefore absent from the 323/554/591 ms figures even though they affect the user's interaction.

Inside the engine, the published result summary also does not reconcile the engine wall time. For example, the real 11-Cell Time row reports approximately 591 ms engine wall but only about 125 ms raw access, 88 ms transform and 20 ms provenance in the headline table. The detailed stage timers are nested/inclusive (`indexed_raw_access` contains row-group I/O and mapping; `continuous_time_phase_capacity` contains transform sub-stages), so summing every named timer would double-count rather than identify the true residual. Several materially plausible regions are not currently isolated at all.

Code inspection identifies the following specific hypotheses that must be timed before any new worker/process/cache architecture is chosen:

1. **Repeated request/selection/capability work.** The router calls `_guard_canonical_cycling()`, then the engine calls `ensure_canonical_cycling_available()` again; both resolve selection/source state. `compute_time_capacity()` then resolves selection again. If a compute job is opened, `_open_compute_job()` resolves selection again.
2. **Duplicate cache-identity construction.** `time_capacity_data_signature()` calls `result_key(..., request_options=None)`, followed immediately by another `result_key(..., request_options=options)`. Each call independently resolves selection, preloads sources, bulk-loads scalar metadata, rebuilds per-unit/source fingerprints, serializes the key payload and hashes it.
3. **Per-Cell scalar metadata access inside the engine.** The module already provides `load_scalar_metadata()` specifically to avoid three small metadata queries per Cell, but the Time/Capacity engine calls `cell_active_mass_mg()`, `cell_nominal_capacity_mah()` and `cell_electrode_area_cm2()` per Cell without passing a bulk snapshot. Measure SQL statement count/time before changing this.
4. **Voltage capability/header access.** The indexed path times `voltage_capability_context`, but `_resolve_time_capacity_voltage_context()` can access `SourceFile.header_meta`, which source preloading deliberately defers. Determine whether ordinary requests trigger lazy ORM/header JSON loads per source and what they cost.
5. **Repeated raw-index/Parquet-footer validation.** Stitch planning validates the raw layout/index, and `load_raw_cycles()` validates the active layout again before opening the Parquet file for the row-group read. This may be necessary for the publication/race safety boundary, so do not remove it blindly; measure JSON/index validation, footer/schema validation, row-group decode and Arrow→pandas conversion separately and assess whether a request-local validated descriptor can safely reduce duplicated work.
6. **Repeated sorting/mapping.** `load_indexed_time_capacity_raw()` stable-sorts loaded records by `record_index` before mapping/concatenation, while the engine later stable-sorts the combined frame again by cycle/segment/record index. Measure both sorts separately and establish whether either is provably redundant before changing ordering logic.
7. **Untimed post-downsample materialization.** The current `display_downsampling` timer covers index selection, but the subsequent boundary merge/`np.unique`, `raw.iloc[take]`, array slicing, phase conversion and boundary recomputation occur outside that timer. Isolate this as its own exclusive stage.
8. **Untimed compact trace/Python-list projection.** The final `traces.append(...)` performs multiple `_jsonsafe*` NumPy→Python list conversions, rounding/non-finite handling, integer/text conversion and dictionary construction. With up to thousands of returned points per Cell this can be material and currently sits in the residual. Time numeric preparation separately from Python list/object construction.
9. **Synchronous result-cache persistence plus response serialization.** On a miss, `store_result()` JSON-encodes the full scientific result, gzip-compresses and atomically writes it, writes the sidecar and may prune; the same result is then serialized again for the HTTP response. Measure cache JSON encode, gzip, file write/replace, sidecar/prune and HTTP response encode separately. Do not move persistence off-path or change cache semantics until its measured contribution is known.
10. **Global finalization outside per-Cell jobs.** Explicitly time selection-independent/global result assembly after the Cell loop (badges, parser/version/channel/settings/rendering payloads and any other owner-side finalization) so per-Cell parallelizable work can be distinguished from serial request work.

The current statement that indexed raw read/decode is the dominant residual is therefore not sufficiently demonstrated. It may be the largest currently *named* individual stage, but that is not the same as being the largest exclusive share of the complete interaction.

**Target**

Before implementing persistent Python processes, additional threading, a new RAM/reuse cache, alternate serialization, or another production performance mechanism, extend the opt-in 050.12 profiling so the ordinary production request is represented by a **non-overlapping timing tree that reconciles to the measured wall boundary**. Nested diagnostic timings may remain, but every timer must be labelled/structured so inclusive child timings are not added to their parent, and an explicit residual must make omitted work visible.

Produce two reconciled levels:

1. **Complete backend request boundary** for the real production endpoint: request/analysis setup + capability guard; source/data-signature construction; render-specific result-key construction; result-cache lookup; compute; result-cache persistence; response preparation/serialization; other owner-side work; explicit residual; total backend wall.
2. **Engine compute boundary**: owner/global setup; each Cell job; global finalization; explicit residual. For Cell work, expose a representative aggregate/exclusive partition covering source/identity resolution, stitch/index planning, index/footer validation, row-group read/decode/Arrow→pandas, mapping/concat, exact filter/sort, voltage capability/header work, scalar metadata, scientific transforms, protocol work where active, plot-array materialization, display-coordinate work, downsample index selection, post-downsample slicing/materialization, provenance, compact trace/Python-object projection, and any remaining residual.

Also record SQL statement count and cumulative SQL time for the request, with enough attribution to show whether repeated selection/scalar/header lazy loads are occurring. Record source/header lazy-load count where practical. The profiler must remain opt-in/local and must not put raw data, paths or private values in durable diagnostics.

This round is **measurement and accounting only**. Do not implement the process-pool idea or the optimization hypotheses above yet. Return the detailed evidence so reviewer/user can choose the next intervention from measured exclusive costs.

**Acceptance criteria**

- Run at least five comparable warm repetitions on mains power for the saved real Performance analysis for: 1-Cell small/range control, 6-Cell Time All, 10-Cell Time All, 11-Cell Time All, and 6-Cell capacity All; retain fixture coverage and the exact-result-cache hit control.
- For each representative real workload report p50 and min/max (or another small documented tail/range) for the **complete router/backend request wall**, not only `compute_time_capacity()`.
- The complete request timing partition reconciles to its wall median within measurement noise; target <=2% or <=1 ms unexplained, whichever is larger. If profiler overhead prevents this, quantify the overhead and report the remaining residual explicitly rather than hiding it.
- The engine timing partition separately reconciles to engine wall with the same explicit residual discipline.
- Parent/child timers are explicitly marked inclusive vs exclusive so no table invites double-counting.
- Report the full named-stage table, not only raw/transform/provenance headline columns. Include currently unnamed post-downsample slicing/materialization and compact trace/Python-object projection.
- Separately report result-cache store JSON encode, gzip/compression, atomic disk write/replace, sidecar/prune, and final HTTP response serialization on a miss.
- Separately report both cache-identity calls and the canonical/selection guard costs; include SQL statement count/time and identify any N+1/per-Cell metadata or lazy-header queries observed.
- Separately report raw-index JSON/validation/footer cost, actual row-group decode/Arrow→pandas cost, mapping/concat, and both sort boundaries, without weakening the current non-waiting layout/publication safety contract.
- Preserve exact scientific digest and deterministic trace order across every profiled sample; exact persisted result-cache hits must remain direct and must not dispatch engine/raw/worker work.
- Update the 050.12 implementation record with the reconciled tables and a ranked list of the largest **exclusive** residual costs plus realistic optimization candidates/upper-bound savings. Do not label raw read/decode the dominant residual unless the reconciled evidence demonstrates it.
- Focused profiler/accounting regression tests and canonical `python scripts\preflight.py` pass. Browser/user-visible timing may remain NOT RUN for this R1 cycle because the requested evidence is backend decomposition.
