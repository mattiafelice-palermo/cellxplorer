## Finding

The background-progress follow-up implemented the Stage A/B/C split correctly — validation outside
the write transaction ([`files.py` `_create_imported_cells_impl_raw`](../../../backend/app/routers/files.py)),
one relational commit, a `registration_committed` marker, sources committed as `parsing` / `pending`,
and a global watcher in [`App.tsx`](../../../frontend/src/App.tsx) that invalidates Cell queries on
commit and throttles refreshes during cache progress.

The mechanism is right. It cannot fire, because **Stage B is not short**.

`full_cell_metadata_from_header()` expands the entire parsed Neware header into one `CellMetadata`
row per XML leaf (`raw.<field>`), and those inserts happen inside the Stage B transaction. A
representative NDAX header carries ~977 raw fields, so a 1,000-file separate-cell import builds
roughly 993,000 `CellMetadata` ORM objects before a single `flush()`.

The same full header is *already* persisted correctly as one JSON document per source in
`SourceFile.header_meta`. The relational expansion is a duplicate copy that no bounded read path
needs: `list_cells()` already restricts its metadata query to `SCIENTIFIC_SUMMARY_METADATA_KEYS`.

### Measured cost

Simulating the exact shape of `_create_imported_cells_impl_raw` for 1,000 cells — build the whole
graph in memory, one `flush()`, one `commit()` — varying only metadata rows per cell:

| Scenario | Rows/cell | Total rows | Build | Flush | Commit | Total | Peak RAM | DB |
|---|---|---|---|---|---|---|---|---|
| Current (curated + `raw.*`) | 993 | 993,000 | 84.5s | 269.6s | 41.0s | **395s** | 3.5 GB | 128 MB |
| Curated only | 16 | 16,000 | 3.1s | 10.8s | 1.2s | **15.1s** | 102 MB | 31 MB |
| Overrides only | 0 | 0 | 1.1s | 6.6s | 0.3s | **8.1s** | 67 MB | 29 MB |

Six and a half minutes of blocking relational work before any cache job starts. That is the observed
"Cell Database stays empty until everything finishes". The 3.5 GB peak is the second-order failure:
a million live ORM instances held until flush will push a normal machine into swapping, which makes
the whole application feel frozen rather than merely slow.

**Locked decision:** keep the ~16 curated `_metadata_preview` fields in `CellMetadata`; remove only
the `raw.*` expansion. The further 7 s from dropping the curated fields is noise against an import
that also hashes, reads headers, and builds Parquet caches, and is not worth changing
`legacy_value` resolution in `_scientific_metadata_values()` for newly imported cells.

## Ownership model

```text
Cell
├── user metadata, scientific overrides, presets   → CellMetadata
└── ordered SourceFiles
    ├── curated searchable columns                 → SourceFile columns
    └── complete parsed header                     → SourceFile.header_meta (one JSON document)
```

Copying the *first* source's header onto the Cell also misrepresents a continued Cell, whose sources
legitimately differ in start time, channel, protocol, and software version. Per-source header display
is both cheaper and more scientifically honest.

## Confirmed by reading the code — do not re-litigate

- `SourceFile.header_meta` has been written on every import path since the baseline
  (`header_meta=meta.get("raw") or None`), so existing databases already hold the full header per
  source. The new read path works retroactively; no backfill and no migration are required.
- `raw.*` keys are absent from `SCIENTIFIC_SUMMARY_METADATA_KEYS`, so they never entered an analysis
  cache key. **No `CALC_VERSION` bump.**
- A server-side header cache already exists — `import_inspection.remember_header_metadata` /
  `cached_header_metadata`, an LRU bounded at `_HEADER_CACHE_LIMIT = 1024`.
- `file_dict()` does not include `header_meta`, so Cell detail payloads stay lean today and must
  continue to.

## Follow-up order

### R1 — Stop expanding the raw header into `CellMetadata` (priority: blocking)

File: `backend/app/routers/files.py`

Current: `full_cell_metadata_from_header()` merges `_metadata_preview(meta)`, then every
`meta["raw"]` entry as `raw.<key>`, then draft metadata.

Target: drop the `raw.*` loop entirely. Keep the curated preview fields and draft/user metadata.
Rename to `cell_metadata_from_header()` since it is no longer "full". Update the caller at the
import registration site and `tests/test_import_flow.py`.

Acceptance: a registered Cell has curated + override + user metadata rows only; no key begins with
`raw.`. The complete header remains readable from that Cell's `SourceFile.header_meta`.

### R2 — Serve the complete header per source, lazily (priority: blocking)

File: `backend/app/routers/library.py`

Current: no endpoint exposes `header_meta`; it is only consumed internally by
`protocol.reconstruct_protocol`.

Target: add a read-only endpoint returning one source's stored header document. It must not be
folded into `GET /cells/{id}` — at ~57 KB per source that would regress every Cell detail open.

Acceptance: returns the stored header for a registered source, `404` for an unknown source, and an
empty document rather than an error when a source predates header capture.

### R3 — Per-source metadata display (priority: blocking)

File: `frontend/src/components/CellDetailTabs.tsx`

Current: `MetadataPanel` renders `Object.entries(cell.metadata)` minus `override.*`, which is where
the ~977 `raw.*` rows surfaced, plus curated per-source rows.

Target: keep the scientific and curated rows. Suppress legacy `raw.*` entries so existing cells do
not double-display what the per-source section now owns. Add one collapsible section per source that
fetches its full header on expand.

Acceptance: an existing cell imported before R1 shows no `raw.*` rows in the flat list and shows the
same values under its source section; a cell imported after R1 shows identical information. Nothing
fetches a header until a section is expanded. Follows the visual style guide, collapsed by default.

### R4 — Tests (priority: blocking)

Backend: registration writes no `raw.*` metadata rows; the curated and override rows survive; the
registered source retains its complete `header_meta`; the header endpoint returns it and 404s
correctly.

Frontend: `raw.*` suppression and per-source section policy, as pure functions where the existing
test style allows.

### R5 — Stop round-tripping the full header through the browser (priority: deferred)

Inspection returns `inspection.header_metadata` — the complete ~57 KB header per file — which the
frontend stores and posts back at registration. For 1,000 files that is tens of megabytes in each
direction.

Registration already prefers `import_inspection.cached_header_metadata()` over the payload, so most
of the mechanism exists. The open question is the `_HEADER_CACHE_LIMIT = 1024` ceiling: dropping the
payload puts header re-reads back on the registration path for any batch that overflows the LRU.

Deliberately **not** implemented in this batch. Land R1–R4, measure the resulting import, and decide
with numbers.

## Implementation record

Branch: `feature/spec-035-user-experience-optimization`. Version `0.17.0-beta028`.

### R1 — done

`full_cell_metadata_from_header()` renamed to `cell_metadata_from_header()` in
`backend/app/routers/files.py` with the `raw.*` expansion loop removed; it now returns the curated
`_metadata_preview()` summary plus draft/user entries. The registration caller and
`tests/test_import_flow.py` follow the new name.

`tests/test_import_flow.py::test_imported_cell_metadata_keeps_full_flattened_header` asserted the
behavior being reversed, so it was inverted rather than deleted, as
`test_imported_cell_metadata_excludes_the_raw_header`.

### R2 — done

Added `GET /api/cells/{cell_id}/sources/{source_file_id}/header` in `backend/app/routers/library.py`.
It resolves the source through `_ordered_cell_file_links` so a source belonging to another Cell
cannot be read through this route, and returns `{}` rather than an error for a source with no stored
header. `file_dict()` is unchanged, so Cell detail payloads stay lean.

### R3 — done

`frontend/src/cellMetadataDisplay.ts` (new) holds `visibleCellMetadataEntries()`, which hides
`override.*` and `raw.*`. `MetadataPanel` in `frontend/src/components/CellDetailTabs.tsx` uses it and
gained `SourceHeaderSections` / `SourceHeaderTable`: one collapsed `Accordion` item per source whose
query is mounted only while that item is open, so nothing is fetched until expanded. `CellSourceHeader`
added to `frontend/src/api.ts`.

Loading is one `Loader` with dimmed text, errors are a red `Alert`, and a source with no stored
header gets a gray `Alert` explaining what is missing — no "No data" while pending.

### R4 — done

Backend (`tests/test_import_flow.py`): registration writes no `raw.*` rows while keeping curated,
user, and override rows and leaving the complete header on `SourceFile.header_meta`; the header
endpoint serves the stored document, 404s for an unknown source and an unknown cell, and returns an
empty document for a source without a header.

Frontend (`frontend/tests/cellMetadataDisplay.test.ts`, new): curated/user entries survive, legacy
`raw.*` and `override.*` are hidden, all-hidden and empty inputs yield an empty list, and keys that
merely *contain* those prefixes are kept.

### R6 — Batch cell deletion and background the cache cleanup — done

Reported after the metadata fix landed: deleting 1,000 cells took several seconds with no feedback.

`delete_cells_from_library` looped `delete_cell_from_library`, which called
`delete_empty_replicate_groups` **inside** the loop; that function ran one `COUNT` per replicate
group. Measured at 1,000 cells and 20 groups: **55,064 statements, 8.7 s**, of which ~21,000 reads
were the repeated group scan.

Now: dependent tables are cleared with one chunked statement per batch, empty groups are collected
once through a single aggregate query, and `delete_cell_from_library` delegates to the batch path so
the two endpoints cannot diverge. Entity removal stays ORM-level because callers hold those objects.

**3,089 statements, 0.45 s — 19x.** The residual ~3 reads per cell are SQLAlchemy cascade loads;
`passive_deletes` would remove them but is not worth the risk on a deletion path.

Cache removal moved to a `cache_cleanup` background job above
`CACHE_CLEANUP_BACKGROUND_THRESHOLD` sources, with a four-thread pool (measured 2.2x over serial on
NTFS; 8 threads added little). Small deletions stay inline so the response still reports bytes
reclaimed. Deliberately **not** a blocking progress modal: the relational delete is now sub-second,
so the cells vanish immediately and only the disk reclamation continues in the background, matching
the import handoff pattern.

Tests: statement-count regression guard on batched deletion, inline-vs-background threshold, job
totals with a failing source, and the existing deletion suite unchanged.

### R7 — Cache generation review — no change made

Reviewed at the user's request. Measured per file (9 MB source, 427,772 rows): `parse_timeseries`
0.403 s (50.6%), `calc.per_cycle` 0.204 s (25.7%), Parquet writes 0.189 s (23.8%).

No worthwhile win remains in the per-file path: Spec 028 already made `per_cycle` 2.61x faster and
Spec 029 brought zlib-ng, and 028 recorded why further parse work is not justified. Codec choice is
a dead end for speed (lz4 saves ~1.6% overall), though zstd writes at snappy's speed for 22% less
space — a cache-budget question, not a performance one.

The real lever is `import_cache_worker_count`, capped at 4 while a 16-CPU machine could use more:
1,000 files is ~13.3 min of CPU, so 4 workers is ~3.3 min against ~1.7 min at 8. Left unchanged —
the parent spec locks worker counts as small and deterministic, and it trades background throughput
for foreground responsiveness. Raise it only on an explicit decision.

### R5 — done

`_inspect_import_path` no longer returns `inspection.header_metadata`. Measured on the real
1,000-file corpus, that field was **56.4 KB per file — ~58 MB to the browser and ~58 MB back** for a
batch that only needed a 100-byte identity proof. Inspection already stores every header it reads
under the same `(hash, size, mtime_ns)` fingerprint, so registration reads it from there.

Registration keeps its payload-reading branch: a modal opened before the upgrade can still post the
old shape, and honouring it is free.

Measured at 200 files: **10.9 MB payload -> 0.0 MB**, zero header reads, no change in Stage A time.

**Known limit, accepted.** `_HEADER_CACHE_LIMIT` is 1024 entries (~57 MB at 56 KB each). At or below
that, registration is a pure cache hit. Above it the earliest entries are evicted and those files
have their header reopened — ~6 ms each, so a 2,000-file import adds roughly 6 s. Raising the limit
trades that against resident memory in a desktop process; it was left alone rather than guessed at.

### R8 — Import path audit, first modal to third-modal close

Measured against the real 1,000-file corpus (1.59 GB). **Two hypotheses were tested and rejected**;
both are recorded so nobody re-derives them.

| Stage | Cost (1,000 files) | Notes |
|---|---|---|
| First modal — `scandir` discovery | 0.01 s | Nothing to gain |
| Inspection — hashing | 3.58 s serial → 0.89 s | Already pooled, 4 workers |
| Inspection — header reads | 6.42 s serial → 1.60 s | Already pooled; the larger half |
| Stage A validation | ~1.4 s | No rehash, no header read |

**Rejected: "Stage A re-hashes every file serially."** It does not. `_prepare_import_source_file`
takes the fingerprint branch when size and `mtime_ns` still match the inspected values and reuses
the inspected hash. Instrumenting a real 200-file registration counted **0 hash computations and 0
header reads**. `_source_identity_snapshot_or_error`, which always hashes, is reached only from
`_validate_staged_source_snapshots` on the continuation-attach path, where chains are short. Do not
"parallelize" this; there is nothing there to parallelize.

**Rejected: parallelizing the evicted-header re-read.** A thread pool made it *slower* — 0.94x at
four threads, 0.92x at eight — because header parsing is GIL-bound, not I/O-bound. A four-process
pool was 0.57x, dominated by Windows pool startup at this batch size. This is the same reason
`inspect_files` only crosses to a process pool above `INSPECTION_PROCESS_THRESHOLD`. The fallback
stays serial; a prefetch helper was written, measured, and removed.

Nothing further is worth doing in this path. The remaining levers are the deliberately capped
`import_cache_worker_count` (see R7) and the parser itself.

### Measured result

Real registration path, 200 cells with a 977-field header, cache jobs stubbed so only the blocking
Stage A+B work is timed:

| | Cells | `cell_metadata` rows | Elapsed |
|---|---|---|---|
| Before | 200 | 195,800 | 20.16 s |
| After | 200 | 400 | **0.31 s** |

**65× on the path that gates Cell visibility.** Extrapolating linearly to 1,000 files gives ~101 s →
~1.6 s, and linear is optimistic for the old code: the isolated 1,000-cell measurement took 395 s
because cost grows superlinearly once a million live ORM objects create memory pressure.
