## Findings

### R1 — High: later-cycle refinement is re-zeroed into a different Time coordinate system

Affected files:
- `backend/app/routers/analyses.py`
- `backend/app/services/analysis_engine.py`
- `backend/app/services/cache.py`
- `backend/app/services/time_capacity_path.py`
- `backend/app/services/time_capacity_workers.py`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRefinementPolicy.ts`
- `tests/test_analysis_engine.py`
- `tests/test_time_capacity_path.py`

**Current (round 1)**

A later candidate cycle window reconstructed cumulative Time only from the local slice, re-zeroing it relative to the overview. The endpoint also cleared an explicit sparse `cycles=[...]` selection into a contiguous range.

**Target**

Use the same canonical consecutive-Time coordinate as the overview with bounded indexed reads, and never silently broaden explicit sparse-cycle semantics.

**Acceptance criteria**

- Later-cycle refinement excluding the overview origin remains non-empty and exactly aligned to overview `display_x`.
- No full raw read is required to recover the Time offset.
- Serial/process refinement parity and deterministic order hold.
- Explicit sparse selections are preserved exactly or are ineligible.

**Resolution — resolved**

Raw-layout version 2 stores validated source-local cumulative reset facts and per-cycle starts. `consecutive_time_request_facts()` derives the candidate prefix and canonical overview origin from those bounded index facts. The worker applies the prefix after local `_continuous_time()` and uses the canonical origin for display coordinates before viewport filtering. `compute_time_capacity()` fails refinement closed if the indexed facts/path are unavailable rather than falling back to a full raw read. The regression now uses an overview spanning cycles 1–50 and a candidate 28–30, and proves cycle 29 `display_x` is exactly equal between overview and refinement. A focused process-vs-forced-serial test compares the complete traces/settings/rendering. Both frontend policy and the backend endpoint reject explicit sparse-cycle refinement.

### R2 — Medium: stacked ordinary Time refinement can reset the viewport on replacement

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRefinementPolicy.ts`
- `frontend/tests/timeCapacityRefinementPolicy.test.ts`

**Current (round 1)**

Stacked Time/Consecutive was eligible even though stacked Plotly deliberately lacks the zoom-memory/uirevision mechanism needed to guarantee replacement without viewport reset.

**Target**

Either provide a tested safe stacked viewport-preservation mechanism or gate stacked mode out of 050.15 refinement.

**Acceptance criteria**

- Stacked mode safely preserves viewport or is ineligible.
- Existing stacked plotting behavior is otherwise unchanged.

**Resolution — resolved**

`timeCapacityRefinementEligible()` now requires `stacked !== true`; focused frontend policy coverage verifies stacked Time is ineligible. No existing stacked zoom/rendering mechanism was changed.

### R3 — Medium: keep-mounted Time/Capacity does not cancel refinement on tab change

Affected files:
- `frontend/src/features/analyses/editor/AnalysisEditor.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRefinementPolicy.ts`
- `frontend/tests/timeCapacityRefinementPolicy.test.ts`

**Current (round 1)**

Because Time/Capacity remains mounted after first visit, switching tabs did not itself cancel a pending debounce or in-flight refinement request.

**Target**

Inactive Time/Capacity must cancel/invalidate only the transient refinement while preserving the canonical overview/React Query state.

**Acceptance criteria**

- Inactive state cannot schedule refinement.
- Cancellation advances generation so a late response cannot replace current data.
- Returning to Time/Capacity can reuse the canonical overview.

**Resolution — resolved**

`AnalysisEditor.tsx` now passes `active={activeTab === "time_capacity"}` to the retained card. On inactive transition the card calls the existing `cancelRefinement()`, which clears the debounce, aborts the controller, increments generation, clears only transient refined data and blocks scheduling through `timeCapacityRefinementCanSchedule()`. The canonical query/result is retained. Focused policy coverage verifies inactive scheduling is false and an old generation is rejected.

Affected files:

**Target**

**Acceptance criteria**

**Resolution — resolved**

The implementation record now includes the accepted compact transport, density and worker decisions plus one focused production-endpoint refinement benchmark. The benchmark uses six golden-fixture Cells, one warm request per viewport and three reported warm repetitions:

The 10% case is raw-density capped but still exceeds the >=3× criterion by a wide margin. The focused benchmark completed in 16.49 s. Browser/manual checks are explicitly NOT RUN. No S100/S50 or unrelated broad matrix was rerun for the correction.
