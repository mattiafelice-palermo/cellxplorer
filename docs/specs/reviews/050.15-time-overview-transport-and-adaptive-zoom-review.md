## Findings

### R1 — High: later-cycle refinement is re-zeroed into a different Time coordinate system

Affected files:
- `backend/app/routers/analyses.py`
- `backend/app/services/analysis_engine.py`
- `backend/app/services/time_capacity_workers.py`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRefinementPolicy.ts`
- `tests/test_analysis_engine.py`
- `frontend/tests/timeCapacityRefinementPolicy.test.ts`

**Current**

The client deliberately narrows a refinement to the cycles visible in the overview plus one adjacent cycle. The backend then loads only that local cycle range. `_continuous_time()` reconstructs cumulative Time from that local frame, so a candidate range that starts at (for example) cycle 29 has no elapsed-time contribution from cycles 1–28. `_time_capacity_display_x(... origin_cycle_start=1)` cannot recover time that was never loaded; it therefore makes the local candidate start near zero. The worker then filters those local coordinates against the canonical overview's later absolute viewport range, which can return empty/wrong data.

The current regression test starts the overview at cycle 2 and refines a candidate that still contains cycle 2, so it does not exercise the real later-viewport case.

There is a second semantic problem for explicit-cycle selections: the endpoint clears `settings["cycles"]` and replaces the original sparse selection with one contiguous `cycle_start..cycle_end` range. A plot of `[1, 10, 20]` can therefore refine around cycle 10 using unrequested neighboring cycles as plotted data.

**Target**

Refinement must use the **same canonical consecutive-Time coordinates as the overview while retaining bounded indexed reads**. A later viewport must not be re-zeroed just because earlier cycles were omitted from the refinement read.

For explicit `cycles=[...]`, preserve the exact selected-cycle semantics. If implementing bounded exact sparse refinement is not safe in this child, make explicit-cycle ordinary Time ineligible for adaptive refinement instead of broadening it silently.

**Acceptance criteria**

- Add a regression with an overview spanning many cycles (e.g. 1–50) and a viewport around a later cycle whose candidate read excludes cycle 1. The refinement is non-empty and its `display_x` values are in the same coordinate system as the overview and inside the requested viewport.
- The correction does not require a full raw read merely to recover the Time offset; reuse index/source timestamp facts or another bounded authoritative offset mechanism.
- Forced-serial and process refinement return identical Cell order/scientific/provenance output.
- An explicit sparse cycle selection is never silently broadened. Either prove exact sparse refinement or make that request ineligible and cover the policy with a focused test.

### R2 — Medium: stacked ordinary Time refinement can reset the viewport on replacement

Affected files:
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/timeCapacityRefinementPolicy.ts`
- `frontend/tests/timeCapacityRefinementPolicy.test.ts`

**Current**

`timeCapacityRefinementEligible()` allows ordinary Time/Consecutive regardless of `stacked`. But the card deliberately disables `useZoomMemory()` for stacked voltage/current and omits Plotly `uirevision` there because `matches` + `uirevision` is an existing Plotly relayout trap. When a refined result replaces the overview, there is therefore no mechanism guaranteeing that the stacked x/y viewport is retained. This contradicts C1's locked requirement that refinement replacement preserve the current viewport exactly with no autorange/reset/flicker.

**Target**

Do not run adaptive refinement in a mode where replacing the data can reset the user's viewport. Either implement a tested safe stacked viewport-preservation mechanism that respects the existing Plotly constraint, or gate 050.15 refinement to non-stacked ordinary Time. Prefer the smaller safe change if stacked preservation is not already supported by repository patterns.

**Acceptance criteria**

- Focused policy/lifecycle coverage proves stacked mode either preserves its viewport during replacement or is ineligible for refinement.
- Existing stacked plotting/zoom behavior is otherwise unchanged.

### R3 — Medium: keep-mounted Time/Capacity does not cancel refinement on tab change

Affected files:
- `frontend/src/features/analyses/editor/AnalysisEditor.tsx`
- `frontend/src/features/analyses/editor/families/time-capacity/TimeCapacityPlotCard.tsx`
- focused frontend tests for the relevant lifecycle/policy

**Current**

The Time/Capacity `Tabs.Panel` uses `keepMounted`. `TimeCapacityPlotCard` receives no active-tab signal, and its cancellation effects run on data-identity change or component unmount. Switching to Cycles/Steps/etc. therefore leaves a pending 150 ms timer or in-flight `/time-capacity/refine` request alive while the Time/Capacity panel is hidden. C1 explicitly requires a tab change to abort/supersede refinement.

**Target**

Propagate the smallest existing active/inactive signal (or equivalent) to the Time/Capacity card. When the Time/Capacity tab becomes inactive, cancel the timer/request, advance the generation, clear transient refined data, and prevent new refinement while hidden. Do not broadly discard the retained canonical overview/React Query state that makes returning to Time/Capacity fast.

**Acceptance criteria**

- A focused test proves switching away before the debounce fires prevents the request.
- A focused test proves switching away with a request in flight aborts/invalidates it and a late response cannot replace data.
- Returning to Time/Capacity retains/reuses the canonical overview behavior; only the ephemeral refinement is discarded.
