## Previous review checkpoint

The previous follow-up corrected the main third-modal responsiveness regressions:

- capacity previews are explicit rather than automatic on modal entry;
- the loaded-file list is virtualized;
- preview requests are abortable and session-scoped;
- `/api/imports/cells` now returns `202 Accepted` and starts a worker-owned registration job.

Those changes are useful and should be preserved. Runtime testing of the pushed implementation exposed a second set of defects after the user clicks **Import**. The previous implementation record is therefore historical and does not establish merge readiness.

## Review round 3 — Accepted import lifecycle, progress and durable population

### Runtime evidence

With approximately 1,000 reviewed files, after clicking **Import**:

- the global activity indicator remains at `0/1000`;
- the third modal closes immediately;
- the Cell Database remains empty;
- no progressively generated Cell data appear.

Code inspection explains these symptoms. The registration worker performs continuation/cache-dependent validation before inserting any Cell, progress is incremented only later, and the frontend detaches from the registration token immediately after the `202` response.

## Locked workflow update

This section supersedes the earlier rule that the modal must automatically close after background-job acceptance.

1. No relational import or hidden scientific preparation starts before the user clicks **Import**.
2. Clicking **Import** freezes the submitted payload and starts one idempotent background import job.
3. The third modal remains open by default and changes into a read-only progress view.
4. The user may keep watching progress or click **Continue in background**.
5. Closing the modal after acceptance detaches the progress view only. It must not cancel or roll back the accepted import.
6. Relational registration is committed before scientific cache preparation begins.
7. After relational commit, all Cells appear in the Cell Database with pending/parsing status.
8. Scientific data and summaries are applied incrementally as individual files finish.
9. Multiprocessing is permitted only for scientific cache preparation, not SQLite/ORM registration.
10. For more than 25 files, scientific preparation may use a bounded process pool. For 25 or fewer, use the lower-overhead serial path.

## Open findings

### R1 — Critical: Cold imports are rejected by cache-dependent continuation validation

**Affected files**

- `backend/app/routers/files.py`
- `backend/app/services/continuations.py`
- `backend/app/services/cache.py`
- `tests/test_import_flow.py`

**Current**

`_create_imported_cells_impl()` first loops through every submitted draft and calls `_inspect_cell_draft_chain()` before creating any relational rows. A separate-cell draft is therefore routed through continuation analysis even when it contains only one source.

`continuations.enrich_source_timing()` requires raw and cycle caches to mark a source inspection as ready. When a cache is missing it calls `cache.schedule_build()`, returns `inspection_status="pending"`, and `ensure_submittable_chain()` immediately rejects the submission as `inspection_incomplete`.

On a cold cache this produces the following sequence:

1. scientific preparation starts;
2. the source is marked pending;
3. registration is rejected;
4. the transaction rolls back;
5. no Cell is stored.

Even with warm caches, every source completes this prevalidation pass before the job counter can move from zero.

**Target**

Separate-cell registration must not use continuation timing or cycle-cache validation.

For separate cells, validate only:

- supported source type;
- source availability and stable identity;
- final checksum against the inspected identity;
- Cell-name validity and uniqueness;
- duplicate SourceFile ownership;
- folder and replicate-group validity;
- header metadata and scientific override validity.

Do not parse timeseries, calculate cycles, read scientific Parquet, or schedule cache work during this validation.

Continued-cell mode may perform additional chain validation, but cheap identity/header checks and cache-dependent timing checks must remain distinct.

**Acceptance criteria**

- A valid cold-cache import of one separate Cell succeeds.
- A valid cold-cache import of approximately 1,000 separate Cells reaches relational commit.
- No scientific cache is created before relational registration commits.
- Separate-cell submission cannot fail merely because raw or cycle caches are absent.
- A cache failure after relational commit preserves the Cell and SourceFile rows.

### R2 — Critical: The modal closes and stops polling immediately after acceptance

**Affected files**

- `frontend/src/pages/InboxPage.tsx`
- `frontend/src/useImportJobProgress.ts`
- frontend import-modal tests

**Current**

The save mutation handles the `202 Accepted` response as completion. Its success handler:

- sets `registerToken` to `null`;
- invalidates Cell and related queries before the worker commits;
- shows an acceptance notification;
- calls `onSaved()`.

`onSaved()` closes the modal and clears the staged import session. Clearing the token disables the dedicated registration-job polling hook. There is no later import-specific query invalidation when relational commit actually completes.

**Target**

After `202 Accepted`:

- retain the registration token;
- keep the third modal open;
- freeze all submitted fields and disable resubmission;
- show live validation/registration/preparation progress;
- expose **Continue in background**;
- treat close/Escape after acceptance as detach, not cancel;
- retain the accepted job in the global Activity surface.

On durable relational commit, invalidate/refetch:

- Cells;
- SourceFiles;
- folder tree;
- replicate groups;
- Activity.

On individual cache-result commits, refresh affected Cell/source summaries without forcing an expensive global recomputation.

**Acceptance criteria**

- Clicking Import does not automatically close the modal.
- The submitted form becomes read-only.
- Progress continues to update inside the modal.
- **Continue in background** closes the modal immediately without cancelling the job.
- The same job remains visible in Activity.
- Cells appear automatically after relational commit without application restart or manual refresh.
- Terminal worker failure is surfaced to the user.

### R3 — Critical: Progress does not represent the work being performed or durable state

**Affected files**

- `backend/app/routers/files.py`
- `backend/app/services/background_jobs.py`
- `frontend/src/importProgress.ts`
- `frontend/src/components/ImportProgressPanel.tsx`

**Current**

The worker performs a complete validation pass over all submitted drafts before `record_result()` is called. The activity indicator can therefore remain at `0/N` during substantial work.

During the later insertion loop, items are marked ready with `Cell staged for commit`, but the database transaction is not committed until every Cell, folder reference and replicate group has been prepared. Progress can consequently imply that hundreds of Cells are complete even though all of them remain rollbackable.

**Target**

Represent the import with truthful stages:

1. **Validating sources — X of N**
   - final identity/checksum and relational-plan validation;
   - no timeseries parsing;
   - no long database write transaction.

2. **Registering Cells**
   - one short relational transaction;
   - create Cell, one internal Test, ordered TestFile links, metadata, folder links and replicate references;
   - commit atomically.

3. **Preparing cycling data — X of N**
   - parse raw data and build cycle caches;
   - relational rows are already visible;
   - per-source errors do not roll back registration.

Do not label an item ready before the corresponding durable state exists.

**Acceptance criteria**

- Validation progress leaves zero promptly.
- No scientific parser executes in the relational registration transaction.
- Relational commit happens before cache preparation.
- After registration commit, all submitted Cells are visible with pending/parsing status.
- Pre-commit failure leaves no partial relational import.
- Post-commit cache failure preserves registered Cells and identifies affected sources.

### R4 — High: Scientific multiprocessing is unbounded and results are applied only after the batch

**Affected files**

- `backend/app/routers/files.py`
- `backend/app/services/background_jobs.py`
- cache-preparation tests

**Current**

`import_cache_worker_count()` can use every logical CPU. There is no 25-file threshold or conservative worker cap.

`build_import_caches_parallel()` uses ordered `executor.map()`. A slow early file can prevent completed later results from being reported. `apply_import_cache_results()` runs only after the entire batch returns, so SourceFile parse status, cycle count and capacity summaries are not committed as individual files finish.

**Target**

- 25 files or fewer: serial, below-normal-priority cache preparation.
- More than 25 files: bounded process pool.
- Cap worker count at `min(4, max(1, logical_cpu_count // 2), file_count)` unless measured evidence supports a different bound.
- Use `submit()` plus `as_completed()`.
- Worker processes return plain result payloads and never own SQLAlchemy sessions.
- The coordinator applies and commits each completed result incrementally.

**Acceptance criteria**

- 25 files use the serial path.
- 26 files use bounded multiprocessing.
- Worker count never consumes all logical CPUs.
- A slow first file does not hide completion of later files.
- Source status and summaries update as each result arrives.
- One file failure does not stop successful files from becoming ready.

### R5 — High: Continued mode still starts hidden scientific cache preparation before Import

**Affected files**

- `frontend/src/components/ContinuedImportEditor.tsx`
- `backend/app/routers/files.py`
- `backend/app/services/continuations.py`

**Current**

Continued mode automatically polls `/api/imports/continuations/inspect` while the modal is open. The backend continuation inspection calls `enrich_source_timing()`, which schedules cache generation whenever raw or cycle caches are missing.

Switching to continued mode can therefore start full timeseries preparation before the user clicks Import, despite the explicit-preview policy.

**Target**

Automatic continued-mode inspection may use only already available identity/header information and existing caches.

A check requiring a new full timeseries parse must be either:

- started by an explicit **Inspect continuation data** action; or
- queued after Import as part of the accepted job.

Merely opening or switching the modal must not start hidden scientific preparation.

**Acceptance criteria**

- Entering continued mode with cold caches starts no parser/cache job.
- Cheap compatibility information remains available from inspected headers.
- Full continuation timing/cycle checks require explicit user action or accepted import execution.

### R6 — High: Tests mock the failing boundary instead of exercising it

**Affected files**

- `tests/test_import_flow.py`
- `tests/test_background_jobs.py`
- frontend import-modal tests
- this review file

**Current**

The acceptance test mocks `run_import_registration_job()`. It proves that the request returns before a mocked worker but not that the real worker can register a cold-cache source.

The failure test mocks `_create_imported_cells_impl()`. There is no integration test combining:

- the real accepted endpoint;
- the real threaded registration worker;
- worker-owned `SessionLocal`;
- file-backed SQLite;
- initially empty scientific cache;
- job polling;
- relational commit;
- subsequent scientific preparation.

The previous review record reported the follow-up complete, but the runtime behaviour demonstrates that the critical lifecycle was not covered.

**Target**

Add backend integration coverage for:

- cold-cache separate-cell registration;
- no cache work before relational commit;
- validation progress;
- Cells visible before scientific preparation completes;
- incremental cache-result persistence;
- cache failure preserving registered Cells;
- accepted job continuing after frontend detachment;
- 25/26-file execution-policy boundary;
- real threaded `SessionLocal` against file-backed SQLite.

Add frontend coverage for:

- modal remains open after `202`;
- accepted state is read-only;
- Continue in background detaches only the UI;
- polling token is retained;
- relational completion invalidates library queries;
- terminal failure is shown;
- 1,000 rows remain virtualized during progress.

**Acceptance criteria**

- The new tests fail against commit `824864ffac71aa7dcbc04174ec384535675aa4c6`.
- Focused tests pass after correction.
- A production desktop check with approximately 1,000 cold-cache sources verifies modal progress, background detachment, automatic database population and incremental scientific readiness.

### R7 — Medium: Worker setup can leave a permanently running job

**Affected files**

- `backend/app/routers/files.py`
- worker-lifecycle tests

**Current**

Registration and cache workers construct `SessionLocal()` before entering the main guarded `try` block. A session-construction, process-pool creation or early setup failure can terminate the daemon thread without marking the background job failed.

**Target**

Wrap the complete worker lifecycle, including priority setup, session construction and executor creation, in a top-level failure boundary that always transitions the job to a terminal state.

**Acceptance criteria**

- Injected `SessionLocal()` failure marks the job failed.
- Injected process-pool creation failure marks the cache job failed.
- No exception path leaves a job indefinitely `running` without live work.

## Implementation order

1. Remove cache-dependent continuation validation from separate-cell registration.
2. Split validation, relational registration and scientific preparation into explicit stages.
3. Keep the modal open after acceptance and retain job polling.
4. Add Continue in background/detach semantics.
5. Commit relational state before scientific cache preparation.
6. Add bounded >25-file multiprocessing with `as_completed()` and incremental result commits.
7. Stop hidden continued-mode cache generation before Import.
8. Add real cold-cache threaded integration and frontend lifecycle tests.
9. Perform the approximately 1,000-file production desktop check.
