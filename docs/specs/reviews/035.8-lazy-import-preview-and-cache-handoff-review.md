## Review round 2 — Third-modal responsiveness and workflow correction

The current implementation passes the earlier functional checkpoint, but a 1,000-file import exposes
serious third-modal regressions:

- the application becomes sluggish after the third modal opens;
- selecting files causes slow foreground preview preparation;
- closing the modal can appear ineffective while work continues;
- the current implementation starts the first active preview automatically.

This review records a new explicit user decision and overrides the earlier 035.8 rule that the active
source should auto-preview when the modal opens.

## Locked workflow clarification

The intended workflow is now:

1. The second-to-third-modal inspection may establish file identity, checksum, header metadata and
   duplicate/update status. It must not register Cells or prepare scientific caches.
2. The third modal opens with every preview in `idle`. Merely opening the modal must not parse any
   timeseries or start any capacity preview.
3. A capacity preview starts only after an explicit user click on a file/preview action. Switching to
   another file by an explicit click may start that file's preview. Returning to a ready file reuses
   the existing result. There is no automatic first-file preview and no prefetch.
4. No actual import work starts before the user clicks **Import** in the third modal.
5. After the user clicks **Import**, the application freezes the submitted draft payload, queues the
   import as background work, acknowledges acceptance promptly, closes the modal and reports progress
   through the normal Activity/background-job surface.
6. Closing or cancelling the third modal before submission performs no import and must remain
   immediate even when a preview request is running.

An explicitly requested preview may build/reuse its scientific cache because the user requested that
file's preview. Hidden or merely staged files must not be parsed or cached before **Import**.

## Confirmed current implementation

- `frontend/src/pages/InboxPage.tsx` contains an effect that automatically calls
  `onPreviewRequested(draft)` for the active draft when the third modal opens and its preview state is
  `idle`.
- `frontend/src/components/ContinuedImportEditor.tsx` contains the equivalent automatic preview
  effect for its selected preview source.
- `/api/imports/preview` calls `build_capacity_preview`, which calls
  `cache.build_write_behind`. Despite its name, `build_write_behind` performs
  `parsing.parse_timeseries` and `calc.per_cycle` synchronously; only Parquet writing is deferred.
- The third modal's Loaded files panel directly renders `drafts.map(...)`, mounting all staged cards.
- Preview-state updates map over the complete `drafts` array before React reconciles the full list.
- Manual close currently hides the modal but does not clear the staged import session, abort the
  request or prevent all late updates.
- The current save mutation begins only after the Import button is clicked, but the modal remains
  tied to a synchronous registration request before the later cache-job handoff. This does not meet
  the clarified requirement that the actual import workflow itself be accepted and executed in the
  background.

## Follow-ups

### R1 — Critical: Remove automatic preview generation

**Affected files**

- `frontend/src/pages/InboxPage.tsx`
- `frontend/src/components/ContinuedImportEditor.tsx`
- `frontend/src/importPreviewPolicy.ts`
- `frontend/tests/importPreviewPolicy.test.ts`

**Current**

Opening the third modal automatically requests a preview for its initially active source. Continued
mode does the same for its selected preview source.

**Target**

- All staged sources remain `idle` when the third modal opens.
- No preview request occurs merely because a source is active by default.
- An explicit user click on a file row or dedicated Preview action selects the file and requests its
  preview when still idle.
- Ready previews are reused; errors remain retryable; no adjacent or hidden file is prefetched.
- Separate-cell and continued-cell modes follow the same explicit-click policy.

**Acceptance criteria**

- Opening the third modal with 1,000 files produces zero `/api/imports/preview` requests.
- Clicking one file produces exactly one preview request for that file.
- Clicking another file produces exactly one request for the second file.
- Returning to a ready file produces no new request.
- No source other than one explicitly clicked by the user leaves `idle`.

### R2 — Critical: Queue the actual import only after explicit submission

**Affected files**

- `backend/app/routers/files.py`
- `backend/app/services/background_jobs.py`
- `frontend/src/pages/InboxPage.tsx`
- `frontend/src/components/ContinuedImportEditor.tsx`
- `frontend/src/api.ts`
- `tests/test_import_flow.py`
- focused background-job tests

**Current**

The Import button starts a synchronous registration request. The modal stays in a pending state until
that request returns, after which scientific cache preparation is handed to background work.

**Target**

- Before the user clicks Import, no Cell/Test/SourceFile registration, source adoption or batch cache
  preparation occurs.
- Clicking Import freezes an immutable submission payload and creates one background import job.
- The request returns promptly after the job is accepted, with a job ID/token and submitted Cell/file
  count.
- The third modal closes after acceptance; registration and subsequent cache preparation continue in
  the background.
- The background coordinator owns its own `SessionLocal`; workers never share a request SQLAlchemy
  session.
- Registration remains transactional. A failure before commit creates no partial imported Cells.
- After registration commits, cache-preparation failures preserve the imported Cells and report the
  affected sources as errored/retryable.
- Repeated clicks or request retries cannot enqueue duplicate imports for the same submission token.
- Activity distinguishes at least registration from scientific preparation and reports final
  success/failure truthfully.

**Acceptance criteria**

- Waiting in the third modal without clicking Import causes no relational import or hidden cache
  preparation.
- Cancel before submission leaves the database unchanged.
- Clicking Import returns control and closes the modal without waiting for all selected files to be
  registered or parsed.
- The rest of the application remains usable while the job runs.
- Background progress is visible after the modal closes.
- Restart/failure behaviour is explicit: the job either resumes safely where supported or reports an
  interrupted/failed state without claiming completion.
- Separate-cell and one-continued-cell submissions both preserve their existing domain invariants.

### R3 — Critical: Virtualize the third-modal loaded-file list and bound state updates

**Affected files**

- `frontend/src/pages/InboxPage.tsx`
- a focused reusable virtual-list component or policy module if extraction is justified
- frontend tests for the import editor

**Current**

The modal mounts every staged file card through `drafts.map(...)`. Preview and edit updates map over
the complete draft collection and cause the large list to reconcile again.

**Target**

- Use fixed-row viewport virtualization with bounded overscan for the Loaded files panel.
- Keep only visible rows mounted.
- Separate per-file preview state from the large immutable inspection payload, or otherwise ensure a
  one-file state change does not recreate every row object.
- Preserve selection, active-row, duplicate-warning, grouping, drag/drop and removal semantics.

**Acceptance criteria**

- With 1,000 staged files, the DOM contains only a bounded visible window plus overscan.
- Clicking a row, editing active-file fields and receiving a preview result remain responsive.
- A preview transition updates the active detail and mounted row only, not 1,000 rendered cards.
- Keyboard navigation, scrolling and light/dark presentation remain correct.

### R4 — High: Make close/cancel immediate and session-safe

**Affected files**

- `frontend/src/pages/InboxPage.tsx`
- `frontend/src/api.ts`
- preview loader/session policy and tests

**Current**

Close primarily changes `modalOpen`; staged drafts and request bookkeeping remain. The exported API
helpers do not expose an abort signal, and a late preview result can still attempt a state update.

**Target**

- Closing before submission invalidates the import-session generation and clears disposable staged
  and preview state.
- Abort in-flight preview requests where supported.
- Always ignore late responses from a closed or replaced session.
- Unmount the heavy import editor when closed.
- Backend cache artifacts already completed from an explicitly requested preview may remain; closed
  frontend state must not be restored accidentally.

**Acceptance criteria**

- Cancel, Escape and the modal close control respond immediately during preview preparation.
- The application is interactive as soon as the modal closes.
- A late preview response cannot reopen, repopulate or mutate the closed session.
- Reopening starts from a clean staged-import state.
- Closing before clicking Import never starts an import job.

### R5 — High: Add behavioural regression coverage for the 1,000-file workflow

**Affected files**

- `frontend/tests/importPreviewPolicy.test.ts`
- new focused import-modal component/integration tests
- `tests/test_import_flow.py`
- background-job tests

**Current**

Existing frontend tests cover request fingerprints, content-based keys and result-state conversion,
but not modal mounting, explicit-click behaviour, close during work or background submission.

**Target**

Add automated coverage for:

- zero preview requests on third-modal open;
- one request per explicitly clicked uncached file;
- ready-result reuse and retry after error;
- bounded mounted rows for a 1,000-draft fixture;
- immediate close and late-result rejection;
- no import before the Import button;
- prompt background-job acceptance after clicking Import;
- transactional registration failure;
- post-commit cache failure reporting;
- separate-cell and continued-cell submission.

**Acceptance criteria**

- The tests fail against the current implementation for the confirmed regressions.
- Focused backend and frontend tests pass after the fixes.
- A production-build browser check uses approximately 1,000 files and records:
  - no preview on entry;
  - one preview only after a file click;
  - responsive close while previewing;
  - modal closure after background import acceptance;
  - continued Activity progress after closure.
