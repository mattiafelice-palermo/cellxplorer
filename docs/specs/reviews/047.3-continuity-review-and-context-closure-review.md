## Findings

### R1 — Medium: a hard inspection error loses its only visible explanation, and the footer tells the user to do something that cannot help

Affected files:
- `frontend/src/components/ContinuationSourceList.tsx`
- `frontend/src/components/ContinuedImportEditor.tsx`
- `frontend/src/pages/InboxPage.tsx`

**Current**

Section D permits a concise `Error` badge with the detailed reason living "in Continuity review /
tooltip". The implementation removed the inline reason from the compact row:

```tsx
-{source.inspection_error && <Text size="xs" c="red" pl={22}>{source.inspection_error}</Text>}
```

and moved it to a native `title` attribute on the status `Badge`. That would be acceptable if
Continuity review carried the same information — but for this class of error it does not, and the
surrounding state actively misdirects.

`backend/app/services/continuations.py` emits the blocking `inspection_failed` finding only when the
source has *no* hash:

```python
if source.get("inspection_status") == "error" and not source.get("hash"):
```

Two reachable paths set `inspection_status = "error"` *after* the hash is established, so they
produce no finding at all:

1. cycle-range extraction errors — `source["inspection_error"] = "; ".join(errors)` (e.g. non-numeric
   cycle labels);
2. cache-build failure — `source["inspection_error"] = source["cache_build_error"]`.

For both, the resulting UI state is:

- the Continuity review modal shows nothing, because it renders findings only and no finding exists;
- `inspection_complete` is `false` (the source is not `ready`), so `continuationReviewRequired(...)`
  early-returns `false` — the modal does not auto-open and the "Continuity review required before
  import." line never appears;
- the footer therefore falls to `inspectionRequired` and reads **"Inspect continuity before
  importing."**, even though inspection has already run and hard-failed;
- the command button still reads "Inspect continuity", and clicking it re-runs the same failing
  inspection.

The user is told to repeat the one action that cannot resolve the state, while the actual reason is
reachable only by hovering a small badge — a native `title`, so it is not keyboard reachable and is
inconsistent with the Mantine `Tooltip` used by the Move/Remove controls in the same row.

Import is still correctly blocked (`can_submit` requires every source `ready`), so this is a
diagnosability defect, not a safety one. But it is a regression against pre-047.3 behavior, where the
reason was always visible under the row, and section D's "detailed reason belongs in Continuity
review / tooltip" assumed the review surface would carry it.

The footer message also conflates three distinct states behind one string, since
`inspectionRequired = !result?.inspection_complete` is true for all of them: never inspected,
inspection in progress (caches building), and inspection failed. Only the first is described
correctly.

**Target**

A source whose inspection hard-failed explains itself somewhere the user will actually find, and the
footer/command state distinguishes "not yet inspected" from "inspection failed".

Any of these satisfies the first half, in preference order: surface `inspection_error` inside the
Continuity review surface as a non-finding source-error section; or keep it in the row using the
Mantine `Tooltip` already used by neighbouring controls; or restore a concise inline reason for the
error case only.

For the second half, the footer must not instruct the user to inspect when inspection has already
completed with an error.

**Acceptance criteria**

- With a source in `inspection_status: "error"` that carries a hash and produces no finding, the
  user can reach `inspection_error` without hovering a native `title` — via the review surface, a
  Mantine `Tooltip`, or visible row text.
- The footer status for that state does not read "Inspect continuity before importing."
- Pure coverage distinguishes at least "not inspected" from "inspection errored" in whatever policy
  helper carries the footer state, so the two cannot silently collapse again.
- Import remains blocked for that source exactly as it is today; `can_submit` semantics unchanged.

## Checked and accepted (no finding)

- **Section A — the workspace is quiet.** The persistent blocking Alert, the confirmation
  acknowledgement checklist, and the informational/warning finding rows are all gone from the
  three-column layout; the compact rows no longer render finding rows. What remains below the pane
  row is a single `size="xs"` line, shown only when review is genuinely outstanding and the modal is
  closed. No colored Alert is used for the neutral pre-inspection state, which still shows the
  restrained "Inspect continuity to prepare the combined preview." copy from 047.2.
- **Section B1 — grouping is severity-driven.** `ContinuationReviewModal` derives its three groups
  from `blockingFindings(...)`, `severity === "confirmation"`, and `informationalFindings(...)`.
  Blocking rows carry no checkbox and cannot be acknowledged away; confirmations get exactly one
  checkbox each; warning/info sit under a collapsed `Accordion` labelled `Details (n)` and are shown
  nowhere in the main workspace. No parallel list of confirmation codes was introduced — severity
  alone decides, as the spec requires.
- **Section B2 — acknowledgement identity preserved.** `preserveAcknowledgements(...)` still runs on
  every new result, so an acknowledgement survives only while its exact finding ID does.
  `acknowledgedMetadataOnlySourceKeys(...)` is untouched and still binds metadata-only consent to the
  current server finding. No generic "I understand" checkbox was introduced. Traced the reorder path:
  a reorder changes the inspection query key, `result` becomes `undefined`, the auto-open effect
  closes the modal, and the stale acknowledgement is dropped when the new result arrives — matching
  the spec's acknowledge → reorder → expire sequence.
- **Section B3 — open/close behavior.** The auto-open effect keys on `dataUpdatedAt`, so it fires once
  per fresh completed inspection and does not reopen when the user closes the modal or ticks a
  checkbox (those change neither `dataUpdatedAt`, `opened`, nor `result`). Clean inspections do not
  interrupt; warning/info-only results do not auto-open, since `continuationReviewRequired` ignores
  those severities. The command relabels to "Review continuity" / "Inspected", and closing the modal
  with review outstanding leaves the primary action disabled with "Continuity review required before
  import." in the footer, satisfying the requirement that a disabled button alone is insufficient.
- **Section C — submission safety is unchanged.** `continuedImportCanSubmit(...)` still gates
  `canSubmit` alongside the ≥2-source and scientific-draft checks; `reviewRequired` was added as
  reporting state and does not replace any gate. The server remains authoritative. `Inspect
  continuity` is not cosmetic — it is still what produces the result every gate reads.
- **Section D — compact statuses.** `compactSourceStatusLabel` returns exactly the four permitted
  values (`Not inspected`, `Preparing`, `Ready`, `Error`), with `Preparing` correctly driven by
  `cache_build_status`. No per-row warning/info counts were added. Historical source / Tracked tail
  badges remain.
- **Section E — registration/progress untouched.** The `save.mutate({ mode: "continued", ... })`
  payload, `replicate_groups: []`, destination folders, job token, progress panel, commit boundary,
  Continue in background and Done/autoclose paths are all unchanged from 047.1; the diff does not
  reach that region of `InboxPage.tsx`.
- **Section F — regressions.** Separate mode is untouched. In `ContinuationSourceList`, every change
  is inside the `compact-import` branch; the default branch — including its `inspection_error` line,
  detail rows, findings rows and raw-data button — is byte-identical, so `ContinuationManagementPanel`
  (which passes no `variant`) still renders the full detailed list.
- **Section G — performance knowledge updated.** `state-and-performance.md` now distinguishes the
  ordinary per-source preview ("only the active source may request an ordinary per-source capacity
  preview") from the continued-chain combined preview, and states that the latter never starts from
  Step-3 open or a mode switch, is gated behind inspection, reads prepared ordered caches through
  backend stitch semantics, returns bounded display data, and creates no second scientific cache. All
  existing identity/fingerprint and late-result protections were retained rather than rewritten.
- **Sections H1/H2/H4 — project-context corrected.** `CELLXPLORER_ARCHITECTURE.md` replaces
  `SourceFile → Test → Cell` with `Cell └── ordered SourceFiles` and explains the tracked tail, the
  single internal Test row, and that a protocol restart does not create another Test. The MPR
  paragraph now describes the narrow independently verified source-local cycle-1 path with the
  header-proven neutral preamble, mixed/repeated identity remaining metadata-only, and `.mpt` as
  validation material — wording that matches `AGENTS.md` on current `main`, not this feature branch.
  Synchronization metadata in both changed files was updated to `main` at `5e50736` (`0.26.0-beta.6`),
  which is the real current main. The drift audit stayed narrow: no screenshot-level UI detail leaked
  into the mirror.
- **Section I — index closure.** `docs/specs/README.md` links all three child review files and records
  the current status. The 047.3 review link resolves as of this file.
- **Focused tests.** The new `continuationReviewRequired` coverage asserts that warning/info do not
  require review, that confirmation does, that acknowledging clears it, that blocking always requires
  it, and that an incomplete inspection never demands review. Existing coverage for preserved
  acknowledgements, metadata-only binding, reorder expiry, footer order/acknowledgement projection and
  the separate-mode payload remains green and unmodified.
