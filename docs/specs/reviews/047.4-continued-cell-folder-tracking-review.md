## R13 — High: file checkboxes render one click behind, and Shift/Ctrl range selection never applies

Affected files:
- `frontend/src/components/ImportFilesystemPickerModal.tsx`

**Current**

The user reports: a single click puts no check in the box; the check for click *N* only appears when
click *N+1* happens; Shift/Ctrl does not extend the selection; and on **Continue** the missing last
checkbox flashes in for an instant. That last detail is the tell — the selection state is correct all
along, and only the rendered checkbox is stale.

The cause is in the new handler:

```tsx
onClick={(event) => {
  event.stopPropagation();
  if (!isFolder) {
    event.preventDefault();          // <-- this
    toggleFile(entry, event.shiftKey, event.ctrlKey, event.metaKey);
  }
}}
onChange={() => { if (isFolder) activateFolderCheckbox(entry); }}
```

`Checkbox` is controlled — `checked={selected.has(entry.path)}`. Calling `preventDefault()` on the
click cancels the browser's native toggle **and** suppresses the `change` event, so for files
`onChange` never fires. React's controlled-input machinery restores a checkbox's DOM state through
that change event and through its internal value tracker; with the native toggle cancelled and no
change event, the DOM node's `checked` and React's rendered value drift apart, and the box only
catches up on the next render triggered by an unrelated interaction. Hence "one click behind", and
hence the flash on Continue when the modal finally re-renders.

Shift/Ctrl is a second, independent failure: modifiers are read off the click event, but because the
handler is fighting the controlled input, `toggleFile`'s range branch is applied against a
`lastSelectedPath` anchor that is being updated on a path the user never perceives as committed.

**Target**

Let the checkbox behave as a normal controlled input: never `preventDefault()` on it. Drive the state
change from `onChange` and read the modifier keys from the change event's native event, which for a
checkbox is the originating click:

```tsx
onClick={(event) => event.stopPropagation()}
onChange={(event) => {
  if (isFolder) { activateFolderCheckbox(entry); return; }
  const native = event.nativeEvent as MouseEvent;
  toggleFile(entry, native.shiftKey, native.ctrlKey, native.metaKey);
}}
```

If `nativeEvent` modifiers prove unreliable for keyboard-activated toggles, the alternative is to
record modifiers in a ref from `onMouseDown` and read that ref in `onChange` — but still without
`preventDefault()`. Keyboard activation (Space) must keep working and must behave as a plain toggle.

Confirm the anchor semantics while you are there: plain click sets the anchor and replaces the range;
Shift extends from the anchor to the clicked row over `visibleEntries` (the filtered/visible order, so
a search filter cannot select hidden rows); Ctrl/Cmd toggles one row and moves the anchor.

**Acceptance criteria**

- One click on a file checkbox shows the check immediately, with no second interaction.
- Shift+click selects the contiguous visible range from the anchor; Ctrl/Cmd+click toggles a single
  row; both are reflected immediately.
- Keyboard Space still toggles the focused checkbox.
- No `preventDefault()` remains on a controlled checkbox in this component.
- Pure coverage for `toggleImportFileSelection` includes a Shift range over a *filtered* visible list.
- Browser check: select three files with click, Shift+click, Ctrl+click and confirm the count and the
  boxes agree at every step.

## R14 — Medium: returning from the second modal to the first discards the whole selection

Affected files:
- `frontend/src/components/ImportFilesystemPickerModal.tsx`
- `frontend/src/pages/InboxPage.tsx`

**Current**

Selection lives only inside the picker (`const [selected, setSelected] = useState<Map<...>>(new Map())`)
and is wiped whenever the modal opens:

```tsx
useEffect(() => { if (!opened) return; ... setSelected(new Map()); ... });
```

So stepping forward to step 2 and pressing Back re-opens the picker with an empty selection, losing
work the user already did. The user is right that this should not happen — Back is a navigation, not a
discard, and nothing warns that the selection will be lost.

**Target**

Going back restores exactly the previous selection. Either lift the selected-entry map into
`ImportModal` (which already owns the staged drafts and therefore already knows what was chosen) and
pass it in, or seed the picker's initial state from the current staging when it reopens for a Back
navigation, while keeping the reset for a genuinely fresh import.

Distinguish the two entry paths explicitly — a fresh "Import" opens empty; a Back from step 2 opens
populated.

**Acceptance criteria**

- Select files → Continue → Back: every previously selected file is still checked, and the count
  matches.
- Starting a brand-new import still opens with an empty selection.
- Removing a file in step 2 and going Back does not resurrect it.
- Focused coverage for whatever pure helper carries the seeded-versus-reset decision.

## R15 — Medium: the tracking toggle is in the wrong place for what it does

Affected files:
- `frontend/src/components/ContinuedImportEditor.tsx`

**Current**

The spec put the toggle in the footer, replacing the neutral "Review N selected files" copy. Having
now seen it in use, the user asks whether there is a better home. I could not evaluate the rendered
result — no screenshot was attached to this round, and browser verification is not available to me —
so this is a reasoned recommendation from the layout, to be confirmed on screen.

The footer is the wrong register. Everything else in that row is *transient status about this
submission* ("Continuity review required…", "Inspect continuity before importing"), whereas tracking
is a **durable property of the Cell being created** — it outlives the import and keeps running
afterwards. Putting a persistent configuration control in a status slot also forces the precedence
ladder in the spec's section A1, where the toggle has to lose to four continuity states and can
therefore vanish exactly when the user goes looking for it.

**Target**

Move the toggle into the **Cell draft pane** (right column), below the scientific fields, as a small
titled group — for example a `Divider label="Folder tracking"` followed by the switch, a one-line
dimmed folder/pattern summary, and the Settings button. That pane already holds "things that will be
true of this Cell", which is exactly what tracking is, and it is always visible rather than competing
with footer status.

The footer then keeps its 047.3 states and, when nothing else applies, may carry a single dimmed
confirmation such as `Tracking C:\…\CellA for new .mpr files` — status, not control.

Confirm on screen before finalising; if the Cell-draft pane proves too crowded at the supported
geometry, the fallback is directly beneath the source chain, still outside the footer.

**Acceptance criteria**

- The toggle is not in the footer status slot and cannot be hidden by a continuity state.
- It reads as part of the Cell being created, with folder and pattern visible next to it.
- Footer precedence for the 047.3 states is unchanged.
- Light and dark mode checked at the supported desktop geometry.

## R19 — Medium: format selection must be a multi-select of supported formats

Affected files:

- `frontend/src/folderTrackingPolicy.ts`
- `backend/app/services/cell_folder_watch.py`
- `backend/app/models.py`, `backend/app/migrations/versions/v0004_cell_folder_watch.py`

**Current**

The watch stores exactly one extension (`normalize_extension` returns a single value), and the dialog
asks for one. The user wants a dropdown listing the currently supported formats with checkboxes, so

section 1 of the spec must be updated to say so.

this one is not released. Confirm the forward path from a `v0003` database still applies cleanly after
the amendment.

**Target**

Format selection is a Mantine `MultiSelect` (checkbox style) populated from the formats the importer
actually admits — derived from the central extension policy, never a hardcoded list. At least one
format must be selected. The watch persists the set, and matching admits a candidate whose extension
is any member.

**Acceptance criteria**

- The dropdown lists exactly the importer's supported formats and allows multiple selection.
- Saving with an empty selection is rejected in the dialog.
- A watch with two formats attaches valid files of both.
- `v0004` amended in place; forward migration from a real `v0003` database verified.
- Spec section 1's trackability rule updated for multi-format selections.

## R26 — High: pre-existing files the user chose *not* to import will be attached automatically

Affected files:
- `backend/app/services/cell_folder_watch.py`
- `backend/app/models.py` and the folder-watch migration
- `frontend/src/components/FolderTrackingSettingsModal.tsx`

**Current**

The user asks what happens when a matching file they never selected is already sitting in the folder.
Tracing the scan loop, it is treated exactly like a newly arrived file:

```python
if path.suffix.lower().lstrip(".") not in watch.extensions: continue
if not matches_filename(path.name, watch.pattern_kind, watch.pattern): continue
...
candidate = _candidate_for(db, watch.id, normalized)
```

There is no baseline — nothing distinguishes "was already here when the watch was created and the
user did not select it" from "appeared afterwards". Any pre-existing match that is not already
attached becomes a candidate and, if it passes stability and continuity, is **attached
automatically**.

The screenshot makes the consequence concrete: the watched folder is `C:\Users\matti\Downloads` with
pattern `*.mpr`. Every unrelated `.mpr` in Downloads is an attach candidate for this Cell. Worse, a
user who deliberately declined a file — a bad run, a duplicate export — has that decision silently
reversed on the next scan.

This is the mirror of the auto-acknowledgement rule the spec already locks. Section F promises that
nothing invalid or ambiguous is ever silently dropped; the matching promise, that nothing
*unrequested* is ever silently added, is currently unmet.

**Target**

Record a **baseline** when the watch is created: the files already present in the folder that match
the rules but were not among the imported sources. Those are excluded from automatic attachment for
the life of the watch.

Excluded is not invisible. Record them as `ignored` candidates so they stay listed with a clear
reason, and give the user a deliberate way to include one later. The matching-files preview should
distinguish the groups at save time:

```text
selected for import        → become the Cell's sources
already here, not selected → ignored; new files only from now on
```

Only files first observed after the watch exists are attached automatically.

**Acceptance criteria**

- A matching file present at save time and not selected is never auto-attached.
- It appears as an `ignored` candidate with a reason the user can act on.
- A file that appears after the watch is created is still attached normally.
- The dialog's preview labels which currently-present files will be tracked and which are baselined.
- Backend regression tests cover: baseline file not attached on first scan; a genuinely new file
  attached; a baselined file explicitly re-included by the user.
- The baseline survives a restart.
