## Assessment

The implementation establishes the intended inspection vocabulary, structured findings,
acknowledgement policy, staged-file support, and frontend policy helpers. However, the current
inspection result can become submittable before the information required to evaluate the chain is
available. Repeated inspection can also start duplicate background cache work.

These are correctness issues, not UI polish. Lifecycle mutations in Spec 034.3 must not rely on the
current `can_submit` result until the findings below are addressed.

## Confirmed correct by code reading

- Findings have stable codes, severities, messages, details, and acknowledgement requirements.
- Blocking findings cannot be waived by acknowledgement.
- Required acknowledgement codes are derived centrally rather than duplicated in route code.
- Staged sources and registered sources use a shared inspection representation.
- Header-derived source identity and compatibility fields are exposed to inspection.
- Frontend continuation policy is isolated in a small module with focused tests.
- Inspection does not modify the database.
- Source hashing attempts to detect changes during the inspection read.

## Follow-up tasks

### R1 — High: pending or partial inspection is considered submittable

**Affected files**

- `backend/app/services/continuations.py`
- `backend/app/services/cache.py`
- `backend/app/services/parsing.py`
- `frontend/src/continuationPolicy.ts`
- `tests/test_continuations.py`
- relevant frontend policy tests

**Current**

`can_submit` is blocked only by findings with blocking severity. A source may therefore be returned
as pending while `can_submit` remains true. `ensure_submittable_chain` follows the same rule and does
not reject incomplete inspection.

The cache enrichment path also treats partial cache availability as ready:

- raw cache without cycle cache can be returned without cycle-range evidence;
- cycle cache without raw cache can be returned without raw timestamp evidence;
- when neither cache exists, an ad hoc background build is started and the result remains pending.

This allows attach, reorder, or detach to proceed before overlap, order, and cycle-boundary findings
are known. It is incompatible with the preflight-gate role assigned to Spec 034.2.

Header-derived findings are also delayed by the pending-cache early return even though those values
are already available without scientific cache construction. This includes compatibility evidence
such as protocol, channel, capacity, mass, and related metadata.

**Target**

Make inspection completeness explicit and authoritative.

A chain is submittable only when:

1. all sources required for the proposed chain have stable inspected identities;
2. all header-derived findings have been evaluated;
3. all cache-derived checks required by the inspection contract are complete; and
4. no blocking finding exists and every required acknowledgement is present.

Pending, building, failed, or partially enriched sources must produce `can_submit: false`. Do not
represent incomplete evidence as compatible.

Evaluate header-derived findings immediately, regardless of cache state. Cache-dependent findings
may remain pending, but their absence must block submission.

For partial caches:

- raw-only must derive or build the cycle information required by inspection;
- cycle-only must derive or build the raw timing information required by inspection;
- a failed build must return a stable blocking/pending diagnostic rather than silently omitting the
  check.

Keep this work outside request-critical parsing where possible, but correctness takes priority over
returning a prematurely permissive result.

**Acceptance criteria**

- `pending`, `building`, `failed`, and partial-cache states all return `can_submit: false`.
- `ensure_submittable_chain` rejects the same states.
- Header-only incompatibilities are returned immediately while cache work is pending.
- Raw-only and cycle-only fixtures cannot become submittable until both required evidence sets are
  available.
- Once enrichment completes, a fresh inspection returns deterministic findings and `can_submit`.
- Tests cover no-cache, raw-only, cycle-only, failed-build, header-incompatible, and fully-ready
  cases.
- Frontend policy cannot enable submission for an incomplete inspection response.

### R2 — Medium: repeated inspection can launch duplicate cache builds

**Affected files**

- `backend/app/services/continuations.py`
- `backend/app/services/cache.py`
- `tests/test_continuations.py`

**Current**

When inspection finds that cache enrichment is required, it starts a daemon thread directly.
Repeated inspection requests for the same source can therefore start multiple builds for the same
hash and calculation version before the first build finishes.

The existing cache write-behind coordination does not make this safe: the direct inspection thread
is outside the normal tracked/deduplicated build lifecycle. Duplicate parsing and cache writes are
possible, increasing I/O and creating timing-dependent inspection responses.

**Target**

Route inspection enrichment through one deduplicated cache-build mechanism keyed by the stable
source identity and calculation version. At most one build for the same source/version may be in
flight in the process.

Prefer extending or reusing the existing cache coordination rather than adding a separate worker
framework. The mechanism must:

- return the same pending state to concurrent callers;
- avoid duplicate parsing;
- expose completion/failure to subsequent inspection calls;
- remain safe when the source changes and receives a new hash;
- preserve normal cache maintenance behavior.

**Acceptance criteria**

- Two or more concurrent/repeated inspections start one cache build for a source hash/version.
- All callers receive deterministic pending responses while that build is active.
- A later inspection observes the completed caches without starting another build.
- A failed build can be retried according to a defined, tested rule and does not spin up repeatedly
  on every request.
- A changed source hash is treated as a distinct build key.
- Tests instrument the build entry point and assert the exact invocation count.
