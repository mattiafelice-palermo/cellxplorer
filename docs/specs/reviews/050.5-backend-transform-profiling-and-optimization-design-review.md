## Findings

### R1 — Medium: the derivative profile leaves the dominant backend cost unlocalized

Affected files:
- `backend/app/services/analysis_engine.py`
- `scripts/profile_time_capacity_transforms.py`
- `docs/specs/050.5-backend-transform-profiling-and-optimization-design.md`
- focused profiling tests as needed

**Current**

050.5 is required to explain why dQ/dV scales to multi-second backend work and to identify the dominant internal operation/loop before a later derivative optimization child is designed. The new `_derivative_curve()` instrumentation times only three inner blocks: rolling smoothing, `np.gradient`, and ratio/filter division.

The recorded medians show that those timers account for only a small minority of the derivative stage:

| Scenario | Derivative total | Rolling + gradient + ratio/filter | Unaccounted inside derivative | Unaccounted share |
| --- | ---: | ---: | ---: | ---: |
| 1–3 | 34.3 ms | 6.5 ms | 27.8 ms | ~81% |
| 1–20 | 162.1 ms | 34.3 ms | 127.8 ms | ~79% |
| All | 1,302.3 ms | 279.8 ms | 1,022.5 ms | ~78% |

That residual is not generic route or serialization time: it is inside the already measured `derivative` stage. Current code leaves several repeated operations outside the new sub-timers, including the contiguous `(cycle, segment, phase)` run scan, per-segment status/CV string handling, percentile/span calculation and outlier rejection, absolute-discharge handling, and output assignment. With roughly four-fifths of derivative time still unattributed, the implementation record can say that cost scales with hundreds of segments, but it cannot yet say which backend operation actually dominates that scaling.

The frontend explanation — one Plotly trace for each finite contiguous `(cycle, phase)` run — is sufficiently grounded and is not part of this finding.

**Target**

Complete the profiler-only derivative decomposition far enough to localize the dominant backend cost. Add only a small number of bounded timing buckets around the currently unmeasured work that code inspection shows can be material (for example run scanning/grouping and the post-gradient per-segment cleanup/statistics block), then rerun the existing 1–3 / 1–20 / All matrix. Do not optimize the derivative algorithm or trace architecture in 050.5.

Update the implementation record so the recommendation for the later derivative child names the measured dominant backend operation(s), rather than inferring the cause from segment count alone.

**Acceptance criteria**

- The 1–3, 1–20 and All dQ/dV evidence reports derivative-total time plus decision-useful sub-stage timings for the remaining material work.
- The previously ~78–81% unexplained derivative residual is decomposed enough that it is no longer the dominant unidentified bucket.
- The implementation record explicitly identifies the dominant backend derivative operation(s) from measurements and separately retains the already-correct frontend trace-count explanation.
- Profiling remains opt-in/bounded; ordinary scientific output is unchanged and golden digests remain unchanged.
- Focused profiling tests and canonical preflight pass.
- No derivative optimization, prepared-data optimization, 050.6+, or proto-child 050.P1 is implemented in this fix round.
