## Findings

### R1 — High: opening Time/Capacity can still block on a full background legacy-cache conversion

Affected files:
- `backend/app/services/cache.py`
- `backend/app/services/time_capacity_path.py`
- focused raw-layout/Time-Capacity concurrency tests

**Current**

050.3 starts every indexed plan with `cache.load_raw_layout_index()`. That function acquires `_raw_layout_io_lock` before deciding whether the sidecar is usable. `prepare_raw_layout()` also holds the same re-entrant lock while it reads the complete legacy Parquet, validates it, writes the candidate optimized Parquet, builds the index and publishes the pair.

Therefore, while the existing background scientific-preparation worker is converting a large legacy cache, a Time/Capacity request for that source does not immediately see "layout unavailable" and take the required legacy fallback. It waits behind the conversion lock until the complete conversion finishes. This makes the background full-cache conversion part of the plot request's critical path even though the request itself did not initiate the conversion.

That conflicts with the locked 050.2/050.3 lifecycle contract: a valid legacy raw cache must remain directly renderable via the old full-read path, and plot requests must not block on multi-hundred-MB layout preparation. It also recreates exactly the class of long, apparently unnecessary Time/Capacity waits Parent 050 is intended to remove during rollout/background preparation.

The current tests separately prove legacy fallback when no index exists and safe conversion publication, but they do not hold a conversion in progress and assert that `build_time_capacity_stitch_plan()`/`compute_time_capacity()` promptly chooses legacy access rather than waiting for conversion completion.

**Target**

A Time/Capacity request that encounters a source whose raw-layout conversion is currently in progress must take a bounded safe path immediately—normally the scientifically equivalent legacy full-read path—rather than waiting for the full conversion to complete. Preserve the indexed reader's raw/index consistency when a stable indexed pair is actually used.

Do not weaken cleanup/publication safety or allow an index to be paired with different raw bytes. The fix should distinguish "indexed pair stable and readable" from "layout currently preparing" at a cheap boundary before the request waits on the long conversion critical section.

**Acceptance criteria**

- A focused concurrency test holds/blocks `prepare_raw_layout()` during its expensive conversion phase, starts a Time/Capacity plan/request for the same valid legacy raw cache, and proves the request selects legacy access without waiting for conversion release.
- The request still returns the same scientific payload as the ordinary legacy path.
- Once conversion is complete, a subsequent request uses the indexed path normally.
- Indexed raw/index validation remains serialized strongly enough that a selective read never combines a stale sidecar with replacement raw bytes.
- No request-path source reparse or synchronous layout rewrite is introduced.
- Run focused cache/raw-layout/Time-Capacity tests and canonical preflight before handoff.

### R2 — Medium: range planning allocates every integer between unbounded request endpoints before intersecting the known cycle plan

Affected files:
- `backend/app/services/time_capacity_path.py`
- `tests/test_time_capacity_path.py`

**Current**

`requested_global_cycles()` derives the valid dense globals from the compact plan, but for range mode it returns `tuple(range(lower, upper + 1))` using the request's `cycle_start`/`cycle_end` directly. `time_capacity_settings()` does not clamp those values to the known Cell cycle range.

The old Time/Capacity path simply applied range predicates to an already loaded frame, so an out-of-range endpoint had bounded cost. The new planner can allocate an arbitrarily large Python tuple before it maps anything to actual source cycles. For example, a saved/direct request with `cycle_start=1` and `cycle_end=1_000_000_000` attempts to materialize roughly one billion integers even when the Cell has only a few hundred known global cycles.

This violates the lightweight-plan goal and the locked rule that requested globals outside the known chain simply produce no rows; out-of-range request values should not make memory/time scale with the distance to an invalid endpoint.

**Target**

Resolve range requests by intersecting/clamping against the known dense global cycles before materializing the requested set. Complexity should scale with the known chain/requested valid cycles, not with arbitrary numeric endpoint magnitude.

**Acceptance criteria**

- A range extending far above the known maximum selects only the known in-range cycles without constructing an enormous intermediate range.
- A range extending far below the known minimum is equally bounded.
- A wholly out-of-range request returns no cycles/rows.
- Normal ranges, explicit non-contiguous cycles and continuation-boundary mapping remain unchanged.
- Add focused regression coverage using deliberately extreme endpoints without large memory allocation.
