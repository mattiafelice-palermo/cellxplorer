## Findings

### R1 — High: request could wait for background raw-layout conversion — RESOLVED

**Current after `836ee0d`**

`cache.try_load_raw_layout_index()` acquires the raw/index consistency boundary only if immediately available. Time/Capacity chooses the scientifically equivalent legacy reader while conversion is busy. `load_raw_cycles(..., wait_for_layout=False)` closes the race where conversion begins after indexed planning. Blocking readers retain the serialized validation boundary.

**Acceptance evidence**

The added threaded regression blocks layout conversion, proves the Time/Capacity access path completes through legacy data before conversion is released, and confirms a subsequent request uses the indexed path after conversion completes. This satisfies the original R1 acceptance criteria without weakening atomic publication/index consistency.

### R2 — Medium: range planning could allocate an endpoint-sized tuple — RESOLVED

**Current after `836ee0d`**

`requested_global_cycles()` now clamps request endpoints to the known dense global-cycle minimum/maximum before materializing the tuple. Extreme upper/lower endpoints and wholly out-of-range cases have focused regression coverage.

**Acceptance evidence**

The new tests use endpoints of magnitude `10**100` and return only the bounded known cycles or an empty result, so work no longer scales with arbitrary numeric endpoint distance.

The implementation evidence does not justify a reserved 050.4 child. Narrow requests remove whole-source materialization; the all-cycle path necessarily reads/transforms exact detail, and no distinct remaining backend cache/prefetch bottleneck was demonstrated.
