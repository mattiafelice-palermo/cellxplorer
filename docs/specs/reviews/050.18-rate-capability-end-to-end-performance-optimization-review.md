## Review summary

050.18 is **not yet review-clean**, but the remaining blocker is an evidence/closure defect rather than a demonstrated scientific or runtime-code defect.

The production change is directionally and structurally strong. The request-local `_ExecutionIndex` replaces repeated full-frame measurement/phase scans with bounded row-position ownership, preserves the existing `_ordered()` boundary, reuses numeric arrays for voltage/capacity/current, and keeps the optimization strictly request-local. `compute()` builds one index per loaded raw source and reuses protocol reconstruction only for identical JSON header metadata plus nominal capacity. Exact persisted-result hits remain above this code path, so the new index is not constructed on a clean hit.

The implementer reports a six-Cell forced-miss p50 reduction from the locked **1267.82 ms** baseline to **158.77 ms** (155.77–162.16 ms), with a one-Cell miss of **48.34 ms** and exact-hit measurements of **9.02/12.25 ms**. That is approximately an **87.5% six-Cell latency reduction**, far beyond the 25% minimum promotion bar.

However, Spec 050.18 deliberately requires more than a fast headline number: it requires evidence that the **whole meaningful Rate Capability path** was re-profiled after the dominant scan removal and that every remaining material cost was optimized, experimentally rejected, or explicitly left alone for a measured reason. The handoff says the detailed benchmark JSON remains untracked under `tmp/`, while neither the spec nor another durable repository record contains the final stage table, route shares, SQL/serialization evidence, retained-tranche deltas, rejected candidates, or the final execution-parent residual. Therefore the reviewer cannot verify the mandated stop condition from the branch itself.

No new migration, persistent cache, result-schema, parser-identity, `CALC_VERSION`, worker/concurrency, or Time/Capacity change is present in the implementation commit.

## Findings

### R1 — Medium: final whole-family optimization evidence is not durable, so the mandated stop condition cannot be reviewed

Affected files/evidence:

- `docs/specs/050.18-rate-capability-end-to-end-performance-optimization.md`
- `docs/specs/050-agent-coordination.md`
- untracked `tmp/` Rate-only benchmark JSON reported by the implementer
- `scripts/profile_analysis_families.py` output as the source of the missing measurements

**Current**

The handoff records the headline complete-route timings and describes the two retained mechanisms: request-local execution indexing/numeric reuse and protocol-reconstruction reuse. It does **not** durably record the final post-optimization opportunity inventory required by sections 5, 11, 12, and 15 of the spec.

In particular, the branch does not currently preserve:

- final per-stage p50/share for the complete six-Cell route;
- final `execution_extraction` child sum and direct residual;
- the measured cost of `execution_index_building`;
- request/context/key, raw materialization, protocol reconstruction, rate-pair, sweep, candidate/common-comparison, invalid-neighbour, result assembly, cache persistence, and JSON serialization costs after optimization;
- SQL statement/time evidence;
- response bytes and structural execution counts;
- profiler overhead control;
- measured route deltas for each retained tranche rather than only baseline→final;
- which secondary candidates were inspected/rejected after tranche A, and why no further production work was warranted.

The detailed JSON containing at least some of this information is explicitly reported as untracked under `tmp/`. Because 050.18 was authored to prevent stopping after the first dominant optimization, the reviewer cannot infer completion solely from the excellent final latency.

**Target**

Make the final Rate Capability optimization decision reproducible from durable repository evidence without tracking disposable benchmark JSON. Add a concise implementation/evidence record to the 050.18 spec (or another canonical tracked document referenced by it) that summarizes the final profiler output and the tranche-by-tranche decision history.

No production-code change is requested by this finding unless the recovered final profile itself reveals another material unexplained cost.

**Acceptance criteria**

- Record the implementation commit and final Rate-only benchmark environment/workload identity.
- Record baseline and final 1-Cell miss, 6-Cell miss p50/min/max, and exact-hit p50.
- Record the final six-Cell per-stage p50/share for all materially relevant Rate stages, including `execution_index_building`, `execution_extraction`, its non-overlapping children/direct residual, raw materialization, protocol reconstruction, downstream sweep/selection/comparison/validation, cache persistence, serialization, and complete route.
- Record SQL statement count/time, response bytes, structural execution counts, and profiler overhead required by the spec.
- Record each retained optimization tranche with its measured complete-route delta.
- Record secondary candidates that were re-profiled and rejected/deferred, with the measured reason for stopping.
- Explicitly state whether any remaining stage still crosses the spec’s materiality heuristic (~5% of six-Cell miss or ~10 ms p50, including related combined work). If one does, either optimize/test it or document a concrete scientific/complexity reason not to.
- Preserve the reported scientific digest/order/provenance parity and clean exact-hit evidence.
- If the current temporary JSON still exists and is trustworthy, no benchmark rerun is required merely to satisfy R1; transcribe its relevant results. If it is no longer available, rerun only the Rate Capability benchmark needed to reconstruct the evidence.
