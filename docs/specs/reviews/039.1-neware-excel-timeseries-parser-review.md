## Findings

### R1 — Medium: Required time-reset-only execution-boundary regression is missing

Affected files:
- `tests/test_neware_excel.py`

**Current**

The production algorithm correctly includes the locked boundary rule:

```text
same cycle + same step_index + same status + time_s decreases → new executed step
```

However, the committed synthetic fixture does not isolate that rule. Its repeated cycle-1 programmed step `step_index == 2` is separated by a `Rest` execution with a different programmed step/status. Therefore that test would still produce two executed step IDs if the `time_s`-decrease boundary were accidentally removed from production code.

Child 039.1 explicitly requires a regression where a repeated same-cycle/same-`step_index` execution is distinguished by the step-relative time reset itself. This matters scientifically because losing that boundary can merge distinct executions and corrupt per-step capacity/energy aggregation and later Steps analysis while the existing synthetic suite still passes.

**Target**

Add one focused synthetic regression that makes the time reset the only execution-boundary signal: consecutive records must keep the same cycle, programmed `step_index` and canonical status while `Time(min)` drops/reset and `Total Time(min)` remains monotonic. Assert that the records on the two sides of that reset receive distinct canonical `step` IDs.

No production-code change is requested unless the new regression exposes a defect.

**Acceptance criteria**

- A committed test contains consecutive records with identical cycle, `step_index` and status and a meaningful `time_s` decrease/reset.
- The test asserts two distinct, globally increasing canonical executed `step` IDs across that reset.
- The test would fail if the `time_s`-decrease clause were removed while the other three boundary clauses remained.
- `python -m unittest tests.test_neware_excel -v` passes after the regression is added.
- The 039.1 implementation record records the follow-up verification exactly.
