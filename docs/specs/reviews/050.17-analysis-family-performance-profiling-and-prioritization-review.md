## Findings

### R1 — High: dominant-stage selection can double-count overlapping nested timers and hide an unattributed scientific remainder

Affected files:
- `scripts/profile_analysis_families.py`
- `tests/test_profile_analysis_families.py`
- `docs/specs/050.17-analysis-family-performance-profiling-and-prioritization.md` implementation record

**Current**

The root reconciliation correctly avoids summing arbitrary nested helpers, but `_dominant_stage()` later estimates the direct scientific remainder by summing almost every named timer below `scientific_compute`. Those helpers are not guaranteed to be siblings. For example, a timed `stitch_cycles()` call can include separately timed cache/data-access helpers; both appear in `nested_stages_ms` under the same nominal parent. Subtracting both from the inclusive `scientific_compute` timer double-counts overlapping time.

The summarized common stage objects also assign `parent: None`, so the machine-readable output does not retain enough hierarchy to distinguish inclusive parents from descendants when choosing the dominant removable cost.

This can suppress the real unexplained scientific remainder and promote a smaller named child into the priority table even though 050.17 explicitly requires “more focused profiling” when the dominant remainder is unattributed.

**Target**

Use an actual non-overlapping hierarchy or exclusive timers for any stage that participates in dominant-cost selection. Compute the direct scientific remainder only from non-overlapping direct children of the same parent. If the corrected remainder exceeds every named child, mark that family unresolved and recommend focused profiling rather than an optimization.

**Acceptance criteria**

- The structured JSON preserves truthful parent/child relationships or exclusive timings for stages used in optimization attribution.
- No residual calculation subtracts both an inclusive helper and one of its descendants.
- Add a focused regression with intentionally overlapping parent/child timings proving the selector does not double-count them.
- Re-evaluate Cycles, Steps, DCIR and Chargeability dominant stages, shares, ceilings and next actions from the corrected attribution model.
- Any in-scope family whose corrected unexplained scientific remainder dominates is explicitly marked unresolved, per the spec.
- Rate Capability may keep its separate deep hierarchy, provided its own parent/child reconciliation satisfies R2.

### R2 — High: mandatory Rate Capability deep profile does not yet support the recommended execution-extraction optimization

Affected files:
- `backend/app/services/rate_capability.py`
- `scripts/profile_analysis_families.py`
- `tests/test_profile_analysis_families.py`
- `docs/specs/050.17-analysis-family-performance-profiling-and-prioritization.md` implementation record

**Current**

The six-Cell profile usefully attributes about 1.11 s of the roughly 1.30 s route to the inclusive `execution_extraction` parent, but the required decomposition inside that parent is incomplete:

- measurement-step filtering/grouping (`raw[step_index == ...]` plus `_execution_groups`) is not separately timed;
- `_phase_rows()` and `_reached_voltage()` are timed only by external profiler wrappers and are not surfaced as measured p50 values in the structured `rate_deep.stages_ms` summary;
- the implementation record reports capacity/current/rate child timings but omits the phase-row and cutoff timings;
- the implementation record does not quantify which execution substage grows most from one Cell to six Cells;
- it does not quantitatively answer whether repeated DataFrame scans/filtering are materially responsible relative to protocol reconstruction or other execution work.

The final recommendation nevertheless names repeated phase-row/cutoff work as the first optimization. That recommendation is plausible from code inspection, but 050.17 requires it to be traceable to measured substage evidence.

**Target**

Complete the Rate deep decomposition through the `execution_extraction` parent and explicitly answer all five section-12 questions. The structured Rate record and implementation report must quantify measurement filtering/grouping, phase-row filtering, cutoff validation, capacity/current/rate work, and the remaining execution-parent residual, then compare the relevant one-Cell and six-Cell substages before naming the first optimization.

**Acceptance criteria**

- `rate_deep` contains measured p50/call-count values for measurement-step filtering/grouping, `_phase_rows()`, `_reached_voltage()`, capacity extraction, current extraction and rate normalization.
- `execution_extraction` has a reconciled child sum and residual that do not double-count nested stages.
- The one-Cell and six-Cell Rate records support an explicit statement of which substage grows most in absolute time and/or factor.
- The implementation record explicitly answers whether repeated DataFrame filtering/scanning is materially responsible and distinguishes that from protocol reconstruction.
- The first Rate optimization recommendation and plausible complete-route ceiling are recomputed from the measured child/residual evidence rather than inferred from the inclusive parent alone.
- Focused tests assert actual required Rate deep fields/timers, not only descriptive strings saying they are “covered”.

### R3 — Medium: SQL/query evidence is collected and then discarded

Affected files:
- `scripts/profile_analysis_families.py`
- `tests/test_profile_analysis_families.py`

**Current**

Every instrumented route creates `time_capacity_profiling.SQLProfile(env.db)`, which counts SQL statements and cumulative SQL time, but the `finally` block calls `sql_profile.finish(None)`. `SQLProfile.finish()` only publishes its metrics when given a profile dictionary, so statement count, SQL time, statement-kind counts and source-header lazy-load count are discarded from every workload record.

This leaves the ORM/query-volume evidence absent even though the profiler already incurs the instrumentation and 050.17 asks for SQL/query count where applicable when explaining scaling and owner/context cost.

**Target**

Persist the request-local SQL metrics into each instrumented sample and summarize them in the workload JSON without query text or parameter values.

**Acceptance criteria**

- Each instrumented miss/hit sample records SQL statement count and cumulative SQL time, plus the existing bounded by-kind/header-load diagnostics where available.
- Workload summaries expose p50/count evidence without private SQL text or values.
- Focused tests prove the SQL profile is emitted and detached/restored after the request.
- The final five-family matrix records enough SQL evidence to judge whether ORM/query work is material for each family.

### R4 — Medium: focused tests do not exercise several profiler contracts explicitly required by 050.17

Affected files:
- `tests/test_profile_analysis_families.py`
- `scripts/profile_analysis_families.py`

**Current**

The eight new profiler tests mostly exercise summary/helper functions with synthetic dictionaries. In particular:

- the “all families” test calls `_summarize_samples()` with the same fabricated sample rather than exercising the real family route harness;
- the exact-hit test validates `_exact_hit_is_clean()` on fabricated metrics rather than proving a real profiled hit bypasses family scientific compute/raw access;
- the clone test verifies spec expansion but not relational/cache clone integrity;
- the Rate deep test checks descriptive `required_decomposition` strings rather than the actual required timers/counters.

The final profiler run is useful execution evidence, but section 16 separately requires focused regression tests for these contracts.

**Target**

Add bounded focused tests that exercise the real profiler boundaries sufficiently to guard the evidence model, while keeping preflight runtime appropriate. The amended family set is the five non-Time/Capacity families; no new Time/Capacity profiler test is required for acceptance.

**Acceptance criteria**

- Focused coverage exercises the profiling route/harness for each of Cycles, Steps, DCIR, Chargeability and Rate Capability sufficiently to prove the common workload schema comes from real route output.
- A real exact-hit profiling test proves family compute and raw reads are not entered.
- Clone-focused coverage proves the multi-Cell fixture has distinct relational SourceFiles/cache identities while preserving the intended scientific projection.
- Rate-focused coverage asserts the actual required deep stage/counter fields and reconciliation from R2.
- Patch/context cleanup after a real profiled request is covered so instrumentation cannot leak into later tests.
