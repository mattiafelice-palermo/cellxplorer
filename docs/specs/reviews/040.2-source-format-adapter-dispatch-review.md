### Generic `.xlsx` rejection is behaviorally unchanged

`parse_timeseries` dispatches by suffix through `_EXTENSION_FORMAT_ID` and deliberately does not call
`recognize_source`, so the structural rejection of an arbitrary workbook happens inside
`neware_excel.parse_timeseries` rather than at the facade. The reviewer initially flagged this as a
possible change in user-facing failure behavior, and resolved it by diff: the pre-refactor code
dispatched `.xlsx` to `neware_excel.parse_timeseries` with no facade-level structural check either.
The two versions are structurally identical on this path, so no behavioral difference is possible.
The unsupported-extension message is also byte-identical between versions, and
`read_header_metadata`'s `except Exception -> {"raw": {}, "error": ...}` contract — which
`ensure_supported_source_metadata` consumes to produce the user-facing rejection — is preserved.

The implementer's reasoning for skipping the facade check (a second `recognize_source` call would
open the workbook header twice) is consistent with the parent's locked bounded-import rule.

## Design decisions accepted

### `neware_binary.py` extraction declined

The spec permitted but did not require extracting a binary adapter module. The implementer declined
because `tests/test_parsing.py` and `tests/test_import_flow.py` patch `parsing._flatten`,
`parsing._read_ndax_metadata_flat` and `parsing.NewareNDA` as module attributes; extraction would
force rewriting those mock targets during a refactor whose entire purpose is behavior preservation.
Accepted. The spec's alternative — isolating binary internals behind private helpers while keeping
public functions format-neutral — is what landed (`_parse_neware_binary_timeseries`,
`_read_neware_binary_header_flat`), and `AGENTS.md`'s "the only direct NewareNDA integration" line
remains accurate.

### Static registry, not a plugin framework

One frozen `SourceFormatDescriptor` dataclass, two module-level instances, one
`_EXTENSION_FORMAT_ID` dict. No dynamic loading, no importlib discovery, no base-class hierarchy —
as the parent and child both require.

`SUPPORTED_NEWARE_SOURCE_EXTENSIONS` is now *derived* from the dispatch table rather than declared
separately. This is a genuine improvement: the extension policy and the dispatch decision can no
longer drift apart.

### `source_parser_family` deliberately not generalized

It retains its suffix-only implementation and its pre-existing `"binary"`/`"excel"` return values
rather than adopting the new `format_id` spelling. This is correct and the docstring explains why:
`scanner.ingest_path` calls it on a bare filename to block exact-hash relinking across parser
families, so it must not become content-dependent. Changing its return values would be out of scope
and safety-relevant. The guard is intact.

### Forward-looking API with no current consumer

`source_parser_descriptor()` is called by nothing in production. This is intended — the spec asks
this child to *expose* adapter identity for 040.3 to consume, while explicitly forbidding cache or
provenance changes here. Recorded so 040.3's reviewer confirms it gets wired up rather than
duplicated.

## Error-taxonomy follow-up (`8262f017`)

### Why this was reopened after approval

The initial review accepted the implementer's decision to skip `InvalidSourceFormatError` as "unused,
since the existing three-tier error taxonomy already covers every raise site." **That acceptance was
a reviewer error.** The spec's "Error taxonomy" section asks for a small format-neutral error layer;
the argument that it is unused holds with one adapter family and fails with three.

The user raised the question while asking where a non-conforming `.xlsx` error is thrown, which
surfaced the gap.

### What was already correct, and stays correct

Investigation confirmed the layering the user asked about was already right, and this follow-up did
not change it:

- the structural check runs *before* canonical mapping — `_parse_records` calls `_require_columns` as
  its first statement, so a non-conforming workbook fails before any row is mapped;
- the error originates in the adapter, not the canonical layer:
  `neware_excel.UnsupportedNewareExcelError` raised at `neware_excel.py:1433`, message
  "Not a recognized Neware Excel export: required record sheet is missing.";
- `read_header_metadata` reports the same message through its `{"raw": {}, "error": ...}` contract.

### The actual defect

`parsing.UnsupportedSourceFormatError` and `neware_excel`'s `NewareExcelError` tree were unrelated
classes. Nothing bit today because every caller catches bare `Exception` (`scanner.py` at ten sites,
`import_inspection.py:263`). With a third adapter, callers could not distinguish "this file is not a
valid export of format X" from "we have a bug in our mapping code" — two conditions needing opposite
handling.

### Resolution

`backend/app/services/source_format_errors.py` (imports nothing from `parsing` or `neware_excel`, so
no circular import):

```text
SourceFormatError(ValueError)
├── UnsupportedSourceFormatError
└── InvalidSourceFormatError
```

`NewareExcelError(ValueError)` is retained as the adapter-specific base, with each subclass
multiply-inheriting from the matching neutral type.

### Reviewer verification

The MRO was the risk — a diamond can fail to linearize, or linearize in an order that changes which
handler wins. Measured directly rather than accepted:

```text
UnsupportedNewareExcelError -> NewareExcelError -> UnsupportedSourceFormatError -> SourceFormatError -> ValueError -> ...
InvalidNewareExcelError     -> NewareExcelError -> InvalidSourceFormatError     -> SourceFormatError -> ValueError -> ...
```

This matches the correct C3 linearization. The reviewer then measured the full catchability matrix:

| raised | `NewareExcelError` | `SourceFormatError` | `UnsupportedSourceFormatError` | `InvalidSourceFormatError` | `(OSError, ValueError)` |
|---|---|---|---|---|---|
| `UnsupportedNewareExcelError` | Y | Y | Y | **N** | Y |
| `InvalidNewareExcelError` | Y | Y | **N** | Y | Y |
| `parsing.UnsupportedSourceFormatError` | **N** | Y | Y | **N** | Y |

The `N`s are the point: the taxonomy discriminates unsupported from invalid, and a non-Neware error
is not catchable as a Neware one. `except (OSError, ValueError)` — the exact shape at
`scanner.py:843` — still catches everything, so no existing handler changed behavior.

Also verified: `parsing.UnsupportedSourceFormatError is source_format_errors.UnsupportedSourceFormatError`
(one class, re-exported, not redefined); `issubclass(CanonicalCyclingError, SourceFormatError)` is
`False`, keeping adapter bugs outside the source-rejection hierarchy as intended; and the generic
`.xlsx` failure is byte-identical in both type name and message.

`python scripts\preflight.py` re-run by the reviewer: exit 0, 5/5.

The `canonical-cycling-data.md` adapter recipe gained a sixth step telling the `.mpr` author which
types to raise, including the circular-import constraint and an explicit warning not to fold
`CanonicalCyclingError` into the hierarchy. Each claim in it was checked against the code.
