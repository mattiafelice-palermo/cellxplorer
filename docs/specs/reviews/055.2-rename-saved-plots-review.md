## Confirmed by code inspection

### Rename persistence and metadata scope

`renameSavedPlotInList(...)` is keyed by stable saved-plot ID and returns a new list where only the matching plot receives a new trimmed `name` and `modified_at`. The target plot's ID, tab, selection, computation, aggregation, presentation/style and creation metadata remain unchanged; non-target plots remain untouched.

`AnalysisEditor.renameSavedPlot(...)` validates first, treats an unchanged trimmed name as a no-op, then routes the saved-plots metadata mutation through the editor's existing `update(...)`/autosave path. The implementation introduces no second display-name field and no schema/migration change.

### Dirty-state behavior

The saved-plot scientific dirty contract remains `plotViewSignature(spec)` versus `activePlotBaselineSignature`. `plotViewSignature(...)` serializes selection visibility, DCIR segments, computation, aggregation and presentation, but not `saved_plots` metadata. Therefore renaming the active plot does not enable its scientific `Update` action.

The existing persistence policy also preserves the intended mixed states:

- clean active saved plot + rename: autosave persists the renamed saved plot while the scientific signature stays clean;
- already-dirty active saved plot + rename: `buildStablePersistSpec(..., mode: "edited_saved")` restores the persisted saved view into the server-bound top-level workspace while retaining the renamed `saved_plots` metadata, so the rename persists without accidentally persisting the unsaved scientific edit;
- live draft + inactive saved-plot rename: draft-session persistence restores the normal top-level workspace while retaining the renamed saved-plot metadata, so the current draft is not converted into persisted scientific state.

A later explicit plot `Update` uses the current `activePlot.name`, so it does not regenerate/revert the custom saved name.

### Validation and modal behavior

The rename helper and modal enforce the locked name rules:

- trim leading/trailing whitespace;
- reject blank/whitespace-only values;
- cap names at 120 characters;
- allow duplicates;
- unchanged trimmed name is a no-op.

The modal uses Mantine `Modal` + labeled `TextInput`, pre-fills the current name, focuses/selects the input on open, submits through a form, provides Cancel, and relies on the modal's close behavior for Escape. The Rename submit button is disabled when validation fails.

### Export filename handling

The opened saved plot's stored name remains the export-facing identity:

- `activePlot` is resolved from `spec.saved_plots` by stable ID;
- `displayPlotName` uses `activePlot.name` for the active tab;
- all plot-family cards receive `displayPlotName` as `plotName`;
- `PlotHeader` places that `plotName` into the existing filename-template context as `plotTitle` and sanitizes the rendered filename through the existing export filename helper.

Unsaved/New plots keep the existing subtitle/generated-name fallback. The added `slugFilename(...)` test also confirms the custom saved name remains filesystem-safe under the existing sanitizer convention.

## Finding

### R1 — P2 — Nested Rename keyboard activation is intercepted by the saved-plot card

**Affected files**

- `frontend/src/features/analyses/editor/artifacts/SavedPlotsPanel.tsx`
- focused component/event test location as appropriate

**Current**

Each saved-plot row is a `Box role="button"` with a parent `onKeyDown` that handles every bubbled `Enter` or Space event by calling `onOpen(plot)`. The new Rename button is nested inside that row.

The mouse path correctly avoids this problem because `onMouseDownCapture` returns when the event target is inside a child `button`. The keyboard path has no equivalent guard. When keyboard focus is on Rename and the user presses Enter or Space, the event bubbles to the parent row, which calls `preventDefault()` and `onOpen(plot)`. Depending on the native button activation sequence, this can open the saved plot in addition to, or instead of, opening the rename modal.

For an inactive saved plot, that directly violates the locked requirement that rename must not disturb the current active plot or draft. It also violates the expected keyboard behavior of the Rename action itself.

**Target**

Child interactive controls must own their keyboard events. The saved-plot row's Enter/Space shortcut should open the plot only when the keyboard action originates from the row/non-interactive card surface, not from Rename/Delete or future nested interactive controls.

A minimal fix may mirror the existing mouse guard (for example, ignore key events whose target is within a child button) or use an equivalent robust interactive-descendant check. Do not remove keyboard open behavior from the card itself.

**Acceptance criteria**

1. With an inactive saved plot and another plot/draft active, keyboard-focus the Rename button.
2. Press Enter: the rename modal opens and the parent row does **not** call `onOpen`; active saved-plot/draft identity is unchanged.
3. Repeat with Space.
4. Enter on a valid name submits the rename exactly once without opening the plot as a side effect.
5. Escape and Cancel close the modal without mutation.
6. Keyboard activation of Delete likewise does not open the saved plot if the shared parent guard covers nested buttons generally.
7. Enter/Space on the saved-plot row itself still opens the plot.
8. Add focused regression coverage for the nested-control keyboard propagation behavior, using the existing component/event testing pattern if available.
9. Re-run the relevant focused frontend test(s) and `python scripts\\preflight.py --no-cache`.
