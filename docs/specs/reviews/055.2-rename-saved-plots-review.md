## R1 — RESOLVED — Nested Rename/Delete keyboard activation

### Previous defect

The saved-plot row is itself keyboard-openable. Its previous `onKeyDown` handled every bubbled Enter/Space event by calling `onOpen(plot)`, including events originating from nested Rename/Delete buttons. Keyboard activation of Rename could therefore open an inactive saved plot and disturb the current active plot/draft.

### Fix inspected

`SavedPlotsPanel.tsx` now determines whether the keyboard event originated in a nested button:

```ts
const originatedInNestedButton =
  event.target instanceof HTMLElement && event.target.closest("button") !== null;
```

It then delegates the card shortcut decision to `shouldOpenSavedPlotCardFromKey(...)`.

The policy returns true only for Enter/Space when `originatedInNestedControl === false`. Therefore:

- Enter/Space with focus on the saved-plot row still calls `onOpen(plot)`;
- Enter/Space with focus on Rename does not invoke the parent row's open shortcut;
- Enter/Space with focus on Delete likewise does not invoke the parent row's open shortcut;
- other keys do not open the row.

For keyboard events dispatched from a focused Mantine button, the event target is the button element, so the generic nested-button guard applies to both actions without special-casing Rename.

### Focused regression coverage

`frontend/tests/analysisPlotPolicy.test.ts` adds direct coverage for the extracted keyboard policy:

- Enter on row surface → open;
- Space on row surface → open;
- non-activation key → no open;
- Enter from nested control → no parent open;
- Space from nested control → no parent open.

The repository frontend does not currently include a React Testing Library/component-test dependency; the extracted pure-policy regression therefore matches the existing lightweight Node-test pattern rather than introducing a new test framework for this narrow event rule.
