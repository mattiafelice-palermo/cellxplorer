## Findings

### R1 — High: Missing `test` sheet is treated as a metadata failure instead of capability degradation

Affected files:
- `backend/app/services/neware_excel.py`
- `tests/test_neware_excel.py`

**Current**

`read_metadata()` calls `_sheet_by_name(workbook, "test", required=True)` and then requires a Step plan marker/header. Therefore a structurally valid Neware workbook with a usable canonical `record` sheet but no `test` sheet cannot return bounded metadata/capabilities; `parsing.read_header_metadata()` catches the exception and degrades all metadata to `{"raw": {}, "error": ...}`.

Parent 039 explicitly classifies missing declared-protocol metadata as a warning/capability-degradation case, not as a raw-scientific parse failure. Child 039.2 likewise defines explicit `DeclaredProtocol`/`ProtocolConditions` capabilities so downstream logic can fail closed without inventing protocol semantics.

**Target**

Allow bounded Excel metadata acquisition when `test` is absent. Return the source-format/capability structure with `DeclaredProtocol=false` and `ProtocolConditions=false`, retain any independently available bounded `unit` metadata, and omit rather than invent Neware-compatible Step/Head fields that require the missing sheet. `parse_timeseries()` must remain independently governed by the required `record` contract.

**Acceptance criteria**

- A synthetic workbook with valid `record` and no `test` sheet still has `parse_timeseries()` succeed.
- `read_metadata()` / `parsing.read_header_metadata()` return `source_format="Neware Excel"` and explicit capabilities with `DeclaredProtocol=false` rather than an all-empty metadata error.
- No programmed steps, conditions, nominal capacity, mass or protection values are fabricated from missing data.
- Chargeability remains unavailable/fail-closed because conditions are absent.
- Existing real-workbook metadata/protocol behavior remains unchanged.

### R2 — Medium: Step-summary timing validation still uses observed median timestamp cadence instead of the locked declared-interval/2-second rule

Affected files:
- `backend/app/services/neware_excel.py`
- `tests/test_neware_excel.py`

**Current**

The 039.1 `_step_time_tolerance_seconds(frame)` path remains unchanged in 039.2: it computes the median positive timestamp difference over the raw frame and uses `max(2 s, median observed interval)`. The committed regression even accepts a 63-second step summary for a 60-second raw step because the observed cadence is 60 seconds.

The locked rule is `max(2 seconds, declared record_interval_s)`; Child 039.1 explicitly says to use 2 seconds when the declared interval is not yet available, and Child 039.2 is the stage that may route the now-parsed declared record interval into the same validation helper. Using arbitrary observed gaps can make the reconciliation dramatically too permissive for sparse/irregular records and allow an invalid `step` summary to validate.

**Target**

Make step-summary timing reconciliation use the declared record interval when available from the 039.2 metadata/test-plan contract and otherwise use exactly the 2-second floor. Do not infer the tolerance from median timestamp gaps.

**Acceptance criteria**

- With declared record interval `N`, onset/end/duration tolerance is `max(2, N)` seconds.
- Without a declared interval, tolerance is 2 seconds.
- A synthetic sparse timestamp gap larger than the declared interval does not expand the tolerance.
- Replace/update the existing regression that currently validates the 60-second inferred-cadence behavior.
- The supplied workbook still validates its 201 step executions.

### R3 — Medium: Required `Date` values accept arbitrary numerics as nanosecond timestamps

Affected files:
- `backend/app/services/neware_excel.py`
- `tests/test_neware_excel.py`

**Current**

The canonical-record `_timestamp()` and metadata `_metadata_timestamp()` helpers pass arbitrary values directly to `pd.Timestamp`. Pandas interprets a plain integer/float as nanoseconds from the Unix epoch rather than rejecting it as a malformed Neware date. Thus a non-date numeric cell can silently become a valid-looking `datetime64[ns]` value, contrary to the child’s strict/fail-closed timestamp contract.

In a correctly date-formatted Excel cell, `openpyxl` already returns a Python datetime/date-like value; accepting unrelated bare numerics is therefore not required for the verified workbook contract.

**Target**

Restrict timestamp conversion to the verified date-like/string forms and reject arbitrary bare numerics/bools. Preserve valid openpyxl datetime values and the verified textual form without adding timezone semantics.

**Acceptance criteria**

- A numeric `record.Date` cell such as `123` fails with `InvalidNewareExcelError` identifying the Date field.
- A numeric metadata Start time likewise fails rather than becoming a 1970-era nanosecond timestamp.
- Valid openpyxl datetime values and verified date strings still parse to naive timestamps.
- Existing duplicate-timestamp behavior remains unchanged.
