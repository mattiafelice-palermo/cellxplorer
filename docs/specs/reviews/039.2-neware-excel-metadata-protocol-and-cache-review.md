## Findings

### R6 — High: Excel parser revision was not advanced after canonical parser/metadata semantics changed

Affected files:
- `backend/app/services/neware_excel.py`
- `backend/app/services/parsing.py` (derived bundle identity; normally no logic change beyond the revision input)
- `tests/test_neware_excel.py`
- golden expected provenance files that intentionally store the current global `parser_version`
- `docs/specs/039.2-neware-excel-metadata-protocol-and-cache.md`

**Current**

`EXCEL_PARSER_REVISION` is still `1`, so the global bundle remains `v2026.06.11-cxp1`. That same identity was already in use before the R1–R4 production fixes changed accepted Excel inputs and normalized/raw semantics:

- R1 changed normalized metadata behavior for record-valid workbooks without `test` metadata;
- R2 tightened step-summary reconciliation and therefore which execution mappings are accepted;
- R3 changed canonical raw timestamp validation, rejecting numeric Date cells that the previous parser could cache as 1970-era timestamps;
- R4 changed source-format recognition at the metadata seam.

Child 039.2 explicitly locks the rule that `EXCEL_PARSER_REVISION` increments whenever canonical Excel raw or normalized metadata/protocol meaning changes. This is also operationally important: `cache.build()` returns an existing raw/cycle cache immediately when files already exist at the current parser/calc version, and a current raw cache can be reused without reopening the source. Therefore a cache produced by the pre-fix `cxp1` implementation can remain addressable as current `cxp1` after the stricter code is installed, bypassing the new validation semantics and misrepresenting provenance.

**Target**

Advance the Excel parser revision for the final 039.2 semantics and let the existing bundle formula produce a new parser identity. Do not change `CALC_VERSION`. Preserve old parser-version caches as historical/reproducible artifacts; the new identity should simply prevent them from being treated as current.

**Acceptance criteria**

- `EXCEL_PARSER_REVISION` is advanced from `1` to a new current revision (a single increment for the current reviewed semantic state is sufficient; do not encode every intermediate review commit).
- `parsing.PARSER_VERSION` deterministically changes with it and remains within `SourceFile.parser_version`'s 30-character limit.
- Existing current-version Excel raw/cycle cache paths therefore change, preventing pre-fix `cxp1` caches from being reused as current output.
- Golden expected files are updated **only** for the intentional parser-version provenance field; no numerical golden output is refreshed or changed to hide drift.
- Existing binary numerical parser output remains unchanged despite the intentional global bundle/provenance identity change.
- `CALC_VERSION` remains `1.6.1`.
- Focused version/cache tests and the golden regression/preflight path pass after the bump.

### R7 — Medium: Optional metadata values can bleed into the next label/value group

Affected files:
- `backend/app/services/neware_excel.py`
- `tests/test_neware_excel.py`

**Current**

The verified `test` information layout is organized as independent label/value groups approximately `A/C`, `D/F` and `G/I`. `_find_labeled_value()` finds a label and then scans **every remaining cell to the right** until it finds the first non-blank value.

That means a legitimately missing optional value can be replaced by the next group's label or value. For example, in a row shaped like:

```text
A: Start step ID | C: <blank> | D: Volt. upper | F: 4.2V
```

looking up `Start step ID` walks past its blank value slot and returns `"Volt. upper"`. `_integer_value()` then rejects that text, turning a missing optional field into a metadata failure. The same helper is also used for optional `unit`-sheet timestamps, so a blank value can similarly bleed into a later label group.

Child 039.2 requires parsing the observed A/C, D/F, G/I-style label/value positions and distinguishes optional metadata missing from corrupt/invalid metadata. Scanning across independent groups violates that contract and can make otherwise usable structured Neware workbooks fail metadata extraction.

**Target**

Bind each recognized label to its verified value slot/group and never search through a subsequent metadata label group. A missing value should remain missing (`None`) unless the workbook actually supplies a value in that label's supported position.

**Acceptance criteria**

- A synthetic `test` row with `Start step ID` present, its own value blank, and `Volt. upper` populated in the next group returns `start_step_id=None` while still parsing the protection voltage correctly.
- Equivalent coverage exists for a middle or later optional metadata group so the fix is not special-cased to one label.
- Optional `unit`-sheet Start/End time extraction cannot consume the neighboring label when its own value is blank.
- Existing verified workbook metadata values remain unchanged.
- The parser still uses deterministic verified positions; no fuzzy or arbitrary row-wide value guessing is introduced.
