## Findings

### R4 — High: The metadata seam now labels arbitrary `.xlsx` workbooks as Neware Excel

Affected files:
- `backend/app/services/neware_excel.py`
- `tests/test_neware_excel.py`

**Current**

The R1 fix changed `read_metadata()` so `test` is optional, but `read_metadata()` does not first prove the required Neware `record` contract. A workbook with suffix `.xlsx` and no `test`, `record`, `unit`, `cycle` or `step` sheets therefore returns a valid metadata tree containing:

```text
Excel.SourceFormat.Value = neware_excel
DeclaredProtocol = false
ProtocolConditions = false
```

`parsing.read_header_metadata()` consequently reports `source_format="Neware Excel"` instead of returning a parser-domain recognition error. This bypasses the existing `is_supported_workbook()` boundary and conflicts with Parent 039's locked decision that support is for structured Neware Excel only. It also pushes format-recognition semantics into the later import layer even though `neware_excel.py` is the source-format owner.

**Target**

Keep missing optional/declared-protocol metadata degradable, but require the cheap supported-workbook `record` identity before `read_metadata()` returns Neware source metadata. This must remain header-only/bounded: validate the `record` sheet name and required header row without scanning point rows.

**Acceptance criteria**

- A generic workbook such as `Workbook()` with only the default `Sheet` causes `neware_excel.read_metadata()` to raise `UnsupportedNewareExcelError` (or the equivalent existing parser-domain unsupported error).
- `parsing.read_header_metadata()` on that unrelated `.xlsx` returns the normal metadata error shape, not `source_format="Neware Excel"`.
- A valid Neware-shaped workbook with the required `record` contract but no `test` sheet still satisfies resolved R1 and returns `DeclaredProtocol=false`.
- Recognition performs only sheet/header inspection and does not iterate the full `record` dataset.
- Existing real-workbook metadata behavior remains unchanged.

### R5 — Medium: The explicitly required three-rate Rate Capability compatibility regression is missing

Affected files:
- `tests/test_neware_excel.py`
- optionally the closest existing rate/protocol test owner if that is cleaner

**Current**

Child 039.2 explicitly requires a focused protocol-level regression using a synthetic Excel plan with **at least three declared rates** and proving that Excel-derived protocol mapping produces the normalized fields consumed by the existing Rate Capability service: direction, declared C-rate, programmed step number, operational cutoff and relevant structural/signature context.

The committed Excel protocol fixture contains only the 0.5C and 1C levels, and the 039.2 tests do not run a three-rate Excel-derived protocol through the Rate Capability-facing normalization/pairing seam. The general protocol mapping tests and future 039.4 analysis regression do not satisfy this child-specific locked verification requirement.

**Target**

Add the narrow three-rate protocol regression required by 039.2 without expanding into the full Rate Capability UI/API matrix reserved for 039.4.

**Acceptance criteria**

- A synthetic Excel `test` plan contains at least three distinct declared rates.
- The test obtains protocol data through the Excel metadata → shared flatten/reconstruct path rather than constructing the final protocol object by hand.
- It asserts the Rate Capability-relevant normalized values for the varied steps: programmed step number, direction, C-rate, operational cutoff and any structural field required by the current service seam.
- The test fails if Excel C-rate/step/cutoff mapping drifts while generic binary protocol tests still pass.
- No Rate Capability scientific formula or detector behavior is changed.
