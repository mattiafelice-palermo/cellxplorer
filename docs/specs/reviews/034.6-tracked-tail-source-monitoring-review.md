## Locked correction before implementation

A Cell has one ordered source chain and one tracked tail: its final source. `Test` is an internal
compatibility row only. Monitoring must never select one tail per Test or describe Test-level roles.

The first implementation already normally selects one final source per Cell. Preserve that result,
but simplify all definitions, guards, tests, and copy to the Cell chain.

## Confirmed useful work to preserve

- Explicit `all_ordered_sources` and `tracked_tails` scopes.
- Scheduled monitoring requests tracked tails.
- Manual checks retain the all-source scope.
- Job snapshots capture source identity and scope.
- Scheduled retries use captured items.
- Activity distinguishes current-source checks from all-source checks.
- Tail selection is eager-loaded rather than N+1.

## Required changes

### R1 — High: incompatible source-check requests silently coalesce

**Affected files**

- `backend/app/routers/library.py`
- `tests/test_source_monitor.py`
- `tests/test_source_and_replicates.py`

**Current**

`start_source_check_job` can return the latest running job before verifying that the new request has
the same immutable selection and execution contract. A manual all-source check can therefore be
represented by a running scheduled tail-only job, and a manual update can modify the semantics of
that job.

**Target**

Coalesce only compatible contracts. At minimum compare:

- `source_scope`;
- normalized Cell IDs;
- `include_complete`;
- scan mode;
- check-only versus update behavior;
- stability/retry settings that affect execution.

Incompatible requests must queue/start separately or return a clear already-running response with
the actual current scope. Never upgrade or relabel an existing job.

**Acceptance criteria**

- Manual all-source check during scheduled tail check is not treated as fulfilled by the tail job.
- Manual check-and-update cannot upgrade a scheduled tail-only job.
- Scheduled request during a manual job does not alter the manual job.
- Identical same-scope requests still coalesce intentionally.
- Snapshots remain immutable and accurate.
- Tests cover both request orderings and check/update combinations.

---

### R2 — High: scheduled adoption can update a source that became historical or stale

**Affected files**

- `backend/app/routers/library.py`
- `tests/test_source_monitor.py`
- `tests/test_source_and_replicates.py`
- continuation/source-monitor integration tests

**Current**

The final adoption guard mainly checks whether the SourceFile remains attached, with Test ID used as
part of the check. It does not fully prove that the source is still the final file in the Cell chain
or that its registered identity is unchanged since job start.

**Target**

Before automatic adoption from a `tracked_tails` job, require:

1. source remains attached to the captured Cell;
2. source is still the final source in the Cell’s current ordered chain;
3. current registered hash equals the captured registered hash;
4. final stable physical signature matches the checked source state.

Internal Test ID may be logged for compatibility diagnostics, but it is not the scientific role
check. If any condition fails, skip adoption and report: detached, became historical, registered
identity changed, or source changed again.

**Acceptance criteria**

- Reorder captured tail to an earlier Cell position: zero adoption.
- Detach captured tail: zero adoption with detached reason.
- Manual update before scheduled adoption: stale job cannot overwrite it.
- Unchanged final source adopts normally.
- Activity/job metadata distinguishes historical and stale-snapshot skips.
- Tests assert database state and result metadata.

---

### R3 — Medium: monitoring documentation and user-visible metadata still encode Test roles

**Affected files**

- `backend/app/routers/library.py`
- `backend/app/services/source_monitor.py`
- `frontend/src/api.ts` if Test fields are exposed
- source-monitor tests
- architecture knowledge documentation

**Current**

Job items and documentation describe Test IDs/positions and define the tail through final non-empty
Test order. That preserves the obsolete multiple-Test product model even when the selected source is
correct.

**Target**

- Define source order and tail at Cell level.
- User-visible activity and API copy must not mention Test.
- Job metadata may retain an internal compatibility Test ID only when needed for debugging; clients
  must not use it to calculate role.
- The selected result is one final source per Cell, never one per Test.

**Acceptance criteria**

- No user-visible Test wording in source-check activity.
- Tail tests construct one Cell chain with several sources and assert one selected item.
- Adding internal Test rows in a defensive legacy fixture does not produce multiple monitored tails.
- Architecture documentation matches the one-chain rule.

## Implementation record — corrected review

and pushed to `origin`.

  the architecture knowledge base to document the Cell-level contract and defensive legacy behavior.
