## Assessment

The normal scheduled-selection path now identifies one final source per active Cell, records the
scope in the job snapshot and keeps manual operations on the all-source default. Two concurrency
holes remain: incompatible source-check requests can silently share one running job, and a source
captured as the tracked tail can still be automatically adopted after it becomes historical or its
registered identity changes.

Both findings are correctness blockers because they can make an explicit manual integrity action
inspect only a subset of sources or allow scheduled automation to modify a source that is no longer
the Cell's monitored tail.

## Confirmed correct by code reading

- The internal selector has explicit `all_ordered_sources` and `tracked_tails` scopes.
- Normal scheduled monitoring requests `tracked_tails` explicitly.
- Manual check and manual check-and-update routes retain the all-source default.
- Tail selection uses Tests ordered by `Test.id` and source links by position.
- A trailing empty Test does not contribute a tail.
- Complete Cells remain excluded by default.
- Job snapshots capture source IDs, paths, hashes, Cell/Test IDs and positions.
- Scheduled retries operate on the captured job items rather than reselecting the current tail.
- Activity and background-job descriptions distinguish current-source checks from all-source checks.
- Source selection is eager-loaded rather than issuing one query per source.
- No persistent schema or migration change is introduced by this child.

## Follow-up tasks

### R1 — High: incompatible source-check requests silently coalesce into one running job

**Parent review mapping:** R5

**Affected files**

- `backend/app/routers/library.py`
- `tests/test_source_monitor.py`
- `tests/test_source_and_replicates.py`

**Current**

`start_source_check_job` returns the latest running job before checking whether the new request has
the same immutable selection and execution contract.

Examples:

- a manual all-source check started during a scheduled tail-only check receives the scheduled
  tail-only job as though the manual request had been fulfilled;
- a manual check-and-update can set `update_after_check = true` on an already-running scheduled
  tail-only job;
- requested Cell IDs, `include_complete`, scan mode, source scope, retry and stability behavior are
  not compared before coalescing.

An explicit manual integrity operation can therefore silently inspect or update only one source per
Cell instead of every ordered source.

**Target**

Coalesce only requests with compatible immutable job contracts.

At minimum compare:

- `source_scope`;
- normalized requested Cell IDs;
- `include_complete`;
- scan mode;
- check-only versus update semantics;
- stability/retry settings when they affect execution and deadlines.

For incompatible requests, choose the smallest deterministic behavior that fits the existing
architecture:

- queue/start the request after the current job; or
- reject it with a clear already-running response that reports the current scope.

Do not silently return an incompatible job, and never upgrade a scheduled tail-only job to a manual
all-source update.

**Acceptance criteria**

- Manual all-source check during scheduled tail check is not treated as fulfilled by the tail job.
- Manual check-and-update cannot upgrade a scheduled tail-only job.
- Scheduled tail request during a manual all-source job does not alter or relabel the manual job.
- Identical same-scope requests retain intentional coalescing.
- Job snapshot fields remain immutable and describe the actual work performed.
- Tests cover both request orderings and update/check-only combinations.

### R2 — High: scheduled adoption can update a source that became historical or stale

**Parent review mapping:** R6

**Affected files**

- `backend/app/routers/library.py`
- `tests/test_source_monitor.py`
- `tests/test_source_and_replicates.py`
- continuation/source-monitor integration tests

**Current**

Before scheduled automatic adoption, `_source_still_attached` verifies only that the SourceFile
still has a TestFile link and, when captured, the Test ID still matches.

It does not verify that the source:

- remains the Cell-wide tracked tail;
- remains in the captured Cell and logical role;
- still has the registered hash captured when the job started.

If the user reorders the same Test while the scheduled job is running, the old tail can become
historical while remaining linked to the same Test. The scheduled job can still adopt it. A
concurrent manual source update can also change the registered hash while the old job continues from
its stale snapshot.

**Target**

Before adopting a changed source from a `tracked_tails` job, validate the captured snapshot against
current persistent state.

Require all of the following:

1. the source remains attached to the captured Cell and Test;
2. it is still the final source of the final non-empty Test;
3. its current registered hash equals the job's captured registered hash;
4. the stable physical signature still matches the check result used for adoption.

If any condition fails, skip adoption and record a specific reason such as:

- detached;
- became historical;
- moved to another Test/Cell;
- registered identity changed;
- source changed again during the final stable read.

The job may finish checking the captured file, but it must not adopt obsolete work.

**Acceptance criteria**

- Reorder a captured tail to historical during a scheduled job: zero adoption.
- Detach a captured tail: zero adoption with detached-skip reporting.
- Manually update the captured source before scheduled adoption: the stale job cannot overwrite the
  newer registered state.
- Move or relink the source to a different Test/Cell: zero adoption.
- An unchanged captured tail adopts normally.
- Activity and background-job data distinguish detached, historical and stale-snapshot skips.
- Tests assert both database state and job/activity result metadata.
