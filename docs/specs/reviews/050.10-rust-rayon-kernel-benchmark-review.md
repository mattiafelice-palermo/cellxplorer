## Open finding

### R7 — Medium — do not treat four Rayon workers as the ceiling when the benchmark host can support eight

**Affected files**

- `scripts/profile_rust_derivative_kernel.py`;
- `scripts/rust_derivative_kernel/src/main.rs`;
- `docs/specs/050.10-rust-rayon-kernel-benchmark.md`.

**Current**

The benchmark protocol and Rust worker accept only 1, 2 or 4 Rayon workers. That was the original locked matrix, but the user has explicitly amended the requirement: an eight-worker candidate should not be discarded without measurement when the machine exposes enough CPU capacity.

The existing 10/11-Cell workloads are precisely where an eight-worker pool could still provide useful cross-Cell concurrency. Four workers are already clearly better than two for broad derivative and Time kernels in many rows, so the available evidence does not establish saturation at four.

This is a benchmark question only. It does not mean production must use eight workers, and it must not silently use all logical CPUs.

**Target**

Add one explicit **8-worker Rayon candidate** when the benchmark host reports at least eight usable logical CPUs. Keep the same one-coarse-request, deterministic, scientifically identical native boundary. Compare 8 workers against the accepted 4-worker result rather than rerunning unnecessary losing configurations.

The eight-worker experiment should answer whether the additional threads materially reduce broad multi-Cell native work after accounting for CPU saturation, boundary cost, memory and small-request behavior.

If the benchmark host exposes fewer than eight logical CPUs, record the candidate as `NOT RUN` with the detected CPU count and reason; do not oversubscribe merely to satisfy the matrix.

**Acceptance criteria**

- Record the host logical CPU count used for the eligibility decision.
- If `os.cpu_count()` (or an equivalent bounded host-capacity check) is at least 8, allow a Rust/Rayon pool of exactly 8 workers and benchmark it.
- Run the 8-worker candidate on the discriminating broad cases, at minimum:
  - derivative 6 Cells;
  - derivative 10 Cells where available;
  - ordinary Time 6 Cells;
  - ordinary Time 10 Cells and 11 Cells where available.
- Report 8-vs-4 isolated kernel change and complete Python/native boundary change separately. Do not attribute boundary-copy savings to Rayon.
- Record CPU/effective-core evidence, peak/resident memory and scientific/order parity.
- Run one **persistent eight-worker** session or equivalent warm check that keeps the process/pool resident and includes one-Cell/small derivative and ordinary Time requests, so any idle-memory or small-request penalty versus the accepted persistent four-worker model is visible.
- Preserve one-time startup/pool initialization outside measured warm interactions.
- Select eight workers only if it gives a material, stable net advantage on representative broad work without an unacceptable small-request/memory penalty. Otherwise retain four as the recommended bound.
- Do not test unbounded/all-CPU Rayon as a production recommendation.
- Update the durable 050.10 decision to state explicitly whether 4 or 8 is the largest justified persistent bound on the measured host.
- No production native integration, lifecycle supervisor, cache/migration/scientific-version change or 050.11 composition work in this fix.
- Focused Rust/Python checks, parity verification and canonical `python scripts\preflight.py` pass before handoff.

## Reviewer assessment of current results

Before R7, the substantive 050.10 conclusions are already clear:

1. **Derivative:** sequential Rust is dramatically faster than the current Python/pandas/NumPy derivative kernel; broad multi-Cell Rayon adds substantial scaling on top.
2. **Ordinary Time:** current vectorized NumPy is already efficient; sequential Rust gives only a modest additional gain, but cross-Cell Rayon still materially reduces the isolated native projection on broad batches.
3. **Capacity projection:** native execution is not independently justified because the numeric work is already tiny and boundary cost dominates.
4. **Lifecycle:** a persistent warm native service is the right steady-state model. Per-interaction process/pool creation is rejected by evidence and by the user-directed architecture.
5. **Boundary:** the disposable subprocess-copy protocol is currently much more expensive than the normal projection kernel, so 050.11 must reason about the whole composed boundary rather than equating isolated kernel speedup with backend speedup.

R7 only determines whether the persistent bounded pool should stop at four workers or whether eight is measurably superior on the available host. Once answered, 050.10 can close and 050.11 can remain focused on composition/architecture selection.
