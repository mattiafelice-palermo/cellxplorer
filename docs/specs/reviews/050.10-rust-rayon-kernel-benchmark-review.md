### R4 — substantially resolved; one attribution defect remains as R6

The requested Rust-specific ordinary Time/Capacity experiment now exists. N1/N2/N3 receive one coarse request containing all selected Cells, and Rust dispatches the independent Cell projections through the same bounded Rayon pool with deterministic collection order.

The **cross-Cell native scaling result is valid** because N1/N2/N3 execute the same Rust kernel and differ only by the bounded worker count. On the real application Time workloads:

- 3 Cells: N1 1.48 ms -> N2 0.91 ms -> N3 0.88 ms;
- 6 Cells: N1 3.11 ms -> N2 1.86 ms -> N3 1.61 ms;
- 10 Cells: N1 4.85 ms -> N2 2.67 ms -> N3 1.87 ms;
- 11 Cells: N1 5.25 ms -> N2 3.15 ms -> N3 2.03 ms.

Thus four-way Rayon reduces the isolated broad Time native kernel by roughly 40-61% relative to one-worker Rust. This directly answers the user's question that Python-thread evidence from 050.9 is not a substitute for native cross-Cell scaling.

The complete subprocess boundary is much less scalable because input/output transfer dominates: for the same real Time rows, N1 -> N3 boundary medians are approximately 27.54 -> 25.72 ms (3 Cells), 63.16 -> 61.45 ms (6), 113.07 -> 105.66 ms (10), and 124.44 -> 120.37 ms (11). Therefore Rayon is genuinely parallelizing the numeric work, but the current disposable pipe boundary captures only a few milliseconds of that gain. 050.11 must not treat the isolated 40-61% kernel scaling as an equivalent full-backend saving.

Capacity-axis projection is correctly rejected as a standalone native target: the current isolated numeric work is already sub-millisecond to low-single-digit, while the subprocess boundary costs tens to more than one hundred milliseconds on broad batches.

### R5 — resolved

The explicit P4 persistent-warm model satisfies the user-directed lifecycle requirement. One Rust process and one four-worker Rayon pool remain resident across a mixed sequence of derivative and ordinary Time/Capacity requests. The first pool-creating request is outside the steady-state timing sequence.

All reported P4 warm requests record zero spawn and zero pool-initialization work. The four-worker pool is reused for broad, one-Cell and narrow requests instead of constructing smaller pools per interaction. Reported idle working set is about 4.6 MB, about 5.0 MB after pool warmup, with measured mixed-session peaks around 53-57 MB. Small-request medians remain approximately 0.7-1.1 ms. This is sufficient benchmark evidence that one resident four-thread pool is a viable steady-state model; production supervision/restart/fallback/packaging remains correctly deferred to the later production child.

## Open finding

### R6 — High — ordinary N0 is not a performance-faithful reference to the current vectorized Python Time projection

**Affected files**

- `scripts/profile_rust_derivative_kernel.py`
- `docs/specs/050.10-rust-rayon-kernel-benchmark.md`

**Current**

The ordinary benchmark correctly uses the current production helpers to construct the parity oracle in `_build_normal_dataset()`, but the timed N0 candidate does not execute the current production implementation.

For Time-axis work, `_normal_continuous_time()` iterates row-by-row in Python:

```python
for index in range(1, len(raw)):
    difference = raw[index] - raw[index - 1]
    ...
```

The actual production `analysis_engine._continuous_time()` is explicitly vectorized: it operates on NumPy arrays, finds reset positions, writes an offsets array and uses `np.cumsum`. The subsequent production display projection is also array-oriented.

Consequently the reported broad-Time N0 values (for example ~596 ms for the real 11-Cell case) are not a trustworthy measurement of the current Python/NumPy implementation. Output parity is exact, but performance equivalence is not. The durable statement that sequential Rust N1 is about 99% below N0 therefore overstates the native-code gain and could cause 050.11 to select a normal-path native mechanism on a false baseline.

This does **not** invalidate the N2/N3 vs N1 Rayon scaling above, because those candidates share the same Rust implementation and boundary. It also does not invalidate R5.

**Target**

Make N0 a performance-faithful representation of the current vectorized normal Time/Capacity projection while preserving the same owner-resolved numeric boundary used by N1-N3.

Prefer timing the current production vectorized helpers on a minimal prepared frame/array adapter, or reproduce those helpers with equivalent NumPy-vectorized operations if calling them directly would reintroduce unrelated owner work. Do not replace the current vectorized implementation with a scalar Python algorithm merely to create an isolated reference.

The goal is to answer two separate questions truthfully:

1. current vectorized Python/NumPy projection -> sequential Rust N1;
2. sequential Rust N1 -> Rayon N2/N3.

**Acceptance criteria**

- N0 uses the current vectorized production operation structure, not a scalar Python rewrite.
- N0 and N1-N3 still start from the same owner-resolved numeric inputs and produce the same scientific/display output.
- Rerun the representative ordinary matrix: 1/3/6/10/11 broad Time where available, broad capacity, and the narrow control, with at least five comparable warm repetitions.
- Report corrected N1 vs N0 separately from N2/N3 vs N1.
- Preserve the already-correct one-coarse-call batched Rayon implementation and persistent P4 lifecycle; do not broaden this fix into production integration.
- Update the 050.10 durable decision so it no longer claims a ~99% sequential-native normal-Time gain unless the corrected vectorized N0 evidence supports it.
- Scientific parity, focused checks, Rust tests/build and canonical `python scripts\preflight.py` pass before handoff.

## Reviewer assessment

Two important architectural questions are already answered:

1. **Native cross-Cell parallelism works.** Four-way Rayon materially reduces the isolated broad Time numeric kernel relative to one-worker Rust, even though the current benchmark subprocess-copy boundary absorbs most of that saving.
2. **Persistent warm execution works.** One resident four-thread Rust/Rayon service can stay ready across mixed workloads with negligible idle memory and no per-interaction spawn/pool initialization.

R6 is narrowly about the remaining sequential-native attribution for ordinary Time. Once corrected, 050.10 can close and 050.11 can remain focused on composition of independently validated mechanisms rather than repeating Rust-isolation work.
