## Findings

### R1 — High — C0 and C1-C3 do not start from the same measured kernel boundary

**Affected files**

- `scripts/profile_rust_derivative_kernel.py`
- `docs/specs/050.10-rust-rayon-kernel-benchmark.md`

**Current**

The selected native kernel is documented as derivative rolling + gradient + ratio/filter + postprocess, with Python retaining request/provenance orchestration and resolving compact numeric buffers before the native call.

C0 does not measure that same pre-resolved numeric boundary. `_run_python_reference()` calls the complete current `_derivative_curve()` for every Cell. That function still performs status classification, cycle/segment/phase boundary scanning, per-segment slicing, finite-row counting, and output-array setup before executing rolling/gradient/filter/postprocess.

C1-C3 do not pay those same steps. `_build_dataset()` calls `_capture_python_input()` once before any reported candidate timing; that function performs the status classification and contiguous segment scan and materializes the `SegmentInput` buffers. Every Rust timing then starts from those already-segmented buffers and charges only frame encoding/copy, IPC, the native numerical work, and response decoding.

Therefore the headline C0 -> C1 comparison is not a like-for-like Python-vs-Rust measurement of the selected kernel. Some work that C0 repeats on every call has been moved outside the C1-C3 timer. The very large Rust win may remain real, but the reported 86-98% sequential-native gain and complete boundary ratios cannot be attributed cleanly until both sides use the same starting boundary.

**Target**

Make C0/C1/C2/C3 boundary-identical. Prefer a Python reference adapter that consumes the same already-resolved per-Cell/per-segment numeric buffers used by Rust and reproduces only the selected rolling/gradient/ratio/filter/postprocess kernel in Python/NumPy/pandas. Then C0 is the Python implementation of exactly the work Rust receives.

Alternatively, if status/segment preparation is intentionally part of the production native boundary, charge equivalent preparation on every Rust candidate call as well. In either design, separately record the Python owner/preparation cost that remains outside the Rust kernel so 050.11 can compose a truthful end-to-end strategy.

**Acceptance criteria**

- C0 and C1-C3 begin from the same resolved numeric input boundary and perform the same selected kernel work.
- Any status classification, contiguous segment scan, finite-row preparation, dtype conversion, and buffer materialization that remains Python-owned is either excluded from both isolated kernel candidates and reported separately, or included on both sides.
- Recompute C1 vs C0 and C2/C3 vs C1 for the representative fixture and real 1/3/6/10-Cell derivative workloads plus the narrow control.
- Keep the existing one-coarse-call batched cross-Cell Rayon design; do not regress to one Python/native call per Cell.
- Update the durable 050.10 decision and boundary-cost table from the corrected run.
- Scientific parity, focused checks, Rust tests/build, and canonical `python scripts\preflight.py` pass before handoff.

### R2 — Medium — the reported Rust process-start measurement is only `Popen()` return latency

**Affected files**

- `scripts/profile_rust_derivative_kernel.py`
- `docs/specs/050.10-rust-rayon-kernel-benchmark.md`

**Current**

`RustWorker.__init__()` records `process_start_ms` from immediately before `subprocess.Popen(...)` until `Popen` returns. That is spawn-API latency, not the time until the Rust executable has loaded and reached a ready state. The remainder of process/module startup is folded into the first request's write/read boundary.

The implementation record nevertheless describes the ~5-6 ms value as "Rust process start" while also using the first request as cold-call evidence. This makes the required cold lifecycle attribution ambiguous: actual executable/module startup, first function execution, and first Rayon-pool initialization are not cleanly separated.

**Target**

Make the lifecycle labels observationally accurate. Either add a minimal worker-ready handshake and measure spawn-to-ready explicitly, or rename the current `process_start_ms` to `spawn_api_ms`/equivalent and state that true executable startup is included in the cold first-call boundary. Continue to report lazy Rayon-pool initialization separately.

**Acceptance criteria**

- No metric labelled process/module start measures only `Popen()` return latency.
- Cold evidence clearly distinguishes, where measurable: spawn-to-ready/module startup; first request/function call; first Rayon-pool initialization; steady-state warm calls.
- If a handshake is not added, the report explicitly says executable startup is included in the cold first-call wall time and does not claim a separate process-start duration.
- Update the lifecycle paragraph in the 050.10 implementation record accordingly.

### R3 — Medium — `rayon_queue_parallel_ms` cannot represent parallel scheduling overhead

**Affected files**

- `scripts/profile_rust_derivative_kernel.py`

**Current**

The benchmark computes:

`rayon_queue_parallel_ms = max(0, parallel_region_ms - kernel_sum_ms)`.

`kernel_sum_ms` is the sum of elapsed `process_cell()` times across Cells. Under successful parallelism that sum is expected to be larger than wall-clock `parallel_region_ms`, so the subtraction becomes negative and is clamped to zero. The field therefore collapses to zero precisely when multiple Cell kernels overlap successfully and cannot be interpreted as queue or scheduling overhead.

The spec requires Rayon queue/parallel-region timing. `parallel_region_ms` itself is valid and the existing cross-Cell speedups/effective-core evidence is useful, but the queue/overhead field is mathematically invalid and should not be carried into 050.11 as evidence.

**Target**

Remove/rename the invalid derived field or instrument an actually meaningful scheduling measure. At minimum preserve `parallel_region_ms`, per-Cell kernel elapsed times, worker count, and effective-core/concurrency evidence. If queue/start-delay is claimed, capture per-Cell task start relative to parallel-region start or another valid scheduling timestamp rather than subtracting summed concurrent work from wall time.

**Acceptance criteria**

- No reported field describes `parallel_region_ms - sum(concurrent cell times)` as Rayon queue/overhead.
- `parallel_region_ms` remains reported for C1/C2/C3.
- Any queue/scheduling metric has a physically meaningful definition and documented interpretation; otherwise record queue timing as not separately measured.
- Update the disposable report schema/summary if the invalid field is currently exposed there.

## Reviewer assessment of the current results

The core architecture experiment is sound and directly addresses the intended multicore question. The benchmark sends one coarse request containing all selected Cells, and Rust parallelizes **across Cells inside Rayon** with bounded 1/2/4-worker pools. This is the right experiment for determining whether multiple independent series can be calculated concurrently without the Python GIL coordinating each Cell.

The observed signal is also large enough that R1 is unlikely to erase the qualitative conclusion: broad multi-Cell derivative work shows strong sequential-native and additional Rayon scaling, whereas one-Cell and narrow work do not justify Rayon. However, the exact C0->C1 magnitude must be corrected before 050.11 uses it to size the production boundary or estimate complete latency.

The derivative kernel remains a justified primary Rust candidate because 050.9 specifically identified rolling, gradient, ratio/filter and postprocess as the dominant compact hotspot. 050.9 did not establish an equally compact normal Time/Capacity numerical kernel, so this review does not require inventing a second Rust kernel. If 050.11 later identifies a measured compact normal-path kernel, the same batched cross-Cell native pattern should be evaluated rather than assuming the derivative result generalizes automatically.
