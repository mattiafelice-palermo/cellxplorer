## Resolved findings

### R1 — resolved

Derivative C0 and C1-C3 now start from the same prepared segment-buffer numeric boundary. Status classification, contiguous segmentation and buffer preparation remain Python-owned and are reported separately, so the sequential Python-to-Rust comparison is like-for-like.

### R2 — resolved

The worker-ready handshake separates spawn API latency, spawn-to-ready, first request/lazy Rayon-pool initialization and steady-state warm calls. No process-start metric now measures only `Popen()` return latency.

### R3 — resolved

The invalid `parallel_region_ms - sum(concurrent Cell times)` queue-overhead calculation is removed. The benchmark retains physically meaningful parallel-region timing, per-Cell elapsed work and effective-core evidence without claiming a separate queue metric.

### R4 — resolved

Ordinary Time/Capacity now has an explicit N0/N1/N2/N3 native ablation using one coarse request containing all selected Cells. N1/N2/N3 differ only by bounded Rayon worker count and preserve deterministic result order.

The corrected vectorized N0 baseline shows that ordinary Time is already efficient in NumPy: sequential Rust improves broad Time only modestly (roughly 16-32%), while Rayon provides a separate cross-Cell reduction inside Rust. Capacity projection is already too cheap for the subprocess boundary to justify native execution by itself.

### R5 — resolved

The benchmark explicitly models one resident Rust process with one already-created Rayon pool across mixed repeated requests. Measured warm interactions pay zero process-spawn and zero pool-initialization cost, including one-Cell and small controls. Production supervision, restart/fallback and packaging remain correctly deferred to a later implementation child.

### R6 — resolved

The ordinary N0 continuous-Time adapter now reproduces the production vectorized NumPy operation shape rather than a scalar Python loop. The false ~99% normal-Time native claim is removed. The accepted interpretation is modest sequential-native improvement plus genuine cross-Cell Rayon scaling.

### R7 — resolved

The final benchmark machine exposed 16 logical CPUs, so exact 8-worker candidates were run rather than assuming four workers were the ceiling.

Representative 8-vs-4 results:

| Workload | 8 vs 4 isolated kernel | 8 vs 4 complete boundary |
| --- | ---: | ---: |
| Golden dQ/dV, 6 Cells | -12.31% | -2.26% |
| Golden dQ/dV, 10 Cells | -17.62% | -3.14% |
| Real dQ/dV, 6 Cells | -29.69% | -1.18% |
| Real dQ/dV, 10 Cells | -19.89% | -1.32% |
| Golden Time, 6 Cells | +19.40% | +0.46% |
| Golden Time, 10 Cells | -11.10% | +0.00% |
| Real Time, 6 Cells | +3.67% | +1.84% |
| Real Time, 10 Cells | +4.36% | +0.30% |
| Real Time, 11 Cells | -12.51% | +1.25% |

Eight workers therefore have a real isolated derivative signal, but the present Python/native copy boundary reduces that advantage to only about 1-3% complete-boundary improvement. Ordinary Time is mixed in isolation and flat/slower at the complete boundary.

Persistent P8 also remains inexpensive in memory, but the real-application small controls regress versus P4: ordinary Time rises from 0.669 ms to 0.911 ms and derivative from 0.776 ms to 0.892 ms. The mixed-session peak rises only modestly, from about 54.4 MB to 56.3 MB, so memory is not the rejection reason; the decision is based on weak complete-boundary benefit plus small-request regression.

**Decision:** retain **4 workers as the largest justified persistent bound on the measured host**. Eight workers are not rejected as a mechanism forever: if a later production binding materially reduces Python/native copy/IPC cost, the 8-worker derivative result may become worth revisiting. 050.11 must not assume the current subprocess boundary is permanent, but it must compose the accepted evidence rather than promote P8 now.

## Accepted 050.10 conclusions

1. **Derivative kernel:** sequential Rust is dramatically faster than the current Python/pandas/NumPy derivative kernel; broad multi-Cell Rayon adds substantial scaling on top.
2. **Ordinary Time:** current vectorized NumPy is already efficient. Sequential Rust gives only a modest isolated gain, while cross-Cell Rayon materially reduces the same native kernel on broad batches. The current subprocess-copy boundary is much larger than that kernel, so isolated percentages are not full-backend gains.
3. **Capacity projection:** native execution is not independently justified because the numeric projection is already tiny and the boundary dominates.
4. **Lifecycle:** steady state is one persistent native worker process with a pre-created bounded Rayon pool; per-interaction process/pool startup is rejected.
5. **Worker bound:** P4 is the accepted persistent bound on the measured 16-logical-CPU machine; P8 improves isolated derivative work but not enough at the current complete boundary to justify the broader steady-state cost/behavior.
6. **Scientific parity:** all final reported C/N/P candidates preserved finite placement, output shape, Cell order and scientific values under the existing repository tolerance gate, with zero reported deviations in the final evidence.
