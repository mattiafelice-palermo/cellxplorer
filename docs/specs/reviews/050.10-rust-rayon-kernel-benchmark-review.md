## Open findings

### R4 — High — 050.10 still does not measure Rust/Rayon cross-Cell scaling for ordinary Time/Capacity

**Affected files**

- `scripts/profile_rust_derivative_kernel.py` or a narrowly scoped sibling benchmark if clearer;
- `scripts/rust_derivative_kernel/` or a narrowly scoped sibling/native mode if required;
- `docs/specs/050.10-rust-rayon-kernel-benchmark.md`.

**Current**

The current native experiment is derivative-only. That is justified as the primary native hotspot, but it leaves a separate architectural question unanswered: 050.9 showed only about a 9-11% improvement for representative broad ordinary Time/Capacity when independent per-Cell work was scheduled with Python threads. Python-thread scaling is not equivalent evidence for a batched Rust/Rayon execution model because Python/pandas/object/GIL and native-library interactions differ materially from one coarse native call that schedules independent Cell work inside Rayon.

The user explicitly requires this Rust-specific question to be answered in 050.10, before 050.11 composition begins.

**Target**

Add a bounded benchmark of the ordinary Time/Capacity per-Cell **numeric transform/projection boundary** using the same architectural principles as the derivative experiment:

```text
Python resolves request/ORM/source/cache/provenance state
        -> prepares compact per-Cell numeric inputs once
        -> one coarse native request containing N Cells
             -> sequential native Cell work (1 worker)
             -> same Cell work under Rayon 2 workers
             -> same Cell work under Rayon 4 workers
        -> ordered compact outputs
        -> Python assembly remains outside the isolated native benchmark
```

Do not broadly port the engine or move ORM, Parquet orchestration, provenance or response assembly into Rust. Reuse the measured normal Time/Capacity transform boundary from 050.9 and choose the smallest faithful numeric subset that represents the repeated per-Cell calculation after owner-side preparation. The purpose is to isolate **cross-Cell native parallelism**, not to invent a new scientific algorithm.

Use a Python reference adapter that consumes the same prepared numeric boundary as Rust so sequential-native gain and Rayon gain remain separately attributable. Preserve the existing production mathematics and exact/tolerance rules.

**Acceptance criteria**

- Add explicit ordinary Time/Capacity native candidates, e.g. N0 Python reference / N1 sequential Rust / N2 Rayon-2 / N3 Rayon-4, or equivalent names with the same attribution.
- N0-N3 begin from the same owner-resolved numeric input boundary and perform the same normal Time/Capacity numeric work.
- Native execution is one coarse batch containing all selected Cells; do not call Rust independently once per Cell from Python.
- Include representative 1-, 3-, 6- and 10/11-Cell broad Time-axis workloads where the existing fixture/application data permit, plus a broad capacity-axis workload and a narrow/small control.
- Report isolated numeric-transform wall time, complete Python/native boundary time, worker count, CPU/effective concurrency, copied bytes, ordered output, and scientific parity.
- Report N1 vs N0 separately from N2/N3 vs N1 so native-code gain is not conflated with Rayon gain.
- Compare the measured native cross-Cell scaling with the accepted 050.9 Python-thread result, but do not treat Python-thread evidence as a substitute.
- If no compact faithful normal numeric boundary can be formed without a broad engine rewrite, document that concrete boundary analysis and return it for review rather than silently deferring the question to 050.11.
- No production request is switched to Rust in this child.
- Focused checks, relevant Rust tests/build, parity checks and canonical `python scripts\preflight.py` pass before handoff.

### R5 — High — persistent warm Rust/Rayon execution must be an explicit 050.10 candidate, not an incidental benchmark detail or a 050.11 decision

**Affected files**

- `scripts/profile_rust_derivative_kernel.py` and any normal Time/Capacity native benchmark added for R4;
- `scripts/rust_derivative_kernel/src/main.rs` or equivalent benchmark worker mode;
- `docs/specs/050.10-rust-rayon-kernel-benchmark.md`.

**Current**

The derivative harness already uses a persistent subprocess across its warm repetitions and keeps a lazily-created Rayon pool inside that process, which is the correct direction. However, the durable 050.10 decision still presents worker-count experiments mainly as C1/C2/C3 candidates and treats process/pool lifecycle as supporting measurements. It does not yet explicitly benchmark the user’s intended steady-state architecture: **one already-running native service with a bounded pool already ready to crunch the next analysis request**.

The user explicitly wants this lifecycle question settled in 050.10, not deferred to 050.11. 050.11 should compose accepted mechanisms; it should not decide whether every interaction needs to pay process/thread startup.

**Target**

Promote persistent warm execution to an explicit benchmark model. Represent the likely production steady state with one long-lived Rust worker process and one bounded Rayon pool, preferably four threads unless corrected 050.10 evidence shows another bounded size is superior. Create/initialize the pool once before the measured warm interaction sequence, keep it alive across multiple derivative and ordinary Time/Capacity requests, and measure subsequent calls without spawn or pool-construction cost.

Keep cold lifecycle evidence, but account for it separately as an application/service initialization cost. Do not repeatedly create a new native process or Rayon pool for each plotted interaction in the steady-state measurement.

This remains benchmark-only: do **not** wire the process into production application startup in 050.10. The later production child owns supervision, restart/fallback and packaging. 050.10 must nevertheless establish the lifecycle/performance model that 050.11 will compose.

**Acceptance criteria**

- Add an explicit persistent-warm candidate/session in which one Rust process survives multiple analysis requests and its Rayon pool is initialized once before measured steady-state calls.
- Demonstrate from recorded fields that warm requests have zero process-spawn and zero pool-initialization work on their critical path.
- Exercise the same persistent worker across repeated broad and small requests; include both derivative and the R4 ordinary Time/Capacity mode if the worker supports both.
- Record one-time spawn-to-ready and pool-initialization cost separately from steady-state request latency.
- Record idle/steady resident-memory cost for the persistent process/pool and bounded thread count.
- Explicitly test whether a persistent 4-thread pool is acceptable for 1-Cell/small requests when only one task is available; do not require recreating a 1- or 2-thread pool per request merely because the workload is small.
- If 2 workers are materially better on memory/latency or 4 workers cause a measurable small-request penalty even when idle, record that and choose the smallest justified persistent pool size from evidence.
- The implementation record must state the 050.10 steady-state recommendation in terms of a persistent process/pool, not per-call spawning.
- No production lifecycle integration is added in this child; later production work owns health checks, crash restart/fallback and packaging.

## Reviewer assessment

The returned R1-R3 fixes make the derivative benchmark scientifically and temporally interpretable. The existing design already proves the important multicore mechanism: a single Python-to-Rust request can contain multiple Cells and Rust can schedule them with `par_iter()` inside a bounded Rayon pool while preserving deterministic order.

The remaining work is not a request to broaden 050.10 into general architecture composition. It closes two Rust-specific unknowns that must be known **before** composition:

1. whether ordinary Time/Capacity benefits materially from the same batched native cross-Cell model, rather than assuming the ~10% Python-thread result is the native ceiling;
2. what the steady-state native lifecycle looks like when the process and pool are already resident.

Once R4/R5 are answered, 050.11 can stay narrow: combine only the accepted read-concurrency / normal-path execution / derivative native mechanisms, control oversubscription, and choose one production architecture. 050.11 should not repeat these Rust-isolation experiments.
