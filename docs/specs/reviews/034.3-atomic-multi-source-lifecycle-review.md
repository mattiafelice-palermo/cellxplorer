## Assessment

The lifecycle service introduces useful atomic attach, reorder, and detach primitives, shared impact
handling, activity records, and cache invalidation. The implementation is not yet safe for the
parent feature, however. Validation and impact calculations are scoped to the selected Test rather
than the complete Cell continuation chain, inspected source identities are not locked through the
write, and the legacy registration endpoint can bypass the lifecycle gate.

These defects can produce scientifically invalid source ordering or mutate the database based on
stale inspection evidence. Complete all findings before implementing Spec 034.4.

## Confirmed correct by code reading

- Attach, reorder, and detach are implemented as explicit service operations rather than scattered
  router writes.
- Database changes are grouped transactionally and failures are intended to leave no partial source
  set.
- Required acknowledgement codes are checked before mutation.
- Source positions are normalized after lifecycle changes.
- Analysis-impact preview, invalidation, and activity-log concepts are integrated.
- The implementation reuses existing `TestFile`, cache, and analysis-usage models.
- No released migration is edited and no new schema revision is introduced.

## Follow-up tasks

### R1 — High: lifecycle validation inspects only the selected Test, not the complete Cell chain

**Affected files**

- `backend/app/services/continuations.py`
- `backend/app/routers/files.py`
- `tests/test_continuations.py`
- relevant source/replicate lifecycle tests

**Current**

The parent contract defines a Cell continuation as all Tests in deterministic Test order, with each
Test's source files in position order. The lifecycle implementation does not consistently build that
complete chain:

- attach prepends or appends staged sources around only the target Test's ordered sources;
- reorder inspects only the target Test's proposed order;
- detach relies on impact confirmation but does not inspect the new complete continuation chain.

As a result, boundaries between Tests are not validated. Detaching a source can also create a new
adjacency between surviving sources that was never inspected. A locally valid Test mutation can
therefore make the Cell-level continuation invalid.

**Target**

Create one shared helper that constructs the complete proposed Cell chain before every lifecycle
mutation. The chain must use the parent specification's deterministic order:

1. Tests belonging to the Cell in canonical Test order;
2. source files within each Test by normalized position;
3. staged additions inserted at the requested location;
4. reorder/detach changes applied in memory before inspection.

Pass that full proposed chain through the authoritative 034.2 inspection gate. Do not duplicate
pairwise compatibility logic in the lifecycle service.

For detach, inspect every new adjacency created by removal. A detach is not safe merely because it
removes data.

**Acceptance criteria**

- Attaching to a non-final Test validates its boundary with both the preceding and following Test.
- Reordering a Test validates boundaries inside the Test and with adjacent Tests.
- Detaching the first, middle, or last source validates every newly adjacent surviving pair.
- A blocking Cell-level boundary finding causes zero database writes.
- Required acknowledgements include findings from the entire proposed Cell chain.
- Tests cover at least two Tests with multiple files and mutations in the earlier Test.
- The same helper is used by attach, reorder, detach, and impact preview.

### R2 — High: inspected source identity is not preserved through the database write

**Affected files**

- `backend/app/services/continuations.py`
- `backend/app/routers/files.py`
- `backend/app/services/parsing.py`
- `tests/test_continuations.py`

**Current**

Inspection attempts to establish a stable source hash by comparing the source before and after the
inspection read. During mutation, `_register_or_refresh_source_file` computes a hash again and then
reads metadata/stat information, but it does not:

- verify stability before and after the mutation read;
- compare the mutation hash to the exact identity approved by inspection;
- re-run inspection when the identity differs.

A file can therefore change after the user reviewed and acknowledged findings but before the
transaction writes the SourceFile/TestFile state. The acknowledgements may then apply to different
bytes than those inspected.

**Target**

Bind every staged or refreshed source to an inspected snapshot identity. The mutation request must
carry or internally retain the inspected hash/signature for each source. Immediately before any
database write:

1. read the source identity with the same stable before/after rule used by inspection;
2. compare it with the inspected identity;
3. reject the entire mutation when the source is unstable, missing, or changed;
4. require a fresh inspection and acknowledgement for the new identity.

Do not silently accept a new hash and do not partially register unchanged sources. The failure must
occur before the first persistent mutation.

**Acceptance criteria**

- A source modified between inspection and attach is rejected with a stable conflict/error response.
- A source modified during the final identity read is rejected as unstable.
- The same protection applies to refreshed registered sources, not only new staged files.
- On every mismatch, TestFile order, SourceFile metadata, activity logs, and cache invalidation remain
  unchanged.
- Tests mutate or substitute the source between inspection and submit and assert zero database
  writes.
- A fresh inspection of the new bytes can subsequently be submitted normally.

### R3 — High: the legacy registration endpoint bypasses the canonical lifecycle gate

**Affected files**

- `backend/app/routers/files.py`
- `backend/app/services/continuations.py`
- tests for `/api/register` and source registration

**Current**

The existing registration route can still append or associate SourceFiles with an existing Test
without using the new continuation inspection, acknowledgement, snapshot-stability, impact,
invalidation, and activity workflow.

This provides a second write path to the same persistent relationship. Any caller using the legacy
endpoint can create a source set that the 034.3 lifecycle APIs would reject.

**Target**

Establish one canonical mutation path.

Choose the smallest compatible option:

- prohibit the legacy route from adding a file to an existing Test and return a clear response that
  directs callers to the continuation lifecycle API; or
- delegate the operation to the same lifecycle service with the same inspection token/identity,
  acknowledgement, impact, stability, invalidation, and activity requirements.

Do not retain an unvalidated compatibility bypass for internal or historical callers. New-Test
registration may retain its existing behavior only when it cannot create a continuation boundary;
cover that distinction explicitly in tests.

**Acceptance criteria**

- No endpoint can append a source to an existing continuation without the canonical 034.2/034.3
  gate.
- Existing-Test calls to the legacy route are rejected or delegated deterministically.
- New-Test registration behavior is documented and tested.
- API tests prove that a chain rejected by the lifecycle service cannot be created through
  `/api/register`.
- Existing unrelated registration/import behavior remains intact.

### R4 — Medium: impact preview identifies the wrong tracked tail for mutations in an earlier Test

**Affected files**

- `backend/app/services/analysis_usage.py`
- `backend/app/services/continuations.py`
- `backend/app/routers/files.py`
- `tests/test_continuations.py`
- relevant analysis-usage tests

**Current**

The existing tracked-source helper correctly identifies the final source of the final non-empty Test
for a Cell. Lifecycle impact preview does not consistently simulate that complete state. Attach,
reorder, and detach calculations assume the selected Test controls the Cell-wide tail.

When an earlier Test is changed and a later non-empty Test remains, the preview can report the wrong
tracked source and therefore the wrong analysis impact or confirmation token.

**Target**

Calculate impact from the complete proposed Cell state produced for R1. Determine the tracked tail
only after applying the mutation in memory across all Tests. Use the same result for:

- preview response;
- confirmation-token generation/validation;
- post-mutation activity metadata;
- cache/analysis invalidation decisions.

Do not special-case the selected Test as the Cell tail.

**Acceptance criteria**

- Mutating an earlier Test while a later Test remains does not change the tracked tail unless the
  complete proposed chain actually changes it.
- Removing the final source of the final non-empty Test correctly moves the tail to the previous
  surviving source across Test boundaries.
- Preview and committed activity data agree on the before/after tracked source IDs.
- Confirmation tokens are invalid when the proposed full-chain impact changes.
- Multi-Test tests cover attach, reorder, and detach in both earlier and final Tests.

### R5 — Medium: duplicate staged source keys can collapse request state

**Affected files**

- `backend/app/services/continuations.py`
- `backend/app/routers/files.py`
- `tests/test_continuations.py`

**Current**

`staged_name` is used as a request-local identity in dictionaries and result maps, but duplicate
values are not rejected. Later values can overwrite earlier ones in structures such as staged
lookup, source-ID mapping, cache-job results, and import/replicate result maps.

Two different staged files with the same key can therefore produce ambiguous ordering and associate
parse or registration results with the wrong source.

**Target**

Validate staged request identity before inspection or background work starts. Every staged key used
for correlation must be non-empty and unique within the request.

Reject duplicates atomically with a stable validation response that identifies the duplicate key.
Do not silently rename, suffix, or collapse entries. If user-visible filenames need not be unique,
introduce or use a separate generated request ID and retain the display name independently.

**Acceptance criteria**

- Duplicate staged correlation keys are rejected before hashing, parsing, cache building, or DB
  mutation.
- The response identifies the conflicting key without exposing internal paths unnecessarily.
- Two files with the same display filename remain possible only when they have distinct explicit
  request identities.
- Order, parse status, source-ID mapping, and activity records use the unambiguous identity.
- Tests cover identical keys with different paths and repeated references to the same path.
