## Findings

### R1 — High: structurally valid corrupted step metadata can silently truncate scientific rows

Affected files:
- `backend/app/services/cache.py`
- `backend/app/services/stitch.py`
- `tests/test_raw_cache_layout.py`

**Current**

`_build_raw_layout_index()` now writes `step_column` and `step_to_row_groups`, but `_validate_raw_layout_index()` does not validate either field or include the detail mapping in the physical fingerprint. `load_raw_step_rows()` subsequently checks only that mapping keys/groups are syntactically valid, sorted, unique, and within the row-group range.

A sidecar can therefore remain valid under the existing raw shape fingerprint while its optional step map is wrong in a structurally valid way. For example, omitting one real row group from a requested step's group list still passes all current checks. The reader opens only the listed groups, exact-filters the requested `step_index`, marks diagnostics `ready`, and returns the resulting partial frame. `stitch_raw_steps()` treats that as a successful selective read, so Steps or DCIR can silently lose an occurrence rather than falling back to the full raw path.

This violates Spec 050.16 C: **stale/corrupt detail metadata must immediately fall back to the current full-raw path**, and it creates a scientific-correctness risk in the two promoted families.

**Target**

Make the optional step-detail metadata integrity-verifiable as part of the active raw-layout identity, without scanning the full raw dataset or reopening the original source on an interactive request. Any semantically inconsistent/corrupted detail map must be rejected before it can be used as a successful selective read, causing the existing full-raw fallback.

The implementation may use validated per-row-group step facts plus a detail fingerprint/checksum, a separately versioned detail sidecar, or another bounded physical-layout mechanism; do not change scientific cache identity or `CALC_VERSION`.

**Acceptance criteria**

- Add a regression that starts from a valid indexed raw cache, mutates `step_to_row_groups` in a structurally valid way so a requested step omits or points at the wrong real row group while the raw Parquet itself is unchanged, and proves the detail reader rejects the map and the family path falls back rather than returning partial science.
- A valid detail map still reads only implicated row groups and retains exact Steps/DCIR payload and ordering parity with forced full raw.
- Validation remains cache-byte/sidecar based; it does not open the original source or perform an unbounded full-raw scan on the interactive request path.
- No SQLite migration or `CALC_VERSION` bump.

### R2 — Medium: selective step reads release the raw-layout consistency lock before Parquet access

Affected files:
- `backend/app/services/cache.py`
- `tests/test_raw_cache_layout.py`

**Current**

`load_raw_step_rows()` calls `try_load_raw_layout_index()`. That helper acquires `_raw_layout_access(wait=False)` only while loading/validating the index, then releases it. `load_raw_step_rows()` later opens `raw_path(...)` and calls `ParquetFile.read_row_groups(...)` outside the shared raw-layout consistency boundary.

This differs from the established `load_raw_cycles()` implementation, which keeps `_raw_layout_access(...)` held continuously from index validation through row-group selection and Parquet read. A raw-layout publisher can therefore acquire the lock after the step reader validates one index generation but before it reads the raw file. The new reader no longer guarantees that the row-group map and Parquet bytes are the same validated pair, and a conversion that becomes busy after the initial lookup is not converted into the locked immediate fallback required by Spec 050.16.

**Target**

Keep the non-waiting raw-layout consistency boundary across index validation, detail-map validation, row-group selection, and Parquet read/filter, mirroring the already accepted selective cycle reader. If the boundary is busy, return `None` immediately so `stitch_raw_steps()` uses the existing full-raw fallback; do not wait for interactive layout preparation.

**Acceptance criteria**

- `load_raw_step_rows()` acquires `_raw_layout_access(wait=False)` for the complete index-to-Parquet read boundary rather than acquiring and releasing it only inside `try_load_raw_layout_index()`.
- Add a focused concurrency regression that forces layout publication/conversion to contend at this boundary and proves a busy selective request fails over safely instead of reading with an index/raw generation mismatch.
- Normal valid selective reads retain the measured bounded row-group behavior and exact Steps/DCIR parity.
- Existing full-raw fallback, cache cleanup protection, and Time/Capacity cycle-selective behavior remain unchanged.
