## 1. Goal

Close the remaining Cycles attribution gap first, then optimize every Cycles boundary where the corrected measurements show a meaningful end-to-end benefit.

Unlike the other four family children, this child is intentionally **profiling-first**. 050.17 proved that choosing `stitch_cycles()` as the optimization target would be premature: the largest six-Cell cost is still an unattributed direct remainder inside scientific compute.

Do not implement a Cycles optimization until that remainder is decomposed.

Time/Capacity is out of scope.

## 6. Opportunity inventory after closure

Once attribution is sufficient, inventory **all** material opportunities, not only the new largest stage.

Use the common decision rule: investigate stages around >=5% of the six-Cell route or >=10 ms, or repeated related work whose combined saving is material.

Likely hypotheses to confirm or reject include:

- repeated cycle-cache reads/stitch allocations;
- unnecessary DataFrame copies during derived-column construction;
- repeated scalar/numeric conversion;
- per-series Python list/object projection;
- replicate aggregation;
- redundant filtering/provenance passes.

These are hypotheses only. Do not pre-implement them before timing.

## 7. Optimization tranche A — largest measured direct Cycles cost

After profiling closure, implement the highest-confidence low-risk change with the largest removable absolute milliseconds.

Examples depending on evidence:

- if derived-column construction dominates, reduce copies/conversions while keeping formulas exact;
- if per-series projection dominates, vectorize/batch conversion and avoid repeated list walks;
- if stitching dominates, reduce duplicate frame concatenation/copying while retaining continuation/source labels;
- if aggregation dominates, reuse aligned arrays/group reductions.

The actual target is chosen from the new profile, not from this list.

## 8. Optimization tranche B — remaining material Cycles costs

Re-profile after tranche A and address every remaining material cost in descending **route benefit / scientific risk / complexity** order.

Do not stop solely because the former dominant stage is fixed. Conversely, do not pursue tiny changes after the route is already low-latency.

## 9. Concurrency gate

Cycles is currently ~171 ms for six Cells. Parallelism is unlikely to beat serial/vectorized cleanup unless the profiling closure reveals a large independent per-Cell CPU block.

Only test concurrency if >=100 ms of independent CPU work remains and complete-route controls include lifecycle/IPC/RSS. Exact hits must never dispatch workers.

## 10. Cache/version policy

Expected: no migration, no `CALC_VERSION`, no result-schema bump.

A change to any formula/rounding/meaning is out of scope and would require separate scientific/version review rather than being smuggled into this child.

### Implementation and benchmark evidence

The current-head baseline was captured before the optimization tranche:

```powershell
python scripts\profile_analysis_families.py --families cycles --skip-time-specialist --repetitions 5 --output tmp\050.22-baseline.json
```

The measured current-head forced-miss p50 was 34.09 ms for one Cell and 168.42
ms for six Cells; the six-Cell exact persisted hit was 23.70 ms. This is
consistent with the locked 050.17 anchors of 35.88 ms, 170.99 ms, and 22.45
ms respectively.

The closure instrumentation is opt-in and lives in the direct body of
`analysis_engine.compute()`. It separates compute setup, source bookkeeping,
post-stitch projection, status badges, active-mass resolution, protocol
masking, derived columns, filtering, series projection, source projection,
response assembly, aggregation, provenance, and final response assembly. The
profiler attaches those direct stages as siblings below `scientific_compute`
after the route finishes, so the normal route pays no timer calls when no
profiling dictionary is supplied. The five-repetition closure profile showed
zero sibling overlap and a six-Cell direct residual of 0.98 ms p50 before
optimization, below the 26.78 ms largest named direct child.

The retained optimization tranches are:

- `add_derived_columns()` converts each source numeric column once, computes
  the derived arrays before constructing the output frame, batches the derived
  frame append, and uses a stable NumPy retention-reference selection with the
  previous skip-NaN maximum semantics;
- Cycles quantity projection converts all 29 requested columns in one numeric
  matrix and maps NaN to JSON null in one pass, preserving missing-column and
  non-finite behavior;
- `cell_metrics()` uses the already numeric cycle arrays for stable first/last
  cycle selection, means, medians, maxima, duration totals, and CV masks,
  avoiding repeated `nsmallest`/`nlargest` and temporary DataFrame masks while
  retaining the existing formulas and filtering semantics.

The final five-repetition measurement was captured with:

```powershell
python scripts\profile_analysis_families.py --families cycles --skip-time-specialist --repetitions 5 --output tmp\050.22-final-profile.json
```

| forced-miss measurement | 1 Cell | 6 Cells |
| --- | ---: | ---: |
| unprofiled complete-route controls | 23.60–28.93 ms | 102.62–107.04 ms |
| unprofiled complete-route p50 | **24.62 ms** | **103.18 ms** |
| profiled complete-route p50 | 27.87 ms | 111.19 ms |
| exact persisted-hit p50 | 16.30 ms | **21.85 ms** |
| scientific compute p50 | 15.00 ms | 75.22 ms |
| `stitch_cycles` inclusive p50 | 6.09 ms | 35.07 ms |
| cycle scientific extraction p50 | 0.81 ms | 5.53 ms |
| direct derived columns p50 | 1.35 ms | 7.91 ms |
| direct series projection p50 | 0.39 ms | 2.40 ms |
| direct residual / largest named child | 0.22 / 1.35 ms | **0.84 / 7.91 ms** |

The six-Cell result is a 39.7% reduction from the locked 050.17 miss baseline
and a 38.7% reduction from the measured current-head baseline, exceeding the
153.9 ms acceptance ceiling. The final six-Cell response retained 1,158 cycle
rows across six traces, was 725,074 bytes, used 60 SQL statements with 1.34 ms
cumulative SQL time, and loaded six deferred source headers. Exact-hit
controls continued to report zero raw loads and zero scientific-compute calls.
Scientific payload and series-order parity were true for every profiler
control.

The remaining large route boundaries are cache/Parquet materialization inside
`stitch_cycles` (21.11 ms data access within 35.07 ms inclusive), plus cache
persistence outside scientific compute (23.02 ms). A batched
`apply_cycle_mapping()` variant was measured and removed because it did not
produce a stable complete-route improvement; further changes to Parquet
materialization or persistence would require a separate cache-path design.
The route is below the acceptance target and the remaining independent CPU
work is below the 100 ms concurrency gate, so no worker dispatch was added.

Focused profiling, Cycles scientific/metrics/stitch tests, and the golden
analysis corpus passed. Browser/Plotly validation is **NOT RUN** by explicit
user instruction. No migration, `CALC_VERSION` bump, cache-version change, or
result-schema change was needed.

### Review fix R1

The first implementation used `np.max()` for the selected first-N discharge
capacity values, which propagated NaN instead of matching the prior Pandas
`Series.max(skipna=True)` contract. The fix keeps the stable NumPy ordering but
filters NaN values before the maximum; an empty or all-NaN window still returns
NaN. A focused regression now covers mixed and all-NaN windows and verifies
that the mixed case continues to populate capacity retention, last-cycle
retention, and cycles-to-80 metrics.

The bounded no-regression profile after the fix remained parity-clean: the
six-Cell unprofiled control was 103.02 ms for the one repetition, with zero
scientific/order parity failures and a closed 0.77 ms direct residual. The
five-repetition performance evidence above remains applicable because the
fix only restores NaN handling in the retention-reference reduction.
