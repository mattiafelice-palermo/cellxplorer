# 052.3 — Time/Capacity fixed request-overhead reduction

**Status:** Active child — implementable
**Parent:** Spec 052 — Time/Capacity cycle navigation
**Repository:** `mattiafelice-palermo/cellxplorer`
**Branch:** `feature/time-capacity-cycle-navigation`
**Reason for child:** explicit user decision after a profiling review of the 052.2 moving-preview path. Child 052.2 made the navigator's request cadence correct (single in-flight, latest-wins, reduced-resolution moving previews). Profiling showed the remaining limit is **backend fixed per-request overhead**, not the navigator. This child removes that overhead.

## Goal

Reduce the fixed, range-independent cost of one ordinary Time/Capacity request so that moving slider previews become visually continuous, **without changing any scientific output**.

Because 052.2 admits exactly one moving preview at a time and always requests the latest range, the observed drag frame rate is now precisely:

```
moving preview fps ≈ 1000 / backend_request_latency_ms
```

At the measured 117 ms for a 1000-point moving preview this is ~8.5 fps. Every millisecond removed from the fixed overhead converts directly into drag smoothness.

This child covers five backend changes:

1. an in-memory raw-layout index cache;
2. relocating job isolation copying from planning to serial dispatch;
3. non-persistent moving previews;
4. removing double serialization on the process path;
5. cooperative abandonment of superseded requests (**measurement-gated**, see Stage 5).

No parser, migration, endpoint contract, cache-version, or scientific-algorithm change is intended. **Scientific output must be byte-identical.**

## Verified current facts that constrain the implementation

Measured on this branch at `5558d33`, AC power, real application library ("Performance analysis", 6 Cells), via the production router/backend path:

| Workload | Latency |
|---|---|
| 6 cells, all cycles, V vs t | 247 ms |
| 6 cells, 10-cycle window, 1000 pts/cell (the moving preview) | **117 ms** |
| 6 cells, 10-cycle window, 500 pts/cell | 115 ms |
| 1 cell, cycles 1–3 | 42 ms |

Stage breakdown for the 10-cycle window (~117 ms), from the opt-in `profile=true` twin:

- **~70 ms owner-side setup** — `ensure_canonical_cycling_available` + `_build_jobs`, roughly half raw-layout index load/validation and half `deepcopy`;
- **~46 ms cell jobs** — indexed Parquet row-group decode, exact cycle filter, transform, display downsampling;
- **~16 ms result persistence** — JSON encode + gzip + write under the global `analysis_cache._lock`;
- **~7 ms** canonical guard + source data signature.

Facts that constrain design:

- **Resolution is nearly free.** 500 → 1000 points per cell costs +2.4 ms. Request cost is dominated by fixed overhead, not returned points. Lowering `max_points_per_cell` is therefore *not* a viable latency lever.
- **Narrow windows never reach the worker pool.** `choose_execution` requires `selected_rows >= max(12_000, cell_count * 4_000)`; a 6-cell 10-cycle window is 16,492 rows, so it returns `small_selected_row_count` and runs serial. Moving previews are a **serial-path** workload; parallel-path work does not help them.
- `_load_raw_layout_index_unlocked` re-reads and re-validates the sidecar JSON from disk on **every** request, per source, including a pyarrow Parquet footer read. There is no in-memory cache. The sidecar is keyed by `(file_hash, parser_version)` and its contents are immutable for that key.
- `_build_jobs` performs `deepcopy(plan)` and `deepcopy(plan_diagnostics)` **per Cell** — ~26 top-level copies expanding to ~27,000 recursive calls per request.
- **`_run_process` pickling already provides worker isolation**; the build-time copy is redundant there. `_run_serial` executes `_run_job` in-process on shared objects, so serial is the only path where the copy is load-bearing.
- `_run_serial` is the single chokepoint for all three serial executions, including both `_run_process` failure fallbacks (`PoolNotReadyError` and generic `Exception`). Isolation placed there cannot diverge from the execution decision.
- `load_indexed_time_capacity_raw` treats `plan` as read-only; there are no attribute assignments to plan objects in `time_capacity_path.py`. `plan_diagnostics` **is** mutated, but `_materialize_read` already deep-copies it before use, and `_cell_result` copies it again.
- `_run_process` pickles every `(job, request)` once to compute `input_bytes` and again on submit, unconditionally — not gated on `access_diagnostics`.
- The route has no client-disconnect handling; `compute_time_capacity_analysis` is a synchronous `def` executed in Starlette's thread pool and always runs to completion.
- 052.2 admits **one** moving preview at a time (`inFlight` + latest-wins `pendingRange`), so client-side request pile-up is already prevented.

## Stages

Stages are independent and must be committed separately so each can be profiled in isolation. **Stage 1 and Stage 2 interact — see the safety note in Stage 2.**

### Stage 1 — In-memory raw layout index cache

Cache validated raw-layout indexes in the backend process, keyed by `(file_hash, parser_version)`.

Requirements:

- the cache must live behind the existing raw-layout lock discipline in `cache.py`; do not introduce a second lock ordering;
- entries must be invalidated when the sidecar or Parquet file changes. Validate cheaply against the sidecar's `stat()` (`st_mtime_ns` and `st_size`) before serving a cached entry; a mismatch reloads and revalidates;
- any existing raw-cache invalidation or reclamation path (including Spec 043 Part B cache reclamation and parser-identity upgrades) must clear affected entries;
- the cache must be bounded. An unbounded dict keyed by file hash grows with library size; use a bounded LRU with an explicit, documented entry ceiling;
- **entries handed to callers must not be mutable shared state** — see Stage 2.

### Stage 2 — Delete redundant job isolation copying

Remove `deepcopy(plan)` and `deepcopy(plan_diagnostics)` from `_build_jobs` entirely.

**Measured justification.** Relocating the copy into `_run_serial` was the original plan, but it would have saved nothing on the serial path — and moving previews *are* serial. A direct experiment settled it: for the 6-cell 10-cycle window, the 6-cell full range, and the 6-cell capacity axis, a pickle digest of every `job.plan`, `job.plan_diagnostics`, `job.descriptor` and the shared `request` taken before and after `_run_serial(jobs, request)` is **unchanged in every case**. Nothing on the read path mutates owner-resolved job state, so the copy is dead weight in both execution modes.

This holds because:

- `load_indexed_time_capacity_raw` treats `plan` as read-only;
- `_materialize_read` already deep-copies `plan_diagnostics` before passing it to the readers that *do* mutate it;
- `_cell_result` copies the diagnostics again before building its own.

Requirements:

- delete both build-time copies; do not replace them with a copy elsewhere;
- `_run_process` continues to rely on pickle for worker isolation, unchanged;
- the `deepcopy(job.plan_diagnostics)` in `_materialize_read` **must be preserved** — it is the guard that makes this safe, and removing it would make the mutation real;
- **add a regression test that pins the invariant**: build jobs, digest `plan` / `plan_diagnostics` / `descriptor` / `request`, run `_run_serial`, and assert the digests are unchanged. This is what protects the deletion, and it is also what protects Stage 1's shared cached index from being mutated by a consumer.
- **Safety note (Stages 1 + 2 together):** once Stage 1 hands the same index object to multiple requests, this non-mutation invariant becomes load-bearing across requests rather than merely wasteful to violate. The Stage 2 test is therefore a prerequisite for Stage 1, not an optional extra. If a future change needs to mutate plan state, it must reintroduce a copy at that point.

### Stage 3 — Non-persistent moving previews

Moving previews must not be written to the analysis result cache.

Requirements:

- add an explicit request field (e.g. `persist: bool = True`) to the compute request model; the route skips `analysis_cache.store_result` when it is false;
- the frontend sets it false for `resolution === "moving"` requests only; idle-promoted full previews and committed ranges persist as today;
- a non-persisted response must still be correct and complete — this is a caching decision, not a response-shape change;
- non-persisted requests must still *read* the result cache; a moving preview that happens to hit an existing entry should serve it;
- the existing `/time-capacity/refine` endpoint is already non-persistent and must remain so.

### Stage 4 — Remove double serialization on the process path

`_run_process` must not pickle `(job, request)` solely to measure `input_bytes` unless diagnostics were requested.

Requirements:

- compute `ipc_input_bytes` only when `access_diagnostics is not None`;
- when diagnostics are off, report the field as `None` rather than a wrong value;
- the 050.14/050.23 diagnostic contract must be unchanged when diagnostics **are** requested.

### Stage 5 — Cooperative abandonment of superseded requests (measurement-gated)

**Outcome: NOT IMPLEMENTED — closed by measurement.**

The premise of this stage was a growing queue of uncancellable superseded computations during a drag. Child 052.2's single-in-flight backpressure removed that premise before this child began.

The measurement is `frontend/tests/timeCapacityCycleNavigation.test.ts`, "a realistic drag supersedes at most one admitted request": it drives the real scheduler policy with a 120 Hz pointer stream over a 3-second drag at the measured post-change 84 ms latency, and counts admissions against in-flight requests. Results:

- requests are admitted at roughly one per round trip, not one per pointer event, because `timeCapacityPreviewOnMove` parks the newest range in `pendingRange` while `inFlight` is set;
- **at most one** request per drag is ever superseded, and only at the very end: `timeCapacityPreviewPromoteOnIdle` deliberately does not check `inFlight`, so the idle full-resolution promotion may overtake a still-open moving request;
- the cost of that is therefore one abandoned ~84 ms computation per completed drag, not a queue.

Implementing cooperative abandonment would add a cancellation model to the backend to reclaim a single sub-100 ms computation per interaction. That is not a worthwhile trade against the complexity and the risk of returning partial scientific results, so the stage is closed.

If the navigator's cadence ever changes such that overlapping in-flight requests become possible again, reopen this stage — the test above is the tripwire, and it will start failing.

## Verification requirements

### Scientific parity — mandatory, blocking

Every stage must preserve byte-identical scientific output. Parity is proven with `scientific_digest(...)` from `scripts/profile_time_capacity_concurrency.py` over a fixed workload matrix, comparing the pre-change baseline to each post-change build.

The matrix must include, at minimum:

- 1 cell / explicit cycles 1–3 / time;
- 6 cells / full range / time;
- 6 cells / 10-cycle window / 1000 points per cell (the moving preview);
- 6 cells / full range / capacity axis;
- one derivative view;
- one workload large enough to select `mode == "process"`, to cover the Stage 2 pickle-isolation path.

A digest mismatch on any workload blocks the stage. Ordering equality (`result_order`) must also hold.

### Performance evidence

- baseline and post-stage medians recorded per stage, same host, **AC power** (battery was measured 2.2× slower and invalidates comparison);
- report the derived `1000 / latency` moving-preview frame rate alongside raw latency;
- record the `profile=true` stage breakdown before and after so the reduction is attributable to the intended stage.

### Standard gates

- focused backend tests for each stage, including the Stage 2 cross-request mutation test and a Stage 1 invalidation test;
- canonical preflight;
- TypeScript + production build for the Stage 3 frontend field;
- browser/manual acceptance recorded truthfully as RUN or NOT RUN.

## Acceptance criteria

1. Scientific digests identical to baseline across the full matrix, for every stage.
2. The 6-cell 10-cycle 1000-point moving preview is materially faster than the 117 ms baseline, with the improvement attributable to the intended stages in the profile breakdown.
3. Stage 2's isolation cannot be bypassed by a `_run_process` fallback, proven by test.
4. Stage 1's cache is bounded and correctly invalidated, proven by test.
5. Moving previews leave no new analysis result-cache entries; committed ranges still do.
6. Stage 5 either implemented with evidence, or closed with recorded measurement showing it is unnecessary.
