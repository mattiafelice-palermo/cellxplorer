## 1. Goal

Optimize the complete DCIR result-cache-miss route, not merely the current dominant helper. Start from the 050.17 measurements, remove worthwhile repeated work in DCIR occurrence extraction, then re-profile and address every remaining stage with a credible material end-to-end benefit.

Preserve DCIR scientific meaning, protocol ownership, pulse/rest adjacency semantics, provenance, ordering and exact-cache-hit behavior.

Time/Capacity is out of scope.

## 2. Locked baseline

| Workload | p50 |
| --- | ---: |
| 1 Cell forced miss | **72.39 ms** |

## 4. Current occurrence-extraction shape

`dcir.per_occurrence(...)` currently performs a substantial amount of Pandas object work:

- resets/copies the input frame;
- converts step/cycle/time/record-index columns;
- creates continuity/boundary masks;
- computes run IDs;
- materializes grouped run DataFrames;
- walks adjacent run pairs;
- repeatedly derives last finite voltage, duration, timestamp/current facts and DCIR quantities.

The first hypothesis is to preserve the exact run/adjacency semantics while computing reusable run metadata in fewer passes and with fewer temporary DataFrames.

## 5. Locked scientific semantics

Preserve exactly:

- configured candidate rest/pulse step ownership;
- rest-to-pulse adjacency and record-index continuity requirements;
- source-cycle and occurrence identity;
- source-file boundaries;
- pulse duration semantics;
- baseline and pulse voltage/current selection;
- current sign/absolute handling;
- DCIR calculation and units;
- missing/NaN handling;
- protocol candidate recognition;
- deterministic result IDs/order;
- provenance and parser pinning;
- multi-source safety behavior.

A faster implementation may change representation, not scientific meaning.

## 7. Optimization tranche A — run metadata without DataFrame churn

Preferred direction, subject to measured confirmation:

- normalize required numeric arrays once;
- determine run boundaries/IDs once;
- build compact run metadata (start/end positions, step, cycle, source continuity, timestamps, first/last finite values where needed);
- scan adjacent runs using compact metadata rather than retaining a list of copied DataFrame groups;
- slice original arrays only when a statistic genuinely requires the underlying rows;
- eliminate repeated numeric/timestamp conversions;
- preserve stable order exactly.

If `groupby` itself is not material after profiling, do not rewrite it purely for style.

## 8. Optimization tranche B — scalar/statistical reuse

After tranche A re-profile:

- avoid repeated `_last_finite` scans over the same run;
- compute duration/timestamp endpoints once per run;
- precompute current medians or other reused run statistics only where they are actually consumed;
- avoid constructing intermediate Series for one scalar when exact NumPy/Pandas array operations are materially cheaper;
- keep NaN semantics identical.

## 9. Optimization tranche C — raw/protocol/assembly costs

After occurrence extraction improves, re-profile the complete route and address remaining meaningful costs, including:

- step-addressable read planning and row-group decoding;
- `stitch_raw_steps(...)`;
- protocol reconstruction/candidate detection;
- repeated series planning;
- result/provenance construction;
- cache persistence/serialization;
- SQL/ORM owner work.

Do not convert Chargeability/Rate raw access strategies into DCIR without measurement; DCIR already has a specialized selective path.

## 10. Concurrency gate

Do not add multiprocessing/threads just because six Cells scale linearly.

Concurrency is eligible only if the optimized serial DCIR route still has a clearly independent per-Cell CPU stage large enough to overcome scheduling/IPC costs and a controlled benchmark demonstrates a material complete-route win. Reuse existing bounded infrastructure only if ownership/lifecycle are compatible; do not create another resident pool casually.

## 11. Cache/version policy

Expected: no migration, no `CALC_VERSION` bump, no result-schema version bump.

Exact persisted hits must remain ~direct-body operations and must not:

- read raw Parquet;
- reconstruct protocol;
- run `per_occurrence`;
- build run metadata;
- dispatch workers.

### Retained and rejected decisions

- **Retained tranche A:** required DCIR columns are converted to numeric arrays
  once; boundary masks and compact run start/end positions are built once; the
  adjacent-run scan no longer creates copied DataFrame groups. Existing
  record-index continuity, cycle/time reset, timestamp duration precedence,
  finite-value selection, and stable output order remain unchanged.
- **Retained tranche B:** last-finite voltage/cycle values, pulse-current
  medians, timestamp endpoints, durations, and C-rate values are derived from
  the normalized arrays within one matching-run pass. The measured occurrence
  parent is 34.29 ms p50, with a 2.93 ms direct residual and no child overlap.
- **Retained tranche C:** a request-local DCIR Cell context unions the step
  indices required by all configured series, performs one selective raw read
  (or one safe full-raw fallback), and reuses the frame in configured series
  order. Identical immutable header metadata plus nominal capacity reuses one
  protocol reconstruction per request; five of six clone reconstructions were
  request-local hits in the six-Cell run. No persistent cache or cache-key
  change was introduced.
- **Serial execution retained:** no worker/IPC/RSS candidate was run. The final
  route has several required serial boundaries rather than one isolated
  worker-safe kernel; the concurrency gate was not satisfied and no new pool
  lifecycle was justified.
- **Persistent run caches, source reads, migrations, and version changes
  rejected/deferred:** run metadata remains request-local, the canonical raw
  cache/selective fallback remains the source, and no `CALC_VERSION`, schema,
  result-schema, parser-identity, or frontend change was needed.

### R1 follow-up evidence: prepared source-frame reuse

Reviewer finding R1 required the DCIR source frame and run preparation to be
owned once per distinct source, rather than once per configured series. The fix
uses one request-local prepared source frame per source index, then performs
target-specific adjacent-pair selection for each series. It was benchmarked
with five repetitions of the same forced-miss and exact-persisted-hit workloads:

```powershell
python scripts\profile_analysis_families.py --families dcir --skip-time-specialist --repetitions 5 --output tmp\050.19-r1-five.json
```

The repaired route measured 36.05 ms p50 (33.70–44.95 ms) for one Cell and
139.27 ms p50 (137.63–141.55 ms) for six Cells. The exact persisted-hit p50
was 11.18 ms for one Cell and 14.54 ms for six Cells. Unprofiled control
medians were 34.19 ms and 138.67 ms respectively. The route-level p50 is not
claimed as a speedup over the earlier three-repetition 131.77 ms result: raw
materialization and stitching remain the dominant variable cost, while this
round closes the repeated source-preparation defect. The profiler overhead
control remained scientifically and order-parity true for every sample.

The repaired six-Cell DCIR deep profile measured source preparation at 27.99
ms p50 across 6 calls and occurrence extraction at 3.23 ms p50 across 12
calls. Source-preparation child timers summed to 27.75 ms with 0.25 ms parent
residual and no overlap; occurrence child timers summed to 0.066 ms with
3.17 ms parent residual and no overlap. Normalization, boundary construction,
run metadata, scalar extraction, and adjacency scanning each ran once per
source (6 calls each); target-pair selection ran 12 times and quantity
calculation ran once per valid occurrence (84 calls). This is the required
source-versus-target ownership split; no series repeats frame normalization,
run construction, or source-wide adjacency scanning.

The final R1 structural counts were 6 raw-load calls, 42 row groups, 4,488
rows returned, 172,032 physical Parquet rows read, 6 source-header lazy loads,
12 traces, 84 response points, 17 SQL statements, and 32,168 response bytes.
`stitch_raw_steps` remained a single selective stitched read per Cell at
54.38 ms inclusive p50 (11.59 ms exclusive), with data-access materialization
at 41.64 ms p50. The selective raw/stitch path is retained because it already
unions the required step indices, bounds each read to the canonical cache,
preserves source provenance and ordered stitching, and has a safe full-raw
fallback. A persistent cross-request raw-frame cache or a broader stitch
rewrite would add invalidation/lifecycle risk without a measured correctness
or route-level benefit; the current R1 fix therefore stops at the requested
source-preparation boundary. The current scientific-compute inclusive p50 was
128.99 ms, leaving a 36.47 ms direct parent residual rather than an unmeasured
claim about the remaining route.

All five R1 forced-miss samples preserved the baseline scientific digest and
series order, and exact-hit controls continued to bypass raw reads, scientific
compute, and DCIR deep profiling. Focused verification, canonical preflight,
and the explicit browser/manual `NOT RUN` status are reported in the handoff
coordination entry for this review round.
