## 1. Goal

Reduce Chargeability warm result-cache-miss latency across the complete route. The first measured target is protocol reconstruction, but this child must re-profile after that work and continue through every secondary boundary where a meaningful end-to-end gain remains justified.

Preserve safe expression evaluation, protocol/candidate semantics, occurrence/reference-capacity science, provenance and exact-hit behavior.

Time/Capacity is out of scope.

## 2. Locked baseline

050.17 authoritative Chargeability measurements:

| Workload | p50 |
| --- | ---: |
| 1 Cell forced miss | **37.65 ms** |
| 6 Cells forced miss | **195.51 ms** |
| 6 Cells exact persisted hit | **17.89 ms** |
| dominant stage | `protocol_reconstruction` |
| dominant p50/share | **120.69 ms / 61.70%** |

This strongly suggests repeated protocol reconstruction is the first opportunity. Do not assume the remaining ~75 ms is irrelevant: once reconstruction is reduced, occurrence extraction, raw access, candidate logic, assembly or ORM work may become dominant.

## 4. Locked scientific and safety contracts

Preserve:

- the restricted AST grammar and no-arbitrary-code behavior of `parse_linear_expression`;
- candidate recognition and assignment-step ownership;
- nominal-capacity dependence of protocol reconstruction;
- reference-capacity selection;
- occurrence grouping and cycle/source identity;
- current/capacity/voltage/time calculations;
- chargeability expression semantics;
- configured filters;
- deterministic ordering/IDs;
- provenance/parser versions;
- multi-source fail-closed behavior.

Do not memoize protocol results under an identity that omits any input affecting reconstruction.

## 6. Optimization tranche A — exact protocol reuse within the request

First determine **why** protocol reconstruction is ~121 ms for six Cells.

Preferred low-risk direction is request-local reuse, not a speculative persistent cache.

Investigate whether the route currently reconstructs the same source protocol more than once across:

- guards;
- cache-key/provenance work;
- `chargeability.compute(...)`;
- candidate derivation;
- repeated selection units referring to the same Cell/source.

Where exact inputs are identical, build/reuse a request-local protocol reconstruction map keyed by all scientific inputs required for equivalence, at minimum source identity/parser/header state and nominal capacity as appropriate to the current `protocol.reconstruct_protocol()` contract.

Possible ownership locations:

- extend `AnalysisRequestContext` with lazily populated protocol facts;
- add a narrow request-scoped helper/cache object consumed by the guard and family service;
- another simpler existing pattern if current code already owns protocol reuse elsewhere.

### Hard constraints

- no process-global mutable protocol cache;
- no stale result after metadata/nominal-capacity/source change;
- no cache-key collision;
- no persistent schema just to memoize Python objects;
- do not eagerly reconstruct protocols on exact persisted result hits if the current hit can remain cheaper without it.

If the dominant 050.17 timing comes from unavoidable unique reconstructions rather than duplicate reconstruction, benchmark alternative reconstruction implementation only after proving that fact.

## 7. Optimization tranche B — protocol reconstruction itself

If unique reconstruction remains material after request-local reuse, profile inside `protocol.reconstruct_protocol()` for the Chargeability workload and optimize only measured expensive operations.

Candidates may include:

- repeated header normalization/parsing;
- repeated string/regex scans;
- repeated nominal-capacity rate derivation;
- rebuilding immutable structures that can be derived once per call.

Any shared protocol-service change affects DCIR/Rate/other consumers. It therefore requires focused protocol safety tests and must preserve output exactly for all supported parsers, not only the Chargeability fixture.

## 8. Optimization tranche C — occurrence/raw/science path

Re-profile after protocol work.

If now material, optimize:

- `_reference_capacity(...)`;
- `_occurrence_rows(...)` step filtering/grouping;
- repeated `pd.to_numeric` / timestamp conversion;
- per-occurrence scalar extraction;
- safe expression evaluation setup when the same compiled expression can be reused request-locally;
- full raw materialization, but only if it becomes a meaningful share;
- result/provenance assembly and serialization.

Prefer single-pass/reused arrays over new concurrency.

## 9. Expression handling

`parse_linear_expression(...)` is a security boundary.

If expression parsing/evaluation is optimized:

- cache only validated/compiled safe representations;
- key by the exact expression text/config;
- do not broaden the accepted AST;
- do not call `eval` on untrusted unrestricted input;
- preserve numerical output and error behavior.

Security correctness outranks latency here.

## 10. Concurrency gate

Chargeability's current six-Cell route is ~196 ms. Do not introduce process/thread complexity unless the optimized serial path still contains a sufficiently large independent per-Cell CPU cost and complete-route controls prove a win. Startup/IPC/RSS and small-workload regression must be counted.

## 11. Cache/version policy

Expected: no migration, no `CALC_VERSION` bump, no result-schema bump.

Exact persisted hits must remain direct and must not reconstruct protocol merely because the miss path now has a request-local protocol cache.

## 12. Implementation order

1. Capture current 1/6-Cell baseline + call counts for protocol reconstruction.
2. Prove duplicate vs unique reconstruction ownership.
3. Implement request-local exact reuse where duplicate work exists.
4. Re-profile complete route.
5. If unique reconstruction remains material, profile/optimize the shared reconstruction internals with cross-family safety coverage.
6. Re-profile and optimize occurrence/raw/expression/assembly secondary costs where meaningful.
7. Consider concurrency only under its gate.
8. Run final family profile, golden analysis, protocol safety and canonical preflight.
9. Record rejected candidates.

## 13. Performance acceptance

Because ~62% of the six-Cell route is currently protocol reconstruction, the child should achieve a material route reduction if duplicate/redundant work is present.

Minimum target: **25%** reduction of the six-Cell forced-miss p50 from 195.51 ms, nominally **146.6 ms or better**, unless profiling proves that the 120.69 ms consists of scientifically necessary unique reconstruction that cannot be reduced safely.

Do not stop merely on crossing the target if additional measured low-risk costs remain.

Report:

- 1/6-Cell miss p50/min/max;
- exact-hit p50;
- protocol reconstruction call count and p50 before/after;
- source-header lazy-load count;
- SQL count/time;
- raw rows;
- occurrence counts;
- response bytes;
- final stage distribution.
