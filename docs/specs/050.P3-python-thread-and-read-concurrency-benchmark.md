## Purpose

Measure how much of the current post-050 multi-Cell analysis latency can be reduced with **Python-side concurrency alone**, before introducing a Rust kernel or combined execution architecture.

This proto-child exists to answer one narrow question:

> For independent selected Cells, how much wall-time improvement comes from overlapping exact cache reads and/or running the existing per-Cell Python analysis path in a small bounded thread pool?

It is a benchmark/decision gate. It does **not** authorize production thread pools.

## Why this is a separate child

Earlier Spec 050 work removed large amounts of unnecessary work before concurrency was considered:

- 050.2/050.3 introduced cycle-addressable raw access for Time/Capacity;
- 050.5 showed broad normal Time/Capacity was then dominated by post-read transformation rather than raw Parquet I/O;
- 050.6 removed unconsumed phase/capacity work and reused prepared rows where beneficial;
- 050.7 reduced derivative postprocessing overhead;
- 050.8 extends selective exact detail reads to the other analysis families.

Representative accepted 050.6 normal Time-axis medians were approximately:

- 1 Cell / All: **90 ms** backend;
- 3 Cells / All: **267 ms**;
- 6 Cells / All: **543 ms**.

That near-linear multi-Cell scaling makes cross-Cell concurrency worth measuring, but the current post-050 bottleneck must be re-profiled rather than inferred from historical 050.5 percentages.

## Core hypothesis

Selected Cells are normally independent work units until deterministic result assembly:

```text
request + resolved immutable metadata
        |
        +--> Cell A -> exact required cache rows -> existing analysis work --+
        +--> Cell B -> exact required cache rows -> existing analysis work --+--> ordered merge
        +--> Cell C -> exact required cache rows -> existing analysis work --+
        +--> Cell D -> exact required cache rows -> existing analysis work --+
```

Python threads can still provide real concurrency when workers are waiting on I/O or executing native code that releases the GIL. The current path includes PyArrow/Parquet, NumPy and vectorized/native pandas work, so thread scaling must be measured rather than dismissed on the basis of the GIL alone.

Threads may still lose when the remaining work is Python-bytecode/GIL-bound, when several workers saturate the same SSD, or when nested native worker pools oversubscribe the machine.

## Locked decisions for promotion

1. **Profile the current production path first.** Do not reuse old 050.5 cost fractions as proof of the present bottleneck.
2. **Benchmark mechanisms separately.** Concurrent reads and whole-Cell threaded execution are distinct rows.
3. **Parallelize across Cells only.** Do not change or parallelize inside scientific formulas in this child.
4. **Use bounded worker counts.** Compare 2 and 4 threads; do not automatically use all logical CPUs.
5. **Preserve deterministic output order.** Completion order must never change Cell/series/result ordering.
6. **Do not share live ORM state across workers.** Resolve SQLAlchemy/relational state in the owning request thread and pass only immutable plain-data descriptors where needed.
7. **Do not parallelize exact persisted result-cache hits.** They remain the current direct fast path.
8. **Control native oversubscription.** Record relevant PyArrow/NumPy/BLAS/native thread settings.
9. **No whole-Cell RAM cache, speculative prefetch, migration, cache-layout redesign or `CALC_VERSION` bump.**
10. **No Rust implementation in this child.** Rust/Rayon is owned by 050.P5 so its contribution can be measured independently.
11. **No adaptive zoom or Plotly redesign.** Those are separate boundaries; adaptive zoom is owned by 050.P4.
12. **No production executor is authorized by benchmark code.** A later implementation child is required after the evidence is reviewed.

## Required benchmark phases

### A0 — current sequential production baseline

For each workload record the current post-050 stage decomposition:

- metadata/planning;
- raw/prepared Parquet read/decode;
- scientific transform;
- derivative work where applicable;
- result assembly/serialization;
- total backend wall time;
- CPU utilization/effective core usage.

This establishes what remains worth parallelizing.

### B1/B2 — concurrent reads only

Benchmark exact per-Cell cache read/decode concurrently while leaving the scientific transform sequential after the read phase:

- **B1:** 2 read threads;
- **B2:** 4 read threads.

This isolates whether overlapping PyArrow/Parquet/native decode work reduces wall time or merely creates storage contention.

### B3/B4 — whole existing per-Cell Python path in threads

Benchmark each Cell's existing read + transform path as one thread job:

- **B3:** 2 whole-Cell threads;
- **B4:** 4 whole-Cell threads.

Do not change the formulas or substitute a new algorithm merely to make threading scale.

B3/B4 versus B1/B2 must distinguish whether any gain comes mainly from read overlap or from native/GIL-releasing transform work as well.

## Required scientific workload matrix

Reuse existing fixtures/profilers and the compact/standard interactive contract. Do not invent a parallel-only scientific path.

### Normal Time/Capacity

At minimum:

- 1 Cell, All, Time axis;
- 3 Cells, All, Time axis;
- 6 Cells, All, Time axis;
- **10 Cells, All, Time axis when representative local data permit**;
- 1 Cell, All, capacity axis;
- 3 Cells, All, capacity axis;
- 6 Cells, All, capacity axis;
- one representative narrow multi-Cell range such as cycles 1-20.

### Derivative Time/Capacity

At minimum:

- 1 Cell, All, dQ/dV;
- 3 Cells, All, dQ/dV when the fixture permits;
- 6 Cells, All, dQ/dV when the fixture permits;
- one broad dV/dQ case;
- one small derivative range to detect dispatch regressions on small jobs.

### Controls

- exact persisted result-cache hit;
- one single-Cell request to show the expected near-zero cross-Cell concurrency benefit;
- one continuation-boundary case when representative data exist;
- one narrow viewport-like/range request so later comparison with 050.P4 is possible without implementing adaptive zoom here.

Record `NOT RUN` rather than fabricating unavailable multi-Cell or browser evidence.

## Measurements

For every applicable row, record at minimum:

- total backend wall time;
- per-Cell job wall time;
- aggregate CPU time where measurable;
- process CPU utilization/effective core usage;
- peak RSS;
- raw/prepared row groups and rows materialized;
- Parquet read/decode time;
- transform time;
- derivative time where applicable;
- result assembly/serialization time;
- worker dispatch/queue time;
- worker count;
- relevant native-library thread settings;
- scientific payload digest/equality;
- canonical output ordering.

Use at least five repetitions for controlled comparisons where practical. Report median and range/min/max. Alternate or randomize candidate order when useful so filesystem/OS-cache warming does not systematically favor one strategy.

## Required questions and decision output

A promoted numeric child must answer:

1. What fraction of the current representative multi-Cell wall time is read/decode versus transform versus assembly?
2. Does sequential execution already use multiple cores materially through native libraries?
3. What gain comes from concurrent reads alone?
4. What additional gain, if any, comes from whole-Cell Python threading?
5. Does 2 or 4 threads materially increase peak RAM or I/O contention?
6. Does any threaded candidate change numerical output, provenance or deterministic ordering?
7. Is thread scaling strong enough to justify a later production implementation child?
8. Which remaining measured CPU kernel, if any, is large and stable enough to justify the separate 050.P5 Rust/Rayon benchmark?

The result must explicitly choose one of:

- **P3-A — remain sequential:** no stable material wall-time gain;
- **P3-B — read concurrency is useful:** exact-read overlap helps, but whole-Cell threading adds little;
- **P3-C — whole-Cell threading is useful:** 2 or 4 threads materially reduce representative multi-Cell wall time;
- **P3-D — Python threading is limited by a remaining CPU/GIL boundary:** record the measured kernel for 050.P5 rather than jumping directly to multiprocessing.

The smallest worker count that captures most of the gain is preferred. Four workers are not selected merely because four were benchmarked.

At minimum:

Browser/manual evidence is required only for claims about user-visible total latency; backend-only measurements must be labelled as backend evidence.

## Explicit out of scope

Until separately promoted, do not:

- add a production thread or process pool;
- implement Rust/PyO3/Rayon;
- change scientific calculations or result schemas;
- parallelize inside one Cell/formula;
- share SQLAlchemy sessions across workers;
- add a whole-Cell RAM cache or speculative prefetch;
- redesign persistent raw/prepared cache layout;
- redesign Plotly traces;
- implement adaptive zoom;
- reintroduce 050.P2 progressive streaming;
- add a migration or bump `CALC_VERSION` for benchmark-only work.
