## Purpose

Determine how CellXplorer should execute independent per-Cell analysis work after the earlier Spec
050 changes have removed unnecessary reads and unnecessary calculations.

This proto-child exists because the remaining performance question is no longer simply "is Python
slow?" or "is Parquet slow?". Earlier profiling showed that the dominant cost moved as each
optimization landed:

1. 050.2/050.3 removed unnecessary full-source raw materialization from Time/Capacity range reads;
2. 050.5 showed that the dominant broad normal-view cost was then post-read transformation,
   especially phase-capacity reconstruction rather than indexed Parquet I/O;
3. 050.6 removed unconsumed transforms and reused exact prepared phase/capacity rows where measured
   beneficial;
4. 050.7 substantially reduced derivative control/postprocessing overhead;
5. 050.8 applies the same `read less first` principle to Steps, DCIR, Chargeability and Rate
   Capability.

The next valid question is therefore which parts of the **necessary remaining multi-Cell work**
benefit from concurrency or native execution, and whether those gains remain after all boundary,
I/O, memory and packaging costs are included.

This proto-child does **not** authorize production concurrency or a production Rust extension. If
promoted, its first numeric child remains a benchmark/decision gate. Production execution changes
must be implemented only by a later child after the benchmark demonstrates which mechanism or
combination materially reduces wall time without scientific, memory, storage or packaging
regressions.

## Verified evidence that motivates this proto-child

### Historical Time/Capacity bottleneck was not primarily raw file I/O

The accepted 050.5 profiling decomposition showed, on the representative six-Cell / All
Time/Capacity workload:

- indexed raw I/O: approximately **284 ms**;
- phase-capacity reconstruction: approximately **2,707 ms**;
- backend total: approximately **4,419 ms**.

Thus the original broad normal-view slowdown was dominated by post-read scientific preparation, not
Parquet access.

050.6 subsequently changed that production path. Representative six-Cell / All / Time medians fell
from approximately **4,419 ms to 543 ms**, while six-Cell / All / capacity-axis requests used the
prepared phase/capacity representation and fell from approximately **1,219 ms forced fallback to
719 ms** on the accepted same-machine matrix.

### Derivative work was a separate computation hotspot

050.7 reduced the measured derivative stage while preserving the numerical algorithm:

- dQ/dV All: approximately **434 ms -> 156 ms**;
- dV/dQ All: approximately **421 ms -> 158 ms**.

The accepted All-cycle derivative structure still contained approximately:

- 71,190 selected rows;
- 908 contiguous runs;
- 454 eligible runs;
- 405 finite output segments / frontend traces.

Therefore derivative views remain a legitimate CPU/native-compute workload, but the previously
measured repeated Python/control overhead has already been reduced substantially.

### 050.8 confirms that read reduction and wall-time reduction are not interchangeable

The accepted 050.8 implementation evidence shows why concurrency must follow measurement rather than
architecture intuition:

- Steps reduced physical materialization from 18/18 row groups to 1/18 and improved the representative
  route median from about 51.5 ms to 35.4 ms;
- DCIR reduced 40/40 groups to 14/40 and improved about 247 ms to 70.9 ms;
- Chargeability reduced 6/6 groups to 1/6 but remained approximately 33.7 ms vs 34.0 ms because the
  remaining candidate/extraction work dominated that small fixture;
- Rate Capability reduced 6/6 groups to 5/6 and improved about 217.6 ms to 173.4 ms.

The same principle applies to parallelism and native execution: higher CPU utilization, more
simultaneous reads, or a faster isolated kernel are not acceptance criteria. The acceptance
criterion is reduced user-relevant wall time on the current production path.

## Execution boundaries to test

A multi-Cell Time/Capacity request naturally separates into at least three boundaries:

```text
resolve relational/protocol metadata
        |
        +--> read/decode exact required prepared/raw rows for Cell A --+
        +--> read/decode exact required prepared/raw rows for Cell B --+
        +--> read/decode exact required prepared/raw rows for Cell C --+
        +--> read/decode exact required prepared/raw rows for Cell D --+
                                                                    |
                                                                    v
                                                       scientific transforms
                                                       / derivatives / downsample
                                                                    |
                                                                    v
                                                       deterministic result assembly
                                                       + serialization
```

The benchmark must distinguish these costs instead of treating "parallel execution" as one opaque
change.

The candidate mechanisms are:

1. **Concurrent Python/PyArrow reads.** Use a small bounded thread pool only for independent Cell
   read/decode work, then perform the existing Python scientific transform sequentially. This
   isolates the value of overlapping Parquet/native I/O and decode.
2. **Whole-Cell Python threads.** Execute each existing per-Cell read + transform job in a bounded
   thread pool. This tests the simplest production architecture and captures any concurrency from
   PyArrow, NumPy and other native operations that release the GIL.
3. **Sequential Rust native kernel.** Keep reads sequential and replace only a measured transform /
   derivative / downsampling kernel with a compiled Rust implementation that uses one native worker.
   This isolates the value of native execution from parallelism.
4. **Parallel Rust/Rayon kernel.** Keep reads sequential and execute the same Rust kernel across
   Cells using a bounded Rayon worker count. This isolates the additional value of native
   cross-Cell parallelism over the sequential Rust kernel.
5. **Hybrid concurrent reads + sequential Rust kernel.** Overlap PyArrow reads but keep the Rust
   compute itself single-worker. This measures whether I/O overlap and native compute gains add
   without introducing native compute concurrency.
6. **Hybrid concurrent reads + parallel Rust/Rayon kernel.** Overlap independent reads, then run
   the compact numerical work through the bounded parallel Rust kernel. This is the full candidate
   architecture, but it is tested only after the isolated components so its gains are attributable.
7. **Persistent Python processes only as an optional control.** Evaluate them only if the current
   profile shows material Python/GIL-bound work and neither threads nor a viable Rust prototype
   answers it. Python multiprocessing is no longer the default second step merely because threads
   scale weakly.

The benchmark must test each applicable mechanism **alone before combinations**. A combined result
must never be presented without the isolated component results that explain where its gain came
from.

## Why Python threads are credible

The GIL prevents simultaneous execution of Python bytecode; it does not prevent useful concurrency
while a worker is executing native code or waiting on I/O. The current analysis path contains
substantial work in PyArrow/Parquet, NumPy and native/vectorized pandas operations. A small thread
pool may therefore overlap real work even though CellXplorer remains a Python service.

Threads are attractive because:

- dispatch/startup overhead is small;
- workers share the same process memory without IPC serialization;
- PyArrow/Parquet read/decode is native work;
- NumPy operations commonly execute outside the GIL;
- portions of pandas backed by vectorized native kernels may also release the GIL;
- independent Cells map naturally to independent jobs;
- Windows packaging does not gain a second multiprocessing lifecycle.

Threads are not assumed to win. They can lose when:

- the remaining work is mostly Python bytecode holding the GIL;
- several workers saturate one SSD and simply create storage contention;
- native libraries already use internal threads and application-level concurrency oversubscribes the
  machine;
- per-Cell jobs are too small for dispatch/synchronization overhead to amortize.

## Why a Rust/Rayon kernel is a first-class benchmark candidate

A compiled Rust kernel can address a different boundary from read concurrency. Python may remain the
orchestration, relational, protocol and provenance layer while Rust owns only a compact measured
array kernel.

The desired shape is conceptually:

```text
Python resolves Cell/protocol/cache metadata
        |
        +--> exact NumPy/Arrow-compatible numeric buffers for selected Cells
        |
        v
one coarse Python -> Rust call
        |
        +--> Cell A numeric kernel --+
        +--> Cell B numeric kernel --+
        +--> Cell C numeric kernel --+--> deterministic compact arrays
        +--> Cell D numeric kernel --+
        |
        v
Python result/provenance assembly + serialization
```

The prototype should use a coarse boundary with contiguous numeric buffers rather than thousands of
fine-grained Python/Rust calls. Borrow NumPy-compatible buffers without copying where practical. If
copying, dtype conversion, string conversion or ownership transfer is required, **measure and include
that boundary cost** in the candidate wall time.

Rust does not eliminate all cost. It cannot make SQLite/ORM resolution, Parquet materialization,
JSON serialization or Plotly rendering disappear. That is why sequential Rust, parallel Rust and
hybrid read+Rust cases are separate benchmark rows.

### Rayon lifecycle

Rayon normally maintains reusable native worker threads inside the process. This is materially
different from a Windows Python process pool:

- no second Python interpreter;
- no per-request `spawn`;
- no DataFrame pickling/IPC;
- shared process address space;
- native parallel CPU execution without the Python GIL.

The benchmark must nevertheless record:

- first Rust call including module/kernel initialization;
- first parallel call including any lazy Rayon-pool initialization;
- steady-state warm calls;
- worker count;
- native-thread oversubscription with PyArrow/BLAS/NumPy;
- resident-memory change.

Do not hide a one-time initialization penalty inside steady-state medians, and do not omit it from
startup/packaging feasibility either.

## Rust kernel scope for the benchmark

Do **not** port the analysis engine wholesale. Re-profile first and prototype only compact kernels
that are both measurable and scientifically stable.

Potential Time/Capacity candidates include:

- display-row selection/downsampling when that stage is material;
- contiguous segment/run classification;
- derivative smoothing/rolling work;
- derivative gradient/postprocessing;
- finite-row selection and compact output-index generation;
- other array transforms proven material by the current profiler.

For ordinary consecutive Voltage vs Time after 050.6, the transform may already be cheap enough that
Rust contributes little. That is a valid outcome. Derivative views are a stronger candidate because
050.7 still measured material derivative work after the earlier Python-side optimization.

Scientific formulas and semantics are not redesigned for Rust. The prototype must reproduce the
current algorithm and output contract.

## Locked decisions for any future promotion

1. **Measure the current post-050.8 production path first.** Historical 050.5 percentages are
   evidence about why 050.6 existed, not proof of the current bottleneck.
2. **Benchmark components independently before combinations.** At minimum isolate read concurrency,
   whole-Cell Python threads, sequential Rust, parallel Rust, and the justified hybrids.
3. **Parallelize across Cells before parallelizing inside one Cell/formula.** Existing per-Cell
   scientific semantics remain the implementation contract.
4. **Preserve deterministic output order.** Completion order must never change canonical
   Cell/series/result ordering.
5. **Threads are the lowest-complexity production candidate, not the predetermined winner.** Test
   sequential, 2 threads and 4 threads.
6. **Rust/Rayon is a first-class benchmark candidate when the current profile exposes a compact
   numerical kernel.** It no longer waits behind Python multiprocessing.
7. **Rust must be benchmarked sequentially before Rayon.** This separates native-code acceleration
   from parallel acceleration.
8. **Hybrid read+Rust must be benchmarked only after the isolated components.** Report whether the
   combined gain is additive, sub-additive or negative.
9. **Processes require separate evidence.** Benchmark a persistent process pool only when current
   profiling identifies substantial Python/GIL-bound work and there remains a useful unanswered
   comparison after thread/Rust experiments.
10. **No per-request Python process spawning.** If processes are evaluated, workers are persistent
    for the backend lifetime or another equivalently bounded lifecycle.
11. **Do not send live ORM state across execution boundaries.** SQLAlchemy sessions, ORM entities,
    connections and transactions remain owned by the request/main process.
12. **Do not pickle whole source DataFrames merely to gain CPU parallelism.** Process experiments
    receive compact immutable descriptors and open their own exact cache groups.
13. **Bound worker counts.** Initial thread/Rayon/process comparisons use 1/2/4 workers as applicable;
    do not automatically scale to all logical CPUs.
14. **Control nested native parallelism.** Record or bound PyArrow, NumPy/BLAS, Rayon and other native
    worker counts so `4 application workers x N native threads` is not mistaken for a fair result.
15. **Do not parallelize exact persisted result-cache hits.** A cache hit remains the existing direct
    fast path.
16. **Do not add a whole-Cell RAM cache or speculative prefetch as part of this work.**
17. **Do not change scientific meaning, formulas, provenance, continuation semantics, protocol
    matching, hidden/excluded semantics, exports or saved-plot identity.**
18. **No SQLite migration or scientific/cache version bump for benchmark-only work.**
19. **Frontend/Plotly work remains a separate ownership boundary.** Record Plotly contribution but do
    not combine a Plotly architecture change with the backend execution benchmark.
20. **Adaptive zoom remains owned by 050.P4.** P3 may use a narrow viewport/range as a workload
    control, but it must not implement viewport refinement itself.

## Required ablation matrix after promotion

The promoted numeric child must retain one table where rows are execution strategies and columns are
identical scientific workloads. Do not report only the fastest combination.

### Phase A — establish current baseline

- **A0 — sequential Python production path.** Existing implementation, no benchmark concurrency.
- Record current stage decomposition and CPU/native-thread behavior.

### Phase B — isolate Python concurrency

- **B1 — concurrent-read only, 2 threads.** Parallelize exact per-Cell read/decode; existing Python
  scientific transform remains sequential after reads finish.
- **B2 — concurrent-read only, 4 threads.** Same with 4 read workers.
- **B3 — whole-Cell existing Python path, 2 threads.** Each Cell performs existing read + transform
  in a thread.
- **B4 — whole-Cell existing Python path, 4 threads.** Same with 4 workers.

This phase distinguishes "threads helped because Parquet/native reads overlapped" from "the whole
existing Cell job scales in threads".

### Phase C — isolate native execution

Only prototype a Rust kernel after the Phase-A profile identifies a compact material kernel.

- **C1 — sequential Rust kernel.** Sequential reads; Rust kernel forced to one worker.
- **C2 — Rust/Rayon kernel, 2 workers.** Sequential reads; same Rust kernel parallel across Cells.
- **C3 — Rust/Rayon kernel, 4 workers.** Sequential reads; same Rust kernel parallel across Cells.

For every C row report Python->Rust boundary/copy time independently. C1 vs A0 isolates the native
kernel gain. C2/C3 vs C1 isolate the Rayon parallel gain.

### Phase D — combinations

Run only after Phases B/C establish useful isolated effects:

- **D1 — best concurrent-read configuration + sequential Rust kernel.** Isolates whether read overlap
  and native compute gains compose without parallel Rust compute.
- **D2 — best concurrent-read configuration + best bounded Rayon configuration.** Full hybrid.
- **D3 — whole-Cell Python threads plus an internally parallel Rust kernel only if architecture makes
  that combination meaningful and oversubscription can be controlled.** Do not run it merely to
  create another row.

For each combination calculate and report the expected additive improvement from its isolated parts
and the actual measured improvement. Explicitly state whether interaction between the mechanisms is
additive, sub-additive, neutral or negative.

### Phase E — optional Python process control

Only when justified by the current profile:

- **E1 — persistent 2-process pool**;
- **E2 — persistent 4-process pool**.

Processes are a control/fallback, not a mandatory benchmark if threads and/or Rust already answer the
measured bottleneck.

## Benchmark questions a promoted numeric child must answer

1. For broad multi-Cell Time/Capacity normal views, what fraction of backend wall time is now:
   - raw/prepared Parquet read/decode;
   - scientific transform work;
   - derivative work where applicable;
   - Python/native boundary conversion where applicable;
   - response assembly/serialization?
2. Does sequential production execution already use more than one CPU core materially because native
   libraries release the GIL or create internal workers?
3. How much does **read concurrency alone** change wall time and physical I/O behavior?
4. How much does **whole-Cell Python threading alone** change wall time?
5. How much faster/slower is the **same candidate kernel in sequential Rust** than the current Python /
   NumPy/pandas implementation after boundary/copy cost is included?
6. How much additional gain comes specifically from **Rayon 2/4-way parallelism** over sequential
   Rust?
7. Does the **hybrid concurrent-read + Rust/Rayon** architecture add the isolated gains, or do I/O,
   memory bandwidth or thread oversubscription make the result sub-additive?
8. Does adding workers reduce total I/O wall time or merely increase storage contention?
9. Does any candidate materially increase peak RAM or temporary allocation volume?
10. What is the cold first-call cost of the Rust extension and Rayon initialization, and what is the
    warm steady-state cost?
11. Does any candidate change response ordering, numerical values, provenance or cache behavior?
12. After the best backend candidate, what fraction of end-to-end latency is frontend/Plotly?
13. Is the remaining backend gain large enough to justify a production implementation child?

## Measurements

Record at minimum for every applicable candidate:

- total backend wall time;
- per-Cell job wall time;
- aggregate CPU time where measurable;
- process CPU utilization / effective core usage;
- peak RSS / process memory;
- temporary allocation or copied-byte estimate where measurable;
- raw/prepared row groups and rows materialized;
- Parquet read/decode time;
- scientific transform time;
- derivative time when applicable;
- Python->Rust boundary/conversion/copy time when applicable;
- Rust kernel time when applicable;
- Rayon queue/parallel-region time when applicable;
- result assembly and serialization time;
- Python worker dispatch/queue time when applicable;
- worker count(s);
- relevant PyArrow/NumPy/BLAS/Rayon native-thread settings;
- scientific payload equality/tolerance report;
- canonical result ordering.

For Rust candidates additionally record:

- extension/module load state;
- first-call latency;
- first parallel-call latency;
- warm-call median;
- whether each input/output buffer is borrowed zero-copy or copied;
- bytes copied across the boundary;
- selected Rust compiler/profile and relevant target settings;
- Windows packaged-runtime feasibility if the benchmark reaches packaging validation.

When an installed-app/browser run is available, also retain:

- HTTP/fetch/parse time;
- frontend trace/layout preparation;
- Plotly completion;
- total interaction time;
- Plotly trace count.

Use at least five repetitions for controlled backend comparisons where practical. Report median and
range/min/max. Do not silently discard outliers. Randomize or alternate candidate order where useful
so filesystem/OS-cache warming does not systematically favor the last strategy.

## Scientific parity requirements

The benchmark is performance-only; it does not authorize a scientific algorithm change.

For selection/index/downsampling operations that should be exact, require exact canonical output and
provenance equality.

For floating-point kernels that are reimplemented in Rust:

- preserve the current mathematical algorithm and operation semantics;
- compare against the current Python implementation using the repository's existing scientific/golden
  tolerances;
- report maximum absolute and relative deviation for affected arrays;
- require identical finite/non-finite placement, segmentation, Cell ordering and provenance;
- do not accept a faster kernel whose numerical difference exceeds existing scientific acceptance;
- do not bump `CALC_VERSION` merely because the same calculation is implemented in compiled code.

If exact digest equality is achievable, record it. If floating implementation details prevent
bit-for-bit equality but values remain within established tolerances, record that explicitly rather
than silently weakening the comparison.

## Decision table

The promoted child should finish with one explicit decision and an attribution table showing the
isolated speedup of each mechanism.

### Outcome A — remain sequential Python

Choose when none of the isolated or combined candidates produces a material, stable wall-time
improvement after memory, I/O, boundary and packaging costs are included.

### Outcome B — implement bounded Python threads

Choose when read-only or whole-Cell 2/4-thread execution materially reduces representative multi-Cell
backend wall time and captures most of the useful gain without scientific/output changes,
pathological memory growth or small-request regression.

The later implementation child must use the smallest worker count that captures most of the gain.

### Outcome C — implement a sequential Rust kernel

Choose when native execution materially reduces the measured numerical kernel but Rayon adds little
or the workload is usually single-Cell. Keep the production Rust boundary as small as the benchmark
justifies.

### Outcome D — implement bounded Rust/Rayon cross-Cell compute

Choose when sequential Rust is beneficial and 2/4-way Rayon produces an additional material,
stable reduction after boundary cost and nested-thread controls are included.

### Outcome E — implement the hybrid concurrent-read + Rust/Rayon architecture

Choose only when both isolated mechanisms are individually useful and their combination produces the
best stable user-relevant wall time. The implementation record must state how much of the final gain
came from read concurrency, native execution and Rayon parallelism separately.

### Outcome F — implement bounded persistent Python processes

Choose only when threads scale weakly, profiling supports a GIL/CPU explanation, the Rust route is
infeasible or inferior for the measured kernel, and a persistent process pool is materially better
after startup lifecycle, memory, IPC and storage contention are included.

### Outcome G — backend execution is no longer the dominant user-visible opportunity

Choose when backend work is already small enough that frontend/Plotly, transport or another measured
stage dominates the end-to-end interaction. Author a separate child for that measured boundary
rather than forcing a backend execution change.

## Plotly and adaptive-zoom boundaries

Backend execution optimization cannot solve Plotly render/update time.

Current branch facts relevant to the later decision:

- interactive ordinary line/marker traces are already converted to `scattergl` when WebGL is
  available;
- derivative rendering currently creates one Plotly trace for each finite contiguous
  `(cycle, phase)` derivative segment;
- accepted 050.7 evidence still reported 405 output segments/traces for the representative All-cycle
  derivative case;
- the 050.4 installed-app profile measured roughly 388 ms of Plotly completion in the earlier
  All-cycle derivative case with hundreds of traces;
- the Time/Capacity card passes the complete current trace array through the shared
  `react-plotly.js` component and records Plotly completion at `onInitialized` / `onUpdate`.

Therefore a later frontend child, if current re-profiling confirms derivative Plotly remains
material, should investigate interactive derivative trace consolidation before replacing Plotly or
reviving progressive streaming.

Separately, 050.P4 owns the hypothesis that an ordinary consecutive Voltage vs Time plot can remain
at approximately 4,000 displayed points per Cell while a zoomed viewport fetches or selects a denser
representation of only the visible window. P3 must not implement that behavior, but its narrow-range
control should make it possible to estimate whether the best backend execution strategy is likely to
compose well with adaptive zoom.

Do **not** use the failed 050.P2 progressive-series streaming experiment as the default Plotly
solution. Incremental series arrival and static final-figure render cost are separate questions.

## Verification requirements after promotion

The measurement child must not alter scientific meaning. At minimum:

- focused Time/Capacity path/profiler tests affected by benchmark instrumentation;
- `python -m unittest tests.test_golden_analysis` if production scientific/service code is touched;
- exact/tolerance scientific parity across sequential/thread/Rust/Rayon/process candidates as defined
  above;
- deterministic ordering checks despite out-of-order completion;
- current cache-hit path regression showing no worker/native dispatch on an exact result hit;
- current structural row-group/read diagnostics remain valid;
- first-call vs warm-call native initialization measurement if Rust is prototyped;
- memory and worker-lifecycle teardown checks for any benchmark pools;
- Windows build/import smoke check for the Rust prototype if a Rust candidate survives the local
  performance gate;
- `git diff --check`;
- canonical `python scripts\preflight.py`.

Browser/manual verification is required only for claims about user-visible total or Plotly latency.
Backend-only measurements must be described as backend evidence.

## Explicit out of scope

Until separately promoted for production, do not:

- add production thread/process pools;
- ship a production Rust/PyO3/Rayon path from this measurement child;
- port the analysis engine wholesale to Rust;
- change family scientific calculations or algorithms;
- parallelize within one scientific formula/segment unless a later measured child explicitly scopes
  that work;
- share SQLAlchemy sessions across workers/native code;
- serialize whole DataFrames to process workers;
- change persistent raw/prepared cache layout;
- add a whole-Cell RAM cache or speculative prefetch;
- redesign Plotly traces;
- implement 050.P4 adaptive zoom;
- reintroduce 050.P2 progressive streaming;
- change result schemas, scientific cache meaning or `CALC_VERSION`;
- add a migration;
- change saved-plot/export/portable behavior;
- modify unrelated analysis editor code.

A benchmark-only Rust module is permitted after promotion solely to measure a compact current kernel;
that permission does not authorize production use.

## Promotion criteria

Promote this proto-child only when all are true:

1. 050.8 is review-clean or otherwise stable enough that the cross-family selective-access work will
   not invalidate the benchmark baseline.
2. The user/spec author explicitly chooses to investigate cross-Cell execution and native-kernel
   alternatives.
3. The promoted numeric child is written as a self-contained **benchmark/decision** child, not as a
   preselected thread/process/Rust implementation.
4. Current production profiling is included so the old 050.5 bottleneck is not assumed to still
   dominate.
5. The benchmark preserves the isolated-strategy ablation matrix before any combined architecture is
   judged.
6. Backend execution, 050.P4 adaptive zoom and Plotly/frontend implementation remain separate later
   implementation scopes even if all are found worthwhile.

The proto ID `050.P3` remains historically reserved after promotion and must not be reused.
