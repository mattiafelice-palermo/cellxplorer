# Spec 050.P3: cross-Cell parallel execution benchmark and decision

Status: **Proto-child — non-implementable until promoted**  
Parent: [`050-runtime-performance-optimization.md`](050-runtime-performance-optimization.md)  
Branch: `feature/runtime-performance-optimization`  
Related design note: [`050-performance-data-access-and-parallelism-notes.md`](050-performance-data-access-and-parallelism-notes.md)  
Origin: user discussion after review-clean 050.6/050.7 and implementation of 050.8, 2026-08-22.

## Purpose

Determine whether CellXplorer should parallelize independent per-Cell analysis work after the earlier
Spec 050 changes have removed unnecessary reads and unnecessary calculations.

This proto-child exists because the remaining performance question is no longer simply "is Python
slow?" or "is Parquet slow?". Earlier profiling showed that the dominant cost moved as each
optimization landed:

1. 050.2/050.3 removed unnecessary full-source raw materialization from Time/Capacity range reads;
2. 050.5 showed that the dominant broad normal-view cost was then post-read transformation,
   especially phase-capacity reconstruction rather than indexed Parquet I/O;
3. 050.6 removed unconsumed transforms and reused exact prepared phase/capacity rows where measured
   beneficial;
4. 050.7 substantially reduced derivative control/postprocessing overhead;
5. 050.8 applies the same `read less first` principle to Steps, DCIR, Chargeability and Rate
   Capability.

The next valid question is therefore whether the **necessary remaining work for multiple selected
Cells** should execute concurrently.

This proto-child does **not** authorize production concurrency. If promoted, its first numeric child
must remain a benchmark/decision gate. Production parallel execution should be implemented only by a
later child after the current branch demonstrates which concurrency model actually reduces wall time
without scientific, memory, storage or packaging regressions.

## Verified evidence that motivates this proto-child

### Historical Time/Capacity bottleneck was not primarily raw file I/O

The accepted 050.5 profiling decomposition showed, on the representative six-Cell / All
Time/Capacity workload:

- indexed raw I/O: approximately **284 ms**;
- phase-capacity reconstruction: approximately **2,707 ms**;
- backend total: approximately **4,419 ms**.

Thus the original broad normal-view slowdown was dominated by post-read scientific preparation, not
Parquet access.

050.6 subsequently changed that production path. Representative six-Cell / All / Time medians fell
from approximately **4,419 ms to 543 ms**, while six-Cell / All / capacity-axis requests used the
prepared phase/capacity representation and fell from approximately **1,219 ms forced fallback to
719 ms** on the accepted same-machine matrix.

### Derivative work was a separate computation hotspot

050.7 reduced the measured derivative stage while preserving the numerical algorithm:

- dQ/dV All: approximately **434 ms -> 156 ms**;
- dV/dQ All: approximately **421 ms -> 158 ms**.

The accepted All-cycle derivative structure still contained approximately:

- 71,190 selected rows;
- 908 contiguous runs;
- 454 eligible runs;
- 405 finite output segments / frontend traces.

Therefore derivative views remain a legitimate CPU/native-compute workload, but the previously
measured repeated Python/control overhead has already been reduced substantially.

### 050.8 confirms that read reduction and wall-time reduction are not interchangeable

The accepted 050.8 implementation evidence shows why concurrency must follow measurement rather than
architecture intuition:

- Steps reduced physical materialization from 18/18 row groups to 1/18 and improved the representative
  route median from about 51.5 ms to 35.4 ms;
- DCIR reduced 40/40 groups to 14/40 and improved about 247 ms to 70.9 ms;
- Chargeability reduced 6/6 groups to 1/6 but remained approximately 33.7 ms vs 34.0 ms because the
  remaining candidate/extraction work dominated that small fixture;
- Rate Capability reduced 6/6 groups to 5/6 and improved about 217.6 ms to 173.4 ms.

The same principle applies to parallelism: higher CPU utilization or more simultaneous reads are not
the acceptance criterion. The acceptance criterion is reduced user-relevant wall time on the
current production path.

## Core hypothesis

For a multi-Cell analysis, the selected Cells are usually independent scientific work units until
final aggregation/result assembly:

```text
request + resolved immutable metadata
        |
        +--> Cell A -> exact required row groups -> existing scientific compute --+
        +--> Cell B -> exact required row groups -> existing scientific compute --+--> deterministic merge
        +--> Cell C -> exact required row groups -> existing scientific compute --+
        +--> Cell D -> exact required row groups -> existing scientific compute --+
```

If the current remaining per-Cell work is dominated by PyArrow/Parquet decode, NumPy operations, or
other native code that releases the GIL, a small persistent thread pool may reduce wall time with
minimal dispatch and serialization overhead.

If the remaining work is instead substantially Python/GIL-bound, threads may scale poorly and a
small persistent process pool may win despite higher memory and IPC cost.

The benchmark must decide between those cases. Do not assume either one in advance.

## Locked decisions for any future promotion

1. **Measure the current post-050.8 production path first.** Historical 050.5 percentages are
   evidence about why 050.6 existed, not proof of the current bottleneck.
2. **Parallelize across Cells, not inside scientific formulas.** Existing per-Cell scientific
   calculations remain the single implementation of record.
3. **Preserve deterministic output order.** Worker completion order must never change canonical
   Cell/series/result ordering.
4. **Threads are the first concurrency experiment.** Benchmark sequential, 2 threads, then 4
   threads before authorizing process-based execution.
5. **Processes require evidence.** Benchmark a persistent process pool only when thread scaling is
   weak and current profiling identifies substantial Python/GIL-bound CPU work or another measured
   reason processes should win.
6. **No per-request process spawning.** If processes are evaluated, workers are created once for the
   backend process lifetime or another equivalently persistent bounded lifecycle. Windows `spawn`
   cost must not be paid once per plot or once per Cell.
7. **Do not send live ORM state to workers.** SQLAlchemy sessions, ORM entities, connections and
   transactions remain owned by the request/main process. Resolve relational state first and pass
   immutable plain-data descriptors only.
8. **Do not pickle whole source DataFrames merely to gain CPU parallelism.** A process worker should
   receive compact job descriptors and open the exact required prepared/raw Parquet groups itself.
9. **Bound worker count.** Initial comparison is 2 and 4 workers. Do not scale automatically to all
   logical CPUs.
10. **Control nested native parallelism.** Record or bound PyArrow, NumPy/BLAS and other native
    worker counts so `4 application workers x N native threads` is not mistaken for a fair result.
11. **Do not parallelize exact persisted result-cache hits.** A cache hit should remain the existing
    direct fast path.
12. **Do not add a whole-Cell RAM cache or speculative prefetch as part of this work.** Concurrency
    is evaluated against the current bounded persistent-cache architecture.
13. **Do not change scientific meaning, formulas, provenance, continuation semantics, protocol
    matching, hidden/excluded semantics, exports or saved-plot identity.**
14. **No SQLite migration or scientific/cache version bump for the benchmark itself.**
15. **Rust is not a general fallback.** A PyO3/Rayon extension may be considered only after a later
    profile isolates a compact, stable, CPU-bound numerical kernel whose inputs/outputs are suitable
    contiguous arrays and whose Python/native-library implementation remains materially expensive.
16. **Frontend/Plotly work is a separate ownership boundary.** Record Plotly contribution in the
    end-to-end matrix, but do not change Plotly architecture in the same implementation child as
    backend concurrency.

## Why persistent threads are the first experiment

A persistent `ThreadPoolExecutor` is ordinary multithreading with a bounded, reused worker
lifecycle. It is the lowest-complexity candidate because:

- dispatch/startup overhead is small;
- workers share the same prepared/cache memory without IPC serialization;
- PyArrow/Parquet read/decode work can execute in native code;
- NumPy operations commonly execute outside the GIL;
- portions of pandas backed by native vectorized operations may also release the GIL;
- independent Cells map naturally to independent jobs;
- Windows packaging does not gain a second multiprocessing lifecycle unless measurement requires it.

Threads are not assumed to win. They can lose when:

- the remaining work is mostly Python bytecode holding the GIL;
- several workers saturate one SSD and simply create storage contention;
- native libraries already use internal threads and application-level concurrency oversubscribes the
  machine;
- per-Cell jobs are too small for dispatch/synchronization overhead to amortize.

## Why a persistent process pool is the second experiment

A small `ProcessPoolExecutor` or equivalent can bypass the GIL for Python-heavy per-Cell work, but
its benefit must exceed:

- Windows process-lifecycle complexity;
- higher resident memory;
- worker initialization/import cost;
- IPC/serialization;
- duplicated native-library state;
- possible concurrent Parquet I/O contention.

If measured, process jobs should resemble:

```text
{
    source/cache identities,
    parser/scientific versions,
    requested cycles/steps,
    analysis settings,
    scalar Cell metadata,
    compact protocol/planner state
}
```

rather than an ORM object graph or a large pandas DataFrame.

Each worker may open the exact required prepared/raw cache groups itself. The caller then merges
compact scientific results in the original deterministic Cell/selection order.

## Benchmark questions a promoted numeric child must answer

A promoted measurement child must answer all of the following from the **current** branch:

1. For broad multi-Cell Time/Capacity normal views, what fraction of backend wall time is now:
   - raw/prepared Parquet read/decode;
   - scientific transform work;
   - derivative work where applicable;
   - response assembly/serialization?
2. Does the workload use more than one CPU core materially during sequential execution because
   native libraries already release the GIL or create internal workers?
3. How does backend wall time scale for the same scientific request under:
   - sequential execution;
   - 2 persistent threads;
   - 4 persistent threads;
   - 2 persistent processes, only if justified;
   - 4 persistent processes, only if justified?
4. Does adding workers reduce total I/O wall time or merely increase storage contention?
5. Does parallel execution increase peak RAM materially?
6. Does any candidate change response ordering, floating-point payloads, provenance or cache
   behavior?
7. After the best backend candidate, what fraction of end-to-end latency is now frontend/Plotly?
8. Is the remaining backend gain large enough to justify a production implementation child?

- per-Cell job wall time;

- peak RSS / process memory;
- raw/prepared row groups and rows materialized;
- Parquet read/decode time;

- worker-pool dispatch/queue time;

- total interaction time;

Use at least five repetitions for controlled backend comparisons where practical. Report median and
range/min/max. Do not silently discard outliers.

## Decision table

The promoted child should finish with one explicit decision:

### Outcome A — remain sequential

Choose when neither threads nor processes produce a material, stable wall-time improvement after
accounting for memory and I/O contention.

### Outcome B — implement bounded persistent threads

Choose when a 2- or 4-thread pool materially reduces representative multi-Cell backend wall time
without scientific/output changes, pathological memory growth or small-request regression.

The later implementation child must use the smallest worker count that captures most of the gain.
Do not select four workers merely because four was benchmarked.

### Outcome C — implement bounded persistent processes

Choose only when threads scale weakly, profiling supports a GIL/CPU explanation, and a persistent
2- or 4-process pool produces a materially better net result after startup lifecycle, memory, IPC
and storage contention are included.

### Outcome D — backend parallelism is no longer the dominant user-visible opportunity

Choose when backend work is already small enough that frontend/Plotly, transport or another measured
stage dominates the end-to-end interaction. Author a separate child for that measured boundary
rather than forcing a concurrency implementation.

## Plotly boundary recorded by this proto-child

Backend parallel execution cannot solve Plotly render/update time.

Current branch facts relevant to the later decision:

- interactive ordinary line/marker traces are already converted to `scattergl` when WebGL is
  available;
- derivative rendering currently creates one Plotly trace for each finite contiguous
  `(cycle, phase)` derivative segment;
- accepted 050.7 evidence still reported 405 output segments/traces for the representative All-cycle
  derivative case;
- the 050.4 installed-app profile measured roughly 388 ms of Plotly completion in the earlier
  All-cycle derivative case with hundreds of traces;
- the Time/Capacity card passes the complete current trace array through the shared
  `react-plotly.js` component and records Plotly completion at `onInitialized` / `onUpdate`.

Therefore a later frontend child, if current re-profiling confirms Plotly remains material, should
investigate **interactive derivative trace consolidation before replacing Plotly or reviving
progressive streaming**.

The leading hypothesis is to preserve the backend scientific arrays and export representation but
coalesce interactive derivative segments by displayed scientific series and phase, using explicit
NaN/null separators between cycle segments and per-point metadata for cycle/phase/source hover
identity. Because current appearance is Cell/replicate-series scoped rather than cycle scoped, a
single Cell could potentially render as one charge trace plus one discharge trace instead of
hundreds of per-cycle segment traces while preserving visible line breaks and charge/discharge dash
semantics.

This is a hypothesis, not an authorized frontend change. A separate frontend-focused spec must
prove:

- visual parity;
- no line connection across scientific gaps;
- cycle/phase/source hover parity;
- legend and style-rule parity;
- zoom/pan behavior;
- saved plot, thumbnail and portable-report fidelity;
- vector/raster export behavior;
- data-export fidelity;
- actual installed-app Plotly wall-time reduction.

Do **not** use the failed 050.P2 progressive-series streaming experiment as the default Plotly
solution. Incremental series arrival and static final-figure render cost are separate questions.

## Verification requirements after promotion

The measurement child must not alter scientific meaning. At minimum:

- focused Time/Capacity path/profiler tests affected by benchmark instrumentation;
- `python -m unittest tests.test_golden_analysis` if production scientific/service code is touched;
- exact scientific payload/digest equality across sequential/thread/process candidates;
- deterministic ordering checks despite out-of-order worker completion;
- current cache-hit path regression showing no worker dispatch on an exact result hit;
- current structural row-group/read diagnostics remain valid;
- memory and worker-lifecycle teardown tests if any reusable pool code is temporarily introduced;
- `git diff --check`;
- canonical `python scripts\preflight.py`.

Browser/manual verification is required only for claims about user-visible total or Plotly latency.
Backend-only measurements must be described as backend evidence.

## Explicit out of scope

Until separately promoted, do not:

- add production thread/process pools;
- change family scientific calculations;
- parallelize within one scientific formula or derivative segment;
- share SQLAlchemy sessions across workers;
- serialize whole DataFrames to process workers;
- change persistent raw/prepared cache layout;
- add a whole-Cell RAM cache or speculative prefetch;
- implement Rust/PyO3/Rayon;
- redesign Plotly traces;
- reintroduce 050.P2 progressive streaming;
- change result schemas, scientific cache meaning or `CALC_VERSION`;
- add a migration;
- change saved-plot/export/portable behavior;
- modify unrelated analysis editor code.

## Promotion criteria

Promote this proto-child only when all are true:

1. 050.8 is review-clean or otherwise stable enough that the cross-family selective-access work will
   not invalidate the benchmark baseline.
2. The user/spec author explicitly chooses to investigate cross-Cell parallel execution.
3. The promoted numeric child is written as a self-contained **benchmark/decision** child, not as a
   preselected thread/process implementation.
4. Current production profiling is included so the old 050.5 bottleneck is not assumed to still
   dominate.
5. Backend concurrency and Plotly/frontend implementation remain separate later implementation
   scopes even if both are found to be worthwhile.

The proto ID `050.P3` remains historically reserved after promotion and must not be reused.
