# 051.2 — Time/Capacity consecutive capacity-axis concatenation

**Status:** Active implementation plan  
**Parent:** [`051-biologic-mpr-extensible-column-registry.md`](051-biologic-mpr-extensible-column-registry.md)

## Why this is a promoted child

The 051.1 browser acceptance established that BioLogic cycle reconstruction and capacity mapping are correct, but it also reproduced a real user-visible defect in the generic Time/Capacity plot path: `display_mode = consecutive` does not work when the X axis is capacity. The same behavior reproduces on Neware, and reviewer inspection confirms the owning logic predates Spec 051.

The user explicitly requires this defect to be fixed before the current workflow is considered complete. This child therefore keeps the fix isolated from BioLogic parsing while remaining on the already-open feature branch and workflow. Its implementation must be format-neutral and must work for both Neware and BioLogic canonical data.

## Goal

Make Time/Capacity `Consecutive` mode behave as an actual continuous acquisition-order capacity coordinate for all supported capacity X axes:

- Capacity (mAh);
- Specific capacity (mAh/g);
- Areal capacity (mAh/cm²).

The corrected plot must concatenate successive charge/discharge capacity segments instead of restarting the X coordinate at every phase or cycle boundary.

This is a **display-coordinate correction**, not a change to canonical capacity science. Raw/canonical charge and discharge capacities, `calc.per_cycle(...)`, prepared phase-capacity values, cycle identity, and exported scientific quantities must not be redefined.

## Verified current failure

Browser verification on the real application established:

- Cell 135 / EGG: Capacity + Consecutive is visibly scrambled; the compact API response contains 752 backward `display_x` transitions over 3,977 points;
- the first obvious reset is from approximately 58.163428 mAh to 0 at the next cycle/rest boundary;
- Time + Consecutive is monotonic;
- Neware control cells `BQV_2370`–`BQV_2374` reproduce the same defect, with seven backward `display_x` resets per Cell over cycles 1–3;
- overlap/reset and overlap/mirror behave as overlap modes;
- the frontend plots the backend-provided `display_x`; the malformed coordinate already exists before rendering.

The current owner is `backend/app/services/analysis_engine.py::_time_capacity_display_x(...)`. In `Consecutive`, it subtracts one origin from the selected capacity values. That is sufficient for an already-continuous time coordinate but cannot concatenate a capacity coordinate that resets at cycle/phase boundaries.

## Locked display semantics

### 1. Time + Consecutive is unchanged

Do not change the existing continuous-time behavior. The correction applies only when `x_axis` is one of the three capacity axes and `display_mode == "consecutive"`.

### 2. Overlap modes are unchanged

`overlap_reset` and `overlap_mirror` retain their current per-cycle/per-phase semantics. This child must not redesign them.

### 3. Capacity + Consecutive means acquisition-order concatenation

For one Cell, selected rows are traversed in canonical acquisition order.

The existing exact `phase_capacity` transform remains the scientific/display input for capacity progress inside a charge or discharge phase. Do not replace it with raw current integration or a second capacity calculation.

For each contiguous active charge/discharge segment in acquisition order:

1. take the segment's existing finite phase-capacity values;
2. normalize the first visible finite value of that segment to local progress 0;
3. add a running display offset equal to where the previous active segment ended;
4. preserve the segment's internal shape after removing only its segment origin;
5. at the next charge/discharge segment, continue from the previous displayed endpoint rather than restarting at 0.

Conceptually:

```text
segment_display_x = running_offset + (segment_capacity - segment_first_capacity)
running_offset = last_finite(segment_display_x)
```

Do not concatenate by cycle number alone. A cycle may contain multiple charge steps or multiple discharge steps that already belong to one phase-capacity segment, and the existing `phase_capacity` transform already handles source counter resets inside a phase.

### 4. Rest / neutral rows hold the current capacity coordinate

A rest/control row does not transfer capacity. In Consecutive capacity mode:

- rests before the first active segment use X = 0;
- rests between active segments hold the last finite displayed capacity coordinate;
- rests after the last active segment hold the final displayed coordinate.

This preserves acquisition continuity and allows voltage relaxation during rest to render vertically at fixed capacity instead of jumping back to a source counter value.

### 5. Boundary resets must not create backward jumps

A normal cycle/phase/source boundary must not produce a backward `display_x` reset merely because the underlying phase-capacity counter restarts.

Do not hide genuine within-segment source behavior by blindly applying `np.maximum.accumulate` or absolute values. The fix is segment-origin concatenation, not smoothing. Small within-segment decreases already preserved by the existing phase-capacity contract remain source/display behavior; the acceptance criterion specifically forbids reset-induced jumps at segment boundaries.

### 6. Each Cell owns its own origin

For a multi-Cell plot, each Cell's Consecutive capacity coordinate starts from its own X = 0. Do not concatenate different Cells together.

For a continued Cell with ordered SourceFiles, source boundaries do not reset the display coordinate if the selected acquisition continues into the next source. Existing stitched global-cycle/source ordering remains authoritative.

### 7. Selection and refinement must remain coordinate-stable

The existing cycle-range and adaptive/refinement paths must not make the same Cell shift horizontally merely because a refined response reads a subset of rows.

If a refinement request cannot derive the same Consecutive-capacity offset from its bounded subset, carry/derive the minimum required origin/offset through the existing owner-resolved request/refinement contract rather than reading the full source or reconstructing scientific state in the frontend.

Acceptance requires overview and refined responses for the same visible region to use compatible `display_x` coordinates.

## Ownership and implementation constraints

- Keep the corrected logic in backend Time/Capacity display-coordinate ownership. Do not implement capacity concatenation in React/Plotly.
- Prefer one shared helper used by the established analysis-engine fallback and the optimized ordinary Time/Capacity worker path so serial/process/fallback results cannot drift.
- Reuse `time_capacity_derived.phase_capacity(...)`; do not duplicate scientific capacity reconstruction.
- Do not add source-format conditionals. Neware and BioLogic must go through the same logic.
- Keep the transform O(n) in selected/display rows. Do not add per-cycle DataFrame scans or N² grouping.
- Do not read source files or add new Parquet reads merely to construct the display coordinate.
- Do not modify cycle reconstruction, parser behavior, canonical capacities, `calc.py`, or BioLogic-specific code for this defect.

## Cache/versioning consequences

The persisted Time/Capacity result payload contains `display_x`. Its meaning changes for Capacity + Consecutive, so stale result-cache entries must not survive the fix.

### Required

- bump `RESULT_SCHEMA_VERSIONS["time_capacity"]` in `backend/app/services/analysis_cache.py` from the current generation to the next generation (currently `5 -> 6` unless branch state changed before implementation);
- add/update cache tests proving an old Time/Capacity result-schema generation is not reused after the bump.

### Not required

- **do not bump global `CALC_VERSION`**: canonical/raw/per-cycle scientific meaning is unchanged;
- do not bump BioLogic/Neware parser identities;
- do not add a migration;
- do not bump the prepared-derived cache version solely for this display-coordinate correction unless implementation actually changes the persisted prepared-derived schema/meaning. If no prepared field changes, leave it alone.

## Required tests

Add focused tests that fail on the current implementation and pass only after true concatenation.

At minimum cover:

1. two-cycle charge/discharge capacity data where each phase resets to zero: Consecutive `display_x` concatenates without boundary resets;
2. charge -> rest -> discharge: rest rows hold the charge endpoint and discharge begins from that same X;
3. discharge -> rest -> charge ordering;
4. multiple same-direction steps within one phase: no artificial extra offset at step boundaries;
5. cycle transition: next cycle begins at the previous cycle's final displayed capacity rather than zero;
6. ordered multi-source Cell: source boundary preserves the running display coordinate;
7. raw mAh, mAh/g, and mAh/cm² axes follow equivalent concatenation semantics;
8. each Cell in a multi-Cell result starts from its own zero origin;
9. Time + Consecutive is byte/numerically unchanged for the same fixture;
10. overlap/reset and overlap/mirror are unchanged;
11. compact and non-compact ordinary Time/Capacity produce equivalent Consecutive-capacity coordinates before display-only downsampling differences;
12. optimized serial worker, process-worker result, and analysis-engine fallback agree on `display_x` for the same request;
13. adaptive/refinement response aligns with the overview coordinate for an overlapping region;
14. a persisted old Time/Capacity result-cache generation is invalidated by the schema-version bump;
15. Neware fixture regression reproduces the former boundary reset and proves it is removed;
16. BioLogic/reconstructed-cycle fixture regression proves the same generic transform works without source-specific logic.

Do not write a test that merely checks `np.diff(display_x) >= 0` for all data, because genuine within-segment source noise may exist. Tests should specifically assert the expected coordinates at known phase/cycle boundaries.
