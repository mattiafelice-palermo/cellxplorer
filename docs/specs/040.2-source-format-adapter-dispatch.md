## Goal

Convert the parser boundary from a Neware-specific implementation into a small, explicit **source-format adapter dispatcher**, while preserving the exact canonical output and import behavior of the already-supported Neware formats.

At the end of this child:

- `backend/app/services/parsing.py` is a format-neutral public facade rather than the sole Neware implementation;
- supported source formats are recognized centrally;
- Neware binary (`.nda/.ndax`) and structured Neware Excel (`.xlsx`) have explicit format IDs and adapter revisions;
- every full parse is validated against 040.1's canonical contract;
- metadata/header reads dispatch through the same format decision;
- user-facing extension acceptance remains exactly what Parent 039 established;
- cache/stitch/analysis consumers may still temporarily use the existing global parser bundle until 040.3; do not pre-implement the provenance migration here.

The purpose is to isolate **format recognition and source-specific parsing ownership** before changing cache/provenance semantics.

## Current verified behavior at the merge base

`backend/app/services/parsing.py` currently owns:

```python
NEWARE_NDA_VERSION = NewareNDA.version.__version__
EXCEL_PARSER_REVISION = neware_excel.EXCEL_PARSER_REVISION  # 6
PARSER_VERSION = f"{NEWARE_NDA_VERSION}-cxp{EXCEL_PARSER_REVISION}"
SUPPORTED_NEWARE_SOURCE_EXTENSIONS = frozenset({".nda", ".ndax", ".xlsx"})
```

and provides:

- `source_filename_allowed` for the shared extension policy;
- `source_parser_family`, returning `binary` or `excel`;
- `ensure_supported_source_metadata`, which rejects a structurally invalid `.xlsx` after bounded metadata inspection;
- suffix dispatch in `parse_timeseries`;
- source-owned post-parse validation through `validate_parsed_output`;
- suffix dispatch in `read_header_metadata` while keeping the fast `.ndax` XML path;
- one global bundle identity (`v2026.06.11-cxp6`) consumed by cache/provenance code.

`scanner.ingest_path` already relies on `source_parser_family` to reject exact-hash relinking across binary/Excel parser families. Preserve that safety behavior while generalizing the descriptor model.

`neware_excel.py` owns structured-workbook semantics and rejects generic Excel through its verified sheet/header contract. Metadata inspection remains bounded and does not parse the full `record` sheet.

## Target ownership

Keep the architecture intentionally small. Preferred shape:

```text
backend/app/services/
├── parsing.py                 # public format-neutral facade
├── canonical_cycling.py       # 040.1 contract
├── neware_excel.py            # existing 039 source-format owner (or landed equivalent)
└── ... existing Neware binary helpers / fast_neware ...
```

It is acceptable to extract a narrow Neware binary adapter module if that reduces `parsing.py` to a clear facade, for example:

```text
backend/app/services/neware_binary.py
```

Do not create a deep `plugins/` package or abstract base-class hierarchy unless the current code demonstrates a concrete need.

## Format IDs

Introduce stable internal source-format identifiers, conceptually:

```text
neware_binary
neware_excel
```

The exact spelling may be kebab/snake case, but once persisted in metadata/tests it becomes a compatibility contract.

The format ID is **not** the file extension:

- `.nda` and `.ndax` may share `neware_binary` if they are handled by the same adapter contract;
- `.xlsx` enters inspection by extension but is recognized as `neware_excel` only after structural checks;
- an arbitrary `.xlsx` must not receive a successful source-format ID.

## Adapter surface

Implement an explicit narrow representation of source-format behavior. A frozen dataclass or equivalent static registry is sufficient.

Conceptual fields/callables:

```python
format_id
extensions
adapter_revision
recognize(path)
parse_timeseries(path)
read_header_metadata(path)
```

Requirements:

- dispatch is deterministic;
- no dynamic loading/importlib plugin discovery;
- recognition is cheap enough for the existing bounded inspection path;
- recognition must not read the full cycling dataset merely to identify a format;
- full parse returns the 040.1 canonical DataFrame;
- full parse runs canonical validation before returning to downstream cache/scientific consumers;
- metadata read returns the current normalized header/capability contract.

## Recognition policy

### Neware binary

`.nda` and `.ndax` should follow the existing tested binary parser path. Extension may be sufficient because the underlying parser performs real format validation during header/full read; preserve current failure behavior.

### Neware Excel

`.xlsx` recognition must preserve Parent 039's structural contract. Do not classify a generic workbook as Neware simply by extension.

Use the existing cheap workbook/header recognition path. Do not open/stream all `record` rows during `read_header_metadata` or recognition.

### Unknown/unsupported source

Return/raise one clear unsupported-format result at the facade boundary. Preserve user-facing messages established by Parent 039 where appropriate.

Do not silently fall through to NewareNDA for a future unknown extension.

## Parser revision versus current global parser bundle

040.2 introduces source-format-specific **adapter revision information**, but 040.3 owns persistent cache/provenance changes.

Therefore this child should expose enough information for later code, conceptually:

```python
source_parser_descriptor(path) -> {
    "format_id": ...,
    "adapter_revision": ...,
    "canonical_raw_version": CANONICAL_RAW_VERSION,
}
```

but preserve the currently required global parser-bundle compatibility alias used by caches/provenance until 040.3.

If current code calls `parsing.PARSER_VERSION`, keep it valid in this child. Mark its role clearly as a transitional compatibility bundle, not the permanent per-source identity.

Do not change cache filenames or saved analysis provenance in 040.2.

## Error taxonomy

Prefer a small format-neutral error layer, conceptually:

```text
UnsupportedSourceFormatError
InvalidSourceFormatError / adapter-specific subclass
CanonicalCyclingError
```

Do not erase useful format-specific error detail. The facade should translate only enough for callers to present consistent user-facing messages.

A corrupt `.ndax` and an unrelated `.xlsx` are both parse failures, but their diagnostic messages may legitimately differ.

## Performance requirements

Preserve:

- no parser/scientific imports in list endpoints;
- lazy scientific stack behavior;
- bounded import inspection;
- cheap metadata path for `.ndax` and `.xlsx`;
- existing fast Neware binary optimizations;
- no inner multiprocessing/thread pools inside one adapter solely because a registry now exists.

Add a focused timing/regression check if dispatch introduces measurable overhead to the hot full-parse path. The target is essentially noise compared with actual parsing.

### Format IDs and adapter-revision scheme

```text
FORMAT_NEWARE_BINARY = "neware_binary"   extensions {".nda", ".ndax"}   adapter_revision = NEWARE_NDA_VERSION  (e.g. "v2026.06.11")
FORMAT_NEWARE_EXCEL  = "neware_excel"    extensions {".xlsx"}           adapter_revision = str(EXCEL_PARSER_REVISION)  (e.g. "6")
```

Both are instances of one frozen `SourceFormatDescriptor` dataclass (`format_id`, `extensions`,
`adapter_revision`) — a two-entry static registry, not a plugin framework. One shared
`_EXTENSION_FORMAT_ID` table built from those two descriptors drives `parse_timeseries`,
`read_header_metadata`, and `recognize_source`, so a suffix cannot be routed to a different format
by one function than another. `source_parser_descriptor(path)` returns
`{"format_id", "adapter_revision", "canonical_raw_version"}` (`canonical_raw_version` from
`canonical_cycling.CANONICAL_RAW_VERSION`, currently `1`) — exposed for Spec 040.3, not read by any
cache/provenance boundary yet. `parsing.PARSER_VERSION` (e.g. `"v2026.06.11-cxp6"`) remains the one
transitional global bundle every existing consumer reads; it is now documented in `parsing.py` as
built from exactly the two adapter revisions above, and `TransitionalParserBundleTests` in the new
test file asserts that composition directly rather than only asserting the value is non-empty.

### Recognition stays cheap; generic `.xlsx` stays rejected

`recognize_source` is extension-only for binary (NewareNDA performs real validation during its own
read, so a duplicate check here would only add I/O). For `.xlsx` it calls the existing
`neware_excel.is_supported_workbook`, which opens only the `record` sheet's header row via
`_header_map`/`_require_columns` — it does not read the sheet's data rows, so recognition stays
bounded even on the ~301k-row workbooks referenced in `state-and-performance.md`. `parse_timeseries`
and `read_header_metadata` deliberately do *not* call `recognize_source` themselves — they dispatch
by suffix through the same `_EXTENSION_FORMAT_ID` table, and `neware_excel.parse_timeseries`/
`read_metadata` perform the identical structural check as a side effect of the real (also bounded)
read, so a generic `.xlsx` is rejected exactly as before without opening the workbook header twice.
`FormatRecognitionTests.test_arbitrary_xlsx_is_not_recognized` proves `recognize_source` returns
`None` for a workbook with no Neware-shaped `record` sheet at all.

### Ambiguities / decisions

- The spec's illustrative `SourceFormatDescriptor` surface lists `recognize`/`parse_timeseries`/
  `read_header_metadata` as per-descriptor callables. Implemented instead as one shared
  extension -> format_id table (`_EXTENSION_FORMAT_ID`) plus module-level dispatch functions,
  because binary and Excel parsing/metadata already have materially different call shapes
  (`neware_excel.parse_timeseries(path)` vs. the private `_parse_neware_binary_timeseries(path)`
  helper) and embedding bound functions in a frozen dataclass would not simplify dispatch, only
  add indirection the spec's own minimalism guidance (no more than "a couple of small types")
  argues against.
- **Corrected below (follow-up round):** the original implementation record here said "did not add
  a new `InvalidSourceFormatError` class" on the grounds that the existing three unrelated exception
  trees (`parsing.UnsupportedSourceFormatError`, `neware_excel.NewareExcelError`/subclasses,
  `canonical_cycling.CanonicalCyclingError`) already covered every raise site and an unused class
  would be dead code. That reasoning held for two format families but not three: Parent 041 adds
  BioLogic `.mpr`, which would add a fourth unrelated exception tree with no shared catch surface, so
  a caller could only write `except Exception` to reject "any bad source, any format" — indistinguishable
  from a genuine adapter bug. See "Error taxonomy follow-up" below for what actually landed.
- Neither `neware_excel.py` nor `canonical_cycling.py` needed changes to satisfy this child's original
  tests or acceptance criteria at initial approval; both were rebased in the follow-up round below
  (`canonical_cycling.py` was not touched — see that section).

### Error taxonomy follow-up (post-approval)

During review follow-up (error-attribution question), the "Error taxonomy" section above was found
to be only partially implemented: three format-neutral base types were specified but the shipped code
had no shared base at all, only `parsing.UnsupportedSourceFormatError` and the independent
`neware_excel.NewareExcelError` tree. This follow-up completes that section without changing any
existing behavior, message, or the acceptance criteria of the original round.

**New module:** `backend/app/services/source_format_errors.py` — imports nothing from `parsing` or
`neware_excel` (verified by an AST-walking test,
`test_source_format_errors.HierarchyShapeTests.test_module_imports_nothing_from_parsing_or_neware_excel`),
which is required because `parsing` imports `neware_excel`, so the reverse would be circular. It
defines:

```text
SourceFormatError(ValueError)              # neutral base
├── UnsupportedSourceFormatError           # not a recognized source of this format
└── InvalidSourceFormatError               # recognized, but structurally broken
```

**`neware_excel.py` rebased**, `NewareExcelError(ValueError)` kept as-is (so every existing
`except NewareExcelError` call site is unaffected), with its two subclasses now multiply inheriting
from the matching neutral type:

```text
UnsupportedNewareExcelError(NewareExcelError, UnsupportedSourceFormatError)
InvalidNewareExcelError(NewareExcelError, InvalidSourceFormatError)
```

Measured MRO (Python's C3 linearization, both classes):

```text
UnsupportedNewareExcelError -> NewareExcelError -> UnsupportedSourceFormatError -> SourceFormatError -> ValueError -> Exception -> BaseException -> object
InvalidNewareExcelError     -> NewareExcelError -> InvalidSourceFormatError     -> SourceFormatError     -> ValueError -> Exception -> BaseException -> object
```

`NewareExcelError` sits ahead of the neutral types in both MROs, so `except NewareExcelError` still
catches both subclasses (`NewareExcelRebaseTests.test_adapter_specific_catch_still_works`), while
`except SourceFormatError` now also catches both uniformly
(`test_neutral_base_catches_both_neware_excel_rejection_types`), and `ValueError` remains in the MRO
so `scanner.py:843`'s `except (OSError, ValueError)` is unaffected
(`test_value_error_still_catches_every_type`, which reproduces that exact except-clause shape).

**`parsing.py`** no longer defines `UnsupportedSourceFormatError`; it imports and re-exports all
three neutral types from `source_format_errors`, so exactly one `UnsupportedSourceFormatError` class
exists (`ParsingReExportTests.test_parsing_unsupported_source_format_error_is_the_same_class` asserts
`parsing.UnsupportedSourceFormatError is source_format_errors.UnsupportedSourceFormatError` by
identity, not just equality). The module docstring's "Error taxonomy" note was rewritten to describe
the new hierarchy and to explicitly document why `canonical_cycling.CanonicalCyclingError` is *not*
part of it (an adapter bug producing an invalid canonical frame is categorically different from a bad
source file, and must stay loud rather than being catchable by `except SourceFormatError`).

**No message changed anywhere.** This is a type-hierarchy-only change:
`NewareExcelRebaseTests.test_error_messages_unchanged` asserts exact string equality on both
subclasses' `str()`, and `GenericXlsxUnchangedBehaviorTests` proves a generic `.xlsx` (no Neware
`record` sheet) still raises `neware_excel.UnsupportedNewareExcelError` with the exact message
`"Not a recognized Neware Excel export: required record sheet is missing."` both when calling
`neware_excel.parse_timeseries` directly and when reached through `parsing.parse_timeseries`'s
dispatch — same type name, same message, both before and after this change.

**Catch sites untouched.** `scanner.py` and `import_inspection.py` still catch bare `Exception`
everywhere they did before; this change makes narrower catching *possible* for a future caller, it
does not require refactoring any existing catch site, and none were touched.

**Tests:** `tests/test_source_format_errors.py`, 18 tests — hierarchy shape, the re-export identity,
both Neware Excel MROs and their catch behavior (neutral base, adapter-specific base, `ValueError`,
including the exact `scanner.py:843` except-clause shape), message-text equality, the generic-`.xlsx`
before/after-identical behavior through both entry points, and that `CanonicalCyclingError` is
deliberately excluded from the hierarchy.
