# 049.1 - Reviewed protocol-family grouping

**Status:** Implementation complete - review pending

**Parent:** [`049-protocol-family-comparability.md`](049-protocol-family-comparability.md)

## Goal

Extend the protocol-family comparison surface from a pairwise diagnostic into a reviewable
all-family grouping workflow. A scientist should be able to compare every initial family against a
pinned reference, see only the key differentiator for each candidate, name the proposed groups, and
make those groups available as protocol options in the editor.

## Scientific boundary

- The existing per-source semantic protocol signatures remain the authoritative identity.
- Applying a group does not merge source files, rewrite signatures, or store a synthetic protocol
  signature.
- A group stores analysis-local metadata: its name, member signatures, comparison basis, selected
  dimensions, and empty-rest/pause policy.
- When a grouped protocol is selected in the editor, reference step selections are mapped by
  comparable workflow order into exact source-local `(protocol_signature, step_indices)` targets.
- Applying a group is disabled unless Step flow and loops is selected. This prevents mapping a
  selection across families whose step order has not been compared.
- An empty Rest/Pause step is ignorable only when it has no current, C-rate, voltage, timing,
  recording, protection, or condition value. It remains visible in comparison evidence.

## User experience

The settings action beside the protocol selector opens a modal titled **Compare and group protocol
families**. The modal uses a split review layout:

1. a left control pane for Strict / Workflow / Custom, the reference family, comparison dimensions,
   the empty-rest/pause policy, and the result legend;
2. a right comparison matrix with a sticky Dimension and Reference column, one column per existing
   protocol family, horizontal scrolling for wide studies, and a concise first differentiator;
3. a full-width Proposed protocol groups area with editable names, included source families,
   truncated cell chips with hover titles, and the grouping evidence summary;
4. a single Apply grouped protocols action that persists the named grouping metadata.

The raw protocol families remain available for exact source inspection. Applied group options are
shown alongside them and selecting one drives the same source-local step editor.

## State contract

`AnalysisSpec.protocol_groups` is optional and backward-compatible. Each entry contains:

- `id`, `name`;
- `family_signatures` and `reference_signature`;
- `comparison_mode` and the six selected comparison dimensions;
- `ignore_empty_rest_pause`.

The analysis engine ignores this presentation/editor metadata. Scientific filters continue to read
the explicit targets in `protocol_segments` / `dcir_segments`.

## Acceptance criteria

1. The comparison modal shows all existing families against one selectable reference.
2. Candidate cells show `Same`, `Different`, or `Ignored` plus a compact differentiator, not the
   full duplicated evidence string.
3. Custom mode exposes termination conditions and the empty-rest/pause policy.
4. Proposed groups update when the mode, selected dimensions, reference, or empty-step policy
   changes; names remain editable per proposed membership.
5. Applying groups persists names and membership without changing source protocol signatures.
6. Applied groups are selectable in the segment editor and selections expand to exact source-local
   targets by comparable step order.
7. DCIR suggested-pair selection expands across an applied group using the same mapping boundary.
8. A group cannot be applied when Step flow and loops is not selected or protocol details are
   unavailable.
9. Empty Rest/Pause comparison and step mapping have focused tests; the existing semantic
   comparison tests remain green.
10. Frontend build and repository preflight pass. Browser verification remains delegated to the
    user unless explicitly requested.
