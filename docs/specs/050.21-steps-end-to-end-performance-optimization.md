## 1. Goal

Optimize the complete Steps analysis miss path using the 050.17 evidence, beginning with `step_blocks.per_block()` and then re-profiling to address every remaining stage whose route-level benefit is meaningful.

The child must preserve programmed-step/block ownership, CV classification, capacity/time totals, provenance, selected raw semantics and exact persisted cache hits.

Time/Capacity is out of scope.

## 2. Locked baseline

050.17 authoritative Steps measurements:

| Workload | p50 |
| --- | ---: |
| 1 Cell forced miss | **41.41 ms** |
| 6 Cells forced miss | **193.85 ms** |
| 6 Cells exact persisted hit | **14.17 ms** |
| dominant stage | `step_block_extraction` |
| dominant p50/share | **65.49 ms / 33.78%** |

The route is not critically slow, so production complexity must be proportionate. The objective is to remove obvious repeated work and then stop when the remaining gains are micro-scale.

## 4. Current hot-path hypothesis

`per_block(...)` currently performs several overlapping forms of DataFrame work:

- `assign_blocks(...)` sorts/resets/copies and normalizes step/record columns;
- status strings and masks are inspected;
- a further copy may be used for CV calculations;
- CV charge classification delegates to the established calc kernel;
- block groups are materialized/iterated;
- time/capacity helpers group/slice again, sometimes per step.

The likely optimization is fewer repeated groupby/slice/copy/conversion passes while retaining the existing calc semantics.

## 5. Locked scientific semantics

Preserve exactly:

- record-index continuity and block boundaries;
- programmed step labels/ownership;
- cycle/source labels;
- status-derived charge/discharge/rest interpretation;
- CV classification and capacity semantics;
- step/block time aggregation;
- charge/discharge capacity aggregation;
- selected segment/series filtering;
- deterministic result order/IDs;
- provenance/parser versions;
- selective-read fallback behavior.

Do not duplicate or approximate the CV scientific kernel merely to avoid a function call.

## 6. Required opportunity inventory

Use call/group/row counts.

Investigate stages around >=5% of six-Cell latency or >=10 ms, plus repeated passes whose combined cost is material.

## 7. Optimization tranche A — one normalized block representation

Preferred direction:

- sort/normalize the selected rows once;
- compute step/cycle/record arrays once;
- compute boundary/block IDs once;
- retain compact positional ranges or group codes rather than repeatedly copying group DataFrames;
- expose the exact data required by existing downstream science without rebuilding equivalent masks/groupings.

If `assign_blocks(...)` already produces all needed structure, refactor consumers to reuse it instead of recreating ownership.

## 8. Optimization tranche B — grouped time/capacity aggregation

After tranche A, re-profile.

Where material:

- combine time/capacity group reductions into fewer passes;
- avoid nested `groupby` when an already computed block/step code can drive vectorized/grouped reductions;
- reuse numeric capacity/time arrays;
- avoid repeated masks for the same charge/discharge step subset;
- preserve all NaN behavior and per-step semantics.

Use native Pandas/NumPy grouped operations already in the dependency set; do not add a new dataframe engine for this child.

## 9. Optimization tranche C — CV/status work and secondary route costs

Re-profile after grouped aggregation.

If CV/status classification is material:

- reuse normalized status/cycle arrays;
- call the existing CV kernel once at the broadest safe scope;
- avoid per-block recomputation of equivalent classification facts.

Then inspect:

- selective raw read/stitch cost;
- series filtering/planning;
- provenance/result assembly;
- serialization/SQL.

Do not optimize a sub-5 ms boundary merely to make the profile prettier.

## 10. Concurrency policy

The current six-Cell miss is under 200 ms and the dominant extraction stage is ~65 ms. Concurrency is **not expected** to be justified.

Only benchmark it if serial/vectorized cleanup still leaves >=100 ms of independent CPU-bound multi-Cell work. Otherwise keep Steps serial and simple.

## 11. Cache/version policy

Expected: no migration, no `CALC_VERSION`, no result-schema bump.

Exact result hits must not perform raw reads, block assignment, CV classification or aggregation.

## 12. Implementation order

1. Capture current Steps-only 1/6 baseline.
2. Add narrow `per_block` substage profiling if needed.
3. Implement tranche A and benchmark complete route.
4. Retain only if material.
5. Re-profile and implement tranche B.
6. Re-profile and implement tranche C only for remaining meaningful costs.
7. Avoid concurrency unless the explicit gate is met.
8. Run final benchmark, golden regression and preflight.
9. Record rejected changes.

## 13. Performance acceptance

Minimum expected target: **10%** reduction of the six-Cell forced-miss p50 from 193.85 ms, approximately **174.5 ms or better**, unless the deeper profile proves the 65.49 ms parent is already dominated by irreducible scientific work.

Continue past the target if low-risk measured savings remain; stop when remaining candidate savings are micro-scale or add disproportionate complexity.

Report 1/6 miss, hit, per-substage distribution, selected physical rows/row groups, SQL counts/time and response bytes.
