## Goal

Integrate the evidence-backed ordinary Time/Capacity performance architecture into the **real CellXplorer production path**. This child is not another benchmark-only exercise.

The user's primary product objective remains: ordinary `voltage_current` Time/Capacity interactions should feel effectively immediate, with an ambitious target of roughly **200 ms user-visible p50** for representative warm multi-Cell work where the host can support the optimized path.

By the end of this child, selected optimizations must be production code used by CellXplorer, with serial fallback, exact persisted-cache-hit bypass, scientific/provenance parity, deterministic ordering, Windows packaged-backend lifecycle safety, and bounded resources.

Derivatives are regression coverage only. Do not redesign the production architecture around derivative performance.

## Evidence from 050.13 that locks this architecture

The corrected 050.13 S25 development workload is accepted as representative for fast iteration: real six-Cell ordinary Time/Consecutive, compact/standard, 1200 px, about 20.5k selected rows/Cell and about 3.9k current display points/Cell before adaptive density.

Corrected 050.13 evidence:

- persistent 2-process whole-Cell work including **actual compact result IPC + unpickle + deterministic owner merge + final JSON body assembly**: about **249.65 -> 159.08 ms p50**;
- persistent 4-process equivalent: about **249.65 -> 122.64 ms p50**;
- output IPC for six Cells: about **2.88 MB**; immutable input descriptors: about **55 KB**;
- T18 adaptive display density: about **-26% projection** at 1200 px, returning about 2.35k points/Cell rather than about 3.9k while retaining cycle coverage and leaving full export unchanged;
- T3 request/owner resolved-state reuse: useful (~6% on its measured boundary);
- T4 shared scientific/source fingerprint: useful on the identity boundary (~45% boundary reduction; only a few ms complete-request value);
- T5 request-local validated stitch-plan reuse: useful on its measured boundary (~9%);
- T12 omission of redundant compact `time_s` when canonical `display_x` is present: useful (~6% projection), subject to frontend/export contract update;
- T1 phase omission on narrow ordinary Time + Consecutive: borderline useful (~5% projection) and safe only for that narrow consumer contract;
- T15 serializer experiment is small; T16 complete-route one-body strategy was only ~0.6% and does not justify a cache architecture rewrite by itself;
- T17 write-behind works mechanically but adds lifecycle/race complexity and is not selected;
- T6/T7/T8/T9/T10/T11/T14 were neutral/slower in corrected integrated tests and are rejected;
- corrected in-process Rust/Rayon gather/display preparation was slower than NumPy for the tested production-relevant boundary. Do **not** add Rust to production in this child.

## Locked production decisions

1. **Productionize the Python architecture.** No production Rust/PyO3/Rayon dependency for ordinary Time/Capacity.
2. **Use a persistent Python process pool for eligible broad ordinary Time/Capacity requests.** Four workers are the preferred broad-workload candidate when host resources support them; two workers are the bounded fallback; small requests remain serial.
3. **Workers receive immutable owner-resolved descriptors/cache plans only.** Never pass a live SQLAlchemy `Session`; never pickle full pandas DataFrames from owner to worker. Each worker reads its own indexed cache data and returns only the compact final per-Cell result needed for deterministic merge.
4. **Exact persisted result-cache hits bypass everything.** A direct result-cache hit must not resolve/dispatch process jobs, read Parquet, or execute scientific transforms.
5. **Resolve relational/scientific owner state once per miss request** and reuse it for capability/selection facts, cache identities, stitch plans and worker descriptors where the existing contracts allow it. No unbounded cross-request ORM cache.
6. **Derive scientific and render cache keys from one shared authoritative fingerprint pass** while preserving exact existing key values and direct-hit semantics.
7. **Reuse request-local validated stitch plans** while retaining the actual indexed-read publication/freshness recheck and safe fallback behavior.
8. **Adaptive density is display-only.** Full precision/non-compact export remains exact and unbounded by display point budgets.
9. **Compact ordinary Time/Consecutive may omit redundant data only after updating all real consumers.** In the narrow path, canonical `display_x` may replace transmitted `time_s`, and phase may be omitted/empty only where frontend rendering/export does not consume it. Overlap/reset, overlap/mirror, derivatives and full export retain required arrays.
10. **Do not add T16/T17 cache lifecycle complexity or a new serializer dependency unless post-integration profiling proves it materially necessary.** First integrate the high-value architecture above and remeasure.
11. **No `CALC_VERSION` bump** for scientifically equivalent performance work. If the compact response schema changes, use the repository's response/cache schema-version mechanism so stale cached compact bodies are not misinterpreted.
12. Preserve source provenance, continuation semantics, voltage-channel semantics, protocol masking, saved-plot behavior, autosave/draft behavior, light/dark UI behavior and full-resolution export fidelity.
13. Never modify, reset or discard unrelated branch work.

## Part A — production owner/request context

### A1. Extract/reuse the existing whole-Cell worker boundary

Do not import benchmark scripts from production.

Create the smallest backend service-level representation needed to execute one Cell without ORM state. Reuse the proven 050.9/050.13 shapes where appropriate:

- immutable resolved Cell metadata;
- ordered source descriptors/version facts;
- validated indexed stitch plan and requested cycles;
- requested raw/derived columns;
- compact rendering settings and voltage facts;
- source/provenance facts required to assemble the final Cell trace.

The owner request must resolve these once. The per-Cell function must be callable both:

- directly in-process for serial fallback/small jobs;
- in a spawned persistent worker process.

There must be one scientific implementation, not separate serial and process algorithms that can drift.

### A2. Shared owner fingerprint

Refactor the cache-key path so the expensive scientific/source/unit fingerprint is built once on a miss request and both existing keys are derived from it:

- scientific/data signature;
- render-specific result key.

Acceptance requires **exact key equality with the pre-050.14 implementation** for representative fixture/application requests. Do not silently invalidate all caches merely for performance.

### A3. Request-local plan reuse

Build validated Time/Capacity stitch plans once per resolved Cell and reuse those plans for worker descriptors/serial execution. Keep the indexed read's actual freshness/publication check (`wait_for_layout`/equivalent current safety boundary) so cache replacement races still fall back safely.

Do not introduce a long-lived mutable plan cache unless separately justified; request-local reuse is sufficient.

## Part B — persistent Python worker pool

### B1. Lifecycle

Implement a backend-owned persistent process-pool service for ordinary Time/Capacity.

Requirements:

- Windows `spawn` safe;
- compatible with the existing packaged entrypoint's `multiprocessing.freeze_support()`;
- no recursive server/app startup in workers;
- worker functions/import targets are top-level and pickle-safe;
- startup/import/warmup occurs **off the interaction critical path**. Prefer asynchronous/lazy background warmup after backend startup rather than adding ~1-2 s to the first eligible plot interaction;
- deterministic clean shutdown;
- if worker initialization fails, log once and use serial fallback rather than failing scientific requests;
- if a worker dies during a request, fail closed to the serial path for that request or retry once in owner according to the simplest safe existing error pattern; do not return partial scientific results.

### B2. Worker count and host gating

Four workers are preferred only when the host can support them. Determine the smallest deterministic runtime rule using already-known host facts and the fast S25 measurements.

At minimum benchmark/validate:

- serial: 1 Cell cycles 1-3;
- serial versus process: 3 Cells S25 Time;
- serial versus process: 6 Cells S25 Time;
- 6 Cells S25 Capacity;
- 2-worker and 4-worker candidates on the eligible broad cases.

A reasonable starting rule is:

- small requests: serial;
- broad multi-Cell requests: four workers on hosts with sufficient logical CPUs/memory;
- otherwise two workers;
- if resource detection is unavailable or pool is unhealthy: serial.

Do not use timing-history or ML heuristics. The final gate should be based on deterministic request/host facts such as resolved Cell count, selected-row estimate, logical CPU count and available/total memory.

### B3. Memory measurement

050.13 could not report RSS because `psutil` was unavailable. Before selecting four workers as the default eligible path, measure real parent + worker RSS on the Windows development host.

Do this in benchmark/test tooling without forcing a new production dependency if practical. On Windows, a small `ctypes` process-memory helper is acceptable. Record:

- parent RSS;
- each worker RSS after warmup and during S25 6-Cell Time;
- total backend+workers RSS;
- 2-worker versus 4-worker delta.

Choose four workers only if the memory footprint is reasonable for a desktop application and there is no evidence of paging/host pressure. Otherwise choose two as default and retain four only behind a stronger host gate.

### B4. Bounded dispatch

Do not create unbounded speculative/background work.

- Only dispatch on an actual cache miss requiring computation.
- Submit at most the Cells belonging to that request.
- Preserve selection order in owner merge.
- Cancel futures that have not started if the owning request aborts/fails where the current stack exposes that signal; do not build a complex cross-request scheduler in this child.
- Do not parallelize derivatives merely because the pool exists. This child gates production process execution to ordinary `voltage_current` Time/Capacity where 050.13 evidence applies.

## Part C — compact ordinary response and adaptive display density

### C1. Omit redundant `time_s` for compact Time/Consecutive

For the narrow production path:

```text
view=voltage_current
x_axis=time
display_mode=consecutive
compact=true
precision=standard
```

`display_x` is canonical. Update frontend types/consumers so the compact response does not need to gather/round/create/transmit a redundant `time_s` array.

Requirements:

- `timeCapacityX()` must use `display_x` without first requiring `time_s`;
- hover, saved plot, PNG/SVG/vector export and plot-data export from the compact rendered result must remain correct;
- full-resolution/non-compact scientific export retains `time_s` exactly;
- overlap modes retain whatever raw time representation they require.

### C2. Omit phase only for the narrow consecutive consumer

For the same narrow Time/Consecutive compact path, avoid `_phase_from_raw()` and avoid transmitting a full phase array if no real consumer requires it.

Requirements:

- frontend segment construction must treat consecutive mode as one segment without reading phase;
- overlap/reset, overlap/mirror, derivative and full-export paths retain phase exactly;
- response typing/schema explicitly permits the narrow omission rather than relying on accidental undefined behavior;
- scientific cache/result schema compatibility is handled intentionally.

If implementation or regression evidence shows that preserving a tiny placeholder phase field is materially simpler than schema omission, it may be retained only if the expensive classification itself is still skipped.

### C3. Adaptive point budget

Productionize T18 with a deterministic rule that uses **viewport width and resolved visible Cell count**, not viewport alone.

Use the measured 050.13 six-Cell behavior as the reference:

- 600 px / 6 Cells -> about 1.2k points/Cell;
- 1200 px / 6 Cells -> about 2.4k points/Cell;
- 2400 px / 6 Cells -> current cap (~4k points/Cell).

A simple starting rule that matches that evidence is a bounded total display budget equivalent to roughly **12 viewport-widths of points across visible Cells**:

```text
per_cell_budget = clamp(
    floor=800,
    ceiling=current max_points_per_cell,
    value=(2 * viewport_width * 6) / max(visible_cell_count, 1)
)
```

This is a starting production candidate, not a sacred formula. Adjust only if fast S25/browser evidence shows a clearer safe rule.

Always force required extrema/source boundaries/mandatory points exactly as the existing downsampler does. Full precision/non-compact export ignores this adaptive budget.

### C4. Visual acceptance

Because adaptive density changes displayed sampling intentionally, perform a manual/browser visual check before review handoff if the environment permits it:

- 1 Cell and 6 Cells;
- 600, 1200 and 2400 px representative widths;
- broad Time plot with visible peaks/transitions;
- ensure no visually meaningful extrema/source transitions disappear;
- verify zoom/hover remains usable.

If browser automation cannot run in the environment, state that explicitly and provide the exact manual checklist; do not claim visual validation passed.

## Part D — result assembly, cache and fallback

1. Owner merge must preserve original resolved selection order exactly.
2. The production process result must be scientifically digest-equivalent to the serial result for the same response representation.
3. Source cycle/position/filename/hash provenance required by the active compact frontend/export contract must remain exact.
4. Direct persisted cache hits must return through the existing fast body-splice path without process-pool dispatch.
5. A pool-disabled/unavailable host must produce exactly the same result through the serial implementation.
6. Do not adopt T16/T17 by default; 050.13 showed only ~0.6% complete-route benefit for one-body encoding and write-behind adds lifecycle complexity. Reprofile after the high-value production stack is integrated. Only implement a further serialization/cache change if the **post-integration** complete route still shows >=5% or >=5 ms stable benefit and the change remains simple.
7. Do not add `orjson` or another serializer to production solely because its microbenchmark was faster. Same post-integration gate applies.

## Implementer record — 2026-08-23

Implementation is ready for independent review. The real production route now
uses `backend/app/services/time_capacity_workers.py` for the narrow ordinary
`voltage_current` / standard / compact path when indexed caches are current.
The owner resolves source identities, scalar metadata, immutable descriptors and
stitch plans once; spawned workers receive only pickle-safe `ReadJob` and
`ResolvedRequest` values, reopen indexed caches, and return per-Cell results for
selection-order merge. Startup warmup is asynchronous and shutdown is explicit.
Legacy, unsupported, stale or failed worker paths return to the established
serial engine without partial results.

from one owner pass. Compact consecutive Time uses `display_x` directly and
skips phase classification and redundant `time_s`; overlap/alternate paths and
full/non-compact output retain their required arrays. The adaptive budget is
`clamp(800, configured_max, floor((2 * viewport_width * 6) /
max(visible_cells, 1)))`. The response profile records execution mode, gate
reason, IPC, effective cores, parent/worker RSS samples and combined backend RSS.
