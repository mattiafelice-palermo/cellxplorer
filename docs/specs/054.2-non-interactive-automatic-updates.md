# Spec 054.2 — Non-interactive automatic updates

> Repository snapshot used while drafting: `main` at `e396a32f86a4bfd8f4ed9c547096a08bc397d911` (2026-08-26).
> Re-verify anchors against the implementation branch before coding, especially if Spec 053 has merged.

## Parent

`054-updater-lifecycle-hardening.md`

## Dependency

**054.1 must be accepted first.**

This child must also consume the final release-channel configuration from Spec 053.

## Goal

When the user chooses to update CellXplorer from inside the application, apply the verified update without opening the normal interactive installer wizard.

The desired interaction is:

1. CellXplorer reports that an update is available.
2. The user chooses to update.
3. CellXplorer downloads the update and shows progress.
4. CellXplorer applies it without further installer prompts/pages.
5. The target application exits/restarts as required.
6. The user's channel-specific data remain intact.

The user should not have to click through NSIS pages for an ordinary in-app update.

## Locked decisions

- The existing full installer remains available for fresh/manual installation; this spec changes the **in-app updater mode**, not the standalone installer experience.
- The user must still explicitly initiate the update.
- The in-app updater's Windows installer mode must be non-interactive/silent enough that the NSIS wizard is not presented.
- CellXplorer's own modal/progress UI is the user-facing update surface.
- Do not hide failures. Download/install errors must return to an actionable application state whenever the process is still alive.
- Do not reset user data during an update.
- Stable, Beta, and Alpha retain separate data roots and install identities.
- Do not add a bespoke second update engine if Tauri's supported updater install mode can provide the required behavior.
- Do not bypass updater signature verification.
- Do not add a generic rollback framework in this child.
- Do not silently discard unsaved analysis work. If the current application already has a leave/dirty guard that can be reused safely before the irreversible install step, use it; otherwise the updater must at minimum make the impending restart/exit explicit before installation begins. Do not create a broad analysis-editor refactor.

## Current behavior and anchors

### Tauri updater configuration

`src-tauri/tauri.conf.json` currently contains:

```json
"plugins": {
  "updater": {
    "...": "...",
    "windows": {
      "installMode": "basicUi"
    }
  }
}
```

`basicUi` is the current reason the Windows update application path may surface installer UI.

Channel-specific Tauri configurations must be inspected as well. All release channels should use the same intended in-app updater behavior unless a documented platform/channel limitation requires otherwise.

### Backend update state

`src-tauri/src/app_updates.rs` already separates:

- checking (`check_app_update`);
- downloading (`download_app_update`);
- verified bytes held in `PendingAppUpdate`;
- installation (`install_app_update`);
- restoration of pending update state when `update.install(&bytes)` returns an error.

Preserve this state machine and its version/signature validation.

### Frontend coordination

Relevant files:

- `frontend/src/appUpdater.ts`;
- `frontend/src/components/AppUpdateCoordinator.tsx`;
- `frontend/src/components/AppUpdateModal.tsx`.

The current frontend already has download/progress concepts. Reuse these rather than adding a second progress flow.

### Application exit

The updater builder installs an `on_before_exit` hook that calls:

`prepare_exit_for_update(&app)`

which marks lifecycle quitting and stops the tracked backend.

Preserve the channel-isolated behavior established by 054.1.

## Target behavior

### A. Update available

The current update-available presentation may remain visually consistent with existing UI.

Before the irreversible application step, the user must understand that CellXplorer will close/restart to finish the update.

### B. Download

While downloading:

- show determinate progress when content length is available;
- otherwise show an indeterminate but visibly active state;
- prevent duplicate update starts;
- keep cancel/close behavior consistent with what the current state machine can safely support;
- a download failure leaves the app running and offers a retry path.

### C. Apply

After verified bytes are available and the user has chosen to proceed:

- invoke the updater in non-interactive Windows mode;
- do not open ordinary installer pages;
- do not ask install-directory, start-menu, desktop-shortcut, or similar fresh-install questions;
- stop only the target channel's processes;
- preserve the existing installation location;
- preserve user data.

The frontend should transition to a clear "Applying update…" state before the process exits.

### D. Relaunch

Use the updater/Tauri behavior that is already supported by the repository and platform.

Target outcome:

- successful update results in the new version becoming the next running instance without the user manually navigating an installer;
- if automatic relaunch is not reliable in the current Tauri/NSIS path, the application may exit after a clearly completed install and require a normal launch, but this fallback must be explicitly documented and manually verified.

Do not invent a parallel relaunch mechanism unless needed and proven by packaged testing.

### E. Failure before process exit

If `install_app_update` returns an error while the application is still alive:

- restore/retain the verified pending bytes as the current Rust code allows;
- surface a concise error;
- let the user retry installation without redownloading where safe;
- do not mark the update as complete.

### F. Failure after installer takeover

If Windows updater takeover requires the current process to exit and a later failure cannot be returned to the old frontend:

- preserve installation/data safety;
- rely on the installer/updater's supported failure semantics;
- document what the user sees;
- do not add destructive cleanup.

## Data-preservation requirements

An update must not delete or replace channel data roots:

- Stable data root;
- Beta data root;
- Alpha data root after Spec 053.

The application may run ordinary forward-only schema migrations on next launch when required by the new build. This spec does not change migration semantics.

Explicitly verify that:

- analyses remain listed;
- saved plots remain present;
- settings/channel preferences remain present where they currently persist;
- updating one channel does not touch another channel's data root.

## Configuration requirements

Change the Windows updater install mode from the current `basicUi` to the appropriate Tauri-supported non-interactive mode.

Apply the setting consistently to:

- Stable config;
- Beta config;
- Alpha config from Spec 053.

Do **not** change the standalone NSIS bundle's intended fresh-install mode merely because the updater artifact uses a silent mode.

## Tests

### Static/config tests

Extend existing release/config consistency checks, or add focused ones, to assert:

- all supported channels use the intended updater install mode;
- channel configs still point to their own endpoints/identifiers;
- updater artifacts remain enabled;
- no channel accidentally inherits another channel's endpoint or identifier.

### Rust tests

Preserve and extend `app_updates.rs` tests around:

- install readiness;
- version mismatch;
- missing verified bytes;
- retryable install state after pre-hook/install errors;
- channel-specific version validation.

### Frontend tests

Add focused tests for the coordinator/modal state machine where practical:

- download progress updates the UI;
- applying state disables duplicate actions;
- download failure produces retry state;
- install failure returned to the frontend produces retry state;
- update initiation does not mutate unrelated application state.

Do not build a browser-level installer simulation in frontend unit tests.

## Packaged manual verification

Required on Windows.

For at least one real signed updater artifact per available channel configuration:

1. install an older build;
2. create/confirm representative application data;
3. make a newer valid update available;
4. launch the old build;
5. initiate update from CellXplorer;
6. verify progress appears in CellXplorer;
7. verify the normal NSIS wizard **does not appear**;
8. verify the application exits/relaunches as expected;
9. verify the new version is running/installed;
10. verify representative data remain present;
11. verify another concurrently running channel remains alive (cross-check 054.1);
12. exercise a download or controlled install failure if practical and record behavior.

## Acceptance criteria

- In-app Windows update no longer presents the ordinary interactive installer UI.
- User sees clear download/apply progress in CellXplorer.
- Duplicate update actions are blocked while one is active.
- Signature/version validation is unchanged or stronger.
- Successful update installs the requested release into the current channel installation.
- Existing channel data are preserved.
- Other channels remain unaffected.
- Failure before process exit is surfaced and retryable where the existing verified-byte state permits it.
- Current canonical preflight passes.
- Packaged Windows verification is recorded.

## Out of scope

- fully automatic unattended background updates;
- update scheduling;
- delta updates;
- rollback snapshots;
- redesign of release publishing;
- redesign of the standalone installer;
- unrelated app lifecycle refactors.
