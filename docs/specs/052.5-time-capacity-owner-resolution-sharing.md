# 052.5 — Time/Capacity owner-resolution sharing

**Status:** Active child — implementable
**Parent:** Spec 052 — Time/Capacity cycle navigation
**Repository:** `mattiafelice-palermo/cellxplorer`
**Branch:** `feature/time-capacity-cycle-navigation`
**Reason for child:** explicit user decision after 052.4. Profiling of the remaining time-axis budget showed the Time/Capacity route resolving the same owner-side state four times per request, while the mechanism built to prevent exactly that — `AnalysisRequestContext` — was already in use by every other analysis family.

## Goal

Resolve owner-side request state once per Time/Capacity request instead of four times, **without changing any scientific output**.

## Verified current facts that constrain the implementation

Measured on this branch after 052.4, six-Cell ten-cycle time-axis request, call counts instrumented at the route boundary:

| function | calls | total |
|---|---|---|
| `resolve_selection` | 4 | 1.49 ms |
| `preload_cell_sources` | 4 | 4.95 ms |
| `canonical_cycling_capability` | 2 | 4.52 ms |
| `load_scalar_metadata` | 2 | 0.51 ms |
| | | **12.54 ms (17% of the request)** |

Facts:

- `AnalysisRequestContext` exists for this purpose and is documented as request-local and never retained across requests. `analysis_family_workers` already uses it for cycles, steps, DCIR and chargeability; Time/Capacity was the outlier.
- `_result_fingerprint_payload` and `ensure_canonical_cycling_available` already accept `request_context`. `time_capacity_keys` and `_build_jobs` did not.
- The context must be built **before** the result-cache lookup, because `time_capacity_keys` needs the same resolution in order to compute the key at all. Building it early therefore costs nothing extra — it is the same work, performed once.
- The context holds live ORM objects and must never be passed to a worker process. Only the immutable descriptors built inside `_build_jobs` cross that boundary.

## Stages

### Stage 1 — Thread the context through the Time/Capacity path

- build one `AnalysisRequestContext` at the top of `compute_time_capacity_analysis`, under its own `owner_request_context` profiling stage;
- pass it to `_guard_canonical_cycling`, `analysis_cache.time_capacity_keys`, and `engine.compute_time_capacity`;
- add a `request_context` parameter to `time_capacity_keys` (passthrough to `_result_fingerprint_payload`), `compute_time_capacity`, `try_compute_time_capacity`, and `_build_jobs`;
- inside `_build_jobs`, take `units`, `missing_refs`, `scalar_metadata` and the per-Cell `files`/`hashes`/`parser_versions` from the context when present;
- **every context parameter stays optional**, preserving the existing direct-service fallback when no context is supplied.

### Stage 2 — Voltage-capability header decode: REJECTED, recorded

`preload_cell_sources` deliberately defers `SourceFile.header_meta` because it holds megabytes of raw instrument header that no interactive request needs. `_persisted_voltage_capabilities` then reads that attribute, firing a lazy load and a full JSON decode per source file, once per request — roughly 4–5 ms on a six-Cell request — to retrieve one small dict. The deferral is defeated.

Memoizing the extracted value across requests was implemented and then **backed out**. There is no safe key:

- `parsing.py` rewrites `source.header_meta` in place near the BioLogic MPR cycle-verification helpers **without** changing `parser_version`, `hash`, or any other observable column;
- the content hash therefore does not prove freshness, and neither does the parser identity;
- the failure mode is a stale voltage capability, which mis-resolves voltage roles and reference electrodes — a scientific labelling error.

This was caught by the existing suite: `MultiVoltageTimeCapacityTests` passed in isolation and failed in-suite, because the memo served one case's capabilities to another.

The safe fix is to persist the small capabilities dict in its own column, written wherever `header_meta` is written, leaving the deferral intact. That needs a migration and belongs in its own child. A `NOTE` at `_persisted_voltage_capabilities` records this so the next reader does not re-attempt the unsafe version.

## Non-goals

- No cross-request caching of owner-side resolution. Everything here is request-local.
- No schema migration.
- No change to the navigator, the dispatch gate, or scientific transforms.

## Verification requirements

- **Scientific parity is mandatory and blocking**, proven with `scientific_digest` over the `scripts/profile_time_capacity_request_overhead.py` matrix.
- A regression test pinning `resolve_selection`, `preload_cell_sources` and `load_scalar_metadata` to exactly one call per request.
- Canonical preflight.
- Browser/manual acceptance recorded truthfully as RUN or NOT RUN.

## Results

Owner-side resolution per request:

| function | before | after |
|---|---|---|
| `resolve_selection` | 4 calls | **1** |
| `preload_cell_sources` | 4 calls | **1** |
| `load_scalar_metadata` | 2 calls | **1** |
| `canonical_cycling_capability` | 2 calls, 4.52 ms | 2 calls, **0.03 ms** (context-served) |
| total | 12.54 ms | **3.16 ms** |

End-to-end, warm 6-worker pool, 9 repetitions:

| Workload | 052.4 | 052.5 | Change |
|---|---|---|---|
| single-cell explicit cycles | 31.1 ms | 28.2 ms | −9.1% |
| six-cell full range, time | 86.3 ms | 80.2 ms | −7.1% |
| **six-cell moving preview (time)** | **41.4 ms** | **34.6 ms** | **−16.6%** |
| six-cell moving preview (capacity) | 69.6 ms | 59.5 ms | −14.6% |
| six-cell full range, capacity | 371.3 ms | 380.8 ms | +2.6% |
| six-cell derivative | 306.8 ms | 306.5 ms | −0.1% |

Scientific digests identical on every workload. The capacity full-range row is within run-to-run noise for that workload.

Time-axis moving preview across 052.3–052.5: **112.5 ms → 34.6 ms**, roughly 8.9 → 28.9 fps.

## Outstanding

- Stage 2 not implemented; the ~4–5 ms header decode remains, and the safe column-based fix is unscheduled.
- Measured on one host only; browser/manual acceptance NOT RUN.
